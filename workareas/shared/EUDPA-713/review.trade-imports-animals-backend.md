## Summary
The PR makes five changes:
- `NotificationAggregate` gets an `organisationId`, set once on create.
- A new `TraderOrganisationHeaderFilter` rejects trader requests that have no `Trade-Imports-Organisation-Id`.
- Every trader read and write uses a repository finder that filters by organisation.
- Reading another organisation's fulfilments returns 403.
- Three of the seven document routes now check the organisation.

The core scoping is correct. The problems are in the code and tests around it.

## Positive Observations
- Every trader read and write goes through one helper, `requireTraderNotification`. It filters by organisation in the query, not after the read, as the tech notes ask.
- Only `createNotification` sets the organisation. Replace, amend and copy cannot change the owner, and a copy belongs to the caller.
- `NotificationIT` has real cross-organisation tests: 404 on amend, replace, submit, copy and soft-delete, 403 on fulfilments, and an empty result for the scoped search.
- The admin routes stay unscoped, as the ticket says, and the animals admin app still works.

## Test Coverage
- **Unit tests: partial.** The service and controller tests use the new signatures, but several checks cannot fail:
  - `requireTraderAccess` is stubbed to do nothing.
  - The tests send the same organisation in the header and the body.
  - No test calls the admin routes without the header, so the exemptions are untested.
- **Integration tests: partial.** `NotificationIT` covers the main cross-organisation cases. It does not cover cancel-amend, the dashboard list without a reference number, the document routes or the indexes.

## Risk Assessment
**Overall Risk:** Medium
**Rationale:** The notification scoping is right, but three things are open:
- Four document routes that take an upload id have no organisation check.
- The Actor is still built from the request body.
- Several acceptance criteria have no test that can fail.
