## Colleague lens: findings (window 2026-10-02 to 2026-10-16; current factory)

### Bottom line
1. The clearest in-window example of what "readable" means to this team is PR #396 (animals-frontend). It was not an obligation-model PR. Its author first had it reviewed with the `review` skill, which raised 16 findings and none about naming or comments. Four days later the author made 14 readability-only commits with Claude. So the review tooling cannot see the problem the colleague describes.
2. The "reluctant to remove" habit is confirmed in the window (PR #390, 2026-10-06). When a reviewer flagged a comment, the agent reworded it, spread the new wording to more places, added comment lines, and declined the rename. The fixer personas say "minimal change", and nothing in them says "delete the comment" or "rename instead".
3. The best-practice docs themselves model the habit the colleague complains about. Their "good" comment example describes Hapi's behaviour at the call site. The naming rule bans one-letter names, yet the house code uses `h` about 200 times.
4. Patterned work did look cleaner, but almost no in-window work was patterned. Nearly every Design Release 2.1 plan states "No add-a-* recipe applies".
5. Logging: the main problem is that there is none, more than that it lacks context. `src/server/app` in animals-frontend has zero log calls on main. The in-window lines that were added are mostly infrastructure, and several break the repo's own logging guide.

### 2. "Even when I protest, it's reluctant to remove"
- **Inline review comments are almost absent.** Since 2026-09-15, animals-frontend had 1, plants-frontend 0, ins-frontend 0, address-book 0, animals-backend 3. Review happens in-session or through `review` skill tables posted as PR comments.
- **Clearest in-window case, PR #390** (another colleague, dates). The `review` handoff on 2026-10-06 (issuecomment-6015744021) flagged "The asUtcInstant comment says a date-only arrival date becomes midnight UTC, which this ticket forbids in comments."
  - The agent's reply (issuecomment-6016571042) and commit e9ad6cda (2026-10-06, `Co-Authored-By: Claude Opus 5.5 (1M context)`):
    - "**Reworded** … The same wording … appeared in a few places the review did not list, so I changed those too."
    - It **added** comment lines: the `EAST_OF_UTC` JSDoc in `calendar.test.js` grew from 1 line to 6, and an inline test comment grew from 3 lines to 5.
    - It **declined** renames: "Left as they are: the `asUtcInstant` function name … the `ARRIVAL_INSTANT` test constant name". The finding was treated as a wording error to patch, not as a reason to ask "why is this comment here?"
- **All `review`-skill tables posted on animals-frontend from 10-05 to 10-13** (PRs #388, #390 ×2, #396, #397, #395, #409): 55 findings.
  - Naming: 0.
  - Comment-related: 6. Every one is about whether a comment is *accurate*: stale-comment ×3, misplaced doc-comment ×1, ac-comment ×1, a pointer into `workareas/` ×1. None says "delete this" or "rename instead".
  - Where a stale comment was fixed, the fix was a deletion only when the comment was obviously dead: deee9e5a (2026-10-12), "drop stale postcode rename comment".
- **What the skills tell a fixer to do** (versions 9288350d/6b6835b1, 2026-09-29, in force throughout the window):
  - `review/references/REVIEW_ITEM_FIXER.md:55`: "Make the **minimal** change required". For a comment finding, the minimal change is a reword.
  - `code-style/references/STYLE_IMPLEMENTOR.md` Step 3: "Make the **minimal** change for each item".
  - `code-style/assets/style-implementor-cheat-sheet.md:19-25`: fix patterns for rules 2, 5, 6, 12 and 13 only. There is **no pattern for rule 15** (comments), so nothing says "delete, or rename or extract instead".
  - `review/references/FILE_REVIEWER.md:181-182` lists correctness, bugs, null safety, error paths, security, performance and tests. Lines 259-261 exclude "Could be more SOLID/DRY/clean without a concrete fix" and "Stylistic preferences not in a best-practices file". The skill routes style to `code-style`, but the colleague ran only `review`.
- **The only "remove aggressively" rule is in the build loop's own style-review prompt.** `increment-build-loop.js:3850-3853` (introduced 75105948, 2026-09-22) says: "comments are removed aggressively … no migration/rename comments … names say what a thing does". Interactive sessions and the `review`/`code-style` skills used by colleagues never see it.
- **The docs teach the anti-pattern.** `docs/best-practices/node/code-style.md` §15 (361722f1, 2026-04-28) gives this as its *good* "why" example: `// Hapi validates the full payload before route handlers run, so by the time we reach here the token is guaranteed present.` That is exactly "describing the behaviour of an api at call site".
  - §6 says "Never use single-character variable names", but animals-frontend main has about 200 `(request, h)` signatures against 16 `(request, toolkit)`. The 16 are only in the files PR #396 touched. Agents follow the surrounding code, not the doc, and the cleanup has now created two conventions.
  - `doc-comments/BEST_PRACTICES.md` says "Absence is not a violation. Present-but-wrong is." That makes accuracy, not existence, the reviewer's test.
