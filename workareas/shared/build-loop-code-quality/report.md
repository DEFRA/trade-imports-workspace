# Build-loop code quality: root causes

Scope: the requirements-pipeline BUILD phase (`.claude/skills/requirements-pipeline/workflow/increment-build-loop.js`, its Codex briefs, the personas and best-practices it points at), tested against the DR2.1 build (`workareas/shared/design-release-2-1/`, landed on `feat/NO_JIRA-design-release-2-1-combined` in plants-frontend and the EUDPA-69x theme branches in animals-frontend) and the earlier high-risk-plants and parity programmes. Eight investigations, each finding re-checked by a sceptic. Confirmed findings are weighted above partial ones; refuted ones are listed at the end. Every DR2.1 theme ran with `executor: "claude"` (`themes/*/build-args.json:6`); no Codex-built code has landed in any repo.

Workflow run: `wf_e406c706-419` (2026-10-16). Per-angle evidence and sceptic verdicts are in that run's `journal.jsonl`.

## Summary

1. **The written standard permits the comments Sam objects to, and the loop's stricter rule lives in one prompt.** `docs/best-practices/node/code-style.md:409` ("Comments are appropriate for **why**") and `doc-comments/jsdoc.md:9-12` license rationale comments and JSDoc on exports; `doc-comments/BEST_PRACTICES.md:14` says "Absence is not a violation. Present-but-wrong is." The Java test guides (`java/testing/unit.md:283`, `integration.md:141`) *mandate* `// Given / When / Then`. Sam's "comments are removed aggressively" rule exists only in the style-reviewer prompt (`increment-build-loop.js:3850-3852`) and his uncommitted memory. The planner, implementor, verifier, judge, fixer and all three Codex briefs never see it.
2. **The adversarial verifier is where comment and naming findings die.** The style reviewer does raise them (~200-340 across the DR2.1 journals). The verifier (`:4022` "Default to refuted"; `:4039-4043` judge "against the house conventions the repo actually follows (find a comparable file and compare)" and refute "a matter of taste") refutes about three in four, citing neighbouring AI-written comments as the convention or rule 15's "why" allowance. The judge is not the leak: 77 of 78 comment findings reaching it were fix-now.
3. **The planner writes comments into the plans and the implementor follows them verbatim.** 36-40 of 40 DR2.1 plans contain comment or JSDoc instructions (e.g. `plans/inc-187.md:99`, `inc-111.md:112`, `inc-027.md:107-114`, `inc-001.md:44-86`); the implementor is told "Follow it verbatim" (`:3711`). The planner prompt (`:2338-2390`) has no comment rule and tells it to "keep the existing doc-comment style" by exemplar (`inc-001.md:13`). Implementors also add unplanned JSDoc by copying exemplars (`:3712` "copy its shape").
4. **The standards hand-off is broken end to end, but fixing it alone will not remove the comments.** Sam's suspicion is right about delivery (0 of 47 DR2.1 implementors read `code-style.md` via Read; the plan template has no standards slot; the style persona's rule bundle is never baked) and wrong about effect: Codex read every standard in its one proof run and still wrote comments (`f96a3cd`), and the densest comment commits on the branch came from interactive Opus sessions with everything loaded (`a8e093d`: 72 comment lines to 42 code).
5. **It reinforces itself.** Every exemplar, sibling and "comparable file" is AI output already carrying comments; the verifier's convention test turns the symptom into its defence (three verifiers cited the pre-DR2.1 `Ruled c-030` comment as "the existing convention"). Inline `//` density is falling (6.4% → 3.1% across four phases) but prose JSDoc blocks hold at 15-18%. A one-off clean-up is needed, but only after the standard and the verifier are changed, or it will be refilled.
6. **Structural drift is smaller than it looks, and the layer rules are already machine-checked.** `lint:arch` (dependency-cruiser) runs in every ladder and its baseline is unchanged on the branch. The real structural gap is that `tim backlog standards` never returns the repo's own `src/server/app/docs/architecture.md`, `features.md` or `validation.md`, so no stage holds a written boundary for `shared/kit.js` or feature-folder independence; architectural choices are made at plan time and never re-examined.

## 4. Why the code-style review does not catch it

The review runs, and it raises the findings. It loses them in three places, in this order of weight:

1. **Verifier (`:4020-4044`).** No house rules in its prompt. "Default to refuted" (`:4022`); "against the house conventions the repo actually follows (find a comparable file and compare)" (`:4039-4041`); "a matter of taste dressed as a defect" (`:4042`). Across the DR2.1 journals roughly three in four comment findings and essentially all naming findings are refuted; ~40% of comment refutations point at a neighbouring AI-written comment, ~30-45% at rule 15's "why" allowance, the rest at taste or scope. The reviewer's `category: comment-discipline` (emitted 75 times) is dropped at `:4032`. The inc-112 verifier (`agent-ab23ba6b39b6a79f1`, sonnet) never read a file; it ran `git diff --staged` twice.
2. **The written standard it reads.** `code-style.md:409`, `jsdoc.md:9-12`, `BEST_PRACTICES.md:14` and the Java GWT mandate give the verifier a rule-based defence; several verdicts quote them ("Code-style rule 15 (docs/best-practices/node/code-style.md:387-409) allows why-comments"; "The CLAUDE.md memory note … is a generic default that the repo's actual, checked-in style guide qualifies with this explicit why-comment exception").
3. **Review recall.** The style reviewer flags about one in four added comments (overview-and-review: 29 findings against 64 JSDoc blocks + 102 `//` lines); the two largest rationale essays on the plants branch (`service-time-zone.js`, `incomplete-cards.js` REVIEW_CARDS) were never flagged. Reviewers judge from `git diff --staged` plus the persona; the persona's bundle path does not exist in loop runs; `:3843` says "17-rule" guide (it has 16). Changed-lines-only (`STYLE_FILE_REVIEWER.md:118-120`) means inherited comments are never findings. `.scss`/`.njk` have no comment guidance at all (`:1074` routes styles to no bundle).

Downstream of these the chain works: the judge ruled fix-now on 77-82 of 78-83 comment findings it saw (`:4085` "a house-rule violation is fix-now regardless of severity label") and the fixer applied them (animals `flow.js:52` bare; ins-frontend `list.js:88-89` bare). Severity label ("nit") plays no part: it is read nowhere but the schema (`:1760`). Two smaller leaks: fixes apply only to the twin the finding names (`:1058` groups per repo; plants kept the c-201 comment animals lost), and parallel-theme merges restore trimmed comments (`3919fe0` undone by `faa983f` taking `deec2c7`'s side).

### 4a. Does it reinforce itself?

Yes, through the verifier's convention test and the planner's exemplar rule, not through a rising trend.

- **Mechanism, proven.** `wf_11a9d6a5-051`: main's `notApplicable` comment → inc-111's `viewHeader` comment refuted at journal:197 as matching "sibling explanatory comments (e.g. notApplicable)" → landed `25b65c18` → inc-112's comment refuted at journal:257 because "copy.en.js:4 already carries a sibling comment in the identical style". Three verifiers cited the pre-DR2.1 `Ruled c-030` comment (`3d03865`) as "the existing convention". The same test removes comments when the file is bare ("list.js:89 is the only comment in the whole file" → real:true), so it tracks the file's prior state, not the rule.
- **Exemplars.** Recipes name loop-written files as the worked example and were pointed at them in the same commit (`615efca`, 2026-09-08, closes the `add-a-field.md` placeholder with `arrival-details`; `arrival-bounds.js` 22 of 36 lines comments). Plans name an exemplar's "doc-comment style" (`inc-106.md:141`) and "Arrange/Act/Assert comments" (`inc-103.md:134`). Exemplar chains run AI-on-AI (`inc-112.md:15`, `inc-113.md:16`, `inc-187.md:15` cite inc-111's output). But density does not track the exemplar: pre-exemplar plants feature files are 15.6%, post-exemplar 12.7%; pages built from identical exemplars range 1%-27% (`a610e71` vs `615efca`).
- **Trend.** Plants-frontend production JS by phase (comment lines / added non-blank): port `98c40c5..a794ec5` 22.8%; high-risk-plants loop `a794ec5..642c853` 20.4%; hardening `642c853..634849a` 23.1%; DR2.1 `634849a..28baedf` 18.3%. Flat, but a mix effect: inline `//` falls 6.4% → 5.8% → 4.8% → 3.1%, while prose JSDoc blocks hold 15-18% and are 75-85% of every phase's count. The platform layer was inherited from animals at ~25% (blob-identical files); the loops' own set-level output (13-17%) is twice animals' set files (6.6%). Whole-tree density on main is slightly down (2.32% → 2.18% `//` lines).
- **Where the heaviest comments came from.** Not the loop: `a8e093d` (fix EUDPA-692, Opus interactive session, 72 comment lines / 42 code, `service-time-zone.js` 18/19), `75b06e3` (39/110), `913a18d` (PR #90, 36 `//` + 71 block), `e6c74a2` (EUDPA-698), teammate ticket-skill sessions (`c69acf0` 25%, `31684a0` 30%, cleaned by `696c5e8`/`a918b7f`). Every AI writer here, with or without the standards loaded, produces this style.

**Is a one-off clean-up needed?** Yes, and it must cover the whole features and obligations folders in both frontends plus the base engine (`bridge/`, `engine/`, `model/`, `flow/`, `shared/kit.js`), the ins-tests page objects and specs, and plants-backend's ported `NotificationService.java` — not just the named exemplars, because the verifier picks any comparable file and 74 of 117 plants feature files carry comments. It is only worth doing **after** §5 items 1-3 land: a clean-up judged against today's `code-style.md` would keep most of the 590 JSDoc lines, and a clean-up before the verifier change would be refilled by the next increment (EUDPA-573's trims were followed by 25-30% fix commits).

## 5. Recommended changes, by impact

1. **Make the standard say what Sam means, in the files every stage already reads.** `docs/best-practices/node/code-style.md` §15 (`:387-418`): delete the "why" carve-out and its Hapi example; replace with "No comments.
