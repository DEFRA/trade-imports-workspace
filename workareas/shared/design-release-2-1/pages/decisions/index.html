QUESTION 1 · conflict c-217

Should address search work in every environment, or only where a real address lookup exists?

Design Release 2.1 offers "Search for an address" on every add-address page. The real address lookup is only set up on the local stack (as a stub) and in CDP dev. Should it be set up in CDP test, ext-test, perf-test and production, or should those environments offer manual entry only until it is?

Affects inc-042, inc-071, inc-072, inc-081Requirements req-456, req-457, req-647–654, req-1214–1218
Prototype · Design Release 2.1

Every add-address page starts with a type-ahead address search, then fills the fields from the chosen result.

  • Address book, journey parties and contact address all search
  • Results come from a made-up list inside the prototype
Real service today

No address search anywhere. Every field is typed by hand on one INS page, which the animals journey hands over to.

  • INS frontend "Add address details": manual fields and a country drop-down
  • The animals journey's party pickers only filter the saved address book

Default if nobody answers

EnvironmentWhat gets built
Fit suites and the local stackSearch runs against the lookup stub's fixed results
CDP devSearch runs against the INS backend's real address lookup
CDP test, ext-test, perf-test, prodSearch is built behind a per-environment setting, left off. Pages open with the address fields showing and no search box, until the lookup is set up there

Every field, error message and save is the same in every environment.

Why the rules could not settle it

The prototype searches everywhere, and a settled rule (c-178) says the search must use the real lookup rather than a made-up list. That lookup is an INS backend spike that exists only locally and in CDP dev. Setting it up elsewhere is a platform and cost decision the sources cannot make.

QUESTION 2 · conflict c-218

How should the commercial transporter's Northern Ireland address search work?

A commercial transporter can only be from Northern Ireland. Should its search use the same address lookup filtered to Northern Ireland (BT) postcodes, with the lookup stubs given a few Northern Ireland addresses so it can be seen working outside CDP dev?

Affects inc-042Requirements req-456, req-457Also changes trade-imports-stub
Prototype · Design Release 2.1

Authorisation number and name, then "Search for an address" with an "Enter address manually" fallback.

  • The search offers Northern Ireland addresses from a made-up list
  • Required fields are checked before saving
Real service today

Manual address fields with the country fixed to Northern Ireland. No search.

  • Submitting the form empty saves and returns to the overview with no error. The backlog already fixes this (the prototype wins)
  • The lookup stubs only return 3 London addresses today

Default if nobody answers

  • The commercial transporter search calls the same INS backend lookup and lists only results whose postcode starts "BT".
  • The lookup stubs used by the fit suites and the local stack gain a few BT addresses, so the filter and the fill can be seen and tested there.
  • CDP dev uses the real lookup's Northern Ireland results. Other environments follow question 1.

Why the rules could not settle it

The prototype's Northern Ireland search uses invented data, which c-178 rules out. No source says how a Northern Ireland-only search should be shown or tested where the real lookup is not available.

QUESTION 3 · DR1 row inc-103, left to the design authority

When does an animal count as identified: once one identifier is filled in, or only when all of them are?

Two authorities disagree. Design Release 2.1 asks for every identifier before arrival. The data-fields specification (V4) the real service implements says "Mandatory to Submit – At least one Animal Identifier". DR1 did not decide: it left this to the design authority. Five requirements are blocked until it is settled.

Affects inc-147 (blocked today)Requirements req-905, req-906, req-908, req-931, req-940
Prototype · Design Release 2.1

"You must add all animal identification details before the consignment arrives at the port of entry." Each animal's panel holds every identifier for its commodity.

  • Submitting with identifiers missing is allowed, but the notification is then flagged "Action required"
  • An animal with none shows "Enter a minimum of 1 identifier"; the header says "You need to complete animal identifiers"
Real service today

The same inset text, but one identifier of two is enough. The task shows Complete, the notification submits, and nothing follows up on the rest.

  • Ear tag filled, Passport blank: "Identification details" shows Complete
  • The confirmation page lists only the health certificate as still to do

Default if nobody answers

Both rules hold, at different moments, which is what Design Release 2.1 already shows:

  • To submit, at least one identifier per animal is enough (V4).
  • To be complete, every identifier for the commodity is needed. Until then the Identification task does not show Complete.
  • A notification submitted with identifiers missing lists "complete the animal identifier information in the notification" on its confirmation page, and is flagged on the dashboard as "Information is missing" (DR2.1).

Why the rules could not settle it

The agreed precedence lets only a DR1 judgement override the prototype, and DR1 made none here: it deferred. But the V4 specification is a real validation rule from outside the prototype, so this is a genuine clash between two authorities rather than a design preference.
