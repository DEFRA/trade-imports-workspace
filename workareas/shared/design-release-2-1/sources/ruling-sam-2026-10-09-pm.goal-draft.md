# Draft goal, repos and source entry for ruling:sam-2026-10-09-pm

## Goal (replaces `goal` in sources.json)

Bring the real GB notification services up to Design Release 2.1 of the GB notification service prototype in look and feel: content, wording, layout, components and question order. In scope are the GBN-AG animals notification as two sibling sets in the animals frontend, live-animals and germinal-products, with each set's own notification list, its templates and the INS address book. Wherever a real service differs from Design Release 2.1 in look and feel it changes to match, except where something overrides it: an owner ruling on that same difference, a DR1 judgement on it, or a real constraint the prototype cannot express (persistence, validation, authentication, cross-service behaviour, accessibility). Where a row changes a page or behaviour the high-risk plants frontend also has, the same increment changes plants too, never a separate increment, so that the two start consistent. Plants mirrors the structure, wording patterns, components and behaviour, and keeps its own questions and data. Every page works fully without JavaScript, and JavaScript only enhances a page that already works. A behaviour is built with GOV.UK Frontend first, then another tested government library (Ministry of Justice, HMRC, Scottish Government), and otherwise goes back to design to justify it. No custom JavaScript is written to copy the prototype, and pop-ups are not built: confirmations stay as pages. Where a prototype behaviour needs JavaScript that no accepted component gives, the version that works without JavaScript is built now in its own theme. The JavaScript-only addition is its own increment, one per design question, blocked on design in the waiting-on-design theme; live filtering as the trader types waits there too. A search box uses the real frontend's accessible autocomplete over a native select and behaves as the real frontend configures it. Its entries come from MDM, and only how the list reads (labels, order, hint, placeholder) follows the prototype. Rolling the component out to more screens is EUDPA-635's work, and fields the prototype shows as plain selects stay plain. Reference-list content (countries, territories, ports) is whatever MDM serves through reference-data. It is never edited in code to match Design Release 2.1, and only how a list is shown follows the prototype. For the germinal-products set, the V4 germinal data fields page decides which fields are asked, their format, limits and whether they are mandatory; Design Release 2.1 decides how the pages look and read. Each notification list stays in its own frontend and is reframed in place to the prototype's animals dashboard, in the animals-dashboard theme, with plants' list in the same increments. Every page the prototype sends to "the overall dashboard" goes to the set's own list instead. Some areas are adopted but blocked, and each is re-distilled once it is unblocked:
- **Address search:** waits until the INS address lookup is a real feature. Until then every add-address page offers manual entry only.
- **The commodity catalogue and commodity search, live and germinal:** wait until commodities come from MDM. The commodity pages' wording, their place in the journey and their questions go ahead on today's commodity data.
- **Transporter management:** adding, listing and searching transporters, the type question, the add pages and the address book's transporter tab wait until it is decided whether and where transporters are managed. The transporter step's place in the journey and its germinal copy go ahead.
- **The INS dashboard's summary information:** the counts, glance cards, status-change cards and drill-downs wait until the INS dashboard's requirements firm up. The INS home's controls and templates go ahead.

The backlog's report groups work as ready to go or blocked, and names what each blocked row waits on. Architecture (sets, journeys, services, URL paths, field names, data shapes, code structure) stays the real services'. It changes only where a DR1 judgement, a real constraint or a kept look-and-feel requirement needs it, and then it is designed in the real service's conventions. The owner's rulings may add to data shapes. The 9 October ruling does this with a notification category, the germinal products details and trade-line typeCodes in the animals backend.
