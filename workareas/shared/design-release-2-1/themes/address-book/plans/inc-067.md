## 0. Decisions

1. **A tab is an address type, and the existing `AddressType` owns which uses each one holds.** The address book already has the three groupings as `AddressType` (`AddressType.java:7-14`: `ORIGIN_OR_CONSIGNOR`, `DESTINATION_CONSIGNEE_OR_IMPORTER`, `BRANCH`). The prototype treats the add step's type and the list's tab as one concept: the add types' values are the list's tab ids (`app/data/address-book-add-categories.js:3,10,24` against `app/data/address-book.js:23,34,52`), and the uses offered per add type are keyed by those same ids (`app/routes.js:10039-10043`). inc-061's type hints ('Place of origin, Consignor' / 'Place of destination, Consignee, Importer' / 'Branch address') are exactly the uses each tab holds, and inc-070 needs "a use posted that does not belong to the chosen type is not stored" from the same mapping. So `AddressType` is extended to own, per constant, the uses it holds, and that `ORIGIN_OR_CONSIGNOR` also holds an address with no uses (decision 4). No second enum is added. The list filter binds to `AddressType` and matches on the stored `uses`, never on the stored `addressType` field: criterion 4 puts an address held as place of origin and consignee on both the first two tabs, which a match on its one stored type cannot do. inc-070 reads the same `AddressType` uses to refuse a use outside the chosen type. Rejected: a new list-category enum beside `AddressType` (one concept under two near-identical names, and two owners of one mapping by inc-070); and filtering on the stored `addressType` field (fails criterion 4).
2. **One wire name for the concept: `addressType`, with the `AddressType` values, everywhere.** The address book list takes one optional query parameter `addressType` whose values are `ORIGIN_OR_CONSIGNOR`, `DESTINATION_CONSIGNEE_OR_IMPORTER` and `BRANCH` (the enum's names, UPPER_SNAKE as `JacksonConfig.java` sets for every enum on the wire and as the record's `addressType` field already carries them). The INS list page's tab query parameter is also `addressType`, with the same three values, so the INS front door needs no table translating its URL values into API values. The tests repo's constants module and the k6 suite carry the same name and values. The ruling of 9 October leaves the tab parameter's name and values to the INS service; criteria assert the tab shown, never a query string. The parameter's contract (README, locked contract, `@Parameter` description) states that it lists the addresses with one of that type's uses, so a reader does not take it for a match on the stored `addressType` field. Rejected: the prototype's kebab-case `category` ids (a second name and a second value set for one concept between the INS URL and the API); and a parameter named `tab` or `category`.
3. **Which uses each address type holds.** `ORIGIN_OR_CONSIGNOR`: `PLACE_OF_ORIGIN`, `CONSIGNOR`. `DESTINATION_CONSIGNEE_OR_IMPORTER`: `PLACE_OF_DESTINATION`, `CONSIGNEE`, `IMPORTER`. `BRANCH`: `BRANCH_ADDRESS`. `AddressType` holds these; nothing else in the address book writes the lists.
4. **An address with no uses shows on the Origin and Consignor tab, and on no other.** The claim check: until inc-070 the INS add form posts no type or uses (inc-070 depends on this row), so every address added through the INS front door, the journey handshake add, the INS stub's seeds, the k6 suite's adds and every tests-repo spec that creates through `traderAddress(name)` holds no uses. A strict filter would hide all of them on every tab, and every list, add, search and k6 session check in all four repos would go red with nothing in this row to fix them. The prototype's rule for an address whose kind it does not know is the Origin and Consignor category (`app/data/address-book.js:69-75`, `getAddressCategoryId` returns `'origin-and-consignor'`). So `ORIGIN_OR_CONSIGNOR` also holds an address whose `uses` is missing, null or empty; the other two never do; an address with no uses but a stored `addressType` of another value still lists on Origin and Consignor only, because the filter reads uses. `AddressType` owns this with the uses, so the rule has one owner. This meets criterion 5 differently from its wording; section 14 lists it, and section 7's follow-up gives its removal to inc-070, which makes a use required. Rejected: hiding addresses with no uses, which breaks the slice as above; and a frontend-side rule, which the 9 October ruling (claims 115, 116) gives to the address book.
5. **The filter composes with search and country, inside the organisation and live scope.** A list request with `addressType` returns the caller's organisation's ACTIVE addresses that type lists that also match `q` or `countryCode` as today (OR between `q` and `countryCode`, AND with the type), paged and ordered as today. With no `addressType` it returns what it does today. The animals frontend's party pickers call the list with no `addressType` (`repos/trade-imports-animals-frontend/src/server/app/services/address-book/client.js:50-53`), so they keep seeing every address. The plants frontend's pickers do the same (`repos/trade-imports-plants-frontend/src/server/app/services/address-book/client.js`, listing with `page` and `q` only), so they also keep seeing every address.
6. **One list query, composed, in a repository fragment.** Today four fixed queries cover the combinations of `q` and `countryCode` (`OperatorRepository.java:17-45`), each repeating the organisation and status scope, and `OperatorService.queryPage` (`OperatorService.java:100-127`) branches between them. A third optional filter would make eight fixed queries. The list query moves into one Spring Data custom repository fragment of `OperatorRepository` (an interface the repository extends, with one implementation that builds a `Criteria` query through `MongoTemplate`, as `docs/best-practices/java/spring-data-mongodb.md` §3 prescribes for queries derived methods cannot express). It takes the organisation id as a required argument and always scopes by it and by ACTIVE status, so README's trust-boundary statement (lines 100-103) stays true. It reads the uses an address type lists, and whether it lists an address with no uses, from `AddressType`; it holds no use list of its own. It counts with `exactCount` (`spring-data-mongodb.md:833`). It replaces `searchByQuery`, `searchByAnyCountryCode`, `searchByQueryOrAnyCountryCode`, `TEXT_SEARCH_CLAUSES` and `findByOrganisationIdAndStatus`; `IntegrationBase.activeAddressesFor` reads through the fragment with no filters. `OperatorService.list` keeps page validation and input normalisation (trimmed search term escaped to a partial-match pattern, blank and null country codes dropped) and makes one repository call. Rejected: four more `@Query` strings, which repeat the scope eight times and keep the four-way branch.
7. **An unknown API `addressType` is a 400.** The controller binds `addressType` to `AddressType`. An unknown value fails conversion and the existing `GlobalExceptionHandler.handleTypeMismatch` (`GlobalExceptionHandler.java:66-80`) answers a `bad-request` problem with no `errors` map, the same as a non-numeric `pageSize` (`OperatorListIT.java:172-183`). The list operation's 400 description names an unknown address type.
8. **The contract lock covers the parameter and its values.** The locked contract's list operation gains the `addressType` query parameter with its enum, so `liveApiDocsHaveTheLockedOperationParameters` (`OperatorComplianceIT.java:150-153`) holds the name. The existing value lock for the `addressType` and `uses` fields (`:164-179`) is extended, not copied, to also check that the live document's allowed values for the list's `addressType` parameter equal the locked file's.
9. **INS front door: one registry of the three tabs.** A new group-root module in `features/address-book/` (the shape of `journey-registry.js`) owns the three tabs in order, each with its address type value (decision 2) and its copy keys (tab label, panel heading), the default tab, and the resolution of a requested value to a tab (missing or unknown resolves to the default). Its Nunjucks path joins the INS environment's search paths, as in the animals frontend (`repos/trade-imports-animals-frontend/src/config/nunjucks/nunjucks.js:14`). 11. **Page layout follows the prototype.** Heading, intro, Add a new address, the Filter addresses form, then the sub navigation, then the panel: an h2 with the tab's heading, the results line, Clear search when a search is active, the table, pagination. The filter form carries the selected tab as a hidden input (prototype `app/views/address-book.html:51-53`), so a search stays on its tab. Pagination links carry the tab and the search. Clear search goes to the selected tab with no search. The tab links carry only the tab: keeping the search across tabs (req-1127) is the Type-filter row's (inc-068). When the address book cannot be reached, the page stays as today (heading, intro, Add, filter form, no tabs, no panel, no table). The prototype shows no such state, so this is a choice the code makes for a case the design source does not show; section 0a raises it for the designer.

The Type cell shows the address's uses in stored order, each by its label ('Place of origin', 'Consignor', 'Consignee', 'Importer', 'Place of destination', 'Branch'), joined by ', ' (prototype `app/data/address-book.js:7-19` and `mapAddress`'s `typeLabels.join(', ')`). ## 0a. Questions for the designer

Each is a `design` question: the code makes a choice for a case the prototype does not show, and the designer decides.

1. **The sub navigation's accessible label.** Design source: the prototype draws the tabs as `<div class="govuk-tabs app-address-book-page__tabs">` with `<ul class="govuk-tabs__list" role="tablist">` and no label (`app/views/address-book.html:148-149`, commit 04a073b). The criteria and the 9 October afternoon ruling make them MoJ sub navigation, which renders a `nav` landmark whose label MoJ defaults to an English 'Secondary navigation region'. Code: the tabs will sit in the list template's loaded block, which starts at `src/server/app/features/address-book/list/list.njk:63` (`{% if listLoaded %}`), with the label in `copy.en.js` and `copy.cy.js` under `list`. Options for the designer: keep a plain label the implementor words, naming what the links choose between (the plan's choice, with a Welsh draft); use another wording the designer gives; or keep MoJ's default 'Secondary navigation region' (English on a Welsh page).
2. **The list page when the address book cannot be reached.** Design source: the prototype's list reads in-memory data and has no failure path; it renders the tabs whenever `categoryTabs` is set (`app/views/address-book.html:147`, `app/routes.js:9986-10006`). Code: today a load failure renders `listLoaded: false` with a 500 (`list.controller.js:117-126`) and the template shows nothing below the filter form (`list.njk:63`). Options for the designer: show no tabs and no panel, as today (the plan's choice: every tab would reload the same failing list); show the tabs with an empty panel; or show the tabs with the panel's heading and an error message in it, whose wording the designer gives.
