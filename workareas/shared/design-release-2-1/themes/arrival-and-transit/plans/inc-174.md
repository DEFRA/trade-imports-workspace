## 0. Decisions

1. **The list source.** The transit page offers exactly what the country of origin and import
   reason pages offer: `countries.countryAndSubdivisionOptionsNamedWithCountry()`
   (`services/countries/index.js:101`), which reads reference data's GBNAG_SPS_EX block
   (`index.js:41`), names each subdivision "<territory> (<country>)" through
   `subdivisionDisplayLabel` and sorts by the label shown. Rejected: a transit-specific list or
   filter — the ruling keeps one MDM block and one list (c-048: content differences are MDM's to
   change, never code's).
2. **The label owner.** Every place the transit page or its review card names a stored or chosen
   code — the added-countries rows, the "added"/"removed" status, the "already added" error, the
   search box's chosen value and the review card — goes through `countries.countryDisplayLabel`
   (`index.js:82`). It already returns the subdivision label with its country, the country name,
   else the code, so the controller's and card's `?? code` fallbacks go with it. Rejected:
   keeping `originLabel`, which names a subdivision without its country (the row's c-047
   conflict: a territory read back without its country).
3. **Chosen value shown back on refusal.** The box's chosen label is shown only for a code the page
   offers, and is empty otherwise. For an unknown code (`ZZ`, a tampered `transitedCountry`) that
   keeps today's empty box. **For GB it is a behaviour change:** today `originLabel('GB')`
   returns "United Kingdom" (`services/countries/index.js:66-68`), so a refused GB puts
   "United Kingdom" back into the search box (`controller.js:58`); after this change a refused GB
   leaves the search box empty, because GB is never offered. That is intended: the box shows back
   only a choice the list could have made. `countryDisplayLabel` falls back to the code, so the
   render must not call it for a code that is not offered. Rejected: calling
   `countryDisplayLabel` unconditionally, which would echo a tampered code into the box and keep
   "United Kingdom" for GB.
4. **`originCountries` is removed.** After this change no production code calls
   `countries.originCountries()` (`index.js:93`). Every caller the deletion affects, and where
   each moves:
   - `transit-countries.controller.js:41` (`countryItems`) and `validate.js:29` (`offeredCodes`):
     move to `countryAndSubdivisionOptionsNamedWithCountry` (section 2).
   - `transit-countries.controller.test.js:38` (the module-level `codes` the cap tests draw from):
     reads the countries-and-subdivisions options instead (section 4, last unit bullet).
   - `transit-countries.controller.test.js:454` (the GET list assertion): expects the
     countries-and-subdivisions options after "Select a country" (section 4, U1).
   - `run-mode.test.js:73`, `:122`, `:182`: re-expressed on
     `countryAndSubdivisionOptionsNamedWithCountry` (section 4, run-mode bullet).
   This change makes it unreachable, so the change deletes it. Rejected: leaving a dead export
   for a follow-up. `originLabel` stays: `countryDisplayLabel` calls it.
5. **Where the E2E list assertion lives.** The tests repo already proves each reference list in
   `tests/animals/e2e/features/reference-lists/` (`country-of-origin-list.spec.ts` loops JS on
   and off over `countryAndSubdivisionNamesWithCountry()`). The transit list joins them as a new
   spec there, built on the same helper (row notes, 2 November: build on
   `countryAndSubdivisionNamesWithCountry()` rather than port the stale branch's own list). The
   no-JS list test in `tests/animals/e2e/pages/transited-countries.spec.ts:92-99` moves into it,
   so one test owns the list. Rejected: porting the stale `transit-country-list.spec.ts` and its
   own list builder.
6. **Territory round trip E2E.** The add / save / reopen proof for a territory goes in
   `transited-countries.spec.ts` beside "accepts and persists multiple transited countries",
   using `countryCodes.subdivisions.canaryIslands` (`domain/animals/constants/country-codes.ts:4-6`,
   `subdivisionByCode('ES-CN')` from the captured origin fixture), whose display is
   "Canary Islands (Spain)". The `eu` block holds only countries. Rejected: inventing a
   territory or retyping its label.
7. **Review card.** The row's criteria name only the transit page, but the notes and the same
   rule (one label per code) require the check-answers transit card to read a territory with its
   country too, as the destination country row already does (SCN-CYA-013-C). It is built here so
   the two never differ.
8. **What is persisted.** The answer stores the chosen code itself (`ES-CN`), as canonical
   fulfilment stores every answer; the GBN-AG mapper already sends a territory as its parent
   country (`notification-mapper/mapper-a/sections/transport.js:26`, test at
   `notification-mapper.test.js:604`). No persistence change.
9. **Claims checked.** Main's transit page offers `countries.originCountries()` in `countryItems`
   (`transit-countries.controller.js:41`) and `validate.js:29` `offeredCodes`, and labels with
   `originLabel` (`controller.js:55,58,154,162`, `validate.js:66`, card `transit-countries.js:18`)
   — confirmed. The spec has no REQ-TRANSIT-COUNTRIES-009 or -010 — confirmed (the spec jumps
   008 → 011); the workspace commit 5a995a66 holds their wording. The tests repo has no
   `transit-country-list.spec.ts` on this branch — confirmed; it is written new. The 23 October
   note's partial coverage links are moot (no such requirements on main).
10. **AC 4 (refusal).** "Select countries from the list" stays owned by
   `TRANSIT_REFUSAL.notOnList` in `validate.js`. Only the offered set changes. Existing tests
   (`ZZ`, `GB`, tampered markup) keep proving the refusal against the new set.
