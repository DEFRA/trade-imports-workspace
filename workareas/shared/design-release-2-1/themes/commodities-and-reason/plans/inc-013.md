## 0. Decisions

1. **The result order lives in the search view model, over the labels the page shows.** The row's note says the sort belongs in the frontend view model and not in reference-data, which another team owns; reference-data preserves MDM's order and the frontend groups results in encounter order today (`search/view-model/commodity-groups.js:16`). The order rule orders groups by the plain commodity legend (`search/view-model/labels.js:1`) and each group's rows by the plain species label (`features/commodities/species-label.js:1`). Rejected: ordering by the raw commodity code and the raw `speciesLatinName` directly. Going through the two label owners means inc-025, which changes what a species label reads, moves the order with it in one place instead of leaving the order sorting on a string the page no longer shows.

2. **The order is a rule of its own, in its own module under `search/view-model/`.** `commodity-groups.js` already owns grouping and the checkbox-item shape; adding ordering and emphasis to it would make one module own four rules. Rejected: extending `search/selection/keys.js:9` (`inCanonicalOrder`). That function orders *keys* for storage and de-duplication (code then Latin name) and is what the selected panel and the saved lines already use; the result order is over *rows* and must follow the display labels. Two different rules, two owners.

3. **The emphasis of the matched text reuses `escapeAndBoldMatches` (`src/client/common/helpers/bold-matches.js:21`), and the two emphasised labels are owned in `search/view-model/labels.js`.** That helper already escapes the text and wraps each case- and accent-insensitive match in a bold `<strong>`; a server module importing from `src/client/common/helpers` has precedent at `features/transport/transporters/rows.js:7`. `labels.js` is the search feature's label module, so the commodity legend's emphasised form and the species label's emphasised form both live there, each a one-step composition of its plain owner with the helper. Rejected: a third escaping-and-bolding implementation in the commodities feature (the row's note forbids it), and emphasising inside the template (Nunjucks cannot do accent-folded match positions).

4. **The query the emphasis uses is the normalised query the page already holds** (`search/search-query.js:3`, threaded through `render` at `search/search.controller.js:40-69`). Nothing new is stored or recomputed.

5. **Criterion 2 is honoured over the label the page shows today, which is the Latin name and the commodity code — not the common name.** `speciesLabel` returns `speciesLatinName` alone (`features/commodities/species-label.js:1`), so searching "taurus" bolds "taurus" inside "Bos taurus" and searching "0102" bolds the commodity heading, while searching "cattle" matches through the common name and shows no bold, because the common name is not on the page. The criterion's example "Domestic **cattle** (Bos taurus)" becomes observable when inc-025 puts the common name back into the label; the emphasis rule then covers it with no further change. Rejected: adding the common name to the result label here. That is inc-025's criterion and this row must build only what it makes reachable.

6. **The chips are built from GOV.UK Frontend components and `govuk-*` classes, not from the prototype's `app-commodity-search__selected-*` block.** The programme invariant is explicit: "Pages are built from GOV.UK Frontend components and govuk-* classes; the prototype's custom app-dr2-* blocks are not copied." So the selected panel renders, per chosen commodity, a bold commodity line followed by a `govuk-list` with one entry per chosen species — the species label and its own Remove control. GOV.UK Frontend has no chip component. This is a decision taken by the invariant, not a design question: the observable content the criteria name (the bold commodity line, one entry per species showing its Latin name, a remove control per species named "Remove <Latin name>") is all delivered; only the prototype's pill styling is not. Rejected: porting the prototype's chip CSS, and an icon-only remove button (no visible text, barred by the toolbox and by the GDS requirement for a visible accessible label).

7. **The commodity line becomes a paragraph and the species a list, not a nested list inside one list item.** This follows the design source's own structure (`<p><strong>Cattle (0102)</strong>:</p>` then the chips container, per `trace-prototype-dr2-1-p3-035`) and it keeps every list item in the panel one species, so an assertion over the panel's list items is unambiguous. Rejected: keeping the current single list item per commodity (`search/search.njk:66-71`) with the species nested inside it — the outer item would then match both the code and every species in a `hasText` filter, which is exactly the ambiguity the current shared helper already leans on.

8. **A chip's Remove is a submit button on the page's one form, carrying the species' selection key in the button value, and the removal is applied to the submitted selection.** The page is already one form posting to itself with `Search` and `Clear all` as named `action` submit buttons (`search/search.njk:20-79`, `search/search.controller.js:93-133`), so the remove path adds a third named action and criterion 5 holds with no JavaScript anywhere. The key, not an index, rides in the value — the same rule the set's own page-design doc already states for removing an added transit country (`sets/live-animals/docs/page-design.md:450-453`), "so the row pressed is the row removed however the list has been reordered since the page rendered". Rejected: an index into the panel (brittle against a re-sorted panel) and a separate GET route (no crumb, and a link would trigger a state change).

9. **A removal takes the same path through the controller that `Clear all` takes**: the submitted selection minus the named key, then the search is re-run and the rows re-stored and the page re-rendered with the query and its results intact (`search/search.controller.js:78-91`, `116-121`). So removing one species leaves the others chosen, keeps the results on screen with the other boxes still ticked, and does not touch the saved `commodityLines` until a save — exactly as `Clear all` behaves today. Rejected: committing the removal to the saved lines immediately. That would make a chip's Remove the only control on the page that writes before a save, and it would break the already-specified behaviour that clearing and then refusing a save leaves the saved selection intact (`SCN-COMMODITY-SELECT-009-D`).

10. **A removal is honoured whether or not the submitted selection still holds the key; only a key the stored search rows never held is refused.** Two cases, settled separately:

    - **The key is one the stored search rows know, but the submitted selection does not hold it.** This is an ordinary no-JavaScript interaction and it is honoured silently, with nothing logged. The panel is rendered from `selected`, and on a post `selected` is the merged selection — `mergedKeysFromPayload` over `payload.selection` plus `payload.species` (`search/selection/selected-keys.js:11-12`) — while `carriedKeys = selected.filter((key) => !onScreen.has(key))` (`search/search.controller.js:64`) emits a hidden `selection` input **only** for a choice with no tick box on screen. So for a species whose box is on screen and ticked, a chip is shown and no hidden input carries it; a trader who unticks that box and then presses that same species' chip Remove posts a removal naming a key the merged selection no longer holds. Nothing on this page re-renders without a post, so that sequence takes one post and needs no JavaScript. The asked-for outcome — that species not chosen — is already what the trader wants, so the branch filters the key out of the submitted selection (a no-op when it is absent) and re-renders the working page with the remaining choices, the query and its results. Nothing is logged. The repo's own removal-by-key-in-button-value exemplar does exactly this: `transport/transit-countries/transit-countries.controller.js:144-151` filters the code out of the submitted selection and re-renders, with no refusal and no log, whatever code arrives. Rejected: `h.response().code(HTTP_STATUS_BAD_REQUEST)` with a `kit.logRefusal` line, which the earlier draft of this plan chose. It would answer that ordinary interaction with a blank bad-request page and a logged refusal, breaking criterion 5 ("the chips' remove buttons … all work by posting the page") and the programme invariant that every state change is a form post that works, and breaching `.claude/rules/code-quality.md:80` — "A user's own input error shown back on the form is not one: do not log it."

    - **The key is one the stored search rows never held.** A chip is only ever rendered for a key in `selected`, and `selected` is filtered to the stored search rows (`knownKeysInCanonicalOrder`, `search/selection/keys.js:12`). This is reached by a tampered post, and also by a stale form with no tampering at all: `commitSelection` empties the stored search rows on save (`search/actions/commit-selection.js:66`), so after a save `knownRowsByKey` is just the saved lines; if the trader then removes that line on Commodity details and presses Remove on the still-open search page's chip for it, the key is in neither the saved lines nor the stored rows. Either way it is refused with a bad request and one refusal log, as the feature's other two removals do (`consignment-details/remove/post-remove.js:36-39`, `:50-60`; `animal-identification/remove/post-remove.js:23-30`), through `kit.logRefusal` (`shared/kit.js:134-146`) and `HTTP_STATUS_BAD_REQUEST`, already imported at `search/search.controller.js:3`. `logRefusal`'s own doc comment (`shared/kit.js:129-132`) states this is what it is for — "a state refusal, a tampered post, another service refusing" — and "never for errors the user can correct on the form", which is the line the two cases fall either side of. Rejected: letting a key the stored rows never held fall into the honoured case. That would leave the only outcome-changing branch the change adds unlogged, and would make this removal behave unlike the other two in the same feature.

    An action value that is neither `search`, nor `clear`, nor a removal is unchanged: it falls through to the existing commit path (`search/search.controller.js:123-132`), exactly as today.

11. **Criterion 1's parenthetical label format is out of date and is not built here.** It says the species label reads "common name (Latin name)"; inc-025's own notes record that V4 outranks the prototype on a field's format and the corrected format is the scientific name with the common name in brackets. Decision 1 removes the clash: the order sorts by whatever the label owner returns, so this row states no label format at all and inc-025 owns it.

12. **Welsh.** One new English string is needed — the visible "Remove" word on a chip's control — with its Welsh machine draft beside it in `copy/copy.cy.js`, which carries the machine-draft marker at line 1. The accessible name is that word plus the species label, which is data, not copy, so no second key. The feature's copy already holds a Welsh "Remove" for its tables (`copy/copy.cy.js:47`, `:91`), so the parity convention test's requirement that a translation differ from its English counterpart is satisfied.

13. **Plants is not in this row, and the programme's mirror invariant does not bite.** The invariant applies "where a row changes a page or behaviour the high-risk plants frontend also has". `repos/trade-imports-plants-frontend` has no commodity search page and no selected-species panel — its commodities feature is a commodity-line form (`sets/high-risk-plants/journeys/linear/features/commodities/line-form.js`) and a grep of that set for `commoditySearch`, "Search for a commodity", `selected-summary` and `commodity-selection` returns nothing. So the row's `repos` of frontend and tests is right.

14. **The performance-tests repo needs no change.** The k6 walk submits the search field with the search action and then picks a value out of the rendered species inputs (`perftests:src/k6/live-animals.js:57-69`, `src/k6/journey-pages.js:44-45`). Emphasis inside a checkbox label and a re-ordered list leave the input names and values untouched, so the walk is unaffected. This matches the row's `repos`.

15. **The sort uses the same comparison the repo's existing ordering uses (`localeCompare`, as at `search/selection/keys.js:6`), and the tests derive their expected order with the same comparison rather than hard-coding a list.** Rejected: hard-coded expected orders in the e2e test, which would pin MDM's current content.

16. **Every FIT and e2e command this plan writes carries this run's worker cap.** See section 14: the planner rule is to leave the worker count to whoever runs the check, but this run's caps are fixed (frontend FIT `--workers=4`, ins-tests e2e `--workers=2`) and the plan review requires them written in, so they are. Rejected: leaving them off and relying on each stage to add them.
