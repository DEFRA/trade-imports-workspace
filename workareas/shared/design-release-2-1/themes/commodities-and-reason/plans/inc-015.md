## 0. Decisions

1. **The change is the position of one step in the draft walk, and nothing else.** The main import reason step moves to sit between the commodity page step and the Commodity details step in the live-animals draft walk, so the walk's window from the commodity page through additional details comes to match the order the frontend's opening run offers those six pages in. Every other step of the walk keeps the position it has, and the walk still opens the step after additional details afresh — the walk's later order is its own, not the opening run's (see decision 6). Rejected: leaving the walk alone and widening the per-step check to assert the landing URL instead — that would prove the walk notices the order while still walking the wrong one, which is the opposite of what the row asks. Also rejected: reordering the walk's steps after additional details to match the opening run too — the row asks for the main import reason's place between the two commodity pages, and reordering seven further steps would widen the footprint well past it and is not a change the row's acceptance criterion names.

2. **Only perftests changes.** Frontend and tests already satisfy every behaviour the row names (see above), so neither is edited. The loop still merges `origin/main` into all three as the row's `merge` field says; those merges are no-ops. Rejected: touching the frontend or the tests repo to "make the row visible in all three" — that would be a file edited only for tidiness, which the footprint rule forbids.

3. **The endpoint catalogue's key order is left alone.** `perftests src/config/journey-endpoints.js:22-44` happens to list the live-animals step keys in the old journey order, and `perftests src/config/journey-endpoints.test.js:23-38` pins that list. The catalogue is a lookup from step to endpoint names; its key order drives nothing. Reordering it would edit a second file and a second test for no behaviour, and would put the walk order in two places when the rule has one owner. Rejected: reordering the catalogue keys to match. The test whose title claims coverage while its assertion also pins order is a pre-existing mismatch outside this row's footprint — it goes to section 7 as a follow-up.

4. **The walk's non-stack proof is a unit test on the step order.** The acceptance criterion is a k6 run against the local stack, which is the gate's own e2e rung. A unit test in the perftests repo proves the same ordering without the stack, so the change has a red-to-green signal in the gate's unit phase as well. Rejected: no unit test at all, leaving the row provable only with the stack up.

5. **The unit test asserts the step order directly, not by driving the walk.** Driving the draft steps with a stub walker and asserting the ordered paths would be a stronger test, but the walk includes the documents step, whose upload and scan-polling loop would need a stub of its own and would pull set-up for pages this row does not touch into the test. The ordered step names of the commodity-and-reason window are the honest, bounded statement of this row's behaviour. Rejected: a full stub-walker drive of the whole draft walk.

6. **The walk requests three fewer pages a notification, and that is intended.** In the old order three steps opened their page afresh because the previous save had landed somewhere else: Commodity details (the commodity page's save lands on the main import reason), the main import reason (identification details' save lands on additional details) and additional details (the main import reason's save lands on Commodity details). In the new order each of those saves lands on the next step in the walk, so `reach` passes the page straight through. The documents step still opens afresh in both orders, because additional details' save lands on arrival details and the walk's next step is the documents step — the saving is three pages, not four. `reEditPlan` (`perftests src/lib/traffic-shape.js:44-59`) pads a notification with re-edits up to the model's pages-a-notification target, so the modelled page count per notification holds, with the padding's two-pages-per-re-edit granularity putting it within one page of the target. No threshold reads `pages_per_notification` (`grep -rn pages_per_notification ~/git/defra/trade-imports-workspace/repos/trade-imports-performance-tests/src/config/thresholds.js ~/git/defra/trade-imports-workspace/repos/trade-imports-performance-tests/src/config/smoke.js` finds nothing), so nothing is gated on the difference. Rejected: adjusting the model's page target to compensate — the target is a design figure from the volumetrics source, not a description of the walk.
