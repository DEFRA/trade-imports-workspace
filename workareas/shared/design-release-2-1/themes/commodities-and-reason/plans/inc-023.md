## 0. Decisions

1. **The five codes of the data-fields specification are the list, not the two the prototype shows.** The
   captured Confluence source is a field specification and the prototype's commodity data is demo data; the
   theme's re-analysis (`workareas/shared/design-release-2-1/reanalysis/v4-data-fields-commodity-rules-2026-11-02.md`)
   settles the same question for six sibling rules and finds the specification right wherever the two differ.
   Acceptance criterion 1 names the five. Rejected: the row's `detail` and its superseded note, which name
   cattle and pig only.
2. **Equines go back on the list, and the parity assertions that removed them are restated, not kept.**
   Frontend `598c6045` removed equines for DR1 parity; the data-fields specification is the later source and it
   lists them. A house rule makes a behaviour that contradicts its design source a correctness finding, so the
   two FIT tests, the one unit test and the one spec scenario that assert equines are *not* asked are wrong
   and change here. Rejected: keeping them and asking only for pigs, sheep and goats — that leaves the code
   disagreeing with its design source and the spec asserting a behaviour the service will not have.
   The account of *why* equines are back — that a later data-fields specification supersedes an earlier parity
   narrowing — is history, so it belongs in this change's commit message, which the row asks for, and nowhere in
   the code, the tests or the set's docs. Section 2's doc edit therefore states only the rule as it is now.
3. **The list stays one module-scope allow-list in the commodity rules module, read by the obligation through
   the existing accessor.** No new mechanism, no per-code branch, no change to the obligation's `applyTo`
   helper. Rejected: moving the rule into the obligation (it would split one rule across two homes) and
   rejected: keying it on species or common names (the module's own doc says a rule keyed by a Latin name has
   to track MDM's spelling; a code does not).
4. **The two codes the module spells only as string literals get the same named-constant treatment the other
   three already have, and both lists in the module read the names.** One concept, one name, inside one file.
   This touches the package-count list's lines only to replace two literals with the names of the same two
   codes; its membership does not change. Rejected: leaving the literals and spelling the sheep and goat codes
   twice in one module.
5. **Criterion 1's five codes are proved exhaustively in unit tests, and at FIT and E2E by one newly-added
   code each.** The obligation test already loops the whole list and the anti-drift table pins it exactly, so
   the five-code proof is cheap and total there; the review-render matrix gains a row per newly-added code. FIT
   and E2E prove that the page and the real stack act on the list, not that they act on five of it, so each
   takes one newly-added code. Rejected: five FIT cases and five E2E cases — slow, and they would re-prove at
   the browser what the list test already proves.
6. **The one newly-added code taken through FIT and through E2E is the equine code.** It is the code the design
   sources disagreed over, it is already a species row in both repos' helpers (frontend
   `features/commodities/search/test-support.js:35`, tests `domain/animals/constants/commodity-lines.ts`), and
   its E2E walk has to change anyway for the reason above — so the proof lands in a spec that is already being
   edited rather than in a new slow test. Rejected: the pig code, which would need a new species constant in the
   tests repo and a new slow walk for no extra reach.
7. **The negative FIT case moves off equines onto the cats-dogs-ferrets code.** That code is on the
   package-count list, so the FIT set-up that fills a package count still works, and it is the code the existing
   E2E negative case and the clearing tests already use — one vocabulary for "a commodity the question is not
   asked of". Rejected: the ostrich code, which takes no package count, so the shared FIT set-up would not
   reach the page.
8. **The E2E integration proof carries criterion 3 as well, through the notification view's card.** The walk
   that now answers the question ends on the review, and asserting that card's whole row list there proves the
   label shows for a newly-added commodity. Rejected: a separate review-only E2E test.
9. **No copy changes, so no Welsh work.** The question, its hint, its options and the review label all exist in
   both languages already (`features/additional-details/copy/copy.en.js`, `copy.cy.js`,
   `features/check-answers/copy/copy.en.js:50`, `copy.cy.js:51`). The programme's Welsh invariant is satisfied
   with nothing to add.
10. **The plants frontend is not touched.** The programme invariant mirrors a change into plants where plants
    has the same page or behaviour. Plants has no unweaned-animals question and no animal commodity rules, and
    the row's `repos` names frontend and tests only.
