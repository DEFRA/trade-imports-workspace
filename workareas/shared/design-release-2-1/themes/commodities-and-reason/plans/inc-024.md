## 0. Decisions

1. **The list itself does not change.** `PACKAGE_COUNT_CODES`
   (`repos/trade-imports-animals-frontend/src/server/app/sets/live-animals/services/commodities/rules.js:39-63`)
   holds exactly the 23 codes the first acceptance criterion names — read code by code against the
   criterion, they match with nothing over and nothing missing. The question's label and hint already
   read as the criterion states
   (`…/features/commodities/copy/copy.en.js:50-51`). So this row proves the match and the claim's
   negative half; it edits no production rule. Rejected: re-deriving the list from the prototype's
   nine-mammal flag, which the 2 November re-analysis settled against
   (`workareas/shared/design-release-2-1/reanalysis/v4-data-fields-commodity-rules-2026-11-02.md`).
2. **"No other code reference-data serves" is pinned against the set's own captured catalogue.** The
   set's commodity catalogue is the capture at
   `src/server/app/services/_capture/fixtures/commodities.json`, surfaced as `COMMODITY_GROUPS`
   (`…/services/commodities/stub.js:3`) and refreshed from the live service by
   `npm run capture:live-animals`. It holds 26 codes; 23 are on the package-count list and three are
   not — rabbits other than domestic (`01061490`), ratites (`01063300`) and pigeons (`01063910`). The
   same 26 are the leaf codes the MDM stub serves, so the capture is what a user can actually choose.
   Pinning against it makes a later MDM code fail the pin at the next capture refresh, which is what
   the second criterion asks for. Rejected: pinning against a hand-typed list of "every other code",
   which would not move when MDM does.
3. **The specification is named in the set's doc, and in the test only as the specification.**
   The house rules keep release names, version labels and source ids out of code and test titles, and
   send rationale to the repo's docs. The set doc already names this authority for a sibling rule —
   "set by the live animals data-fields specification"
   (`…/sets/live-animals/docs/services.md:44-46`) — so the package-count bullet is corrected to name
   the same authority, state that the list is that specification's number-of-packages commodities
   which MDM's live-animal data holds, and name the three served codes it does not include with the
   specification's reason for each. In the test the authority is named by the **name of the home that
   holds the 23 expected codes**, not by a comment and not by a page id: decision 11 sets that home.
   Rejected: a Confluence page id, a version label or a URL in the test, which the ids-and-history
   rule forbids.
4. **The review side needs no new unit test.** `check-answers.test.js:1398-1426` already pins the review
   with a whole-matrix equality over six listed codes and one served unlisted code, asserting whether
   the species card carries the packages row. The weaker duplicate at
   `check-answers.test.js:814-817` proves the same single cell by absence; deleting it would widen the
   row's footprint into a file this row otherwise does not need, so it is left alone and recorded as a
   follow-up. So no edit to `check-answers.test.js`.
5. **The page-level negative is proved at FIT and E2E, not by a new unit test.** The view-model half is
   already pinned (`consignment-details.controller.test.js:246-258` asserts `showPackages` true for a
   listed code and false for a served unlisted one). What nothing proves is the rendered page: every
   FIT and E2E journey through commodity details today chooses listed codes only, so the template's
   condition (`_species-quantities.njk:18`) has never been exercised in its false state in a browser.
   That is where the new FIT test and the new E2E spec go.
6. **The integration proof reaches the review through a new journey method, not through the spec's own
   clicks.** The tests repo's own notes are explicit: "A spec reaches a page through a `to*` method in
   `flows/<domain>/journey.ts`, not through its own clicks"
   (`repos/trade-imports-ins-tests/AGENTS.md:20`), and "A sequence used by two tests becomes a `to*`
   method in that file" (`:21`). No existing method reaches the review carrying only the two counts this
   test needs: `toReview` (`:605-610`) runs `completeAnswerSections` (`:437-447`), which answers every
   section of the journey — origin, identification, import reason, addresses, transport, contact,
   documents — for a full `NotificationAnswers` set; the mandatory answer sets in
   `domain/animals/constants/journey-commodity-line-answers.ts` hold no ostrich entry, so driving
   `toReview` for this consignment would mean adding one and then proving two rendered rows by walking
   the whole journey, which is disproportionate to a two-card assertion. `toOverviewWithSavedCounts`
   (`:460-465`) fills `numberOfAnimals`/`numberOfPackages` as single locators, which a two-species page
   turns into a strict-mode failure, so it cannot be reused either. So `flows/animals/journey.ts` gains
   a `to*` method that saves the animal counts for a mixed listed/unlisted species list and opens the
   review from Overview, modelled on `toAnimalIdentificationWithCounts` (`:486-494`), which already
   walks exactly that shape (choose the species, fill a count per species, save back to Overview, open
   one thing from Overview). The sibling spec that does its own clicks for the same reason
   (`tests/animals/e2e/features/additional-details-scope.spec.ts:44-49`) is not cover: "a nearby file
   does it" is never a reason. Rejected: teaching the journey flow to branch per species, which would
   put conditionals in the flow for one row's benefit; and reaching the review by its URL, which skips
   the control the user actually uses.
7. **The germinal and egg entries on the specification's list are not this row's.** The specification
   also lists `05111000`, `05119985`, `0407`, `04071100`, `04071911` and `04071919`. Reference-data
   serves none of them to this journey — the MDM stub holds chapter 01 only — so there is no reachable
   state to spec or test here. Follow-ups in section 7.
8. **`frontend-change` has no recipe for this row, but its general route does apply.** The skill's four
   named recipes do not: the row adds no field, page, section or collection, and changes no obligation
   and no journey flow — the obligation and its allow-list are untouched. Its fifth routing row,
   "change the frontend" (anything else), sends the change to Step 1 layer routing
   (`.claude/skills/frontend-change/SKILL.md:141`, `:149-160`), and that route **is** this row's: the
   layer is the set's services and obligations plus their tests, so the implementor reads the set index
   and the layer guides it names before editing —
   `sets/live-animals/docs/README.md`, `obligation-model.md`, `services.md`, `testing.md`, and the
   platform `docs/obligation-model.md`, `docs/testing.md` and `docs/test-ownership.md` (section 16
   lists them). Its Step 2 baseline guard (`SKILL.md:175-190`) is not covered by anything else in this
   plan, because the gate runs after the change and not before, so it is a check in section 6. Its
   Step 5 spec sync is the work section 8 sets out by hand, so section 8 stands as written rather than
   being delegated.
9. **One loop over the served catalogue, not two loops side by side.** Every one of the 23 listed codes
   is among the 26 the capture serves, so a catalogue-driven loop makes the same in-scope assertion for
   each of them as the existing per-code loop at `allowlists.test.js:38-47` and adds the three negative
   cases; keeping both would leave two loops asserting one thing, which "extend the mechanism that
   exists, do not add a second one beside it" forbids. So the existing per-code loop is **replaced** by
   the catalogue-driven one. Rejected: keeping it for the case of a listed code the capture has stopped
   serving — no such code exists today, that state is itself drift the anti-drift row and the capture
   refresh surface, and building for it now would be building what nothing reaches.
10. **What proves "exactly the 23 codes" is the assertion that holds the list's contents, not the
    catalogue loop.** The catalogue loop reads its expectation from `packageCountCommodityCodes()`
    itself, so adding `01063300` to the list or dropping `0102` from it leaves the loop green. The
    contents are pinned by the anti-drift row at `allowlists.test.js:257-262` against the literal at
    `:206-230`, which stays and is cited as that proof throughout sections 4, 5 and 8. The exclusion
    assertion (test 2) is the pin that moves when the **catalogue** moves. Rejected: claiming the new
    loop as the drift pin, which the review showed it is not.
11. **The 23 expected codes keep one home, named for the authority.** They stay the package-count entry
    of the anti-drift map (`allowlists.test.js:205-243`) — one pin, one literal — but that entry's
    value moves to a module-scope home of its own whose **name** states the authority decision 3
    settles, so the pin reads as pinned against the specification. Rejected: a comment above the
    literal (a comment that explains a name means the name is wrong), and a second copy of the 23 codes
    for the package-count describe to read.
