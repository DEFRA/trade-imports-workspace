## 0. Decisions

**D1 — One owner for how a species reads.**
`features/commodities/species-label.js:1` is already the single seam every listing
goes through (nine call sites, found by `grep -rn "speciesLabel" repos/trade-imports-animals-frontend/src`).
The new format lives there and nowhere else: a species reads as its scientific
name, then a space, then its common name in round brackets.
Rejected: a second label function used only by the five places criterion 1 names.
That is a second mechanism beside one that exists, and it would leave two
readings of one concept in the same feature.

**D2 — The format is not a copy key, so criterion 3 has nothing to do.**
The bracket is punctuation, and the common name itself comes from MDM in one
language and is never translated, so there is no English string to add and
therefore no Welsh counterpart to draft. The repo already keeps species-naming
formats in code rather than copy: the dash form at
`features/commodities/line-title.js:6` and the bracket form at
`features/check-answers/refusal.js:60`. Every copy sentence that names a species
(`features/commodities/copy/copy.en.js:57-58`, `:82-85`, `:87`) keeps its wording
unchanged and only receives a different substituted value.
Rejected: a copy key per locale for the format, which would put identical
punctuation in two locale files and invite them to drift.
What goes inside the brackets is not a string this row owns either — see D15.

**D3 — The review keeps reading exactly as it does today.**
Criterion 1 names five places and the review (Check your answers, and the
read-only view of a submitted notification, which share the same view model via
`features/check-answers/view-model/cards/consignment/species/species-cards.js:13-15`)
is not one of them — because that card already shows the common name on a row of
its own, added deliberately by the same change that introduced `speciesLabel`
(`git show c3183a8e -- .../species/species-card-rows.js`). So the card keeps its
"Common name" row, its "Species" row reads the stored scientific name, and its
title stays the code, a dash and the scientific name. Two call sites therefore
stop asking for a label and read the line's stored scientific name instead:
`species-card-rows.js:13` and `line-title.js:5`.
Rejected: letting the review pick the new label up through the seam, which would
print the common name twice in one card — once in its own row and once inside the
Species value — and would change a page the row does not ask for.

**D4 — The identification card stops feeding the display label to the gates.**
`features/commodities/animal-identification/card/view-model.js:96` takes the
species label and passes the same value to `permanentAddressApplies` (`:99`) and
`identifierColumns` (`:100`). Both gate on an allowlist of commodity-code and
scientific-name pairs (`services/commodities/rules.js:65-71`,
`animal-identification/identifier/fields.js:21-22`). Today that works only
because the label happens to equal the scientific name; with the common name in
brackets the allowlist would stop matching and the permanent address would
silently never be asked. The card must take the gate value from the line's stored
scientific name, as its sibling already does at
`animal-identification/form/forms.js:61-63`, and use the label for display only.
This is the one correctness fix the row requires; it changes no signature and no
caller outside that one function.

**D5 — Keys and helpers that now hold a label are renamed.**
`consignment-details/view-model/groups.js:8`,
`consignment-details/view-model/selected-rows.js:15`,
`view-model/selected-commodity-rows.js:13,17,26,39,41,53` and
`animal-identification/summary/selected-commodities.js:17,19` all name their value
after the Latin name while now holding a label, which the name rule forbids. The
rename reaches the one template that reads such a key
(`consignment-details/_species-quantities.njk:6`) and the unit tests that build or
read those rows. It does not reach `search/selection/rows.js:20` or anything under
`services/commodities/`, where `latinName` is genuinely MDM's scientific name.

**D6 — Every species reading on the two named pages uses the one label.**
That includes the sentences, not only the lists: the progress heading
(`copy.en.js:82-83`), the over-count message (`:84-85`), the saved-animal row
label (`:87`) and the count-drop error (`:57-58`, substituted at
`consignment-details/validation/count-drop.js:26`, which already goes through the
label owner). Criterion 1 names "Identification details" and "Commodity details"
without qualification, and a card titled one way with a heading inside it titled
another way would be two readings of one species on one page.
Rejected: the scientific name alone inside sentences, which needs a second display
rule. The wording question that leaves ("This commodity line lists 3 Bos taurus
(Domestic Cattle) animals…") is recorded as a follow-up for the designer in
section 7, not resolved in code here.

**D7 — No plants mirror.** The ruling's plants-parity invariant does not bite:
the high-risk plants journey asks the species as free text the trader copies from
the plant passport (`repos/trade-imports-plants-frontend/src/server/app/sets/high-risk-plants/journeys/linear/features/commodities/copy/copy.en.js:91-93`,
hint "For example, Quercus robur. Enter the species name as it appears on the
plant passport."), with no MDM list, no stored common name and no species-listing
page. There is no behaviour there to mirror, and `grep -rln "speciesLabel\|speciesLatinName\|latinName"`
over that repo's `src` returns nothing.

**D8 — The tests repo gets one seam of its own.**
`domain/animals/constants/commodity-lines.ts` is the single home every animals
spec and page object already takes its species facts from (`grep -rn "Bos taurus"`
over `tests`, `page-objects` and `domain` finds species names in that file alone),
and `AGENTS.md:12` makes `domain` the home for constants shared by specs.
Each line gains the common name MDM serves it, and the file gains one label
helper beside the two helpers it already exports at `:17` and `:19`. The checkbox
value helper keeps the scientific name (the checkbox value is the stored key
`code|scientific name`, `features/commodities/search/selection/line-key.js:3-4`),
and the card-title helper keeps the scientific name (D3).

**D9 — Each test layer spells the format out once, in its own shared home.**
`sets/live-animals/docs/testing.md:54-57` requires exactly this of a display
format: the arrival-date driver "spells the display format out rather than calling
`formatDisplayDate`, so a format regression fails the assertion instead of moving
expectation and actual together". So the format is spelled out in exactly two
places, each the shared home its layer already reads from:
`features/commodities/search/test-support.js` for the frontend's unit tests and
FIT specs, and `domain/animals/constants/commodity-lines.ts` for the tests repo.
Neither reads it back from `species-label.js`.
Rejected: restating it again in `fit/live-animals-journey.js`. That file already
imports the species rows from `test-support.js` (`fit/live-animals-journey.js:14-21`)
and re-exports them (`:34-40`), so a second copy there would be set-up held in two
places, and inc-026's fixture refresh would have to correct the common names
twice. The drivers read the label off the row instead (section 11).

**D10 — Merge resolutions, tests repo.** No resolutions file exists beside the
backlog (`ls workareas/shared/design-release-2-1/themes/commodities-and-reason/`
shows `backlog.json`, `build-args.json`, `logs`, `plans`, `prototype-differences.md`),
so each is decided here. Previewed with
`git -C repos/trade-imports-ins-tests merge-tree --write-tree --name-only --no-messages HEAD origin/main`,
which reports five conflicted paths. Resolutions are in section 1 and section 2.

**D11 — The frontend merge is a no-op.** `origin/main` (`f9d48dab`) is already an
ancestor of the branch head: `git -C ~/git/defra/trade-imports-workspace/repos/trade-imports-animals-frontend merge-base --is-ancestor origin/main HEAD`
exits 0, and `git log --left-right HEAD...origin/main` shows nothing on the remote
side. The loop's merge brings in no change and leaves no conflict; nothing in this
plan depends on it.

**D12 — The no-common-name proof uses real stub data, not an invented species.**
The frontend's own commodity stub holds species with a null common name
(`services/_capture/fixtures/commodities.json`: "Carnivora excluding Canis
familiaris, Felis catus, Mustela putorius furio" under 01061900, "Casuariiformes,
Rheiformes, Struthioniformes" under 01063300, two equine hybrids under 0101), and
so does the MDM stub the stack serves
(`repos/trade-imports-stub/src/main/resources/responses/mdmProductSearchResponses.json`,
where the "ostrich" search returns "Casuariiformes, Rheiformes, Struthioniformes"
under code 01063300 with `commonName: null`). Criterion 2 is proved against those,
so no fixture is invented and nothing has to be seeded.

**D13 — Searching by a common name now bolds inside the label.**
`search/view-model/labels.js:8-9` bolds the matched run of the label, so a search
for a common name, which matched the species but could never bold anything,
now bolds the bracketed part. That is what the bold requirement already states
("the part of a commodity heading or a species label that the search query
matched", `openspec/specs/live-animals/journey-pages/commodity-selection/spec.md:294`),
so it needs no requirement change — but it is newly observable and gets a test
(section 4).

**D14 — The species label order needs no change.** `search/view-model/result-order.js:9-10`
sorts by the label; because the label begins with the scientific name the order is
unchanged in every case the stubs hold, and the requirement text already says
"in order of the label they are offered under". The risk that a bracket sorts
differently from a letter is covered by the ordering assertions in section 4.

**D15 — The bracketed words are whatever the service serves, not the design
source's example.** The design source gives "Bos taurus (Cattle)"
(`confluence:6497338582`, claim `confluence-6497338582-p1-091`, quoted from the
Live Animal Data Elements table, Species selection, Example cell), and criterion 1
copies that example. No page will ever render that string, because no service
holds "Cattle" as Bos taurus' common name: the MDM stub the stack serves holds
"Domestic Cattle"
(`repos/trade-imports-stub/src/main/resources/responses/mdmProductSearchResponses.json:31-32`)
and the frontend's own commodity fixture holds "Cattle or Cow"
(`src/server/app/services/_capture/fixtures/commodities.json:47-48`). So this row
pins the **format**, and the words inside the brackets are the common name the
service answering that page serves. Each test layer therefore expects its own
service's value, which is what both shared homes already hold: the frontend's
`search/test-support.js:17-57` rows mirror the frontend fixture (Bos taurus →
"Cattle or Cow", Bison bison → "Bisons Spp"), and the tests repo's
`domain/animals/constants/commodity-lines.ts:8-14` copies the MDM stub's values
per `AGENTS.md:23` ("Copy test data from real canned data … Never invent it").
Neither layer hard-codes the other's value, and the E2E labelling pin reads the
service's own answer rather than any constant (T19).
Section 8 quotes the stack's value: the behaviour spec records what a user sees
through the real services, and every scenario whose quote this row restates is
covered by an E2E test running against the stack, so the quoted progress heading
reads "Enter details for Bos taurus (Domestic Cattle) 1 of 3".
Rejected: quoting the design source's "(Cattle)" in the spec, which no run of the
service can satisfy, and rejected: changing either stub so the example string
appears — inc-026 owns the fixture, and the MDM capture is not ours to edit.
The divergence from the design source's example goes to the designer as a
section 7 follow-up.

**D16 — The identification card's baselines are regenerated under the stack, by
the operator, and the plan says when.** The visual spec captures a card for
`commodityLines.domesticCat` (`tests/animals/e2e/visual/identification-card.visual.spec.ts:10-12`),
and the MDM stub serves Felis catus the common name "Domestic Cat"
(`mdmProductSearchResponses.json:186-187`), so both the card title and the
progress heading on that screenshot change and **both** committed baselines go
stale: `identification-card-chromium-darwin.png` and `-chromium-linux.png`.
`@visual` is not excluded from CI — `test:docker-compose:ci` inverts only
`@a11y|@active|@dynamics` (`repos/trade-imports-ins-tests/package.json:45`), and
that is the script the workspace reusable workflow runs
(`.github/workflows/e2e-tests.yml:207-211`), unscoped for the tests repo's own
pull request and scoped to `tests/animals/` (which holds the visual spec) for the
frontend's. So a stale baseline reddens both pull requests.
Every route to regenerate needs the workspace stack: `test:visual:update:macos`
resolves to `_test_docker_compose`, `test:visual:update:linux` resolves to
`bin/update-visual-baselines-linux.sh`, whose header states "Prerequisites:
workspace stack running", and `test:docker-compose:visual` likewise. This run
takes no stack, so the implementor cannot regenerate either file.
Owner and sequencing: the operator who holds the theme's workspace stack
regenerates both baselines in one pass — the linux file first, because it is the
one CI compares, then the darwin file, then the compare run — and commits them
onto `feat/EUDPA-693-commodities-and-reason` before either repo's pull request is
judged. Section 6 names the three commands, each marked as needing the stack.
Until that pass lands, `@visual` is the increment's one known-red check and it is
owned, not ignored: it is named here, in section 5 and in section 6 so the build
run's handover carries it.
What the implementor does in the meantime: leave the spec and both PNG files
exactly as they are. No hand-edited image, no retagging or skipping the spec, no
`--update-snapshots` added to a committed script, and no loosening of the
screenshot assertion.
Rejected: excluding `@visual` from `test:docker-compose:ci` so the increment lands
green. That would hide a real regression check from every repo's pull request for
every future change, far outside this row's footprint, and would leave the
baseline wrong anyway.
