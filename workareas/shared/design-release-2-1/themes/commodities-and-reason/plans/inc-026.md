## 0. Decisions

**D1 — The increment's claim that "the recapture is a run rather than new code" does not hold. The fixture
is derived from the stub's saved MDM search by hand, not refreshed through the stack.**
`capture.js` asks reference-data for `/commodities?q=010&size=100` and pages until the species it has collected
reach the `total` the answer reports. Reference-data caps one answer at the requested size, at most a hundred
species (`CommoditySearchService.search`, `MAXIMUM_PAGE_SIZE`), and the stub answers a saved page for page 0 only
and an empty page for every later page (`ProductController.search`). So a run of `npm run capture:live-animals`
against the stack today collects the first hundred of the three hundred and ten species the stub's `010` search
yields, across thirteen of the twenty-six codes: it would delete `01061900`, `01063300` and eleven other codes
from the fixture and gut the journey's stub-mode tests. Checked by reading both services and by counting the
stub's
`010` response.
Settled: the fixture is rewritten as the full set reference-data's mapping yields from the stub's saved `010`
search — every species row with a Latin name, in the order the response lists them, grouped by code in
first-appearance order, each code's species in first-appearance order, the common name kept as served and `null`
where the response has none. That is what the fixture is documented to hold and what the stack would serve if it
could answer the whole list in one page. There are no duplicate code-and-Latin-name pairs in the response, so the
mapping's de-duplication changes nothing and the derivation is unambiguous. The regenerated catalogue holds the
same twenty-six codes the fixture holds now (checked: the code lists are identical), so no obligation allow-list
gains or loses a code.
Rejected: running the capture script and accepting the hundred-species truncation — it loses thirteen commodity
codes and every species the identification, consignment-details and permanent-address tests select. Also
rejected: adding a generator to the frontend that reads the stub repo's file — the stub's file is not in the
frontend's checkout, so such a script could never run in CI, and it would be a second capture mechanism beside
the one that exists.

**D2 — Acceptance criterion two is met in two halves, by two pins of one agreed vocabulary. Neither half is
the whole-list comparison, and the plan does not claim otherwise.**
The drift the criterion names has two ends, and no CI job holds both files: the fixture lives in the frontend's
checkout and the MDM data lives in the stub's. Measured honestly:

- *The frontend end.* The fixture contract `src/server/app/services/_capture/fixtures.test.js:51` compares the
  loaded fixture against literals in the same repo. It fires only when the fixture is edited or regenerated away
  from the pinned names. It does **not** fire when the stub is recaptured and the fixture is left behind —
  nothing in the frontend's checkout reads the stub. What it proves is that the fixture cannot silently move off
  the agreed vocabulary.
- *The stub end.* The tests repo pins the same vocabulary in
  `domain/animals/constants/commodity-lines.ts` and asserts those full labels against the running stack through
  `page-objects/animals/commodity-selection-page.ts:66`. The stub repo has no entry in
  `config/e2e-tests-pr-scope.json`, so a stub pull request runs every suite, `tests/animals/` included. A
  recapture of the stub that changes one of those names is therefore already red on the stub's own pull request.
  That is the half that catches "the next MDM recapture leaves the fixture behind".

Together the two pins hold the agreed vocabulary in step at both ends. What neither covers is the rest of the
list: today the whole-list comparison (section 5's `jq`) reports `{missingFromFixture: 111, notServed: 138}`, and
after the regeneration it reports `"in step"` — but it is an ad-hoc query over two checkouts, and it has no home
inside this row's repos. The frontend cannot read the stub's file; the tests repo holds neither file; a workspace
`tim` subcommand would be a third repo this row does not own.
Settled: the pinned vocabulary covers **every species the frontend's own shared test rows spell out, plus every
species the tests repo pins** — the union, so the two repos pin one set. That is nine code-and-species triples:
`0101` / `Equus cabalus` / "Horse"; `0102` / `Bos taurus` / "Domestic Cattle"; `0102` / `Bison bison` /
"American Bison"; `0102` / `Bubalus bubalis` / "Water Buffalo"; `01051111` / `Gallus gallus` / "Chicken";
`01061900` / `Felis catus` / "Domestic Cat"; `01061900` / `Nyctereutes procyonoides` / "Raccoon Dog";
`01061900` / `Mustela putorius furo` / "Ferret" (the ferret row of D3); and `01063300` / `Struthio spp.` /
"Ostriches" (the ostrich spelling of D2a). Each is asserted against the loaded fixture with its code, its exact
Latin name and its exact common name. This follows the repo's existing pinned-vocabulary contract,
`src/server/app/services/mapper-a-enum-contract.test.js`.
The whole-list comparison is carried by the open question recorded on the increment row (backlog.json, inc-026
`openQuestions`), alongside the section 7 follow-up: **"A committed check compares the animals frontend's
captured commodity fixture with the stub's saved MDM product search, so the whole list stays in step"** (section
7). Until that lands, the whole list outside the nine pinned species is held only by the stack's own e2e suite
reading reference-data live.
Rejected: committing a copy of the frontend fixture into the tests repo beside the country and port copies
(`resources/reference-data/paths.ts`) and comparing that copy with the stack — it adds a third copy that can
itself go stale, and it would prove the tests repo's copy right rather than the frontend's fixture. Also
rejected: calling the frontend-side pin "the check acceptance criterion two asks for" — it is one half of it, and
saying otherwise would claim a drift check that cannot fire on the drift it names.

**D2a — The ostrich is spelled `Struthio spp.` in the frontend's shared rows, so the two repos name it once.**
The frontend's shared rows spell it `Struthio`
(`.../commodities/search/test-support.js:13`); the tests repo pins `Struthio spp.`
(`domain/animals/constants/commodity-lines.ts:17`). The recaptured stub serves both as separate rows under
`01063300` with the same common name "Ostriches", so either works in stub mode — but the pre-flight note records
that real MDM serves `Struthio spp.` and that the bare `Struthio` divergence broke two specs on cdp test, which
the tests repo worked round in its own constants.
Settled: the frontend's shared row and its label take `Struthio spp.`, so one concept carries one name across the
twin repos and the frontend's row names a species real MDM also holds. Every consumer reads the row or the
constant rather than spelling the name, so only `test-support.js`, the golden oracles and the fixture contract
carry the change. The browser driver that ticks a species already matches its label exactly
(`fit/live-animals-journey.js:595-599`), so the two "Ostriches" rows under `01063300` stay distinguishable.
Rejected: changing the tests repo to the bare `Struthio` — it would reintroduce the cdp-test breakage the tests
repo worked round. Also rejected: leaving the two repos spelling it differently and arguing they are two distinct
reference-data rows — the two repos then name the same test subject two ways, and the frontend's row names the
spelling real MDM may not hold.

**D3 — The shared species row standing for the dog is replaced by the ferret.**
The stub's recaptured MDM data holds no `Canis familiaris` under any search term: `grep -c "Canis familiaris"`
returns `0` over both `mdmProductSearchResponses.json` and `mdmProductSpeciesResponses.json`, and `01061900` now
names its genera with an `spp.` suffix (82 species, `mdmProductSpeciesResponses.json`'s own
`totalElements` for that code). The frontend's shared test rows carry a `Canis familiaris` row that six spec
files select from the stub search, two of them for the permanent-address gate.
Settled: that row is replaced by `Mustela putorius furo`, which the stub serves under `01061900` with the common
name "Ferret" and which `PERMANENT_ADDRESS_SPECIES` in
`src/server/app/sets/live-animals/services/commodities/rules.js:65-70` also lists, so every test keeps its
subject: a second permanent-address species under `01061900` beside the domestic cat.
Rejected: keeping a `Canis familiaris` entry in the fixture that the stub does not serve — that is the exact
drift this row closes.

**D3a — Open question: whether real MDM still holds `Canis familiaris`. This row does not settle it, and does
not assert either answer.**
The only MDM capture any of this row's repos can read is the stub's, and the stub's current data is a recapture
of real MDM in TST (`repos/trade-imports-stub` 5cf8a70, "fix(EUDPA-617): recapture the MDM product responses from
TST"). That capture does not spell `Canis familiaris`. So the evidence available says the spelling MDM serves for
the domestic dog has moved; nothing available says real MDM still holds the old spelling. `rules.js:65-70` keeps
the entry, `openspec/specs/live-animals/journey-obligations/commodity-selection/spec.md:105` states it, and
`src/server/app/sets/live-animals/docs/services.md:63-64` describes it as "MDM's dog".
Settled: the plan records the unmatched rule entry as an open question and leaves `rules.js` and the obligations
spec alone, because correcting a stated obligation on a TST snapshot alone could drop a gate real MDM still
reaches. It is carried by the open question recorded on the increment row (backlog.json, inc-026 `openQuestions`),
alongside the section 7 follow-up: **"Confirm against real MDM whether the domestic dog is still spelled `Canis
familiaris` under 01061900, and correct the permanent-address rule, its obligations spec and the set's services
doc together"** (section 7). This row's own `services.md` edit states only what is checkable from
the frontend's checkout: which species the served catalogue can reach the gate with, and that the rule also lists
a dog spelling the served catalogue does not hold (section 12). The departure from `services.md:55-58`'s "a rule
keyed by a Latin name … has to follow it" is recorded in section 14.
Rejected: dropping `Canis familiaris` from `rules.js` in this row — it changes an obligation the behaviour spec
states, on evidence that does not reach real MDM. Also rejected: asserting in the plan that real MDM still holds
it — no source available says so.

**D4 — Stored answers in the journey's flow and characterisation fixtures follow the new names.**
`src/server/app/sets/live-animals/journeys/linear/flow/fixtures/happy-path.json:12` stores a cattle line whose
common name is the old one, and `fixtures/characterisation-corpus.js` builds its corpus from both that file and
the shared species rows, so the golden oracles in
`src/server/app/sets/live-animals/journeys/linear/fixtures/characterisation-oracles.json` carry the old cattle and
bison common names and the old ostrich spelling too.
Settled: the stored seeds and the oracles follow, so the service has one name per species across the repo.
Rejected: leaving the seeds alone as "just stored answers" — it leaves two names for one species in one repo,
which the house rules forbid, and the corpus already mixes the two sources.

**D5 — The hundred-species cap is proved by a search that matches more than a hundred species, not by one
commodity code.**
No code in the regenerated catalogue holds more than a hundred species; the largest is `01063200` with
eighty-four and `01061900` with eighty-two. A query that is a prefix of several codes still matches far more than
a hundred: the `0106` prefix reaches 261 species, and `search.fit.spec.js:380` already drives that query.
Settled: the two tests that prove the cap (one unit, one browser) search a code prefix that reaches several
codes, so both the group list and the hundred-species count follow the prefix rather than one code. The scenario
in the Behaviour Spec is reworded to match (section 8).
Rejected: raising nothing and letting the cap go unproven.

**D6 — No change in the tests repo beyond the no-op merge.**
`domain/animals/constants/commodity-lines.ts` already carries the stub's names and the `Struthio spp.` spelling
D2a adopts; the specs already assert them against the stack. Adding a second assertion of the same names would be
a test added for its own sake.
