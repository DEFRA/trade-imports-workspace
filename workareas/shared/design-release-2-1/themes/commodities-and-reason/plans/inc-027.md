## 0. Decisions

1. **Why the numbers are lost today is the page's two forms, not only the round trip.** The row's
   notes say the fix is "carrying the submitted values through the remove round trip rather than
   re-reading the saved answers". That is half of it. `consignment-details.njk:13-17` is one form
   holding the crumb, the concurrency token and the Selected commodities table (whose Remove
   controls are submit buttons, `common/constants/table-cells.js`), and
   `consignment-details.njk:23-35` is a second form holding the quantity inputs and the save
   actions. A Remove press therefore posts a body with no quantity fields in it at all: there is
   nothing to carry. So the change is two things: one form, so the typed numbers reach the POST,
   and a response that shows them back.
2. **One form, not hidden mirrors of the inputs.** The alternative — keeping both forms and
   copying the typed values into hidden fields in the table's form — needs JavaScript to stay in
   step with what the trader types, and the programme's no-JavaScript invariant rules it out. One
   form is also what the sibling search page already is (`search/search.njk`: the search box, the
   per-species removals, Clear all and the save actions all in one form).
3. **The page answers a removal with itself instead of redirecting, and that is a departure, not
   a case the repo doc already allows.** A redirect cannot carry the typed numbers, so there were
   three candidates:
   - *(a) persist the typed numbers as part of the removal and redirect.* Rejected: it would write
     unvalidated text into the notification — "abc" in a number of animals would then be stored,
     read by the obligation evaluation, shown on the review and sent to the backend — and the
     programme invariant that a save "still refuses an answer that fails its own format rule" says
     a value that fails its format is never stored.
   - *(b) stash the typed numbers in the journey's flow-only state and redirect, the GET consuming
     them.* Rejected: it is a second mechanism for carrying one page's unsaved work beside the one
     the repo already has (rendering from the POST), it needs consume-once semantics nothing else
     in this feature has, and it makes two more states reachable — a GET that finds a stash left by
     a navigation the trader abandoned, and a Back that re-reads one. The flow-only store does
     exist (`search/selection/rows.js:29-41` keeps the stored search rows there), which is why this
     was a real candidate rather than a straw man.
   - *(c) render the page from the POST.* Chosen. The shape to follow is the transit countries page,
     which re-renders after Add and Remove
     (`transport/transit-countries/transit-countries.controller.js:157-168`).
   What (c) costs: `src/server/app/docs/architecture.md:149` states "A POST that saves redirects
   (post, redirect, get)", and the exception it lists at `:156-157` is the transit countries page,
   *because* that page does not save — "it holds its working list in hidden fields until Continue".
   This removal does save: `remove/post-remove.js:42` and `:63` both call
   `state.reconcileEntriesAt` before the response is built. So this page is a POST that saves and
   renders, which the stated rule covers and the stated exception does not. That is a departure
   from a written rule, recorded in section 14, and section 12 has the doc state the fact
   afterwards. Decision 11 closes the hazard removing the redirect would otherwise open.
4. **The typed numbers are matched to the lines that stay by the line's key, not by field name.**
   Field names carry the line's position (`consignment-details/fields.js:13-14`), and a removal
   renumbers the lines that stay. The existing FIT test at
   `commodities/fit/consignment-details.fit.spec.js:335-358` already pins that: after removing
   the first commodity the second line's count must appear in the first field. The key a line is
   already identified by is `search/selection/line-key.js:3-4`, which is also what
   `reconcileEntriesAt` reconciles the collection by. Matching on anything else (position, label)
   is rejected as a second identity for one concept.
5. **A field the rendered page never posts falls back to what is stored, and that is a plain
   default with no log.** The packages input is only rendered where the commodity takes one
   (`_species-quantities.njk:18` guards it on `group.showPackages`, set at
   `view-model/groups.js:20` from `packagesApply`). So an ordinary removal post carries no packages
   field for those lines, every time, for every trader. Showing the stored value there changes no
   outcome and is not a fallback branch in the house-rule sense; logging it would put a line in the
   log on every ordinary removal. This is the same shape as the two defaults
   `view-model/values.js:11-12` and `:17-18` already apply.
6. **A post that names, for a surviving line, none of the counts the page renders for it (the
   animal count always; the number of packages where the commodity takes one) is an anomaly,
   owned in one place and logged once.** Every line the page renders posts its animal-count field,
   blank or filled, and posts its packages field too wherever the commodity takes one, so a
   surviving line the post carries no rendered count for — whichever of those fields it is missing
   — means the post was not made from the page as rendered — a line added in another tab or window
   since the render, or a tampered post. It is
   honoured rather than refused, because refusing would throw away a removal the trader did press
   over a line they cannot see; the page shows that line's stored values. Because it changes an
   outcome, it logs once, at warn, exactly as the mirror anomaly on the sibling search page does
   (`search/search.controller.js:112-117` honours a selection naming rows the store does not hold
   and logs it at warn). Section 13 records what that line must carry. This is a different rule from
   Decision 5 and has a different home and a different owner.
7. **Enter in a quantity field must keep saving the page.** With one form the first submit button
   in the form is a Remove, so Enter in a number box would remove a commodity. The repo's answer
   is already on the sibling page: `animal-identification.njk:32` puts a visually hidden,
   `aria-hidden`, `tabindex="-1"` submit button first in the form so Enter hits it. This page's
   copy of that guard carries no name and no value, so an Enter post is indistinguishable from
   pressing the page's primary save and the controller needs no branch for it (the identification
   page needs a named action there because its controller decides which cards to read; this one
   does not — build only what is reachable). Its text reuses the shared save-and-continue string
   (`shared/copy.en.js:64`), so no new copy and no Welsh draft. Rejected alternative: naming the
   action, which would add vocabulary nothing reads. While the journey is being amended, the guard
   posts to the URL the page was opened at, which is what both amend save buttons post to —
   `shared/amend-form-actions.js:31-41` builds them from that same path and tells them apart by
   `change=1` on the URL, and `kit.amendReviewTarget` (`shared/kit.js:238-241`) reads the request's
   change context — so Enter while amending lands where the page's own URL already says, the same
   behaviour the sibling page's guard has.
8. **Where the change context goes.** Today `afterRemoval` wraps the page path it redirects to in
   `kit.withChangeContext` (`consignment-details/remove/post-remove.js:25-30`). With the page
   rendered from the POST there is no redirect to wrap: the rendered form posts back to the
   request's own URL, which already carries `change=1`, and the back link comes from
   `kit.runBackLink` as on every other render. The empty-selection redirect keeps
   `commodityQuestionPath`, which wraps the context itself
   (`commodity-question-detour.js`).
9. **The removal still runs no answer validation.** A removal is not a save, so the page comes
   back with no errors and status 200, as a removal shows no errors today. The count-drop check
   (`consignment-details/validation/count-drop.js`) stays on the save path only.
10. **Plants is not mirrored, because it has no page with this shape.** The programme invariant
    asks for plants whenever a page it also has changes. The high-risk plants journey splits the
    collection differently: its list page has a removable row per line and no quantity inputs at
    all, and its details page is a single line's entry form with no removals. There is nothing
    typed to lose on the page that removes, so the invariant does not bite and the row's repos
    stand. (Checked against the plants frontend's commodities feature; the animals repo in this
    workspace holds only the live-animals set, so there is no sibling set to mirror either.)
11. **The removal names the entry it removes, not its position — in this increment, not a
    follow-up.** Today a removal addresses a line by its index: the action values are built from
    the group's position and the line's position (`view-model/selected-rows.js:7-10`) and the
    handlers index into the collection (`remove/post-remove.js:35` and `:49`). While the removal
    redirected, a browser resubmission of it was not reachable. Rendering the page from the POST
    (Decision 3) makes it reachable — a refresh, or Back then Forward, re-posts the same action —
    and a posted concurrency token does not stop it, because the handler has already read state and
    `engine/journey.js:105-112` then prefers the memoised journey as the known version. An index
    resubmitted after the collection has shifted names a different line, so the page would delete a
    commodity the trader never pressed. That is the regression the redirect was holding off, and
    `sets/live-animals/docs/page-design.md:270-273` and `:484-486` already state the rule for the
    two sibling removals in this set: the entry rides in the button value so the row pressed is the
    row removed however the list has been reordered. So this increment re-keys both of this page's
    removals to the entry: the commodity-level removal names the commodity code it drops every line
    of, and the species-level removal names the line's key, the same key
    `search/selection/line-key.js:3-4` already defines and the search panel's own removal already
    posts (`search/selection/remove-action.js:4`). A resubmitted removal then names something the
    selection no longer holds and is refused with a bad request and one logged refusal, which is
    what `page-design.md:274-280` already states for the search panel's equivalent. The cost is the
    action module, the row builder, both handlers and the tests that assert a button's value; it is
    the row's own hazard, so it is the row's own work.
12. **The posted concurrency token is still not checked, and this row no longer needs it to be.**
    `engine/journey.js:105-112` ignores a posted token once the request has read state, so a stale
    post is not refused as stale. With Decision 11 in place a stale or repeated removal can only
    name an entry that is already gone, which is refused; it can no longer delete a line the trader
    did not press. Whether a write should check the posted token at all is wider than this page and
    goes to the backlog as a follow-up (section 7), not into this increment.
13. **The theme ordering note is spent.** The row's third note asks for this to land before or
    with the number-of-packages hard stop. That increment is already `done` in the theme backlog,
    so there is no ordering left to honour; the note needs no action.

## 13. Operability

One branch this change adds changes an outcome, and it logs.

- **A post that names, for a surviving line, none of the counts the page renders for it** (the
  animal count always; the number of packages where the commodity takes one) (Decision 6). The
  page shows that line's stored values instead of what the post carried, because the post carried
  no rendered count for it — a fallback, and the only branch here that chooses a different outcome
  from the ordinary one. It logs once, at warn, at the controller, as
  `search/search.controller.js:112-117` does for the same shape on the sibling page. The line must
  let support find: the journey, by its id; which line or lines it concerns, by the key that
  identifies a line; and which removal was being answered, by what that action named. Warn rather
  than info because nothing downstream refused anything and no trader did this by filling the form
  in — the post did not come from the page as rendered.

Branches the change leaves as they are, each already logging once at its owner: a refused removal
answers 400 and logs its reason (`remove/post-remove.js:36-39` and `:50-60`) — now naming the

Not a branch that changes an outcome, and deliberately not logged: the packages field on a line
the page renders no packages input for, falling back to the stored value (Decision 5). The
packages input is only rendered where the commodity takes one, so an ordinary removal carries no
packages field for those lines every single time; this is the value the field always shows, not a
different outcome chosen for an unusual post, and a log here would fire on every removal and bury
the line above.

## 14. Departures from written rules

- **`repos/trade-imports-animals-frontend/src/server/app/docs/architecture.md:149`** — "A POST
  that saves redirects (post, redirect, get): to `kit.nextTarget()` on success, or to the page a
  refusal names." And `:156-157`, the exception it names: "the transit countries page re-renders
  after Add and Remove, because it holds its working list in hidden fields until Continue."
  This increment has Commodity details save a removal and then render the page, so the write and
  the render are one request. The stated exception does not cover it: transit countries is excused
  because it does not save until Continue, and this removal does save
  (`remove/post-remove.js:42` and `:63` both call `state.reconcileEntriesAt` before the response
  is built).
  Why the row forces it: the acceptance criterion is that the numbers the trader has typed and not
  yet saved are still in their fields after the removal. A redirect carries nothing but a URL, and
  the two ways to carry the numbers across one are rejected under Decision 3 — persisting them
  would store a value that fails its own format rule, which a programme invariant forbids, and
  stashing them in flow-only state would add a second mechanism and two more reachable states for
  one page's unsaved work. The departure is bounded to this page's removal: the save path still
  redirects to `kit.nextTarget()`, the refusals still answer as they do, and the removal's own
  resubmission hazard is closed inside this row by naming the entry (Decision 11). Section 12 has
  the doc state the new fact, so the written rule and the tree agree once this lands.

## 15. Reachability
