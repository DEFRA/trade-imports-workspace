## 0. Decisions

1. **The cap is a value cap, not a digit count.** The row's open question names
   the value cap as its default; the source settles it. The V4 Type cell for the
   number of animals reads exactly `numeric - whole number, max
   9,223,372,036,854,775,807`
   (`workareas/shared/design-release-2-1/sources/6497338582.json`, the
   `number_of_animals_quantity` row's Type cell) and that figure is exactly the
   largest signed 64-bit integer, which is a storable-value limit, not a length.
   A 19-digit length rule would admit values above it, defeating the row's own
   stated reason for the cap. Rejected: a digit rule. Noted honestly — the same
   column writes "numeric - max 10" for the number of packages, which can only be
   a digit count, and that is why a question was raised; the number of packages is
   a different field this row does not change (follow-up below). Sam still owns
   the formal ruling; nothing here needs reopening if it lands as written.
2. **The open question's premise does not hold, in two ways.** First, the row
   says "its own examples are 25 and 5000, which read as digit counts". The
   column those sit in is headed "Example" and its cell for this field reads
   `1, 25, 5000` — example values, as every row in that table carries. They are
   not digit counts. Second, the question the row cites (c-325, which the
   programme report numbers 7, not 5) is about the **number of packages**, and the
   default it names is the digit reading, not the value cap. So the cited question
   does not in fact cover the number of animals at all, and nothing but the Type
   cell in decision 1 speaks to this field. Recorded as two claims corrected;
   planned against the source.
3. **The comparison must be exact, and the bound must be expressible exactly.**
   The shared comparison compares with `Number`
   (`lib/validate/validators.js:197-204`), and no JavaScript number holds the cap
   exactly: `9223372036854775807` and `9223372036854775808` both become the same
   value once read as a number. A bound written as a plain numeric literal is
   therefore already one too high, and a `Number` comparison accepts a value one
   above the cap as though it were the cap. So the comparison moves to exact
   integer arithmetic over the digits the field already proved, and the bound is
   carried in a form that holds the figure exactly. Rejected: leaving the
   comparison on `Number`, which makes the cap off by one and untestable at its
   boundary.
4. **The refusal gets its own message; the existing below-minimum wording is
   untouched.** Today one message covers "not a whole number" and "out of
   bounds" on the required form, and the live-animals wording for it reads as a
   greater-than-zero rule (`.../commodities/copy/copy.en.js:55`). A value of
   nineteen digits is a whole number greater than zero, so reusing that message
   would state something false. The comparison therefore distinguishes the bound
   that failed, and the required form takes a separate message for a value above
   the upper bound, falling back to the existing range message when a call site
   gives none. Rejected: one message spanning both bounds, which would reword the
   existing below-minimum error — a behaviour change this row was not asked for,
   and one the design source does not set.
5. **Both factories map the new outcome.** The optional form already offers an
   upper bound and is already tested at it
   (`lib/validate/validate.test.js:243-255`). Splitting the comparison's
   outcomes without mapping both on that factory would silently replace the
   message that option produces with Joi's own. Rejected: a second comparison
   step used only by the required form — two owners for one rule.
6. **The cap lives in the animals validator in the feature, not in
   `lib/validate`.** `lib/validate` holds no policy: the date window's bounds
   are built in the journey feature for the same reason
   (`src/server/app/docs/validation.md:97-102`). One function states the figure.
7. **No hint on the field, and no change to its width.**
   `sets/live-animals/docs/page-design.md:288-289` records that the number of
   animals question carries no hint because the page repeats the question per
   species. The cap is told through the error only. The input's width class is
   cosmetic and the row does not ask for it.
8. **The message is a function of the cap, and the validator owns the figure.**
   The set holds both precedents: `IDENTIFIER_MAX_LENGTH = 58` sits in the
   validator (`.../commodities/animal-identification/identifier/fields.js:25`)
   while "58 characters or less" is spelled out in the copy
   (`.../commodities/copy/copy.en.js:116-120`), and against that, `capReached`
   and `countDrop` are message functions taking the figures they name
   (`copy.en.js:142`, `:57`). This change takes the second: the copy entry is a
   function of the cap, the animals validator passes it the bound it already
   holds, and the copy function formats the figure with thousands separators
   (`docs/best-practices/gds/language.md`'s numbers rule puts commas above 999,
   which is also how the source writes it). Chosen because a spelled-out figure
   would state it in three files — the validator and both locale copy files —
   and the house rule gives one rule one owner. It also keeps the figure out of
   the Welsh string, where a stale copy would be hardest to spot. Rejected: a
   plain string per locale, the identifier-length precedent. The interpolation is
   asserted in the feature's own copy test, as every other message function in
   that file is (`.../commodities/copy/copy.test.js:90-97`, `:162-166`).
   Flagged for the designer under section 7: the source sets no error wording for
   this case, so the implementor is choosing copy for a case the design source
   does not show.
9. **The cap stays at the V4 figure, and the second acceptance criterion is
   knowingly not met above what the save path holds exactly.** The only store is
   the fulfilment: `engine/write/pipeline/canonical.js:23` calls
   `assembleFulfilments`, which applies each binding's `convert`, and the
   commodities binding converts the number of animals with `toNumberWhenParses`
   (`.../features/commodities/evaluation.js:40-46`,
   `:53-55`), after which `formValue` renders the rounded number back
   (`.../consignment-details/view-model/values.js:5-6`). Above
   9,007,199,254,740,991 that conversion rounds, so a value between that figure
   and the cap is accepted and then saved as a different number. Two ways out
   were open: lower the cap to the largest value the save path holds exactly, or
   keep the source's figure and record the gap. The second is chosen, because the
   figure is the one thing the source actually states for this field (decision 1)
   and lowering it would build a rule no source sets, while the fix for the band
   is a contract question reaching the notification mapper and the backend's
   schema, and the backend is not in this row's repos. Consequences, all carried
   explicitly: section 14 records the departure, naming the criterion it leaves
   untrue; section 7 raises it as an open question for Sam beside the
   number-of-packages question, not only as a backlog follow-up; the set's limits
   doc states the exact-storage figure beside the enforced cap so the doc is true
   rather than half-true; and the tests say which half of the criterion each one
   proves — T4 and T9 prove only that a value at the cap is **accepted**, and T5
   proves that a value at the largest figure the save path holds exactly is
   **accepted and stored as the digits typed**, which fixes the band boundary in
   a test rather than in prose. No test asserts the rounded value as though it
   were intended behaviour. Rejected: lowering the cap (builds an unsourced
   figure, and contradicts the one cell the row cites), and leaving the gap as a
   follow-up alone (the review's finding: nothing would then state that a
   criterion is knowingly left untrue).
10. **Plants is not changed.** The high-risk plants frontend has a commodity-line

## 2. Edits

### frontend `src/server/app/lib/validate/validators.js`

- The shared whole-number-in-range comparison (`:197-204`) must compare the
  submitted digits against each bound exactly rather than through `Number`, and
  must report a value above the upper bound as a different outcome from a value
  below the lower bound. It already proves the value is a run of digits before
  comparing, so exact integer arithmetic over that string is available without a
  second format check. Each bound reaches it in whatever form the call site gives
  and is normalised once, in this function, so neither factory and no call site
  carries a conversion.
- The two factories (`:208-219` optional, `:236-250` required) each map the new
  outcome to a message. The optional form maps it to the single message it
  already takes, so its existing upper-bound contract reads exactly as it does
  now. The required form takes a further, optional message for a value above the
  upper bound and falls back to the message it already uses for out-of-bounds
  when a call site gives none, so the one existing call site that passes no
  upper bound is unaffected. `requiredDateTextInRange` (`:345-358`) is the
  exemplar: it already takes a separate range message beside its invalid one and
  falls back the same way.
- The required form's doc comment (`:221-235`) states the bound as a number and
  says the invalid message covers out-of-bounds. Both become untrue: it must
  state the forms a bound may take and which message covers a value above the
  upper bound. No rationale in the comment — that goes to `docs/validation.md`
  below.
- The default fallback messages in `shared/copy.en.js:94-104` and
  `shared/copy.cy.js:92-102` are reused unchanged. Nothing is reworded there,
  per the programme invariant on shared copy.

### frontend `src/server/app/sets/live-animals/journeys/linear/features/commodities/consignment-details/fields.js`

required-form describe at `:256-307`.** Proves that, with an upper bound given

bound, so one above it is accepted.

`.../consignment-details/consignment-details.controller.test.js`, the
