## 0. Decisions

**The behaviour the row asks for is already built; this row proves it and records it.** Every one of the six
acceptance criteria was checked against the live tree and five of the six already hold. The hub-exit seam
journey-foundation built is `kit.requestSaveChoice` → `kit.hubExitTarget` → `kit.exitTarget` → `kit.nextTarget`
(`src/server/app/shared/kit.js:158-161, 179-182, 229-235, 298-304`), and both page controllers call
`validation.onSubmit` and return the page at 400 on any error **before** they reach `kit.nextTarget`
(`.../features/import-reason/controller.js:98-125`, `.../features/additional-details/controller.js:68-105`). The
save choice is read only inside `kit.nextTarget`, so no code path can relax a check for the hub exit. Both
templates end with the shared `saveActions` macro with no `showReturnControls` override, so both offer the hub-exit
button in every state (`src/server/app/shared/save-actions.njk:20, 37-57`; `.../import-reason/template.njk:83`,
`.../additional-details/template.njk:44`). The increment is therefore a verification-and-spec slice: new tests at
unit, FIT and E2E level that go red if the seam is relaxed, plus the behaviour-spec text and coverage links the
behaviour still lacks. Rejected: writing production code to "add" the rule — there is nothing to add, and a change
with no failing test to justify it would be invented work.

**Criterion 6 already holds, and the row's recorded delta for it is wrong.** The task rows already separate the two
pages: `taskRows` lists `importReason` with `[importReasonPage]` and `additionalDetails` with
`[additionalDetailsPage]` (`.../flow/task-rows.js:53-54`), so the reason row rolls up only the obligations the
import-reason page collects, and the hub puts them in different groups (`.../features/hub/controller.js:26-32`).
The existing unit test already asserts the reason row reads complete for Transit with its two follow-ups and for
temporary admission with its date and port, in each case with no Additional details answer present
(`.../flow/task-rows.test.js:90-118`); I ran it and it passes. The row's `req-168` deltaNote ("main's 'Main reason
for import' row completes only once the Additional details page after it is saved too") does not hold; inc-022's
2 November re-analysis note was right. So no code changes for criterion 6; the row adds the one regression the
existing tests do not carry — the Additional details row judged on its own two answers — and records that the
criterion already holds. Rejected: changing `taskRows`, which would break the behaviour the criterion asks for.

**The Additional details task's own completion has no requirement in the behaviour spec, so the regression lands
with one.** `REQ-OVERVIEW-008` states the reason row's rule and `SCN-OVERVIEW-008-A`'s first THEN is "Main import
reason reads Complete", which the regression never asserts because it drives with no reason saved throughout; its
existing e2e link already covers that scenario full. Nothing under `live-animals/` states when the Additional
details task itself reads To do, In progress or Complete. So the row writes that requirement and one scenario under
the overview capability and links the regression to it. Rejected: linking the regression to `SCN-OVERVIEW-008-A`, a
scenario whose THENs it does not assert; and rejected: adding the test with no link, which leaves observable
task-row behaviour unrecorded when the row is already writing spec text next door.

**The template half of criterion 3 cannot be built in this repo and belongs to its sibling row.** The animals
frontend has no notion of a template: the record statuses are draft, submitted, amend and deleted and nothing else
(`src/server/app/engine/persistence/records.js:3-6`, re-exported at `engine/index.js:15`), and a search over
`src/server/app` for a template identifier, flag or status finds none. So "while a template is being edited from
its review it saves the template and returns to that review" names a state the service cannot reach. The row's own
notes put every live-animals and germinal-products template page under `req-2202` in the
`type-question-and-templates` theme; that row owns it. The amend half of criterion 3 is built and is where this row
adds its proof. Rejected: building a template branch here — the house rules forbid building what this change does
not make reachable, and the spec forbids a scenario for an unreachable state.

**The blank-reason data loss stays open, and no test of this row pins it as desirable.** The open question is
real: `oneOf('reasonForImport', …)` accepts the empty string
(`src/server/app/lib/validate/validators.js:169-176`), so a blank reason passes on both save buttons; `revealsFor('')`
then returns no reveals and `toAnswers` emits only the blank reason
(`.../features/import-reason/validate.js:41-42, 135-145`), and the obligations purge the follow-up answers that fall
out of scope (`.../obligations/sections/import-reason.js:43-116`). Under c-372's default reading the page keeps only
the hard stops it already applies, and the reason field has none, so this row does not make the reason mandatory. The
criterion-5 test therefore asserts only what criterion 5 claims — that the blank page is accepted and the trader
reaches the overview — and asserts nothing about the follow-up answers being dropped, so answering c-372 the other
way does not have to unpick a test. Rejected: fixing the data loss here (it is c-372's, or a defect row of its own —
see Follow-ups) and rejected: asserting the drop, which would pin behaviour that is still being decided.

**The programme header's tenth invariant is withdrawn and this row follows the ruling that withdrew it.** See
section 14, which records the departure, the invariant quoted and the ruling.

**The merge the row asks for is a no-op.** `merge` names `origin/main` for both repos. After
`git -C … fetch origin`, `git merge-tree --write-tree --name-only --no-messages HEAD origin/main` printed a tree id
and no further line in either repo, so nothing conflicts, and `git log HEAD..origin/main` is empty in both, so
nothing comes in. There is no resolution to plan and no cleanly-merged-but-wrong file to flag. The loop runs its own
merge mechanics.

**Criterion 2's divergence exists only inside the opening sequence, so every proof of it — unit, FIT and E2E — is
driven there.** Outside the sequence `kit.nextTarget` falls through to `nextInTaskRow`, which for the main import
reason page is the hub (`.../flow/dispatch.test.js:37-42`), and the existing unit test at
`.../features/save-actions.test.js:77-87` asserts Save and continue lands on the hub there too: both buttons land on
the overview, and a test at that point proves nothing about the difference. Inside the sequence Save and continue
goes to commodity details from the reason page and to the port of entry from additional details
(`.../flow/opening-run.test.js:220-238`), while the hub exit goes to the overview. The new unit tests go in
`opening-run.test.js`'s existing "explicit exits beat the run" group, beside the commodity-selection twin already
there; the new FIT test reaches the reason page mid-sequence through `carryOpeningRunToImportReason`
(`fit/live-animals-journey.js:555-567`); the new E2E test reaches it the way `tests/animals/e2e/journeys/opening-run.spec.ts:56-62`
already does, from the origin page without passing through the overview. Rejected: an E2E test reached through
`animalsJourney.toImportReason()`, which runs `startNotification()` and so opens the overview before the page is
reached (`flows/animals/journey.ts:126-134, 501-506`) — the run is over by then, both buttons land on the overview,

`SCN-FLOW-004-B` by `tests/animals/e2e/features/task-page-exits.spec.ts:5-25` and
`.../features/save-actions.test.js:65-75`.

**The opening-run walk as far as the main import reason page becomes a method on the tests repo's journey flow.**
The new E2E test needs it, and it is already written out five times — in each of `flows/animals/journey.ts`'s four
`walkOpeningRun*` methods (`:622-637`, `:660-675`, `:725-740`, `:785-800`) and inline in
`tests/animals/e2e/journeys/opening-run.spec.ts:56-62`. The five differ only in the origin answers and the chosen
species, so one method taking those serves all of them, and promoting it deletes every copy. Rejected: a sixth copy
in the new test, which the test-support rule forbids; and rejected: a local helper in the new test's own spec file,
which would leave the five copies standing.

**Criterion 1's rendered proof is two tests, one submission each.** The two scenarios it answers ask for different
submissions — one with the port of exit and the destination country both blank, one with a destination country
given and no port of exit (`openspec/specs/live-animals/journey-pages/import-reason/spec.md:107-112, :219-224`) — so
one test cannot witness both. Rejected: a single test submitting both states, which would match neither scenario's
GIVEN as written.

**The Additional details task name stays a local module constant in the spec file that needs it.** The file the row
edits already keeps its three sibling task names that way
(`tests/animals/e2e/features/save-and-return-checks.spec.ts:8-12`), so the new test needs no new module and no
change to `flows/animals/journey.ts`. Rejected: promoting the name into `domain/animals/constants/`, which no
criterion needs and which would leave the value copied in 17 further places across the security, a11y and e2e specs
and the page object; that whole promotion is a follow-up (section 7), not this row's.

**No `frontend-change` recipe routes this row.** It adds no field, page, section or collection, and changes no
obligation and no journey flow; the set is `sets/live-animals`, spec namespace `live-animals/`. Section 8 is written
by hand against the spec as it stands.
