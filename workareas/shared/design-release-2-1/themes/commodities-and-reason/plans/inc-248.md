## 0. Decisions

**The merge the row asks for is already in.** `merge` names `origin/main` for the tests repo.
`git -C repos/trade-imports-ins-tests rev-parse --short origin/main` is `b58d91c`;
`git merge-base --is-ancestor origin/main HEAD` exits 0, and `git log --oneline HEAD..origin/main` is empty.
`git merge-tree --write-tree --name-only --no-messages HEAD origin/main` prints one line — the tree id
`0c429e21…` — and no conflicted path. So there is nothing to resolve and nothing merges cleanly-but-wrongly.
The loop's `git merge --no-ff --no-commit origin/main` will report already-up-to-date and stage nothing, so
there is no two-parent merge commit to make for this row. Rejected: planning resolutions for a merge that
has no conflicts.

**The walk searches the commodity list by code prefix, not by a common name.** The stack runs the animals
frontend with the real reference-data path (no stub mode), so the commodity search reaches reference-data,
which reaches the MDM stub. That stub answers only search terms saved verbatim from MDM
(`repos/trade-imports-stub/.../ProductController.java:77` looks the trimmed, lower-cased term up in a map).
There is no saved term `chicken`, `Gallus` or `0105`; the only saved term whose results carry chicken is
`010`, whose page holds 45 MDM rows including the commodity `01051111` with the species `Gallus gallus`
(common name Chicken). Rejected: a species-name search term, which the stub answers with an empty page.

**That search term is safe at the frontend's page size, and I measured it.** The frontend asks for 100
results (`.../features/commodities/search/search.controller.js:37`) and reference-data lists at most that
many distinct code-and-Latin-name matches (`CommoditySearchService.java:50`). The `010` page yields 310
distinct pairs; the chicken pair is the 91st in first-appearance order (`jq` over the stub fixture), so it
is listed. The tests repo's own README already states this rule for a commodity line's search term
(`repos/trade-imports-ins-tests/README.md:185-193`), so no README change.

**The commodity line needs both the code and the Latin name.** The commodity page labels each tick box with
the Latin name alone under a heading of the code, and `Gallus gallus` sits under two codes in that same
search page (`01051111` and `01059400`), so the walk must scope the tick box to the code. The existing
commodity-line shape already carries both.

**The walk uploads an accompanying document, which the row's first criterion does not mention.** The third
criterion needs every overview row to read Complete. The documents group has no minimum entries
(`sets/live-animals/obligations/sections/documents.js:19-28`), so with no document the row rolls up as
optional, and the hub renders anything that is not fulfilled as To do
(`.../features/hub/controller.js:50-52`). The two existing opening-run walks both upload one for the same
reason. Rejected: leaving documents empty, which contradicts the third criterion.

**The walk also fills the transport document reference, which the row's first criterion does not mention.**
It is unconditionally mandatory (`obligations/sections/transport.js:81-85`), so the arrival row cannot read
Complete without it. The design source's poultry scenario sets only a transport identification; the real
page asks for both, and a mandatory real field is not a design difference.

**The destination country reads "Ireland", not the design source's "Republic of Ireland".** The transit
destination list is reference-data's origin-country list, which names `IE` "Ireland"
(`repos/trade-imports-ins-tests/resources/reference-data/countries-origin.json`), and a tests-repo spec
asserts the list is exactly that (`tests/animals/e2e/features/reference-lists/destination-country-list.spec.ts:26-38`).
The label difference between that list and the prototype's own list is already a recorded, separately-owned
difference (the DR1 parity record names Czechia/Czech Republic, Ireland/Republic of Ireland and
Netherlands), and the merged horse walk set the precedent: its row said "origin Republic of Ireland" and the
spec asserts "Ireland" (`tests/animals/e2e/journeys/horse-temporary-admission.spec.ts:32`). So the walk picks
`IE` and the plan expects "Ireland". Rejected: asserting the prototype's wording, which the real list does
not serve, and changing the list, which is another row's work.

**The transporter is one the real service ships.** The design source's poultry scenario picks "Danish Meat
Export ApS", which is not in the frontend's transporter register
(`repos/trade-imports-animals-frontend/src/server/app/services/transporters/records.js:45-122`, which ships
two commercial and four private records). The criterion says only "the chosen transporter". The walk picks
the one commercial record that already has a home in the tests repo's transporter constants, and the review
assertion reads that constant. The register's difference from the prototype's four is a separate backlog
row in the parent workarea, not this one. Rejected: inventing a transporter record (test data is copied,
never invented) and reusing the horse walk's exported transporter constant, whose name predicts the horse
journey.

**The arrival port follows the design source; the exit port already has a home.** The design source's
poultry scenario arrives at Dover and exits at Holyhead. The port-of-entry list is not filtered by means of
transport (`.../transport/port-of-entry/port-of-entry.controller.js:39` lists every port), so a seaport for
a rail arrival is accepted. Holyhead is already in the tests repo's port constants; Dover is not and gets an
entry there, read through the same captured-reference-data lookup the others use.

**The overview expectation is a second, explicit list beside the existing one, and it reads the one row
title that already has a home.** The existing exported opening-run task list carries "Identification
details" and no "Transit countries", which is the wrong list for this consignment, so the new list states
all eleven rows in hub order. One of those eleven titles is already a shared constant — the main import
reason's, in `domain/animals/constants/import-reason-page.ts:3`, which the existing list reads at
`flows/animals/journey.ts:59` rather than retyping. The new list reads it from the same place. The other ten

the new list from the existing one by removing one row and inserting another, which hides the order the
