## 0. Decisions

**The conflicted spec's wait is resolved to the mechanism that already exists, and the theme's own
species-label change is kept on top of it.** The conflict is three hunks, and no single side is right for
all three. `origin/main` carries the wait helper that lives beside the poll timeout, annotation and
`pollOptions` it uses, and it has two caller files; the branch's helper was born in the theme's own
engineering-review commit with one caller file. The house rule is to extend the mechanism that exists
rather than stand a second one beside it, so the wait comes from `origin/main` and the branch's helper
file goes. The species common name, which the branch moved off the one-constant file and on to the
commodity-lines constants, is the theme's own work and stays. Rejected: keeping the branch's helper and
rewriting `origin/main`'s two callers to it, which would make the theme's merge row the owner of a
refactor main has already landed and would widen the row across a file the row does not build.

**The branch's helper did more than main's, and the extra step returns to the specs rather than moving
into main's helper.** The branch's helper submitted the notification and then polled; main's only polls,
with the submit staying an explicit call on the animals journey flow in each spec. Keeping the submit on
the journey flow is what the repo's Playwright guide asks for — a multi-page sequence is a `to*` method
on the domain journey, and locators and page actions never move into a utility — and it is what main's
other dynamics spec already does three times. Rejected: adding the submit to main's wait helper, which
would give one function two jobs (it changes the service's state and reads it back) and would break the
name main's two existing callers read it by.

**The species common name keeps the form the theme's engineering review gave it, reading the cattle
entry of the commodity-lines constants, rather than reading the same value off the commodity line
already destructured in each test.** Both forms import from a home, and the acceptance criteria pin the
commodity-lines import; reading it off the destructured line would leave that import unused and the lint
rung red. The cost is that two adjacent assertions reach the same species two ways. Recorded as a
follow-up in section 7 rather than taken here: a merge row's footprint is the conflict.

**The wait helper stays in the config file it arrives in, not under the Playwright utilities.** The
repo's layout note gives `utils` the helpers and `config` the configuration, so the utilities folder
would be the more literal home. It stays where main put it because every value it uses — the arrival
timeout, the poll annotation, the poll options — is declared in that same file, moving it would change
two caller files this row does not build, and the row's resolution is not the plan's to re-decide.

**Everything else in the merge is taken as git resolves it, after checking the places where both sides
moved near each other.** Checked, and all consistent: main promoted the two accessibility-injection
helpers out of the two scan specs into the shared accessibility utilities and changed both specs in the
same commit, and the branch touched neither; main dropped the party-picker's preceding-siblings locator
together with its only caller spec, and the branch added no new caller; main turned the
missing-required-fields address constant from a function into a value and changed both its callers, and
the branch added no new caller; main added a short-display-date formatter, an app-date-text parser and a
next-page accessibility scan, and the branch holds no second copy of any of them; main's other dynamics
spec reads the arrival date through main's new parser and is not a file the branch touched. The branch's
own doc and README edits already removed the one-constant file from the prose, so no doc is left naming
it.

**A fetched `origin/main` other than `394d906` stops the row rather than being resolved on the spot.**
The merge-start stage fetches, so the implementor can be handed a main this plan never read. Rejected:
letting the implementor resolve whatever it finds by the same reasoning as the planned resolution — the
row's criteria name one file, the plan's own claim that every other path merges correctly is a reading of
one commit, and this row exists because exactly that assumption failed once already. Recorded as the stop
instruction in the header and in section 2's closing line, and as the `MERGE_HEAD` reading in section 5.

**Criterion 7 is proved locally, and the pull-request reading itself is the orchestrator's, after the
push.** The criterion is the only one no stage that runs this plan's checks can read directly. The
merge-start stage runs `git merge --no-ff --no-commit origin/main` before the implementor, so at the
point sections 5 and 6 are read HEAD is still the branch's own commit and a `merge-tree HEAD origin/main`
preview still reports the conflicted path — it answers a question that has already been resolved in the
index. The land stage, which commits the merge as its two-parent commit and pushes, runs no plan checks;
and the row sets `awaitCi: false`, so the CI stage — the only stage that reads `mergeable` and
`mergeStateStatus` — does not run either. So sections 5 and 6 prove the criterion's local substance (no
unmerged entry survives in the index, the merge in progress is of the previewed `origin/main`, and no
conflict marker is left in any file), which is what makes the pushed merge commit non-conflicting; and
the pull-request reading is recorded here, for the orchestrator to make after the push, as
`gh pr view 79 --repo DEFRA/trade-imports-ins-tests --json mergeable,mergeStateStatus` — today
CONFLICTING/DIRTY, expected MERGEABLE once the merge commit is pushed, with `mergeStateStatus` then
reflecting the checks GitHub starts running again. That is deliberately not a section-5 or section-6
check: `gh` is not a form this run's checks may take, and handing it to a stage that will never run it
would record a proof nobody makes. Rejected: leaving the criterion with a `merge-tree` check that would
report the conflicted path and read as a failure at every point it could actually be run.

**No increment-specific end-to-end check.** The row's `gatePhases` is `[]`, so the loop's gate runs no
unit, FIT or E2E phase for it, and the repo's local end-to-end script excludes the `@dynamics` tag the
conflicted spec carries, so no stack run exercises it. Section 6 therefore names the repo's own
format, lint, typecheck and test-duplication rungs itself: for this row they are the proof on top of
