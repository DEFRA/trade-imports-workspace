## 0. Decisions

**D1 — The role rule is applied in each frontend, not pushed down to the address book's `role`
query parameter.** The address book's list endpoint does take a role filter
(`AddressController.list`, `repos/trade-imports-address-book/src/main/java/uk/gov/defra/trade/imports/addressbook/address/AddressController.java:148-155`),
but its own contract says "Narrows the search …; **an address with no roles never matches**", and
`AddressListQueryImpl.holdingAnyOf` (`:60-62`) is a plain `roles in [...]` clause. Acceptance
criterion 5 requires an address holding no role at all to be listed on every picker, which that
parameter cannot express. So each frontend's address-book service asks the book for the
organisation's live addresses matching the search term, reads every page of them, and keeps the
records whose roles include the picker's role or that hold no role at all.
*Rejected:* sending `role` on the wire (drops role-less records, so criterion 5 fails); two reads
per render, one role-scoped and one whole-book (still a whole-book read, and two round trips for
one list). *Follow-up recorded in §7:* give the address book a way to say "this role, or no role"
so the filter can move down later.

**D2 — The text match stays the address book's.** The search term is still sent as `q` and the
book still decides what matches (`AddressController.list`'s `q` parameter, `:135-141`). Only the
role rule is the frontend's. One rule, one owner: the INS address-book list and both journey
pickers keep matching text the same way.
*Rejected:* matching text in the frontend after reading the whole book — it would put a second
text-match rule beside the book's in two repos.

**D3 — "the exporter role" in acceptance criterion 2 is a prototype concept with no counterpart in
the built system, and is not built.** The prototype's consignor section accepts the types
`consignor-or-exporter`, `consignor` and `exporter` (extract
`prototype-dr2-1-source-p8-064`, `app/routes.js:3851-3876`), and its own section data heads that
section "Consignor" with no separate exporter section (`prototype-dr2-1-source-p8-137`). The built
address book has six roles and no exporter among them
(`.../addressbook/address/AddressRole.java:9-21`), and the INS frontend's role vocabulary matches
it (`repos/trade-imports-ins-frontend/src/server/app/services/address-book/address-types.js:14-21`);
`grep -rn "EXPORTER\|exporter"` over all four repos' `src` finds nothing but an unrelated comment.
Ruling 17 of `ruling:sam-2026-10-09` says the prototype never decides data-model shape. So the
consignor picker lists the addresses saved for the consignor role, which is the role that already
covers the exporter, and no exporter role is invented. Recorded as a defect in the criterion's
wording, not in the application.

**D4 — Criterion 2's second clause is already true and belongs to another repo.** "the roles and
addresses page's party sections are Place of origin, Consignor, Consignee, Importer and Place of
destination" names the INS frontend's address-book page, which already offers exactly those five
party roles plus the branch address
(`repos/trade-imports-ins-frontend/src/server/app/features/address-book/copy/copy.en.js:201-205`).
That repo is not in this row's `repos`, and nothing there changes.

**D5 — The two contact pickers keep listing every address.** No acceptance criterion names the
animals contact-address page or the plants consignment-contact picker among the pickers to filter;
criterion 1 enumerates the five party pickers and criterion 4 the two plants party pickers. The
address book's branch-address role exists, but choosing it here would hide addresses on a guess,
which is exactly what the row's own source rules out (`document-dr1-parity-backlog-p6-051`). Both
contact pickers therefore ask for the organisation's whole live book, which is the service's
no-role branch — a branch both repos reach. They still lose their pagination and their restatement
of the choice, because criterion 7 covers "each high-risk plants picker" and the animals contact
page already renders a flat unpaginated list. *Rejected:* filtering the contact pickers to the
branch-address role (not asked for, and hides addresses). *Follow-up in §7.*

**D6 — The two readers in each frontend's address-book service collapse into one.** With the role
rule and no pagination, "every live address of this organisation matching this search for this
role" and "every live address of this organisation" are the same read with different arguments.
`all` (`repos/trade-imports-animals-frontend/src/server/app/services/address-book/index.js:107-132`)
and `search` (`:94-99`) therefore become one exported reader returning the matching records as a
list; keeping both would be a second mechanism beside the one being built. This changes the
animals contact controller's three call sites
(`.../features/contact/controller.js:104`, `:161`, `:190`) and one transporters test; those files
get only their touched lines fixed. Both repos hold a test asserting the module's exact export
list, and both are named in §4. *Rejected:* keeping `all` beside the new reader (two names for one
read, forbidden by the house rules).

**D7 — The results count keeps its two-slot wording.** The design sets "Showing {shown} out of
{total} results" (`prototype-dr2-1-source` extract at `working-set.json:8477-8480`, and the current
copy at `.../features/addresses/copy/copy.en.js:70`). With one page nothing is hidden, so both
slots take the number of rows the page renders. The copy function's shape is unchanged in both
repos. *Rejected:* collapsing the copy to one number — it changes nothing a user sees and the live
filter row re-splits the two numbers.

**D8 — An empty role list keeps today's no-matches wording.** A role with no addresses and no
role-less addresses now renders the results block with no rows, where today only a search can do
that. The design source shows no empty-role state. The implementor invents no new copy: the
existing no-matches message stands. Raised for the designer in §7.

**D9 — A record holding no role cannot be created through the address book, so criterion 5's
compose-stack half is a defect in the row, and the shared e2e seed does not change.** Two write
rules make it impossible:

- `AddressRequest.java:92` carries `@NotEmpty(message = "Select what this address can be used
  for")` on `List<String> roles`, so a create or replace with an empty list is refused with 400.
  `AddressBookRequest` in the tests repo types `roles` as required
  (`adapters/http/address-book-api-client.ts:25,28`), so the only body the seed could offer is
  `roles: []`, which the book refuses.
- `ensureE2eAddressBook` (`flows/shared/address-book-seed.ts:171-185`) creates and replaces through
  that same request type, and the tests repo reaches the address book only over HTTP (there is no
  Mongo adapter for addresses and the compose stack stages no address-book seed), so there is no
  back door.

A *stored* record may still hold none — `Address.java:18` reads *"An organisation-owned address-book
entry. `roles` can be null or empty."* — which is exactly the production case the row cares about:
every record saved before roles landed. A build cannot create that state on the compose stack, so:

- **`flows/shared/address-book-seed.ts` is not changed by this row.** `E2E_ADDRESS_BOOK_FIXTURES`
  does not grow, so `tests/ins/e2e/features/address-book/address-book-tabs.spec.ts:113-117`'s
  every-fixture loop — which reads `roles[0]` of every entry and opens the tab holding it — stays
  true and is untouched.
- **Criterion 5's compose-stack half is recorded as a defect in the row** and has no check in §5.
  Criterion 5's stub-mode half is built and proved by each repo's picker fit specs, and the role
  rule's role-less arm is proved at unit level with the stubbed fetch answering a record whose
  roles list is empty.
- **Each stub book gains one canned record holding no role at all**, which is what makes the
  stub-mode half of criterion 5 observable. The animals stub therefore no longer mirrors the seed
  record for record; its module comment must say what it holds now and that the extra record is the
  pre-roles state the address book will not accept as a write.
- **Criterion 3's end-to-end proof creates its own two-role record inside the spec** through
  `addressBookApi.createAddress`, as `address-book-navigation.spec.ts:114` already does, rather
  than joining the shared fixture array. Consignee and importer are both in the receiving group
  (`AddressRole.java:14-19`), so that record is legal.

*Rejected:* adding a `roles: []` entry to the shared fixtures (the book answers 400, so
`ensureE2eAddressBook` fails for every e2e run and the tabs spec loses its `roles[0]`); seeding the
address book's Mongo directly (a second write path beside the API, and one no test owns).

**D10 — The plants client gains the page-size argument the animals client already has.** Reading
the whole matching book needs the address book's largest page size; the animals client already
exposes it (`.../services/address-book/client.js:34-49`), the plants client does not
(`repos/trade-imports-plants-frontend/src/server/app/services/address-book/client.js:53-66`). The
plants client follows the animals client's shape.

**D11 — The plants picker's client-side module goes.** It exists only to rewrite the pagination
links as the trader ticks a row
(`repos/trade-imports-plants-frontend/src/client/javascripts/components/address-book-picker.js:10-42`).
With no pagination links it has nothing to enhance, so it is unreachable and is removed with its
registration and its unit test. Nothing else on the page depends on JavaScript, which keeps the
programme's no-JavaScript invariant.

**D12 — Inside the files this change edits, the address-book role and the party do not share the
name "role".** Each party today carries a `role` key that nothing reads
(`.../features/addresses/parties.js:14`, `:22`, `:30`, `:38`, `:46`, `:56`), while `role` is
already the established *log* field name for the party, holding `party.id`, at
`party-picker.controller.js:135`, `:162` and `:173` and at
`.../addresses/address-return/controller.js:40`, `:45`, `:85`, `:138`, `:148`, `:171`, `:174` and
`:186`. Putting the address-book role into the dead `role` key would leave one word meaning two
things in one feature folder, one of them a field a support engineer searches on. So:

- the dead `role` key in `parties.js` goes, and each party gains a key whose name says it holds the
  **address-book role**, distinct from the party itself; the plants parties registry gains the same
  key under the same name, so the two repos share one vocabulary;
- the log field that holds `party.id` is renamed to say it holds the **party**, across the whole of
  that concept's vocabulary in the `addresses` feature folder — `party-picker.controller.js` and
  `address-return/controller.js`, the helper parameter at `address-return/controller.js:40` and
  `:45`, and the assertions in `party-picker.controller.test.js:282`, `:312`, `:571` and
  `address-return/controller.test.js:94`, `:100`, `:118`, `:155`, `:249`, `:269`, `:317`, `:362`,
  `:392`, `:406`, `:451`, `:464`, `:480`.

`address-return/controller.js` is edited for that rename alone: its touched lines and the functions
holding them are brought into line and nothing else in the file changes. The row needs it because
the row is what introduces the second meaning of "role" into the folder; a rename that stopped at
`party-picker.controller.js` would split one log concept across two files.
*Rejected:* reusing the dead `role` key for the address-book role (two concepts, one name, in a
file this change edits); naming the new key distinctly and leaving the log field alone (the log
field still mispredicts in a file this change edits, and the folder still reads as if the logs
carry the book role).

**D13 — The plants happy path splits its one party record in two, because no legal record can be
both a consignor and a place of destination.** `RolesHeldTogetherValidator.java:19-21` keeps every
role on a record inside one group, and `AddressRole.java:11-21` puts CONSIGNOR in sending and
PLACE_OF_DESTINATION in receiving. `tech-imports-ltd` is the plants stub record the destination
step, the consignor step and the contact step of the happy-path fixture all pick

*Rejected:* giving `tech-imports-ltd` both roles (the address book would refuse the record, so the

## 13. Operability

The change adds no branch that changes an outcome. The role rule narrows a list; it never refuses,
redirects, retries or falls back. The branches that do change an outcome are untouched and keep
their existing logs, with the field that carries the party renamed to say so (D12) and the same
value in it:

- a picker saved with nothing chosen, logged once with the notification id and the party the picker
  is for (`party-picker.controller.js:161-164`; `save-selection.js:42-45` in plants, which logs the
  field name);
- a chosen id that is not a live record, logged once as a refusal with the party and the address id
  (`party-picker.controller.js:171-175`; `save-selection.js:54-61`);
- a save the engine could not commit, logged by the shared recoverable save with the party and the
  address id (`party-picker.controller.js:135`);
- a return from the INS address book, logged with the notification id, the party, where it landed
  and the address id (`address-return/controller.js:85`, `:138`, `:148`, `:174`, `:186`).

None of those lines carries the address-book role, and none needs to: support searches for the
notification, the party and the address id, and the role is derivable from the party.

The removed fallback — the address book answering an out-of-range page with a bad request, handled
at `services/address-book/index.js:85-89` in both repos — logs nothing today and is gone, not
silenced: no page number is ever sent that the book can refuse.

One thing to watch rather than log: a picker whose role has no addresses now renders an empty
results block on first open. That is a state of the organisation's book, not a failure, so it is
not logged; D8 and §7 record the wording question it raises.
