## 0. Decisions

1. **The claim that the five parties are stored differently is false on this
   tree.** `document-dr1-parity-backlog-p6-021` says "place of origin is
   stored inline while consignor, consignee, importer and destination are
   stored as references, so copying the place of origin onto the consignor
   must copy the record, not the reference". On HEAD all five parties are
   committed through one function,
   `party-inline.js:5` (`answerForInlineParty`), reached from
   `party-picker/selection.js:14` for every party in `parties.js:11-52`. Every
   party is stored inline, so "copy the record, not the reference" is the only
   thing the code can do. Planned against the tree as it is.

2. **What a same-as press copies: the source party's stored answer, by
   value.** The alternative — re-reading the source's address-book record by
   its `pickedFromId` and rebuilding through `party-inline.js:5` — was
   rejected: it fails when the record has since been deleted, it asks the book
   for something the notification already holds, and `page-design.md:339-340`
   states that the page never asks the address book for a chosen party. The
   stored answer already holds everything the target needs (the record it came
   from, name, phone, email and the wire address), and the page already has a
   precedent for copying one stored party onto another answer:
   `permanent-address/answers.js:28-35` writes `answers.placeOfDestination`
   verbatim onto an animal. The copy must be by value, not a shared reference,
   so a later edit of either party cannot reach the other.

3. **The copied party keeps the source's `pickedFromId`.** The only read of it
   is the picker's pre-tick when that party's picker reopens
   (`party-picker.controller.js:106`), and a selection the role-filtered list
   does not hold simply leaves no row ticked
   (`party-picker/view-model/index.js:16`); the notification mapper drops it
   before the record goes to the backend
   (`services/persistence/records/notification-mapper/mapper-a/sections/direct-fields.js:6`),
   which its own contract test already names and proves
   (`mapper-a-contract.test.js:149`). Stripping it would be a second
   stored-party shape for no gain. Those facts are today also carried by a doc
   comment on `party-inline.js:3-4`, which this change deletes (decision 17);
   this decision rests on the call sites and the contract test above, and on
   the `page-design.md` entry decision 17 gives the picker half of the fact.

4. **The control is a submit button drawn as a link, through the class the
   repo already has.** `govuk-link app-link-button`, defined once at
   `src/client/stylesheets/core/_main.scss:9` and already used by
   `confirmation/template.njk:39`, `dashboard/template.njk:91`,
   `commodities/search/search.njk:72` and
   `common/components/remove-action-button.js:12`. No new CSS, no new
   component: the design source sets a link-styled button
   (`prototype-dr2-1-source-p8-033`, `trace-prototype-dr2-1-p6-045`) and the
   repo already owns that control. The prototype's own
   `app-roles-and-addresses-page__section-link-button` block is not copied,
   per the programme invariant on `app-dr2-*` blocks. The design source's own
   trace note raises that a button dressed as a link sits outside the
   govuk-frontend toolbox; section 14 weighs that rule and says why no
   departure is recorded.

5. **The page becomes one form.** The sections are rendered outside the form
   today (`template.njk:15-41` versus `template.njk:43-48`), so a button in a
   section cannot post it. The form opens before the sections loop and closes
   after the save actions, keeping the crumb and concurrency-token inputs at
   its top. The alternative the DR1 note offers
   (`document-dr1-parity-backlog-p6-023`) — leaving the form where it is and
   giving each button a `form` attribute — was rejected: the repo's own
   precedent is one page form wrapping the content that posts it
   (`documents/template.njk:54-…`, `transit-countries/transit-countries.njk`),
   and a `form` attribute is a second mechanism beside it.

6. **No implicit-submit button is added.** `shared/save-actions.njk:13` exists
   for a page whose text field would otherwise submit the wrong button. This
   form holds no text field, so implicit submission cannot occur and Enter on
   a focused control activates that control, which is correct.

7. **The posted field is the page form's `action`, as the repo's other
   per-item submit buttons use.** `transit-countries/remove-action.js:1-12`
   owns that feature's vocabulary and
   `transit-countries.controller.js:236-244` dispatches on it; documents and
   commodities do the same. A new field of its own
   (a second per-button field beside the `exit` field `kit.js:163-175` owns)
   was rejected as a second mechanism.

8. **The pairs live with the action vocabulary, not on `parties.js`.** One new
   module in the addresses feature folder owns both "which source fills which
   target" and the value its button posts. Putting the source id on each party
   in `parties.js:11-52` was rejected: `parties.js` is the registry of facts
   about a party that the picker, the edit page and the hub all read, while
   the pairing is a fact about this one shortcut and nothing else reads it.

9. **Each label is its own copy string keyed by the source party, not composed
   from the party title.** "Same as " + a lowercased title happens to work in
   English and does not work in Welsh, and the programme invariant requires a
   Welsh draft beside every new English string. Two strings in English and two
   in Welsh (one per source party), in the feature's own copy, in the `hub`
   namespace beside `change` and `editDetails` (`copy/copy.en.js:8-9`).

10. **The button's accessible name names the section it fills, through the
    section's existing hidden suffix.** Two sections offer "Same as consignee"
    (`trace-prototype-dr2-1-p6-043`, `-p6-044`), and
    `page-design.md:333-337` already states this page's rule: a control whose
    visible text two sections would share carries a visually hidden suffix
    naming the party. The suffix is `hiddenSuffix` on the section object
    (`controller.js:41`), already used for Change and Edit details at
    `template.njk:32` and `:34`. The visible text is exactly what the design
    source sets; only the screen-reader name gains the party.

11. **The button sits where the add link sits, first in reading order.** The
    acceptance criteria say "beside its add link"; the trace's verbatim
    reading order (`trace-prototype-dr2-1-p6-042`) is button then add link.
    Settled as: one paragraph in the not-chosen branch of the section holding
    the same-as button then the add link, mirroring how the chosen branch
    holds Change then Edit details in one paragraph (`template.njk:31-36`).

12. **After a copy the target section shows Change *and* Edit details.**
    Criterion 4 names Change. The page's existing rule gives every party that
    holds an address both links: `controller.js:53-63` builds `changeHref` and
    `editDetailsHref` together on the `chosen` branch, and
    `page-design.md:327-329` states the same in words — a section shows "either
    a named 'Add a …' link or the chosen address in an inset text with Change
    and Edit details under it". The party edit page opens for any party the
    answers hold, on `answers[party.id]` alone
    (`party-edit/party-edit.controller.js:70-76`), so a copied party opens it
    too. No special case is built.

    This is where `page-design.md:354-356` stops being true: it says Edit
    details is offered only for an address the picker has copied onto the
    notification. After this change a party can hold an address the picker
    never copied — the shortcut copied it from the paired party — and the edit
    page still opens for it. Section 12 carries that hit, and section 2 says
    what the entry must state instead.

13. **A same-as post for a pair that is not on offer is refused silently and
    logged, not shown as an error.** It can only arise from a stale page or a
    tampered post, and the page has no error state of its own. The response is
    the addresses page again with nothing committed, mirroring the picker's
    "nothing chosen" path (`party-picker.controller.js:160-166`).

14. **The commit goes through `kit.recoverableSave`** (`kit.js:337`), as both
    the picker (`party-picker.controller.js:117-137`) and the permanent
    address page (`permanent-address/controller.js:182-198`) do, so a
    recoverable backend failure re-renders the addresses page with its
    recoverable banner rather than throwing. This needs the view build lifted
    out of `controller.js:158-182` into a render helper both `get` and the
    new post path call — a bounded refactor inside the file the row already
    edits.

15. **The new FIT tests join `fit/hub-picker.fit.spec.js`** rather than a new
    spec file, because that file already owns the hub's local helpers
    (`openAddresses`, `openPartyPicker`, `saveAndContinue`,
    `expectBackOnTheAddressesPage`, `pickEveryParty` at :53-94) and a new file
    would copy them — which the gate's duplication rung checks.

16. **Plants is untouched.** Ruling `sam-2026-10-09-pm` leaves high-risk
    plants out: it has no roles and addresses page to carry the shortcut. The
    programme's "mirror it in plants" invariant does not bite, because plants
    has no page with this behaviour.

17. **`party-inline.js`'s doc comment goes, and its facts get a home outside
    the code.** The change edits that file (section 2 gives it the copy
    function), so its existing breach is fixed in this change rather than
    carried: the comment at `:3-4` describes another module (the notification
    mapper's `toParty`), makes a claim about callers ("nothing reads details
    through it"), and is rationale rather than the exported function's
    contract — three things `.claude/rules/code-quality.md` forbids under
    Comments and Doc comments. The facts it carries already have homes or gain
    one: the mapper half is named and proven by
    `mapper-a-contract.test.js:149`, and the picker half is observable
    behaviour, so it goes into `page-design.md`'s "Consignment addresses
    pages" section as a fact about reopening a party's picker (section 2). The
    alternative — rewording the comment — was rejected: the house rules say a
    stale or out-of-place comment is deleted, not reworded, and the function's
    name and body already say what it returns. No doc comment replaces it;
    `answerForInlineParty` and the new copy function are internal to the
    feature folder, and the rules allow none on internal helpers.

## 2. Edits

### frontend — `src/server/app/sets/live-animals/journeys/linear/features/addresses/template.njk`

- The `<form>` that today wraps only the save actions (`:43-48`) must wrap the
  party sections too: it opens before the sections loop (`:15`) and closes
  after the save actions, with the crumb and concurrency-token hidden inputs
  staying at its top. The heading, intro and warning stay outside it.
- The not-chosen branch of a section (`:38`) must offer, in one paragraph, the
  same-as submit button (when the section has one) followed by the existing
  add link. The button is a submit carrying the posted action in its value,
  drawn with `govuk-link app-link-button`, with the section's `hiddenSuffix`
  in a `govuk-visually-hidden` span after its text — exactly the shape
  `:32` and `:34` already use for Change and Edit details.
- The chosen branch (`:26-36`) is unchanged: a section with an address never
  offers a same-as button.
- No comments: `npm run lint:templates` rejects them.

### frontend — `.../addresses/controller.js`

- `hubSection` (`:36-43`) gains the same-as control on the branch that already
  builds `addLink`, so by construction only a section with no address can
  carry one. A section with no same-as source carries none.
- `partySectionBuilder` (`:45-65`) asks the new module for this party's source
  party and, when there is one and the parties map holds an address for it,
  passes the control's label and posted value into `hubSection`. The map it
  already receives (`parties`, built by `frozen-parties.js:39-47`) holds a
  display party only when the stored party has a name
  (`frozen-parties.js:19-23`), so "the source has an address" is exactly
  "`parties[sourceId]` is there".
- `cphSection` (`:67-80`) and `permanentAddressSection` (`:100-132`) never
  carry one: they are not parties and the new module knows no pair for them.
- The view build inside `get` (`:164-181`) moves into a render helper that
  `get` and the new post path both call, taking the recoverable-error flag and
  the success banner. `get` keeps taking its banner from
  `takeAddedAddressBanner` (`:169`); the post path passes none, so a page
  shown after a copy carries no success banner.
- `post` (`:184-187`) reads the payload's action. When it is a same-as action:
  it reads the target party, asks the new module for its source, and refuses —
  logging once, committing nothing, redirecting to the addresses page carrying
  the request's trail — when there is no such pair, when the stored answers
  hold no address for the source, or when the target already holds one.
  Otherwise it commits the copy (section 10) through `kit.recoverableSave` and
  redirects to the addresses page carrying the request's trail. Any other post
  keeps today's behaviour exactly: `kit.nextTarget(request, page, scope)`.
  `kit.pageRoutes` (`kit.js:385-402`) already wraps the post in the stale-token
  redirect, so a stale concurrency token needs nothing here.

### frontend — `.../addresses/party-inline.js`

- It gains one exported function, beside `answerForInlineParty` (`:5-11`),
  that takes a stored party answer and returns an independent copy of it for
  another party: the same stored shape, by value, with no object shared

- It gains **no test file of its own**. `party-inline.js` has none today, and
  the copy is only observable as what a party section then shows, so it is
  proven through the controller cases 4 to 6 in section 4 and the FIT case 11
  — the behaviour-through-inputs-and-outputs rule — rather than by a new unit

## 3. New files

### frontend — one module in `.../features/addresses/`, beside `parties.js`

Owns the shortcut's vocabulary: which source party fills which target party
(the three pairs and no others), the value a target's button posts, whether a
posted action is a same-as action, and which target it names. Not part of
`parties.js` for the reason in decision 8, and not part of `controller.js`

`.../features/transport/transit-countries/remove-action.js`.

## 14. Departures from written rules

None — and the one candidate is weighed rather than passed over.

**The link-styled submit button (decision 4).** The rule is
`docs/best-practices/gds/components.md:70-74`, "Stay in the GOV.UK toolbox":
"If it is not in GOV.UK Frontend, do not build it. Custom CSS forks the design
system and loses its accessibility testing and its consistency with other
services. … Use `govuk-*` components and utility classes … **Do not add a SCSS
partial or a CSS rule.**" The design source's trace extract raises the same
point in its own note, that a button dressed as a link sits outside the
govuk-frontend toolbox.

This is not a departure, and a reader can check why: the plan adds no SCSS
partial and no CSS rule. The class already exists at
`src/client/stylesheets/core/_main.scss:9`, where it sets a `<button>` to the
GOV.UK link colour and typography, and it already has four live uses in the
app — `confirmation/template.njk:39`, `dashboard/template.njk:91`,
`commodities/search/search.njk:72` and the shared
`common/components/remove-action-button.js:12`, the last of which every remove
cell on the documents, commodities and transit-countries pages renders through.
The visible `govuk-link` half of the pair is a GOV.UK Frontend class. So the
control this row adds is the repo's existing control for "a thing that must
POST but reads as a link", used as it stands; what the rule forbids — forking
the design system with new CSS — is not done, and building a second
link-styled control beside this one would itself breach the house rule against
a second mechanism.

Two things follow rather than being waived. First, the control must be a real
`<button type="submit">`, so it is a button to assistive technology and keeps
its keyboard behaviour, which is what section 4's FIT cases 13 (axe at two
widths, controls showing) and 14 (no JavaScript) prove. Second, whether a link
is the right visual treatment for a control that changes the notification is
the design source's call, not this plan's: the source sets it
(`prototype-dr2-1-source-p8-033`, `trace-prototype-dr2-1-p6-045`) and the
house rules make code that differs from its design source a correctness
finding, so the plan builds what the source sets. Section 7 records nothing
further here; if a reviewer wants the treatment revisited it is a `design`
finding for the designer, not a change this row makes.
