## 0. Decisions

1. **What is left to build.** The row's detail says the animals half has
   shipped. Verified against the live tree: `addresses/party-picker/_cells.njk`
   has `pickerSelectCell`, `pickerAddressCell` and `pickerViewCell` and no
   disclosure macro; `view-model/table-rows.js:6-18` adds the view cell behind
   `withViewLinks`; `view-model/address-lines.js:11-12` already gives the picker
   street lines then one locality line. So acceptance criterion 2 is a guard
   that is already true, and the work left is the plants side of criteria 1, 3
   and 4. Rejected: rebuilding the animals half, which the row's own detail and
   the live tree both say is done.

2. **Criterion 3's literal wording is wrong; the design sources win.** The
   criterion says each address line, town or city, county and postcode go "on
   its own line". The design sources it cites say otherwise: the prototype
   claim (`prototype-dr2-1-source-p8-060`) reads "Address (one line per address
   **line**)", and the rendered trace it cites
   (`trace-prototype-dr2-1-p6-066`) quotes a row as
   `Västra Hamngatan 6 / Floor 2 / Gothenburg, 41117` — street lines on their
   own lines, then town and postcode together. The row's own notes record the
   same decision ("street lines on their own lines, then town or city, county
   and postcode on one line. That is decided against this row's criterion"),
   and the animals twin already ships that shape, which the programme
   invariant on plants mirroring animals requires. So plants takes the street
   lines/locality-line shape. Rejected: one part per line, which no cited
   source shows and which would put plants out of step with animals.
   Choosing one layout across every page that shows an address stays a
   separate snagging concern, not this row's.

3. **Criterion 4's content list contradicts criterion 1; criterion 1 wins.**
   Criterion 4 lists the disclosure as holding name, address lines, country,
   phone and email — which is a description of the current code
   (`repo-plantsfrontend-p6-012` is a repo claim, not a design requirement).
   Criterion 1 and the row's detail say the disclosure keeps only the telephone
   number and email address, because the row's own columns already show the
   name, the address lines and the country. Criterion 4 is therefore honoured
   as the part that is a requirement — the row's last cell is still a
   "View details" disclosure that opens in place — and its content list is
   superseded. Rejected: keeping the full list, which would leave criterion 1
   unbuilt.

4. **All three plants pickers change, not two.** Criterion 3 names the
   consignor and place of destination pickers. The consignment contact picker
   is the same feature: `consignor-select`, `place-of-destination` and
   `consignment-contact-select` all bind
   `address-book-picker/view-model.js` and render
   `address-book-picker/template.njk`, so one owner serves all three and the
   contact picker changes with them. The design-snagging row this one depends
   on already asked for the contact picker to take the same picker layout.
   Rejected: branching the view model so the contact picker keeps the old
   column, which would be a second mechanism beside the one that exists.

5. **The country keeps its own column.** Criterion 1 says the name, address
   lines and country appear in the row's own columns, and the live table head
   (`address-book-picker/results.njk:38-45`) has Select, Name, Address,
   Country and a hidden Actions column. The earlier snagging row's phrase
   "with the country no longer in a column of its own" is not carried out in
   the tree and contradicts this row's criterion 1, so the column stays and
   the Address column excludes the country, exactly as the animals twin does.

6. **The parts list is split, not duplicated.** `address-lines.js:2-8` holds
   one ordered parts list that the one-line form reads. The picker column now
   needs the street parts apart from the locality parts, so that list is
   split into those two groups and the existing one-line export joins both
   groups' values exactly as it does today. Rejected: a second parts list
   beside the first, which would be two owners for one ordering.

7. **The one-line form stays, and its two callers are untouched.** The
   existing one-line export is still what the picker's current-address card
   (`address-book-picker/render.js:28`) and the check-answers address row
   (`check-answers/view-model/index.js:130`) read. Criterion 3 is about the
   picker's Address column only, so neither of those changes. Rejected:
   making every address display per-line, which the row does not ask for and
   which would widen the footprint into the review page.

8. **No empty-disclosure branch.** The address book is the only writer of
   these records and makes the telephone number and email address required
   (`trade-imports-ins-frontend/src/server/app/features/address-book/fields.js:15-16`),
   so a record always carries both, and the existing blank-dropping filter
   already covers an older record missing one. Nothing is built for a record
   carrying neither.

9. **The expected-cell-text rule is promoted in the tests repo.** The animals
   page object already owns the rule that turns a record into the text the
   Address cell reads
   (`page-objects/animals/party-picker-page.ts:22-25`). Plants now needs the
   same rule, and both domains' page objects already import from
   `page-objects/shared/address-picker-results.ts`, so the rule moves there
   and the animals copy is deleted. That changes the animals page object and
   the two animals spec call sites — a caller change the row genuinely needs,
   because one display rule gets one owner and promoting a helper deletes the
   local copies. Rejected: a second copy in the plants page object.

9a. **The row accessor's radio locator gets one owner, in the same move.**
    The promoted row accessor finds a picker row by the radio that selects a
    named address, and that radio locator exists twice already, identically:
    `page-objects/animals/party-picker-page.ts:63-65` and
    `page-objects/plants/address-book-picker-page.ts:24-26` both build it from
    the same role and the same accessible name. This plan edits both files, so
    writing the row accessor's own copy in the shared module would make three.
    The locator therefore moves to `page-objects/shared/address-picker-results.ts`
    with the row accessor, and each page object's existing named accessor reads
    it from there — exactly as both already read the search, results-heading
    and group locators. Every spec and flow call site keeps the accessor it
    calls today (`flows/plants/journey.ts:230`, `:238`, `:252`,
    `tests/animals/e2e/features/address-book/addresses-picker.spec.ts:40`, and
    the rest), so no caller changes. Rejected: building the radio locator a
    third time inside the shared row accessor, which would leave one rule with
    three owners in files this change already opens. The animals contact
    address page's radio accessor
    (`page-objects/animals/contact-address-page.ts:14`) is a different locator
    — a plain accessible name, not the picker's select label — and is not part
    of this move.

10. **No copy changes, so no Welsh draft is needed.** The disclosure's summary
    words already exist in both locales
    (`address-book-picker/copy/copy.en.js:20-21`,
    `copy/copy.cy.js:22-23`), the table head words are unchanged, and the
    address lines are record data rather than copy. The programme's Welsh
    invariant is satisfied with no new string.

11. **No new accessibility test.** The shared FIT picker suites already run axe
    on every changed picker in its empty, searched and no-match states
    (`fit/high-risk-plants-journey.js:400-419`), and those states all render
    the changed Address cell and the changed disclosure. Rejected: a fourth
    axe state, which would prove nothing the existing three do not.

12. **Signed-off check.** All three plants picker pages are at
    `maturity: 'exploring'`
    (`consignor-select/page.js:4`, `place-of-destination/page.js:4`,
    `consignment-contact-select/page.js:4`), so no page in this row's
    footprint is signed off and nothing is held.

13. **Which rung red-probes what, and why no end-to-end probe runs here.**
    A coverage link recorded `full` needs a probe that inverts the production
    line its Then depends on, sees the test red and restores it
    (`openspec/config.yaml:81-83`). Two rungs can carry one in this increment:
    the plants unit rung, which runs under vitest with no server, and the
    plants FIT rung, which serves the app on its own port and needs no
    workspace stack. Both probes are the implementor's work and section 8
    names each one. The end-to-end rung cannot carry one: this increment runs
    no workspace stack, so no agent here can invert a plants production line,
    watch the plants E2E spec fail and restore it — the E2E spec's only run is
    each repo's pull request in CI, which is green-only evidence. So the E2E
    link is recorded `partial` with a note saying it has not been seen
    failing, and every scenario's `full` strength rests on a link probed on
    the unit or FIT rung. Each scenario still derives `full`, because at least
    one of its links is. Rejected: recording the E2E link `full` on the
    strength of a green CI run, which the coverage rule forbids; and deferring
    the scenarios until a stack-holding run can probe them, which would leave
    behaviour this increment ships unrecorded. Promoting the E2E link to
    `full` is a follow-up, in section 7, for a run that holds the stack.

## 2. Edits

### plantsfrontend

**`src/server/app/sets/high-risk-plants/journeys/linear/features/address-book-picker/address-lines.js`**

- The single ordered parts list becomes two groups: the street parts
  (`addressLine1`, `addressLine2`) and the locality parts (`townOrCity`,
  `county`, `postcode`), in the same reading order they have now. The address
  book holds two address lines only, so there is no third street part.
- A new export owns the picker's Address column rule: each street part the
  record holds on its own line, then the locality parts the record holds
  together on one line joined by commas, blanks dropped, the country left out.
  This is the same rule the animals twin owns at
  `trade-imports-animals-frontend/src/server/app/sets/live-animals/journeys/linear/features/addresses/party-picker/view-model/address-lines.js:11-12`,
  whose structure the implementor follows.
- The existing one-line export keeps exactly the output it has today — the
  record's parts in reading order joined by commas, blanks dropped, country
  excluded — now reading both groups. Its doc comment must state that contract
  and must no longer say it is for the results table, which stops being true:
  the results table takes the per-line form instead.
- The disclosure export narrows to the record's telephone number then its
  email address, in that order, blanks dropped. Its name must say it returns
  the record's contact details, because a name predicts what the code returns
  and the present name would promise the whole record. Its doc comment states
  that contract; the clause about the contact details the table has no column
  for stops being true now that the name, address lines and country are gone
  from it, so it goes.
- The rename reaches every use of the concept, not only the identifier. Every
  place either row key is written or read, found by grepping the repo for both
  concept words: the row fields the view model sets (`view-model.js:11`,
  `:13`), the cell the table rows read (`table-rows.js:18`), the loop the
  disclosure macro reads (`_cells.njk:24`), the shared view-model assertion
  (`test-support.js:111`), and the three stand-in rows the unit tests build
  (`address-lines.test.js`, `table-rows.test.js:14`, `:16`,
  `results.test.js:18`, `:20`). The one-line export keeps its own name and its
  two callers (`render.js:28`, `check-answers/view-model/index.js:130`), which
  are a different concept and are not part of the rename.
