## 0. Decisions

**D1 — Criterion 2's two halves.** Criterion 2 asks for an `h2` reading "Select an address" *and* says "the page's only visible heading above the choice is the page heading". Read together with the design source (`prototype:dr2-1-source` p8-118 quotes `<h2 …>Select an address</h2>`), the second clause is about the fieldset legend, not the sub-heading: the legend stops being the page heading and becomes a visually hidden duplicate of the sub-heading, so it adds no second visible heading. Built that way. Rejected: dropping the sub-heading and keeping only a hidden legend — it contradicts criterion 2's own first clause, the design source, and the house pattern already used by the role pickers (`addresses/party-picker/_address-picker.njk:13` and `:41`) and by plants (`address-book-picker/results.njk:29` and `:52`).

**D2 — Where the required check lives.** The page's one validation already states its rules once and is read twice, and `lib/validate/page-validation.js:53` and `:59` hand each reading a `stored` flag for exactly this. The membership rule therefore splits by reading: the stored reading keeps today's membership-only rule that allows a blank, and the submitted reading refuses both a blank and a non-member. Rejected: a check in the controller's POST beside the validation — a second mechanism for the same rule, and it would not be read by the task list or the review.

**D3 — The secondary save button needs no second path.** `shared/save-actions.njk:42-47` renders it as another submit in the same form, and `shared/kit.js:243` reads its `exit` value only to pick where a *valid* save goes. Both buttons already reach the one POST handler and the one validation, so criterion 8 lands with criterion 7's change and adds no code. The repo already states this contract (`src/server/app/docs/validation.md:60-63`). Criterion 8's extra case — a value the book does not hold, submitted from the secondary button — still gets its own test.

**D4 — Home for "the address on one line, ending at the postcode".** A second export beside the existing one-line rule in `addresses/address-summary.js:1`, both reading one shared list of parts. Rejected: (a) changing the existing rule in place — the transporters list (`transport/transporters/rows.js:29`, `:52`) and the review's party rows need the country; (b) joining the role picker's line array (`addresses/party-picker/view-model/address-lines.js:11`) with commas — that composes one display rule out of another display rule's output rather than giving the new rule an owner.

**D5 — Home for the sub-heading's wording.** The words "Select an address" already have an owner in this set: `addresses/copy/copy.en.js:72` (Welsh `copy.cy.js:73`, already carrying the machine-draft marker), the heading the role pickers show over the same kind of list. The contact page reads that leaf, as `addresses/party-picker/party-picker.controller.js:32` and `:73` already hand it to their template. Rejected: a new leaf in the contact feature's copy — it would duplicate the string and its Welsh, and the programme invariant on shared wording points the other way.

**D6 — Where the add-an-address link sits.** Criterion 1 puts the intro directly under the page heading and criterion 2 puts the sub-heading below the intro, so the link cannot stay where it is today (above the page heading, because today the heading is the legend inside the form). It moves below the sub-heading and above the options, where the design source puts its own add affordance (`prototype:dr2-1-source` p8-118). Its presence rule (offered only outside stub mode) is unchanged, and `live-animals/addresses` REQ-ADDR-004 states only that a link is offered, not where, so no spec text moves. Rejected: leaving it above the page heading — a link above a page's H1 is neither the design source's layout nor GDS's.

**D7 — Criterion 9 already holds; the row's note that it does not is wrong.** The contact address is a mandatory obligation (`sets/live-animals/obligations/sections/misc.js:5-9`), the overview's `contact` task row collects it (`journeys/linear/flow/task-rows.js:62`), submit readiness requires every row ready (`flow/section-status.js:16-19`), the review refuses while any row is outstanding (`check-answers/refusal.js:111`), the declaration's POST runs that refusal before it submits and redirects back to the review (`declaration/controller.js:204-210`), and the review then names the contact card (`check-answers/view-model/incomplete-cards.js:52`, `check-answers/copy/copy.en.js:118`). I ran `src/server/app/sets/live-animals/journeys/linear/flow/task-rows.test.js` on this branch: 62 passed, including the case holding a notification without a contact not submittable. So this row builds nothing for criterion 9 and only proves it. What does change is the route to it: a blank contact save no longer reaches the review, so the proof opens the review from the overview with the contact page never answered.

**D8 — Criterion 9's literal wording is unreachable; the plan proves its reachable form.** A trader cannot press the declaration's submit button on a notification with no contact address: the review's own Continue (step `review`) is refused first by the same check (`declaration/controller.js:204`), so the declaration page never opens. The reachable, observable form — opening the review with no contact address and pressing Continue keeps the trader on the review, which names the contact address as outstanding — is what the checks prove, and it is already recorded as `live-animals/journey-pages/check-your-answers` REQ-CYA-007.

**D9 — Criterion 4's "with the Welsh language chosen" is unreachable today.** `shared/copy.js:15` resolves a locale only when one is passed, and no controller passes one, so no page renders Welsh. What criterion 4 and the programme invariant actually need is a Welsh draft beside every new or changed English string, marked a machine draft, resolving through that seam. Built that way and proved by the feature copy tests and `copy-parity.test.js`. No Welsh-render scenario is written: the Behaviour Spec takes no scenario for a state the service cannot reach yet.

**D10 — Plants takes the intro and the sub-heading only.** The afternoon ruling of 9 October reaches plants with exactly those two (`ruling:sam-2026-10-09-pm` p3-043), and plants' sub-heading already exists (`address-book-picker/copy/copy.en.js:8`, rendered by `address-book-picker/results.njk:29`), so plants is a copy-only change to one feature's `description`. Plants keeps its current-address card and its blank save (`req-1967`). Rejected: extending criteria 6, 7 and 8 to plants — no source extends them, and plants' blank save is a built, separately-ruled behaviour. Recorded as a follow-up.

**D11 — The contact edit route keeps an entry point, so its tests re-route rather than go.** Conflict c-241's outcome keeps the route and drops the contact page's link; the review's contact card still carries its own edit action (`check-answers/view-model/cards/addresses/contact-address.js:37`), and dropping the review's edit links is a different row (c-138). The three tests-repo tests that opened the edit form from the contact page therefore open it from the review's contact card instead.

**D12 — Criteria 7 and 8 cite a claim that is about something else.** `confluence:6497338582` p2-131's extract is about the MDM list behind Port of Entry, not the contact address. A provenance slip in the row only: the behaviour is carried by `prototype:dr2-1-specs` p3-100 (the error wording and its link target), the 26 October ruling (`ruling:sam-2026-10-26` p1-001, p1-024 and conflict c-361's outcome) and the Data Fields page's "mandatory to proceed" marking cited by `req-764` and `req-2187` (p2-189, p2-195, p2-201, p2-203). Planned against those.

**D13 — `req-766` and `req-767` are in the row's requirements with no criterion.** The 6 November trim took the page's navigation out of this row and gave it to EUDPA-774, and the criteria match the trim. Nothing in this plan touches where Save and continue or Back go, nor the opening run, nor amend returns.

**D14 — The journey-flow spec changes, because the row falsifies one of its scenarios.** `openspec/specs/live-animals/journey-flow/spec.md:44-48` states, as SCN-FLOW-003-B, that the contact page's Save and continue reaches check your answers "with or without a contact address chosen", and `openspec/coverage/live-animals/journey-flow/coverage.json:62` witnesses the blank half with the very E2E case section 4 rewrites. Making a blank save a refusal falsifies that When, so the scenario is restated to the end behaviour — an address must be chosen before Save and continue goes on, and without one the trader is kept on the page — and the falsified coverage link is replaced by a test that witnesses the restated claim. The scenario carries no `**Signed off**` line, so nothing is held; this is an ordinary spec edit. Rejected: leaving journey-flow under "no spec change" on the grounds that the page order is unchanged — the order is unchanged, but what a valid Save and continue requires is not, and the coverage link would be left pointing at a test that no longer proves its claim.

**D15 — The whole-page headings locator is promoted, not copied.** The tests-repo assertions this row needs ("the page's headings are exactly these") read every heading in a page's main region. That locator already exists on `page-objects/animals/import-reason-page.ts:23-25`, a sibling subclass of the `NotificationPage` the contact page object extends, with one reader at `tests/animals/e2e/pages/import-reason.spec.ts:16`. It moves to `NotificationPage` in `page-objects/shared/base-page.ts` and the local copy goes, so both page objects read one locator. Rejected: adding a second copy on the contact page object — two mechanisms for one locator, which the house structure rule bars, and the duplication rung would be right to flag it.
