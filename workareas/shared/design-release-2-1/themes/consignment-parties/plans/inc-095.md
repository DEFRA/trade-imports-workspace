## 0. Decisions

1. **Which repos actually change: frontend and tests. The INS front door needs nothing.**
   The row lists insfrontend, but every behaviour its third acceptance criterion asks for is already built and proven there. `features/address-book/journey-registry.js:24,42` maps the consignment contact fulfilment id to the branch-address role; `services/address-book/address-types.js:33` gives the branch address type that one role alone, so `ownAndOtherRolesOfParty` returns no other roles and `add/add.controller.js:153-161` renders no roles question in that mode; `rolesToSaveForParty` (`journey-registry.js:85-91`) saves the new record with the branch-address role. It is pinned by `add/add.controller.test.js:1026` (saved as a branch address), `:1058` (no roles question), `:1123` and `:1392` (the contact page's own buttons, Back and Cancel), and by `features/address-book/fit/add.fit.spec.js:463`. The handshake itself is refused unless the fulfilment id is listed (`handshake-context.js:36-42`). Rejected alternative: open insfrontend to add something anyway — that would build a second mechanism beside the one that already answers the criterion.
   Consequence for section 8: the INS half of criterion 3 is already recorded in `openspec/specs/ins/address-book/spec.md` (its requirement at line 1306 and scenarios at 1308-1314, and the no-roles-question requirement at 1330 with its scenario at 1360), so this row writes no `ins/` spec text.

2. **Plants is out, by the row's own note and a standing requirement — and that is a departure, recorded in section 14.** The programme invariant carries a page change to the high-risk plants frontend whenever plants has the same page, and plants does have it (`repos/trade-imports-plants-frontend/src/server/app/sets/high-risk-plants/journeys/linear/features/consignment-contact-select/`). The row records that no ruling carries the branch-only list or the add-a-branch path to the plants contact page, which keeps listing the whole book with no add link (the row's note, req-1966, c-291). Rejected alternative: mirror into `plantsfrontend` — it would build behaviour no source asks for and contradict a requirement that already exists. Because this departs from a written invariant, section 14 states it with the invariant quoted.

3. **The branch filter goes through the role narrowing the address-book service already owns, client-side.**
   `services/address-book/index.js:56-61` already narrows a list to a role, by the rule at `:20-21` (a record holding that role, or holding no role at all, matches). The contact page passes the contact party's role to it. Rejected alternative: ask the address book to filter server-side. The service supports it (`AddressService.java:85-88` builds criteria from requested roles), but `services/address-book/address-book.test.js:169-179` deliberately pins that this frontend sends the search term and not the role, so switching would change a decision this row has no mandate over.

4. **"Newest added first" needs no sorting in the frontend.** The address book serves a page sorted `createdAt` descending, tie-broken on id (`AddressService.java:68-72`), and `readEveryLivePage` (`services/address-book/index.js:26-51`) concatenates pages in order, so the list already arrives newest first and the role filter preserves it. Rejected alternative: sort in the contact controller — a second owner for an order the system of record already decides.

5. **The page accepts only what it offers, and the by-id read goes through the owner that already exists.**
   Filtering the rendered list alone would leave the page's GET and its POST answering "is this one of my addresses?" differently: POST would accept a record held for a consignment role, which the page no longer offers. So the role test applies to the posted record too, and a record that does not hold the contact role travels as no selection — the page's existing refusal, with its existing error, committing nothing.
   `loadLiveAddress` (`contact/controller.js:119-122`) is deleted rather than extended. It is a second copy of a rule that already has an owner: `chosenPartyFor` (`addresses/party-picker/selection.js:4-12`), whose doc comment states it — a selection looked up in the book, a missing or soft-deleted record treated as no selection. This controller already imports from that module (`contact/controller.js:14`), and the address-book hand-back reads through it too (`addresses/address-return/controller.js:87`). The posted answer is read through `chosenPartyFor`, and the contact page's own owner adds only what is its own: that the record holds the role this page's list offers, through the exported role rule (decision 3) and the party table's role (section 9).
   Rejected alternatives: keep `loadLiveAddress` and bolt the role test onto it, which leaves two owners for the lookup rule in lines this row is editing anyway; or push the role into `chosenPartyFor` for every party, which would change what the five consignment pickers accept — behaviour a follow-up row owns (section 7), not this one.
   The single by-id read stays a single read: the record the book returns already carries its roles, so no extra request is needed, and `contact/controller.test.js:239-245` pins that only one request goes out.

6. **Where the sentence sits and how its link is marked up comes from the design source, quoted at its file:line.** The workarea records the row's source verbatim at `workareas/shared/design-release-2-1/distil/working-set.json:15534-15541`, claim `prototype-dr2-1-source-p8-118`, ref `app/views/design-release-2.1/contact-address-for-consignment.html:64-68`:
   > `<h2 class="app-contact-address-page__section-heading">Select an address</h2> ... If the correct address is not shown, <a class="govuk-link" href="{{ addAddressHref }}">add a new branch address</a>, then return to this page.`
   That settles three things: the sentence follows the "Select an address" heading, it is one paragraph with the link inline inside it, and the link carries `govuk-link`. The page already renders its add paragraph in exactly that position (`contact/template.njk:12-18`), so the position does not move; the bare link becomes the sentence with the link inside it. The prototype's `app-contact-address-page__section-heading` on the heading is not copied — a programme invariant forbids the prototype's custom classes, and the heading already uses `govuk-heading-m`. Rejected alternative: put the sentence below the options — the design source places it directly after the heading.

7. **The sentence lives in the contact feature's own copy, not in shared copy.** A programme invariant forbids rewording shared copy in place, and `shared/copy.en.js:74` (`addressHandshake.addNewAddress`, "Add a new address") is the party pickers' button label, read by `addresses/copy/copy.en.js:83` and rendered by `addresses/party-picker/party-picker.njk:16`. It keeps its wording and its meaning. Rejected alternative: reword the shared key — it would silently change five other pages.

8. **The stub-mode half of criterion 2 is already true and stays untouched.** `contact/controller.js:46-48` issues no add href in stub mode and `template.njk:14` hides the paragraph, so a stub run shows the radios and the save controls alone; `contact.fit.spec.js:87-91` and the stub-guarded case in `tests/animals/e2e/pages/contact-address.spec.ts:86-89` already prove it. The branch filter, by contrast, applies in both modes: criterion 1 is not qualified to the full stack.
   Transporters need no exclusion work: a transporter is its own record in its own collection, never an address-book address, so the addresses read can never return one. Criterion 1's transporter clause is true before the change.

9. **Every tests-repo spec the filter breaks, and where the second branch-held address comes from.** The filter removes from the contact page every record held for a consignment role, in stub mode and on the full stack. Two specs choose such a record on that page today, and both are this row's to fix:
   - `tests/animals/e2e/pages/contact-address.spec.ts` chooses the branch fixture throughout (`:31`, `:37`, `:41`, `:52`, `:57`, `:63`) and keeps passing; it gains this row's new cases.
   - `tests/animals/e2e/features/change-from-cya.spec.ts:102` checks the consignee record on the contact page and `:112` asserts the review then shows it. The consignee record is held as consignee alone (`flows/shared/address-book-seed.ts:139-148`, name from `domain/shared/constants/journey-party-names.ts:3`) and as `CONSIGNEE` in the frontend's stub book (`services/address-book/stub/index.js:19`), so after the filter it is no longer offered. That case exists to prove choosing another contact address from the review, and it needs a second address the page does offer.
   The shared fixture book holds exactly one branch record (`flows/shared/address-book-seed.ts:19-28`, listed at `:95`), and the seeded draft already holds it as its contact address (`domain/animals/constants/journey-options.ts:128`), so there is nothing else to choose. The live address book refuses a record with an empty roles list, so no role-less record exists there either.
   Settled: the shared seed gains a second record held as a branch address, and the frontend's stub book gains the matching record. Set-up two cases share belongs in the shared helper, and the stub book's own doc comment (`services/address-book/stub/index.js:1-14`) states the parity it must keep — each stub record carries the roles the tests repo's shared fixture gives the record with the same address, so a picker lists the same records in stub mode as it would from a live book carrying that fixture. One shared name then works in both modes, and the review-change case chooses it.
   Rejected alternatives: create the second record through the address-book API inside that one case, as `tests/animals/e2e/features/address-book/addresses-picker.spec.ts:18-40` does for its own records — the frontend reads the stub book in a stub run, so an API-created record would not be listed there and the case would fail outside the compose stack; or drop the review-change case's contact half, which would delete the only proof that a different contact address can be chosen from the review.

10. **Nothing in the row's claims turned out to be false.** Checked against the live tree: the contact page does list the whole book (`contact/controller.js:89`); the address book does now accept the branch-address role (`AddressRole.java:21`, `RoleGroup.java:6`), so the row's note that typed records were missing on `main` is stale and the external dependencies it names have landed; the INS add page does set the branch role from the handshake; the return already lands on the contact page with the record committed and the banner set (`addresses/address-return/controller.js:124-140`); the banner wording criterion 4 quotes already exists (`shared/copy.en.js:76-77`). The open question about where contact addresses ultimately come from is left as the row leaves it: the list stays the organisation's own address book, narrowed to branch addresses.
