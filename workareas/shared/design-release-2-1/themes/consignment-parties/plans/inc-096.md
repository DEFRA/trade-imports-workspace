## 0. Decisions

1. **Four of the five criteria already hold on the branch; the work is the
   task's completeness.** The row's note says "there is no permanent-address
   feature folder yet", read at `origin/main` before
   `c4aec878` (identification details and permanent address) merged. The live
   tree has the feature, and the addresses page already builds the permanent
   address section with the hint, the two bullets and the add link
   (`features/addresses/controller.js:121-153`, `features/addresses/copy/copy.en.js:19-29`),
   shows it only for a consignment with a line that needs one
   (`features/permanent-address/cards.js:40-41`), shows the saved address with
   a Change link on return (`features/addresses/controller.js:110-119`), and
   carries the Welsh draft of every one of those strings
   (`features/addresses/copy/copy.cy.js:20-30`). Criteria 1, 2, 4 and 5 are
   met and proven (`features/addresses/controller.test.js:145-300`,
   `features/addresses/copy/copy.test.js:75-101`,
   `features/permanent-address/permanent-address.fit.spec.js:347-372`,
   `repos/trade-imports-ins-tests/tests/animals/e2e/pages/permanent-address.spec.ts:14-49`).
   Criterion 3 does not hold: the Overview task reads Complete as soon as the
   five parties and any in-scope CPH number are given, whatever the permanent
   address section still shows. Only that gap is built. Rejected: re-deriving
   the section from the row's `sources` and rebuilding what main already
   carries.

2. **The task's extra answer is carried by the set's own row status, not by a
   row part.** `bridge/status/statusOf` keeps only the parts whose key is in
   the scope Set (`bridge/status/index.js:88`), and a part key is a bare
   obligation name or a collection name (`bridge/status/classification/index.js:12`).
   The permanent address is a leaf inside `animalIdentifiers` inside
   `commodityLines`, so its scope key is a positional path
   (`docs/scope-and-wipe.md:31-34`: "A leaf inside a group is its positional
   path"), and the nested group's key is positional too. No part key the
   addresses row can carry reaches it. So the addresses row declares the extra
   answer it owes, as a predicate over the answers and the evaluation, in the
   same shape `applies` already takes
   (`sets/live-animals/journeys/linear/flow/task-rows.js:54, 70-76`), and the
   set's `rowStatus` holds the row short of fulfilled while that predicate says
   the answer is owed. Rejected: (a) teaching `bridge/status`'s facets a nested
   member filter — the per-record invariant check in
   `bridge/status/completeness/index.js:96-100` is not filtered by members, so
   an animal missing its ear tag would hold the addresses row back as well, and
   the change lands in the bridge both sets read; (b) a `pageValidation` on the
   permanent address page feeding `invalidRowIds` — the repo has already ruled
   that out in writing (`features/validation-coverage.test.js:26-29`: "a
   pageValidation would wrongly surface its own stored reading on the task list
   and the review page"), and it would need a new refusal message and a Welsh
   draft for it; (c) adding the permanent address page to the addresses row's
   `pages` — inert, since the page collects nothing and is a sub-page, and
   `pages` is the journey-foundation theme's.

3. **A line that needs a permanent address with no animal identified yet leaves
   the task able to complete.** The page asks for no permanent address in that
   state: it shows the message and the link to the consignment details instead
   of cards (`features/permanent-address/controller.js:119-122`,
   spec `REQ-PERM-ADDR-016`), and the identification row reads Complete there,
   because the unit-record floor stands down for a single line
   (`sets/live-animals/obligations/sections/commodities/identifiers.js:95-97`,
   `bridge/status/completeness/invariants.js:84-100`). Holding the addresses
   task at To do would leave the trader a task they cannot finish from the page
   it points at, behind a task that already reads Complete. The prototype reads
   the same way: the section is complete "when its per-animal permanent
   addresses are complete" (`prototype:dr2-1-source` p8-039), vacuous with no
   animals. So the predicate asks that no animal that needs a permanent address
   is without one. Rejected: requiring at least one addressable animal, which
   is what the page's own display gate needs but would also stop such a
   notification being submitted — a product change no criterion asks for.

   In that state the page does still draw an empty Permanent address section:
   `permanentAddressSection` returns a section for any consignment with a line
   that needs one (`features/addresses/controller.js:128-130`) and renders its
   add link because nothing is chosen. So the task can read Complete while a
   section the page shows is empty, which is a departure from criterion 3,
   listed as such in section 14 rather than left to be read later as a
   shortfall.

4. **One owner for "every animal that needs a permanent address has one", and
   one owner for the name test underneath it.** The addresses controller already
   judges the first inline for the section's saved-address display
   (`features/addresses/controller.js:138-140`). The row's predicate would be a
   second expression of it, so the judgement moves to one exported function in
   the permanent address feature and the controller's display gate calls it,
   keeping its own extra condition that there is an address to show.

   Underneath it sits "a stored address counts as held when it has a name". The
   display path applies that test inside `toDisplayParty`
   (`features/addresses/frozen-parties.js:19-21`), which is `async` and returns
   a display party, so the new judgement — synchronous over the answers and the
   evaluation, because `rowStatus` is synchronous (`flow/task-rows.js:73-76`,
   called from `features/hub/controller.js:72` and
   `check-answers/view-model/incomplete-cards.js:61`) — cannot call it. Writing
   the name test a second time would leave one rule with two owners, so the test
   itself is extracted into one synchronous predicate exported from
   `frozen-parties.js`, which `toDisplayParty`'s own early return then calls and
   which the new judgement calls. That is the structural change this row needs;
   it touches the one function and adds no other call site. Rejected: (a)
   leaving the controller alone and writing the completeness judgement twice;
   (b) making the new judgement `async` so it could call `toDisplayParty` — the
   row status seam it is read through is synchronous and resolving country names
   to decide a task status is work no status needs.

5. **No new FIT test.** The rule lives in the set's `rowStatus`, which the unit
   suite drives directly, and the hub's rendering of Complete and To do from a
   row status is already FIT-proven
   (`features/hub/hub.fit.spec.js:103-131, 310-325`). The trader-visible walk is
   proven end to end in the tests repo, which is this row's integration proof. A
   FIT walk would repeat that walk and force the five-party set-up out of
   `fit/live-animals-journey.js:1104-1123` into a promoted helper for no
   coverage the unit and E2E tests do not already give. The new E2E spec
   therefore carries no `@duplicated-in-frontend` tag
   (`repos/trade-imports-ins-tests/README.md:337`).

6. **The review page changes with the task, and that is wanted.** The review's
   card-error state reads the same row status
   (`features/check-answers/view-model/incomplete-cards.js:57-63`), so a
   consignment whose permanent address is owed will now have its roles and
   addresses card marked and named in the review's error summary. That is what
   the design source says ("this drives the hub status and the review card for
   'Roles and addresses'", `prototype:dr2-1-source` p8-040), it needs no new
   copy (`features/check-answers/copy/copy.en.js:109-120` already holds the
   card's outstanding message), and it is spec'd in section 8. Rejected:
   suppressing it to keep the change to the hub.

7. **Submit readiness does not move.** `readyForCheckYourAnswers` rolls up the
   same `rowStatus` (`flow/section-status.js:16-19`), so the downgrade reaches
   it. It changes no verdict: wherever an identified animal owes a permanent
   address the identification row is already short of fulfilled (the leaf is
   mandatory within the unit record,
   `sets/live-animals/obligations/sections/commodities/identifiers.js:184-190`,
   and `flow/task-rows.test.js:321-341` asserts it), and in the no-animal state
   of decision 3 the predicate is satisfied. Recorded as a risk to re-check
   against the suites rather than assumed.

## 2. Edits

### frontend `src/server/app/sets/live-animals/journeys/linear/features/permanent-address/cards.js`

Gains the feature's judgement of whether every animal that needs a permanent
address has one: false while any animal on a line whose commodity and species
pair needs a permanent address holds no permanent address with a name, true
otherwise, including when no line needs one and when a line that needs one has
no animal identified yet. It composes what the module already owns —
`addressableUnits` for the animals that are asked (`cards.js:43-54`) — and asks
the one owner of "a stored address counts as held" for each animal's stored
permanent address — the predicate extracted from `frozen-parties.js:19-21` in
the next edit below;
the module already reaches into that feature folder for its form helpers
(`cards.js:4-10`), and its sibling `saved-addresses.js:2` already imports from
`frozen-parties.js`. It is synchronous over the answers and the evaluation, the
signature `features/commodities/lines.js:6` already uses for a row predicate. It
is exported because the row table and the addresses controller both read it.

### frontend `src/server/app/sets/live-animals/journeys/linear/features/addresses/frozen-parties.js`

The test that a stored address counts as held — it has a name — stops living
inside `toDisplayParty`'s early return (`:19-21`) and becomes one exported
synchronous predicate over a stored party in this file, which that early return
then calls. `toDisplayParty` keeps its signature, its `async` shape and its
return in every case, so every caller of it is untouched. Nothing else in the
file changes. Reason in decision 4: the new row-status judgement is synchronous
and cannot call `toDisplayParty`, and the test must keep one owner.

### frontend `src/server/app/sets/live-animals/journeys/linear/features/addresses/controller.js`

`permanentAddressSection`'s saved-address gate (`:138-140`) stops judging
completeness for itself and asks the new owner in `cards.js`, keeping its own
condition that there is a saved address to show; nothing else about the section
changes, so the page renders exactly as it does now in every state the existing
tests pin. The module already imports from that file (`:11-14`), so this adds no
new dependency direction.

### frontend `src/server/app/sets/live-animals/journeys/linear/flow/task-rows.js`

Two changes, both in the shape the file already has:

- the `addresses` row (`:61`) declares the extra answer it owes — the predicate
  from `cards.js` — alongside its pages, as the `animalIdentification` row
  declares `applies` from `features/commodities/lines.js` (`:54`);
- `rowStatus` (`:73-76`) composes that declaration with the bridge's verdict: a
  row whose declared answer is still owed reads in progress rather than
  fulfilled, and a row that declares none, or whose declared answer is given,
  keeps the verdict `statusOf` returns. The composition is generic over the row,
  so the addresses row is data and not a special case in the function. The
  downgrade target is the in-progress status, never not-started: `statusOf` only
  returns fulfilled once every in-scope part is satisfied, so something is
  always answered when it bites.

Exemplar for both: the `applies`/`rowApplies` pair in the same file, and
`sets/live-animals/docs/journey-flow-and-gates.md:50-58`, which frames `applies`
as the escape hatch for what a row's parts cannot express.

### frontend `src/server/app/bridge/status/index.js`

The module header's second paragraph (`:4-7`) — the claim that
`statusOf(parts, answers, inScope, evaluation)` is the sole runtime source of
the five-way status, naming `flow/task-rows.js` `rowStatus`,
`flow/section-status.js` `sectionStatus` and `readyForCheckYourAnswers` — is
deleted outright. It is the only text in this file this change makes untrue, it
is rationale, and it describes callers in other modules by name, so it is
deleted rather than reworded or replaced. Nothing is written in its place: what
the repo needs to say about the set's row-status seam and the bridge's roll-up
over parts is recorded in the two set docs section 12 edits. No behaviour and no
other line in this file changes.

## 14. Departures from written rules

1. `src/server/app/sets/live-animals/docs/journey-flow-and-gates.md:43-58`:
   "Most row status comes from the union of each page's `collects`. `parts`
   narrows a row to a collection facet… `applies` is the escape hatch for a row
   whose parts cannot express its applicability." The set gains a second escape
   hatch, so a row's status is no longer either the engine roll-up over its
   parts or Not applicable. Reason: the answer criterion 3 asks the row to count
   is a leaf inside a nested collection, whose scope keys are positional paths
   (`docs/scope-and-wipe.md:31-34`), so no part key the row can carry reaches
   it; the alternatives are a change to the shared bridge's facet and invariant
   semantics, or a mechanism the repo has already ruled out in writing
   (decision 2). The doc is corrected in the same change (section 12), and the
   bridge stays the only source of the roll-up over parts.
2. `src/server/app/sets/live-animals/docs/page-design.md:15`: "`rowStatus` stays
   a pure engine query." The new declaration is a pure synchronous function of
   the answers and the evaluation, so the sentence's point — no I/O in
   `rowStatus`, unlike the stored-answer check the hub does per request — still
   holds; but the doc must be corrected (section 12) because the row status is
   no longer only the engine roll-up.
3. The row's criterion 3, "The overview's 'Roles and addresses' task does not
   read 'Complete' while any section the page shows is empty", and the design
   source it rests on, `prototype:dr2-1-source` p8-039: the section is complete
   "when it is the destination address and set, or, when it is not, when its
   per-animal permanent addresses are complete". For one state the plan departs
   from the criterion's first half: a consignment with a line that needs a
   permanent address and no animal identified yet shows an empty Permanent
   address section (`features/addresses/controller.js:128-130` returns the
   section for any such consignment, and renders its add link because nothing is
   chosen) while the task can read Complete. Reason, in full in decision 3: with
   no animal identified the page asks for no permanent address — it shows the
   message and the link to the consignment details instead of cards — the
   identification task already reads Complete in that state, and p8-039's own
   test ("its per-animal permanent addresses are complete") is vacuous with no
   animals, so holding the task at To do would leave the trader a task they
   cannot finish from the page it points at. The behaviour is recorded as its
   own scenario in section 8 and proved by assertion 4 in section 4, so it is a
   stated departure and not a shortfall. The other way to honour the criterion —
   drawing no Permanent address section at all while no animal is identified —
   is rejected here because criteria 1 and 2 ask for the section whenever the
   consignment has a chosen species that needs one, and the existing section
   tests pin that; which of the two the design means is a question for the
   designer, carried as a follow-up in section 7.

## 15. Reachability

Everything this plan builds is reached the moment it lands: the predicate is
called by the addresses row and by the addresses page's section, and the
composition in `rowStatus` is exercised by the one row that declares an extra
answer. Nothing is built for a state that cannot occur — the no-animal state of
decision 3 is reachable today (`REQ-PERM-ADDR-016`), and the plan adds no branch
for a second row, a second declaration or a status the hub cannot render.
