## 0. Decisions

**D1 — Acceptance criterion 1 contradicts criteria 3 and 4 and the row's own detail on the contact address page; built as criterion 3 says.** Criterion 1 puts the contact address page among the pages that "end with their primary button alone", while criterion 3 gives that same page a secondary save button and a cancel link, and the row's detail says in its next sentence that "the contact address page is reached from the overview, so it keeps its two return controls". The distil's own ruling is unambiguous: conflict c-208's outcome says the contact address page "is overview-linked and keeps its controls", and only the CPH number page, the permanent address page and the party pickers end with the primary alone. Built that way: criterion 1 applies to the CPH number and permanent address pages, criterion 3 to the contact address page. Rejected: stripping the contact page's return controls — it would contradict criteria 3 and 4, c-208, c-209 and the page's own task row on the overview. This is the defect the row carries, recorded here rather than silently resolved.

**D2 — Criteria 1, 2 and 4 are already true on this branch; this row proves them and changes nothing for them.** Read on the branch at the HEADs above: `cph-number/template.njk:94` and `permanent-address/template.njk:76` already ask the shared macro for no return controls, and so does the shared party-picker form at `addresses/party-picker/_address-picker.njk:76-81`, which passes its own primary and no return controls. No cancel-amend dialog exists in either frontend — `grep -rni "dialog\|modal"` over both `src/server/app` trees finds only the date picker. The Amend bar and its Cancel amend link are built, at `shared/kit.js:73-97` in both repos, and `live-animals/notification-lifecycle` already requires the bar on every page but the confirmation and the declaration, with a scenario for Cancel amend on a question page opening the confirmation page. So the only behaviour this row changes is criterion 3 and its plants twin. Rejected: re-building any of it — the house rule is to build only what the change makes reachable, and a second mechanism beside one that exists is barred.

**D3 — The plants consignment contact page takes the same wording, in this increment.** The programme invariant is categorical: where a row changes a page or behaviour the plants frontend also has, the same increment changes plants, mirroring wording patterns. Plants has that page (`consignment-contact-select`), hub-linked with the same two return controls, and `req-770` names it as taking this row's change in this increment. Nothing else in the row reaches plants: plants has no CPH number page and no permanent address page, and its three address-book pickers are hub task rows (`journeys/linear/flow/task-rows.js:27-38`) rather than pages reached from a "Roles and addresses" page, so criteria 1 and 4 have no plants twin. Rejected: leaving plants out — it would leave `repos` naming a repo the plan does not touch and break the mirror invariant, and the two frontends would word one page's controls differently with no source saying they should.

**D4 — The two changed strings live in each contact feature's own copy, merged over the shared save-actions copy.** The programme invariant bars rewording shared copy in place and sends a set-specific string to the feature's own copy. The shared leaves are read by every other page, so they stay as they are and each contact feature owns only the two strings that differ, keyed exactly as the shared leaves are, so the override is key-for-key. The primary's words are not duplicated: the page's controls read a save-actions copy resolved once as the shared copy with the feature's two strings over it. Rejected: (a) giving each contact feature a complete save-actions copy bundle — it duplicates "Save and continue" and its Welsh into two features in two repos; (b) adding a second copy parameter to the shared macro — a second mechanism beside the one `copy` parameter it already takes; (c) a generic merge helper as a Nunjucks global — the two globals that exist (`src/config/nunjucks/globals/globals.js`) are view-model shapers, not a map merge, and a generic merge in templates invites copy assembly in views.

**D5 — Where that resolution lives.** In animals the contact page has its own controller and template, so the resolution is module set-up in `contact/controller.js` and the template passes the resolved copy to the macro in place of `sharedCopy.saveActions` (`contact/template.njk:34`). In plants the three picker pages share one template and one render seam, so the resolution lives once in `address-book-picker/render.js` and the page's own copy reaches it through the binding `pickerRoutes` already takes (`address-book-picker/picker-routes.js:163`, the `settings` object each picker controller passes). Only the contact picker supplies one; the other two keep the shared wording with no change to their controllers. Rejected: resolving it in each plants picker controller — three owners for one display rule, and the other two pickers would have to state a default they do not need.

**D6 — The FIT save-control helpers take the page's own labels rather than gaining a second copy.** Both repos' journey helpers pin the shared labels inside themselves (`fit/live-animals-journey.js:1467-1500`; `fit/high-risk-plants-journey.js:74-78`, `:80-83` and `:527-552`), so the contact specs could not use them after the change. Each helper that names a return control takes the label it looks for, defaulting to the shared copy, which is the shape the same file already uses for the transporter forms' differently-worded exit (`fit/live-animals-journey.js:1526`). Every existing caller is unchanged. Rejected: a local locator in each contact spec — set-up two tests use belongs in the shared helper, and two local copies would drift from the macro.

**D7 — The tests repo's shared notification page object gains the hub-worded pair; the overview-worded pair stays true.** `page-objects/shared/base-page.ts`'s `NotificationPage` names each exit control by the words it carries (`:291-301`), and already carries a separate getter for the transporter forms' differently-worded exit (`cancelAndReturnToDashboard`, `:294-296`). The contact pages follow that precedent: one more pair of getters on the same class, inherited by both the animals and the plants contact page objects, which both extend it. The overview-worded getters keep their meaning for every other page, so no caller outside the contact pages changes. Rejected: (a) renaming the existing pair to a label-free hub-exit vocabulary and locating the controls by their form field — honest, but it changes about thirty call sites across the repo for a two-string change, which widens the row's footprint beyond what it needs; (b) declaring the pair separately on each contact page object — two owners for one pair of locators, which the duplication rung would be right to flag.

**D8 — The shared layout check keeps one owner and learns the page's labels.** `page-objects/shared/journey-checks.ts:71-76` checks the layout rule — the two buttons alone in one group, the cancel link entirely below it — and pins the overview wording inside itself. The layout rule holds for the contact page with different words, so the helper takes the page's own two return controls and their labels, defaulting to the overview-worded pair. Its one existing caller is unchanged. Rejected: a second layout check for the contact page — one rule, one owner.

**D9 — Welsh is a machine draft, and no Welsh render path is built.** The locale seam resolves a locale only when one is passed and no controller passes one, so no page renders Welsh today. Each new English string gets a Welsh draft beside it under its module's existing machine-draft marker, which the locale-parity check holds in step. No Welsh scenario is written: the spec takes no scenario for a state the service cannot reach.

**D10 — The design source does not show plants, and that is not a design finding.** The prototype carries the animals journey only, so it says nothing about the plants contact page's return controls. The programme's own rule fills that gap — plants mirrors the animals page's wording pattern — so the wording is set by a source, not chosen by the code, and no `design` finding is owed. The prototype's inconsistency (this one page says "hub" while its siblings and the page it leads to say "overview") is adopted deliberately by c-209 and is not re-opened here.

**D11 — The plants picker test factories own the return-control labels, and take them through the binding each picker spec already passes.** Plants, unlike animals, declares most of a picker page's browser and controller tests once and runs them for three pages: `fit/high-risk-plants-journey.js:1112`'s `describeAddressPicker` and `address-book-picker/controller-test-support.js:528`'s `describeAddressBookPickerController`. Both pin the shared return-control wording inside themselves — the browser factory by calling the module-level `saveAndReturnToHub` and `cancelAndReturnToHub` helpers at four case sites and by naming those controls in four generated titles, the controller factory by a module-scope save-control table whose label feeds three `it.each` title templates and one fixed title. Each factory takes the two labels through the binding its three callers already pass it, defaults them to the shared copy, and is the one place either label is stated for a plants picker. Rejected: (a) leaving the factories alone and giving the contact spec its own copies of those cases — set-up two tests share belongs in the shared helper, and the contact page's cases would drift from its siblings'; (b) locating the controls by their form field and dropping the words from the titles — honest, but it stops both factories proving the wording at all, which is exactly what criterion 3 asks for; (c) passing the whole feature copy module in — the factories need two labels, not a copy bundle, and a wider parameter invites them to read copy they do not own.

**D12 — The new party-picker FIT case proves the served page; the macro test that exists proves the macro.** `src/server/app/sets/live-animals/journeys/linear/features/addresses/party-picker/_address-picker.test.js:184-192` renders the shared picker macro on its own and asserts Save and continue is present while the two return controls and the hub-exit field are not. That is the macro's witness and it stays. It cannot stand for criterion 4, for two reasons the tree shows: it renders the macro's HTML string rather than the page the service serves, and the page template wraps the macro and puts a secondary button of its own above it (`party-picker.njk:14-20`), so only a page-level check can say what the served page ends with; and it proves the absent controls by absence, which the house rule bars as a proof of removal, while the shared ending helper asserts positively that the primary is the journey form's last control and its last visible child. The new FIT case is the page-level witness and is what criterion 4's coverage link names.
