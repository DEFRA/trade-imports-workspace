| Repo | Path | Branch | HEAD |

No other repo changes. The row's repos are insfrontend and tests, and the slice needs
neither more nor less: the germinal journey pages the return points at belong to the
germinal products theme, and the increment's own notes say this lands before them.

## 0. Decisions

1. **The journey type the germinal handshake carries is `gbn-ag-germinal-products`.**
   The germinal set does not exist yet, so this value is chosen here and the germinal
   set must send it. The programme's germinal plan already names the address-book
   return entry by that value
   (`workareas/shared/design-release-2-1/germinal/option-b-plan.md:111`), so taking it
   keeps one vocabulary across the two services and no later rename. Rejected: minting
   a fresh word here, which would leave two names for one journey and force the
   germinal theme to pick one.

2. **Both registered entries hold the one party-to-role map and the one consignment
   contact party by reference; neither carries a copy, and no lookup stops reading them
   off the entry.** The shape is settled, not left open: the party-to-role map becomes a
   module-scope value in `journey-registry.js` and each registered entry references it,
   exactly as each entry already references the module-scope return path template
   (`journey-registry.js:27`, read at `:34`) and the module-scope consignment contact
   party (`:24`, read at `:35`). So every entry still answers all five questions a
   lookup asks of it — which role each party's fulfilment id has, which party is the
   consignment contact, which return path, which set base, which frontend base-URL key —
   and only the last two differ between the two journeys. The alternative shapes were
   rejected for what they cost: a second map inside the germinal entry copies a rule and
   could only invent party identifiers that do not exist yet; and lifting the map out of
   the entries so the lookups read module scope directly would drop the journey-type
   gate (Decision 3), silently widening what the add page accepts to any listed
   fulfilment id under any journey type. The germinal set is a duplicate of the live
   animals feature pages with the same six parties, so the same party implies the same
   role — which is what makes the row's fourth criterion true with no further code.

3. **One module-scope lookup in `journey-registry.js` owns "is this a journey the
   service serves", and the three readers of the registry become its callers.** Today
   that question is answered in three places —
   `roleOfParty` (`journey-registry.js:47-49`), `isConsignmentContact` (`:59-61`) and
   `buildReturnUrl`'s entry check (`:102-105`) — each indexing the registry by the
   handshake's journey type. Registering a second journey makes that one rule with three
   owners, so the house rule on one rule one owner applies inside the file the row is
   already editing: the lookup moves to one module-scope function and those three read
   it. Nothing it gives back changes: a journey type the registry does not hold still
   resolves to no entry, so the handshake still resolves to no role (an unresolvable
   handshake, a page-not-found add page) and to no consignment contact, and
   `buildReturnUrl` still throws for it. That gate is the only thing that keeps a listed
   fulfilment id unresolvable under a journey type the service does not serve, and it
   survives this change unchanged in behaviour. Lookups the change touches, listed
   honestly: `roleOfParty` (`:47-49`), `isConsignmentContact` (`:59-61`),
   `buildReturnUrl` (`:102-105`, and `:109`, which keeps reading the return path
   template off the entry it found). `isResolvableHandshake`, `isReceivingParty`,
   `ownAndOtherRolesOfParty` and `rolesToSaveForParty` keep reading through
   `roleOfParty` and are not edited. Rejected: leaving the three inline lookups, which
   leaves one rule with three owners and no file:line a reviewer can hold the gate to.

4. **"A handshake that names a return address of its own is refused" is already how
   the add page behaves, and the plan proves it positively rather than building a
   refusal.** Checked against the tree: the add page reads only the four handshake
   fields
   (`repos/trade-imports-ins-frontend/src/server/app/features/address-book/handshake-context.js:52`)
   and builds every destination from the registry
   (`.../journey-registry.js:101`, used at `.../add/add.controller.js:75`, `:108`,
   `:217`); the module that honours a caller-supplied return
   (`.../return-to.js:94`) has no call site on the add page. So nothing a caller
   supplies can move the destination. The tests therefore assert the registered
   germinal destination exactly, for a handshake that also carries a return of its
   own — never the absence of the caller's value. Rejected: adding a refusal branch
   and an error for a value the page does not read, which would be unreachable code.

5. **The germinal set base joins the set-base constants, keyed to the animals
   frontend's base URL.** Set bases and the frontend that serves each one have one
   home
   (`repos/trade-imports-ins-frontend/src/server/common/constants/journey-set-bases.js:1`
   and `:6`), and the germinal set is served by the animals frontend. Rejected:
   a `/germinal-products` literal inside the registry entry, which would be a second
   mechanism beside the one that exists.

6. **The hand-back log gains the journey type.** The add page logs the hand-back, the
   cancel hand-back and the roles it discarded with the notification and party only
   (`.../add/add.controller.js:99`). With two journeys registered, those lines no
   longer say which journey the trader was sent to, so support cannot tell a germinal
   hand-back from a live animals one. One function owns that log context and gains the
   journey type; nothing else in the controller changes. This is the one structural
   change outside the registry, and it is the row's own doing.

7. **The expected return address in each test repo is built by one owner that keeps
   its own journey-to-set table, not by reading the registry.** The insfrontend test
   helper already keeps its own animals base URL rather than reading config
   (`src/server/common/test-helpers/journey-handshake.js:64`), so the assertion stays
   independent of the value under test. The tests repo gets the twin of that builder.
   Rejected: importing the registry into the expectation, which would assert a value
   against itself.

8. **The tests repo gets one home for a journey handshake, and the unknown-journey
   refusal stays where it is proved today.** The same handshake address is typed out in
   full in `tests/ins/e2e/features/address-book/address-book-add-handshake-guard.spec.ts:11`
   and `tests/ins/security/address-book/address-book.spec.ts:40` — copies have already
   spread, which is when the repo's own rule gives a value a home
   (`repos/trade-imports-ins-tests/AGENTS.md:24`). The row needs germinal handshakes of
   the same shape, so the home owns the shape and every handshake built from it, the
   unregistered-journey one included, and both copies are deleted by reading it. What
   each spec proves does not move: the guard spec keeps owning the unknown-journey
   refusal and the security spec keeps walking the same refusal as part of its scan;
   both now open the add page at its own address with the handshake as a query
   (Decision 9's mechanism), and neither gains or loses an assertion. The new
   end-to-end spec builds germinal handshakes from the same home and asserts nothing
   about the unknown journey type. Rejected: leaving the two copies and typing a third
   shape for the germinal handshakes, which spreads the copies further; and moving the
   refusal into the new spec, which would delete proof the guard spec already carries.

9. **Both tests-repo specs the row touches reach the add page through the page's own
   address and the open-with-a-query mechanism, not a retyped path.** Each edited line
   today is a raw navigation that retypes `/address-book/add` with the handshake
   appended. That path has a home (`page-objects/ins/address-book/add-page.ts:8`) and
   the repo has a mechanism that opens a page at its own address with a query
   (`page-objects/shared/opens-at-expected-url.ts:10-12`), which also settles sign-in
   either way round — it signs in when asked and returns straight away when the session
   already is. So the change is not only the data in those lines: the navigation itself
   goes through that mechanism, as `AGENTS.md:20` and `:24` require. Rejected: changing
   only the journey type and leaving the retyped path and the raw navigation, which
   would keep two copies of the add page's address in specs that the row is editing
   anyway.

10. **The new end-to-end spec carries the handshake route's own stack gate, no service
    tag, and reads the saved record over the address book's HTTP API.** Three settlings,
    each against a precedent in the same folder:
    - *Environment.* The directly comparable spec — same folder, same
      `/address-book/add` handshake route — gates on the compose stack, in its own
      words: `tests/ins/e2e/features/address-book/address-book-add-handshake-guard.spec.ts:6`,
      "INS handshake routes are only exercised against the compose stack". I found no
      evidence that the add page's handshake route is served in the deployed
      environments, and the germinal return page the controls point at exists in none of
      them, so the new spec carries the same gate for its own reason (the whole
      hand-over and return is exercised against the compose stack), and the sibling's
      gate stays exactly as it is. The earlier reading of
      `tests/ins/e2e/features/notification-type/notification-type.spec.ts:192` was
      wrong: that spec drives the animals frontend and carries `@animals-frontend`, and
      says nothing about the handshake route.
    - *Service tag.* None. `config/service-tags.ts:7` keeps `@ins-frontend` and
      `@address-book` out of specs under `tests/ins`, which already run by path for
      both services' pull requests. `@animals-frontend` is allowed here but is not
      earned: the behaviour under test is the INS frontend's and the address book's, and
      the animals frontend appears only as the address the redirect names.
    - *Reading the record back.* Through the address book's HTTP client
      (`adapters/http/address-book-api-client.ts:93`, handed to specs by the fixture at
      `fixtures/ui.ts:170`), compared against the shared address the form was filled
      from (`domain/ins/constants/trader-address.ts:22` and `:28`) with exactly the
      party's role. That route brings no tag and no environment gate of its own — the
      specs that already use it carry neither
      (`tests/ins/e2e/features/address-book/address-book-add-roles.spec.ts:94`,
      `address-book-validation-messages.spec.ts:66`) — so the compose gate above is the
      spec's only gate. Rejected: the direct Mongo read, which would bring the
      `@mongodb` tag and a second stack gate
      (`address-book-persistence.spec.ts:10-12`) for a record the service's own API
      already serves.

11. **The address the browser is sent to is read with the browser's own address, and no
    navigation-capture mechanism is added to the tests repo.** The germinal return page
    does not exist yet, so the animals frontend answers a page-not-found at it; the
    assertion is the address, not what answers there, so a landed 404 is expected and
    harmless. The two link controls are asserted by the address they offer before
    anything is activated. The insfrontend fit suite keeps using its own existing
    mechanism for this, which aborts the animals frontend and reads the return request
    (`src/server/app/features/address-book/fit/add.fit.spec.js:545` and `:553`).
    Rejected: `utils/playwright/main-frame-navigations.ts:8`, which records paths
    without their query and so cannot see the fulfilment id, token, address id and
    landing the criterion names; and adding request interception to the tests repo,
    which uses none today.

12. **The row's claims hold.** Verified against the tree: the registry registers one
    journey, pointing at the live animals set base (`journey-registry.js:30`), the
    animals frontend has only the live animals set
    (`repos/trade-imports-animals-frontend/src/server/app/sets/` holds `live-animals`
    alone), and the set-base constants know only live animals and high-risk plants. No
    claim in the row is wrong. One wording note: the third criterion's "refused" is
    satisfied by the add page never reading a caller's return (Decision 4), not by an
    error response.
