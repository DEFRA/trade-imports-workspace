## 0. Decisions

**D1 — Every behaviour the row's five criteria require is already true in the code. The row's work is proof and spec, not production change.** Read on the branch at the HEADs above:

- Both frontends post every save control of a page to that page's one POST handler, with the save-and-return control carrying a named form field and nothing else (`shared/save-actions.njk:42-47`). The handler validates first and consults the field only to pick where a valid save goes (`shared/kit.js:187-190` and `:243-245`). So a page's checks cannot differ between its controls unless a page reads that field before validating, and none does.
- The contact address page validates the submission, then refuses it before any commit, for every control alike (`contact/controller.js:139-153`), and its rule requires a choice on a submitted form (`contact/validate.js:13-17`). Criterion 1's and criterion 2's check halves hold.
- The contact address page's valid save redirects through the shared next-target helper, which answers with the overview for the save-and-return control (`contact/controller.js:181`, `shared/kit.js:243-245`). Criterion 2's save half holds.
- The county parish holding number page offers one save control: its template asks the shared macro for no return controls (`cph-number/template.njk:94`). That one control saves what was entered and reports each wrong part on its own (`cph-number/controller.js:98-100`, `cph-number/validate.js:62-90`). Criterion 3 holds.
- The permanent address page likewise offers one save control (`permanent-address/template.njk:76`), which applies the page's own new-address refusals and, with those passed, writes the answers (`permanent-address/controller.js:149-208`, `permanent-address/validate.js:81-96`). Criterion 4 holds.
- The plants consignment contact page is one of three pages served by one picker route pair, whose save path runs the same selection check whichever control posted it, the search button alone branching earlier (`address-book-picker/picker-routes.js:111-148`, `address-book-picker/save-selection.js:35-60`). Criterion 5 holds.

So nothing is built. Rejected: writing a production change to "make the rule hold" — there is nothing that breaks it, and adding a second mechanism beside the one that exists is barred. Rejected also: reporting the row as not carriable — its criteria are true claims, and what they are missing is a witness and a spec line, which is work this plan does.

**D2 — Criterion 2 names the control by the words it no longer carries; it is built as the page reads today.** The criterion says "'Save and return to overview' on the contact address page". On that page the control reads "Save and return to hub" and the link below it "Cancel and return to hub" (`contact/copy/copy.en.js:13-16`), which inc-097 put there and which the page spec and `live-animals/journey-flow`'s REQ-FLOW-014 already record. It is the same control, posting the same field. Everything this plan writes names it by the words the page carries. Rejected: rewording the page back to the shared copy to match the criterion's wording — it would undo a landed, spec'd and signed decision for a stale label in an acceptance criterion.

**D3 — Criteria 3 and 4 name pages that offer one save control, so the rule is satisfied with nothing to compare, and they are already proven.** The county parish holding number page's save, including a submission that poses as a hub exit, is proven at the rule's own owner (`features/save-actions.test.js:227-249`); its per-part messages are proven in its validation and browser tests and recorded as REQ-CPH-004. The permanent address page's new-address refusals and its save are proven in its own controller and browser tests and recorded as REQ-PERM-ADDR-012, REQ-PERM-ADDR-007 and REQ-PERM-ADDR-008. So neither page takes a new test; the county parish holding number page's cross-page witness is unlinked in the coverage matrix today and gains its link (section 8). Rejected: adding a permanent address case to `features/save-actions.test.js` beside the county parish holding one — it would restate assertions the feature's own tests already make, which the duplication rung would be right to flag, and the county parish holding case exists there only because the page's refusal of a posed hub exit is behaviour no feature test covers.

**D4 — Criterion 1's state is reachable, two ways, and that is what the new tests seed.** A radio cannot be un-checked in a browser, so an amending trader can press a save control on the contact address page with nothing chosen only when the page opens with no option chosen. It does exactly that whenever the copy the notification holds is not one of the addresses offered: the page pre-selects only a copy whose source record is still on the list (`contact/controller.js:107`, `:118-120`). Two reachable routes reach it — the source record is no longer offered by the organisation's book, and the copy's details were edited on the notification, which the review offers while amending and which deliberately drops the link back to the source record (`addresses/party-edit/address-rules.js:119-121`, whose doc comment states that an edited copy no longer matches the record it was picked from so the picker should not pre-select it; `check-answers/view-model/cards/addresses/contact-address.js:35-37`, `addresses/party-edit/party-edit.controller.js:27`). An amendment always holds a contact address, because a notification with none is not submittable (`flow/task-rows.test.js:567`), so the "no address held" variant is not a route. Rejected: reporting criterion 1 as describing an unreachable state — it describes a real one, and naming the route is what the tests need.

**D5 — Criterion 1's witnesses are a unit case at the rule's one owner and one end-to-end case; no browser-test case.** The browser tests serve the stub address book, whose records cannot be removed, so the only route to the state there is a submit-and-amend walk followed by an edit of the contact copy — several pages the contact feature's browser spec does not own, for a state the unit case pins exactly. The end-to-end suite already drives amendments and the review's edit links, so it carries the user-visible half. Rejected: a browser-test case as well — three witnesses for one behaviour, the slowest of them the least precise.

**D6 — The contact address page's new cases live in `features/save-actions.test.js`, not in the feature's own tests.** That file is the one place the cross-page rule is proven, page by page, and it already holds a hub-exit group and an amending group for it (`:59-250`, `:259-302`). The feature's own tests prove each control's refusal separately (`contact/controller.test.js:135-154`) and never compare them, which is the assertion the rule needs. Rejected: putting the comparison in `contact/controller.test.js` — it would give the rule a second owner and leave the amending group naming one page when the row's point is that no page is an exception.

**D7 — The plants frontend takes no file change.** Criterion 5 is proven for the consignment contact page by the two shared plants factories, which declare a picker's cases once and run them for all three pickers over both of the page's save controls: the controller factory's refusal groups (`address-book-picker/controller-test-support.js:46-49`, `:261-272`, `:303-332`, `:354-366`, `:448-456`) and the browser factory's refusal cases (`fit/high-risk-plants-journey.js:1384`, `:1430`). The end-to-end suite drives the blank save on each control too (`tests/plants/e2e/features/contact.spec.ts`). Only the plants spec text is short of the rule, and that write is in this workspace repo. Rejected: a plants `features/save-actions.test.js` mirroring the animals one — a second owner for a rule the picker factories already own for every picker.

**D8 — The permanent address page honours a posted hub exit while the county parish holding number page refuses one, and neither offers the control. Out of scope.** The county parish holding page pins the choice to "not a hub exit" before redirecting (`cph-number/controller.js:33-38`); the permanent address page reads the request's own choice (`permanent-address/controller.js:205-208`). Neither page offers the control, so no control a trader can press behaves differently and the row's invariant is untouched; the difference is in where a save goes, which the row's own notes hand to EUDPA-774. Recorded as a follow-up (section 7). Rejected: fixing it here — it changes a page's navigation, which this row was trimmed of.

**D9 — No journey-flow requirement text is reworded; one scenario is added to the requirement that already owns the amend-time rule.** `live-animals/journey-flow` states the cross-page rule twice already, for a valid save and for an amendment: REQ-FLOW-004 (`:138`) and REQ-FLOW-015 (`:372-373`), whose statement is already qualified to "each of a page's save buttons" and whose single scenario names the main import reason page. Criterion 1 is a second page under REQ-FLOW-015, so it is a scenario there, not new requirement text. `plants/journey-flow` REQ-PLANTS-FLOW-004 (`:101`) and `plants/addresses` (`:143`) own the plants side and are already right. Rejected: a new requirement stating the rule a third time.

**D10 — Both frontends' validation docs name one page's label for a rule every page follows. Not edited here.** `src/server/app/docs/validation.md:59-63` in animals and `:46-50` in plants state the rule in terms of "Save and return to overview", which the contact address page no longer reads. The statement is true of every page's behaviour and this row makes nothing in it untrue, and neither file is edited for the row's own work, so the bounded-tidy-up rule leaves it alone. Recorded as a follow-up.

**D11 — No signed-off scenario is touched.** `tim spec diff --signed-off` is the loop's own check; read by hand, `openspec/specs/live-animals/journey-flow/spec.md` carries seven signed-off scenarios (`:22`, `:88`, `:104`, `:169`, `:305`, `:461`, `:469`) and this row edits none of them — REQ-FLOW-015 and its scenario (`:372-380`) carry no sign-off. The four page specs this row writes to carry no `**Signed off**` line at all (`grep -rn "Signed off"` over the contact address and plants consignment contact specs prints nothing), and their maturity levels are `detailing` (contact address, county parish holding number, permanent address) and `exploring` (plants consignment contact), so none is a signed-off page.

**D12 — Welsh.** No English string is added or changed, so no Welsh draft is owed and the locale-parity check has nothing new to hold.

**D13 — Criterion 1's given is spec'd by qualifying the requirement that owns "shown chosen on return", not by a scenario that contradicts it.** REQ-CONTACT-002's statement is an unqualified MUST: a chosen contact address is copied onto the notification and, on return, "MUST show it as chosen in the list". The page qualifies that in two ways (D4): a held copy is pre-selected only while its source record is still offered and the copy is unedited (`contact/controller.js:118-120`, `addresses/party-edit/address-rules.js:119-121`). So the qualification goes into REQ-CONTACT-002's own statement, and criterion 1's given sits as a scenario under it (section 8). Rejected: putting that scenario under REQ-CONTACT-001, which owns the list as the page is first opened — the scenario is about a notification that already holds a copy and the trader returning to the page, which is REQ-CONTACT-002's subject, and moving the scenario would leave REQ-CONTACT-002's MUST unqualified and so untrue of the running page. Rejected also: leaving REQ-CONTACT-002's statement as it is and adding the scenario anyway — the spec would then state one thing and witness the opposite.

**D14 — Criterion 1's "the trader's own choice still shown" clause is owed nothing beyond what the new scenario already states.** The contact address page's only input is its radio group, so "what they entered" is the chosen option and nothing else. In the state criterion 1 describes — an amendment whose page opens with no option chosen (D4), and a save control pressed without choosing — the trader has chosen nothing, so there is no choice to keep; what the clause resolves to is that the refused page comes back offering the organisation's addresses again, with none chosen, which is what the refusal renders (`contact/controller.js:144-152` renders the full offered list with no selected value) and what the new scenario's THEN states and the new unit and end-to-end cases assert positively. The one state where a trader did submit a value and it is deliberately not kept is a value the book does not hold, which REQ-CONTACT-004 already states ("MUST NOT show any option as chosen once refused") and SCN-CONTACT-004-A and -B already witness. The open end is whether a trader amending a notification that already holds an address should see nothing ticked after a refusal: that is the designer question section 7 carries, and it is this clause's open end, not a defect this row fixes. Rejected: treating the clause as unproven and adding a case that asserts a preserved selection — the page does not preserve one, and a test of behaviour the page does not have would be wrong.

**D15 — Which partial coverage links this stackless run can clear.** The run holds no workspace stack, so no end-to-end link can be red-probed and every end-to-end link, new or existing, stays `partial` with the absent stack as its reason. Unit and FIT links can be probed on this machine, so a link whose only reason for being `partial` was "the production line it depends on is this row's own uncommitted edit" can now be probed and promoted, because that edit landed with inc-097. A link that is `partial` for what it proves rather than for want of a probe keeps its `partial` and its own reason. Section 8 names each link and which of these it is. Rejected: promising both of criterion 2's partial scenarios full links across the board — their end-to-end links cannot be probed here.
