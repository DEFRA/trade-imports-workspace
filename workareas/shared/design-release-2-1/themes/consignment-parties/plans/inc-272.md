## 0. Decisions

**One record cannot hold the roles both journeys' pickers ask for, so the suite seeds one record per role group.**
The row's first criterion asks for "the address the k6 suites seed" to be saved "with every role the
journey's pickers filter by". That is impossible: the address book refuses a record whose roles span
more than one group (`trade-imports-address-book/src/main/java/.../address/AddressRequest.java:25`, with the
rule stated at `:102-106` — "Every role must come from one group: sending (PLACE_OF_ORIGIN, CONSIGNOR),
receiving (CONSIGNEE, IMPORTER, PLACE_OF_DESTINATION) or branch (BRANCH_ADDRESS)"), and the INS add form
drops any posted role the chosen address type does not offer before it saves
(`trade-imports-ins-frontend/src/server/app/features/address-book/add/add.controller.js:302-310`, through
`.../services/address-book/address-types.js:23-39`). The plants consignor picker filters by `CONSIGNOR`
(sending group) and the place-of-destination picker by `PLACE_OF_DESTINATION` (receiving group), so the
suite seeds one record under each of those two address types, both under the one address name the pickers
search for. Rejected: one record with every role (refused by the address book); one record per role (five
records where two suffice, and the roles of a group can share a record).

**Both journeys' roles are seeded, not only the plants ones.** The row's third criterion reads as though
live animals is unaffected. It is not: the commit that added role filtering to the plants pickers
(`trade-imports-plants-frontend` `0ad43df`) added it to the animals pickers in the same change
(`trade-imports-animals-frontend` `b2063dbe`, `src/server/app/sets/live-animals/journeys/linear/features/addresses/parties.js:14-46`),
and both commits are on this branch only. Four of the five animals party pickers therefore find nothing
either, and each of those parties is mandatory
(`trade-imports-animals-frontend/src/server/app/sets/live-animals/obligations/sections/parties.js:18-22`),
so the animals declaration would refuse too. The run that failed never reached it: the abort came at 67% of
the window on the plants threshold, and the summary carries no live-animals confirmation check at all
(`workareas/shared/design-release-2-1/themes/consignment-parties/logs/inc-088-ci-fail-2-animals-smoke.log:1195,1987`).
So the two seeded records carry every role either journey's pickers filter by: the sending record holds
place of origin and consignor, the receiving record holds consignee, importer and place of destination.
Rejected: seeding only the two plants roles, which would leave the animals scenario red for the same reason.

**The consignment-contact sections were never the problem.** The row's detail says the plants journey
cannot answer "consignor, place of destination or consignment contact". The contact pickers in both
journeys bind no address-book role (`trade-imports-plants-frontend/src/server/app/sets/high-risk-plants/journeys/linear/parties/index.js:33-38`;
`trade-imports-animals-frontend/.../features/addresses/parties.js:54-62`), and a record matches when no role
is asked for (`trade-imports-plants-frontend/src/server/app/services/address-book/index.js:18-21`), so the
contact section is answerable today and the run log shows its check passing. Planned against the two
sections that are genuinely unanswerable.

**A search asks for one role, not just one tab.** A tab lists every record holding any role of its group,
so a stale record holding only place of origin would make the sending tab look seeded while the consignor
picker still found nothing. The INS list page takes a role filter as well as the tab
(`trade-imports-ins-frontend/src/server/app/features/address-book/list/list.controller.js:193-206,341-350`,
offered per tab by `.../address-book-tabs.js:7-14`), so the set-up asks per role. That is what makes the
suite "keep working when a picker's role changes": a newly declared role is found missing and seeded, even
against a stack that already holds the old record. Rejected: searching the tab only, which is one request
fewer and silently wrong against a reused stack.

**The order of the list path's parameters is free, and is chosen to leave today's paths untouched.** The
list route reads each parameter by name, not by position: the tab at
`trade-imports-ins-frontend/src/server/app/features/address-book/list/list.controller.js:344`, the search
term at `:345`, and the role at `:247` through the parameter name its tab declares
(`.../features/address-book/address-book-tabs.js:12`). So no order is required of the suite. The narrowing
is put between the tab and the encoded search term for the one reason that holds: with no role asked for the
path is byte-identical to what the suite builds today, so the session's tab comparison
(`src/k6/front-door.js:189-191`) and its searches keep matching without being touched. Rejected: appending
the narrowing last, which is equally correct for the route but makes the existing search paths differ from
their current bytes for no gain.

**The branch address type is not seeded.** No picker in either journey filters by a branch role, so seeding
one would build something nothing reaches.

**The address-book session and the background filler keep adding under one address type.** Their tab
assertions and their worst-case search are all written against one tab, and spreading them is a load-shape
change this row does not need. Only the roles they tick change, because every add in the suite now derives
its roles from the one declaration. Rejected: leaving their tick as a separate single role, which would put
the roles in two places and break the row's fourth criterion.

**The row's own words "`ADDED_ROLE` … saves the record with it" check out**: `src/lib/address-book.js:12`
holds the single role and `:39-43` builds the answers that tick it; the save itself is
`src/k6/front-door.js:148-164`.

## 13. Operability
