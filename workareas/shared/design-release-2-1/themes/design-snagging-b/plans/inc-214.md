## 0. Decisions

1. **Which lines get a card.** A commodity line gets a species card only when its commodity carries identifier fields and the line has a positive number of animals (the engine's cap for its identifier collection is a whole number above zero). This matches the prototype (a species with no entry count gets no panel) and makes the uncapped states unreachable, so their copy and branches go (see 15). Rejected: keeping a card with the open "Enter details for <species>" counter for an uncounted line.
2. **The page still exists while lines lack a count.** The guard that carries a request on when nothing on the consignment carries an identifier keeps its present test (any line with identifier fields), so journey flow and the hub row are unchanged. A consignment whose identified lines have no count yet renders the summary and no sections. Rejected: redirecting onward when no line has a card, which changes journey flow and the task row's applicability.
3. **What each submit saves.** A card button (`add:<line>`) builds, validates and saves only that line's form; every other card's typed values are neither validated nor saved, and the page reloads with that card's form empty. "Save and continue", "Save and return to overview", the amend save buttons and the hidden implicit-submit default save only the forms of lines whose number of animals is exactly 1; a line of more animals is never saved by them. One-animal forms still refuse a format failure (over-length identifier, partial address) on every save, including the hub exit, as the programme invariant requires. Rejected: saving every form holding data (today's behaviour), which the prototype does not do and which errors on a species the trader did not submit.
4. **Implicit submit stays.** The hidden first submit button that Enter fires stays, so Enter never fires a Remove now that the saved table sits below each form. Under decision 3 it saves only one-animal forms; Enter in a multi-animal form leaves that entry unsaved, as the prototype's Save and continue does. Recorded as a risk.
5. **Re-render after a refusal** shows the values of the forms that were submitted for saving; other cards open empty. The prototype keeps only the first failing species' values. Rejected: carrying every card's typed values, which would need forms built for lines the submit does not save.
6. **Summary rows reuse the Commodity details grouping.** One row per commodity (Common name = the commodity's catalogue name, "Cow" for 0102, Species = every chosen Latin name under it, one per line with a comma and a line break, Number of animals = the total of its lines' counts), except a commodity on code 01061900, where each species line is its own row named by the species' common name. The grouping rule now lives in one shared module at the commodities feature root, which both pages read; Commodity details adds its remove action and Identification adds its total and change link. Rejected: copying the grouping into the identification summary (two owners of one rule). This corrects the backlog note's inc-046 AC2 as the row says: 01061900 gets a row per species.
7. **A count total with no counted line** shows an empty cell, as an uncounted line does today.
8. **`consignment-details/lines.js` moves to the commodities feature root**, because the shared grouping module, the identification controller and the identification sections all read it and a feature-root module must not import from a page folder. It also gains the commodity-group builder (decision 19). Its other importers change their import line only.
9. **The species cell markup has one owner**: a shared Nunjucks macro at the commodities feature root, used by the Commodity details table and the identification summary. Rejected: a second hand-written loop of the same `,<br>` markup.
10. **Card look** follows `documents/template.njk:68-152` (hand-written GOV.UK summary card: title wrapper, title, actions list, content), not the prototype's custom CSS and div grid. The species name is the card title as an `h3` under the commodity section's `h2`; "Change number of animals" is the card's action, with the species name visually hidden. The entry fields sit in a two-thirds column inside the card content, as documents does; the saved-animals table and over-count message sit full width in the card. The card button is the primary (green) button. The trailing section break after every card goes (summary cards are already bordered; the prototype has none — the inc-205 follow-up).
11. **Headings**: H1 page title, `h2` commodity section, `h3` species card title, `h4` the entry counter and the permanent-address question beneath it. Rejected: keeping the counter at `h3` beside the card title.
12. **Full width**: the page passes the `display` surface to `kit.base` (as `documents/view-model/render.js:44` does). The error summary, caption, H1 and inset sit in a two-thirds column, as `documents/template.njk:13-52`; the summary table, Add another commodity link, sections and save actions are full width.
13. **Identifier labels have one name.** Every entry label now equals its saved-animals column heading ("Microchip", "Passport", "Tattoo", "Ear tag", "Horse name") and no identifier has a hint, so the per-field label-and-hint copy block is deleted in both locales and the fields read their label from the identifier-label copy. Rejected: keeping two copy blocks holding the same five words.
14. **Length errors** read "<label> must be 58 characters or less" in English. The Welsh messages already say "58 nod neu lai" and stay. Trimming already happens before the length check (`lib/validate/validators.js:55-63` trims, `identifier/fields.js:38` stores trimmed), so the 58-characters-with-spaces criterion needs a test, not code.
15. **Claims checked against the tree.** The completion message, counter-without-cap, Microchip label and hints, "or fewer" errors, secondary card button, three-column summary with species common names and the saved table above the form are all as the row says. The anchor `identification-card-<line index>` that the Commodity details count-drop error links to (`consignment-details/validation/count-drop.js:30`) and the card-level error summary use (`card/error-summary.js:15`) keeps its value and moves onto the species card, so the refusal lands on that card in its section. No claim is wrong.
