## 0. Decisions

1. **Commodity search already logs nothing (the row's claim is stale).** On `origin/main`, `search.controller.js:84-91` shows the "Select a commodity" error without calling `kit.logRefusal`. Its tests at `search.controller.test.js:197` and `:207` assert `logger.entries` is empty. Only the test half of that criterion is left (decision 4). The controller does not change.
2. **`kit.logRefusal`'s `fieldErrors` option stays in both frontends,** documented as only for refusals the trader cannot correct on the form. It fills `errorCodes`, which support searches by. Every remaining caller is such a refusal:
   - animals documents (scans not cleared);
   - animals party picker (an id the book does not hold);
   - animals transit countries (the cap, or a country not on the list);
   - plants check answers (sections still unanswered);
   - plants address-book picker (an id not in the book).

   Rejected: removing the option. That would change five callers and give check answers a reason key, to lose a field support uses. Both `kit.js` doc comments (the `wip` already has them) and both `architecture.md` paragraphs say the same thing.
3. **Transit countries: one owner for "which add refusals are the trader's own input".** It is a predicate beside `TRANSIT_REFUSAL` in `validate.js`. It covers nothing chosen and already added. The controller's add branch asks it before logging. The cap and not-on-the-list refusals log once, as now. Continue's list refusal (`postContinue`) still logs, because it is a tampered or stale post. The `wip` has this shape, and its tests (decision 4) stay as the `wip` wrote them.

   - **No refusal line:** `expectNoRefusalLogged` (`engine/test-support.js:346` animals, `:129` plants), which filters for the refusal message only. A test whose title says nothing about logging, or says it logs no refusal, may use this.

   Applied to every touched test:
