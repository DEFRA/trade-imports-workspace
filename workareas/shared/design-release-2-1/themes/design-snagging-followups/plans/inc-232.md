## 0. Decisions

1. **One rule: Save and return to overview runs exactly the checks Save and continue runs.** The lenient mechanism is removed, not narrowed:
   - the `allowMissing` option of `validate` in `lib/validate/run.js` (both repos);
   - the `allowMissing` context of `pageValidation.onSubmit` in `lib/validate/page-validation.js` (animals);
   - every controller that passes it.

   Rejected: keeping the option with no callers. That builds what nothing reaches.
2. **`kit.isHubExit` is deleted in both repos.** After this change it has no production caller:
   - the `allowMissing` call sites are gone;
   - the commodity search page's hub skip is gone.

   `kit.hubExitTarget` stays, because it still decides where a valid save goes.
3. **Claims in the row that do not hold, planned against the code as it is:**
   - *"startsADocument counts only an offered type, so Save and continue drops a part-filled document with no type."* Not true at this HEAD. The page POST uses `answersADocument` (`documents/form/payload.js:63-69`), which already counts a reference, any type and any date text. Save and continue with a reference and a date but no type is refused today (`documents/controller.test.js:1143`).

     What really drops input is different. The save buttons post the typed fields to the page with no file (the template's form has no enctype, `template.njk:54-58`). So a chosen file never reaches the page on Save and continue or Save and return. A complete document is refused with "Choose a file and select 'Save and add another'", and a file chosen on its own is dropped without a word.
   - *"The transporter page already refuses a blank choice on Save and return."* Not true. It accepts a blank choice on both buttons and saves nothing (`transporters.controller.test.js:162`, `:201`). Because both buttons agree, it already meets the rule and is left alone.
   - The line numbers in the row (`documents/controller.js:293-335`, `controller.test.js:582-614`) have drifted. The code they mean is `leavePage` and `continuesADocument` (`controller.js:301-331`) and the tests at `controller.test.js:961-970` and `:1193-1199`.
4. **Pages whose answers are all optional do not change.** Removing the option makes no observable difference to these, because their rules already accept a blank on both buttons:
   - animals arrival details (port of entry);
   - additional details;
   - transit countries;
   - transporter;
   - the role and party address pickers (both repos), which move on with nothing chosen from either button.

   Their tests and spec scenarios stay (SCN-FLOW-004-G, REQ-ARRIVAL-006, REQ-PLANTS-ADDR-005 and the picker scenarios). The animals origin page needs care here: its `onSubmit` is called without the context.
5. **Upload documents: every save button sends the file while the add form is open.**
   - When the add form is open (an upload session was opened and the notification is below its cap), every save button posts the whole form to that upload session as multipart, as "Save and add another" does today. Each button carries its own submitted choice. This covers Save and continue, Save and return to overview, and, while amending, Save and return and Save and continue.
   - When the add form is closed, the save buttons post to the page as they do today.
   - Remove buttons always post to the page.

   This is the only way a complete document reaches the service from a no-JavaScript page.

   Rejected: posting the whole form to this service. That would mean taking multipart files in hapi and relaying them, against the direct-to-uploader design in `page-design.md:340-345`. Also rejected: keeping "choose a file and use the add action". That contradicts the criterion that a complete document is saved on Save and return.
6. **What "started" means, owned once.** A document is started when it has any of these:
   - a reference;
   - a type, whether or not the page offers it;
   - any date-of-issue text;
   - a returned file entry with a file name and content.

   One function in `documents/form/payload.js` owns this rule. It replaces both `startsADocument` and `answersADocument`, which today split one rule across two functions. On the page POST path no file can arrive, so only the typed fields count there.
7. **What each path does with the trader's choice.** "Save choice" below is what decision 9 defines: the hub exit and the change context.

   | Path | Form | What happens |
   |---|---|---|
   | Page POST (add form closed) | Started document, any save button | Refused. At the cap, the capacity error alone, as today. Otherwise every field error, plus the "Upload a document" file error when a session is open. Every value is kept and nothing is appended. |
   | Page POST (add form closed) | Untouched | Routed by the request's own save choice, as today: Save and return to overview goes to Overview; every other save button runs `leavePage`'s holds, then goes where kit sends it. |
   | Returned upload | Started, incomplete or invalid | Refused on every choice with the claim's all-or-nothing errors. Values are kept and nothing is appended. This is `claimUpload`'s existing refusal. |
   | Returned upload | Untouched | Nothing is claimed. Save and add another is refused as today, because the add action always tries to add. Every other choice is routed by the returned save choice: Save and return to overview goes to Overview; Save and continue, the amend Save and return and the amend Save and continue run `leavePage`'s holds, then go where kit sends them. With nothing pending, the amend Save and return reaches the review and the amend Save and continue reaches the next page, whether or not the page was opened from a Change link. |
   | Returned upload | Complete | Claimed and appended once, then routed by the returned save choice: Save and add another redirects back to the page, as today; Save and return to overview redirects to Overview; Save and continue and both amend buttons run `leavePage`'s holds, which hold the trader on the page (decision 8b). |

   The "Choose a file and select 'Save and add another'" message (`notYetAdded`, en and cy) and `notYetAddedFileError` become unreachable and are deleted.
8. **Save and return to overview still does not wait for a scan or an unlisted taken-on document** (`leavePage`'s two holds).
   - Those holds stop the journey moving past the page. They are not answer validation.
   - A document saved by Save and return to overview is always "Scanning for virus" at that moment. Holding it would make the "complete document → Overview" criterion impossible to meet.
   - `page-design.md:376-378` already records this exit and stays true.

   Rejected: running the holds on the hub exit too.

   **8b. Save and continue straight after a claim has one outcome: held.** The trader stays on Upload documents, the new document is listed as "Scanning for virus", and the error summary shows the settling message ("You cannot continue until all documents have been scanned or removed"). The same holds for the amend Save and return and the amend Save and continue, which are not hub exits and so run the same holds, exactly as they do on a page POST today.
   - Why it is deterministic: the claim and the hold read happen on the request the upload service returns the browser with, before any refresh read of the scan. The stub keeps a newly registered upload "Scanning for virus" until a refresh read (`services/document-uploads/stub.js:109-117`), and `loadPage` reads without refresh on that request (`handlers/load-page.js:9`).
   - How it is reached: **rendered directly** on the returned request, by `leavePage`'s existing scan hold (`renderStillSettling`, `controller.js:289-299`), with status 400. `leavePage` loads the page state afresh, so the new document is listed.
   - A reload of that response replays the returned request. It saves nothing a second time: `isAlreadySaved` (`controller.js:182-185`) already stops a second append, and the existing replay test (`controller.test.js:555-558`) proves it. `page-design.md:363-364` is edited to state this (section 12).

   Rejected: redirecting to the page. A plain GET of the page shows no settling hold, so the hold would need a new query flag the GET reads: a second mechanism beside `leavePage`'s hold.
9. **One mechanism carries a returned upload's save choice into kit's rules: kit's routing functions take an explicit save choice (option a).** A returned upload is a GET with no payload, and its query is the return path fixed when the session opened (`contracts/upload-session.js:29-45`), not the query of the button pressed. So kit cannot read the choice from the request, and the request is never faked or mutated.
   - **The save choice** is one value with two parts: the hub exit (Save and return to overview was pressed) and the change context (the save returns to the review). Today kit reads the first from `request.payload?.exit` (`shared/kit.js:142-143`) and the second from `request.query.change` (`shared/kit.js:147`).
   - **`shared/kit.js` gains one exported reader of a request's save choice**, built from those two readings, so the hub-exit and change-context rules each keep one owner there. `hubExitTarget` (`:142-143`) and `changeContext` (`:147`) keep their behaviour and read through it.
   - **`shared/kit.js` gains one exported reader of a returned form's save choice**, beside the request reader. Its inputs are the request, the form the upload service returns and the journey. Its rules:
     - hub exit when the returned form's `exit` is `hub`, as the request reader;
     - while the journey is being amended (the test `amendReviewTarget` uses, `kit.js:159-162`), the change context comes only from the button: on when the returned form carries the amend Save and return's submitted choice, off otherwise;
     - otherwise the change context is the request's own, which is the context the page was opened and posted with.
   - **`exitTarget` (`kit.js:152-156`) and `nextTarget` (`kit.js:184-189`) gain an optional trailing options object carrying a save choice.** When it is absent they read the request's save choice, exactly as today.
     - Callers: every existing caller of `exitTarget` and `nextTarget` (the animals controllers under `sets/live-animals/journeys/linear/features/`, among them contact, transporters, continue-from-transporter-list, transit countries, port of entry, additional details, consignment details, animal identification, commit-selection, the party picker, addresses, import reason, origin, CPH number and documents) passes nothing new and is not edited.
     - The one new caller is the documents controller, on the returned-upload path.
     - Reason: it is the only way to route a GET by a choice made on another request without a second routing rule. Rejected: option (b), translating the returned choice into a request-shaped value for kit. That either fakes a request or copies kit's hub and change-context rules into the documents feature.
   - **The amend Save and return's submitted choice is owned by `amendFormActions`** (`shared/amend-form-actions.js:25-34`), which already owns "Save and return returns to the review, Save and continue goes on" as the two URLs. It also returns the name and value the amend Save and return submits when its form posts somewhere other than the page, and kit's returned-form reader compares against that one value. While amending, the two amend buttons can no longer be told apart by their form action, because both post to the upload session.
   - The plants `shared/kit.js` is not given either reader or the options: plants has no page whose save returns through another service (section 15).
10. **The save-actions macro is extended, not bypassed.**
    - `shared/save-actions.njk` (animals) gains an optional parameter: the form action and encoding the save buttons post with.
    - When it is given, every save button carries that form action and multipart encoding, and its own submitted choice: the primary and Save and return to overview as today, the amend Save and continue the primary's, and the amend Save and return the choice `amendFormActions` returns (decision 9).
    - Only the documents page passes it.
    - The plants twin of the macro is not changed: plants has no page that sends a file, so the option would be unreachable there.

    Rejected: hand-writing the documents page's button group, which would be a second mechanism beside the macro.
11. **The browser's oversize check runs for any submit that sends the file.** In `client/oversize-validation/submit.js`, the check keys on whether the submitter posts multipart, not on whether it has any form action. Two reasons:
    - Save and continue and Save and return now send the file.
    - The amend buttons carry a page-bound form action when the add form is closed, and that does not send the file.
12. **The trader's own input errors stop being logged** in the functions this change edits. This follows the house rule and the programme invariant:
    - the documents page's "Continue refused: the document has not been added" line (`controller.js:352-355`);
    - the claim's `returned-upload-breaks-the-page-rules` refusal (`claim-upload.js:100-104`);
    - the commodity search page's blank-selection refusal (`search.controller.js:82-84`).

    These logs stay: capacity, scans not cleared, a document taken on but not listed, and service failures. They are state or service outcomes, not input errors.
13. **Plants origin tidy-up inside the touched function.**
    - With the option gone, the blank-country early return in `errorsFor` (`origin/controller.js:108-110`) is unreachable, so it is removed.
    - The doc comment on the internal `errorsFor` (`:85-96`) breaks the doc-comment rule, so it is deleted.

    In the same way, the plants commodity-type blank-type branch in `keepLinesAllowedBy` (`commodity-type/controller.js:71-73`) is unreachable and is removed.
14. **No new copy.** Every message shown already exists in English and Welsh. The deleted `notYetAdded` key goes from both decks in the same change.
15. **Every comment breach in the files this change edits is fixed in this change** (the bounded tidy-up). Where a comment explains a name, the name changes and the comment goes. Where a comment carries rationale, the rationale goes to the repo's docs, unless the docs already state it, and the comment goes. The list is in section 2, file by file, and the doc homes in section 12.
