## 0. Decisions

1. **Claims checked against the tree — all hold.**
   - "What are you importing?" saves through `commit-selection.js:32-36`: hub exit, else the review's change context (Commodity details with `?change=1`), else `kit.nextTarget` (the run's next step, `importReason`, or the task row's next page).
   - `consignment-details.controller.js:72-75` and `animal-identification.controller.js:63-66` build their links with `kit.withChangeContext` only, so the commodity question never knows who opened it.
   - The addresses page's return marker is the `return` query parameter (`addresses/controller.js:29` CPH link; `cph-number/controller.js:33-36`; `party-edit.controller.js:29-39`, which accepts it only from a closed list).
   - The FIT `adds another commodity while preserving an existing quantity` (`consignment-details.fit.spec.js:337-357`) asserts the trader lands on Overview. That is the defect, pinned. It changes in this increment.
2. **The marker reuses the existing `return` query parameter, read from a closed list.** The value names the opener page as party-edit's does: its slug, accepted only for Commodity details or Identification details. Rejected: a new parameter name, or a session flag. Both would be a second mechanism beside `return=`, and a session flag would not survive without JavaScript as plainly as a URL does.
3. **One new module in the commodities feature owns the detour rule.** It holds the closed list of openers, builds the commodity-question href for an opener (carrying the change context when the opener has it), and reads a request's marker back into the opener's path (with change context). Rejected:
   - a kit (L2) helper: kit is set-agnostic, and moving cph and party-edit onto a shared reader would widen the footprint for clean-up alone (follow-up);
   - putting it in `commit-selection.js`: the two opener controllers would then import from the search action.
4. **Precedence of a save on "What are you importing?"**: hub exit (Save and return to overview) first, then a recognised return marker, then today's change branch (Commodity details with change context), then `kit.nextTarget`. So:
   - the opening run with no marker goes on to the reason for import as now (AC3);
   - a Change straight from the review carries no marker and still goes to Commodity details with change context (AC4);
   - Save and return to overview still exits to the overview.
5. **A marker plus change context returns to the opener with change context.** Example: review → Commodity details?change=1 → Add another commodity → save → Commodity details?change=1, whose own save then goes to the review. Rejected: dropping change context on return, which would strand a trader who came from the review.
6. **Amend follows the same rule.** `amendFormActions` keeps the page's own query on both amend buttons, so the marker survives either. "Save and return" while amending a detour goes back to the opener with change context, not straight to the review. Today it goes to Commodity details with change context, not the review, so this changes nothing a trader relies on.
7. **Identification's "Add another commodity" link carries the marker too.** It shares the one `addHref` with the summary rows' Change links (`animal-identification.controller.js:63-66`, `:89-91`). The row names Change. Giving one link and not the other would mean two hrefs for one destination. Both return to Identification details.
8. **The commodity question's Back link opens the opener while the marker is present.** Today it opens origin in the run and the overview otherwise. That mirrors `cph-number/controller.js:48`, where a detour's Back opens the page that opened it. Rejected: leaving Back on origin, which would take a trader on a detour from Commodity details out to the first step of the run.
9. **The search and Clear all re-renders keep the marker without any template change.** `search.njk:20` posts to the page's own URL (`<form method="post">` with no action), so the query string travels with every post, without JavaScript.
10. **Plants needs no change.** `trade-imports-plants-frontend`'s commodity loop already returns:
    - the list's Add another and Change open the details page (`list.controller.js:43`, `:64`);
    - details' save returns to the list (`details.controller.js:195-197`), carrying change context (`links.js:15-23`);
    - no later page links back into the commodity question.
    - `details.controller.test.js` "Should commit the cleaned values and return to the list" and "Should carry a change context through every redirect" already pin this.
    - plantsfrontend stays in the repo list with no commit.
11. **"Counts already saved" means saved before Add another was followed.** `reconcileEntriesAt` keyed by `lineKey` keeps a kept line's stored entry, which `search.controller.test.js:300-331` already proves. Counts typed into Commodity details but not saved are lost on following a link today. They stay out of scope.
12. **Spec: one new requirement on commodity selection** says where its save goes. The Commodity details and Identification details requirements that open the detour gain the return. Rejected: a journey-flow requirement. The AC names these three capabilities, and the detour is not a run step.
13. **The reader tells three outcomes apart, and only the save logs.** The new module's reader returns one of:
    - nothing, when the request carries no `return` marker;
    - the honoured opener path (with change context), when the marker is on the closed list;
    - a refusal carrying the raw value received, when a marker is present but not on the list.
    - `commit-selection.js` is the one place that logs, in the save's target step, once per save. It logs the honoured return and the refused marker. `search.controller.js` `render` (the Back link) uses only the honoured outcome and logs nothing, so no GET or search re-render logs.
    - Rejected: logging inside the reader. It runs on every render and every save, so it would log the same decision more than once (`pino-logging.md` §4a, "Log it at the branch that decides, once").
    - Rejected: one "nothing" for both cases. The save could not then log the value it refused.
14. **Removing a commodity on the detour from Identification details returns there.** The commodity question is a list of ticked species. Unticking one and saving goes through the same `selectionTarget` return step, so no extra code. `reconcileEntriesAt` drops the unticked line. Identification details' summary is built from every line (`animal-identification.controller.js:60-62`), so it lists only what is left.
15. **When the removal leaves nothing to identify**, the save still returns to Identification details. That page's existing guard (`noIdentifiersTarget`, `animal-identification.controller.js:120-129`) then sends the trader on to Identification's next target and logs the skip once, as it does today. This is the spec's "A consignment with nothing to identify never shows the page" (REQ-IDENT-019). Unit test `animal-identification.controller.test.js:899` already pins the guard. No new branch. Removing every commodity is refused on the commodity question itself (`search.controller.js:81-88`), so a save never leaves the notification empty. Rejected: sending the trader somewhere else from `selectionTarget` when nothing needs identifying. That would be a second owner of Identification's skip rule.
16. **Unit tests sit with the test that already pins the same href.** `change-context.test.js` already pins Commodity details' add link under change context (:100-107) and the unmarked review Change save (:85-97). The first changes to the marker-plus-change href. The second is the pin for the unmarked review Change and is not repeated in `search.controller.test.js`. `consignment-details.controller.test.js` gains only the case with no change context, which no test covers.

## 13. Operability

Both logs live in `commit-selection.js`, in the save's target step (Decision 13). They fire once per save, never on a GET or a search re-render.
- **The save honours a detour marker and redirects to the opener.** That branch changes the redirect, so log once at info. Support must be able to find the journey id and which opener page it returned to.
- **A marker that is not on the closed list falls back to the unmarked target.** A refused return address: log once at info (`pino-logging.md` §4a) with the journey id and the value received, which the reader's refusal outcome carries.
- The reader logs nothing. The Back link render and the opener links change no outcome, so they get no log.
- The removal that leaves nothing to identify reuses Identification's existing skip log (`animal-identification.controller.js:124-127`). No new line.
