## 0. Decisions

1. **The house style is applied in `kit.dateField`, not by un-scoping the stylesheet.** `kit.dateField` always gives the form group the house date-picker class, with any page classes after it. That is what the row's notes ask for. It keeps the stylesheet's extra specificity over the MoJ rules, so they do not rely on source order. Rejected: un-scoping the selectors in `_date-picker.scss` to hit every `.moj-datepicker__*`. That would rely on stylesheet order to beat MoJ's equal-specificity `:focus` rules, and would leave `formGroupClasses` with no house default to sit beside.
2. **`formGroupClasses` stays as an option.** After this change no page passes it: animals arrival details drops its opt-in. It stays because the next import reason row (inc-207, which changes the exit date's label weight and spacing) passes a GOV.UK margin override on the exit date's form group. Rejected: deleting the option now and re-adding it in inc-207.
3. **`labelClasses` is ported from the stale arrival-and-transit branch (animals bb6fb2e0, plants b2f3bdc).** Port only the option and its unit test, in both kits. It defaults to the GOV.UK small label. inc-207 is the row that passes it. The row explicitly asks for it ("lets a page choose its date label's weight"). Rejected: leaving it to inc-207.
4. **The open calendar's look is MoJ's own, plus two mouse-focus corrections that a user can reach.** Read against the live MoJ stylesheet (`node_modules/@ministryofjustice/frontend/moj/components/date-picker/_date-picker.scss`) and script (`date-picker.mjs`):
   - MoJ already draws, with no line from this row: the 2px outline in the GOV.UK text colour round the dialog (the "black border"); the Select and Close buttons as GOV.UK primary (green) and secondary (grey) buttons; and the yellow focus state for keyboard focus.
   - Opening the calendar with a mouse runs `setCurrentDate`, which moves focus onto the day it opens on and gives that day MoJ's `--selected` class (date-picker.mjs:435-440). MoJ's day `:focus` rule (`_date-picker.scss:125-135`) then paints it yellow, and `tbody:focus-within` (`:52-54`) draws a yellow outline round the calendar body. The prototype shows neither under mouse focus.
   - So this row adds exactly two corrections, scoped under the house class and written with govuk-frontend colour functions:
     - **day:** the focused day the calendar opens on, under focus that is not `:focus-visible`, keeps its resting look: GOV.UK link blue with white text;
     - **calendar body:** the yellow outline shows only while a day has `:focus-visible`.
   - **Not built, because no user state reaches them:**
     - a plain day (no `--selected`) or a `--current`-only day under mouse focus. The script focuses only the day it gives `--selected`; clicking any other day selects it and closes the dialog (date-picker.mjs:469-480); month buttons clicked by mouse keep focus on themselves (`focus = false`, :65-67, :595-611).
     - the dialog's Select and Close buttons under mouse focus. Clicking either closes the dialog (:71-84), and a pressed or hovered GOV.UK button never gets its focus style (`govuk-frontend/.../button/_mixin.scss:94`, `&:focus:not(:active):not(:hover)`).
   Rejected: the previous plan's third correction (dialog buttons) and the plain-day variant, and copying the prototype's mixin wholesale (its toggle rules duplicate `%blue-icon-button`; its `!important` overrides and 320px width contradict the house in-flow rule).
5. **The calendar keeps the house 360px maximum width.** The prototype uses 320px. No criterion states a width. Rejected: changing to 320px with no criterion asking for it.
6. **The toggle keeps the house `%blue-icon-button` look, which turns yellow on any `:focus`.** The prototype uses `:focus-visible` on the toggle, so after a mouse user picks a date (MoJ returns focus to the toggle, date-picker.mjs:527-531) the house toggle shows yellow where the prototype's stays blue. Kept because criterion 1 asks for the yellow focus state "when focused", MoJ's own toggle does the same, and the placeholder is shared with the type-ahead button. Rejected: editing the shared placeholder.
7. **No copy changes. The note's "example '27/3/2026'" is already met or is out of scope.** The exit date hint already reads 'For example, 27/3/2026', and so do the plants arrival hints. Date of issue reads 'For example, 12/12/2025'. Criterion 5 says each page keeps its existing hint, and criteria outrank notes. Rejected: rewording the date of issue hint.
8. **The notes' "update the header comments of `_date-picker.scss`" does not apply.** Neither frontend's `_date-picker.scss` has a header comment at the pinned HEADs. The new rules carry no comments either: their reason goes to the docs home (Decision 10).
9. **Plants gets the house style for the first time.** Its arrival details page never opted in, so today its picker is MoJ's near-black overlay. Through `kit.dateField` it now picks up the in-page calendar, the blue toggle and the mouse-focus corrections with no page edit.
10. **Rationale has one home per frontend: the existing "Date picker" sections** in the workspace's `docs/repos/trade-imports-animals-frontend.md:55-57` and `docs/repos/trade-imports-plants-frontend.md:83-85`. Each is extended in place. It must state: every field built by `kit.dateField()` gets the house picker; the calendar sits in the page flow (already there, still true); the toggle is the blue icon button; why the open calendar keeps resting colours under mouse focus and shows yellow only under keyboard focus. Nothing goes into the frontends' `validation.md`. Rejected: writing the same rationale into each frontend's `validation.md` as well (two homes for one reason), and moving the sections into the frontend repos (they already live in the workspace's per-repo pages, and moving them widens the change for no gain).
11. **The integration proof is one tests-repo feature spec per domain**, through a new shared date-picker page component modelled on `TypeAhead`. Rejected: spreading single assertions across the existing page specs. Four pages share one behaviour, and the behaviour is the subject.
12. **Colour checks are web-first.** Every new colour check, FIT and E2E alike, is a Playwright `toHaveCSS` assertion on a locator, so it retries. One-off geometry reads (the calendar's bottom edge, the next label's top) happen only after a web-first wait for the dialog to be visible. Rejected: reading a value with `computedStyle` and comparing it afterwards (`docs/best-practices/playwright/BEST_PRACTICES.md:138`, "Use web-first assertions").
13. **Bounded tidy-up covers every comment and title breach in the files this row edits** (section 2 lists each). Where a deleted comment carries a reason about the date picker, that reason goes to the Decision 10 home. Every other deleted comment is deleted outright: its test's assertions or the code's names already say what it says.
