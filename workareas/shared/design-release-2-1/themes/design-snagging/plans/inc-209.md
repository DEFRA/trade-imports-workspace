20. **The list rule has one owner, in `validate.js`, and the Continue and GET log lines take their reason from it.** Today `listErrors` (`validate.js:26-41`) decides whether a list is refused and why: a code the page does not offer, told apart as not on the list (on submit) or no longer available (on stored), or more countries than the cap.     - **The offered / not-offered split** of a code list gets one owner beside `offeredCodes` in `validate.js`, reading `offeredCodes`. `listErrors`'s check (28) and the controller's render filter (53) both use it, and neither keeps its own inline filter.
    - **The list-refusal decision** becomes one exported function in `validate.js`, using the split. Given a list and whether it is the stored reading (a named option, as `pageValidation` passes `stored` in its context, never a positional flag), it yields which refusal applies by a stable reason name, plus the codes it turned on (the not-offered codes, or the list's length for the cap), or nothing when the list is fine. `listErrors` maps that result to its message keyed by the field, so the reason and the message keep one owner.
    - **`listErrors` loses its positional boolean.** Today it is `listErrors(selected, stored)` (`validate.js:26`), called as `listErrors(values.transitedCountries, stored)` from `validation`'s `checks` (54). It takes the stored reading as a named option instead: the `checks` context object, or an options object carrying `stored`. The call at 54 passes it that way. House rule, Names: no positional boolean flags.
    - **The reason names** are one frozen set exported from `validate.js`, as `DECLARATION_REFUSAL` is (`declaration/controller.js:27`). `addErrors` uses the same names for the concepts both share (a code not on the list, the cap) and adds its own for nothing chosen and already added. One concept, one name.
    - **The controller's Continue and GET refusal branches** ask that decision function for the reason and codes when the validation has refused, and log them. They work nothing out themselves.

    Rejected: a split helper in the controller, which made two owners of one rule (`listErrors` decided, the controller worked the answer out again to log it). Rejected: widening `pageValidation` (`lib/validate/page-validation.js`) to return each check's reason, which changes a mechanism every page uses. Rejected: logging inside the `checks` callback, because `onStored` also runs for the task list and review pages, where a log line per render would be noise and has no request to hand. The cost is that the deciding function runs a second time, in the refusal branch only, against the same offered list; the rule itself still lives in one place.
