## 0. Decisions

1. **One mechanism for the run's Back link, in both twins.** Back during the opening run is a property of the run, so it goes through the seam that already carries the run's forward step. The journey-flow seam (`flow/journey-flow.js`) gets a second run policy beside `nextRunTarget`: the run's previous step for a page. `shared/kit.js` gets one helper beside `runTarget` that answers that previous step while the journey is in its opening run, and nothing otherwise. Each run-step page sets its `backLink` to that helper's answer, falling back to the page's existing Back (Overview, or the page's own saved-state rule).
   Rejected: hard-coding a previous-page path in each controller. That spreads the run order over five animals controllers and eight plants controllers, and a skipped step would be skipped in some and not others. Also rejected: a `from=hub` query marker (ruled out by Sam on 9 October, ruling p1-198). The run flag already in the session (`flow/run-state.js` `inOpeningRun`) is the only state.
   The row's salvage note names two seams, `runBackLink` and `runBackTarget`. They are the same thing: build one.
2. **Each run step declares where its Back link looks, nearest first.** A `RUN_STEPS` entry may name the earlier steps its Back link may open, in order. The previous-step policy returns the first of them whose existing step target passes (the same `flowPageTarget` gate the forward walk uses), so a skipped step is skipped going back too. A step that names none has no run Back link and keeps Overview.
   Rejected: a generic "nearest earlier step". In animals the spec keeps identification details, arrival details, the transporter, documents, roles and addresses and the contact address on Overview, and sends Commodity details back to "What are you importing?", past the main import reason between them. A generic walk gets both wrong.
3. **Animals: what each step names.**
   - "What are you importing?" names origin of the import.
   - The main import reason names "What are you importing?".
   - Commodity details names "What are you importing?".
   - Additional details names identification details, then Commodity details.
   - Transit countries names arrival details.
   - Origin (the first step) and the steps the spec keeps on Overview name none.
4. **Animals: the identification candidate applies only when a chosen species needs identifiers.** The identification step's own gate passes for every consignment: the page redirects itself onwards when nothing needs identifying. A Back link to it would bounce the trader forward again. So the additional details page's identification candidate also has to pass "any selected species needs identifiers". That rule already has one owner: `identifiesAnAnimal` in `flow/task-rows.js:22`, which decides whether the identification task row applies. Export it and use it. Do not write a second one.
   This means the previous-step policy needs the notification's answers as well as its scope. The seam contract carries the step id, the scope and answers from the request's read view, and the journey id. It is the same in both twins; plants' policy reads scope only.
   Rejected: asking the identification controller's own `identifiedLines`. It reads the evaluation inside a feature controller, and a flow module must not import a controller.
5. **Plants: every run step after the first gets a run Back link.** Criterion 9 says "a page reached in the opening run has a Back link to the previous page in plants' own step order". So this covers the commodity list, origin, arrival status, arrival details, place of destination, consignor, identification numbers and the contact address. The row's notes name only four (arrival status, arrival details, identification numbers, the commodity list). The criterion is the requirement, and the other four plants specs also say "Back opens Overview" today, so they change too.
   - The commodity list names commodity type.
   - Origin names the commodity list.
   - Arrival status names origin.
   - Arrival details names arrival status, then origin. Potatoes skip arrival status.
   - Place of destination names arrival details.
   - The consignor names place of destination.
   - Identification numbers names the consignor, then place of destination. Potatoes skip the consignor.
   - The contact address names identification numbers.
   - Commodity type (the first step) and check your answers name none.
   - The commodity details sub-page is not a run step and keeps its own rule (REQ-PLANTS-COMMODITY-DETAILS-009).
6. **Origin and commodity type keep their own Back outside the run.** Animals origin is the first run step and is unchanged. Plants origin, outside the run, keeps its saved-state rule (dashboard, or Overview once answered). Criterion 9's "opened from the overview, the origin page included, has a Back link to the overview" is that rule.
7. **Back from the view is chosen by notification status, in one function per twin.** The view (`check-answers/controller.js`) is shared by every state. A SUBMITTED notification gets the set's notification list (`dashboardPath()`). Every other state gets Overview.
   - The view shown after a cancelled amendment is the restored SUBMITTED view (`cancel-amend/controller.js` redirects to `notification-view?cancelled=1`), so it goes to the list with no extra branch.
   - An amendment in progress keeps Overview.
   - A draft's review keeps Overview. The live-animals spec's SCN-CYA-003-A (a draft's review goes to the list) is already ahead of the code. It belongs to the templates theme's draft-review row and stays untouched here.
   - A deleted notification cannot be viewed.
8. **Claims checked against the tree.**
   - Animals: Back on the five changed pages goes to Overview today (`search.controller.js:36`, `consignment-details.controller.js:50`, `import-reason/controller.js:57`, `additional-details/controller.js:39`, `transit-countries.controller.js:60`). True.
   - Animals view: Back goes to Overview (`check-answers/controller.js:121`). True. Plants view: same (`check-answers/controller.js:95`). True.
   - The row's note "update both controller tests' expected backLink" is half wrong. Animals `check-answers.test.js` asserts no `backLink` today, so it gains new assertions. Plants `check-answers/controller.test.js:92` asserts a draft's Back is Overview, which stays true.
   - The spec already holds the submitted-view scenario in both prefixes (SCN-CYA-003-B, SCN-PLANTS-CYA-010-B). The spec sync adds coverage links for them, not new scenarios.
   - "Main's run already does this" (criterion 8) holds. `opening-run.test.js` proves the reason going to Commodity details and Additional details going to arrival details in the run, and the reason going to Overview outside it. Additional details going to Overview outside the run has no unit proof yet, so one is added.
9. **No log lines.** A Back link is an href on a rendered page. Choosing it refuses, redirects or retries nothing (see section 13).
10. **Fit tests that start the run, stay in it and assert Back → Overview are now wrong.** Each is rewritten for the case it actually sets up. If the set-up stays in the run, the test asserts the previous step. Where a page's "opened from Overview" scenario needs its own proof, a test opens the page from its Overview task and asserts Overview.
    - Animals: the import reason fit's Back test (`import-reason.fit.spec.js:233`) uses `startNotificationAtImportReason`, which never shows Overview. It moves to an Overview-opened set-up.
    - Plants: most feature fits walk the run without ever showing Overview, so their Back assertions move to the previous step. Each page keeps one Overview-opened case.
11. **E2E homes.**
    - Animals view: `tests/animals/e2e/features/promoted-lifecycle.spec.ts`, which already submits, views and amends. The `@duplicated-in-frontend` view-states file is not used: this proof is through the real stack.
    - Plants view: `tests/plants/e2e/features/review.spec.ts`.
    - Run Back: `tests/animals/e2e/journeys/opening-run.spec.ts` and `tests/plants/e2e/features/origin.spec.ts`. Origin is the plants run step whose Back opens the commodity list.
12. **Seam unit test is a forwarding test, not an "unconfigured" test.** Both twins' vitest set-up configures the journey flow for the set before any test file runs (animals `test/setup-obligation-set.js:40`, plants through `installFixture`), so `journey-flow.test.js` cannot reach the `UNCONFIGURED` branch for its set id. The new accessor is proved the way plants already proves `journeyNextRunTarget` (`flow/journey-flow.test.js:11-21`): configure a policy, read through the accessor, assert the exact answer. The `UNCONFIGURED` entry is still added beside `nextRunTarget` so an un-booted read fails the same way.
    Rejected: a test against an unconfigured set id. It would test `setKeyed`, not the new accessor.
13. **opening-run.test.js moves onto the shared engine test support.** Its local `captureH` (`:54-73`) copies `stubH` (`engine/test-support.js:98`), `buildRequest` (`:75-85`) copies `journeyRequest` (`engine/test-support.js:133`), and `drive` (`:87-93`) copies `driveHandler` (`engine/test-support.js:209`). The row edits this file, so all three go:
    - a one-handler case uses `driveHandler` with its new opening-run option;
    - a sequence of handlers (create, then GET, then POST on the same journey) builds each request with `journeyRequest` (the opening-run record passed through its `state` override) and each toolkit with `stubH`;
    - redirects are read from the handler's returned response, and cookies from `stubH`'s cookie record, not from a local `captured` object.
    Where a handler chains a call on the redirect result that `stubH`'s redirect does not offer, `stubH` gains it in `engine/test-support.js`. No local toolkit stays. So nothing goes in section 14.
    The `active`/`complete` record builders (`:95` and the `complete` beside it) are one-line values for `journeyRequest`'s `state` override. They stay local: they are data, not set-up copied from a shared helper.
14. **Plants picker suite gets an explicit in-run expectation per picker.** `describePageServed` (`address-book-picker/controller-test-support.js:83`) receives only `{ pickerName, get, seed }` from `describeAddressBookPickerController(picker)` (`:556`). It has no previous page to assert. The `picker` object gains one field: the in-run previous step for that picker, as the page it expects plus the seed whose scope opens that step. The three call sites supply it (section 4).
    Rejected: computing the expectation from the run policy inside the suite. That would assert the policy against itself.
15. **Register functions and set-up blocks touched for the seam lose their breaching comments.** Each gateway's `register`, each second-set fixture's `register`, the animals vitest set-up block and plants `installFixture` are touched to pass the new key. Their comments describe other modules or tests, carry rationale, or count. They are deleted (section 2), and any rationale the repo docs do not already hold moves to the doc named in section 12.
