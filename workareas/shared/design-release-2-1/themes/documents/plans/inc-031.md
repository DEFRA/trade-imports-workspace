## 0. Decisions

- **The behaviour is already in the code; this row is test-and-spec work only.** Checked against the live tree: the documents task row is unconditional (`flow/task-rows.js:67`) and the hub hides only a conditional row at Not applicable (`features/hub/controller.js:56`), so the overview links the row from the moment a notification exists; the journey's one section gate is the review's (`flow/flow.js:66`) and the documents section has none; the only pre-handler redirect in the set is the entry guard (`routes-live-animals.js:91-99`), which admits any journey page whose opening run has begun in this session or whose notification carries a committed user answer (`flow/entry-guard.js:59-71`); and the page's own GET reads nothing about commodities (`features/documents/controller.js:75-83`). The set's own doc already states the rule: no row on the hub is ever shut (`sets/live-animals/docs/journey-flow-and-gates.md:50-54`). Rejected: planning a production change to "open" the page — there is nothing to open, and anything added would be unreachable.
- **The claim the increment makes about the real service is wrong, and I plan against reality.** The detail says "The real overview only unlocks the task once origin, commodities and commodity details are complete." The code does not do that. What is true is that both repos' test helpers answer origin, the commodity and the commodity details before opening the page (`fit/live-animals-journey.js:566-579`, `flows/animals/journey.ts:207-209`), so no test has ever opened it from a weaker state. The gap is proof, not behaviour.
- **"The commodity answered" means the what-are-you-importing answer alone.** The design source's helper chooses the species and saves, with no commodity-details step (`prototype-specs/e2e/support/journey.js:138-143`); the real set splits that one prototype page into a selection page and a details page. So the second criterion's state is origin plus the species selection. Rejected: reading it as origin plus commodity details, which proves less than the first criterion already does.
- **Each test's red probe is the line its own assertion depends on, and one of the three has none.** This matters because the entry guard short-circuits: `entryGuardTarget` returns at `flow/entry-guard.js:64-66` whenever the opening run has begun for that journey in this session, and the dashboard's create POST is the only caller of `beginOpeningRun` (`features/dashboard/controller.js:123`; `sets/live-animals/docs/journey-flow-and-gates.md:158-161`). Every test below reaches the page in the same browser session that created the notification, so the committed-answer branch at `:67-69` and `hasCommittedNotificationAnswers` at `:46-49` never run, and inverting either leaves all three green.
  - The two tests that follow Overview's documents row depend on that row existing and carrying a link: dropping it from `flow/task-rows.js:67` leaves the overview with no such link and turns them red. That is their probe.
  - The test that opens the page's own address has no such line. The entry guard is satisfied before it is consulted, and the page's GET makes no prerequisite check, so the behaviour it proves is an absence and no single production line can be inverted to disprove it. The plan records that and its coverage link is `partial`, with a note saying why. Rejected: inverting the page's title copy or its GET handler as a stand-in — that turns every documents test red and witnesses nothing about the entry condition.
  - Rejected: reaching the page in a browser session that did not create the notification (clearing the browser's cookies and signing in again), which would put `flow/entry-guard.js:46-49` in play and give a real probe. That is `live-animals/journey-flow` SCN-FLOW-008-B — a link to a page inside a journey that already holds an answer the user entered — whose owner is REQ-FLOW-008, and whose FIT/E2E hole is already recorded in `openspec/coverage/live-animals/journey-flow/coverage.json:395`. Instantiating it under `upload-documents` would give one rule two owners in the Behaviour Spec. It goes to section 7 as a follow-up for that capability.
- **The spec requirement states this page's own fact and cross-references the flow capability instead of restating its rules.** What is this page's own is that its prerequisite set is empty: it is offered and opens with nothing beyond the origin of the import answered. Whether a page is offered at all is `live-animals/journey-flow` REQ-FLOW-005's; whether a journey opened out of context opens at all is REQ-FLOW-008's and REQ-FLOW-009's; that every Overview row is linked and none is blocked is `live-animals/journey-pages/overview` REQ-OVERVIEW-002's. The new requirement's Purpose cross-references all three and restates none. Rejected: a new journey-flow requirement, which would put one page's fact in the cross-cutting capability; and a scenario phrased as a deep link, which would restate SCN-FLOW-008-B.
- **`answerWhatYouAreImporting` stays the one owner of answering what the trader is importing** (`fit/live-animals-journey.js:655-658`). The step the new test needs is that plus following Overview's row to reach it and ending back on Overview. Three places would otherwise hold those extra lines: inline in `unlockSections` (`:566-579`), inline in `completeAnswerSections` (`:859-861`) and in the new spec. So the overview-entry step is extracted once in the shared FIT helper, composes `answerWhatYouAreImporting`, and both existing callers go through it. Rejected: a sibling step that repeats the species selection and save beside `answerWhatYouAreImporting` — a second mechanism for one concept; and a local copy in the new spec file — a third copy of the same three lines.
- **The species each caller answers does not change.** `answerWhatYouAreImporting` gains a species parameter defaulting to the species it answers today, and the overview-entry step passes one through with the same default, so `completeAnswerSections` and `carryOpeningRunToImportReason` (`:525`) behave exactly as now while `unlockSections` keeps passing its own.
- **The required checks for this change are the ones the set's testing doc names for a shared FIT helper.** `sets/live-animals/docs/testing.md:33-43` requires the set-focused Vitest run, the whole unit suite, the `features` Playwright project and lint for a journey change, and the `journeys` project as well when the change touches shared FIT helpers. This change edits `fit/live-animals-journey.js`, through which `openDocuments`, `openArrival` and `openTransit` reach 63 call sites across the set's specs, so all five run (section 6). The frontend's `.husky/pre-push` runs only format, lint and Vitest (`package.json:28-29, 40`), so Playwright has to be named explicitly. Rejected: running only the new spec file, which would leave a shared-helper regression invisible until CI.
- **The integration proof is written here and run by the branch pull request's CI, not locally.** The row's `gatePhases` is empty, so the loop runs no gate rung, and the row's own note records that the local docker-compose e2e rung on this machine timed out nearly every spec and died without writing a result while the lease holds a 20-container stack on 12 CPUs. A timed-out run is not a pass (workspace `CLAUDE.md` rule 6), so no local e2e check is named: naming one that cannot resolve would stop the increment with nothing broken. Both repos' pull requests run `tests/animals/` against the branch-tagged tests image and the branch service images, which is where this spec is proved. Rejected: naming the single-spec docker-compose run as a check, which the earlier plan did — the cause of the earlier failure is the machine under the stack, not the number of specs selected.
- **The page keeps its address, and nothing names that address as a literal.** The 9 October ruling (claim 20) dropped the move, and the row requires the page be asserted by its heading. The one navigation that needs an address goes through the existing helper that opens the overview and then a page by its slug (`fit/live-animals-journey.js:438-441`), with the slug read from the feature's own page module.
- **`unlockSections` is a misleading name in both repos, and renaming it is a follow-up.** It unlocks nothing; it answers pages. Renaming touches four frontend spec files and six tests-repo call sites only to clean them, which bounded tidy-up forbids here. Section 7.
