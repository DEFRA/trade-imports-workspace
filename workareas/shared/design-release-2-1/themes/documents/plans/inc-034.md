## 0. Decisions

**D1 — Only the Back link is missing. Everything else the row asks for is already true, and I checked each claim.**

- Opened from the review page, Save and continue already returns to the review:
  `shared/kit.js:217-223` sends a save carrying change context to the review, and
  `features/change-context.test.js:202-210` proves it for this page today.
- Opened from the overview outside the opening run, Save and continue already returns to the
  overview, and inside the opening run it already goes on to the addresses page:
  `flow/run.js:62-68` orders the documents step before the addresses step, and
  `shared/kit.js:262-268` falls back to the run target then the task row.
- The return context already survives Save and add another and Remove:
  `features/documents/contracts/upload-session.js:22-23` rebuilds the page's own address through the
  shared change-context helper, and `features/change-context.test.js:140-171` proves both round trips.
- It also survives the upload-service round trip the add now takes: the session's return address is
  built by the same helper (`handlers/add-form-session.js:15`), and the save choice made on the
  submitted form is read back by `shared/kit.js:165-171`.
- The Back link does not follow any of this: `features/documents/view-model/render.js:106` hard-codes
  the overview.

So the whole build is the Back link, in both the review case and the amendment case.

**D2 — Criterion 2's "Save and continue" half is wrong and is not built. Build its Back-link half only.**

While a notification is being amended, the page already ends with a primary "Save and return" that
goes to the review and a secondary "Save and continue" that goes on to the next page. That is a
decided, merged, specified behaviour: `openspec/specs/live-animals/journey-flow/spec.md`
REQ-FLOW-013 and SCN-FLOW-013-C ("Save and continue while amending goes on, not back to the
review"), built by journey-foundation inc-004 from the prototype's own rendered amend pages
(`prototype:dr2-1-specs` p5-114, p5-116, p5-119; `trace:prototype-dr2-1` p14-071, p14-072), and
proved today by `tests/animals/e2e/features/amend-endings.spec.ts:53-67`. Making Save and continue
return to the review would make the two amend buttons do the same thing.

The behaviour criterion 2 is reaching for — while amending, a save returns the trader to the review
however the page was opened — is already delivered by that primary button, which carries its choice
in the posted form rather than the address (`shared/amend-form-actions.js:4-7`,
`shared/kit.js:165-171`), so it survives the upload-service round trip too
(`features/amend-endings.test.js:78-89`).

Rejected: building criterion 2 as written. Recorded as a defect in this row.

**D3 — The Back-link rule lives in the shared run Back-link helper, and the documents page opts in.
It is not made unconditional.**

The helper at `shared/kit.js:236-249` is called by five other pages
(`import-reason/controller.js:57`, `additional-details/controller.js:39`,
`commodities/consignment-details/consignment-details.controller.js:67`,
`commodities/search/search.controller.js:41`,
`transport/transit-countries/transit-countries.controller.js:61`). Making the review rule
unconditional would change all five, which this row's criteria do not ask for, and would contradict
two standing decisions: REQ-FLOW-013 ("A page MUST keep its usual Back link and never link back to
the review"), proved by `tests/animals/e2e/features/amend-endings.spec.ts:43`, and the deferred
requirement req-1616, which says a page opened from a review Change link goes back to the previous
journey page rather than to the review.

The design source makes the review rule page-specific too: the prototype computes it inside the
documents handler itself (`prototype:dr2-1-source` p10-010, `app/routes.js:11089, 11093` —
`const fromReview = isFromReview(req) || isAmendingNotification(sessionData)` then
`backLink: fromReview ? '/review-notification' : '/notification-hub'`), not in its shared layout.

So the helper gains a named option by which a page declares that it returns to the review, the rule
itself stays in the helper, and the documents view model is its only caller. Rejected: a second
Back-target rule written inside the documents feature (the row's own note forbids it, and it would
split one rule across two owners).

**D4 — The documents view model becomes async, rather than the Back link being computed in the page
loader.**

The helper must be awaited (it reads the opening-run flag through the session port,
`flow/run-state.js:21`). The exemplar that already does this is
`additional-details/controller.js:30-43`: an async render that awaits the helper inside the shared
chrome call. The seven call sites in the documents controller gain an `await`. Rejected: computing
the Back link in `handlers/load-page.js` — that loader's name predicts loaded page state, not a view
link, and a view concern would move out of the view model.

**D5 — The page's three states are settled as: review while amending, review under change context,
overview otherwise.** The amendment case does not depend on the address (criterion 2's "however the
page was opened"), because it reads the notification's status. The change case reads the existing
change context; no new marker in the address and no hidden form field is added, as the row requires.
Where both hold, the answer is the same, so order between them is not observable; the review case is
answered before the opening-run lookup so it also holds for a change made during the opening run.

**D6 — This is a general frontend change, not one of the four recipes.** It adds no field, page,
section or collection and changes no obligation and no flow data (page order, task rows, entry
guards all stand). Routed by `frontend-change` Step 1: the layers touched are the shared platform
(`app/shared/`) and one feature's view model, so the guides read are
`src/server/app/docs/flow-and-gates.md`, `src/server/app/docs/architecture.md` and
`sets/live-animals/docs/journey-flow-and-gates.md`. Set: `sets/live-animals`; spec namespace
`live-animals/`.

**D7 — Plants takes nothing.** The programme's mirror invariant applies only where plants has the
same page; it has no documents feature
(`repos/trade-imports-plants-frontend/src/server/app/sets/high-risk-plants/journeys/linear/features/`),
and plants is not one of this row's repos.

**D8 — The four comments in the documents view model go with this change, under bounded tidy-up.**

This change edits `features/documents/view-model/render.js` for the row's own behaviour, so the whole
file must meet the house rules. It carries four breaches:

- Doc comments on three non-exported helpers — lines 25-35, 53-60 and 77. `.claude/rules/code-quality.md:29`
  allows a doc comment only on the contract of an exported public API, and
  `docs/best-practices/doc-comments/jsdoc.md:13-14` names a feature's view model and its internal
  helpers as places not to write one. All three go. Nothing replaces them: each helper's name already
  says what it answers with, and where a name does not, renaming is the fix rather than a comment.
- The rationale comment inside `render` at lines 112-113, which explains why one key is written after
  the spread of the caller's extras. `.claude/rules/code-quality.md` puts rationale in the repo's
  `docs/` or the behaviour spec, never in code. It goes, and the ordering it explains is kept true by
  ownership rather than by prose: the helper that already owns the add form's whole state — whether it
  is open and why it is not — also answers with the fact that no upload session could be opened, and
  that helper's result is already applied after the caller's extras. One owner states the add form's
  state, and no reader needs telling why a line sits where it does.

Rejected: leaving them because the change is about the back link. A scope limits which files are
opened, never which lines of an opened file are fixed. Also rejected: rewording the doc comments into
plain comments — the rules do not want a comment there at all.

**D9 — The collection recipe's change-context instruction gains the review case.**

`sets/live-animals/docs/add-a-collection.md:346-349` tells an author to wrap every internal link and
redirect, back links included, in the shared change-context helper so the context survives the loop.
The documents page is the collection that recipe is written from (`sets/live-animals/docs/features.md:83`
names it first under Collections). After this change its back link does the opposite: it reads the
change context and answers with the review page rather than carrying the context onward. An author
following the recipe for a page that returns to the review would build the wrong thing, so the recipe
is edited in this change (section 2). Rejected: leaving it, on the grounds that the sentence is still
true of row actions and the add/remove/save round-trips — it is written as a rule about every internal
link, and back links are named in it.
