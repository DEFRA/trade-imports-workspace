## 0. Decisions

- **The gate becomes rejection-only, in the one place that already owns it.** `leavePage`
  (`controller.js:324`) refuses on `hasDocumentsNotClearedByScan`, which in `scan/status.js:47`
  treats every status other than `COMPLETE` as uncleared, so `PENDING` and `REJECTED` are refused
  together. The change narrows that predicate to "the scan rejected this document" and leaves the
  branch where it is. Rejected: adding a second, pending-specific test beside the existing one in
  `leavePage` — that would be two gates for one rule, and the branch that has to disappear is the
  pending one, not a new one.
- **The predicate gets one owner, in `scan/status.js`.** After narrowing, the same "the scan
  rejected this document" test is wanted by `scan/summary-errors.js`'s `rejectedErrors`
  (`summary-errors.js:13`), which today inlines its own `scanStatus === REJECTED` comparison.
  `scan/status.js` exports the predicate and `summary-errors.js` uses it. Rejected: leaving the
  two comparisons side by side — one rule, one owner.
- **`settlingSummaryErrors` and the "You cannot continue until all documents have been scanned or
  removed" copy are deleted, not left dormant.** Under the new rule the refusal fires only when a
  document is rejected, and `settlingSummaryErrors` (`summary-errors.js:21`) returns `[]` in exactly
  that case, so it can never produce a line again; the only caller of the copy key is that
  function. `render` already prepends `rejectedErrors(documents)` to the summary
  (`view-model/render.js:47`), so the refusal render needs no summary errors of its own. The key
  goes from `copy.en.js:132` and `copy.cy.js:137` together, keeping the locale key trees in step.
  Rejected: keeping the string "in case design wants it back" — unreachable code and copy.
- **The hub-exit short-circuit stays exactly as it is.** The programme invariant that Save and
  return to overview must make the same checks as Save and continue is built by inc-232 in
  `themes/design-snagging-followups`, not here. This row changes only the scan branch. Whichever
  of the two lands second updates the other's tests; the build report must say which order it
  happened in.
- **The review keeps its own hold on a document still being scanned.** `check-answers/refusal.js:43`
  marks the uploaded-documents card and refuses the review while any document is pending, and the
  animals backend publishes only claimed documents whose scan status is `COMPLETE`
  (`OutboxService.java:81-84`, verified), so without that hold a trader could submit a notification
  whose document is silently dropped from the outbound event. The row says nothing about the review,
  so the review's behaviour is unchanged and its spec requirement stays true. The question of
  relaxing it goes to the backlog as a follow-up, not into this row.
- **The "Still checking some documents. Refresh again in a moment." hint stays.** It is the
  no-JavaScript refresh fallback's message when the poll has given up (`template.njk:166`,
  `copy.en.js:96`), about reading the status, not about continuing. Deleting it would break the
  manual-refresh behaviour the spec records separately. The acceptance criterion's "the page says
  nothing about waiting" is satisfied by the refusal line going.
- **Plants takes no mirror change.** The programme invariant mirrors a change into
  `trade-imports-plants-frontend` wherever it has the same page or behaviour. It has no documents
  feature at all (no `documents` directory anywhere under its `src/server/app`), and the theme's
  repo map lists only frontend and tests. Nothing to mirror.
- **Where the integration proof lives.** `gatePhases` is `[]`, so the loop runs no local gate. The
  end-to-end proof is still written in this row, in the tests repo, and is run by the pull-request
  CI for both repos (both run `tests/animals/` against the branch-tagged images). Section 5 names
  it as a stack check so a stage can run it directly under the run's lease.
- **The pending leg of the end-to-end proof is guarded, not raced.** The stack's uploader mock
  settles a scan after about three seconds (`MOCK_VIRUS_RESULT_DELAY: 3` in
  `docker/stack/infrastructure.compose.yml`), so a row can already read "Check completed" on the
  first render. The repo's own `firstScanStatus` helper (`utils/scan-status.ts`) exists for exactly
  this and already guards `documents-refresh-no-js.spec.ts`; the new pending assertion runs behind
  the same guard. Rejected: asserting the pending state unguarded — a flaky assertion. Rejected:
  skipping the pending leg end to end — the frontend fit suite proves it deterministically (the
  stub holds a fresh upload pending until a refresh read, `services/document-uploads/stub.js:109`)
  and the guarded e2e witnesses it through the real stack.
- **Only one of the two amend claim-return cases goes to the review.** `kit.returnedSaveChoice`
  (`shared/kit.js:165-171`) reads `change` in an amend journey from the amend return marker alone,
  ignoring the `change=1` query, so the amend Save and continue case resolves to `change: false`
  and `hubExit: false` and lands on the overview, while the amend Save and return lands on the
  review. The existing untouched-form cases prove both (`controller.test.js:545-563`). The
  parameterised case therefore carries an expected target per choice, not one shared target.
  Rejected: asserting the review for both amend choices — the code does not do that.
- **The deleted copy key's parity is proved by a check that can see it.** `test:live-animals`
  filters to `src/server/app/sets/live-animals`, and `copy-parity.test.js` and
  `copy-convention.test.js` both sit at `src/server/app/`, so that script cannot reach either.
  Section 5 names those two files directly through the repo's `test` script. Rejected: leaving the
  Welsh-beside-English invariant to `test:live-animals`, which would never have run it.
- **The refusal log's `documents` value comes from the summary's owner, not from a new string.**
  With `copy.errors.cannotContinue` gone, the field's message is whatever `rejectedErrors`
  (`scan/summary-errors.js:11`) built for this page state — the same call the render makes. Rejected:
  inventing a one-line "a document was rejected" string for the log, which would be a second owner
  of refusal wording and a copy key the page never shows. The departure this takes from
  `logRefusal`'s singular doc comment is recorded in section 14.
- **The two pending unit cases become one parameterised test.** After the change, Save and continue
  and the hub exit both leave the page while a scan is pending, so two separate tests would be
  near-identical ten-line blocks and the duplication rung flags clones of ten lines or more over
  changed test files. One parameterised test over the save choice keeps both branches proven
  without a clone. The file already uses that shape (`controller.test.js:463`).
- **No claim in the increment was found false.** The prototype's Design Release 2.1 journey adds a
  document and goes straight on with Save and continue, with no scan step at all
  (`prototype-specs/e2e/journeys.fit.spec.js:102-112`); the note that
  `documents-scan-lifecycle.spec.ts` no longer asserts the hold is correct; the rejected wording in
  `copy.en.js:143` is the one the criterion quotes; the backend's publish filter is as described.
  The prototype source repo itself is not checked out on this machine, so the prototype evidence
  read is the workarea's own copy of its driving specs, which the sources file lists as a source in
  its own right.

## 2. Edits

**frontend — `src/server/app/sets/live-animals/journeys/linear/features/documents/scan/status.js`**

The predicate at `:47` stops meaning "not cleared by the scan" and starts meaning "the scan
rejected this document", comparing against the rejected status rather than against anything that is
not complete. The two exports built on it (`:49`, `:52`) follow: one answers whether any document
on the page was rejected, the other returns those documents in the shape `scanned` already produces
(`:38`). Their names must say "rejected", because after the change that is the only value they can
describe; the import list in `controller.js:44-49` follows. The predicate is exported, because
`summary-errors.js` is the second reader of the same rule.

**frontend — `.../documents/scan/summary-errors.js`**

`settlingSummaryErrors` (`:21`) and the module-scope `CANNOT_CONTINUE_MESSAGE` (`:9`) go. The copy
import stays for `rejectedErrors`. `rejectedErrors` (`:11`) filters through the predicate

**frontend — `.../documents/controller.js`**

`leavePage` (`:324`) refuses only when a document was rejected: the hub-exit short-circuit at `:326`
is untouched, the scan branch at `:329` tests the new rejected predicate, and everything after it —
the unsaved-claim recovery and the continue — is untouched. A document still being scanned now falls
through to those later steps and, when they are satisfied, to `continueToNextPage` (`:305`).

`renderStillSettling` (`:310`) is the refusal render for the rejected case now, and its name must say
so. It no longer passes `summaryErrors`: `render` already prepends `rejectedErrors(documents)`
(`view-model/render.js:47`), so the refusal's summary is one line per rejected file, owned in one
place. Its refusal log (`:311-315`) keeps `kit.logRefusal` and keeps reporting the field the refusal
is raised under, so `errorCodes` still reads `documents`; the `reason` value and the field carrying
the refused uploads must both say that the scan rejected them rather than that scans have not
cleared, and the field carries what `scanned` produces for those documents — upload id, scan status
and tag key.

The `documents` entry of `fieldErrors` can no longer be the deleted "cannot continue" string, and
its replacement is not a string the implementor chooses. Its one source is
`rejectedErrors(pageState.documents)` (`scan/summary-errors.js:11`) — the same call `render` makes
at `view-model/render.js:47`, so the value logged under the field and the lines the page shows come
from one owner, and the per-file wording stays in `copy.errors.rejected`. Where the scan rejected
more than one document, every one of those lines belongs to the one `documents` key: the key is
what `logRefusal` turns into `errorCodes`, and the value is never logged. No new copy key, constant
or message is introduced; see section 9 for the doc comment this reads against.

The `settlingSummaryErrors` import (`:50`) goes.
