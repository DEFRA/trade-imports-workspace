## 0. Decisions

1. **The character and length rules go into the existing REQ-DOCS-006, not a new requirement.** REQ-DOCS-006 (`openspec/specs/live-animals/journey-pages/upload-documents/spec.md:109-111`) already owns the document reference's validation, and `openspec/config.yaml` holds "One subject, one capability" and forbids scattering one subject. Rejected: a new sibling requirement for the character rule, which would split one field's validation across two requirements and make a reader check both before trusting either.

2. **Two new scenarios, not one.** Acceptance is a separate observable outcome from refusal, and two tests already prove them separately (`controller.test.js:2246` accepts four printed-reference shapes; `controller.test.js:2261` refuses three disallowed shapes). Rejected: one scenario with both halves in its THENs, which would have had to claim a single coverage strength for two different witnesses.

3. **SCN-DOCS-006-B gains the length message verbatim.** The row asks the requirement to state the hundred-character cap; a reader can only check that against the running page if the scenario quotes what the page says. `controller.test.js:2276` already asserts that exact sentence against the constant, so the quote is backed. Rejected: stating the cap only in the requirement body, which leaves the spec unable to be checked against the page.

4. **SCN-DOCS-001-A gains a `partial` unit coverage link; it does not lose the fit links.** The scenario's THEN is a page observation — the page loads and states both the maximum file size and the accepted file types. The fit link at `upload.fit.spec.js:190` makes that page observation but reads the size bullet through `copy.file.smallerThan(MAX_FILE_SIZE_LABEL)`, so it holds whatever the label says and cannot witness the figure the scenario now quotes. `upload-config.test.js:61` pins the opposite half: the byte count is fifty million and the oversize message names that size. It never loads the page and asserts nothing about the accepted file types, so by `docs/reference/openspec.md:169` ("Unit only — mechanism / config, not product observation") it is not on its own a strong witness of this THEN and is written `partial`, with notes saying what it pins and what it does not observe. The scenario's derived rollup is unchanged: the fit link already carries `full`. Rejected: writing the unit link `full`, which would claim a strong witness of a page observation for a test that never loads the page; and leaving the fit links alone with no unit link at all, which leaves the quoted figure with no witness anywhere.

5. **`copy/copy.test.js`'s two size-bullet tests stop naming a figure the service once applied as its limit.** `page-design.md:344-345` states the design: "The file size limit is whatever `MAX_FILE_SIZE_MB` in `journeys/linear/features/documents/upload-config.js` holds; nothing else states a figure." Both tests currently assert against `'10MB'` — the figure the service applied before this limit was raised — so a reader grepping the documents feature for the limit finds it, which is the drift this row exists to close. Each test keeps proving that its locale's template substitutes the size it is given, using a sample size that has never been the service's limit; the figure the service applies stays owned by `upload-config.js:41` and pinned once, at `upload-config.test.js:61`. Rejected: asserting the live label in `copy.test.js`, which would put a second pin of the figure beside the one that exists; and deleting one of the two cases, which weakens the substitution proof the titles claim.

6. **`fit/upload.fit.spec.js:335`'s title is corrected because it mispredicts.** It says "over 58 characters" while its body submits `REFERENCE_MAX_LENGTH + 1` (101) and asserts `copy.errors.referenceMaxLength`, which names 100. 58 is the cap on other fields entirely — the origin page's internal reference (`features/origin/validate.js:20`), the identification values, the arrival page's transport document reference — so the title points a reader at the wrong rule. The corrected title states what the assertions prove and names no length belonging to another field. The body is not changed. Rejected: leaving it, on the grounds that the row is a spec row — the row's own subject is this rule, and `coverage.json:157` quotes this title as the witness for the scenario the row rewrites.

7. **No production code changes, and no backend or tests-repo change.** The service already applies both rules: `upload-config.js:41` holds 50, and the reference rule is `claim-contract.js:1` and `:7`, mirrored in the backend at `ClaimUploadRequest.java:26` and `:45` with the same pattern and the same `@Size(max = 100)`. The spec is what is wrong, not the code.

8. **`frontend-change` routes this row by its general-change route, at the set/journey layer.** The row now names the frontend and edits two of its test files, so the skill applies. It is none of the four recipe triggers — it adds no field, page, section or collection and changes no obligation and no journey flow — so it takes the fifth row of the routing table, "change the frontend (anything else)", and with it Step 1.2 (`.claude/skills/frontend-change/SKILL.md:155`): "For a general change, decide the layer first (L1–L4 above), then Read the matching guide(s)". The layer is set/journey — every file this plan changes lives under `sets/live-animals/` or is that set's own documentation — so the obligation discharged is the set index, `sets/live-animals/docs/README.md`, and from it `page-design.md` (which owns the documents page's design decisions, and is the rule this plan applies in decisions 5 and 11), `features.md`, `journey-flow-and-gates.md`, `services.md`, `limits.md` and `testing.md`. The two files edited are tests, so the platform's own testing guides come with them: `src/server/app/docs/testing.md` and `src/server/app/docs/test-ownership.md`, reached from the platform index `src/server/app/docs/README.md`. Every one of those is listed in section 16 for the implementor to read in full. The precedent is this theme's `inc-037`, which took the same route at the feature layer. The spec writes in section 8 are the writes this route's Step 5 makes; they are set out here rather than left to the step to invent. Rejected: treating the row as unrouted because it changes no production behaviour, which is what the previous draft of this plan did — the routing table keys on what is changed, not on whether the change is observable, and skipping the route cost the set's `page-design.md` and the testing guides from section 16.

9. **Section 6 names the two scoped test runs the loop's gate will not run.** The row's `gatePhases` is empty, so no unit, fit or e2e rung runs against the frontend; the first attempt went ladder-red on exactly that gap. The two runs listed are scoped to the files this row edits and to the tests its new coverage links name — nothing wider. The whole-repo format, lint, duplication, unit and fit rungs are left to the pull request's CI, the verification the theme's other rows use, as the row's 27 October note directs.

10. **`tim spec lint` is the spec validator, not `openspec validate`.** The latter runs through `npx`, which an agent in this run may not invoke; `tim spec lint --capability` covers the conventions, the coverage internals and the binding, and is what the acceptance criterion names.

11. **The rationale carried in the two edited test files moves to the set's `page-design.md`, where two of the five facts already live.** Both files are edited for the row's own behaviour, so bounded tidy-up makes every house-rule breach in them this change's to fix, and five comments breach the same two rules: `.claude/rules/code-quality.md`, "A comment describes only the lines directly below it. Never describe callers, other modules, the backend, a library, the UI or a test", and "Rationale goes in the repo's `docs/` or the behaviour spec, never in code" (the one in `copy.test.js` is also a doc comment on something that is not an exported public API). Two of the five say what `page-design.md` already says (`:335-339` for the scan-tag wording, `:405-406` for the shut add control), so those comments are deleted outright. The other three state facts the set's documentation does not yet hold, so each gains a bullet in `page-design.md`'s Documents section before its comment is deleted — that doc is the existing home for the documents page's design rationale and needs no new file. Rejected: deleting all five and losing three facts the set's documentation does not record; and leaving the three because the row is "a spec row", which the bounded tidy-up rule does not allow for a file edited for the row's own behaviour.

12. **The two coverage links whose test name is stale are repaired without their strength being re-claimed.** SCN-DOCS-004-A's first e2e link and SCN-DOCS-006-B's fit link each name a test title that no longer exists; the tests themselves are unchanged in what they do, and both links already stand at `full` on this tree. Repairing the pointer and writing notes is not a new strength claim, so `openspec/config.yaml:59-61`'s red probe is not owed again for them — what the probe would establish is already recorded. The fit one is probed anyway, because this row changes that test's title and section 6 runs the spec that contains it; the e2e one is not, and cannot be: no end-to-end rung runs for this row (`gatePhases` is empty), and a probe of it would need the leased stack's frontend image rebuilt, which this run does not do. Rejected: downgrading the e2e link to `partial` because this run cannot probe it, which would drop a scenario's recorded coverage on no evidence that the witness is weak; and writing the strength as a fresh `full` claim, which would owe a probe the row cannot run and would stop the increment with nothing broken.
