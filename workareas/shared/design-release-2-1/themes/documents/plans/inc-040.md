## 0. Decisions

1. **`unlockSections` keeps main's parameter and default and the theme's delegation, not either side whole.** Main rewrote the helper so a chosen commodity is a search row (`{ commodityCode, speciesLatinName, speciesCommonName }`) rather than a Latin-name string, and swapped `unlockSections`' default from a Latin-name string literal to the cat row constant (`origin/main:fit/live-animals-journey.js:615-620`, `:33-38`). The theme replaced the same four body lines — the overview-link click, the species tick, the save and the overview assertion — with a call to the overview-entry step it added (`fit/live-animals-journey.js:566-568`). The resolution takes main's signature and default and the theme's single delegating call, because the two sides change different things about the same function: main changes *what a chosen commodity is*, the theme changes *who owns the click-select-save-return sequence*. Rejected: taking main's body whole, which would leave the sequence written out in two places — the helper and `answerWhatYouAreImportingFromOverview` — against one rule, one owner; and taking the theme's body whole, which would pass a Latin-name string into a `selectSpecies` that now reads a commodity code and a Latin name off each chosen value.

2. **`answerWhatYouAreImporting` takes one optional chosen-row parameter, defaulting to main's cattle row.** The theme gave it an optional parameter so the overview-entry step could forward a species (`fit/live-animals-journey.js:652-657`); main kept it parameterless and swapped the string literal for the cattle row constant (`origin/main:fit/live-animals-journey.js:700-703`). One signature serves every caller on the merged branch: the opening-run step calls it with no argument (`origin/main:fit/live-animals-journey.js:530`), `answerWhatYouAreImportingFromOverview` forwards whatever it was given — undefined from `completeAnswerSections` (`fit/live-animals-journey.js:865`) and from the documents entry fit spec (`.../documents/fit/entry.fit.spec.js:32`), the row it was handed from `unlockSections` — and no spec calls it directly. Rejected: two helpers, one parameterless and one taking a row, which is a second mechanism beside the one that exists.

3. **The chosen-commodity vocabulary across the three helpers is main's, not the theme's.** Main's `unlockSections`, `selectSpecies`, `tickSpecies`, `openCommodityDetails` and `expectSpeciesSelected` all name their argument for the chosen search row; the theme's two helpers still name theirs for a species name. After the resolution the value is a row everywhere, so the parameter names of `answerWhatYouAreImporting` and `answerWhatYouAreImportingFromOverview` follow main's, which already predicts what the value holds. Rejected: keeping the theme's species-name wording over a value that is no longer a name — a name that mispredicts.

4. **`refusal.js` takes main's file whole and re-applies the theme's one substitution.** Main added `toArray`, the review copy, the unlisted-species check and the refusal branch that logs it; the theme replaced one inline scan-status comparison with the predicate it had extracted (`src/server/app/sets/live-animals/journeys/linear/features/check-answers/refusal.js:40`, predicate at `.../documents/scan/status.js:47`). The two touch different lines of one import block and one function, so the resolution is main's file with `isRejectedByScan` added to the existing `scan/status.js` import and used as the rejected-scan predicate. `SCAN_STATUS` stays imported: main's pending-scan comparison still uses it. Rejected: dropping the theme's predicate to take main's inline comparison, which would put the rejected-scan rule back in two places.

5. **The theme's extracted rejected-scan rule survives the merge, reached through `hasRejectedDocuments` — the sibling in the same module that owns the rule — rather than main's inline comparison.** `scan/status.js` exports both `isRejectedByScan` and `hasRejectedDocuments`, and `hasRejectedDocuments` is exactly `isRejectedByScan` used with `.some`, already the call `documents/controller.js:328` makes. `refusal.js` calls it in place of main's own `.some(isRejectedByScan)`, which is what AC3 protects in substance — one rule, one owner for the rejected-scan check — even where AC3's wording names `isRejectedByScan` as the literal import. Rejected: main's inline comparison, which would put the rejected-scan rule back in two places.

6. **The tests repo's `docs/animals-journey.md` loses one stale bullet in this row; the frontend's `docs/testing.md` inaccuracy does not. The dividing line is which file this branch already owns an edit to, not which statement the merge falsifies — neither statement is falsified by the merge, because both are already untrue on `origin/main`.** `origin/main:page-objects/animals/commodity-selection-page.ts:65` renamed the tests-repo page object's species method and left `origin/main:docs/animals-journey.md:61` naming the old one; that line is byte-identical on the branch, which is why the file merges cleanly and why the merge transports the inaccuracy rather than causing it.
