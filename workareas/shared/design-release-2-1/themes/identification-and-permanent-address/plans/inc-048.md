## 0. Decisions

- **The claim does not hold as a "fix" — it already holds as behaviour.** Tracing `form/forms.js` on the pinned HEAD: `linesToReadFormsFor` (`forms.js:87-95`) filters the lines a `add:N` action builds forms for down to the one line named by `N` before `withEmptyFormGuard` (`forms.js:133-144`) ever looks at `anyData`. So pressing one species' own "Save and add another"/"Save and finish" already reads only that species' own posted fields — a filled sibling card never enters the `forms` map the guard inspects, and an *empty* sibling therefore cannot make `anyData` true either. This is exactly what the backlog's own 11 November note independently concludes ("criterion 1's core is already built"). Decision: plan this increment as **proof, not production change** — write the tests the row asks for against the current tree, run them, and if (as traced) they pass unmodified, that is the increment. Rejected alternative: pre-emptively rewrite `withEmptyFormGuard`'s `anyData` scan to take an explicit line index — rejected because the trace above shows the scoping this would add already exists one call up the chain (`linesToReadFormsFor`), so the rewrite would be a second mechanism beside the one that already does the job, which the house rules forbid.
- **AC2 ("Save and finish") is the same code path as AC1 ("Save and add another"), not a second branch.** The card's own button always posts `action=add:<index>` regardless of its label (`_identification-card.njk:60-65`; `card/view-model.js:59-64` only changes the button's *text*, never its `name`/`value`). So AC1 and AC2 are two acceptance criteria over one `linesToReadFormsFor`/`withEmptyFormGuard` code path. Decision: prove AC2 with its own unit test (a real, separate seed — a line one save away from its cap, so the button's text genuinely is "Save and finish") but do not duplicate it at FIT/E2E once AC1 has proved the mechanism live in a browser; a second full-stack proof of the identical branch would be padding.
- **AC4's two controls (`Save and continue`, `Save and return to overview`) post no `action` field at all on this page.** `animal-identification.njk:41`'s `saveActions({...})` call passes no `primary`, so the primary button falls back to `{ text: copy.saveAndContinue }` with no `name`/`value` (`shared/save-actions.njk:35`); the hub-exit button carries `name="exit" value="hub"`, never `name="action"` (`shared/save-actions.njk:42-47`). So for both controls `payload.action` is `undefined` → `action = ''` → `parseAddAction('') === null`, and `withEmptyFormGuard` short-circuits on `addIndex === null` before it ever looks at `anyData` (`forms.js:135`). Both controls are therefore already exempt from the blank-record refusal, uniformly. Decision: prove this for `Save and continue` by citing the already-green `animal-identification.controller.test.js` test "Should exit without appending when no form holds data — the zero-record pass" (no code change needed to keep it green), and add one new unit test for `Save and return to overview` specifically (`payload: { exit: 'hub' }`), since no existing test exercises that control's own payload shape on this page.
- **A programme invariant is contradicted by this row's own AC4, and by the shipped `REQ-IDENT-009`/`REQ-IDENT-021`.** The theme header's invariant reads: *"Every save control a page offers makes exactly the same checks on that page's answers... the controls differ only in where they go once every answer passes."* On the identification page this is false by design: the in-card button enforces "at least one identifier" (`REQ-IDENT-009`) and `Save and continue`/`Save and return to overview` do not (`REQ-IDENT-021`'s own text: they "validate and save **only** the forms of species with one animal" — a multi-animal line's answers are not even read, let alone checked, by those two controls). This row's AC4 restates the same exemption as a requirement, not a bug. Decision: keep the page as specified (REQ-IDENT-009/021, and this row's own AC4) rather than "fixing" it to match the header invariant — changing it would reverse a previously-delivered, ruling-backed behaviour and fail this row's own AC4. Flagged under Departures and Risks for the programme owner; no code or spec text changes as a result.
- **Stand-in species for "cattle and dogs."** `domain/animals/constants/commodity-lines.ts` (tests repo) and the frontend's own `search/test-support.js` have no plain "dog" (`Canis familiaris`) row — only `raccoonDog` (searchTerm `'dog'`, Latin name `Nyctereutes procyonoides`). Decision: use the pairing every neighbouring test in both repos already uses for "two cards, one filled one blank" — cattle (`BOS_TAURUS_ROW` / `commodityLines.cattle`) plus a second 0102 species (`BISON_BISON_ROW` / `commodityLines.bison`) for the FIT/E2E proofs, and cattle plus a 01061900 species (`FELIS_CATUS_ROW`) for the unit proof, where a second scoped-field species makes the "first identifier field" assertion unambiguous. "Dogs" in the acceptance criterion is illustrative of "a second species card," not a literal species pin.
