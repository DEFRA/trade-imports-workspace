## 0. Decisions

1. **The page is its own top-level feature folder, not a sub-folder of the
   addresses feature.** The CPH number page is the live precedent: it is
   reached only from the consignment addresses page, returns there, and still
   lives at `features/cph-number/`. Rejected: putting it under
   `features/addresses/`, which would read as a second party picker and would
   mix the commodity-line knowledge the page needs into the parties feature.

2. **The page is a sub-page in the `consignment-parties` flow section and in no
   task row.** `src/server/app/flow/navigation.js:13` treats a page as a step
   only when it is not a sub-page *and* belongs to a task row, so a sub-page in
   a section takes its place in the page order without ever being offered by
   Save and continue; placing it ahead of the consignment addresses page makes
   the addresses page the next step, which is where Save and continue must go.
   Rejected: adding it to the "Roles and addresses" task row, because
   `features/amend-endings.test.js:37` renders every task-row page against the
   comprehensive characterisation corpus, which carries no cat, dog or ferret
   line — the page would redirect rather than render and the test would crash
   on an absent view. Extending that corpus would also move the fulfilments half
   of `fixtures/characterisation-oracles.json`, which
   `bridge/feature-assembly.golden.test.js` holds byte-identical — on top of the
   evaluation half this increment already re-baselines because the manifest gains
   a leaf (decision 16 and section 2). Consequence
   recorded under 7 as a follow-up: the page carries no amend-parity entry in
   `amend-endings.test.js`, and nothing in the template branches on amending,
   so the two renders cannot differ.

3. **The same-as-destination answer is stored as its own obligation leaf on the
   animal identifier record, beside the permanent address.** The increment says
   each animal's choice is stored with the notification, and the page must
   reopen with the chosen option selected. Rejected: folding the flag into the
   permanent-address value object, because `model/obligations/is-blank-value.js`
   judges that object blank-or-not as a whole, so an animal whose only stored
   content was the flag would read as having a permanent address and the
   notification would become submittable with none. Also rejected: deriving the
   choice by comparing the stored address with the current place of destination,
   which flips to "Enter a new address" as soon as the place of destination is
   edited and loses the answer entirely when the choice is made before a place
   of destination exists.

4. **The backend repo is not changed.** The animal identifier record already
   carries the permanent address as a consignment party with a full standard
   address block including county and country code
   (`AnimalIdentifier.java:20`, `ConsignmentParty.java:19-25`,
   `Address.java:15-23`), and the GBN-AG event already publishes it
   (`outbox/gbnag/TradeProductInstance.java:38`). The new choice leaf has no
   home in the notification shape, so per the add-a-page recipe's step 7 the
   notification mapper is left unchanged and the omission is asserted instead of
   a field being invented. The canonical obligation fulfilments the frontend
   round-trips are sent to the backend as an opaque payload
   (`services/persistence/records/real/lifecycle/mutate.js:25`), so the choice
   persists across sessions with no backend field.

5. **Cards come from the animal identifier records entered on each line, not
   from the line's animal count.** The prototype renders one card per animal
   counted, before any identifier is entered. The real service cannot: the
   permanent address is stored on the animal identifier record, and
   `bridge/fulfilments/project-answers/dense-indices.js:17-35` fails the whole
   projection when a nested collection has a gap, so an address written against
   animal 2 while animal 1 holds nothing would make the notification unreadable.
   This is a persistence constraint the prototype cannot express, which
   `ruling:sam-2026-10-07` lets override it. Consequence: the second clause of
   criterion 6, "shows no inset when none are entered", has no reachable state —
   `animal-identification/form/forms.js:133-144` refuses an animal record with no
   identifier, so every record carries at least one. The card's inset is still
   built from the entered identifiers and renders nothing when the list is
   empty, but no test is planned for that state. Reported under 0.11 as a claim
   that does not hold.

6. **The page's own guard is "no animal on this consignment needs a permanent
   address".** One rule covers both criterion 2 (a consignment with no cat, dog
   or ferret line) and a pet consignment whose identifiers have not been entered
   yet. Both are sent to the consignment addresses page and logged once, the
   shape `transport/transit-countries/transit-countries.controller.js:129-141`
   and `commodities/animal-identification/animal-identification.controller.js:110-122`
   already use. Consequence: a trader who follows the new link before entering
   any identifier bounces straight back; criterion 1 makes the section depend on
   the consignment's species, not on its records, so the section is there before
   the records are.

7. **Criterion 1's "five sections" is read as the five party sections.** Today
   a cats-only consignment shows exactly those five, because
   `obligations/sections/commodities/aggregates.js:17-26` leaves the CPH number
   out for commodity code 01061900. After this increment the same consignment
   shows six: the five party sections and Permanent address, still no CPH. The
   criterion's first clause requires the new section and the prototype's own
   driving spec asserts it beside the absent CPH link, so the count in the
   second clause is about the party sections.

8. **The page ends with the primary save control alone on a draft and while
   amending alike.** `sets/live-animals/docs/page-design.md` "How a page ends"
   says a page reached from another page ends that way, and the shared save
   actions macro already takes an option that drops the return controls
   (`shared/save-actions.njk`, used by `features/cph-number/template.njk:85`).
   Criterion 9 fixes the non-amend case; the invariant that a page ends the same
   way while amending fixes the other, and the template takes no amend branch,
   so they cannot diverge.

9. **The stored permanent address takes the service's one party shape.** Every
   other address on the notification is stored as a party with the name, phone
   and email at party level and the rest in an address block carrying a country
   code (`features/addresses/party-edit/address-rules.js:73-85`). The animal
   identification page stores a different shape today, with phone and email
   inside the address block and no country code, which
   `services/persistence/records/notification-mapper/shared/lines/species-entry.js:4-11`
   then lifts back out. The new page writes the one shape, and that lift is
   removed. The wire shape the backend receives is unchanged, so no persistence
   assertion in the tests repo moves. No compatibility read of the old nesting is
   written: a draft saved before this increment loses the phone and email of an
   already-stored permanent address.

10. **The new address fields ask no country and the stored country is the
    United Kingdom.** Criterion 8's field list, the prototype's rendered form
    and today's identification form all ask eight fields and no country, while
    criterion 11 requires the saved record to read back with country United
    Kingdom. `services/countries/index.js:50-51` already owns the United
    Kingdom's name and code; the code becomes an export of that module rather
    than a literal in the new feature.

11. **Claims that do not hold.** Criterion 6's "shows no inset when none are
    entered" names a state no reachable journey produces (see 0.5). Criterion 10's
    "has the place of destination's name, address, country, email and phone as its
    permanent address on the review page" is carried here only as far as the
    stored record and the name the review's species card already shows: the review
    shows a permanent address by name alone today
    (`features/check-answers/view-model/cards/consignment/species/identifier-cell.js:5-6`),
    and the increment's own notes put the summaries in a later row.

12. **The permanent-address field name and applicability rule stay where they
    are.** `features/commodities/animal-identification/identifier/fields.js:19-22`
    owns both and the new feature imports them. Moving them into the new feature
    would mean a new file plus two check-answers files edited only to follow the
    move — clean-up outside this row's footprint. Follow-up under 7.

13. **The status of a missing permanent address stays on the "Identification
    details" task row.** The obligation lives beneath the animal identifier
    record, and that row claims the whole `animalIdentifiers` facet
    (`journeys/linear/flow/task-rows.js:54-60`). `bridge/status/facets.js:4-9`
    filters only the direct children of the named collection, and
    `bridge/status/classification/index.js:41-47` reads the facet's collection
    from the top level of the answers, so no facet can name a leaf two levels
    down. Criterion 12's submit block therefore holds unchanged. Rejected:
    teaching the status facets to address a nested leaf, a platform change well
    outside this row. Follow-up under 7.

14. **Plants is not changed.** The permanent address applies to the animal
    journey only, and the high-risk plants frontend has no consignment addresses
    page section or animal identifier record for it to mirror, so the
    programme's plants-parity invariant does not bite.

15. **Dogs are not exercised by a test.** The permanent-address species rule
    already lists the domestic dog
    (`sets/live-animals/services/commodities/rules.js:65-71`), but the commodity
    catalogue the stub and the fit suites serve
    (`services/_capture/fixtures/commodities.json`) holds no Canis familiaris, so
    no reachable journey selects a dog. Cats and ferrets are the two reachable
    pet species and both are exercised.

16. **The manifest gains a leaf, so the characterisation baseline moves and this
    plan owns the move.** The evaluation the characterisation test pins carries
    one entry per manifest obligation
    (`model/obligations/evaluator/implications/build.js:3-12` loops the whole
    obligation array and `model/obligations/evaluator/index.js:84-95` returns it
    as `evaluation.obligations`), and
    `bridge/fulfilments.characterisation.test.js:36-38` asserts that object both
    by value and stringified. Each of the five corpus cases holds 50 entries
    today, matching the 50 obligations listed in `obligations/index.js:122-173`,
    so decision 3's new leaf makes it 51 in every case and the committed oracle
    has to be re-baselined (section 2). The fulfilments half does not move:
    `bridge/assemble-fulfilments.js:23-27` emits only the leaves a feature
    contributed a value for, and no corpus case carries a cat, dog or ferret
    line, so no case gains an answer. Rejected: giving the new leaf a home
    outside the manifest array so the baseline stands — there is no such home;
    every obligation the evaluator knows is in that array, and a leaf outside it
    would never be scoped, written or read.

17. **The page asks its question once, as each card's radio group legend.** The
    prototype's per-animal page carries a page-level sub-heading question above
    the cards (`prototype:dr2-1-source` p9-036, "Where will their permanent
    address be?") as well as each card's radio legend (p9-040, "Select an
    address"). Only the card legend is built. Criterion 3 fixes what the page
    shows above the cards — caption, heading, browser title and back link — and
    names no question there; criterion 7 puts the question on the card, which is
    where the trader answers it, once per animal. A question above the cards
    would be a second home for the one thing the page asks. Recorded as a
    departure from the prototype under 14 and as a design question under 7.
    Rejected: building both, as the prototype does, which would ask the same
    thing twice in two different words.

18. **The fraud warning moves with the address onto the new page; the "what a
    permanent address is" guidance moves to the consignment addresses page
    instead.** The prototype shows the warning on the per-animal page
    (`prototype:dr2-1-source` p9-034) and today's identification card renders it
    (`animal-identification/_identification-card.njk:34`, from
    `commodities/copy/copy.en.js:97`), so the warning belongs where the address
    is entered and it is part of this page. Its companion guidance — the "A
    permanent address is where an animal:" lead-in and its two bullets, which
    the prototype repeats on both pages (p9-025 and p9-035) — is built once, in
    the consignment addresses page section criterion 1 specifies, at the point
    the trader decides to add an address. So the warning carries a requirement
    and a scenario in the new capability in place of the deleted REQ-IDENT-012
    (section 8), a browser assertion (section 4, test 21) and a coverage link.
    Rejected: dropping the warning with the rest of the block, which would lose a
    standing spec requirement with no source saying it should go.

## 3. New files

All paths relative to
`repos/trade-imports-animals-frontend/src/server/app/sets/live-animals/journeys/linear/features/`
unless stated. The folder layout and the responsibilities of each file come
from the set's `docs/add-a-page.md` step 1; `features/cph-number/` is the
structure to follow for a sub-page reached from the consignment addresses page,
and `features/addresses/party-edit/` for the address form inside it.

- `permanent-address/page.js` — the page identity: its id, its slug and that it
  is a sub-page. Imports nothing, so the flow, the status and the controller can
  all read the same object without a cycle.
- `permanent-address/controller.js` — owns the page. Its guard sends a
  consignment where no animal needs a permanent address to the consignment
  addresses page, logging once. Its GET builds one card per animal record on
  each line that needs one and prefills each card's choice and address from what
  is stored. Its POST writes each answered animal's choice and permanent address,
  wrapped in the shared recoverable save, and redirects to the honoured return
  marker, else to the next page in the journey order. It exports the page's
  routes through the shared route builder and a `meta` that collects nothing
  directly: the commodity-line root another page owns carries everything the
  page writes. Not part of `addresses/controller.js`, because that page owns the
  five party roles and knows nothing of commodity lines.
- `permanent-address/cards.js` — builds the page's card list from the
  notification's commodity lines: which animals get a card, each card's title,
  the identifiers it insets, the two options it offers and the first option's
  one-line hint. The view model is its own module for the same reason
  `animal-identification/card/view-model.js` is.
- `permanent-address/answers.js` — the one owner of the page's answer shape:
  reading each animal's choice and address fields out of a posted form, and
  turning an answer into the stored party and choice. The place-of-destination
  option resolves to a literal copy of that party, the same way every other
  address on a notification is a literal copy.
- `permanent-address/write.js` — the one owner of the write: for each line with
  an answered card, the line's animal records with those animals' choice and
  permanent address set, committed through the shared per-entry collection
  update, one call per changed line, as
  `commodities/consignment-details/consignment-details.controller.js:182-190`
  does. Keeping the write here keeps the controller reading as a few named
  steps.
- `permanent-address/template.njk` — extends the shared layout, renders the
  section caption, the heading, the fraud warning, one card per animal and the
  save actions with the return controls off. Nothing between the warning and

## 14. Departures from written rules

1. **The card set is the animals' identifier records, not the line's animal
   count.** Departs from the design source: the prototype
   (`app/views/design-release-2.1/permanent-address-animals.html`, as driven by
   `prototype-specs/e2e/consignment-parties.fit.spec.js:300-312`, which sets a cat
   count of two and shows two cards with no identifier entered) and from
   criterion 5 read that way. Reason: a permanent address is stored on the animal
   identifier record, and
   `bridge/fulfilments/project-answers/dense-indices.js:17-35` fails the whole
   answer projection when a nested collection has a gap, so an address written
   against animal 2 while animal 1 holds nothing would make the notification
   unreadable. `ruling:sam-2026-10-07` claim 6 lets a real persistence constraint
   override the prototype. Also raise this with the designer: a trader who has
   entered one of two animals' identifiers sees one card.
2. **The page ends with the primary save control alone.** Departs from the
   prototype, which offers "Save and continue" and "Save and return to hub"
   (`prototype-specs/e2e/consignment-parties.fit.spec.js:320`). Reason: the DR1
   judgement in `document:dr1-parity-notes` on the same difference, carried by
   criterion 9, and `sets/live-animals/docs/page-design.md` "How a page ends",
   which gives a page reached from another page the primary alone.
3. **The page refuses nothing.** Departs from the prototype's error states
   (`prototype-specs/e2e/consignment-parties.fit.spec.js:325-343`). Reason: the
   increment's own notes put validation in a later row, and criterion 12 fixes the
   no-option-chosen behaviour as a save rather than a refusal. Recorded under 7
   as the coverage this increment removes and that row restores.
4. **The page asks no question above the cards, and carries no "A permanent
   address is where an animal:" guidance.** Departs from the design source: the
   prototype's per-animal page has a sub-heading question, "Where will their
   permanent address be?" (`prototype:dr2-1-source` p9-036), and repeats the
   guidance lead-in and its two bullets (p9-035) that it also shows in the
   consignment addresses page section (p9-025). Departs from
   `.claude/rules/code-quality.md`, "Build copy, layout and components as the
   design source sets them". Reasons in decisions 17 and 18: criterion 3 names
   what the page shows above the cards and names no question there; criterion 7
   puts the question on the card, where the trader answers it once per animal;
   and criterion 1 puts the guidance in the addresses page section, so building
   it twice would give one explanation two homes. The fraud warning is kept
   (p9-034) and specified. Raised with the designer under 7.
5. **The new page is in no task row**, where the sibling CPH number page is in
   one. Departs from the pattern `sets/live-animals/docs/add-a-page.md` step 6
   sets for a sub-page off the consignment addresses page. Reason in decision 2:
   `features/amend-endings.test.js` renders every task-row page against a corpus
   with no pet line, and the page would redirect rather than render.
