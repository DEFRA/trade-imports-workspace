## 0. Decisions

1. **Where the page's save rules live.** A new module in the permanent-address
   feature folder, composing two existing mechanisms: the shared rule
   primitives (`src/server/app/lib/validate/validators.js`, exported through
   `lib/validate/index.js:3-27`), and the per-field address rules the shared
   address-rules module already builds from V4's limits
   (`features/addresses/party-edit/address-rules.js:55-67`, today
   module-private, called only from `:69-84` in that same file). The new module
   states which of this page's fields are required and when; each field's limit
   and its over-long message stay with their one owner. Rejected: calling the
   whole-form `addressRules` builder at `:69` and parameterising it — it asks
   for a country this page does not show, checks an email format this page must
   not check, and words three of its six required messages differently from
   this page (`copy.en.js:22`, `:39`, `:47` give "Enter a name", "Enter a
   postcode", "Enter a telephone number" against this row's "Enter a name or
   organisation name", "Enter a postcode or Zip code", "Enter a phone number"),
   so it would need one option per difference and would change its only other
   call site for no behaviour of its own. Also rejected: attaching a
   `pageValidation` — see decision 2.
2. **No page validation on the page's meta.** `pageValidation`'s stored reading
   runs for every page on every submission (`app/docs/validation.md`, "Save
   rules and completion rules"), so attaching one would newly surface
   per-animal permanent-address errors on the task list and the review page.
   No criterion asks for that, and those answers belong to the commodity-lines
   domain, which is why the page already sits on the documented opt-out list at
   `features/validation-coverage.test.js:24-27`. Rejected: adding the stored
   reading anyway "for completeness". Recorded as a departure in section 14.
3. **Who owns the over-long message for an address field.** The existing owner
   keeps it: `features/addresses/party-edit/address-rules.js` reads the limit
   from `:14` and the message from `features/addresses/party-edit/copy/copy.en.js:20-54`
   (and its Welsh twin), which already states one `maxLength` message for every
   field this page shows — `name`, `addressLine1`, `addressLine2`,
   `townOrCity`, `county`, `postcode`, `phone` and `email`. This page therefore
   states **no length message of its own**: it composes the per-field rule that
   owner builds, passing only its own required message, so the eight
   "<field> must be N characters or fewer" sentences keep one owner, as the
   row's own note instructs ("reuse that validation and its existing
   '<field> must be N characters or fewer' messages"). The three other routes,
   weighed and rejected:
   - a fresh over-long message per field in this feature's copy — rejected: it
     is a second owner of one display rule over the same V4 limits
     (`.claude/rules/code-quality.md`, Structure: "One rule, one owner", and
     "Extend the mechanism that exists. Do not add a second one beside it.");
   - importing the party-edit feature's copy module into this feature and
     restating the rules here — reachable in this tree (`features/addresses/parties.js:3-4`
     is production and imports `'../contact/copy/copy.en.js'` and
     `'../contact/copy/copy.cy.js'`, so the earlier claim that no production
     file imports another feature's copy was wrong) but rejected anyway,
     because it separates the message from the rule and limit that choose it,
     leaving two places to keep in step;
   - passing no message and taking the shared fallback
     `validatorDefaults.maxLength` at `src/server/app/shared/copy.en.js:100`,
     which `app/docs/validation.md:35-38` documents ("When a call site passes
     no message of its own, a rule in `lib/validate` falls back to
     `validatorDefaults` in `shared/copy.en.js`") — rejected on its words: it
     reads "Enter 255 characters or fewer", naming no field, so this page alone
     among the service's address forms would stop telling the trader which
     field is too long, and it is not the wording the row's note says to reuse.
   The six **required** messages are this page's own: their rule differs (it
   fires on the new-address choice, not on a field being present) and three of
   the six are worded differently from the party-edit page's, so all six live in
   this feature's copy, English and Welsh. A departure note for the over-long
   wording's home is recorded in section 14.
4. **Address line 2 and county.** Criterion 1 says they "save with any value or
   none"; V4 caps them. Settled: the criterion is about required-ness, so both
   stay optional and both go through the owner's optional-with-cap rule, which
   already carries V4's limit and that field's own over-long message. Rejected:
   no cap at all, which would make this the one address form in the service
   without V4's limits.
5. **No format checks.** Email, phone and postcode are checked for being blank
   and for length only, so the email field goes through the owner's
   required-with-cap rule rather than its email rule (`address-rules.js:79-83`,
   which this page does not use). Rejected: keeping the party-edit page's email
   format check — the design source sets no format rule for any address field
   and V4's Validation column states none (`prototype:dr2-1-source p9-061`,
   `prototype:dr2-1-specs p3-105`).
6. **The animal's name appears only in the error summary.** The message on the
   field is the plain field message; the summary entry joins that same message
   to the card's title through one copy function, so each sentence has a single
   source. Rejected: a second, animal-named set of messages in copy.
7. **The place-of-destination refusal names no animal**, in the summary or on
   the radios, following `prototype:dr2-1-source p9-053` and
   `trace:prototype-dr2-1 p7-096` and criterion 3's own wording, even though
   the address messages do name it. Rejected: naming the animal for internal
   consistency — that would depart from the design source. Raised as a
   question for the designer in section 7 instead.
8. **Who answers "does the notification have a place of destination".** The
   controller resolves the display party once per request through
   `features/addresses/frozen-parties.js:19`, whose contract already is "the
   party, or nothing when it has no name", and passes it both to the card
   builder and to the save rules. Rejected: a second truthiness test on the
   stored answer inside the rules module — two owners for one question.
9. **The summary's order and links come from the built cards**, walked in card
   order and then in each card's own field order, so the page keeps one source
   for which fields a card shows and in what order (`cards.js:17`). Rejected: a
   second field-order list inside the summary builder.
10. **The summary goes through the existing summary mechanism.**
    `shared/kit.js:115` already turns a key-to-text map into a titled summary
    whose entries link to the in-page anchor of each key, which is exactly what
    this page needs once the text is the animal-named one. The new module
    therefore owns the ordered map, not a second summary builder. Rejected:
    copying the sibling page's bespoke summary builder
    (`features/commodities/animal-identification/card/error-summary.js`), which
    exists only because that page mixes field anchors with card anchors.
11. **The empty state replaces only the cards.** The caption, heading, fraud
    warning and the save control all stay: the design source puts the warning
    above the cards (`prototype:dr2-1-source p9-034`) and keeps the save
    controls in the empty state, where the save writes nothing (`p9-066`). The
    source does not show whether the warning is suppressed, so section 7 asks
    the designer.
12. **The empty state's words and link are built exactly as set**, with
    "consignment details" linking to the consignment details page
    (`prototype:dr2-1-source p9-065`). In this service a card comes from an
    animal identifier record, not from the animal count, so a trader who has
    given a count but added no record is sent to a page they have already
    answered. Settled: build the copy as the design source sets it — a
    commodity line can exist before consignment details is answered, so the
    source's state is reachable here too — and raise the other sub-state as a
    design question (section 7). Rejected: rewording the message or pointing
    the link at the animal identification page, which would be the plan
    inventing copy.
13. **The skip stays, beside the new empty state.** A consignment where no
    commodity line needs a permanent address keeps today's redirect and its one
    info log (`controller.js:70-89`); the empty state is a second, separate
    branch for a line that needs one with no identifier record yet. Today one
    condition serves both. Rejected: dropping the skip — the consignment
    addresses page offers no permanent address section at all in that case, so
    the page would become reachable only by typing its address.
14. **The place-of-destination warn goes.** With the refusal in place, the state
    `controller.js:91-112` reports cannot be reached, so the branch and its log
    are deleted and the refusal takes over the logging.
15. **Criterion 6's second half needs no production change.** The county parish
    holding and contact address pages already answer a refusal with the
    bad-request status (pinned by their own controller tests) and already pass a
    summary to their views, which is what drives the title prefix at
    `shared/layout.njk:18`. Only the title half is unpinned, so each page's
    existing error-state feature test gains the title assertion. Rejected: a
    new spec requirement for them — `live-animals/page-titles`
    REQ-PAGE-TITLE-002 already states it.
16. **The refused page's Back behaviour is proved through the shared helper**
    already in the journey's test support
    (`sets/live-animals/journeys/linear/test-support.js:92-110`), not a local
    copy.
17. **The shared card-answering helper is used as it stands.** A blank new
    address is driven through `fit/live-animals-journey.js:978-1006` unchanged:
    `:983` tests `if (!newAddress)`, so an empty address object takes the
    new-address path, checks "Enter a new address" at `:989` and fills nothing,
    because `:1001-1005` fills a field only when it has a value. Rejected: the
    earlier plan's edit to that helper and its doc comment — the helper and its
    contract already cover what entries 11, 13 and 14 need, and
    `.claude/rules/code-quality.md`, Structure, says "Build only what this
    change makes reachable". Also rejected: a local copy of the helper inside
    this page's feature spec.
