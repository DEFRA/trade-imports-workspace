## 0. Decisions

1. **What decides "one address" versus the count line.** The section shows one address when every
   addressable animal is saved against the place of destination, or when exactly one animal needs a
   permanent address; otherwise it shows the one count line. The branch is read from each animal's
   stored choice and from how many animals need one — never by comparing two saved addresses for
   equality. That is the prototype's own branch (all-same-as-destination, else exactly one saved
   address, else the count), and it keeps the section stable when a trader edits the place of
   destination afterwards. Rejected: comparing address values, which would flip the section between
   the two shapes on an unrelated edit and has no source behind it.
2. **The section still shows nothing until every animal that needs one has an address.** Today's
   gate on the section's read-back (every addressable animal has a saved address carrying a name,
   `addresses/controller.js:92-94`) stays, so a part-answered section keeps offering to add one. With
   that gate in place, the increment's "only one animal has an address" case can only mean "exactly one
   animal needs one". Rejected: showing the one address as soon as a single animal has one, which would
   contradict inc-054's already-built behaviour that a part-answered section reads as incomplete.
3. **Which address is shown in the all-at-the-place-of-destination case.** The first addressable
   animal's saved address. Every animal in that branch holds its own copy of the place of destination,
   so they are the same address unless the place of destination changed between two saves; the branch
   is defined by the stored choice, so the first copy is what shows. Risk recorded below.
4. **The count line only ever counts two or more animals.** One animal falls into the one-address
   branch, so the count line needs no singular form. Rejected: a singular/plural copy function, which
   would build an unreachable branch.
5. **Where the review's per-animal rows live: the existing roles-and-addresses card.** They join that
   card's row list in the consignment parties section, after the county parish holding row. The design
   source puts them there: the prototype's review adds the permanent address to its Addresses card
   rather than to a card of its own (`prototype:dr2-1-source` claim `p9-079`, `app/routes.js:2709-2739`,
   and claim `p11-111`, `app/routes.js:5141-5147` with
   `app/views/partials/design-release-2.1/review-summary-card.html:52-61`, quoting
   `title: 'Permanent address', rows: buildPermanentAddressReviewRows(sessionData)`), and it matches the
   consignment addresses page's own section order (parties, county parish holding, permanent address).
   Rejected: a card of their own. The review's card registry maps each card to the task rows whose
   answers it shows, for its anchor and its "complete this card" message
   (`check-answers/view-model/incomplete-cards.js:14-53`); the permanent address's completeness belongs
   to the species card, because the `permanentAddress` obligation sits within the animal identifier
   record (`obligations/sections/commodities/identifiers.js:141-147`, `within: unitRecord`,
   `status: 'mandatory'`) and the `animalIdentification` task row owns that collection
   (`journeys/linear/flow/task-rows.js:54-59`), which `incomplete-cards.js:22-26` and `:57-63` attribute to the
   species card. A second registry entry for the permanent address would therefore either duplicate or
   mis-attribute that message, and a card outside the registry would get no anchor and no error
   decoration.
6. **A row is built only for an animal that has a saved permanent address.** This settles the collision
   decision 5 leaves: the card that shows the answer is not the card that owes it. The written rule
   ties the two together — `sets/live-animals/docs/page-design.md:85-90` ("A blank answer on a finished
   card reads \"Not applicable\" ... On a card that still owes answers, every blank cell, required or
   not, has no visible text and no flag, and \"Missing\" is announced only to a screen reader") and
   `:91-92` ("Every task row belongs to exactly one card, so \"no unfinished card\" and
   `readyForCheckYourAnswers` give the same verdict"). The roles-and-addresses card's completeness comes
   from the `addresses` task row alone (`incomplete-cards.js:47-51`), so it can be finished while a
   permanent address is still mandatory and outstanding; a blank row built through the card's party-row
   rule would then read "Not applicable" (`rows/value-text.js:31` via `rows/party-row.js:47-52`) for an
   answer the trader must still give, and `blankEmptyValues` (`incomplete-cards.js:96-107`) cannot
   correct it because it only fires on a card carrying an error. Building no row for an unanswered
   animal keeps both halves of the rule intact: no blank cell exists to read the wrong thing, no task row
   gains a second card, and the outstanding answer stays marked where it is owed — the species card's red
   border and "Complete ..." line, which `:85-90` names as the only visible marking on a card that still
   owes answers. Rejected: a blank row reading "Not applicable", which the rule forbids for a required
   outstanding answer; rejected: adding `animalIdentification` to the roles-and-addresses card's registry
   rows, which breaks `:91-92`; rejected: moving the rows onto the species card, which contradicts the
   design source cited in decision 5. The design source shows no empty case at all (it falls back to a
   notification-level address, which this service does not have — decision 8), so this is a case the
   design source does not set and it is raised as a design question in section 7. Test 7 pins it.
7. **How an animal's permanent address reads as a review row.** Through the review's existing party-row
   rule (`rows/party-row.js:71-78`), so it reads exactly as every other address on that card: the name,
   then each address line, the country, the phone and the email. The prototype's review shows no phone or
   email on any address, including its other parties, so that is a service-wide difference and not
   something this row's criteria state. Rejected: stripping phone and email for the permanent address
   alone, which would give the review two formats for one thing. Raised as a follow-up for the designer
   instead.
8. **The row label.** The species' common name as the notification stored it, plus the animal's number,
   through the label rule the permanent address page already uses
   (`commodities/animal-identification/animal-label.js:7-10`, which falls back to the plain
   animal-and-number form when a species has no common name). The casing is whatever the reference data
   serves, never reworded in code — the programme's standing rule on reference-list content. The
   increment's example "Domestic dog 1" is the prototype's casing, not a copy decision.
9. **Criterion 4 is not built: it names behaviour this service does not have.** The prototype keeps a
   notification-level permanent address and falls back to it, keyed "Address", when it counts no
   animals needing one (`prototype:dr2-1-source` claim `p9-080`, `app/routes.js:2723-2728`). This
   service stores a permanent address only on an animal's identifier record, so with no animal counted
   there is no address to show and no row. The review also deliberately avoids "Address" as a row key
   (`page-design.md:83-84`: the contact address row is keyed "Contact address", not "Address", because
   the page lists several addresses). The state itself is reachable — a line that needs a permanent
   address with its animal count given and identification unanswered holds no identifier records, which
   the permanent address page already handles
   (`permanent-address/permanent-address.fit.spec.js:499-540`) — so what the review's card holds in that
   state is pinned by test 8 rather than left unasserted. Nothing is built for the prototype's "Address"
   fallback.
10. **The review's permanent address column goes in the same change.** Today the review would show an
    animal's permanent address twice over once these rows land: as a "Permanent address" column on the
    species card's identifier table
    (`check-answers/view-model/cards/consignment/species/identifier-columns.js:21-23`) and as the new
    rows. The design source's review identification table carries identifier columns only (prototype
    trace: Animal, Microchip, Passport, Tattoo), and this increment is where the review's display of the
    permanent address is decided — inc-057's notes say that column is outside its own criteria. So the
    column goes here. `REQ-CYA-016` already describes identifier columns alone, so removing the column
    makes the code match a spec it currently exceeds. It also removes a standing breach of
    `page-design.md:85-90`: the column's cell is a plain table cell, so an unanswered animal on a line
    where another animal is answered reads "Not applicable" today
    (`identifier-cell.js:4-7` through `rows/value-text.js:16-24`) on a species card that is still
    unfinished, which the rule forbids.
11. **Where the display shape is resolved: the review's own controller, where the parties already are.**
    A permanent address is stored with a country code and both pages must show a country name, which is
    an async reference-data read. The consignment addresses page already does that work in its GET
    handler before it builds its sections (`addresses/controller.js:120`, awaiting
    `partiesFromStoredAnswers`), so the read-back is awaited there and handed to the sections builder,
    which stays synchronous. The review has the same shape one level up: `renderNotificationView` awaits
    `partiesFromStoredAnswers` (`check-answers/controller.js:176`) and threads the resolved parties
    through `renderCya` (`:97`) and `buildSections` (`view-model/index.js:16`) into the section
    (`sections/consignment-parties.js:8-17`) and the card
    (`cards/addresses/roles-and-addresses.js:30-38`). The permanent address read-back takes exactly that
    route, so no section and no card changes from synchronous to async. Rejected: resolving inside the
    card builder. The card builders are not synchronous by design — `cards/consignment/import-details.js:12`
    is `async` and resolves a country name itself at `:31`, and `sections/about-consignment.js:9` awaits
    it at `:22` — but that shape is for a card that reads its own answers, whereas a stored address
    becomes display shape in one place for this page already, and resolving the permanent address inside
    the card would give that one display rule two owners, the resolved parties arriving ready while the
    permanent addresses resolved themselves. Rejected also: making the addresses page's whole sections
    pipeline async, which the page does not need because its GET handler already awaits.
12. **No plants change.** The programme invariant pairs a change with the high-risk plants frontend
    only where plants has the same page or behaviour. Plants has no permanent address at all
    (`grep -rln "permanentAddress\|Permanent address" repos/trade-imports-plants-frontend/src` finds
    nothing), so there is nothing to mirror. Matches the row's own `repos` list.
13. **No backend change.** The permanent address is already stored on the animal identifier record and
    already mapped; this increment only reads it back.
14. **Where the cross-page review proof lives in the tests repo.** In
    `tests/animals/e2e/features/hub-groups-and-cya-rows.spec.ts`, the feature spec that already walks
    the journey to the review through `toReview` and asserts the roles-and-addresses card's rows. The
    tests repo reserves `tests/animals/e2e/pages/` for single-page tests
    (`tests/animals/e2e/pages/README.md:7`) and `tests/animals/e2e/journeys/` for complete flows
    (`tests/animals/e2e/journeys/README.md:7`); a targeted check of what one card shows after a walk is
    neither, and `features/README.md:7` covers exactly that ("a feature test focuses on validating
    individual components or isolated features in a targeted way"). Rejected: adding it to
    `pages/permanent-address.spec.ts`, which would put a walk to a different page's view model inside a
    single-page spec. That spec's own change stays within its page's scope: one assertion about what the
    consignment addresses page's inset now holds. Its describe block is tagged
    `@duplicated-in-frontend`, which `repos/trade-imports-ins-tests/README.md:336` defines as marking an
    end-to-end spec whose behaviour the frontend's FIT suite also proves, so the review rows gain a FIT
    case of their own (test 13) and the tag stays true.
15. **Welsh: one new string only.** The only new English string is the count line, so that is the only
    new Welsh draft (decision 16's home). The review row labels need none: they come from
    `animal-label.js:7-10` through the identification copy group's label rules, which are already
    present in both locales and interpolate the species name rather than translating it
    (`commodities/copy/copy.en.js:92-93` and `commodities/copy/copy.cy.js:96-97`). The species common
    name itself is reference-data content, which the programme forbids editing in code, so no Welsh
    string is invented for it. Criterion 5's review-labels half therefore needs no work, and the
    copy-parity check in section 5 speaks only for the one string the change adds.
16. **The count line's copy home.** The permanent address section's own copy group in the consignment
    addresses feature (`addresses/copy/copy.en.js:15-23`, `copy.cy.js:16-24`), beside its title, lead-in,
    bullets and add link, under the Welsh file's existing machine-draft marker (`copy.cy.js:1`).

## 3. New files

**`src/server/app/sets/live-animals/journeys/linear/features/permanent-address/<read-back>.js`**
(name the implementor's, in the permanent address feature folder beside `cards.js` and `summary.js`).

Owns one thing: the saved permanent addresses of the animals that need one, read back for display —
for each addressable animal in line and animal order, its label (species common name and number), the
choice it was saved with, and its saved address in the display shape the journey renders (country name
resolved). It is async, because resolving a country name is a reference-data read.

It is not part of `cards.js`, which owns the page's own form cards (options, revealed fields, field
errors); it is not part of `addresses/controller.js` or the review's card, because both of those read
it and neither may own it. It goes through the mechanisms that exist: the addressable-animals rule
(`cards.js:42-53`), the stored-choice rule (`cards.js:95-99`, newly exported), the stored-party display
shape (`addresses/frozen-parties.js:19-37`) and the animal label rule
(`commodities/animal-identification/animal-label.js:7-10`). Structure to follow: `summary.js` in the
same folder (`permanent-address/summary.js:13`), the shape that feature folder already gives a read —
one export, nothing held at module scope.

A colocated unit test file for it is not added: its behaviour is proved through the two pages that
render it (section 4), which is where the increment's criteria are observable.
