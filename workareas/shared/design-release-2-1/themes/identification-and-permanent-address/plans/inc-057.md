## 0. Decisions

**D1 — Most of what the row describes has already gone; only the table column
is left.** The row's detail and its 27 Oct notes say the card still carries a
fraud warning, a permanent-address definition, the question and eight address
fields, validates them all-or-nothing and stores the address on each animal.
None of that is true on this branch's HEAD. Verified against the live tree:

- `_identification-card.njk` holds the identifier inputs, the card's save
  button and the saved-animals table and nothing else (whole file, 52 lines);
- `card/view-model.js` builds no address block (`buildCard`, lines 76-109);
- `form/forms.js` validates only the species' scoped identifier fields
  (`buildLineForm`, lines 33-52, via `identifierChecksFor`);
- `records/append.js:9` stores the form's identifier values alone, and
  `src/server/app/contract.test.js:314` already asserts a unit saved on this
  page carries no permanent address.

What remains is the **'Permanent address' column of the saved-animals table**:
`identifier/table.js:19-22` appends it when the species needs one and
`identifier/table.js:24-25` fills it from the unit's stored address. That, its
two copy keys and the gate predicate the column shares with the permanent
address page are this increment's whole production change. Recorded as a defect
in the row's detail and notes; planned against reality.
Alternative rejected: treating the detail as current and planning the removal of
the block, validation and storage — it would plan edits to code that does not
exist.

**D2 — Stale line references in the notes.** The notes' 27 Oct line numbers
(`_identification-card.njk:33-57`, `card/view-model.js:99,122-129`,
`form/forms.js:40-56`, `records/append.js:12`, `copy/copy.en.js:78` for the
column heading, `copy/copy.en.js:90` for the fraud warning) do not point at
permanent-address code on this HEAD; the column heading is at
`copy/copy.en.js:85` and there is no fraud-warning key in the commodities copy
at all. Treated as hints only.

**D3 — The notes' claim about the review page is wrong too.** The notes say the
review's identifier table reads the unit's permanent address at
`check-answers/view-model/cards/consignment/species/identifier-columns.js:17-18`.
It does not: that file maps the species' scoped identifier fields only (whole
file, 14 lines), and `page-design.md:92` already records that the review's
species card carries no permanent address column. No edit there.

**D4 — The dependency the notes guard against has landed.** The row must not
land before the permanent address page exists. It does:
`features/permanent-address/` holds the page, its copy, its validation and its
write, it is wired in `features/index.js:15,41,64`, and its own FIT spec covers
it. So the service keeps capturing the address after this removal.

**D5 — The gate predicate moves to the feature that owns the question.**
`identifier/fields.js:19` and `:21-22` hold the permanent-address obligation
name and the predicate that asks whether a commodity-and-species pair needs one.
After the column goes, the only caller is `permanent-address/cards.js:36,44`.
The row's whole point is that the permanent address stops being the
identification page's business, so the predicate goes to `cards.js`, where it
becomes module-private beside the two functions that call it. The exemplar for a
feature-local applicability predicate over `appliesForGateValue` is
`check-answers/view-model/applicability.js:1-6`.
This changes one caller's import line, which the row needs rather than tidies:
leaving it where it is keeps the identification feature owning a
permanent-address rule.
Alternative rejected: a new `permanent-address/applicability.js` — nothing
outside `cards.js` needs it, so a new file and a new export would be reach the
row does not create.

**D6 — `identifier/table.js` stays.** Once the column goes, its two exports are
thin, but it is the home `animal-identification.controller.js:32` re-exports the
identifier labels from and `check-answers/.../identifier-columns.js:3` imports
through. Folding it away would change callers outside the row's footprint.

**D7 — The evaluation bindings stay in the commodities feature.**
`commodities/evaluation.js:61-62` binds the permanent address and its origin as
leaves of the unit record, inside the line-and-unit grouping that
`commodities/evaluation.js:22-38` owns. Moving those two leaves to a
permanent-address feature group would copy the line and unit group descriptors
into a second module — a second mechanism beside one that exists. No criterion
touches the bindings. Left alone; noted as a follow-up.

**D8 — Criterion 2 is proved with a ferret, not a dog.** The row asks for "a dog
or a ferret". The frontend's FIT fixtures carry a ferret row
(`commodities/search/test-support.js:73-77`) and no `Canis familiaris` row, and
the tests repo's commodity lines carry neither (its `raccoonDog` is
`Nyctereutes procyonoides`, which is not on the permanent-address list at
`services/commodities/rules.js:91-96`). The existing ferret FIT test
(`identification.fit.spec.js:922-942`) is extended rather than a dog fixture
invented. The dog is still covered at unit level by the matrix row at
`animal-identification.controller.test.js:1069-1079`.
Alternative rejected: adding a dog species to the tests repo's commodity lines —
it would need the stack's reference data to serve it, which no criterion asks
for.

**D9 — Criterion 4 holds today; it needs a test, not a fix.** Saving another
animal appends to the line's unit list (`engine/write/entries/mutate.js:7-23`)
and removing one splices it (`:51-69`); neither rewrites a surviving unit, and
the identification page collects no obligation
(`animal-identification.controller.js:35`), so nothing wipes a stored address.
The criterion is the regression this removal risks, so it gets both a FIT round
trip and an end-to-end leg.

**D10 — Four removal-by-absence assertions in files this change touches are
fixed, and the titles that name a removal with them.**
`identification.fit.spec.js:287-295` proves the address block gone by counting
text and a field at zero, and its test's own title names that absence;
`identification.fit.spec.js:241` counts the address field at zero inside the
per-commodity matrix test; the tests repo's
`animal-identifiers-conditional.spec.ts:20-23` does the same with four
`toHaveCount(0)` label checks under a title that ends "with no address field"
(`:7`); and `animal-identification.controller.test.js:535` names a removal in
its title. Each absence is replaced by an exact positive assertion of what the
card and its table hold now, and each title is restated as what its assertions
then prove. These are lines the change touches, so they are in scope. The two
remaining absence assertions in the matrix test (`:237-240`) stay: they prove
the conditional-identifier behaviour REQ-IDENT-006 states, not a removal.

**D11 — Two FIT locators are promoted, and that rewires one file mechanically.**
Test 8 lives in `permanent-address.fit.spec.js` and needs the saved-animals row
and its removal control, which `identification.fit.spec.js` holds as file-local
helpers (lines 111-117 and 167-171). Copying their bodies into a second spec
breaks the shared-helper rule, so both go to `fit/live-animals-journey.js` and
`identification.fit.spec.js` imports them. That changes thirteen call sites in
that file, all of them the same substitution with no change in behaviour; the
shared helper already imports the commodities copy and the species-label
function those locators need (lines 33, 28).
Alternative rejected: locating the row and its button inline in the new test —
the same locator body in two spec files.

**D12 — The cat-line-of-two walk gets one named home in the permanent-address
spec, and the shared microchip step gains the option it needs.** Test 8 needs a
cat line of two whose first animal is saved by its identifiers and whose second
is still outstanding, so that the second can be saved on Identification details
afterwards. `permanent-address.fit.spec.js`'s existing file-local set-up
(`fillOneCatAndOneFerretIdentifiers`, lines 39-46, and its callers at 63-66)
cannot produce that state: it declares one cat and one ferret and fills both
microchips. The only existing walk of that shape is written inline inside the
three-cards test at `permanent-address.fit.spec.js:343-350`. Both users of the
walk sit in that one spec file, so its home is one named set-up function at the
top of that file, beside the set-ups its other tests already share, and the
three-cards test's inline block is replaced by a call to it.
`docs/best-practices/node/testing/frontend.md:171` reserves the set's journey
helper for a sequence of page steps two *specs* share, which this is not.
Alternatives rejected: copying the inline block into test 8 — two copies of one
walk in one file, which is the breach the review raised; and putting the walk in
`fit/live-animals-journey.js` — no second spec needs it, so it would widen the
shared helper's surface for one caller.
The set-up must save the first cat while the line still has an animal
outstanding, which the shared microchip step cannot do today: it finishes the
line on the last microchip it is given (`fit/live-animals-journey.js:885-898`).
Per `docs/best-practices/node/testing/frontend.md:95` ("extend the helper with
an option rather than writing a local copy of its body") that step gains an
option saying the line keeps animals outstanding, so its last record saves
through the save-and-add-another control instead of save-and-finish. Both
existing callers pass a whole line (`permanent-address.fit.spec.js:350`,
`check-answers.fit.spec.js:136`) and are unchanged.

**D13 — Which control reopens the permanent address page in test 8.** The
consignment addresses page offers the permanent-address section's Change link
only while every addressable animal is answered, and its Add link otherwise
(`addresses/controller.js:117-130`). So with the second cat saved and
unanswered the section offers the Add link again, and once that cat is removed
the Change link returns. Test 8's first reopen therefore goes through the Add
link (the shared step at `fit/live-animals-journey.js:980`) and its second
through the section's Change link, as the hub assertion at
`permanent-address.fit.spec.js:311-332` already does. Recorded so the
implementor does not read the Add link's reappearance as a defect of this row.

**D14 — The column list reads each identifier's label from the one place that
owns it.** `identifier/fields.js:13-17` already gives every scoped field its
label from `copy.identification.identifierLabels`, and
`identifier/table.js:14-18` looks the same label up a second time through
`IDENTIFIER_LABELS`. With the conditional branch gone (D1) that second lookup is
the whole of the surviving function's extra work, leaving one rule — which label
an identifier column shows — with two owners inside the one function this change
edits. The column list takes the label its input already carries.
`IDENTIFIER_LABELS` stays exported: `animal-identification.controller.js:32`
re-exports it and `check-answers/.../identifier-columns.js:3,14` reads it
through that re-export, which section 7 carries as a follow-up rather than
widening this row.
Alternative rejected: leaving the second lookup because the lines "already read
that way" — they are lines this change edits, so they meet the rules in full.
