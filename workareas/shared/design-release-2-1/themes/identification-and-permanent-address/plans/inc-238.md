## 0. Decisions

- **AC1 (the hardcoded green).** Read the comparator colour at run time from the journey's own primary save control, `saveAndContinue(page)` (already rendered on the same page, already imported in the spec), rather than inventing a new "read GOV.UK's design token" helper. The codebase's one existing idiom for reading a GOV.UK colour live — `measureReferenceElement`/`govukColourOf`, local to `type-ahead.fit.spec.js`, reading the CSS custom property `--govuk-{token}-colour` off a synthetic reference element — was considered and rejected: promoting it would touch a second, unrelated feature file for no need the row has, and inspecting the installed `govuk-frontend@6.5.1` CSS shows `.govuk-button{background-color:#0f7a52}` is a literal hex, not `var(--govuk-success-colour)` — so `govukColourOf(page, 'success')` would read a design token that only coincidentally matches the button's colour today, one hop further from what the test actually means ("this card button is styled as a primary button, like every other save control"). Comparing directly to the live `saveAndContinue` button proves that claim more directly, with no footprint outside this one file.
- **AC2 (finding the save controls by role).** Use `expectThreeSaveControls`, already exported from the shared journey helper `fit/live-animals-journey.js:1379` and already used by this identification page's own sibling pages in the same `commodities` feature folder (`fit/search.fit.spec.js:488`, `fit/consignment-details.fit.spec.js:489`), and documented at `src/server/app/sets/live-animals/docs/add-a-page.md:411-415` as proving "by role inside the journey form" that the primary, the hub-exit secondary and the cancel link appear in that order. The row's note that "there is no shared save-controls step anywhere under `src/server/app/shared`" is true of that one directory but does not name the step that already exists one level up, in the repo's root `fit/` folder — that is the mechanism to extend, not a gap to fill with a new one.
- The identification page's save-actions block renders through the shared macro's defaults (`saveActions({ hubHref: hubHref, copy: sharedCopy.saveActions })`, `animal-identification.njk:41`, no `primary`/`secondary`/`showReturnControls` override), so it renders exactly the three-control bundle `expectThreeSaveControls` checks — the same bundle every other default-styled journey page renders.
- Dropping the `.govuk-button-group` CSS-class locator is not a separate clean-up decision beyond the row: AC2 directly asks for it ("by role"), and `docs/best-practices/playwright/BEST_PRACTICES.md`'s locators section and "Common review flags" table both already name a CSS class selector as a defect to fix.
- `expectThreeSaveControls`'s second assertion (the form's last button must be "Save and return to overview") is a strictly stronger check than the one it replaces (the old test only asserted the literal, hardcoded string `'Save and finish'` had zero matches inside the button-group). No coverage is lost; the replacement catches the same regression — a bespoke primary standing in for the shared one — more robustly and without a literal string duplicating `copy.identification.saveAndFinish`.

### `src/server/app/sets/live-animals/journeys/linear/features/commodities/fit/identification.fit.spec.js`

- **`GOVUK_GREEN` constant (line 43):** delete. Once the one assertion that reads it (below) reads its comparator live instead, the constant is dead.

This is what finds the controls "by role through the shared save-controls step" per acceptance criterion 2.
- **Test `'shows the card button as a primary button'` (lines 1049–1055):** keep the existing `page.getByRole('button', { name: copy.identification.saveAndAddAnother })` locator and keep the `toHaveCSS('background-color', …)` assertion, but source the expected value by reading the live computed `background-color` of `saveAndContinue(page)` (already on the same page, already imported) via Playwright's element `.evaluate()`, instead of the deleted `GOVUK_GREEN` literal. This is what checks the green "against GOV.UK's green read at run time" per acceptance criterion 1 — read from a real rendered GOV.UK primary button on the page under test, not a hardcoded literal and not a second, parallel colour-token mechanism.

No other file changes. No production code in this repo changes.

## 4. Tests

Both are existing tests whose body changes; no new test is added.

1. **`'ends on the same Save and continue as every other journey page'`** (`identification.fit.spec.js:295`) now proves, by role and in document order inside the journey's one `<form>`, that the identification page offers exactly the shared primary ("Save and continue"), the shared hub-exit secondary ("Save and return to overview") and the shared cancel link ("Cancel and return to overview"), with the hub-exit button last in the form. Removing or changing the `saveActions({ hubHref: hubHref, copy: sharedCopy.saveActions })` call at `animal-identification.njk:41` (e.g. giving it a bespoke `primary` or turning off `showReturnControls`) turns it red, since `expectThreeSaveControls` would no longer find all three controls in that order.
2. **`'shows the card button as a primary button'`** (`identification.fit.spec.js:1049`) now proves the card's "Save and add another" button renders with the same live `background-color` as the journey's own "Save and continue" button. Changing the card's button away from the shared default (e.g. adding a `classes` override at `_identification-card.njk:33-37`) turns it red, since the two buttons' computed colours would then differ.

No INTEGRATION PROOF (E2E) is needed: this increment changes only how two already-existing FIT assertions read their expected values and locate their targets. Nothing a user or another system can observe changes.
