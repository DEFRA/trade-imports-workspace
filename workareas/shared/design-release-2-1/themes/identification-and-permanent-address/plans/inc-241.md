## 0. Decisions

1. **The fallback rule is "the commodity declares no identifier type at all", not "none of passport, tattoo,
   ear tag or horse name".** Criterion 2 names four lists; the data specification's own words for both rows are
   "Shown when given commodity does not have a specific identifier type"
   (`workareas/shared/design-release-2-1/sources/6497338582.json`, the Animal Identifier – Identification details
   and Animal Identifier – Description rows). Microchip is a specific identifier type too, and no code in the
   catalogue declares microchip without also declaring passport
   (`src/server/app/sets/live-animals/services/commodities/rules.js:10-29`), so the two readings cannot be told
   apart by any commodity that exists. Rejected: gating on the four named lists, which would add a branch for a
   state the catalogue cannot reach and would contradict the data specification the moment MDM served a
   microchip-only code.

2. **Defect in the row: Atlantic salmon is not a live-animals commodity, and it is not the only fallback
   species.** Criterion 2 and note 4 say "an Atlantic salmon line is such a species today" and "in today's live
   catalogue that is Atlantic salmon alone; poultry and the rest join with the MDM commodity catalogue". Neither
   holds. The catalogue the search serves
   (`src/server/app/services/_capture/fixtures/commodities.json`) carries 26 chapter-01 codes and no fish code;
   `grep -rln "Salmo salar\|Atlantic salmon"` over the frontend, the tests repo and reference-data finds nothing.
   Six of those 26 codes declare identifiers, so **20 codes already fall back today** — ostriches (`01063300`),
   poultry (`01051111` and the rest of `0105…`), rabbits, pheasants, bees and so on. `rules.js:117-128` does
   carry a `0301` "Live fish" / "Fish" description and name, but `0301` is not in the served catalogue, so no fish
   line can be selected. The behaviour the row asks for is unaffected; only its worked example is wrong. Every walk
   in this plan uses ostriches (`01063300`, `Struthio spp.`), which is already a fixture row in both repos
   (`features/commodities/search/test-support.js`, `domain/animals/constants/commodity-lines.ts`), and poultry
   where an existing journey already uses it.

3. **"Every selected species has a panel" keeps today's animal-count rule.** A line with no number of animals
   still gets no panel (`animal-identification/line-cap.js:10` `capAllowsEntry`, which the identification page's
   card list already applies, and `openspec` SCN-IDENT-020-B). Criterion 1's change is that the *commodity's
   identifier list* no longer decides whether a line gets a panel; the declared count still does, because the
   panel's progress heading and its save button are both stated in terms of the count. Rejected: giving a
   countless line a panel, which the row does not ask for and which would need new copy for a panel with no
   counter.

4. **The field labels are "Identification details" and "Description", in that order.** Criteria 3, 5 and 6 quote
   them, and they match how the existing identifier labels are taken from the data specification: every row there
   reads "Animal Identifier – <label>" and the label in the service is the bare second half (Microchip, Passport,
   Tattoo, Ear tag, Horse name — `features/commodities/copy/copy.en.js:76-82`). Rejected: "Animal description",
   which the tests repo's current negative assertion guesses at
   (`tests/animals/e2e/features/animal-identifiers-conditional.spec.ts:56`); nothing in the design source sets it.
   The page's H1 is also "Identification details", so the page title and one of its field labels read the same.
   That is what the design source sets, so it is built as set; the question for the designer is recorded as a
   follow-up in section 7 rather than resolved here.

5. **One owner for "which identifier fields does this line's commodity ask for": the commodity service's
   identifier read.** `services/commodities/index.js:23` `identifiersFor` is already that owner — the entry
   fields, their validation, their blank values, the saved-animals columns and the review's identifier columns all
   reach it through one call (`animal-identification/identifier/fields.js:13` `scopedFields`). It gains the
   fallback: the identifiers a code declares, else the two free-text answers. The fallback pair itself is data and
   is declared in `services/commodities/rules.js` beside `COMMODITY_IDENTIFIERS`. Rejected: a second service read
   for "the fields the page asks for", which would put one rule in two functions; and putting the fallback in
   `scopedFields`, which would split the rule between the service and the feature.

   **What the read answers for a code the captured catalogue does not serve: the same fallback pair.** The function
   is a read over the identifier map alone, so a code absent from the map — unserved as much as served-with-none —
   gets the fallback. That is the answer the obligation gate already gives the same code: `isOutsideUnion`
   (`model/obligations/helper-internals.js:25`) admits any non-blank value that is not on the identified list, an
   unknown code included, so service and gate agree rather than disagreeing on an argument only one of them
   recognises. Rejected: answering nothing for an unserved code, which would need the served catalogue as a second
   list inside the identifier read and would then contradict the gate. A line with **no** commodity code still
   shows no identifier field, because that same gate refuses a blank gate value and `scopedFields` filters by it —
   so nothing renders a fallback field on a line that has chosen nothing.

6. **The panel's scope is a per-unit complement gate over the identified-code list, not a new allow-list.**
   `notInUnionOf` (`src/server/app/model/obligations/helpers/not-in-union-of.js:13`) is the declared dual of
   `allowListed` and already supports the depth-2 projection the five typed identifiers use
   (`gatedParentGroup: unitRecord`); `bridge/applicability.js` `admitsValue` already reads it
   (`model/obligations/helper-internals.js:17`, `COMPLEMENT_GATE_TYPES`), so `scopedFields` needs no change to
   filter by it. The union is `identifiedCommodityCodes()`. Rejected: a hand-maintained list of fallback codes,
   which would drift from `COMMODITY_IDENTIFIERS` on the next MDM catalogue change — the drift
   `services.md:34-37` says the derived lists exist to prevent.

7. **The two answers join the unit record's any-of rule.** `obligations/sections/commodities/identifiers.js:70`
   states that a unit record must carry at least one of the identifiers open to it, as a list of leaf ids. Leaving
   the two out would make the manifest say a fallback unit need carry none of its own answers, and
   `bridge/status/completeness/invariants.js:43` `anyOfLeafCouldApply` reads that list per parent to decide whether
   the collection floor is vacuous, so the list is the model's statement of which answers a record can be asked
   for, not a branch. No page can produce a blank fallback record today (the page refuses a blank card save and
   never appends one), so this changes no outcome a trader can reach; it keeps the declaration true, and the model
   does answer differently for a hand-fed state the evaluator test exercises (section 4, entry 12). Rejected:
   leaving the list as it is.

8. **The record floor is not widened.** `floorAppliesToParent` on the unit record (`identifiers.js:71-73`) stays
   gated on `identifiedCommodityCodes`, so a fallback line is never asked for a record. That is what keeps
   criterion 4's "both optional" true end to end: with the floor standing down for a fallback parent
   (`completeness/invariants.js:67` `floorAskedOfParent`), a fallback-only consignment's Identification details task
   reads Complete with no record saved, and the review stays reachable. Widening the floor would make a
   fallback-only consignment unsubmittable. Rejected accordingly. Note that after decision 7 the floor stands down
   for a fallback parent through `floorAskedOfParent` alone, no longer through an empty any-of set, so the two
   invariant tests that read Complete for such a line stay green by the other mechanism (section 4, entries 18
   and 19).

9. **`needsIdentifying` goes.** Its two callers both stop asking its question: the identification page gives every
   line a panel, and the Overview task row applies as soon as the notification holds a commodity line. Keeping it
   would leave an export nothing reaches, in a file this change edits. Its test case in
   `services/commodities/index.test.js:129-133` goes with it. `identifiedCommodityCodes` stays — the floor, the
   new gate and the copy checks all read it.

10. **The identification page keeps its pass-on guard, on a narrower condition and under a name that predicts
    it.** Today it passes the request on when no line carries an identifier
    (`animal-identification.controller.js:109-121`). The only state left for it is a notification with no commodity
    line at all, which is reachable by address and is already proved to land on What are you importing?
    (`animal-identification.controller.test.js:1138-1151`). The guard stays with that condition and is renamed with
    it (edit 8); the ostrich pass-on behaviour and its tests go. Rejected: deleting the guard, which would render an
    empty page for a notification with nothing chosen.

11. **Check your answers and the submitted view are left alone.** The review's identifier table already reads the
    same `scopedFields` owner (`check-answers/view-model/cards/consignment/species/identifier-columns.js:9`), so a
    filled fallback answer shows there as a column with no edit at all. Per the row's note, how the two answers
    show on the review and the submitted view belongs to the overview-and-review theme, so no review test, copy or
    spec text is written here and no scenario is added to the check-your-answers capability. This is a departure
    from step 5 of the set's add-a-field recipe and is recorded in section 14.

12. **The published GBN-AG payload is untouched.** `outbox/gbnag/TradeProductInstance.java:26-50` names the fields
    it maps, so two more on `AnimalIdentifier` change nothing it sends. The data specification gives the two
    answers no PIMS field.

13. **The blank-card refusal keeps the shared message.** `form/forms.js:105-117` puts the existing
    at-least-one-identifier message on the panel's first field, whichever panel it is. The design source does not
    show that state for a fallback panel, so the shared message is kept rather than a new one invented; the
    question goes to the designer as a follow-up.

## 15. Reachability

Everything this plan builds is reachable the moment it lands: 20 of the 26 codes the captured catalogue serves
declare no identifier, so the panel, its two fields, both length messages, the saved-animals columns, the reopen
round trip, the gate and the two backend fields are all exercised by an ostrich or poultry line a trader can
choose today.

Two things are deliberately **not** built:
- a branch distinguishing a commodity that declares microchip alone from one that declares nothing (decision 1):
  no such code exists, and none is expected before the MDM commodity catalogue lands.
- any change to the record floor for a fallback line (decision 8): the data specification makes both answers
  optional, so no row reaches a mandatory fallback answer.

The two obligation ids added to the unit record's any-of rule (decision 7) are read on every evaluation by
`bridge/status/completeness/invariants.js:43` `anyOfLeafCouldApply`, whose `READABLE_GATE_TYPES` (`:30`) already
accepts the gate they carry; they complete a declaration rather than add an unreachable branch. The state in which
that declaration changes the model's answer — a fallback unit that exists holding neither answer — is not reachable
from the page, which refuses a blank card save; it is proved at the evaluator, which is fed state directly
(section 4, entry 12).
