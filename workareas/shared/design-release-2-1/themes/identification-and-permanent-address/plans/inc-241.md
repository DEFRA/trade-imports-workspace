## 0. Decisions

**D1 — Atlantic salmon is not in the catalogue; the species that falls back today is the ostrich.** Criterion 2 says "an Atlantic salmon line is such a species today", and the row's notes say "In today's live catalogue that is Atlantic salmon alone; poultry and the rest join with the MDM commodity catalogue". Both are wrong against the live tree. The served catalogue (`src/server/app/services/_capture/fixtures/commodities.json`) holds 26 codes, all under chapter 01, none for fish: `0101 0102 0103 010410 010420 01051111 01051200 01051300 01051400 01051500 01059400 01059910 01059920 01059930 01059950 01061410 01061490 01061900 01062000 01063100 01063200 01063300 01063910 01063980 01064100 01064900`. `grep -rni "Salmo salar|Atlantic salmon"` over the frontend, reference-data and stub finds nothing. Twenty of those codes already declare no identifier of their own, poultry (`01051111`) and ostriches (`01063300`) among them, so the fallback is reachable today for most of the catalogue, not one species. The plan builds the rule, not the example, and uses the species the repos already carry for this case — ostriches (`Struthio spp.`, `01063300`) in the frontend's own test rows and the tests repo's `commodityLines.ostrich`, and poultry (`commodityLines.chicken`) in the tests repo's rail walk. Rejected: adding a fish code and Atlantic salmon to the captured catalogue — the row's own notes say it needs no catalogue change, and the catalogue is MDM's.

**D2 — the fallback condition is "the commodity declares no identifier of its own", written once as the two new obligations' gate.** Criterion 2 phrases it as "asks for none of passport, tattoo, ear tag or horse name". `services/commodities/rules.js:10-29` gives the four lists the codes `0102 0101 0103 010410 010420 01061900`, which is exactly `IDENTIFIED_CODES` (`rules.js:63`) — microchip never appears on a code without passport — so for every code the set declares and every code the catalogue serves the two readings agree. The plan gates on the identified-commodity-code list, as `unitRecord.requires.floorAppliesToParent` already does (`obligations/sections/commodities/identifiers.js:72-74`), because it is one flat list, it is the vocabulary the set and its docs already use for this idea, and `deriveUnion` (`model/obligations/helpers/internals/derive-union.js:6-12`) flattens a list of lists one level, so the horse-name list's `[code, species]` pairs would enter a four-list union where `isOutsideUnion`'s identity test can never match them. Rejected: the literal four-list union. If MDM ever serves a commodity with a microchip and nothing else the two readings diverge — section 7 carries that as a question for the data owner.

**D3 — the obligation gate is the one owner of the fallback rule; the panel's field list stays `scopedFields`.** `animal-identification/identifier/fields.js:13-18` already composes "the commodity's identifier names" with "the gate admits this commodity and species" (`bridge/applicability.js:16-22`, which reads a complement gate correctly through `admitsValue`, `model/obligations/helper-internals.js:36-41`). The two new names join that function's candidate list for every line; their gate decides where they show. Rejected: returning the two names from `services/commodities/index.js`'s `identifiersFor` when a commodity's own list is empty — that would put the fallback condition in two places (the service and the obligation gate the model needs anyway), and would make `identifiersFor` return names the commodity does not ask for.

**D4 — `needsIdentifying` goes; the task row's applicability comes from the same owner.** With the fallback, every commodity line with a code is asked for at least one identifier field, so a per-line predicate over the identified-code list (`services/commodities/index.js:42-43`) can never be false for a real line and mispredicts its name. The controller stops filtering card lines by it (`animal-identification.controller.js:41-47`), and `task-rows.js:22-25` answers "does any commodity line ask for an identifier field" from the panel's field owner instead. The row's Not-applicable state stays reachable: a notification with no commodity line (`flow/status.test.js` already pins it for `{}` and `{countryOfOrigin}`).

**D5 — the page keeps its skip, for the one state that still reaches it.** `noIdentifiersTarget` (`animal-identification.controller.js:109-121`) stays reachable only for a notification with no commodity line, which `animal-identification.controller.test.js:1137-1147` already drives by direct request and which lands on commodity selection, not additional details. The branch and its single log stay; what the log says is now untrue (nothing on the consignment "carries an identifier" becomes "there is no commodity line to identify") and is restated in section 13.

**D6 — the record floor is left where it is.** `unitRecord.requires.floorAppliesToParent` keeps the identified-code list, so a fallback line is never asked for a record at all, which is what criterion 4's optionality requires. The two new leaves do join `requires.anyOfIds`, so a record that exists on a fallback line must carry one of them — the same rule `withEmptyFormGuard` (`form/forms.js:105-116`) already enforces on the page. Nothing else changes: `emptyCollectionSatisfiesFloor` (`bridge/status/completeness/invariants.js:86-102`) stands the floor down for a parent outside `floorAppliesToParent`'s decision before it ever asks whether a leaf could apply.

**D7 — check your answers and the submitted view need no work.** `check-answers/view-model/cards/consignment/species/identifier-columns.js:4-11` reads the same panel field owner and keeps only the columns some saved animal filled in, so the two answers appear there by themselves once filled, and `openspec/specs/live-animals/journey-pages/check-your-answers/spec.md:365-373` already states that generically. The row's notes put the review's identifier columns in the overview-and-review theme; nothing is built for them here, and nothing needs to be. `permanent-address/cards.js:56-59` reads the same owner, and a permanent address applies only to cat, dog and ferret lines under `01061900`, a code that declares its own identifiers, so the fallback fields and a permanent address never meet.

**D8 — the plants invariant does not fire.** The programme invariant about mirroring a change into the high-risk plants frontend applies "where a row changes a page or behaviour the plants frontend also has". Plants has `features/identification-numbers`, a page of four fixed consignment-level numbers (`identification-numbers/fields.js:1-7`), with no per-animal record, no commodity-driven field list and no fallback. There is nothing to mirror, and plants is not in the row's repos.

**D9 — the blank-record message and the field label are built as they stand and raised with the designer, not changed.** Two design questions fall out, both recorded in section 7 and neither fixed here: the field label the data specification sets, "Identification details", is word for word the page's own H1 (`copy.en.js:68`); and a blank fallback panel refused on its own save control shows the shared message "Enter at least one identifier for this animal" (`copy.en.js:105`) on a panel that asks for identification details and a description rather than an identifier. The design source sets both, so the code follows it.

**D10 — criterion 1's summary half is already true.** `animal-identification.controller.js:61-63` passes every commodity line to `buildSelectedCommodities`, and `animal-identification.controller.test.js:1072-1092` pins an ostrich line listed in the summary with no card. Only the panel half of criterion 1 is new work. The claim in the row's detail — a line such as that one "is listed in the 'Selected commodities' summary but gets no panel and no fields" — holds exactly.

**D11 — the row's note about `COMMODITY_IDENTIFIERS` is wrong and immaterial.** It says the map "carries only 0102, 0101 and 01061900"; `rules.js:10-29` also carries `0103`, `010410` and `010420`. All six declare identifiers, so all six are outside the fallback either way.

**D12 — criterion 8's reopen is already carried by the fulfilment envelope; the backend field is for the notification projection.** The page reads its answers back from canonical fulfilment, which is encoded by obligation id (`services/persistence/records/fulfilment-codec/encode.js:19-42`), so the two answers survive a reopen as soon as their obligations exist. What does not survive without more work is the notification document: `notification-mapper/shared/lines/from-fulfilment.js:4-11` enumerates animal-identifier obligations by a fixed key list and derives each unit's fulfilment index from them, so a record holding only the two new answers would vanish from the projection, and `AnimalIdentifier.java:15-20` has no field to hold them. Both are in scope here. The published GBN-AG payload (`backend TradeProductInstance.identifiersOf`) is not: the data specification gives the two answers no PIMS field, and the notification-record area owns publishing.
