## 0. Decisions

**D1 — the row's own note names the wrong layer for the Enter proof it claims exists.** The notes say "`identification.fit.spec.js` carries a passing test that Enter in an ear tag field saves the card and keeps the trader on the page with the saved row listed." `grep -n "Enter" .../fit/identification.fit.spec.js` returns nothing: no test in that file presses Enter or posts `action: "implicit-submit"`. The real proof is two layers away from where the note puts it: a unit test, `animal-identification.controller.test.js:779-800` ("Should save the value typed into a multi-animal line after its existing records and stay on identification details"), which posts the action value directly rather than pressing a key; and a genuine browser-level proof, `tests/animals/e2e/pages/animal-identification.spec.ts:116-127` ("saves the card typed in when Enter is pressed in its field and stays on Identification details"), which does press Enter. `openspec/coverage/.../identification-details/coverage.json`'s `SCN-IDENT-021-C` already links both and reads `"coverage": "full"`. Criterion 1 is therefore already proved — correctly, just not where the note says — and needs no new test.

**D2 — the row's own open question is already answered by the built and spec'd design; this plan does not reopen it.** The open question asks whether Enter should save only the pressed panel (criterion 1's wording) or every panel holding a typed value (EUDPA-734's commit message). `openspec/specs/.../identification-details/spec.md:359-361` (`REQ-IDENT-021`) already states the second reading as intended, built behaviour: "The system MUST, when Enter is pressed, validate and save every species form holding a value." `form/forms.js:59-67` (`linesToReadFormsFor`) implements exactly that — for `implicit-submit` it reads every line, not only one. The two readings agree whenever only one panel holds a typed value, which is every scenario this row's four criteria describe. This plan tests only that case and changes nothing for the many-panels-typed-into case; the open question stays open, left for whoever the row's notes already point it at (inc-224's branch).

**D3 — criterion 2's cross-panel preservation is a real, untested gap; close it with one new behaviour, not a code change.** No test at any layer — unit, FIT or e2e — exercises Enter in a panel that already holds a saved animal, with another panel that already holds a saved animal of its own, and checks both tables afterwards. Every existing Enter test starts a line at zero saved animals. Reading the renderer settles whether this already holds: `card/view-model.js:79` (`buildCard`) takes `units` from `entry.animalIdentifiers` — the full, persisted answer for that line — not from the posted form, and `records/append.js:17-34` (`appendLineRecords`) appends a record only for a line whose own form `holdsData` (`:20`), skipping every other line untouched. Both lines already behave correctly; the gap is proof, not production code. Add one FIT test and one e2e test (D7 below says why both).

**D4 — criterion 3 (Tab order) has no test anywhere; the DOM already satisfies it.** `_identification-card.njk` renders, inside one `<section>` per card: the fields (`:21-30`), then the card's own save button (`:32-38`), then that card's own saved-animals table with its Remove buttons (`:48`, rendered by `remove-action-button.js:7-15` as ordinary `<button type="submit">` elements). The page's one hidden default-submit button (`animal-identification.njk:32`, via `shared/save-actions.njk:13-15`) sits ahead of every card and carries `tabindex="-1"`, so it is never a Tab stop. Nothing in the page moves a later card's elements ahead of an earlier card's own save button and Remove buttons. The mechanism already matches the criterion; add one new FIT test, no production change.

**D5 — Tab-order proof is FIT-only, matching the one precedent in this codebase.** `grep -rn "press('Tab')" repos/trade-imports-ins-tests/tests` returns nothing: no e2e spec anywhere walks Tab order. The one existing Tab-order test in either repo, `transporters.fit.spec.js:785-797` ("is reached by Tab after the search box and its button, before the first transporter"), lives in FIT. Follow that precedent rather than starting a first e2e Tab-order test.

**D6 — criterion 4 already has its test; no change.** `identification.fit.spec.js:1066-1073` ("has no serious or critical axe violations once an animal is saved") opens a Felis catus panel declared for two animals, saves one through `addFelisCatusRecordRow`, and asserts no serious or critical violations — exactly "a species panel open and animals saved in it." No new test, no production change.

**D7 — the new cross-panel test goes in both repos, to keep the e2e describe block's duplication tag true.** `tests/animals/e2e/pages/animal-identification.spec.ts:32` tags its whole describe `{ tag: '@duplicated-in-frontend' }`; the tests repo's own `README.md:336` defines that tag as "an end-to-end spec whose behaviour the frontend's own FIT suite also proves." Adding the new cross-panel e2e test to that describe without a FIT counterpart would make the tag's claim false for it. Add the FIT test (D3) and the e2e test (D3) together, so the tag stays true for every test the describe now holds.

**D8 — Tab order and axe violations are not Behaviour Spec content.** `openspec/config.yaml`'s scope for what the spec records — page titles, the question asked and controls offered, quoted wording, page order, obligations, task-list rows and captions, the browser title, dashboard/lifecycle/event/API behaviour — names nothing about keyboard focus order or automated accessibility checks, and no spec anywhere under `openspec/specs/` mentions "axe" or "Tab order" (`grep -rln "axe" openspec/specs` returns nothing). Criteria 3 and 4 get test coverage only; no spec or coverage change.

**D9 — no backend change.** The row's `repos` list excludes `trade-imports-animals-backend`, and none of the four criteria touches what the backend reads, stores or publishes — all four are about which control a keypress or a Tab reaches on one already-rendered page.

## 4. Tests

### frontend — fit (`src/server/app/sets/live-animals/journeys/linear/features/commodities/fit/identification.fit.spec.js`)

1. **Pressing Enter in a panel that already holds one saved animal appends that panel's new animal to its own table, and leaves a different panel's already-saved animal listed too.** Covers criterion 2. Open two multi-animal panels together (`openIdentification`, `:73-78`, following the two-species combination `:1274-1277` already uses) — one panel's own helper (`addBosTaurusRecord`, `:179-182`) and the other's (`fillFelisCatusRecord` + `submitAdd`, `:108-116`) each save one record first, so each panel's saved-animals table starts at one row with its own Remove button. Fill a second value into one panel's field and press Enter on it (not click its button). Assert: that panel's table now lists two animals (its original row plus the new one); the other panel's table still lists exactly its one original row, unchanged; the page stays on Identification details. Red without `records/append.js:20`'s `if (!form.holdsData) { continue }` guard — remove it and the untouched panel's empty form would append a blank record onto its own table too, breaking the "unchanged" assertion.

2. **Tabbing forward from a panel's last identifier field reaches that panel's own save button next, then that panel's own first Remove button — never the other panel's controls.** Covers criterion 3. Reuse the same two-panel, one-saved-animal-each set-up as test 1 (factor the shared "open two panels, save one animal in each" steps into one local helper in this file, used by both tests, following the shape `addFelisCatusRecordRow` (`:184-189`) already gives a single-panel version of). Focus the last of the panel's rendered identifier fields (`card.getByRole('textbox').last()`, as `:290-306` already establishes Felis catus's field order ends with its save control). Press Tab once: assert that panel's own "Save and add another" button (scoped to that panel's `speciesCard` locator, `:166-170`) is focused. Press Tab again: assert that panel's own first Remove button (scoped the same way, matching the hidden-text-tolerant name pattern `expectCompleteCard` already uses at `:132-141`) is focused. Red if the save button or the saved-animals table ever moved ahead of the fields, or behind the next card's own elements, in `_identification-card.njk:21-48`.

### tests repo — e2e (the integration proof, `tests/animals/e2e/pages/animal-identification.spec.ts`)

3. **Through the real stack: pressing Enter in a panel that already holds one saved animal appends the new animal to that panel's table, and leaves a different panel's already-saved animal listed too.** Covers criterion 2, mirroring test 1 through the frontend, the engine's persisted state and a real page reload. In the existing `describe('Animal identification sections and species cards', …)` (`:32`, which already opens cattle, bison and the domestic cat at two animals each via its `beforeEach`, `:33-37`), save one record on the cattle card and one on the bison card (`cardEarTag` + `cardSaveControl`, `page-objects/animals/animal-identification-page.ts:95-112`), then type a second ear tag into the cattle card's field and press Enter on it. Assert `savedAnimalsRows(cattle)` (`animal-identification-page.ts:68-70`) now has two rows and `savedAnimalsRows(bison)` still has exactly one, unchanged. Placed in the same tagged describe as the existing Enter test (`:116-127`), keeping its `@duplicated-in-frontend` tag true for this test too (D7). Red without `records/append.js:20`'s guard, exercised end to end this time rather than against a mocked `state` module.

No e2e addition for criterion 3 (D5, D8) or criterion 4 (D6, D8).
