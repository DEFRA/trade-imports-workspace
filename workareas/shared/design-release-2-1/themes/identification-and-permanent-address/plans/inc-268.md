## 0. Decisions

1. **One edit, in the commodity identifier map.** The tattoo's gate, its place
   on the panel, its saved-animals column, its length check and its review
   column are all derived from one map of CN code to identifier list
   (`services/commodities/rules.js:10`). Adding the tattoo to the cattle and
   swine entries there is the whole production change. Rejected: adding the
   codes to a separate tattoo list, which would be a second mechanism beside
   the derivation the set's `docs/services.md` states ("Adding an identifier to
   a code is one edit").
2. **Cattle order: ear tag, passport, then tattoo. Pig order: ear tag, then
   tattoo.** The design source settles both — the tattoo goes last on cattle
   because that is where the design release puts it on the species that
   already ask for one. Field order and column order both follow the array
   order in the map, so the order is set by where the new entry is appended.
   Rejected: any other position, which the design source does not support.
3. **The tattoo covers the whole pig code, not only the domestic pig.** The
   data dictionary names `0103` "Pigs" in the tattoo list and "Pig (Domestic)"
   in the ear-tag list, and flags that as unsettled. The ear tag is already
   built whole-code on `0103`, the map is keyed by code with a species only
   where an identifier names one, and the acceptance criterion says a pig
   panel. Building it whole-code mirrors the ear tag and keeps one concept one
   shape. Rejected: a code-and-species pair gate, which would make the tattoo
   narrower than the ear tag on the same code with nothing in the source
   asking for that.
4. **No copy change, and no Welsh change.** The tattoo label and its
   58-character message already exist in the commodities feature copy in both
   languages, because the pet code already asks for a tattoo, and the existing
   copy test walks every identifier every identified code asks for in both
   languages. The seventh acceptance criterion is therefore already true and
   stays true through the map edit; the set's `docs/copy-status.md` already
   records the commodities feature's Welsh as a machine draft. Rejected: adding
   copy keys, which would duplicate existing ones.
5. **The characterisation goldens are regenerated by observing the run, not by
   hand-guessing key order.** Two golden suites compare the evaluated
   fulfilments both by value and by `JSON.stringify`, so the position of the
   tattoo's key inside the evaluated fulfilment map matters. The implementor
   runs the suite, reads the actual output from the failure, and writes that in
   — for the one corpus case whose cattle unit carries a tattoo value, and for
   the case whose cattle unit carries only an ear tag (where the tattoo comes
   into scope with an enumerated unit index and no value). Rejected: editing
   the file by analogy with the passport entry, which would pass the
   value comparison and could still fail the byte comparison.
6. **The pig behaviour is proved at unit and FIT level; the end-to-end proof
   rides on cattle.** The tests repo's commodity catalogue holds no pig line,
   and which species the stack's reference data serves under `0103` cannot be
   confirmed with the stack down, so inventing a pig end-to-end line would
   gamble the gate on an unverified search term. Cattle is already the species
   every animals end-to-end journey uses, so the cattle tattoo carries the
   slice through the real stack — browser entry, persistence, review and the
   outbound event. Rejected: a pig end-to-end line now; recorded as a
   follow-up.
7. **Two acceptance criteria cite provenance that does not carry what they
   assert, and the behaviour is still right.** The third criterion cites the
   claim about the page labelling `0102` inconsistently across its identifier
   lists, which says nothing about the saved-animals table; the fourth and
   fifth cite the repo claim about which fields a cow line shows, which says
   nothing about the length refusal or the review. The behaviour each
   criterion asks for is held by the sources the row does carry: the data
   dictionary's tattoo row gives the 58-character limit, and the table and
   review behaviour are the service's own existing general rules applied to a
   species that now asks for one more identifier. Planned against those.
   Nothing in the increment is contradicted.
8. **The increment's note that pigs are absent from the catalogue is stale.**
   The frontend's captured reference-data fixture holds `Sus scrofa
   domesticus` under `0103` and a pig FIT test already runs against it, so the
   pig panel is reachable today. Planned on that basis.
9. **No plants change.** The programme invariant mirrors a change into the
   high-risk plants frontend where plants has the same page or behaviour.
   Plants captures identification numbers for consignments, not per-animal
   identifiers, and has no tattoo, so there is nothing to mirror. Plants is
   also outside this row's repos.
10. **No backend change.** The outbound event mapper already turns a unit's
    tattoo into a typed animal identifier, for any commodity, so a cattle
    tattoo reaches the event with no Java change. Confirmed by reading
    `trade-imports-animals-backend`'s GBN-AG trade-product-instance mapping.
    The tests repo's expectation of that event does change, because a cattle
    animal now carries three identifiers instead of two.
11. **The field order the first criterion states gets spec text of its own.**
    Which commodities are asked for a tattoo is an obligation, and goes in the
    obligations capability beside the ear-tag equivalent. The order the fields
    appear in on the card is what the page does, is observable, and is
    recorded nowhere today — so it goes in the identification page capability.
    Rejected: stating the order in the obligations capability, which would
    have obligations state the page's half.
12. **The feature spec's one sole-animal save-and-reopen helper is widened to
    fill whichever identifier the case under test uses, rather than gaining a
    sibling.** That helper today fills the ear-tag field and nothing else
    (`.../commodities/fit/identification.fit.spec.js:171`), so it cannot save a
    cattle animal by its tattoo alone, which the first criterion needs. It is
    widened so its caller names the field it fills, and the pig case, the
    sheep-and-goat case and the new cattle tattoo-only case all go through the
    one helper. Rejected: a second local save-and-reopen helper beside it,
    which the house rule on extending the mechanism that exists forbids.
13. **The two module-scope expectation values the pig case shares with the
    sheep-and-goat case today become locals of the case that still reads
    them, and the pig case holds its own two.** The shared absent-identifier
    label list names the tattoo, and the shared expected table head is the
    one-identifier head
    (`.../commodities/fit/identification.fit.spec.js:214` and `:219`); once the
    pig card asks for two identifiers neither value is true for it, and the
    sheep-and-goat case becomes their only reader. The house rule that a value
    used by one function lives in that function therefore moves both into the
    sheep-and-goat case, and the pig case states its own expected head and its
    own absent-label list, which name different identifiers — so nothing is
    duplicated. Rejected: keeping both at module scope and adding a second
    pair beside them, which would leave four near-identical module values and
    two of them single-use.
