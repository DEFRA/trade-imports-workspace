## 0. Decisions

1. **Animals run order.** `RUN_STEPS` becomes: origin, commodities ("What are you importing?"), import reason, consignment details ("Commodity details"), animal identification, additional details, port of entry (arrival details), transit countries, transporters, documents, addresses ("Roles and addresses" on the hub, "Consignment addresses" as the page H1), consignment contact, review (`notification-view`). This matches DR2.1 `getJourneySteps` (routes.js:1495-1534) for live animals. Rejected: also reordering the `sections` array to match — sections drive only post-run `nextInSection` and the derived continue prerequisites (`ENFORCED_AT_CONTINUE` = `countryOfOrigin`, `commoditySelection`, both owned before import reason either way), so reordering them changes nothing a user sees and churns `flow.test.js`/spec text for no gain.
2. **"What are you importing?" Save and continue is run-aware.** Today `commodities/search/actions/commit-selection.js` always redirects to the consignment-details page, so the run never sees the commodities step. It becomes: hub exit → hub; change context → `consignment-details?change=1` (unchanged); in the opening run → `kit.runTarget(request, commoditiesPage.id, scope)` (= import reason); otherwise → consignment details (unchanged, the commodities section's two-page shape outside the run). Rejected: routing through `kit.nextTarget` — outside the run that would apply `nextInSection` (also consignment details) but would silently drop the explicit change-context behaviour the details page needs.
3. **Identification skip stays page-owned.** For a consignment with nothing to identify, the run still targets the identification URL and that page's existing GET guard carries the trader on to Additional details (`opening-run.test.js` "Should carry a consignment with nothing to identify on to additional details mid-run"). Observably the trader lands on Additional details, which is what AC2 asks. Rejected: a run-level `identifiesAnAnimal` gate — the step target only sees `scope`, not answers, and the guard already exists.
4. **CPH number leaves the run.** `cphNumberPage` is removed from `RUN_STEPS`. In `flow.js` the `addresses` section becomes `[cphNumberPage, addressesPage]` (CPH first). Effect: outside the run, Save and continue on Roles and addresses is the section's last page → Overview (never the CPH page), and saving the CPH page without `?return=addresses` follows `nextInSection` → Roles and addresses. The CPH page stays a flow page (section membership unchanged, so `answerSections` roll-ups, `status.test.js` and the submit-readiness equivalence suite are untouched). `run.test.js`'s "the run covers the journey" list gains `cphNumber` in `OUTSIDE_THE_RUN`. Rejected: removing `cphNumberPage` from `sections` entirely — it drops `countyParishHoldingCph` from the addresses section roll-up and breaks the section-vs-row equivalence the task-rows suite pins. The CPH controller itself does not change: `hubEntryReturn ?? nextTarget` already yields Roles and addresses on every path once the section order flips; its back link without `?return=addresses` stays Overview (the only remaining non-row entry is the review's Change/error link).
5. **"Everything complete" = `scope.readyForCheckYourAnswers`.** AC5's "every section on the overview is already complete" is read as the same roll-up the review gate uses (every task row fulfilled, not applicable or optional). Implemented as a per-step flag on the addresses step: `{ id: addressesPage.id, target: flowPageTarget(addressesPage), endsRunWhenComplete: true }`, and `nextRunTarget` returns `hubPath(journeyId)` when the current step carries the flag and `scope.readyForCheckYourAnswers` is true. Change context still wins (it is applied by `kit.exitTarget` around the run target). Rejected: a special case keyed on `stepId === addressesPage.id` inside `nextRunTarget` — data on the step reads better and keeps the loop generic.
6. **Review step gate.** The review step's target becomes `flowPageTarget(notificationViewPage)` — the review page's derived gate, i.e. it opens once the continue prerequisites (country of origin, a commodity) are answered, complete or not. This satisfies AC6 (contact → review even when incomplete) while keeping repo-frontend-p1-113 ("a run with no open later step ends on the overview"): a run where no commodity is chosen still collapses to the hub (`run.test.js` "Should collapse to the hub when every later step is unreachable" and the contact fit spec's in-run save both keep landing on the hub). Rejected: an unconditional review target — it would send a commodity-less run to the review and break p1-113. The authored `review` section gate (`readyForCheckYourAnswers`) stays; it is what `nextInSection`/section entry and the review POST refusal use.
7. **Reaching the review ends the opening run.** Both frontends' check-answers GET handler calls `completeOpeningRun(request, h, journeyId)` (the hub's exemplar, `features/hub/controller.js`). Without this, plants' "Continue" on check your answers would ask `nextRunTarget` for the step after the last one and land on the hub, and animals' SCN-FLOW-007-C ("reached Overview or review") would be untrue. Rejected: special-casing the review POST in plants only — it leaves the run alive after the review in both sets.
8. **Plants run ends on check your answers.** Plants `RUN_STEPS` gains a final `{ id: notificationViewPage.id, target: flowPageTarget(notificationViewPage) }` (derived prerequisites: commodity type and country of origin). Plants keeps its own step order otherwise (ruling claims 43/44).
9. **Plants check your answers names what is outstanding (minimum needed by AC9/AC10).** Today plants' review names only origin and removed-party errors, so an incomplete notification with neither would re-render with nothing named. Add one error per task row that is not ready (fulfilled/NA/optional), in task-row order, after the existing field errors, keyed `row:<rowId>` (animals' `party:` prefix technique) and linking to the row's entry page with `?change=1` so saving returns to the review. Copy in `errors.rows.<rowId>` in both locales. Rich per-card marking is left to the overview-and-review theme (row notes). Rejected: redirecting to the hub (that is what AC10 removes) and reusing hub copy (shared/hub wording must not be reworded or borrowed; the strings are set-specific and live in the feature's own copy).
10. **Plants review POST refuses an incomplete notification.** `if (!current.scope.readyForCheckYourAnswers) return h.redirect(hubPath(...))` is replaced: any field error **or** any outstanding row error → re-render with `disableAutoFocus: false` and status 400. The declaration and confirmation keep their own readiness gates untouched.
11. **Tests repo: keep the road walk, add the DR2.1 cattle-by-air run walk.** The claim "today's cattle-by-road walk follows the old order and would break" is only partly true: `AnimalsJourney.completeAnswerSections` drives the notification task by task from the hub (post-run), and the only step the reorder breaks is `fillAddressesToCph` (Continue on Roles and addresses no longer reaches the CPH page). Rewriting `submitNotification` itself as cattle-by-air would drop the road/transit persistence and Dynamics assertions a dozen specs depend on (`persistence-notification.spec.ts` asserts `ROAD_VEHICLE`, `['FR','BE']`). So: fix the CPH step in the shared helper (CPH via its row), and add a new reusable `walkOpeningRunCattleByAir` helper plus a new journey spec that walks DR2.1's cattle-by-air journey from create to "Import notification submitted" in the new order — that spec is AC7/AC8's integration proof and the helper is what later rows reuse ("every later row's end-to-end walk follows this order").
12. **E2E data choices** (all proven on the stack today or present in stub data): origin France with region code suffix `75` and internal reference `CATTLE-2026-01`; species `Bos taurus`; reason Internal market / Breeding; 2 animals, 1 package; ear tag + passport per animal; certified for `Further keeping` (frontend certification-purposes stub), unweaned `No`; arrival by `Airplane` at `Heathrow Airport (GB LHR)` (stub `portsOfEntryResponse.json`); transporter `García Livestock Transport SL`; one document `fileUploadPaths.safeFile1kbPdf`; parties as `fillAddressesToCph` uses; CPH 12/345/6789; contact `Animal and Plant Health Agency`.
13. **Plants rulings ledger.** Append `d-085` to `spec/decisions.json` by hand (the panel README's `spec-add-decision.sh` would mark d-069 superseded, which AC11 forbids): subject `{ "kind": "behaviour", "id": "opening-run" }`, `supersedes: "d-069"` with the resolution stating it supersedes only d-069's landing on the hub, d-069 left byte-identical. Stamp it onto its subject per the ledger convention: `journey-spec.json` behaviour `opening-run` gets `"decision": "d-085"` and a `| Ruled at design-release-2-1 (d-085) …` clause appended to `detail`. `conflicts.json` c-034 keeps pointing at d-069 (its other three parts still stand).
14. **Page naming in criteria.** AC "Roles and addresses" = the hub task row; the page's H1 is "Consignment addresses" today and is not renamed here (a later row's business).
