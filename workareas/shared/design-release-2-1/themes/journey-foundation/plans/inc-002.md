## 0. Decisions

1. **Where the rule lives: one platform fallback, keyed to the task row.** Today `kit.nextTarget` falls back to `nextInSection` (next gate-passing page of the flow section, else the hub). It becomes `nextInTaskRow`: the next gate-passing page of the section **only when that page belongs to the same task row as the page being saved**, else the hub. A page that belongs to no task row (the review section: check your answers → declaration → confirmation; the second-set test fixture, whose `taskRows` is `[]`) keeps the section order unchanged. Change context and "Save and return to overview" are untouched (they are applied by `exitTarget` around the fallback), and the opening run is untouched (it is consulted first). This is the "live flow's own fallback" the 9 October ruling names (c-243); no `from=hub` marker, no query parameter, no hidden form field. Rejected: (a) changing `nextInSection` itself — the animals check-answers controller and the plants hub call it directly for the review section and section entry; (b) "always the hub outside the run" — breaks plants' multi-page rows (commodity type → commodities list, arrival status → arrival details) and the animals CPH page handing back to Roles and addresses; (c) a per-set flag — the rule is the same in both sets (ruling claims 43/44) and req-1934 says "built … by the same flow fallback, keyed to the task row".
2. **How "opened from the overview" is told apart.** By journey state, as the ruling requires: the hub GET completes the opening run, so every page opened from an overview row is saved with the run complete and reaches the fallback. Nothing is added to the row links (`rowEntry` already builds a bare `pagePath`).
3. **"What are you importing?" uses the same fallback.** `commit-selection.js` today hard-codes Commodity details for every save outside the run. Outside the run and outside change context it now calls `kit.nextTarget(request, commoditiesPage, scope)` (run step mid-run; `nextInTaskRow` → hub otherwise). Change context keeps going to `consignment-details?change=1` (the review-page change path the requirement excludes). Rejected: special-casing the redirect to `hubPath` — it would bypass the one rule.
4. **Claim check — animals.** "the consignment addresses page runs on to the CPH number page" is no longer true: inc-001 put the CPH page before Roles and addresses in its section, so Roles and addresses already returns to the overview outside the run. The criterion still holds after this change and is pinned by tests (Decision 9), but no code changes for it. The other three animals chains are real today: commodities → Commodity details (commit-selection), import reason → Additional details, arrival details → Transit countries / Transport details, and transit countries → Transport details.
5. **Claim check — plants, arrival details.** "Today plants' Save and continue on arrival details goes on to the place of destination" is true only inside the opening run (it is `RUN_STEPS` order). Outside the run arrival details is already the last page of the `arrival` section and returns to the overview. The criterion holds; this increment pins it with tests rather than changing code for it.
6. **Claim check — plants, consignor (criterion defect).** The last plants criterion lists "consignor to identification numbers" as a task row of more than one page moving through its own pages. It is not one: `consignor` and `identificationNumbers` are two task rows, each with its own Overview row (`task-rows.js:35-36`). Keyed to the task row, as req-1934 and the previous criterion state, Save and continue on the consignor page opened from the Overview returns to the Overview — that is the one observable plants change. Identification numbers stays reachable from its own row. Planned against req-1934's rule; the criterion's parenthetical example is recorded here as wrong. Rejected: keeping consignor → identification numbers as an exception — it contradicts "keyed to the task row rather than the flow section" and the DR2.1 overview-task return the whole row is about.
7. **"Complete after returning".** Already the hub's behaviour (row status from `rowStatus`); proved end to end in the new E2E (every task saved from the overview then reads Complete), no code change.
8. **Upload documents.** Its add-another round trip redirects to itself (`backToPage`) and never reaches the fallback; only Save and continue does, and the documents section holds one page, so it already returns to the overview. Pinned in the E2E, no code change.
9. **Unit tests for the rule go in the existing `dispatch.test.js`** (animals), which already pins `nextInSection`/`sectionEntry`, and a new `flow/navigation.test.js` (plants, imitating `flow/run.test.js`). Each animals case also asserts that `nextInSection` still returns the old page, pinning that only the fallback moved and the section order did not.
10. **Existing tests that relied on chaining are rewritten, never deleted or weakened.** The rewrite rule everywhere: where a save of a page opened from the overview used to land on the next page of the section, assert the overview instead, then open the next page from its own overview row (`What are you importing?` → `Commodity details`; `Main reason for import` → `Additional details`; `Arrival details` → `Transit countries` (road/rail only) → `Transport details`). A test whose name states the old chaining is renamed only when the name becomes false, and every coverage link to a renamed test is updated (`grep -rln "<old name>" ~/git/defra/trade-imports-workspace/openspec/coverage`).
11. **Integration proof**: a new animals E2E spec `tests/animals/e2e/journeys/overview-task-return.spec.ts` and a new plants E2E spec `tests/plants/e2e/features/overview-task-return.spec.ts`, plus one new test in `tests/plants/e2e/features/parties.spec.ts`. The opening-run criterion ("the opening run, started from the dashboard, still carries page to page") is already proved by inc-001's `tests/animals/e2e/journeys/opening-run.spec.ts` cattle-by-air walk and `fit/journey-smoke.fit.spec.js`; both stay green unchanged.
