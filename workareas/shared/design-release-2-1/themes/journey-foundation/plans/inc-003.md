## How "save and return" works today (pinned against the tree)

- Both frontends render the secondary button from `src/server/app/shared/save-actions.njk` with `name="exit" value="hub"`.
  `kit.hubExitTarget(request)` (`shared/kit.js:96-97` animals, `:103-104` plants) returns the hub path when
  `request.payload.exit === 'hub'`; `kit.exitTarget`/`kit.nextTarget` already redirect there after a save.
- Every required rule in `lib/validate/validators.js` (`requiredText`, `requiredExactDigits`, `requiredMaxText`,
  `requiredEmail`, `requiredOneOf`, `requiredIntegerInRange`, `requiredDateTextInRange`/`requiredDateText`,
  `requiredTime`) reports a blank or absent value with the Joi error type `string.empty` or `any.required`, and
  every format rule with a different type (`any.only` not on the list, `any.invalid` not a real date, `date.range`,
  `string.max`, `string.pattern.base`, `string.length`, `string.email`, `number.base`, `number.range`). That split is
  the whole mechanism: on a hub exit, drop the two "missing answer" types and keep every other one.
- The model's completeness predicate (`model/obligations/is-blank-value.js`) treats `''` and an all-blank object
  (such as `kit.readDate('')` = `{ day: '', month: '', year: '' }`) as blank, so a mandatory answer saved empty
  leaves its Overview task "To do" (animals) / not "Completed" (plants). Nothing in the obligations changes.
- Animals pages in the acceptance criteria, checked one by one:
  - **Origin of the import** — `origin/validate.js:81-91`: region-of-origin code is `requiredMaxText` under "Yes". **Needs the change.**
  - **What are you importing?** — `commodities/search/search.controller.js:76-83` refuses an empty selection with `selectCommodity`. **Needs the change.**
  - **Main reason for import** — `import-reason/validate.js:65-106`: every reveal field is `requiredOneOf`/`requiredDateText` on submit. **Needs the change.**
  - **Identification details** — identifiers are `maxText` only; with nothing entered a hub exit already saves nothing and goes to Overview. Already true; see Decision D5 for the part-filled permanent address.
  - **Additional details** (`additional-details/validate.js`), **Arrival details** (`transport/port-of-entry/validate.js`), **Transit countries** (`transit-countries/validate.js`), **the transporter list** (`transporters/validate.js` — `oneOf`, blank allowed, `commitOrSkip`), **Upload documents** (`documents/controller.js:256-274` already bypasses on hub exit) and **Roles and addresses** (`addresses/controller.js:103-106` validates nothing) — no required rule today. Already true; the plan threads the hub-exit flag through the `pageValidation` ones anyway so every soft-save page states the rule the same way (D3), and the E2E proves the behaviour.
  - **Commodity details** — `consignment-details.controller.js:95-97` validates with `validate(fieldsFor(lines), payload)` and no hub-exit branch. Stays a hard stop: not touched.
  - **CPH number** — `cph-number/template.njk:103` renders `showReturnControls = false`, so it has no "Save and return to overview" at all (row note c-208 holds). Not touched.
  - **Contact address for this consignment** — see Decision D1.
- Plants pages offering "Save and return to overview" (`saveActions(hubHref, …)` with return controls): origin,
  commodity-type, arrival-status, arrival-details, identification-numbers, consignor-select, place-of-destination,
  consignment-contact-select. Of these, origin (`requiredOneOf` country), commodity-type (`requiredOneOf`),
  arrival-status (`requiredOneOf`), arrival-details (`requiredDateTextInRange`, `requiredTime`, `requiredOneOf`) and
  identification-numbers (`requiredMaxText`) refuse blanks today. The three address-book pages refuse nothing blank
  already (spec SCN for consignment-contact-select "A blank save returns to Overview"). The commodity list
  (`commodities/list/list.njk:70`) passes `showReturnControls = false`; the commodity details form has no return
  controls — both out of reach of this row.

## 0. Decisions

- **D1 — Contact address (animals) has no required answer to hard-stop.** AC4 says that on "Contact address for this
  consignment", a missing required answer on "Save and return to overview" shows the page's errors and saves nothing.
  The page has no required answer: `contact/validate.js` is `oneOf` (blank allowed) and the spec says so outright
  (REQ-CONTACT-003, "The contact address is optional, and saving without one returns to Overview", the DR1
  optional-to-proceed rule that EUDPA-667 owns). Its only check — a submitted value not in the address book
  (REQ-CONTACT-004) — is a membership/format rule, which stays enforced on either button. So the plan leaves the
  contact page exactly as it is and does not pass the hub-exit flag to it; making a blank contact refuse only on
  "Save and return" (while "Save and continue" accepts it) was rejected as contradicting REQ-CONTACT-003 and the
  row's own premise. AC4 holds in full for Commodity details. Recorded as a defect in the claim for the backlog
  owner: the contact half of AC4 is vacuous.
- **D2 — One mechanism, in the validation runner.** `validate(schema, payload, { allowMissing })` drops error details
  whose Joi type is `string.empty` or `any.required` when `allowMissing` is true. Rejected: (a) a second family of
  "lenient" validators per page — doubles every rule and lets the two drift; (b) per-page `if (hubExit)` branches
  that pick `oneOf` instead of `requiredOneOf` — the origin and import-reason rule tables would fork for one flag.
  The runner change is one place both frontends already share, and keeps every format message byte-identical.
- **D3 — Opt-in, per controller, from one kit helper.** Add `kit.isHubExit(request)` (true when
  `hubExitTarget(request)` is non-null) to both frontends' `shared/kit.js`. A controller opts in by passing
  `{ allowMissing: kit.isHubExit(request) }`. Pages that must stay strict (commodity details, CPH, contact, the
  transporter-add spokes, the address-picker spokes, identification's permanent address) simply do not pass it.
  Rejected: turning leniency on inside `validate` whenever the payload carries `exit=hub` — L2 must not read the
  request, and the hard stops would then need an opt-out.
- **D4 — "What are you importing?" commits the empty selection on a hub exit.** With nothing ticked and
  "Save and return to overview", `commitSelection(request, h, [])` runs (reconciling commodity lines to none) and
  redirects to Overview. That is "saves what was entered" and matches what un-ticking some boxes and pressing
  Continue already does line by line. Rejected: skipping the commit and leaving the stored selection — it would
  make reopening the page show something other than what was entered (AC2). For a fresh notification (the AC's
  case) both are identical: nothing stored, nothing saved, Overview shown, task "To do".
- **D5 — Identification details: a part-filled permanent address stays refused on both buttons.** The permanent
  address is a structured value; `isBlankValue` counts any object with one filled field as answered, so saving a
  part-filled address would turn the task Complete with mandatory lines missing — breaking AC2. `docs/validation.md`
  ("The collecting controller must validate required subfields before it commits the object") is the rule the page
  follows. The page's own required answer (an identification record at all) is not refused on a hub exit today —
  nothing entered means nothing appended and Overview shown — so AC1 already holds there. No code change on this page.
- **D6 — Upload documents keeps leaving the half-filled add-a-document form behind on a hub exit**
  (`documents/controller.js:268-274`). A document is not a document without its upload; the page's answer is the
  list, which is saved. AC1 holds (no error, Overview shown). No code change.
- **D7 — Plants commodity type: a blank type on a hub exit never reconciles lines.** Today the controller computes
  `linesKeptBy(lines, value.commodityType)`, which for `''` would drop every line. On a blank type the controller
  commits `{ commodityType: '' }` and skips the reconcile and the "removed" redirect (removed is 0). A radio cannot be
  un-chosen in a browser, so a blank only reaches here when no type was ever saved.
- **D8 — Plants origin: skip the narrowing check when the country is blank.** `narrowingErrorFor(constraints, '')`
  would refuse the blank with a narrowing message. `errorsFor` returns null when the value is blank and
  `allowMissing` dropped the required error. The narrowing check still refuses a country outside the consignment's
  constraints on either button (it is a rule on an entered answer).
- **D9 — Plants: which pages opt in.** origin, commodity-type, arrival-status, arrival-details,
  identification-numbers. The three address-book pages already accept a blank; the declaration and check-answers
  pages are not task pages and are not touched.
- **D10 — Name.** The flag is `allowMissing` and the helper `isHubExit`, matching the existing `hubExitTarget`
  vocabulary ("hub" is the internal name for Overview). No user-facing wording changes, so no Welsh drafts are owed.
- **D11 — No backend change.** Notes say the backend stores missing or empty answers; the animals backend has no bean
  validation below `SaveNotificationDto` (`@Valid @NotNull` on the wrapper only), and an all-blank date object or `''`
  are already stored by the existing "optional to proceed" pages. Not in the row's repos, not needed.
