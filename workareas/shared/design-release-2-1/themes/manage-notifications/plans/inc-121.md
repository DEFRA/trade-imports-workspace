## 0. Decisions

1. **The confirmation stays a page at today's address, not a dialog.** The design source
   draws a modal (`prototype-dr2-1-source-p12-055`: `role="dialog" aria-modal="true"`), and
   both the programme invariant and the owner ruling say confirmations stay pages carrying
   the dialog's wording as page content
   (`workareas/shared/design-release-2-1/sources/ruling-sam-2026-10-09-pm.md:309-311`). So
   only the page's copy, its controls and its chrome change; the route, the methods and the
   handlers' shape stay.
   Rejected: building the dialog — a separate `waiting-on-design` row owns it
   (`ruling-sam-2026-10-09-pm.md:315-318`).

2. **The strip goes off from the feature, not from the shared kit.** `kit.base` already
   takes an option that leaves the status strip off a page (animals `shared/kit.js:288`
   documents it, `:302` and `:315` apply it; plants `shared/kit.js:256`, `:268`, `:279`),
   and the kit serves every other page's strip, so this page turns its own strip off
   through that option and drops the back link by passing none (animals `:297`, plants
   `:262`).
   Rejected: teaching the kit about this page, which would move a page decision into the
   shared layer another theme owns (row note).

3. **The journey-strip option comes out of both render calls, and both kits keep the
   option.** With no strip at all, the option that suppresses the strip's own Cancel amend
   link is dead on this page. It is not this row's to delete: plants still passes it from
   its own review (`high-risk-plants/.../check-answers/controller.js:124`), and each repo's
   `shared/kit.js` belongs to the journey-foundation theme, which this row does not edit. In
   animals the option is then left with no production caller at all — `grep -rn
   offerCancelAmend` over `repos/trade-imports-animals-frontend/src` leaves only
   `shared/kit.js:93`, `:97`, `:102`, `:301`, `:316` and two tests
   (`shared/kit.test.js:164`, `features/journey-strip.test.js:107`) — which is recorded as
   a follow-up for the kit's owning theme rather than widened into this row.
   Rejected: deleting the animals kit option here, which would edit the shared layer and
   the two tests that exercise it, outside this row's footprint.

4. **The link back sits inside the existing button group, beside the button.** The design
   source puts the two controls beside each other (`prototype-dr2-1-source-p1-029`:
   a link-styled control inside the dialog's action area), and GOV.UK's button group is the
   documented component for a link beside a button, so no new markup mechanism appears. The
   group already exists in both templates (animals `cancel-amend/template.njk:11-18`, plants
   the same lines).
   Rejected: the `shared/save-actions.njk` shape (a `govuk-body` paragraph below the group)
   — that shape exists for a page's save controls and puts the control on its own line,
   which the design source does not show here.

5. **The confirm redirect keeps the cancellation marker on the address while the banner
   goes.** Criterion 5 requires both, and c-268 settles it. The marker still has a reader
   outside these repos: the performance suite checks it
   (`repos/trade-imports-performance-tests/src/k6/journeys.js`). Nothing in either frontend
   reads it after this change, so the plan deletes the view-model flag, the banner helper
   and the banner's copy keys in both repos rather than leaving a flag no template reads.
   Each repo's shared success-banner slot stays: in animals the dashboard
   (`dashboard/controller.js:124`), addresses (`addresses/controller.js:214`),
   party-picker (`party-picker.controller.js:150`) and transporters
   (`transporters.controller.js:155`) all fill it.
   Rejected: dropping the marker too (criterion 5 and the performance suite both name it);
   rejected: keeping an unused flag.

6. **The guard lands on the set's own notification list from every state, and logs through
   the mechanism each repo's architecture doc names for a refusal answered by a redirect —
   its own named line.** Today both repos send a submitted notification to its view page
   instead (animals `cancel-amend/controller.js:24-27`, plants `:27-30`); criterion 6
   replaces that with the list for every non-amending state, so the status-dependent helper
   is deleted in both. The branch is answered by a redirect, and both architecture docs put
   that case on a hand-rolled named line, not on the shared refusal helper: "A refusal
   answered by a redirect logs its own named line with the journey id and the reason"
   (animals `src/server/app/docs/architecture.md:256-257`, plants `:270-271`), with the
   declaration refusal named canonical (animals `architecture.md:259-274` over
   `declaration/controller.js:70-82`; plants `:273` over `declaration/controller.js:57-67`).
   The shared refusal helper is scoped to the other case — a refusal that **shows the page
   again** (animals `architecture.md:229-231`, plants `:243-245`) — and it hard-codes a
   message saying the page was shown again (animals `shared/kit.js:140`, plants `:148`),
   which is untrue of a redirect. So animals' existing named line stays on its own
   mechanism, keeping the searchable reason name it carries today, and plants — which logs
   nothing on this branch — gains the same line, with the same reason name and the same
   message shape, so the one rule reads the same in both twins.
   Rejected: moving both repos onto the shared refusal helper, which would log a message
   saying the page was shown again when the request was redirected, and would lose the
   named reason support searches by.

   **The plants session-ownership refusal in the same two functions goes on the same named
   line, with its own reason.** `cancel-amend/controller.js`'s `get` (`:50-52`) and `post`
   (`:60-62`) refuse a journey the session does not hold by redirecting to the dashboard
   path and logging nothing. It is a refusal answered by a redirect, which
   `src/server/app/docs/architecture.md:270-271` requires to log "its own named line with
   the journey id and the reason", and `.claude/rules/code-quality.md` requires of every
   branch that changes an outcome. Both lines sit in the two functions this row
   restructures, and the home they need — the named `request.logger` line this row is
   already adding to this module — is part of the change, so the bounded tidy-up covers
   them: the module's one refusal mechanism carries both branches, each with its own
   searchable reason name, the way the declaration feature's frozen reason map and single
   refusal helper do (`declaration/controller.js:52-67`). The journey id is the one the
   route carries, since no record has been loaded on that branch; the notification's status
   is a field only the not-in-amend branch can fill.
   Rejected: leaving the session refusal silent as "a different branch" — it is the same
   two functions and the same mechanism, and the rule is about the outcome, not the cause;
   rejected: extracting plants' duplicated session-ownership predicate into a shared owner
   in this row, which would add a call site in `delete-notification/controller.js` that this
   row does not otherwise edit (follow-up, section 7).

7. **Welsh: criterion 8 as written cannot be observed, so the plan builds the draft and
   nothing else.** Criterion 8 says "with the service in Welsh". There is no locale
   selector: `shared/copy.js` always resolves the default locale and its doc comment says
   locale selection plugs in through a `locale` argument when it is commissioned. What the
   programme invariant actually requires, and what every other row does, is a Welsh draft
   beside the English in the same change, with the same key tree — enforced by each repo's
   `copy-parity.test.js`. The plan lands that and specs no Welsh behaviour. Recorded as a
   claim that does not hold (section 3).

8. **The confirmation page's own behaviour is spec'd under each domain's
   `notification-lifecycle` capability, not a new page capability — and the banner's removal
   is also spec'd in each domain's `journey-pages/check-your-answers`, which states it.**
   `openspec/specs/live-animals/journey-pages/` and `openspec/specs/plants/journey-pages/`
   hold dispatch journey pages only (neither has a `cancel-amend` directory), and both
   confirmation pages are already specified inside `REQ-LIFECYCLE-008`
   (`live-animals/notification-lifecycle/spec.md:117-168`) and `REQ-PLANTS-LIFECYCLE-007`
   (`plants/notification-lifecycle/spec.md:87-137`), so extending those is the existing
   mechanism. Separately, two check-your-answers scenarios state the restored view's
   cancelled message — `SCN-CYA-003-D` (`live-animals/journey-pages/check-your-answers/spec.md:135-139`)
   and `SCN-PLANTS-CYA-009-B` (`plants/journey-pages/check-your-answers/spec.md:161-167`) —
   so they become untrue too and are edited in the same change (section 8).
   Rejected: minting a `journey-pages/cancel-amendment` capability, which would split one
   requirement across two capabilities and leave the delete confirmation page's twin
   behaviour behind; rejected: leaving the two check-your-answers scenarios alone, which
   would leave the spec stating a banner the code no longer renders.

9. **Plants' set specification: `journey-spec.json` and `decisions.json` are updated;
   `backlog-extras.json` and `panel/rulings.json` are not.** The programme invariant
   requires the set's journey specification, its decisions-ledger entry and any guide that
   describes the behaviour. `spec/journey-spec.json:1042` states the amendment-cancelled
   banner as live behaviour and becomes untrue. `backlog-extras.json` and
   `panel/rulings.json` are dated records of what was planned and what a panel ruled at the
   time, so they stay as written.

   **The new ruling's subject is the behaviour `notification-actions-after-submission`
   (`spec/journey-spec.json:432`), and the ledger edit follows `spec/panel/README.md:27-35`
   end to end rather than appending an entry beside the one that stands.** That behaviour is
   the set's record of what a submitted notification offers and what its two confirmation
   pages do; it is `status: "adopted"` with `decision: "d-065"`, and `d-065`
   (`spec/decisions.json:1093`) is the ledger entry whose resolution its `detail` already
   carries. This row changes what one of those confirmation pages shows, where its link back
   goes, what the restored view shows and where a request for a notification nobody is
   amending lands — all of it inside that subject — so it is a new ruling on an existing
   subject, not a ruling on a subject nobody has ruled on. `panel/README.md:3-6` states the
   invariant: "`../decisions.json` is the ledger: one entry per ruling, stamped onto its
   subject ... It is the only place a ruling lives; conflicts.json and the behaviours carry a
   pointer to it, never their own answer." So the new entry supersedes `d-065`, `d-065` is
   marked superseded and points forward to it, and the behaviour is re-stamped to it with
   the new resolution appended to its `detail` — the three steps `README.md:27-35` lists.
   Rejected: appending a free-standing `current` entry and leaving `d-065` and the
   behaviour's pointer alone, which the earlier draft of this plan did — it would leave two
   `current` entries claiming one subject while the subject still pointed at the older one,
   which is exactly what the README forbids. Rejected: minting a new behaviour for the
   cancel-amendment page, which would split one subject in two and leave the delete
   confirmation page's twin behaviour stranded under the old one.

10. **Plants' `docs/copy-status.md` gets no row.** Its table lists the features whose copy is
    provisional and has never carried a cancel-amend, delete-notification or
    notification-view row, so the change makes nothing in it untrue. Its incompleteness is a
    follow-up (section 7), not this row's footprint.

11. **The guard's POST half is proved end to end in animals only.** The tests repo's form
    client mints its crumb on the animals set and runs on the animals seed context
    (`adapters/http/frontend-form-client.ts`, fixture at `fixtures/ui.ts:192-193`), and
    `flows/animals/seeded-journey.ts:127-129` already posts this very address through it.
    Plants has no equivalent client, so plants' POST half stays proved by its controller
    unit test and only its GET half is proved end to end. Building a plants form client is a
    follow-up.
    Rejected: posting from a browser page in a plants FIT spec — the page the form lives on
    is exactly the page the guard refuses to render, so there is no form to post.

12. **The plants cancel-amendment page object gains no locator for the link back.**
    Criterion 7's link half is proved where plants already drives that control from the
    feature's own copy module, in the plants FIT spec (section 4, entry 21); no plants test
    in the tests repo exercises the link, so a locator for it would be support nothing
    reaches (section 15). Only the page object's heading changes, and its one consumer is
    `tests/plants/e2e/features/review.spec.ts:482`.
    Rejected: adding the getter for symmetry with animals' (whose getter has three consumers
    in `cancel-amend-ui.spec.ts`) — symmetry is not reachability; rejected: adding a plants
    E2E test for the link, which would duplicate the FIT proof in the slower rung for no new
    coverage.

13. **The delete-notification page is untouched.** Its shorter wording and plain link back
    are another row's.

14. **Germinal products is not built here.** The requirement behind criterion 1 names three
    sets, but `repos/trade-imports-animals-frontend/src/server/app/sets/` holds
    `live-animals` only, so there is no germinal cancel-amendment page to change. Nothing is
    built for it (section 15).
