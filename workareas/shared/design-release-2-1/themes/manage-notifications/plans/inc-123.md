## 0. Decisions

**D1. One owner of what a copy carries, and it is the animals frontend, over the canonical answers.**
The frontend's canonical fulfilment is the durable answer source and the backend's notification-shape fields are a projection the frontend computes (`src/server/app/docs/persistence.md`, "Canonical fulfilment is the durable answer source" and "Notification projections"). Today two places decide independently what a copy carries: the backend's `NotificationCopyMapper` (field by field, over the record) and nothing at all over the answer payload, which is copied whole. That is the disagreement the row reports.

Settled: the rule lives in one frontend function over the canonical answers, and the record follows by projection. A copy is made, then its answers are replaced with the carried subset through the existing replace-fulfilment write, which rewrites every notification-shape field from the answers it persists — so record and pages agree by construction rather than by two lists being kept in step.

Rejected: (a) correcting `NotificationCopyMapper`'s field list and separately filtering the payload. The payload can only be filtered where it is copied, which is the backend, and the backend cannot filter it without reading obligation ids out of a payload its own doc comment calls opaque and byte-faithful; it would also leave two owners of one rule in two vocabularies, which is what produced the defect. (b) Having the frontend send the carried answers on the copy request. The frontend cannot read an amending notification's submitted answers, so it cannot compute them for the case criterion 8 names.

**D2. One owner of which version is copied, per adapter, and each adapter is proved by its own test.**
`copy` returns a copy of the notification's *submitted* version: for a draft or a submitted notification that is its own answers; for an amending notification it is the snapshot taken when the amendment opened. Stated once as a port post-condition in `src/server/app/docs/persistence.md`, but **proved separately for each adapter**, because no single frontend test drives both:

- The **stub** adapter answers it from the snapshot it already keeps on the journey record. `src/server/app/services/persistence/records/records-port.test.js` imports `records` from `./stub/index.js` (line 2) and nothing else — all four of its describes (`:24`, `:260`, `:341`, `:422`) drive the stub — so that file proves the post-condition for the stub only.
- The **real** adapter forwards the copy to the animals backend and holds no version choice of its own; `real.requests.test.js:416-431` already proves the request it makes and needs no change. The real path's version choice therefore belongs to `NotificationService.copyNotification`, and is proved by the backend cases of section 4 items 1, 2 and 5 and by the end-to-end case of item 20.

Rejected: claiming the port test covers both modes. It cannot fail for the real adapter, so it would be a test that does not fail without the change it is credited with.

**D3. `NotificationCopyMapper` is deleted.**
Once the frontend's write rewrites every notification-shape field from the carried answers, the mapper's field list decides nothing a user or another system ever sees — a second owner of D1's rule, and dead by D1. The copy therefore creates the new draft from the chosen version's answer payload alone, with the empty notification content a brand-new notification starts with; its fields arrive with the frontend's first save, as they do for every new notification. This also means the record never holds another consignment's shipment fields, not even between the copy and the write.
Rejected: keeping the mapper and widening it to carry every field. Same deletion of the field list, but it leaves a class whose only job is a type conversion, and it persists the source's shipment fields on the record until the write lands.

**D4. A failed carried-answers write leaves no copy behind.**
The write is a second request, so it can fail after the copy exists. Left alone, that leaves a draft holding another consignment's animal identifiers, arrival and documents — the exact harm this row removes, and submittable. Settled: on that failure the copy is soft-deleted through the existing soft-delete operation, the failure is logged once with the source and copy references, and the error is rethrown so the existing recoverable-save path renders the error page the user already gets for a failed copy.
Rejected: accepting the orphan. Rejected: making the copy one request by teaching the backend to filter the payload — see D1(a).

**D5. The Packages/boxes figure is absent only where the design source shows it: a notification that has commodity lines, none of which holds a number of packages. A notification with no commodity line yet is left exactly as the spec records it.**
The design source evidences one state only — the copy's overview. `workareas/shared/design-release-2-1/distil/verify/trace-prototype-dr2-1.json`, claim `trace-prototype-dr2-1-p14-102-m1`, is verbatim: "On the copy's hub the Packages/boxes total shows no figure at all, unlike the Animals total, which shows 0", quoting "Animals … 0 … Packages/boxes … Total number of packages in this consignment … Notification tasklist". The row's criterion 5 is about the copy's overview too. On a copy the commodity lines are carried with their code and species and their numbers are given again (criteria 2, 5 and 6), so the copy is precisely "lines exist, no line holds a package count".

For a notification with **no commodity line at all** the recorded behaviour is the opposite and no source in this row shows that state: `openspec/specs/live-animals/journey-pages/overview/spec.md:56` (REQ-OVERVIEW-004) requires the totals "defaulting to zero before any commodity line has been added", SCN-OVERVIEW-004-A (`:59`) says "it shows the animal and package totals as 0, each labelled and captioned", and `repos/trade-imports-animals-frontend/src/server/app/sets/live-animals/docs/page-design.md:37` says "The commodity totals show from the first visit, reading zero". That state is therefore **not changed** by this row, and whether it should also lose its figure is a question for the designer, carried in section 7 with both quotes rather than answered here.

Settled rule, in one function: the animals total is always a figure; the packages total is a figure unless the notification has at least one commodity line and no line holds a number of packages. It is a property of the answers, not of being a copy.
Rejected: special-casing a copy — the state is reachable for any notification whose lines have no package count. Rejected: making the figure absent whenever it is unanswered, the fresh draft included — that chooses the presentation of a state the design source does not show and contradicts a recorded scenario.

**D6. The plants frontend gets the Copy as new wiring only — not the carried/cleared split.**
The owner ruling of 25 November puts plants in this row for the action and its route. Plants' own answers and its own copy mapping live in `trade-imports-plants-backend`, which the row's notes say does not join this programme's repos, and no plants design source in this workarea sets which of plants' answers a copy keeps. Settled: plants gains the action, its route and its spec and ledger entries; a plants copy carries whatever its own layers carry today.
Consequence, recorded as a risk and a follow-up: a plants copy will carry every answer, so its overview will read Complete throughout. Rejected: inventing a plants carried/cleared split here — it would widen the row past its ruling and past its design source.

**D7. Plants offers Copy as new on both the draft and the submitted notification view.**
The ruling says the notification view header gains the action "so both journeys offer the same three actions". Animals builds the action for both statuses its view header renders (`check-answers/view-model/view-header.js:84-99`, draft and submitted), so mirroring animals means both. Rejected: the submitted view alone — it would leave the two journeys differing on drafts, which is the opposite of the ruling's reason.

**D8. Claims in the increment that do not hold against the tree, planned against reality.**
- Criterion 6 and `req-1435` name a **Contact address** task row. `sets/live-animals` has no contact-address obligation, page or task row (`grep -rn "contactAddress\|Contact address"` over the set finds nothing; the row's own notes say EUDPA-776 removed it). Nothing is planned for it, and the spec is not given a contact-address scenario.
- Criterion 4 and `req-1429` name a **storage temperature**. `AdditionalDetails` holds only `certifiedFor` and `unweanedAnimals`, and the set has no storage-temperature obligation. It is a germinal-products field and the row says the germinal half is the germinal row's. Criterion 4 is planned as the certified-for and unweaned answers only.
- `req-1426` names a **net weight**. There is no net-weight obligation in the set; nothing is planned for it.
- Criterion 2's "the copy carries the same notification type, worked out from the copied answers where it is not stored" needs no code. A notification's type is the mounted set, not a stored field (`sets/live-animals/set.js`, and `flow/entry-guard.js:51-57` passes the set id as the current type), so a copy made inside live-animals is a live-animals notification. The "worked out from the copied answers" half is the entry guard: `hasCommittedNotificationAnswers` (`flow/entry-guard.js:41-44`) already sends a notification with no user answer to the first page, and a copy carrying trade answers opens on its overview.
- Criterion 1's "the copy's review page shows it" is about the record, not the page: the origin page and the review already read the internal reference from the copied answers. The change is that the copy's **record** now holds it too, because the record is the projection of the carried answers.
- Criterion 7's "transit countries page comes back with no country chosen" is reachable only after a means of transport is saved on the copy: REQ-OVERVIEW-012 gates the transit countries task and page on a saved rail or road means of transport, and the means of transport is a cleared answer. The test therefore saves a means of transport on the copy first. The copy's overview shows no Transit countries row at all, which matches the design source (`trace-prototype-dr2-1-p14-101` lists none).
- Criterion 5's "Commodity details To do" holds with the carried lines in place: the Commodity details row covers `numberOfAnimalsQuantity` and `numberOfPackages` on the lines only (`journeys/linear/flow/task-rows.js:44-53`), while the carried code and species belong to the What are you importing row (`:29-42`). This matches the design source's own task list, which shows "What are you importing? Complete" beside "Commodity details To do".

**D9. The carried/cleared split is declared as a partition of the set's obligations, not as a flag on each obligation.**
A single pair of lists in the set's obligation module reads as one rule in one place, and a coverage test over the pair forces a decision for any obligation added later. Rejected: a model key on each cleared obligation — it spreads one rule across nine section files and reaches far wider than this row.

**D10. No guard is built for an amending notification with no stored fulfilments snapshot.**
`amendNotification` refuses to open an amendment when the fulfilments payload is missing (`NotificationService.java:243-245`) and then sets the snapshot unconditionally (`:247`), so no reachable path leaves an AMEND aggregate without one. The nearest existing guard, `cancelAmendNotification`, refuses only on a missing *content* snapshot (`:269-272`) and deliberately tolerates a missing fulfilments snapshot (`:276-278`), so there is no existing guard for the field a copy reads and nothing to mirror. Settled: the copy reads the snapshot without a guard of its own, under "Build only what this change makes reachable"; the reachability argument is recorded in section 15.
Rejected: adding a refusal and calling it a mirror of `cancelAmendNotification` — that reason is not true of that method, and the refusal would be unreachable.

**D11. The plants ledger and journey specification are brought up to date on every decision the change contradicts, by superseding each — never by editing one in place.**
`decisions.json`'s convention is one current entry per subject, with a replacement setting `supersedes` and the replaced entry getting `supersededBy` and `status: "superseded"` (for example `d-086` supersedes `d-085`, `d-091` supersedes `d-023`). Read at this HEAD, `d-098` — the current entry on the `notification-actions-after-submission` behaviour — says nothing about Copy as new: its resolution is about the cancel-amendment confirmation page's content and its guard. The park of Copy as new lives in:
- `d-065`, already superseded by `d-098`, which carried it down the behaviour's chain, and which is why that behaviour's `detail` in `journey-spec.json` still reads "Copy as new stays parked with reuse-previous-consignment";
- `d-062`, **current**, subject the `c-030` conflict: "Copy as new and the Notification copied banner stay parked with reuse-previous-consignment (NNS-UN-041)";
- `d-038`, **current**, subject the `reuse-previous-consignment` behaviour: "this stays parked with no increment; unparking later is one increment copying the animals copy action".

Settled: three new entries, each superseding the current entry on its own subject — one on the `c-030` conflict superseding `d-062`, one on the `reuse-previous-consignment` behaviour superseding `d-038`, and one on the `notification-actions-after-submission` behaviour superseding `d-098` so that behaviour's `decision` pointer names the entry that changed its text. Each new entry's rationale states the owner ruling of 25 November and what the entry it chains from actually ruled. After this row no current entry states that the action is parked, and the dashboard's action set and the wider reuse-a-previous-consignment journey keep their current status.
Rejected: one entry superseding `d-098` alone — `d-098` never parked the action, so `d-062` and `d-038` would stand as current decisions describing behaviour the code no longer has. Rejected: editing `d-062` and `d-038` in place — the file's convention is to supersede.

**D12. The Copy as new header locator lives once, in the shared tests-repo view-header helper.**
`page-objects/animals/notification-view-page.ts:32-34` already holds exactly the locator plants needs, and both repos' page objects already compose the shared header helper (`readonly viewHeader = new ViewHeader(this.page)` at `page-objects/animals/notification-view-page.ts:25` and `page-objects/plants/notification-view-page.ts:14`), where `btnAmend` lives for the same reason (`page-objects/shared/view-header.ts:30-32`). Settled: promote the locator into the shared helper and delete the animals local copy in the same change, moving its three call sites to the shared helper. Rejected: a second copy on the plants page object — two locators for one control.

## 15. Reachability

Everything this plan builds is reachable once the increment lands:

- the carried/cleared partition and the carried-answers function — reached by every copy, in both persistence modes;
- the carried-answers write and its compensating soft-delete — the write on every copy, the compensation on any recoverable backend failure of that write, which is the same failure class `kit.recoverableSave` already handles for a copy;
- the submitted-version choice in the backend and the stub — reached by copying a notification while an amendment is open, which the dashboard and the notification view both offer today;
- the absent packages figure — reached by any notification that has at least one commodity line and no number of packages on any of them, every copy included;
- the plants copy action, its route, and both its refusal paths — reached from the plants notification view header on a draft and on a submitted notification.

Nothing is built for a state that cannot occur. The one state deliberately left unguarded is an AMEND aggregate with no stored fulfilments snapshot: `amendNotification` refuses to open an amendment without a fulfilments payload (`NotificationService.java:243-245`) and then stores the snapshot unconditionally (`:247`), so no path produces it, and there is no existing guard for that field to mirror (D10).
