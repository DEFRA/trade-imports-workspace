## 0. Decisions

1. **What "where the page was opened from" means, settled against the live tree.** Nothing marks a page as opened from the overview (`journey-flow-and-gates.md:171`), but the session's opening-run record already says it:
   - The dashboard's create POST begins the run and redirects to origin (`dashboard/controller.js:137-141`).
   - Rendering the overview, or the review, completes the run (`hub/controller.js:114`, `check-answers/controller.js:196`).
   - So while the run is **active**, origin can only have been reached from the list (create) or by stepping Back along the run to its first step; once it is **complete**, the user has been on the overview (or review), and every origin link they can follow is the overview's task row or the review's Change link.
   - A notification this session never ran (no run record) is reached from the list via its overview. The entry guard bounces it to origin when it holds no committed answers (`entry-guard.js:58-69`), so its overview is not reachable and Back must go to the list; with answers, the overview is reachable and Back goes there.

   Rule: **Back opens the list while the opening run is active; otherwise it opens the overview when the overview would admit the request (the run has begun in this session, or the notification holds committed user answers); otherwise the list.** Rejected: a `return=hub` marker on the overview's origin link through `kit.withReturnMarker`/`readReturnMarker` (`kit.js:193-216`). It would need the hub template to carry the marker, the origin form action to carry it through a refused POST and the recoverable-save fallback, and the review's Change link to choose too — a second signal beside the run record that already exists. Rejected: keep "answers decide" and add "or the run is complete" — it leaves answers deciding during the run, which the row says is the defect.
2. **Behaviour change during the opening run, accepted.** A notification created in this session whose origin was saved, then reopened while the run is still active (Back from What are you importing?, or by URL), now sends Back to the list, not the overview. That is the run's own order (the list comes before origin, `journey-flow` SCN-FLOW-001-A) and the page was not opened from the overview. The FIT test asserting the old answer (`origin.fit.spec.js:213-227`) is replaced, not kept.
3. **One owner for "the overview would admit this request".** `entryGuardTarget` already decides it (run begun, or committed answers). The Back rule reuses that decision rather than restating it, so the predicate is extracted inside `entry-guard.js` and both the guard and the Back rule call it. This changes `entryBackLink`'s inputs (it now needs the request, and becomes async); its one caller, the origin controller, is updated. Recorded here because it is a signature change across a caller.
4. **The review's Change link to origin keeps Back on the overview.** The run is complete once the review has rendered, so the rule gives the overview, which `journey-flow` SCN-FLOW-013-B already states for an amendment. Type question and template-review destinations belong to the type question and templates themes (row detail) and are not built.
5. **Where the type-ahead and Back proofs live, and which carry `@duplicated-in-frontend`.** README.md:299 defines the tag: an end-to-end spec whose behaviour the frontend's own FIT suite also proves. So:
   - **Animals Back tests** repeat FIT items 1 and 2 (section 4): tagged. The list case goes inside the existing tagged describe at `tests/animals/e2e/pages/origin.spec.ts:13` (its `beforeEach` already opens origin from the list through `toOriginOfImport`). The overview case needs a different start, so it goes in a new describe in the same file that also carries `@duplicated-in-frontend`.
   - **Animals "hidden from assistive technology, not focusable, never submits"** is already proved by `type-ahead.fit.spec.js:177-198`: it goes inside the existing tagged describe at `country-of-origin-type-ahead.spec.ts:6`.
   - **Animals colours and announcements** are not in the animals FIT suite: a new describe in `country-of-origin-type-ahead.spec.ts` with no tag holds only these.
   - **Plants** (button look, hidden/not-focusable/never-submits, announcements): the plants frontend is not branched and its FIT suite proves none of them, so they go untagged in `tests/plants/e2e/features/origin.spec.ts`.
6. **What "the chosen country" announcement is.** The library's polite status region (`accessible-autocomplete/src/status.js:91-121`, two `role="status"` `aria-live="polite"` regions, filled after a 1.4 s debounce) reads "N result(s) is/are available." and, when a suggestion is highlighted, adds "<name> 1 of N is highlighted". Once a choice is confirmed the region is silenced (`validChoiceMade`). So the test proves the count announcement after typing, and the highlighted-country announcement after moving onto the suggestion with the arrow key. Neither frontend overrides the English strings (only Welsh, `accessible-autocomplete.js:35-50`), so the expected English text is the library's default.
7. **Expected result counts come from canned data.** The query typed and its expected count are derived from the reference-data resource the tests repo already reads (`resources/reference-data/reference-data.ts`), not invented. Pick a plain-ASCII query whose matches in the offered list are known from that resource (animals offers countries and territories named with their country; plants offers its own primed list — the implementor confirms which canned list each page offers and derives the count from it).
8. **Colour assertions.** GOV.UK blue is `govuk-colour('blue')` and the icon is the white `background-color` of the button's `::before` masked by the search SVG (`_icon-button.scss` in both frontends). The test reads the computed background of the button and of its `::before` before any hover or focus (both change the background) and asserts GOV.UK blue and white respectively, plus that the `::before` carries a mask image (the magnifying glass). The expected colours get a home in the tests repo's shared domain constants beside the type-ahead constants, since two specs use them.
9. **The mandatory-country work is not merged** on frontend `origin/main` (`d3067053` is main's tip). Nothing here touches validation, save buttons or the country-mandatory tests; build on main as it is.
10. **Spec IDs for new requirements.** live-animals origin page: REQ-ORIGIN-022 (the joined search button) and REQ-ORIGIN-023 (the library's announcements), the next free IDs after REQ-ORIGIN-021. Plants origin page: REQ-PLANTS-ORIGIN-013 and REQ-PLANTS-ORIGIN-014, after REQ-PLANTS-ORIGIN-012.
11. Plants' Back rule (REQ-PLANTS-ORIGIN-010) is out of scope: the done check scopes plants to the type-ahead proofs only.
12. **Where the Back unit tests live, through existing set-up.** The rule is proved through the origin page's GET, driven by `driveHandler` with its existing `seed` and `openingRun` options (`engine/test-support.js:229-273`, which merges `openingRunState` into the request's session state), asserting the rendered back link in the view context — the same pattern `controller.test.js:363-383` uses for other GET context. That tests the rule through the page's input and output, and needs no new option on `journeyRequest`. Rejected: a new `journeyRequest` option recording the run phase — a second way to seed the run record beside `driveHandler`'s `openingRun` and `journeyRequest`'s `state` overrides (`:156-175`). Consequence: `flow/entry-guard.test.js` holds only the two `entryBackLink` cases, which move to the origin controller's tests, so that file is deleted (section 1).
13. **E2E route to origin from the overview.** `flows/animals/journey.ts` gains one method that, from an overview already open, follows its "Where is this consignment coming from?" task row and waits for the origin page. `answerOrigin` (`journey.ts:152`) uses it in place of its inline click; every spec copy of that click in `country-of-origin-type-ahead.spec.ts` (`:9`, `:31`, `:38`, `:47`, `:60`) is replaced by it; the new overview-case Back test reaches origin by `startNotificationAtOrigin()` then this method. Rejected: two `to*` methods (answered and unanswered) — the start already differs by an existing method, and the task-row step is the shared part.
14. **FIT route to origin from the overview.** FIT items 2 and 3 use the existing `visitOverviewThenOpen(page, 'origin')` (`fit/live-animals-journey.js:474-477`): it renders the overview (completing the run) and then opens origin, which is the state the Back rule reads. The rule reads the run record, not the referrer, so the task-row click itself is not needed and no new FIT helper is added.
