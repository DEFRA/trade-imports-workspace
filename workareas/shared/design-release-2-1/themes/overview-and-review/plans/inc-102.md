## 0. Decisions

1. **The origin card's "Region of origin code" row is already always there; only the "required" row goes.**
   - The claim: the row "always shows".
   - What is true now: the `regionOfOriginCode` obligation is in scope whatever the answer (`obligations/sections/origin.js:30-39`, in scope as both mandatory and optional). So `regionCodeApplies` is always true, and the row already always shows. A unit test proves it (`check-answers.test.js:1141`).
   - The origin page already clears the code when the answer changes to No (`origin/controller.test.js:358-360`). That means a blank code reads "Not applicable" through the existing blank-row rule (`rows/summary-row.js`).
   - What this row does: deletes the "Region of origin code required" row and the guard. `regionCodeApplies` has no other caller, so it goes too.
   - Rejected: keeping the guard "in case". It can never be false.

2. **Transit countries are already optional for submission.**
   - The `transitedCountries` obligation is `status: 'optional'` (`obligations/sections/transport.js:98-111`). An optional row reads as ready (`flow/section-status.js:13-14`).
   - A FIT test already proves that Continue reaches the declaration with none added (`check-answers.fit.spec.js:563`).
   - So the obligation does not change. The arrival obligations are not touched and no other theme is involved.
   - What does change: the separate "Transit countries" card goes, and with it its unfinished-card message and its entry in the review's card list. The `transitCountries` task row joins the Arrival details card's task rows. The card list's own test needs every task row mapped to exactly one card (`check-answers.test.js:2213-2218`).
   - Rejected: keeping a card-list entry for a card that no longer exists.

3. **The Additional details card always has a row and a Change link in live animals. No hide branch and no link-less branch are built.**
   - `animalsCertifiedFor` is mandatory and always in scope (`obligations/sections/misc.js:26-30`). So the card always has its "Certified for" row.
   - The additional details page is always part of the live-animals journey (`flow/task-rows.js:56`).
   - The cases the criterion and the ruling describe (no row; no Change link) belong to a germinal products set that leaves that page out. That set does not exist on this branch (`src/server/app/sets/` holds only `live-animals`), and no backlog row builds it yet.
   - Under "build only what is reachable", the plan proves the criterion as it stands in live animals: the card shows, and its Change link opens the additional details page. See section 15.
   - Rejected: a "hide when empty" branch and an "omit the link when off-journey" flag that nothing can reach.

4. **Means of transport: nothing to build.** The pre-flight note holds: main already reads Air, Rail, Road and Sea (`check-answers.test.js:612-622`).

5. **The transit exit point.**
   - For a transit, the exit row is keyed "Exit border control post" and comes before "Destination country".
   - Temporary admission of horses keeps "Exit date" then "Port of exit". This matches `routes.js:5071-5091`.
   - The one owner of the exit rows and their order stays `mainImportReasonCard`'s exit-rows helper. Because it now branches on the reason, it becomes a few named steps (house rule on pipelines). The literal transit reason code lives in the one function that reads it.
   - Rejected: a second applicability helper just for this label.

6. **Transit countries inside the Arrival details card.**
   - When transit countries apply, the Arrival details card carries a subsection headed "Transit countries". It holds one row, "Countries that the consignment will travel through", whose own row-level Change link opens the transit countries page. This matches `routes.js:5580-5592` and the card macro at `review-summary-card.html:37-51`.
   - The card's heading Change link still opens the port of entry page.
   - Read-only views (submitted) give the row no link, as cards get none.
   - Hidden text for the row's link: the existing hidden text "transit countries".

7. **The subsection goes through the existing headed row-group mechanism, which is generalised. No second mechanism is added.**
   - The documents card already renders a list of `{ heading, rows }` groups inside one card:
     - `cards/documents.js:22-38` builds them
     - `incomplete-cards.js:96-107` blanks them
     - `template.njk:78-81` draws each as an h4 and a summary list
   - The transit subsection is the same shape. Today's key is `documents`, which would mispredict on the Arrival details card, so the group list gets a name that covers both. The implementor names it, and the rename covers every reader:
     - `cards/documents.js`
     - `incomplete-cards.js`
     - `template.njk`
     - the unit and FIT tests that read the key
   - This is a structural decision the row needs, under "extend the mechanism that exists". It is not clean-up.
   - Rejected:
     - a parallel `subsections` key beside `documents`, which would be a second mechanism
     - reusing the `documents` key on the arrival card, which would be a mispredicting name

8. **Every Transport details row always shows.**
   - The rows are Name, Address, Country, Approval number and Type, with an empty answer as "Not applicable" (or the hidden "Missing" on an unfinished card).
   - Country is the country stored on the transporter's address, private or commercial (c-130). Today's read is unchanged.
   - Approval number is no longer dropped when blank.
   - With no transporter chosen yet, the four transporter rows still show, blank.
   - The prototype's order is Name, Address, Country, Approval number, Type (`routes.js:5236-5261`). The code's order already matches.

9. **Arrival date row key.** "Arrival date at port of entry" becomes "Arrival date at destination" (`routes.js:5102`). The copy key keeps its name: it still predicts the value.

10. **Plants mirror.** The plants review has no origin region code, import-reason exit, transit or transporter cards. Its view model holds only `incomplete-cards.js`, `invalid-parties.js` and generic rows. So none of this row's behaviour exists in plants, and the row's `repos` (frontend, tests) is right.

11. **The design question is recorded, not raised as a fix.**
