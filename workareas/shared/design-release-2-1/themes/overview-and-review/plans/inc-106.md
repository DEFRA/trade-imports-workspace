## 0. Decisions

1. **The notes name owners that do not exist on this tree.** `commodities.commodityLabel(name, code)`,
   `commodities.speciesLatinName` and `check-answers/.../species-text.js` are absent on the branch
   and on `origin/main` (fetched). The real owners today are:
   - commodity heading: `commodities/commodity-legend.js:1` `legendFor(code)`, which consignment
     details and identification details already use through `commodities/view-model/commodity-groups.js:4`
     `buildCommodityGroups`;
   - commodity line read: `commodities/lines.js:3` `linesOf(answers, evaluation)`;
   - "a line has a count": `commodities/lines.js:9` `hasAnimalCount`;
   - species label: `commodities/species-label.js:1` `speciesLabel(line)`;
   - animal row label: `commodities/animal-identification/animal-label.js:7` `animalLabelOf(label, number)`;
   - per-commodity-or-per-species read-back: `commodities/view-model/selected-commodity-rows.js:30`
     `buildSelectedCommodityRows`, which reads each commodity once except one whose species are
     listed individually (`src/server/app/sets/live-animals/services/commodities/index.js:19`
     `listsSpeciesIndividually`).
   The plan builds on these. The stale salvage (frontend `be35bf0c`, `6d70bb05`) is read for intent
   only: it is written against a `commoditySelection` data shape the tree no longer has.

2. **The commodity card title is the code alone until the catalogue carries a name. This departs
   from the prototype (section 14, design question A).** The prototype titles each commodity card
   `${entry.commodityName || entry.commonName} (${entry.commodityCode})`
   (`app/routes.js@04a073b:5419`). A commodity line here stores `commodityCode`,
   `speciesLatinName` and `speciesCommonName` only (`commodities/search/actions/commit-selection.js:8`),
   and the catalogue fixture (`src/server/app/services/_capture/fixtures/commodities.json`) has
   `code` and `species` per group, no name. The programme header holds the commodity catalogue
   content until MDM. Decision:
   - The commodity card title is the commodity heading `legendFor(code)` gives (today the code alone),
     the same heading consignment details and identification details show. When the catalogue
     carries a name, `legendFor` gains it in one place and all three pages follow.
   - The What are you importing? card's Common name row reads, in the same order as the Commodity
     code row, the common names of the species chosen under each entry (one entry per commodity,
     one per species under the per-species commodity), comma-separated. This follows the prototype,
     whose read-back rows take `entry.commonName` (`app/routes.js@04a073b:4804-4806`).
   Rejected: the prototype's own fallback, the first species' common name before the code
   ("Domestic cattle (0102)" over a card that also holds bison): it names one species as the whole
   commodity. Rejected: `commodityDescriptionFor` / `commodityNameFor`
   (`src/server/app/sets/live-animals/services/commodities/index.js:26`, `:28`): they cover three
   and two codes only, and feed the notification mapper, not a display rule.

3. **Species name title-casing has one owner beside `speciesLabel`.** A new export in
   `commodities/species-label.js` returns the stored latin name with every word capitalised
   ("Bos Taurus"), as the prototype's `toTitleCaseLabel` does (`app/routes.js@04a073b:5454`).
   The review's Species row and each species block heading use it. The per-species messages
   lower-case that same name ("bison bison"), as the prototype does (`app/routes.js@04a073b:4866`).

4. **Animal row label is the stored latin name and the number** ("Felis catus 1"), through the existing
   `animalLabelOf(entry.speciesLatinName, n)`, not title-cased: the criterion's example is
   "Felis catus 1". The review's own `identifierTable.animalN` copy goes, so one function owns the
   label.

5. **"Identifiers required with more than one species" is the unit-record floor.** The rule's one
   owner is `obligations/sections/commodities/identifiers.js:95` (`floorAppliesToParent: moreThanOne(allowListed(commodityCode, identifiedCommodityCodes))`).
   The review must not restate it. A new set-agnostic export in `src/server/app/bridge/collection-complete.js`
   (beside `entryComplete`, which already maps a positional entry to its fulfilment index) answers,
   for a positional parent entry and a nested collection under it, whether the floor asks that entry
   for a record and none is stored. It reads `emptyCollectionSatisfiesFloor`
   (`bridge/status/completeness/invariants.js:84`). The check-answers view-model already imports the
   bridge (`check-answers/view-model/applicability.js:1`).
   Rejected: counting identified-code lines in the feature (a second owner of the rule).

6. **Which message a species gets.** Only for a line the floor asks for identifiers: no count
   ("Enter the number of animals for <species>") wins over no identifier
   ("Enter at least 1 animal identifier for <species>"), as the prototype orders them
   (`app/routes.js@04a073b:4861-4877`, `getSpeciesMinimumIdentifierReviewErrorMessage`).
   "No count" is `hasAnimalCount` (`commodities/lines.js:9`) negated; the per-species errors module
   calls it and owns no count check of its own. A line the floor does not ask gets no per-species
   message. These sit in the error summary beside "Complete commodity details", which still names
   the card-level shortfall, as the prototype lists both (`app/routes.js@04a073b:5304-5315`).

7. **Species blocks show no message on the journey review, as the prototype sets (design question B).**
   The prototype gives a species block an error only on its action-required variant:
   `const identificationError = reviewVariant === 'action-required' && requiresIdentifiers && !hasIdentifiers`
   (`app/routes.js@04a073b:5459`), and the journey review passes the default `'journey'`
   (`:5410`). Its per-species summary entries link to `#review-species-N` (`:4782`, `:4952`),
   an id the Design Release 2.1 review does not render: the commodity card's species blocks carry no
   id (`app/views/partials/design-release-2.1/review-summary-card.html@04a073b:76-77`). So:
   - the species block shows no error message on the review;
   - each per-species summary entry links to its species block, which carries an anchor and is
     focusable. The prototype's link target does not exist on its own page, so the code chose the
     block; that choice is design question B.
   This follows the prototype where it says something. The GOV.UK error summary pattern (each entry
   links to an error message on the page, `docs/best-practices/gds/patterns.md`) disagrees with it,
   so by `.claude/rules/gds.md` the design is kept and the disagreement goes to the designer
   (design question B). Rejected: a message on each block (the previous plan's choice), which
   settles a guide-versus-design question in code.

8. **Card-to-task-row mapping.** `REVIEW_CARDS` (`check-answers/view-model/incomplete-cards.js:14`)
   splits today's `species` entry: the `commodities` row belongs to the What are you importing? card
   ("Complete what are you importing?"), and `consignmentDetails` with `animalIdentification` belong
   to a commodity details entry ("Complete commodity details"). Keeping `animalIdentification` there
   keeps "every task row belongs to one card" true (a unit missing a mandatory permanent address is
   not named per species). The commodity details entry marks no card: commodity cards carry no card
   id. It links to the first commodity card, and to the "2. Description of the goods" heading when
   no commodity card stands (a notification with no commodity line, where the What are you
   importing? card is also marked).

9. **The unlisted-species refusal moves to the What are you importing? card.** `refusal.js:47`
   keys its error `species`, which today anchors to the section heading through the `species`
   entry this row removes. The species choice is what that card reads back and its Change link opens
   the commodity selection page, so the error keys to that card. `speciesCardErrors` is renamed: no
   species card exists afterwards, so the name mispredicts. Rejected: keying it to commodity details
   (that card's link opens the count page, which cannot change a species).

10. **Change links.** What are you importing? header link opens the commodity selection page.
    Commodity card header link and each species block's first row (Number of animals) open
    consignment details. Identification details has its own link opening animal identification.
    All carry the review trail as every review Change link does (`check-answers/view-model/rows/change-link.js:27`),
    and none show on a read-only review.

11. **Identification details is built from GOV.UK Frontend components, not the prototype's custom
    table. This departs from the prototype (section 14, design question C).** The prototype draws a
    custom `dl` table with the Change link in its header row
    (`app/views/partials/design-release-2.1/review-summary-card.html@04a073b:104-122`), styled by its
    own `app-dr2-review-identification-table` classes. Here: an h5 "Identification details", a GOV.UK
    link with visually hidden text, then the existing `govukTable`. Shown only when the species has
    saved animals, as the table is today and as the prototype shows it (`:90-123`).
    Rejected: copying the custom table, which needs custom CSS no GOV.UK component gives.

12. **Plants mirror.** High-risk plants has no species, identification or per-commodity block on its
    review, so this row changes nothing there (programme invariant on plants holds vacuously).

13. **Germinal products.** The germinal set's review takes its own wording in its own row (notes).
    Nothing under `sets/germinal-products` changes.

14. **`reviewErrorSummary` takes named options.** It gains the species block anchors for href
    resolution, and today takes `disableAutoFocus` as its sixth positional boolean
    (`check-answers/controller.js:46-77`). The flag and the new anchors become named options of
    one options argument. Only `controller.js` calls it, so no other file changes.

15. **The module header comment of `collection-complete.js` is deleted.** Lines 1-19 describe other
    modules (`scope.js`, `purge.js`, `model/obligations/instance-complete.js`), hold rationale ("Known
    structural divergence retained…") and, once the module also answers a floor shortfall, are
    untrue ("supplies the per-entry `complete` flag"). The one fact worth keeping, that a fully empty
    nested instance vanishes on round-trip so its unmet `anyOf` cannot be flagged, moves to the
    repo's `src/server/app/docs/architecture.md`, under "L2: set-agnostic platform".

### Design questions for the designer

Each is recorded here for the implementor to carry into the theme's design findings; none blocks the
build.

- **A. Commodity card title.** Prototype: `` title: `${entry.commodityName || entry.commonName} (${entry.commodityCode})` ``
  (`app/routes.js@04a073b:5419`). Planned code: the card title is `legendFor(code)`
  (`commodities/commodity-legend.js:1`), the code alone today, because no commodity name is stored
  or catalogued until MDM. Options: (a) code alone until MDM supplies names, then "<name> (<code>)"
  on every page that shows the heading; (b) the prototype's fallback now, the first species' common
  name then the code, though it names one species for a multi-species commodity; (c) another
  interim title the designer sets.
- **B. Per-species review messages.** Prototype: the error summary links each per-species entry to
  `#review-species-N` (`app/routes.js@04a073b:4782`, `:4952`), the species block has no id
  (`review-summary-card.html@04a073b:76-77`), and it shows a block message only when
  `reviewVariant === 'action-required'` (`app/routes.js@04a073b:5459`). Planned code: no block
  message on the review; each summary entry links to its species block (new species block module,
  section 3; `cardAnchorHref`, `check-answers/view-model/incomplete-cards.js:77`). Guide: the GOV.UK
  error summary pattern links each entry to its error message
  (https://design-system.service.gov.uk/components/error-summary/). Options: (a) keep as planned,
  the link lands on the block heading with no message; (b) show the same words as an error message
  under each species block heading; (c) link to the first commodity card instead.
- **C. Identification details table.** Prototype: a custom `dl` table, Change link in the header row
  (`review-summary-card.html@04a073b:104-122`). Planned code: h5 heading, a GOV.UK link, then
  `govukTable` (`check-answers/template.njk`, section 2). Guide: "If it is not in GOV.UK Frontend,
  do not build it" (`docs/best-practices/gds/components.md:72`). Options: (a) keep the GOV.UK
  table with its link above; (b) raise a pattern request for the header-row Change link with its
  evidence.

## 14. Departures from written rules

- **Commodity card title is the code alone (decision 2, design question A).** Rule: "Build copy, layout and components as the design source sets them: the prototype, a design release or a ticket's acceptance criteria. Code that differs from its design source is a correctness finding." (`.claude/rules/code-quality.md`, Design). Reason: a real constraint the prototype cannot express. No commodity name is stored on a line or held in the catalogue, and the programme header holds commodity catalogue content until MDM. The prototype's `<name> (<code>)` (`app/routes.js@04a073b:5419`) cannot be built from today's data; its fallback to the first species' common name would mislabel a multi-species commodity. The card shows `legendFor(code)` until names arrive.
- **Identification details uses GOV.UK components, not the prototype's custom table (decision 11, design question C).** Rules: "Build copy, layout and components as the design source sets them" (`.claude/rules/code-quality.md`, Design) and "Where these guides disagree, keep the design and raise a `design` finding for the designer" (`.claude/rules/gds.md`). Reason: the prototype's table (`review-summary-card.html@04a073b:104-122`) is not a GOV.UK Frontend component and needs custom CSS. `docs/best-practices/gds/components.md:72` says "If it is not in GOV.UK Frontend, do not build it", the programme header says a behaviour is built with GOV.UK Frontend first, and only a plants-prototype design release may hold a custom pattern. `govukTable` with a heading and a link above it is the stand-in, and the question goes to the designer.

Decision 7 is not a departure: it follows the prototype (no block message on the journey review) and records the GOV.UK error summary disagreement as design question B.
