## 0. Decisions

1. **The amendment errors already behave as the row asks, in both frontends.** Nothing is built for them.
   - Animals: the review GET hides every answer error while amending unless `?refused=1` (`check-answers/controller.js:189-191`). The declaration POST redirects a refused review to `?refused=1` (`declaration/controller.js:204-210`), which re-shows the review with the summary and focus.
   - Animals tests already prove it: `check-answers.test.js:1968` and `:1989-2036`, `cancel-amend.fit.spec.js:165-197`, `amend-endings.spec.ts:150-172`. The spec states it as REQ-CYA-012.
   - Plants: `hidesAnswerErrors` (`check-answers/controller.js:82-83`) and the 400 re-render in `post` (`:154-166`). Proven by `controller.test.js:489-512`, `cancel-amend.fit.spec.js:142-166` and `review.spec.ts:523-545`. The spec states it as REQ-PLANTS-CYA-014.
   - So the three error criteria (animals AC5 and AC6, plants AC9) need no code. Section 4 names the tests that already carry them, and section 8 confirms the spec says it.
2. **The status bar's "Cancel amend" stays on the review, in both frontends.** The review adds its own "Cancel amend" button beside Continue.
   - The design source draws both. Its status partial shows the Amend tag, the reference and a "Cancel amend" link (`app/views/partials/design-release-2.1/notification-status.html` at `04a073b`). The review page also ends with a secondary "Cancel amend" button (`app/views/design-release-2.1/review-notification.html:76-82` at `04a073b`).
   - The afternoon ruling's plants line asks only for "'Cancel amend' as a button during an amendment" (ruling-sam-2026-10-09-pm claim 47).
   - The claim "there is no 'Cancel amendment' link" (AC2) already holds. Neither review has a link with that text. Animals has none at all. Plants has one only on its dashboard card ("Cancel amendment (<ref>)").
   - Plants AC8 says the button replaces "the 'Cancel amendment' link under the heading". No such link exists on plants' check answers. The only Cancel amend control there is the shared status bar link above the heading. That bar is on every page while amending (ruling claim 40: the shared strip is not changed in place).
   - So I read AC8's "in place of" as being about that non-existent link. I keep the strip, following the design source.
   - Rejected: switching the strip's Cancel amend off on the review (`offerCancelAmend: false`). That departs from the design source, and the twins would then differ from every other amend page.
3. **Cancel amend and Delete are links drawn as buttons.** Each only opens a confirmation page, so each is a `govukButton` with an `href` (c-189: controls that lead to a confirmation are links). Continue stays the form's submit button. Every control works without JavaScript.
4. **Button wording reuses shared copy as it reads today.** The ruling (claim 41) says to reuse it, and to add keys only where wording differs.
   - Animals Delete: `sharedCopy.notificationActions.delete.text` ("Delete"). The submitted view already uses it.
   - Plants Delete: plants' own `copy.delete` ("Delete notification"). The submitted view already uses it.
   - Cancel amend, in both frontends: `sharedCopy.journeyStrip.cancelAmend` ("Cancel amend"), the same words the status bar uses, already with Welsh beside it.
   - No new copy key for the buttons. The only new string is animals' re-submitting title, in English with a Welsh draft beside it.
   - Rejected: a feature-copy key reading "Cancel amend". That would put a second copy of the same words beside the first.
5. **Which reviews get which buttons, from the criteria.**
   - Animals: Delete on every editable review (draft and amendment). Cancel amend only while amending. The delete page already accepts DRAFT, SUBMITTED and AMEND (`delete-notification/controller.js:21-23`).
   - Plants: Delete on a draft only. Cancel amend only while amending, with no delete. The submitted read-only view keeps its Delete.
   - The twins differ here only because their criteria differ. Plants' ruling c-030 keeps delete off its amend review.
6. **Order of the end controls.**
   - Animals: one button group inside the review's form, in the design source's order: Continue, then Cancel amend while amending, then Delete (`review-notification.html:70-90`).
   - Plants: the ending stays `saveActions`. The plants button goes straight after Continue, then "Save and return to overview" follows, then the Cancel link on its own line. The criterion asks for the button "beside Continue" and keeps Save and return and Cancel.
7. **Animals' top button group is for the submitted view only.** Today it shows when `copyAction or deleteHref` is set. Once an editable review also has a delete href, that test would draw a second Delete at the top. It becomes the submitted (read-only) test, and its contents stay as they are.
8. **How the backend tells the frontend that answers changed.** The backend stores a boolean on the aggregate, worked out on write.
   - It is set false when an amendment starts.
   - It is recalculated on every content save while the status is AMEND. The shared spot is `setNotificationDetails`, which both `replace` (PUT) and `updateNotification` reach.
   - It is cleared with the pre-amend snapshots when the amendment is resubmitted (`writeWithOutbox`) or cancelled (`cancelAmendNotification`).
   - It is exposed on the `NotificationFulfilmentsView` projection (the frontend's rehydrate read) and on the aggregate JSON PUT returns.
   - Rejected: computing it on read. The projection is closed and exists so the snapshots are not loaded on read (its class Javadoc says so today; this change moves that rationale to `docs/design-notes.md`).
   - The Javadoc and OpenAPI breaches in the backend files this row edits are fixed here too (bounded tidy-up, section 2), with rationale moved to `docs/design-notes.md`. `NotificationController.java` is edited only because its `@Operation` text lists the projection's fields, which this change makes incomplete.
   - Rejected: computing it in the real frontend adapter. The frontend never sees the snapshot.
9. **What counts as a change: the `Notification` content sub-object only.**
   - The comparison is between the content and `preAmendNotification`, both run through `NotificationContentMapper.deepClone` so their lists are normalised alike.
   - The opaque `fulfilments` payload is never compared.
   - Uploaded documents are not in the content: the frontend's mapper leaves documents out, pinned by `notification-mapper.test.js:273-294`. So a documents-only change reads as unchanged (AC4).
   - An answer changed and then put back reads as unchanged.
10. **The stub adapter carries the same signal, worked out the same way.**
    - In stub mode (unit, FIT), the stub's document marshal works it out on read from the journey's `submittedSnapshot`. It compares the notification projection (`fulfilmentToNotification`) of the current fulfilment with the projection of the snapshot's fulfilment, both in the JSON form the backend would receive.
    - So both adapters define a change identically: notification answers only.
    - The real adapter reads the backend's boolean. Absent or null reads as false.
11. **One name for the signal from the aggregate field to the journey key.** The implementor picks it once and uses it in the Java field, the projection getter, both marshals and the journey key.
12. **Heading and browser title.** Animals only.
    - While amending with the signal true, both the H1 and `pageTitle` read "Review before re-submitting". Otherwise both read "Review your notification".
    - The layout's "Error: " title prefix still applies.
    - Plants keeps "Check your answers": its backend sends no signal (ruling claim 47).
13. **Claims checked against the tree.**
    - "The tests repo asserts today that a draft review has no Delete": holds (`notification-view-states.spec.ts:39-44`).
    - "The cancel-amend spec uses the 'Cancel amendment' link": holds only for plants' dashboard arm (`review.spec.ts:319-322`). The review arms use the status bar's "Cancel amend". They keep working, because decision 2 keeps the strip.
    - "The backend keeps a pre-amend snapshot separately from its documents": holds. `preAmendNotification` and `preAmendFulfilments` sit on the aggregate. Accompanying documents live in their own collection.
    - The note's `hubExitWhileAmending` macro parameter and plants' changed cancel-amend controller: the macro in the tree has no such parameter, and the plants cancel-amend controller is not touched.
    - None of the row's criteria is wrong except AC8's description of the link it replaces (decision 2).
