## 0. Decisions

1. **What "the Cancel amendment link" is today.** Neither review has a link with that text. On both reviews the link the row means is the status bar's **"Cancel amend"** link, which `journeyStrip`/`kit.base` adds on every page while amending (`shared/kit.js` `cancelAmendControl`). The plants dashboard's "Cancel amendment (<ref>)" link is not on the review and is untouched. Settled: on the review only, the status bar stops offering Cancel amend (`offerCancelAmend: false`, the same switch the cancel-amend page already uses) and a secondary "Cancel amend" button beside Continue takes its place. Every other page keeps the status bar link. Rejected: keeping both, which would give the review two controls with the same name.
2. **Cancel amend is a link styled as a button.** It only opens a confirmation page, so it is `govukButton({ href })` (renders `<a role="button">`), not a form post (c-189). Same for Delete, which opens the delete confirmation. Continue stays the form's submit button.
3. **The buttons' wording.** Animals Delete reuses `sharedCopy.notificationActions.delete.text` ("Delete") exactly as the row says. Plants keeps its own `copy.delete` ("Delete notification"). "Cancel amend" goes into each review's own copy as `cancelAmend.button` ('Cancel amend' / Welsh draft 'Canslo diwygio', the Welsh the shared status bar already uses). The shared copy is not touched.
4. **How the backend tells the frontend that answers changed.** The backend keeps a persisted `Boolean answersChangedSinceSubmission` on `NotificationAggregate`. It is set to `false` when an amendment starts, recalculated on every content save while the status is AMEND, and cleared to `null` with the pre-amend snapshots when the amendment is resubmitted or cancelled. It is exposed on the `GET /notifications/{ref}/fulfilments` projection and on the aggregate JSON that PUT returns. Rejected: an open SpEL projection that compares on read. That loads the snapshot on every read, which the projection's Javadoc deliberately avoids. Rejected: comparing in the frontend. The frontend never sees the snapshot.
5. **What counts as a change.** Only the `Notification` content sub-object counts: `deepClone(current).equals(preAmendNotification)`. Both sides go through `NotificationContentMapper.deepClone`, so a commodity's null complement list compares equal to the snapshot's normalised empty list. The opaque `fulfilments` payload and accompanying documents never count, because the frontend's `fulfilmentToNotification` maps no documents into the content (`notification-mapper.test.js` pins `'documents' in notification === false`). An answer changed and then put back reads as not changed.
6. **The stub adapter carries the same signal.** In stub mode (FIT, unit tests), `stub/marshal/document.js` works the field out on read. It compares `fulfilmentToNotification` of the current fulfilment with the same projection of `submittedSnapshot.fulfilment`, JSON-normalised the way the backend receives them, using `node:util` `isDeepStrictEqual`. Both adapters therefore define a change the same way: notification answers only.
7. **Journey key.** The journey object both adapters return gains `answersChangedSinceSubmission` (boolean, always `false` unless the status is AMEND). `resume-self-heal.test.js` pins the journey's keys, so its list gains the key. The key is a backend-supplied durable signal, not something the frontend derives and stores.
8. **Heading and browser title.** Animals only. On an amendment whose `answersChangedSinceSubmission` is true, both the `<h1>` and `pageTitle` read "Review before re-submitting" (new `copy.resubmitTitle`, Welsh draft "Adolygu cyn ailgyflwyno"). Otherwise they read "Review your notification". The layout's "Error: " prefix still applies on a refusal. Plants keeps "Check your answers" throughout, because plants' backend does not send the signal (backlog note p3-047).
9. **Errors on an amendment.** The review's GET for an amendment still shows no error summary and no card errors (`holdsSilently`). The POST of Continue on an amendment that `reviewRefusal` refuses no longer redirects silently. It renders the review with every error the draft path renders (card, party, species and scan errors), focus on the summary and status 400, and the amendment stays AMEND. This is done with a new `refused` option that lifts `holdsSilently` for AMEND only. Plants follows the same pattern in its `render`/`post`. This reverses `REQ-CYA-010` and `REQ-PLANTS-CYA-013` (c-136 outcome). The existing tests that pin the silent hold are rewritten, not deleted.
10. **Delete on an amendment.** Animals shows Delete on draft, amendment and submitted reviews; the delete page already accepts all three statuses. Plants shows its delete button on a draft (new) and on submitted (today), and none while amending. That follows the row and plants' ruling c-030.
11. **Plants placement.** Plants' end buttons come from the shared `saveActions` macro. The macro gains an optional `besidePrimary` list of `govukButton` parameter objects, rendered straight after the primary in its non-amend branch. Only plants check answers passes it. The macro's other callers are unchanged (default `[]`). Rejected: hand-writing the button group in the check-answers template, which would fork the "one place a journey page's ending is stated" rule the macro documents.
12. **Page objects (tests repo).** `AnimalsNotificationViewPage` and `PlantsNotificationViewPage` override the inherited `cancelAmend` getter to return the review's "Cancel amend" button, and add `statusBarCancelAmend` (the inherited status bar link) for the absence checks. Every spec and flow that clicks `notificationView.cancelAmend` therefore keeps working unchanged (`flows/animals/notification-actions.ts:35`, `a11y/notification-lifecycle-states.spec.ts:21`, `addresses-submit-freeze.spec.ts:72`, the plants "CYA" arm of `review.spec.ts`). The animals page object also gains `resubmitHeading`. Its `open()` waits for either level-1 review heading, so opening a changed amendment does not time out.
13. **Claims checked against the tree.** "The tests repo asserts today that a draft review has no Delete" holds (`notification-view-states.spec.ts:41`). "The cancel-amend spec uses the 'Cancel amendment' link" holds only for plants' dashboard arm. The animals review arm uses the status bar's "Cancel amend" link, which decision 1 replaces. "The backend already keeps a pre-amend snapshot separately from its documents" holds (`preAmendNotification` vs `preAmendFulfilments`; documents live in their own collection). Nothing in the row is wrong.
