## 0. Decisions

1. **What counts as the health certificate: an uploaded ITAHC, and nothing else.** The row and the prototype's criteria say "ITAHC or health certificate". The prototype (`app/routes.js:6363-6368` at 04a073b) accepts `itahc` or `health-certificate`, but its own option lists (`app/routes.js:10858-10866`) show `health-certificate` is only the testing variant's label for the same ITAHC. The real service has no separate "health certificate" type; `VETERINARY_HEALTH_CERTIFICATE` is "Other veterinary certificate or veterinary declaration" and does not count. This matches the confirmation page's current rule (`confirmation/outstanding.js:8-13`) and REQ-CONFIRM-006. Rejected: counting `VETERINARY_HEALTH_CERTIFICATE`.
2. **The backend owns the rule and records it at submission.** On submit the animals backend works out what is outstanding from the notification's accompanying documents that the journey claimed and that passed their virus scan (the set the outbox event already references, `OutboxService.java:82-84`), stores the outstanding items on the aggregate, and sets `SUBMITTED_ACTION_REQUIRED` when the ITAHC is outstanding, `SUBMITTED` otherwise. Each submission (first, or from an amendment) works it out afresh. Rejected: the frontend sending a status or items with the submit (the backend would trust client state); and reading the opaque `fulfilments` payload in the backend, which its own doc says it never interprets (`NotificationAggregate.java:69`).
3. **Cancelling an amendment restores the status the last submission recorded**, from the stored outstanding items, and keeps `submittedAt` as today (`NotificationService.java:246-275`). Rejected: storing a pre-amend status beside the items, a second record of one fact.
4. **The outstanding items are stored but not put on the API.** Nothing outside the backend reads them in this row: the frontend, the INS read model and PIMS read the status. They stay off the submit response and the fulfilments projection until a row needs them (build only what is reachable). The status is sent everywhere the status already goes, including the outbox event's `notificationStatusCode` and `statusChanges` (decision 17).
5. **The confirmation page's "still to do" line reads the recorded status, not the answers.** Today `confirmation/outstanding.js:8-13` re-derives "no ITAHC" from the answers; after this change the backend owns that rule, and the prototype's submitted page shows the items "recorded at the declaration" (`prototype-dr2-1-source-p11-155`, `app/routes.js:6436-6438`). One rule, one owner: the confirmation shows its ITAHC line when the status is "Submitted action required". Copy unchanged; REQ-CONFIRM-006's observable behaviour is unchanged. The later confirmation row (declaration redirect, "owes the ITAHC until one is uploaded") builds on this status-driven list rather than re-deriving it. Rejected: leaving the answers-based rule for that row, which would keep two owners of the ITAHC rule (frontend answers, backend scanned documents) that can disagree once a document is removed in an amendment or is still scanning.
6. **"A submitted status" is one predicate in the frontend and one in the backend.** Every guard that today asks "is it SUBMITTED?" (read-only view, back link, review recording, declaration and confirmation guards, cancel-amend and delete targets, list actions, `editableFromStatus`, the real marshal's `submittedAt`, the write-guard reason, the stub's amend, copy and delete guards) asks whether the status is one of the two submitted statuses. Frontend owner: beside the lifecycle constants in `engine/persistence/records.js:3-6`, re-exported where the constants are (`engine/index.js:16`, `engine/store.js:5`). Backend owner: `NotificationStatus` itself. Rejected: `|| status === …` at each call site.
7. **Tag colour: orange.** The prototype's review header colours the action-required tag `#6e3619` on `#fcd6c3` (`app/assets/sass/application.scss:7897-7900`), GOV.UK Frontend's `govuk-tag--orange`. Text "Submitted action required" from `prototype-dr2-1-source-p11-011`. The prototype's dashboard uses a red variant (`application.scss:9568-9571`), but the list's own flag belongs to the "Action required on the notification list" row; the list tag here reuses the status strip's orange.
8. **Continue on the action-required view is a form post to the existing amend action (`dashboard/controller.js:131-148`, route `:184-189`) carrying the existing hub-exit save choice, and `amendPost` follows that save choice.** The frontend already has one mechanism for "this POST goes to the overview": the `exit=hub` field that `kit.requestSaveChoice` reads and `kit.hubExitTarget` turns into `hubPath(request.params.journeyId)` (`shared/kit.js:163-190`), documented as "where a POST goes next" (`src/server/app/docs/architecture.md:132-135`). The amend route carries `journeyId` in its params (`amendPost` reads `request.params.journeyId`, `:132`) and has no payload schema (`pageRouteOptions`, `kit.js:32`), so `hubExitTarget(request)` serves as it stands. `amendPost` redirects to the hub-exit target when the save choice asks for it, else to the review with its dashboard trail as today. The Continue control posts the field pair from the save-actions template (`shared/save-actions.njk:41-46`), which owns that pair on the template side, so no template retypes it. Works without JavaScript. Rejected: a new landing field with its own allow-list and tampered-value log (a second mechanism beside the save choice); a second amend route.
9. **The documents section's "Upload a valid health certificate" error shows only when an action-required notification has no uploaded document at all**, as the prototype (`app/routes.js:5622-5627`, `prototype-dr2-1-source-p11-107`). With other documents but no ITAHC, the cards show and the header warning says what is owed. Inline, under the section heading, no error summary.
10. **The header warning text is fixed: "You need to upload a health certificate".** The ITAHC is the only item this row can record; the identifier item is another row and the "You need to complete missing information before import" fallback is dropped. Placed after the header actions and before the date line, as the prototype header (`partials/design-release-2.1/review-page-header.html`).
11. **The "Import reference numbers" section shows on the action-required view too.** It renders for every read-only view through `submittedHeader` (`submitted-header.js:57-73`); making the view read-only gives it, and the plan proves it.
12. **INS dashboard: unit test plus the tests repo's end-to-end proof; no INS stub row.** Adding a stub notification to `services/ins-backend/stub.js` would change the INS FIT list's counts and order for every dashboard test; the link rule is one function, unit-tested, and the real stack proves it end to end.
13. **Tests: specs whose subject is the Submitted state submit with an ITAHC; everything else now sees "Submitted action required".** A notification submitted from the mandatory answers (no document) is now "Submitted action required", in the frontend's stub FIT and on the stack. Each existing spec that asserts the Submitted state, the `SUBMITTED` code or `DRAFT → SUBMITTED → …` either uploads an ITAHC first (where Submitted is its subject: view-states SUBMITTED block, persistence and promoted-lifecycle walks, cancel-amend, amend-resubmit, address freeze, dashboard Submitted cards, the Dynamics spec so PIMS keeps receiving `SUBMITTED`) or asserts the code the submission now records (outbox and INS read-model specs, which then double as the new status's integration proof). `ALL_ANSWERS` keeps its veterinary certificate: the confirmation spec relies on it to prove a non-ITAHC document still leaves the ITAHC owed.
14. **The seeded journey cannot upload a file** (`seed-form-steps.ts:177-179`) and uploads go browser → cdp-uploader, so a "submitted with an ITAHC" seed seeds the draft, uploads the ITAHC through the documents page in the browser, then declares by the seeded form post. Rejected: the salvage's multipart post to the frontend, which the current documents controller does not take.
15. **No new status reaches plants.** The status rests on the ITAHC; the plants frontend and backend are not in this row's repos and are not touched.
16. **The animals admin, the INS backend and the dynamics gateway need no mapping.** Grep for a `SUBMITTED` literal over `trade-imports-animals-admin/src`, `trade-imports-ins-backend/src/main` and `trade-imports-dynamics-gateway/src/main` finds none: each passes the code through as text. The only frontends that read the code are the animals frontend (throws on unknown, `real/status.js`) and the INS dashboard's link (`list.js:43-52`), both mapped here, satisfying "mapped before the backend first sends it" within one branch name.
17. **The three submission-family events carry `SUBMITTED_ACTION_REQUIRED` for an action-required notification, a stated departure from the published schemas.** The submitted, submission-amended and amendment-cancelled event schemas (named on each event by `OutboxEventType.java:52`) pin `notificationStatusCode` to `const "SUBMITTED"`, and the codelist lists only DRAFT, SUBMITTED, AMEND and DELETED.
    - Why: the INS read model learns a notification's status only from that field (`trade-imports-ins-backend NotificationUpsertService.java:42`, `:86`). An event that said `SUBMITTED` would leave INS showing it as Submitted, and the INS criterion (the action-required row links to its review) would be unreachable. No other channel carries the status to INS, and adding one is outside the row's repos.
    - Safe to land: nothing validates the event against its schema at runtime; the schema URL is metadata (`OutboxEventType.java:52-53`), and the backend, gateway and INS backend hold no schema validation.
    - Depends on: the trade-imports-schemas change and PIMS accepting the code (section 7 follow-ups, section 14).
    - Rejected: (a) send `SUBMITTED` and keep the new code internal, which breaks the INS criterion and the ruling; (b) ok:false for a missing repo, since the contract is not enforced at runtime and every observable criterion is buildable within the row's repos.
18. **Provenance only:** decisions 1-3 come from req-909 and prototype claims p11-006/011/145/155; 5 from p11-155 and req-929's shared-test note; 8 from c-144 and p11-120; the add-only, map-first status rule from the 9 October afternoon ruling (claims 70-76); 11 from the 13 November pre-flight note.
