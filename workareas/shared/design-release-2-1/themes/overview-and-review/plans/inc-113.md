## 0. Decisions

1. **Where action-required is worked out: the animals backend, at submit.** Ruling p1-098 makes the storage the real team's call.
   - `NotificationService.submitNotification` reads the notification's accompanying documents. It already holds `DocumentService`, and `OutboxService` already reads the same collection for the event's referenced documents. It records `outstandingItems` on the aggregate and moves the notification to `SUBMITTED` or `SUBMITTED_ACTION_REQUIRED`.
   - The frontend never decides. It maps what the backend sends.
   - Rejected: the frontend computing it at the declaration and posting it to `/submit`. That would make the browser-facing service the system of record for a lifecycle fact, and the INS read model would still need the backend to carry it.
2. **The test for "has a health certificate": a document whose type is `ITAHC` or `HEALTH_CERTIFICATE`, and whose virus scan is `COMPLETE`.**
   - The prototype's `hasAttachedItahc` accepts exactly `itahc` or `health-certificate` (`app/routes.js:6363-6368`). `VETERINARY_HEALTH_CERTIFICATE` is a separate type in both the prototype and the real list, so it does **not** count.
   - `COMPLETE` matches what the GBN-AG event already treats as an uploaded document (`OutboxService`, `findAllByNotificationReferenceNumberAndScanStatusOrderByCreatedAsc(…, COMPLETE)`). The review already refuses a submit while a scan is pending (`refusal.js` `documentScanCardErrors`), so in practice every document at submit is `COMPLETE` or the submit was refused.
   - inc-115 (the confirmation page's bullet, req-929) is to reuse this test. It is not built here.
3. **Statuses are only added.** The backend enum becomes `DRAFT, SUBMITTED, AMEND, DELETED, SUBMITTED_ACTION_REQUIRED` (appended; nothing renamed or reordered).
   - The frontend gains `SUBMITTED_ACTION_REQUIRED = 'submitted-action-required'` beside the four it has.
   - `isSubmittedStatus(status)` is true for `SUBMITTED` and `SUBMITTED_ACTION_REQUIRED`. Every place that today asks "is this lodged and read-only?" asks it instead. That is listed file by file in section 2.
   - Places that ask "is this exactly Submitted?" do not exist after this change, apart from the tag mapping.
4. **Outstanding items are recorded as codes.** A new backend enum `OutstandingItem { HEALTH_CERTIFICATE }` is stored on the aggregate as `outstandingItems` (a list) and projected on `GET /notifications/{ref}/fulfilments`.
   - The list is worked out afresh on every submission, the first from DRAFT and every re-submission from AMEND (notes: "A re-submission from an amendment works the items out afresh").
   - Amend leaves it as it stands. Cancel-amend derives the restored status from it: non-empty gives `SUBMITTED_ACTION_REQUIRED`, empty gives `SUBMITTED`. A cancelled amendment therefore returns to the status it had, with no extra `preAmendStatus` field.
   - The identifier item is a separate row (notes), so `HEALTH_CERTIFICATE` is the only code now.
5. **The event carries the new status.** `ExchangedDocument.notificationStatusCode` is `notificationAggregate.getStatus().name()`, so a submission without a health certificate emits `SUBMITTED_ACTION_REQUIRED`. The event type is still `NotificationSubmitted` or `NotificationSubmissionAmended`.
   - This is what lets the INS read model (`trade-imports-ins-backend` `NotificationUpsertService` stores `notificationStatusCode` verbatim) show the notification in that status, which AC8 requires.
   - No mapping back to `SUBMITTED` on the wire. See Risks for PIMS and the schemas codelist.
6. **The map-first order is held within the one branch name.** All three repos change on `feat/EUDPA-696-design-release-2-1-overview-and-review`. Within this increment, the frontend and INS mappings are written in the same change as the backend enum. Nothing ships the backend alone (ruling p2-072 to p2-075).
7. **The tag reads "Submitted action required" and is orange.** `STRIP_STATUS[SUBMITTED_ACTION_REQUIRED] = { text: sharedCopy.journeyStrip.submittedActionRequired, classes: 'govuk-tag--orange' }`.
   - The prototype's `--action-required` tag is `#fcd6c3` / `#6e3619`, which is GOV.UK Frontend's orange tag exactly.
   - The ruling names "the strip's status copy" as the home, so the new key goes in shared copy. It is an **added** key. No shared string is reworded.
   - The view header, the status strip and the live-animals dashboard card all read the tag from this one mapping (`journeyStrip(journey).status`).
8. **The action-required view.** It is the submitted view (`readOnly` true, same header, same Amend, Copy as new and Delete), plus three things:
   - **Warning.** In the header, a `govukWarningText` reading "You need to upload a health certificate", shown when `outstandingItems` is exactly `['HEALTH_CERTIFICATE']`. It sits after the action button group and before the "Import reference numbers" section, following the prototype's order (actions, then warning). The "You need to complete missing information before import" fallback (req-904, inc-119) is dropped and not built. Any other outstanding set shows no warning.
   - **Documents section.** "4. Uploaded documents" shows no document cards and, under its heading, the inline error "Upload a valid health certificate". This applies when the notification is action-required, `HEALTH_CERTIFICATE` is outstanding and the notification holds no document at all (the prototype's `hasUploadedDocuments`, any type). The error is rendered with the template's existing `cardError` macro (`govuk-error-message` with the visually hidden "Error:" prefix). No error summary is shown, because `holdsSilently` stays true for a read-only view.
   - **Continue.** The page ends with a primary "Continue" button in a form that posts, with the crumb, to `notifications/{id}/amend`. That is the route the header's "Amend this notification" already posts to (`dashboard/controller.js` `amendPost` → `amendJourney` → redirect to `hubPath`). It starts an amendment and opens Overview, so it works without JavaScript (c-144).
9. **Which tests keep proving the plain "Submitted" path, and which move to the new truth.** A notification submitted with no ITAHC or health certificate is now honestly "Submitted action required". Two rules:
   - (a) A test whose **subject is the plain Submitted state** keeps its assertion. It gains a clean ITAHC before submitting:
     - frontend `check-answers.fit.spec.js` "submitted notification";
     - `dashboard.fit.spec.js` `stageSubmittedNotification`;
     - `cancel-amend.fit.spec.js` `submitNotification`;
     - tests repo `notification-view-states.spec.ts` SUBMITTED;
     - `notification-dashboard.spec.ts` card details and submitted actions;
     - the PIMS `notification-events.spec.ts`;
     - backend IT `createAndSubmitNotificationWithFullContent`.
   - (b) A test whose **subject is lifecycle mechanics** (amend, cancel, freeze, persistence, events) and which submits without a document is updated to expect the action-required status. Its notification really is in that state now, and uploading a document there would add a virus-scan wait without changing what the test proves.
   - Every such site is listed in section 4. The implementor also runs the audit greps there.
10. **Seeding a document in the tests repo.** `AnimalsSeededJourney.createSubmittedNotificationWithHealthCertificate()` posts the real documents form: multipart `action=add` with the ITAHC fields and a 1 kB PDF to `accompanying-documents`. It then waits on the page's own JSON status route (`accompanying-documents/status`) until every document reads `COMPLETE`, then posts the declaration.
    - This mirrors the UI submit, the same way the existing seeder posts every other page.
    - `createSubmittedNotification()` keeps its no-document behaviour and now yields an action-required notification.
    - Rejected: the UI journey `submitNotificationWithDocument` in each `beforeEach`. That is about nine full UI journeys with uploads for one describe.
11. **The stub mirrors the backend.**
    - `stub/lifecycle/transition.js` `finalise` reads the stored fulfilment's `accompanyingDocumentType` records (`obligationSet().accompanyingDocumentType`, the same lookup `notification-mapper/mapper-a/sections/origin.js` uses). It records `HEALTH_CERTIFICATE` when none is `ITAHC` or `HEALTH_CERTIFICATE`. A set with no such obligation records none.
    - The stub has no scan verdicts. Every document an answer holds counts, because the review refuses a pending scan before submit.
    - The two type codes are backend wire codes, like the status codes the stub already uses, so the L2 stub holds no live-animals copy.
12. **The INS dashboard.** `buildNotificationLink` sends both `SUBMITTED` and `SUBMITTED_ACTION_REQUIRED` to `…/notification-view`, and every other status to the hub. The status cell keeps printing the raw code, as it does for every status today. The dashboard template and copy belong to another theme (notes), so they are untouched.
13. **Plants takes nothing** (ruling p2-076). No file under `repos/trade-imports-plants-frontend` changes.

      /** No ITAHC or health certificate has passed its virus scan. */

          EnumSet.of(DocumentType.ITAHC, DocumentType.HEALTH_CERTIFICATE);

      /** What a submission with these accompanying documents still owes, in declaration order. */
      static List<OutstandingItem> outstandingFor(List<AccompanyingDocument> documents) { … }
