## 0. Decisions

1. **Which reviews get the header: keyed on the stored status.** The header heads the review for status Draft, as it already does for Submitted and Submitted action required (animals) and Submitted (plants). An amendment (status Amend) keeps today's journey heading ("Review your notification" / "Review before re-submitting", plants "Check your answers"), the status strip and its foot controls. Provenance: 9 October ruling (header keyed on the real route and stored status, c-246); afternoon ruling claim 40 (strip switched off, header drawn in the set's own template, shared layout unchanged). Rejected: keying on how the review was reached (hub vs dashboard), which the ruling replaced.
2. **One header owner per frontend, extended, not a second one.** The existing submitted-header view model (`check-answers/view-model/submitted-header.js` in each frontend) becomes the owner of the header for every status that has one. It is renamed (module, export, its unit test, the copy key group it reads) because "submitted" no longer predicts what it heads. The implementor picks the name; the same name is used in both frontends and in the tests repo's shared page object. Rejected: a separate draft-header module beside it (a second mechanism for one header).
3. **Draft actions follow the prototype's draft variant.** Prototype `app/routes.js` at 04a073b, `buildDr2ReviewPageHeader` (routes.js:5768-5773): Amend shows only for submitted variants, Copy as new always, Delete always; `review-page-header.html:16-21`: Copy as new is secondary only beside Amend, otherwise the primary button. So the animals draft header offers a primary "Copy as new" then a red "Delete"; plants offers only its red "Delete notification" (afternoon ruling claim 47: plants has parked Copy as new). The "secondary beside Amend, else primary" rule moves into the header view model (today the template hard-codes the secondary class), so one function owns it.
4. **A draft's foot loses its Delete; Delete lives in the header.** Prototype `review-notification.html` (04a073b) renders the foot Delete only for the `journey` variant (`{% if reviewVariant == 'journey' and deleteHref %}`); the draft variant ends with Continue alone. Two "Delete" buttons on one page would also break every by-role locator. Animals: the draft's foot holds Continue only; the amendment's foot keeps Continue, Cancel amend and Delete. Plants: the draft's foot keeps Continue and "Save and return to overview" in its group and the "Cancel and return to overview" link below; Delete notification moves to the header, as it already did for the submitted view. This changes what the earlier review-end-buttons row built and its spec text (REQ-CYA-005, SCN-CYA-008-D, REQ-PLANTS-CYA-006); section 8 rewrites them. Rejected: keeping a second Delete at the foot.
5. **Date created comes from the record's created instant.** Both frontends' journeys already carry `createdAt` (animals `services/persistence/records/real/marshal/document.js:10` and the stub's marshal; plants the same files). It is formatted by the existing `review/notification-date.js` formatter (Europe/London day, month in full), the formatter the date submitted line uses. A journey with no `createdAt` shows no date line, as the submitted header already does with no `submittedAt`. No backend change.
6. **Browser title follows the heading.** A draft's review is titled by its reference, as the submitted view is, because its h1 is now the reference. The "Error: " prefix is kept by the layout whenever the error summary shows (programme invariant). The earlier submitted-header row's statement that a draft keeps "Review your notification" as its title was true only while the draft's h1 read that; SCN-CYA-029-B and SCN-PLANTS-CYA-016-B change in section 8. Rejected: an h1 and a title that disagree.
7. **The Back link is not changed (one criterion not built).** The row asks for a live-animals draft's Back link to the notification list and its notes point at SCN-CYA-003-A. That claim does not hold at this HEAD. The ground is the current spec: REQ-CYA-003 (`openspec/specs/live-animals/journey-pages/check-your-answers/spec.md:109-111`), rewritten by the save-and-continue work in workspace commit 14346101 after every source this row cites, requires a draft or amendment review opened from Overview or by its address to go back to Overview, and SCN-CYA-003-C (`spec.md:125-129`) states it: a review opened with Review and submit on Overview has a back link to Overview. SCN-CYA-003-A is now a different scenario ("the review's back link opens the contact address after Save and continue there", `spec.md:113-117`), with full coverage (`coverage.json:161-167`). Building the criterion would contradict REQ-CYA-003, SCN-CYA-003-C and their tests. Ruling sam-2026-11-10b point 3 (`sources/ruling-sam-2026-11-10b.md:22-24`) is cited only for what it decides: the return links row is blocked until the save and continue work has merged; it says nothing on a review's Back link in general. `check-answers/controller.js:98-103` `backLinkFor` stays as it is.
12. **The deferred-list entry that waits on this row is closed, not left for the owner.** `workareas/shared/design-release-2-1/deferred.md:72` ("Live animals: Back from a draft's review goes to the notification list (SCN-CYA-003-A)") is already untrue at this HEAD: it says SCN-CYA-003-A has coverage 'none' and turns the end-of-theme spec check red, but SCN-CYA-003-A is now another scenario with full coverage, and REQ-CYA-003/SCN-CYA-003-C now set Overview as a review's Back from Overview. It also says "Open until inc-187 lands", and this row lands without building that Back link. Call made: close the entry. Its status becomes closed with the date this row lands, its reason that REQ-CYA-003 and SCN-CYA-003-C (save-and-continue work) set Back to Overview for a review opened from Overview, so the notification-list Back is superseded; its description stops naming SCN-CYA-003-A as the notification-list scenario and stops claiming 'none' coverage or a red spec check. A workspace edit the orchestrator commits (section 12). Rejected: re-pointing it at the save-and-continue work, which has already decided the behaviour and merged.
8. **Error summary stays at the top of `main`.** Both templates include the error summary before the header, as the submitted view does, per GOV.UK's error summary guidance (`docs/best-practices/gds/components.md`). The prototype draws it below the header (`review-notification.html`: header include, then `govukErrorSummary`). Raised as a design question (risks), not changed in code.
9. **Animals draft Copy as new reuses the existing copy action.** `notification-actions/controller.js` copies any known journey (the dashboard already offers Copy as new on drafts, `dashboard/view-model/row/actions.js:49-57`), so the header's copy form needs no new route. It posts the draft's concurrency token, as the submitted header's form does.
10. **The notification list is untouched.** A draft's dashboard row already offers Resume to its hub (`dashboard/view-model/row/actions.js:49-53`), proven by the dashboard FIT test "Resume on a draft notification opens its Overview". That criterion is an invariant check, not a change.
11. **Tests repo: one page-object owner for "the review is shown".** Many specs and flows wait on `notificationView.heading` ("Review your notification", plants "Check your answers") to mean "a draft's review is shown". The page objects gain the state-aware way to recognise the review (the draft header's reference heading with its Draft tag, or the amendment's heading), and every wait or assertion on a draft's review moves to it. Specs that assert an amendment's heading keep `heading`. Rejected: loosening `heading` to any h1.
