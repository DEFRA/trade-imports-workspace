## 0. Decisions

1. **The gate the row asks for already exists, so this row adds no production code.** Re-checked against the live tree at the HEADs above:
   - `reasonForImport` and `animalsCertifiedFor` are `status: 'mandatory'` obligations (`sets/live-animals/obligations/sections/import-reason.js:34-38`, `misc.js`); `containsUnweanedAnimals` is mandatory when an eligible commodity is chosen (`obligations/sections/commodities/aggregates.js`); purpose, destination country, port of exit and exit date are mandatory exactly when their reason is chosen (`import-reason.js:43-116`).
   - The task rows `importReason` and `additionalDetails` roll these up (`journeys/linear/flow/task-rows.js`), and `readyForCheckYourAnswers` requires every row ready (`flow/section-status.js`).
   - The declaration refuses before submit when the review would refuse (`features/declaration/controller.js`, through `check-answers/refusal.js:111-113`), and the engine refuses again at submit (`engine/write/submit.js`). Both return to the review with `?refused=1`.
   - The review then names the card ("Complete main import reason", "Complete additional details": `check-answers/view-model/incomplete-cards.js:22-37,75-80`) and blanks each empty answer row to a hidden "Missing" (`incomplete-cards.js:103-123`).
   - Leaving the pages unanswered is already allowed: the reason, certified-for and unweaned validators use `oneOf` with no required message and map a missing key to blank (`import-reason/validate.js:99-122`, `additional-details/validate.js:14-37`).
   - Rejected alternative: a second, submit-only check naming each missing answer. It would be a second mechanism beside the readiness roll-up and the review's card errors, which already own this rule.
   So the row's claim "this row builds that gate" does not hold. The row reduces to proving each criterion where it is not yet proven, through the real stack, and recording it in the spec.

2. **What is already proven, and what this row adds.**
   - Readiness for every case (no reason, each follow-up missing, no certified-for, no unweaned answer on a cattle line) is proven in `flow/task-rows.test.js`. Nothing to add.
   - A blank follow-up row shows a hidden "Missing" (`check-answers.test.js`, "Should leave a blank in-scope exit answer…" in the main-import-reason describe) — but no test proves the review *names* the main import reason card when only a follow-up is missing. Added at unit level (section 4, test 1).
   - Refusal naming every unfinished card on an `unlocked` draft is proven in FIT (`declaration.fit.spec.js:304`) and E2E (`tests/animals/e2e/pages/declaration.spec.ts:41`). Neither proves the refusal of an **otherwise complete** notification that lacks only one of these answers, nor the unweaned answer alone. Added in FIT and E2E (section 4, tests 2 and 3). The E2E spec is tagged `@duplicated-in-frontend` (README.md:336: the FIT suite proves the same behaviour), so the FIT twin is required, not optional.
   - Leaving the pages blank and moving on is proven (`check-answers.fit.spec.js`, linked to `SCN-OB-SCOPE-005-E`). The new E2E seed adds the stack proof that Save and continue with these answers blank goes on through the journey.
   - A fully answered notification submits with none reported: `declaration.fit.spec.js:204` and every `createSubmittedNotification` seed. Nothing to add beyond the spec link.

3. **A reason with a follow-up missing is not reachable through the stack.** The reason page refuses a chosen reason without its follow-ups on both Save and continue and Save and return to overview (`import-reason/validate.js:74-110`), and the seeded journey posts the same forms. So its proof is the unit test at the review (section 4, test 1), not an E2E. The reveal sits on the same page as the reason, so a reason saved without its follow-up can only arrive from stored data. Recorded, not built around.

4. **How the tests repo seeds an answer left unanswered.** The answer model says every mandatory answer is present (AGENTS.md: "a missing answer is a compile error"). Leaving a question unanswered is what the trader did, not a fact about the consignment, so it goes on the seeded journey's draft creation as a named option listing the questions left unanswered (main import reason, certified-for, unweaned), default none, carried to the seed steps. The seed posts what the page itself posts (`docs/best-practices/playwright/BEST_PRACTICES.md:112-115`: seeded state indistinguishable from UI state; each step posts exactly the fields that page's save-and-continue posts). An unchosen radio group sends no key, so for each named question the seed step leaves that field out of the posted form. When the main import reason is left unanswered, the step also leaves out every follow-up field only a reason reveals, the purpose included: with no reason chosen the trader cannot see or choose a purpose, so the import-reason step posts an empty form. Rejected: posting the field as an empty string (no browser sends that for an unchosen radio group); making the three answers optional in `MandatoryAnswers` (breaks the compile-time guarantee for every other spec); a new `DraftStage` (a stage says how far a draft is answered, not which questions inside it).

5. **The FIT helper.** `completeAnswerSections` (`fit/live-animals-journey.js:1537`) gains the same kind of named option, leaving the named questions unanswered and leaving those pages by Save and return to overview (an unanswered page cannot land on its normal next page through `saveAndExpectLanding`'s expectation, and return-to-overview is what the helper does next anyway). Its existing options (`skipAnimalIdentification`, `skipTransitCountries`) are the shape to follow. Rejected: hand-walking the whole journey in the spec, which copies the helper.

9. **How the FIT cases reach the refusal (plan review, structural).** A draft left with one of these answers unanswered is not ready, so the review's Continue posts `step=review` to the declaration and the declaration controller refuses it at its `isReviewRefused` check (`declaration/controller.js:208-214`) before the `step === review` render at line 216. The declaration page never renders, so nothing can be ticked; `startAtDeclaration` (`declaration.fit.spec.js:74-79`) waits for the declaration heading in `continueFromReview` (line 71) and cannot be used. The FIT cases therefore take the path the existing incomplete-notification refusal takes (`declaration.fit.spec.js:304-320`): open the review with `openNotificationView` (which also records the reviewed concurrency token the controller checks at lines 197-206), then post a confirmed declaration from the review's own form with `postJourneyFormToDeclaration` (`fit/live-animals-journey.js:426`), `step: 'declare'`, `declaration: 'confirmed'`. That post crosses, in order, the controller's `isReviewRefused` branch (lines 208-214, through `check-answers/refusal.js:111-113`) and, if that branch were gone, `declare` into `submitJourney`'s readiness refusal (`engine/write/submit.js:12-18`). `startAtDeclaration` and `continueFromReview` are left as they are. Rejected: clicking Continue and expecting the refused review, which proves the review's own refusal (already SCN-CYA-007-B) rather than the declaration's, and does not cross the submit path the row is about; extending `startAtDeclaration`, which cannot run for an unready draft. `openNotificationView` is used rather than `openReviewFromHub`, so the case does not depend on what the overview offers on an unready draft.

10. **Where the unit test lives and what it seeds (plan review, detail).** The review computes incomplete-card errors on every render of a draft, refused or not (`check-answers/controller.js:214-246`: applied whenever answer errors are not hidden, which covers every draft). So the unit test proves what a draft's review shows, not anything tied to a refused Continue. It lives in `the unfinished notification` describe (`check-answers.test.js:2344`), beside the existing whole-summary assertions there ("Should anchor each entry to the card it names", line 2376), and seeds from the complete `fullSeed` (line 342, which that describe already proves has no error summary at line 2398) with only `reasonForImport` and its follow-ups swapped. Rejected: the `main-import-reason exit answers` describe's local `reasonSeed` (line 1719), which holds only an ostrich commodity line plus the reason answers, so every other card is unfinished too and the summary could never be exactly the main import reason card. The reasons are not gated by commodity in the obligations (`obligations/sections/import-reason.js:34-116`), so the Bos taurus line in `fullSeed` takes every reason.

6. **No log.** No outcome-changing branch is added or altered; the declaration's refusal is already logged once with the journey id and reason.

7. Dependency inc-113 is done; its submit path is unchanged by this row.

8. **The previous attempt failed at implement with no recorded cause and no work kept** (backlog note; `logs/inc-267-preserve-repo-state.json` shows both repos clean at these HEADs). The tree has not moved, so the plan stands as reviewed, with the review's must-address finding (leave an unanswered field's key out of the seeded form, and the follow-ups with it) folded into decision 4 and section 2. To keep the implementation small: the three FIT cases are one parameterised test over a table of (question left unanswered → expected card message, expected blank row), and the three E2E cases the same; the unit cases are one parameterised test. Rejected: dropping the FIT twin to save work, which would make the E2E spec's `@duplicated-in-frontend` tag untrue for the new cases.
