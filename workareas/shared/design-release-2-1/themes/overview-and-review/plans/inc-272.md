## 0. Decisions

1. **The theme owns the review's structure and names; main owns the permanent address rows and identifier table.** Every conflict is settled the same way: take the theme's section heading, card title, card id, copy key and section function, then carry main's permanent-address behaviour into them. The alternative, keeping main's "Roles and addresses" card under a "Consignment parties" group, would undo the theme's headings and titles, which the acceptance criteria forbid.
2. **The deleted section file stays deleted.** The theme deleted the review's "consignment parties" section and replaced it with the "consignment addresses" section. Main edited the old file to forward the permanent addresses. The old file goes. Main's edit is carried into the new section instead. The alternative, keeping both files, leaves a dead section that nothing imports.
3. **A clean merge that silently drops main's rows is treated as a conflict.** `view-model/index.js` merges cleanly and passes the permanent addresses to the theme's section. But the theme's section neither takes nor forwards them, so the review would lose every permanent address row with no conflict to flag it. The plan fixes the section (section 2).
4. **Main's tests that name the old card titles are renamed, not dropped.** Main's new unit, fit and E2E tests use "Roles and addresses", "Import details" and "Reason for import". They move to "Addresses", "Origin of import" and "Main import reason". This covers the clean-merged E2E journey spec for pet cats, which no conflict flags. The alternative, deleting them, would lose main's only proof of the permanent address rows on the review.
5. **The FIT heading-level assertion in the conflict hunk becomes a positive one, over every heading in `main`.** The conflict at the "titles every card with a level 3 heading" test is main's "one level 4 heading per summary card" line against the theme's "no level 4 heading" line. The theme's line proves the old group headings are gone by absence, which the house rules forbid on a line this change touches. Both lines go. In their place the test asserts the exact text of every heading inside `main`, at any level, in document order, on the brand-new notification the test already opens. On that state the page shows, and the list names, exactly:
   - the error summary title (`sharedCopy.errorSummary.title`, a level 2 heading). `template.njk:27` includes `shared/error-summary.njk` above the h1, and the spec's "names every unfinished card in the error summary…" test proves it shows on this state;
   - the page title (`copy.title`, the level 1 heading at `template.njk:29`);
   - each of the six numbered section headings, each followed straight away by its own card titles from the review copy (`copy.cards.*`).
   
   Nothing else heads `main` on this state: the level 4 identifier table and document headings (`template.njk:72`, `:79`) need a commodity line or an uploaded document, which a brand-new notification has neither of, and the layout's banners (`shared/layout.njk:74`–`100`) need a recoverable error, a stale action or a success, none of which occur here. Because the list spans every level, a group heading at level 3 or level 4 (main's old structure: group titles at level 3, card titles at level 4), or at any other level, between a section and its cards turns it red, and so does a card moving section. The alternatives rejected: a level 2 and level 3 list alone, which misses a group heading at level 4 and goes red on the error summary title unless it is named; and keeping the absence line, which carries a known house-rule breach into the merge commit.
6. **The summary card selector moves into the one test that uses it.** Main extracted the summary card selector into a module-scope constant used by three tests: the "permanent address rows" test, the heading-level test and the count-only Change link test. Both conflict hunks take the theme's side (decision 5, and the change-link test, whose theme version already names every card's link exactly), so in the merged file only main's "permanent address rows" test uses it. Under the house rule "A literal value used by one function lives in that function", the selector moves inside that test and the module-scope constant goes. The alternative, keeping main's constant at module scope, leaves a single-use literal there in a file this change edits.7. **The behaviour spec takes main's openspec content as spec sync, not as a backlog-repo merge.** The row's `merge` map covers backlog repos only, but acceptance criterion 4 needs main's identification and permanent address scenarios on the theme's spec. Section 8 names the exact end state of every openspec file main changed. Only `openspec/` is in scope. Main's other workspace changes (this theme's own `backlog.json`, `themes.json`, tickets, other themes' plans, the build-loop script) are left out (section 7). How the orchestrator lands it is lifecycle and not planned here.
8. **Coverage keeps the theme's links where main emptied them.** Main's coverage sets two review scenarios to no coverage: "transit countries are not owed for submission" and "Delete opens the delete confirmation". The FIT test the theme links for the first exists on both sides (`check-answers.fit.spec.js` on HEAD and on main). The theme's links are kept. The alternative, taking main's empty entries, loses proof that exists.
9. **The coverage file keeps the theme branch's layout.** Main reformatted the review coverage file to one key per line, and the theme writes one test link per line. The theme's layout is kept, with main's new requirements written in it. The alternative is a full-file reformat that buries the real changes. `tim spec lint` reads both layouts.
10. **The backend needs nothing beyond the merge itself.** The theme has no backend change, and main's backend change (an identifier field and its controller test) merges with no conflict. The row still asks for a two-parent merge commit there. The loop makes it.
11. **No new tests.** This is a merge. Every behaviour it brings in already has main's tests, and every behaviour it keeps already has the theme's. Section 4 names the existing tests that must pass, and which merge edit each one guards.
12. **FIT checks carry this machine's worker count.** Every animals-frontend FIT command in section 5 ends with `--workers=3` after its spec files, so a stage running it outside `tim build gate` drives the machine no harder than the gate does. The plan review required it, from the run's "this machine's test workers" guard rail. It overrides the planner brief's "write no worker count into a plan".
