## 0. Decisions

1. **The submitted predicate stays, reduced to one status.** Frontend `isSubmittedStatus` (`engine/persistence/records.js:9`) and backend `NotificationStatus.isSubmitted()` (`NotificationStatus.java:6`) each keep owning "is this notification submitted", answering true for SUBMITTED only. Rejected: inlining `=== SUBMITTED` back into the 15+ callers as on main. That touches many files and changes no behaviour, and the name still predicts what it returns.
2. **What is kept from the earlier row:** `submittedAt`, the stored outstanding items (`OutstandingItem.outstandingAmong`, `NotificationAggregate.outstandingItems`, `DocumentService.findClaimedScannedCleanByNotificationReferenceNumber`) and the Date submitted line. AC3 asks for this. Only the status choice goes: `OutstandingItem.submittedStatusFor` is deleted.
3. **Cancel-amend returns to SUBMITTED** in both the backend and the frontend stub, because no other submitted status exists now. The stub's snapshot no longer records the status it came from.
4. **The confirmation page's "Before the consignment is imported" list goes back to the answers-based rule.** It shows the list unless an ITAHC is among the journey's documents, as on main, in `confirmation/outstanding.js`. It currently reads the deleted status, and the backend does not send outstanding items on the API (`docs/design-notes.md`). Rejected: exposing outstanding items on the API, which is new behaviour no row asks for. The list predates the status and its spec requirement stays.
5. **The view's Continue form and the hub-exit branch of the amend POST are removed together. The amend route itself stays.** The form (`check-answers/template.njk:134-141`) and its `continueAmendAction` context existed only for the action-required Continue. They post to the dashboard amend route, which the header's Amend this notification button (`view-header.js:46-52`) also uses, so the route stays. In `dashboard/controller.js`, `amendPost` loses its hub-exit target and always opens the notification view, as on main. Rejected: keeping the hub-exit branch, which nothing can now reach.
6. **The `hubExitButton` macro in `shared/save-actions.njk` stays.** `saveActions` still uses it, so it is reachable. Inlining it back is clean-up in a file this row does not otherwise need, so it goes to section 7.
7. **Specs whose subject is a submitted notification keep their ITAHC upload** (the tests repo's `createSubmittedWithItahcUploadedInUi`, `MANDATORY_ANSWERS_WITH_ITAHC`, the FIT `withItahc` option and the unit helper `submitWithItahc`). They stay valid and pass. Switching them back to a plain submit would only be clean-up, so it goes to section 7. The exceptions are the tests whose subject is a notification *without* an ITAHC: they now expect Submitted (section 4).
8. **Spec handling:**
   - The view requirement that existed only for this status (REQ-CYA-032) is deleted.
   - REQ-LIFECYCLE-010 is rewritten to say submission records Submitted whether or not an ITAHC passed its scan, and cancel returns to Submitted. This keeps provable scenarios for AC1 and AC2.
   - SCN-EVENTS-001-F is rewritten to the SUBMITTED code, which proves AC4.
   - AC5 gets a new scenario under REQ-CYA-029, the submitted view.
   - Every other mention goes back to its wording on main.
9. **The two best-practice guides that name `SUBMITTED_ACTION_REQUIRED`** (`docs/best-practices/java/testing/unit.md:316`, `docs/best-practices/node/testing/frontend.md:181`) are illustrative "Bad" examples about test titles. They are not claims about the service and stay unchanged.
10. **No claim in the row is wrong.** Checked against the tree:
    - the status exists in the backend enum, frontend `records.js`/`status.js`/`kit.js`/stub, INS `list.js` and tests `notification-status.ts`;
    - the view shows the orange tag, the warning, the Continue and the documents error;
    - inc-113's date and outstanding-item recording is in place.
