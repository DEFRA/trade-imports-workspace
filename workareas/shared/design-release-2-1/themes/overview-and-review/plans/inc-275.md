## 0. Decisions

1. **Outstanding items go completely.** That means the aggregate field, the enum, its rule, the only writer in `submitNotification`, the enum's unit test and every test assertion on it. Nothing reads them: the field is `@JsonIgnore`, and no frontend or outbox code uses it. The confirmation page's "You still need to" section is worked out in the frontend from the fulfilment, not from this field, so it stays as it is. Provenance: ruling:sam-2026-11-19, the orchestrator's first call. Rejected: keeping the enum without its rule. Nothing would use it, and the ruling re-adds both together with the banner.
2. **`DocumentService.findClaimedScannedCleanByNotificationReferenceNumber` stays.** `OutboxService.appendEvent` (OutboxService.java:82) still calls it. `NotificationService` keeps its `DocumentService` dependency for `deleteNotificationsAndDocuments`.
3. **The backend flag becomes a primitive `boolean` on `NotificationAggregate`, defaulting to false.** It follows the one stored-flag pattern on main, `AccompanyingDocument.claimed` (accompanyingdocument/AccompanyingDocument.java:58-59, `@Builder.Default` on a primitive).
   - Resubmitting and cancelling set it to false, not null.
   - Saving a draft leaves it false.
   - Rejected: keeping `Boolean` and turning null into false on read. That gives one rule two owners, and it is the three-state flag the review raised.
4. **"Absent means no" has one owner: the aggregate's primitive field, reached on every read through the entity read path.** Today the fulfilments read is an interface projection (`NotificationRepository.findFulfilmentsViewByReferenceNumberAndOrganisationId`, NotificationRepository.java:20-21, served by `NotificationService.findFulfilmentsView`, NotificationService.java:149-162). Spring Data builds that projection from a map of the stored keys, skips a key the document lacks, and returns null for it. A primitive accessor there would fail on an old record rather than say false, and the field default would never be reached. So:
   - The repository's fulfilments read returns `NotificationAggregate`, restricted to the fields the view carries, through a `@Query` with `fields` (the DTO-with-`@Query` form in `docs/best-practices/java/spring-data-mongodb.md` §5). It replaces the interface-projection method. It is still scoped by reference number and organisation, and still leaves out the pre-amend snapshots and `expireAt`.
   - The entity read constructs the aggregate through its no-argument constructor (Spring Data's preferred constructor when one exists) and populates only the keys the document holds. A document with no stored flag therefore leaves the primitive field at false. That is the mechanism, at NotificationAggregate.java:73 (the field declaration). Nothing else in the code says "absent means no".
   - `NotificationFulfilmentsView` stops being a projection interface. It becomes an immutable class built from the aggregate in one place, a static factory on the view itself, which copies the aggregate's values and decides nothing. `findFulfilmentsView` calls that factory.
   - Decision 3's rejected alternative reconsidered against this: still rejected. With the entity read, a read-time null-to-false conversion would be a second owner of a rule the field type already owns.
   - Rejected: backfilling stored documents. The backend has no data-migration mechanism (no Mongock, no change units), so a backfill would be a second mechanism, and it would still leave the projection failing on any document written between deploy and backfill.
   - Rejected: the projection carrying the default (a SpEL `@Value` on the interface accessor). It turns the projection open, so Spring Data loads the whole document, and it puts the rule in an expression string beside the field that already owns it.
   - Rejected: a record DTO projection with a primitive component. Whether the converter passes a default or fails for a missing primitive constructor argument is library behaviour this plan cannot pin, and the rule would again sit outside the aggregate.
5. **One accessor name for the flag, on both types: `isAnswersDifferFromSubmitted()`.** The field, the JSON key and the setter keep the concept's name, `answersDifferFromSubmitted` / `setAnswersDifferFromSubmitted`. Lombok names a primitive boolean's getter `is…`, so the aggregate's accessor becomes `isAnswersDifferFromSubmitted()`. The view is a Lombok immutable class (`@Value` with a builder), so its accessor is the same `isAnswersDifferFromSubmitted()`, and its other accessors keep their `get…` names. Jackson serialises both as `answersDifferFromSubmitted`, so the JSON key does not change. Rejected: a record view, whose accessor would be `answersDifferFromSubmitted()`, a second name for one concept (section 14).
6. **The real frontend marshal passes the backend's flag straight through.** Today it guards with `=== true` (real/marshal/document.js:14). The backend now always sends a boolean, on the fulfilments view and on every aggregate response alike, so the guard has nothing left to do (row notes). The real adapter's test fixtures then take on the backend's shape and carry the flag.
7. **The stub keeps the flag on its stored journey, the way the backend does, and reads it back.** It no longer works the flag out in `marshal` on every read.
   - It is false on create and copy.
   - It is false when an amendment starts.
   - It is worked out on each save while the journey is AMEND.
   - It goes back to false on finalise and on cancel amend.

   Provenance: the orchestrator's third call, and the row's note "false when an amendment starts, worked out on each save, cleared on resubmit or cancel".
8. **On save, the stub compares the notification projection of the new fulfilment with the projection of the submitted snapshot's fulfilment.** Both go through `fulfilmentToNotification`. That projection is exactly what the real adapter sends the backend (real/lifecycle/mutate.js:25), and the backend compares only that notification content. Comparing anything else would break the criterion "just as it is against the animals backend".
   - Rejected: comparing raw encoded fulfilments. A document upload during an amendment would then count as a change. The backend refuses to count that, and records-port.test.js:372 pins it.
   - Rejected: also storing the submitted projection at amend time. That is a second copy of submitted state, which cancel and finalise would then have to clear too.
   - The review raised "running the real mapper on every read". Moving the comparison to save, against a stored flag, is the ruling's remedy. The mapper stays on the stub's save path because the comparison needs the projection.
9. **One owner per adapter for the stub's rule.** "Do the answers differ from the submitted version?" lives in one function in `stub/lifecycle/mutate.js`, next to `replaceFulfilment`, its only caller. The backend's twin rule stays in `NotificationService.answersDifferFromSubmitted` (NotificationService.java:502).
10. **Integration proof.** The row's repos are backend and frontend, so no tests-repo spec changes. The gate's tests-repo `e2e` rung already runs the end-to-end proof through the real stack:
    - `tests/animals/e2e/features/amend-review-title.spec.ts`: opened, then changed, then a document-only change.
    - `tests/animals/e2e/pages/notification-view-states.spec.ts`: the Submitted tag and view.

    Backend ITs prove the always-yes-or-no API, including put-back and a legacy record, over HTTP.
11. **Spec home for the API behaviour.** "The fulfilments read always says yes or no" goes in a new requirement in `live-animals/notification-lifecycle`, beside the backend fulfilments-read scenarios there (REQ-LIFECYCLE-009-D). The review-title scenarios for put-back and for a fresh amendment go under REQ-CYA-028. REQ-LIFECYCLE-010 gains the submitted date.
12. **The shared FIT cancel-amend sequence lives in `fit/live-animals-journey.js`.** The new check-answers test and the cancel-amend spec both need "amend from the list, change an answer, open the cancel-amend confirmation". The local `amendAndOpenCancel` (cancel-amend.fit.spec.js:36-41) is promoted, with the strip's cancel-amend link locator it uses (cancel-amend.fit.spec.js:22-27), and both local copies are deleted.

## 14. Departures from written rules

- **"DTOs | Records"** (`docs/best-practices/java/modern-java.md:662`). `NotificationFulfilmentsView` becomes a Lombok `@Value` class with a builder, not a record. Reason: the house rule "One concept, one name, from request header to repository" (`.claude/rules/code-quality.md`, Names). A record's accessor would be `answersDifferFromSubmitted()` beside the aggregate's `isAnswersDifferFromSubmitted()`; the `@Value` class gives both types the one accessor name. The guide's own table allows `@Value` for immutable value objects (modern-java.md:664).
