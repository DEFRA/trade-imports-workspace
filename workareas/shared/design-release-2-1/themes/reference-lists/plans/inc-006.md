What the live tree does today (checked):

- `services/countries/index.js` loads `GBNAG_SPS_EX` once (`fetchCountries(['GBNAG_SPS_EX'])`) and indexes each country's `subDivisions` into `subdivisionLabels` and `subdivisionToParent`. - The origin page (`features/origin/controller.js`) offers `originCountryOptions()`: countries plus subdivisions, sorted by `text.localeCompare`. Subdivisions there carry their **plain** names ("Canary Islands"), not "<territory> (<parent>)".
- The import-reason page (`features/import-reason/controller.js`) offers `countries.originCountries()` (countries only, in served order, after the placeholder and a disabled divider), and `validate.js`'s `countryRule` accepts only `originCountries()` codes.
- `originDisplayLabel(code)` already produces "<territory> (<parent>)" for a subdivision. The review page's origin row uses it; the review page's destination row uses `originLabel` (the plain name).
- The animals backend keeps `destinationCountry` as a free `String` (`NotificationBase.java`) with no validation, so a subdivision code saves without a backend change.
- Neither the plants frontend nor the germinal-products set has a destination country select (`grep destinationCountry` finds nothing in either), so the "plants mirrors" invariant asks for no plants change.

## 0. Decisions

1. **The label claim does not quite hold.** The ruling (p1-136 and p1-137) says the subdivisions are labelled "<territory> (<parent>)" *"as the origin page does"*. The origin page's select labels them by plain name. The label it describes is the one `originDisplayLabel` gives, which the review page and the dashboard use for the origin. AC3 states the label outright, so the plan follows AC3: each subdivision in the destination selects reads `<subdivision name> (<parent country name>)`. The origin page is left as it is (out of scope). Rejected: copying the origin page's plain names, which would contradict AC3.
2. **Order: sort by the label the user sees.** Countries and labelled subdivisions are merged and sorted with the same comparator the origin page uses (`left.text.localeCompare(right.text)`). Adding " (Parent)" to a subdivision moves it only where its plain name is a prefix of another entry's name. No such pair exists in today's fixture. Rejected: sorting by plain name and then labelling, which can leave the visible list out of alphabetical order.
3. **One new service reader, `destinationCountryOptions()`**, in `services/countries/index.js`, beside `originCountryOptions()`. The import-reason controller and `validate.js` both read it, so the list offered and the list accepted cannot drift. Rejected: labelling in the controller, which would split the list's rules across two layers. `originCountries()` stays: transit-countries and the review page still use it.
4. **Keep the disabled divider** under the placeholder on both destination selects. The reason page's selects are plain native selects (no type-ahead), and the origin controller's own comment says a scroll-only list keeps the divider. AC4's "after the empty placeholder option" holds: placeholder, divider, then the one sorted list. Rejected: dropping the divider, which would be an unasked layout change. Rejected also: adding the accessible-autocomplete. No criterion asks for it, and inc-089 and EUDPA-635 own search boxes.
5. **The review page's destination row reads `originDisplayLabel`**, so a chosen subdivision reads "Martinique (France)" there, as the select showed it and as the origin row already reads. Countries read exactly as before. Rejected: leaving `originLabel`, which would show a bare "Martinique" with no country.
6. **Stored answers need no migration** (AC6). The stored value is the code. Every code from today's 31-country list is still a country entry in `destinationCountryOptions()`, so `onStored` finds it and the select shows it selected. A stored code that the reference data no longer serves keeps today's "no longer available" behaviour.
7. **The integration proof's list-content tests are compose-only.** They compare against the tests repo's captured fixture, as `country-of-origin-list.spec.ts` does, through `skipUnlessComposeEnvironment`. The save-and-reopen tests read a territory from the rendered select instead of the fixture, so they run in every environment.
8. **No new copy**, so there are no Welsh drafts to add. The labels are reference data, and the parentheses format is code, as it already is in `originDisplayLabel`.
9. **Theme placement (the row's note):** the plan builds on the reference-lists branch, as the run is configured. The import-reason folder is touched only in its controller, its validator and their tests.

- Add, below `originCountryOptions`:

  ```js
  /** Countries and their subdivisions for a destination select, one alphabetical list, each subdivision named with its parent country. */
  export const destinationCountryOptions = async () => {
    await ensureLoaded()
    const countryOptions = Object.entries(labels).map(([value, text]) => ({ value, text }))
    const subdivisionOptions = Object.keys(subdivisionLabels).map((value) => ({
      value,
      text: subdivisionDisplayLabel(value)
    }))
    return [...countryOptions, ...subdivisionOptions].sort((left, right) =>
      left.text.localeCompare(right.text)
    )
  }
  ```

  The exemplar is `originCountryOptions` directly above. Use the same comparator. If lint's complexity or duplication rules complain, extract a shared `byText` comparator and use it in both.
