## 0. Decisions

**Criteria 1 and 2 already hold on `main`, with no code change, exactly as the 27 October and 6 November
re-analyses in the row's notes found.** `addressCountries()` (`services/countries/index.js:111-114`) returns the
United Kingdom together with whatever `labels` holds, sorted by the shared label comparator; `labels` is built
either from the stub fixture (`stub.js:7-9`, loaded from `_capture/fixtures/countries-origin.json`, 31 clean EU
entries with no subdivisions feeding this list) when `isStubMode()` is true, or from `fetchCountries(['GBNAG_SPS_EX'])`
(`index.js:36-48`) otherwise — with no filter, rename or edit of what either source returns. The private controller's
`countryItems` (`private-transporter-details.controller.js:88-98`) opens the select on the United Kingdom unless the
held value is itself an offered name. This is already proved: the controller unit test "Should open a fresh GET's
select on the United Kingdom, offering nothing but the offered countries in order"
(`private-transporter-details.controller.test.js:94-107`) and the FIT test "private transporter country select opens
on the United Kingdom and offers every country in alphabetical order" (`transporters.fit.spec.js:1011-1020`, built
from the same stub fixture via `countriesOriginEntries()`) both pass — I ran both (30/30 unit tests, 75/75 FIT tests
in `transporters.fit.spec.js`) to confirm, rather than take the row's notes on trust. No code or test changes for
criteria 1 and 2.

**Criterion 2's "nothing edited in code" for CDP test is a structural guarantee, not a new runnable check.** The
non-stub branch of `ensureLoaded()` (`index.js:36-48`) maps `{ code, name }` straight into `labels` with no filter or
rename, so whatever reference data serves is exactly what `addressCountries()` returns, United Kingdom prepended. No
service in this repo (countries, ports, commodities) has an established pattern for mocking the reference-data fetch
at the network boundary in a unit test, so building one here — just to re-prove a two-line pass-through this row
does not touch — is wider than this row's footprint. Recorded as a follow-up (section 7), proved here by the cited
file:line instead of a new test.

**Criterion 3's "and on the review" half is the one real gap, and it is untested at every layer.** I checked
`check-answers.test.js`, `check-answers.fit.spec.js` and `private-transporter-scope.spec.ts`: none asserts the
Transport details card's Country row for a private transporter. The production line already does this correctly —
`activeTransporterRows` (`check-answers/view-model/cards/movement/transport-details.js:37-45`) renders
`row(copy.rows.country, transporter.address?.country)` for whichever transporter type is active — and an exact
sibling unit test already exists for the **commercial** type ("Should expand the commercial transporter in the
transport-details card when the type is commercial", `check-answers.test.js:508-518`, unlinked from any spec
requirement). Closing the private-type gap, at the same three layers the row's other criteria already use
(unit, FIT, E2E), is this increment's one piece of real work.

**Each new test extends the existing duplication pattern rather than adding a new one.** The FIT and E2E tests this
row extends — `transporters.fit.spec.js`'s "saves and persists a complete private transporter record" and
`private-transporter-scope.spec.ts`'s one test — are the exact pair already linked under
SCN-PRIVATE-TRANS-002-B for the "shows on return to the form" half, and the E2E one already carries the
`@duplicated-in-frontend` tag the tests repo's README defines for "an end-to-end spec whose behaviour the
frontend's own FIT suite also proves". Extending both, rather than adding new spec files, keeps that pairing
symmetric. The unit test is a new sibling of the commercial one, in the same describe block.

**`rowFor` is promoted from `check-answers.fit.spec.js` to the shared FIT helper, not copied.**
`transporters.fit.spec.js` needs the same "find the summary-list row by its term" lookup
`check-answers.fit.spec.js` already defines locally (`:36-40`). `docs/best-practices/node/testing/frontend.md` §3
is explicit: "Set-up used by two tests goes in a shared helper... delete every local copy in the same commit." Home:
`fit/live-animals-journey.js`, beside the other simple page-locator helpers such as `journeyFormOf` (`:298`).
Rejected: a second, file-local copy in `transporters.fit.spec.js`, which is exactly the duplication the guide names.

**`AnimalsJourney.openReviewFromOverview` is made public, and its one inline duplicate is deleted, rather than
inlining a second copy of the same two-line sequence.** `docs/best-practices/playwright/BEST_PRACTICES.md` ("Reaching
the page under test") says a spec reaches a page through a `to*` method, and names exactly this shape of problem as
its "Bad" example: a short sequence of page-object calls inlined in a spec. `flows/animals/journey.ts:253-256`
already holds this sequence — `reviewAndSubmitButton.click()` then wait for `notificationView.heading` — as a
`private` method with three internal callers. `commercial-transporter-submission.spec.ts:31-32` already inlines the
identical two lines outside the class. Adding this row's own need for the same sequence in
`private-transporter-scope.spec.ts` makes it "used by two specs" in the guide's own words, which is the trigger to
promote rather than add a third inline copy. Decision: change the method's visibility only (no body change), replace
the spec's inline duplicate with a call to it, and call it from the new assertion. Rejected: leaving
`commercial-transporter-submission.spec.ts`'s inline copy as it is, which the guide's own rule says to delete "in the
same change" once a second use appears.

**Returning from the review to Overview afterwards uses the page object's own `open(referenceNumber)`, not a new
journey step.** This is a single navigation-by-URL, not a multi-page sequence, and the repo already calls it directly
from specs in several places (`reference-strip.spec.ts:35`, `amend-endings.spec.ts:28`,
`answerAccompanyingDocument` in `journey.ts:485`), each paired with `NotificationPage.referenceNumberFromUrl()`
captured from whichever page is current. No new mechanism.

**Spec sync homes the new behaviour under `check-your-answers`, not `private-transporter-details`.** The capability
that decides what the review draws is `check-your-answers`; no requirement there, or anywhere else, currently
records the Transport details card's row content for either transporter type — the existing commercial unit test
is itself unlinked. Scoped narrowly to the Country row for the private case, matching exactly what criterion 3 asks
for; the sibling commercial gap, and the rest of the card's rows, are a follow-up (section 7).
