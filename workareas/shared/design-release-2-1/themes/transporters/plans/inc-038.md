## 0. Decisions

1. **The row builds the animals frontend's own transporter pages, not the INS front
   door's.** `ruling:ian-2026-11-06` decision 8 says the add pages' home follows the
   address book hand-off, and leaves what becomes of
   `features/transport/transporter-add`, `…/private-transporter-details` and
   `…/commercial-transporter-details` to a re-distil that has not happened. Those three
   folders are live on this branch and still reachable from the journey's transporter
   list, and inc-074 added a parallel set of pages in the INS front door beside them
   rather than replacing them. Every one of this row's criteria names something only the
   animals journey has — a notification status strip, a "transporter type as it was" on
   the notification, the journey's own two add forms. So the row is carried out in
   `frontend` and `tests` exactly as its `repos` list says. Rejected: returning
   `ok:false` pending the re-distil, which would stall a buildable row whose pages a
   trader reaches today and which the design source describes verbatim.

2. **A blank choice is refused by swapping the type page's value-domain rule for the
   save-blocking one in the same module — and the page then stores and routes on the
   value that rule validated, not on the raw payload.**
   `lib/validate/validators.js:189` defines the lenient rule as allowing and accepting
   the empty string, which is why a blank choice passes today and
   `transporter-add.controller.js:64` routes it back to the list.
   `lib/validate/validators.js:156` is the save-blocking sibling, already exercised at
   `lib/validate/validate.test.js:181`, and takes one message that covers both a blank
   and an unknown value — which is exactly what criteria 4 and 5 ask for, one wording for
   both.

   The swap changes more than which values are refused, and the plan has to carry that
   through. The save-blocking rule builds its membership on a trimming string
   (`lib/validate/validators.js:167` and `:171`), and `lib/validate/run.js:19` runs every
   schema with conversion on, so the membership check sees the trimmed string where the
   lenient rule compares the raw one. A padded copy of an offered value therefore passes
   the new rule where it fails the old one. Today's controller does not use what its rule
   validated: `transporter-add.controller.js:75` builds the values it commits and routes
   on straight from the payload, and `:76` throws away what `validate` returned. Left
   that way, the padded value would be committed as the notification's transporter type
   and would open the private form — because with the empty-string arm gone the
   destination function returns the private slug for everything that is not exactly the
   commercial value — and the new add-form rule (decision 4) would then compare that
   stored value with the form's own type and bounce the trader back; decision 6's split
   would meanwhile read the same raw value and classify a whitespace-only post as a
   tampered one rather than the blank the rule refused it as.

   So the values the page re-renders, commits and routes on, and the blank-versus-
   unoffered split, all come from what the field rule validated. That is the repo's own
   mechanism, in a file this plan already cites as an exemplar:
   `addresses/party-edit/party-edit.controller.js:96` takes the validated value out of
   `validate` and `:109` commits what it built from it. The twin page built from the same
   design source does the same
   (`trade-imports-ins-frontend/src/server/app/features/address-book/transporter/transporter-type.controller.js:64`
   and `:68`). Nothing the rule accepts can then be stored or routed as a value that is
   neither Private nor Commercial. Rejected: keeping the lenient rule and adding a
   separate blank check in the controller, which would put the same refusal in two
   owners; and rejected: keeping the raw payload as the committed value and trimming it
   separately, a second owner for a normalisation the rule already performs.

3. **The page's one button gets its label from the feature's own copy, passed to the
   existing save-actions macro as its primary.** `shared/save-actions.njk` already takes a
   `primary` whose absence falls back to the shared save-and-continue wording
   (`shared/save-actions.njk:23` documents it, `:31` reads it, `:37` applies the
   fallback), and three journey pages already pass one
   (`transporters/transporters.njk:102`, `addresses/party-picker/_address-picker.njk:84`,
   `documents/template.njk:173`). The programme invariant forbids rewording a shared
   string in place, and the shared save-actions copy (`shared/copy.en.js:61`) has no
   Continue, so the word belongs in the transport feature's copy — as `check-answers`
   and `declaration` already hold their own (`check-answers/copy/copy.en.js:106`,
   `declaration/copy/copy.en.js:30`). Rejected: adding Continue to `shared/copy.en.js`,
   which would hand a page-specific label to every page.

4. **One owner decides which chosen type opens an add form, in a new module in the
   transport feature, and `transporter-details-save.js` runs it on the POST side.** The
   rule applies to two pages, so it cannot live in either controller. Both controllers'
   POSTs already funnel through `transporter-details-save.js`, so that file takes the
   required type as a value in the `details` object it is already given and asks the owner
   before it reads the payload; each controller's own `get`
   (`private-transporter-details.controller.js:141`,
   `commercial-transporter-details.controller.js:128`) asks the same owner before it
   renders. That is three call sites and one rule. The signature change to
   `saveTransporterDetails` is this row's own behaviour, not clean-up, so it is in
   scope. Rejected: a guard option on `shared/kit.js:460`'s route builder — that is L2
   platform with a whole-journey blast radius for a rule two pages need; and rejected:
   a copy of the check in each controller, which breaks one rule, one owner.

5. **The add-form redirect logs the way the repo logs a redirect away from the normal
   next page: one line straight through `request.logger`, not the refusal logger.**
   `src/server/app/docs/architecture.md:190-192` puts "a redirect away from the normal
   next page" in the first group — "logs once through `request.logger`", carrying
   `journeyId`, the reason and the values the decision turned on. Every redirect branch in
   this repo does exactly that and none of them calls `kit.logRefusal`: the nearest
   sibling is in this very feature, `transit-countries.controller.js:128-141`
   (`redirectToOverviewUnlessApplicable`, called from both `get` and `post`), which logs
   the journey id, a named reason and the answer the decision turned on;
   `commodities/consignment-details/consignment-details.controller.js:90-96` does the
   same for its own nothing-to-ask redirect, and `declaration/controller.js:79-90` for its
   refused Continue. `kit.logRefusal` is the wrong home twice over: `shared/kit.js:118`
   fixes its message at "Answer refused, page shown again", which would be a false
   statement about a trader who was redirected to a different page, and
   `architecture.md:199-201` scopes it to "every other refusal that shows the page again".
   So the redirect's log home is `request.logger`, and its exemplars are the three
   redirect guards above. Rejected: `kit.logRefusal`, for the two reasons just given.

6. **The type question's refusal of a value it never offered logs once; a blank choice
   does not — and the two are told apart by the validated value.**
   `architecture.md:199-201` names "a tampered post" among the refusals that must call
   `kit.logRefusal(request, { ...details })` once before rendering, and the same doc's
   preceding paragraph (`:196-199`) excludes "a blank answer" as the user's own input. One
   field rule refuses both with one message, so the controller tells them apart by what
   the rule validated (decision 2): a value naming no type at all — absent, because
   unchecked radios post nothing, or empty after the rule's own trim — is the trader's
   own blank; anything else the rule rejected never appeared on the page. This feature
   already owns that split — `transit-countries.controller.js:114-126` logs its refusal
   unless the reason is the user's own input, over reasons its own `validate.js` names —
   and the type question's split is the simpler one-case form of it. The line carries the
   journey id, the route and the refused value, so support can tell a tampered post from a
   trader's slip. The existing assertion that no refusal is logged on the unoffered value
   (`transporter-add.controller.test.js:118`) is therefore wrong after this change and
   moves to the blank-choice test, with the unoffered-value test asserting one refusal
   logged instead. Rejected: leaving the unoffered value unlogged on the ground that the
   commercial form's fixed-country rule
   (`commercial-transporter-details.controller.js:86`) logs nothing for its own tampered
   post — that is a breach in a neighbouring file, not a licence; it sits outside this
   row's footprint and goes to section 7 as a follow-up. Rejected: splitting on the raw
   payload, which decision 2 shows misclassifies a whitespace-only post.

7. **The status strip is withheld through the option `kit.base` already has.**
   `shared/kit.js:341` documents `showJourneyStrip: false` as the way a journey page shows
   no strip, `sets/live-animals/docs/add-a-page.md:102` states the same, and two pages
   already use it (`declaration/controller.js:63`, `confirmation/controller.js:26`). The
   type page and the private form take it; the list and the commercial form keep the
   default, which is what criterion 7 asks of them. Rejected: a per-page flag in

8. **The INS twin's blank-choice wording disagrees with the design source, and is a

9. **The fit suites' "reach the type question and choose a type" set-up is promoted to

11. **The strip's unit proof goes in the features-wide strip invariant test, the

12. **Criterion 6's POST arm is proved at unit and the GET arm at unit, fit and e2e.** A
    browser cannot post to a page it is not on, so the e2e proof of the POST arm would
    need a contrivance. The handler-level test drives the POST directly with a

    trader can actually walk, opening the form with the wrong type stored.

13. **"Entry guard" is not this rule's concept word: the repo already owns it for the
    journey-level redirect policy.** `journeys/linear/flow/entry-guard.js` "owns the
    journey's redirect policy before handlers run", and
    `sets/live-animals/docs/journey-flow-and-gates.md:99-103` gives it a section of its

    describes, under Task rows at `journey-flow-and-gates.md:89-97` — a page that "says so
    itself" and redirects when it has nothing to ask, as `consignment-details` and
    `transit-countries` do. So the new module, its exported function, its log's named
    reason, the spec requirement's wording and the test titles all take a concept word of
    their own, drawn from what the rule actually says — that an add form opens only for the
    transporter type it belongs to — and never the words "entry guard". One concept, one
    name, across the set. Rejected: calling it an entry guard because it guards an entry,
    which would give the set two unrelated things one name. The word itself is the
    implementor's to choose; this plan only fences it off.

14. **The words the heading and the visually hidden legend share get one home in the copy
    bundle, read twice by the template.** The design source gives the page a visible
    heading and a visually hidden fieldset legend carrying the same words
    (`prototype-dr2-1-source-p7-049` quotes the heading, `-p7-053` the legend), which is

    (`trade-imports-ins-frontend/src/server/app/features/address-book/transporter/transporter-type.njk:25`
    against `…/features/address-book/copy/copy.en.js:131`), and this very feature already
    does it on the list page, where one key is rendered as a heading and as a visually
    hidden legend (`transporters/transporters.njk:64` and `:91` both read
    `copy.resultsHeading`). So the legend key goes and the template reads the title key
    for both. Rejected: keeping both keys with equal values and a test that asserts they
    agree, which pins a duplicate instead of removing it. The duplication this leaves on
    screen — one question announced as both the heading and the group name — is a
    departure from the repo's govuk-frontend guidance that the design source requires;
    section 14 records it and section 7 carries the question for the designer.

## 13. Operability

Two branches this change adds alter an outcome.

**The add-form redirect**, when a trader opens or posts an add form whose type is not the
one chosen on the notification. It logs once, straight through `request.logger` at info —
the home `src/server/app/docs/architecture.md:190-192` gives "a redirect away from the
normal next page", and the form `transit-countries.controller.js:128-141`,
`commodities/consignment-details/consignment-details.controller.js:90-96` and
`declaration/controller.js:79-90` all take. One line per redirect, from the one owner in
section 3, so the GET and POST sides cannot log twice or differently. It must let support
find which notification it was, which route was asked for, which type that form belongs
to and which type the notification actually held, and it must read as a redirect, so that
a trader reporting "it keeps sending me back" is traced to the stored answer that sent
them. `kit.logRefusal` is explicitly not used here: its message is fixed at
`shared/kit.js:118` to say the page was shown again, which is not what happened.

**The type question's refusal of a value it never offered.** That is a tampered post,
which `architecture.md:199-201` requires to log once through `kit.logRefusal` before the
page renders. It logs the field's error code, the refused value as the rule read it and a
named reason, so support can tell a tampered post from a trader's slip, at the logger's
default level — no other service refused anything here. A refusal on the same branch whose
validated value names no type is the trader's own input shown back on the form and logs
nothing, which the same doc's preceding paragraph requires. The two assertions keep them
apart: the blank-choice test asserts no refusal logged, the unoffered-value test exactly
one.

The strip and copy changes add no branch.
