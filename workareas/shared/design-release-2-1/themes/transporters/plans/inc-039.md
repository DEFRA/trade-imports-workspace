## 0. Decisions

1. **The row builds the animals frontend's own journey add forms, not the INS front door's.** The 6
   November ruling (decision 8) leaves what becomes of `features/transport/transporter-add`,
   `…/private-transporter-details` and `…/commercial-transporter-details` to a re-distil that has not
   happened; all three are live on this branch and reachable from the journey's transporter list, and
   inc-074 added a parallel set of pages in the INS front door beside them rather than replacing them.
   Every criterion of this row names something only the animals journey has — a notification whose chosen
   transporter must be left alone, a return into the journey's own transporter list, a cancel that leaves
   the notification journey for the dashboard. The row is therefore carried out in `frontend` and `tests`
   exactly as its `repos` list says, which is also the decision inc-038's plan took on the same question.
   Rejected: returning `ok:false` pending the re-distil, which would stall a buildable row whose pages a
   trader reaches today and whose behaviour the design source describes verbatim.

2. **The row's notes ask for the save and cancel to be rewritten to the address-book hand-off; the live
   tree says the persistence half of that is already done and the hand-off half belongs to other rows.**
   Note 3 on the row predicted that `services/transporters/register.js`'s in-memory `Map` would have to
   become a real address book record. That file no longer exists: `services/transporters/client.js` now
   POSTs and GETs `/organisation/{orgId}/transporters` on the address book, `services/transporters/index.js`
   joins the organisation's own records ahead of the shipped ones, and the two add forms already persist
   through it (`private-transporter-details.controller.js:201`–`:206` and
   `commercial-transporter-details.controller.js:197`–`:202`). So the row's detail — added transporters
   "belong to the organisation, so they stay on its list for later notifications" — already holds, and
   this row changes only where a save lands, what it says, the two end controls, and what happens to values
   a refused save left behind. The hand-off's own add pages, their Transporter tab and their details page
   are inc-074 (merged), inc-075 and inc-076. Rejected: re-planning the add pages as a hand-off here, which
   would duplicate inc-074's pages and widen the row into `insfrontend` and `addressbook`, neither of which
   is in its `repos`.

3. **Where a saved add lands changes for a complete record only; a blank form keeps walking on.**
   `transporter-details-save.js:54`–`:57` already distinguishes the two: without a record it only re-reads state,
   with one it commits. The first criterion speaks of "saving a complete private or commercial
   transporter", and the banner's own criterion of a transporter having been "added", so the blank post —
   which adds nothing and names nothing — keeps today's destination through
   `continue-from-transporter-list.js` and shows no banner. That also keeps
   `private-transporter-details.controller.test.js:152` and
   `commercial-transporter-details.controller.test.js:216` true as they stand, and keeps
   `continue-from-transporter-list.js` alive rather than orphaned. Rejected: sending the blank post to the
   list too, which would strand a trader who had decided not to add one on a page with nothing chosen, and
   change behaviour no criterion asks for.

4. **A save made from a Change link on the review now lands on the transporter list as well, carrying the
   change context, so the list's own save returns to the review.** The first criterion admits no exception,
   and `commercial-transporter-details.controller.test.js:204` is the only test that pins the old
   behaviour. The redirect therefore goes through `kit.withChangeContext`, the same way each add form's
   own back link already does (`private-transporter-details.controller.js:111`), so a trader who came from
   the review sees the new transporter chosen on the list and reaches the review from the list's own save.
   Rejected: keeping `kit.nextTarget` for a change-context save, which would hide the new row and its
   banner from exactly the trader who had gone looking for the transporter answer.

5. **Cancel is a secondary submit control, not a link.** The design source renders it as a secondary submit
   carrying an action value on both add pages (trace-prototype-dr2-1-p9-030, -p9-066) and the row's fourth
   criterion calls for "exactly two controls". It also has to be a post: cancelling discards the values a
   refused save left behind (prototype-dr2-1-source-p7-083, the row's sixth criterion), which is a write,
   and this repo's cross-site-request protection covers posts, not GET links. Rejected: a link in the shape
   of `shared/save-actions.njk:72`'s overview cancel and of the INS twin's
   `features/address-book/transporter/private-transporter.njk:107`, which cannot discard anything and would
   need a second mechanism to do so. The twins differ here because the behaviours differ: the INS form keeps
   no unsaved values.

6. **The secondary control goes through the existing save-actions macro, not beside it.**
   `shared/save-actions.njk` already documents and honours a caller-supplied `primary` with its own name
   and value (`shared/save-actions.njk:23`, `:31`, `:37`; exercised at `shared/save-actions.test.js:72`),
   and three journey pages pass one. An optional secondary beside it extends that mechanism and keeps "how
   a page ends" in one owner for both add forms. Rejected: each add template rendering its own
   `govukButton` next to `saveActions`, which would put one page's end controls in two owners and copy the
   same markup into two templates.

7. **Both the values a refused save left behind and the one-time banner live in the journey's own
   session, as flow-only answers.** `flow/flow.js:24` already registers a feature-owned flow-only key
   (`STORED_SEARCH_ROWS`, imported at `:22`), written with `state.commit` and read back from the request
   view's `flowOnlyAnswers` (`features/commodities/search/selection/rows.js:35` and `:41`); a patch holding
   only flow-only keys never reaches the backend (`engine/write/pipeline/canonical.js:48`) and lands in the
   yar-backed session (`services/persistence/session/real.js:61`), which is per journey and encrypted or
   server-side. The values are a trader's name, address, email and telephone, so a browser cookie is the
   wrong home for them on size and on content. Rejected: the `addedAddressBanner` cookie pattern at
   `features/addresses/ins-handshake.js:60`–`:75`, which is set with `h.state` and documented as bypassing
   the session port (`src/server/app/docs/persistence.md:51`): it is not keyed by journey, and the add
   form's values could not go in it, so taking it for the banner alone would split one piece of
   add-in-progress state across two stores. Rejected also: a query parameter in the shape of the
   dashboard's deleted banner (`features/dashboard/controller.js:57`), which cannot satisfy "reloading the
   list shows no banner" because a reload re-sends the same address.

8. **Two flow-only keys, one owning module.** The values survive until the form is saved or cancelled; the
   banner survives exactly one render of the list. Separate keys keep each lifetime its own, and one module
   in the transport feature owns writing, reading and clearing both so the save path can clear one and set
   the other in a single commit. Rejected: one key holding both, which makes two lifetimes share one
   value and invites a partial clear.

9. **No nameless banner is built.** The second criterion says a banner with no name reads "Transporter
   added", but no saved transporter can have a blank name: both forms treat any entered field as the start
   of a record and then require the name (`private-transporter-details.controller.js:31`–`:39` with `:80`
   and `:83`; `commercial-transporter-details.controller.js:37`–`:45` with `:96` and `:99`), and a wholly blank post saves
   nothing at all (decision 3). A nameless-banner arm would be a branch for a state the service cannot
   reach, which the house rules forbid building. What is built instead is the named banner plus the
   existing refusal of a blank name. Rejected: building the fallback anyway to match the criterion
   verbatim — see section 15 and the departure in section 14.

10. **Cancel writes nothing to the notification, which leaves the fifth criterion satisfied on the walk
    that keeps the stored type and unsatisfiable on the walk that changes it.** Two walks reach an add
    form, and cancel behaves identically on both — it reads the action, discards the unsaved values and
    redirects — so what the trader is left with differs only by what the type question already did:

    - **The stored type is the form's own** (the trader had a private transporter chosen and picks Private,
      or nothing was chosen yet). The type question's commit at
      `transporter-add/transporter-add.controller.js:101` writes the same value it already held, so
      `privateTransporter`/`commercialTransporter` stay in scope
      (`sets/live-animals/obligations/sections/transport.js:38` and `:53`) and nothing is purged. Cancel
      then leaves the notification exactly as it was before the add began: the same transporter chosen, or
      still none. The fifth criterion holds, and tests 20, 30 drive this walk.
    - **The trader changes the type at the type question on the way in** (a commercial transporter was
      chosen, they pick Private). That same commit flips `transporterType`, and the flip deletes the other
      type's stored transporter before the add form is ever rendered —
      `sets/live-animals/obligations/sections/transport.js:33`–`:34` states the purge and
      `equalsGate(transporterType, …, { inScope: false })` at `:38` and `:53` carries it out, proved today
      by `tests/animals/e2e/features/private-transporter-scope.spec.ts:56`–`:57`. By the time cancel runs
      the notification already has the new type and no transporter, and
      `src/server/app/docs/scope-and-wipe.md:13`–`:15` records that this is one-way: "when a controlling
      answer makes a value leave scope, the value is deleted. Returning to the earlier branch does not
      restore stale data." Cancel therefore cannot leave the chosen transporter as it was before the add
      began, and nothing in this row's footprint can make it: the loss is the type question's, not the
      cancel's. Recorded as departure 4 in section 14, with the criterion and the purge quoted, and
      proved as it is by test 21.

    Rejected: adding an undo for the type answer — the engine has no restore operation, and writing the
    previous type back would re-run the gates on a record that has already been deleted, so the trader
    would be left with neither transporter and a type they did not choose. Rejected: moving the type
    answer's commit off the type question and carrying the chosen type to the add form as flow-only state
    until a save, which does make the criterion hold on both walks but redesigns the add route — it would
    stop the flip purging at all (the proved behaviour at
    `private-transporter-scope.spec.ts:48`–`:57` depends on a blank commercial save flipping the type and
    wiping the private details, and under deferral a blank save commits nothing, decision 3), change what
    `own-transporter-type.js` guards on, and change the obligation gates' input. That is the type
    question's own redesign, well outside this row; section 7 carries it as a follow-up.

11. **Cancel is read before the own-type guard.** `transporter-details-save.js:32`–`:39` currently redirects to
    the type question before anything else when the stored type is not the form's own. Cancel must take the
    trader to the dashboard whatever the stored type is, and it reads no answer and writes nothing to the
    notification, so the guard protects nothing on that path. Rejected: guard first, which would answer a
    cancel with the type question and contradict the fifth criterion.

12. **The sentence-case rule lives in one function outside the copy modules.** The banner's English and
    Welsh wording each take an already-cased name, so the casing rule is not written twice.
    `.claude/rules/copy.md` and `copy-parity.test.js:106` require the two locales' leaves to match in kind
    and arity, which a function of the name satisfies. Rejected: casing inside each locale's text function,
    which would give one display rule two owners.

13. **The cancel label and the banner wording go in the transport feature's own copy.** The programme
    invariant forbids rewording shared copy in place, and `shared/copy.en.js:61`'s save-actions block holds
    only the overview controls while `:74`'s address-handshake block holds the address book's own added
    banner. The transport feature already owns a page-specific button label
    (`features/transport/copy/copy.en.js:152`). Rejected: adding either string to `shared/copy.en.js`,
    which would offer one feature's wording to every page.

14. **The POST owner gains no new `details` member.** The bag at
    `transporter-details-save.js:11`–`:18` carries "the parts that differ between the commercial and
    private transporter pages", and nothing this row adds to that handler differs between them: the kept
    values are keyed by the `transporterType` it is already given, the cancel's destination and the banner
    record are the same on both pages, and the name the banner shows comes from the one payload field both
    forms already share — `nameOrOrganisationName`, in each form's own field order
    (`private-transporter-details.controller.js:42`, `commercial-transporter-details.controller.js:49`) and
    mapped to the record's `name` by each form's record builder
    (`private-transporter-details.controller.js:183`, `commercial-transporter-details.controller.js:179`).
    So the handler reads the saved name off the trimmed values it already holds at `:42`. Rejected: a new
    member per form giving the name, which would add a second name for one concept the two forms already
    agree on, and put a part that does not differ into a bag documented as the parts that do.

15. **The tests that prove the added transporter heads the list run against a transporter store no other
    test writes to, by signing in as an organisation of their own.** In FIT the stub store is a
    module-scope `Map` in the single server process
    (`src/server/app/services/transporters/stub/index.js:3`) whose reset
    (`:28`) is only ever wired into vitest (`features/transport/test-support.js:53`–`:55`), the suite is
    `fullyParallel` over many workers (`playwright.config.js:16`), every session signs in as the same
    organisation by default (`fit/sign-in.js:5`, `src/server/auth/stub-sign-in.js:23`) and tests already
    add transporters to it (`features/transport/fit/transporters.fit.spec.js:378`,
    `features/transport/fit/commercial-transporter-details.fit.spec.js:222`), so another worker's add can
    become the newest row between this test's save and its assertion. `fit/sign-in.js:5` already takes an
    `organisationId`, and the store is keyed by it, so an ordering test signs in with its own id before it
    starts its journey and reads a list only it has added to — the shipped records plus its own. The
    mechanism is that parameter, reached through the shared helper in section 11.
    In the tests repo there is no such lever: every e2e worker signs in with the same credentials
    (`fixtures/auth-state.ts:134`–`:151`, `:89`–`:129`), so the browser's organisation cannot be varied per
    test, and the one isolated-organisation fixture (`fixtures/ui.ts:145`) scopes an API client only. The
    end-to-end ordering assertion is therefore made relationally: the spec reads the names the list shows
    before the add, and afterwards asserts the added transporter sits above every one of them. A
    concurrent add by another worker inserts a row that is not among the names read, so it cannot disturb
    that assertion, while the absolute "first row" of the criterion is proved in FIT under the isolated
    organisation. Rejected: asserting index zero in e2e, which another worker's add can break and which
    the house rules forbid loosening later; rejected: a serial e2e project, which would slow the whole
    suite for one spec and still not stop another spec file's add.

16. **One home for the e2e per-test transporter cleanup: a cross-domain helper under `utils/`, which the
    two INS specs follow to.** `transporterIdsDeletedAfterEachTest` lives today in
    `tests/ins/e2e/features/transporters/run-transporters.ts:11`–`:19` and is reached only by its two
    siblings through a relative import
    (`tests/ins/e2e/features/transporters/private-transporter.spec.ts:9`,
    `…/commercial-transporter.spec.ts:9`); nothing under `tests/animals` imports anything under
    `tests/ins`, and `tsconfig.json`'s aliases reach none of `tests/`. The animals spec needs the same
    rule — every transporter a test creates is removed from the organisation afterwards — and one rule has
    one owner, so the registrar moves to a file of its own under `utils/`, which `tsconfig.json:21` already
    aliases as `@utils/*` and which `AGENTS.md:16` names as the repo's cross-domain helper folder; it is
    outside `**/shared/**`, so the domain-import restriction at `eslint.config.mjs:25`–`:45` does not
    apply, and `utils/transit-countries-assertions.ts:1` shows a `utils/` helper importing `@fixtures` as
    this one must. The two INS specs then import it from there. This is a structural decision the row
    needs, not clean-up: it changes two call sites, and section 7 does not scope them out. Rejected: a
    second copy of the registrar in the animals domain, which gives one rule two owners, and whose body
    the gate's duplication rung on changed test files would read as a copied block. Rejected: leaving it
    in the INS folder and importing across domains, which is the one shape the repo's import conventions
    and aliases do not offer.

## 14. Departures from written rules

1. **The nameless banner the second criterion describes is not built.** The criterion says "with no name it
   reads 'Transporter added'". House rule, `.claude/rules/code-quality.md`: "Build only what this change
   makes reachable" and, in this brief, "name the backlog row that reaches it, or leave it out". No saved
   transporter can have a blank name (decision 9) and no backlog row makes that state reachable, so the arm
   is left out. The criterion's named case is built and proved; the nameless case is recorded here instead.
2. **The banner lowercases the rest of a transporter's name, which the GDS guidance this workspace keeps
   does not.** `docs/best-practices/gds/language.md:81`: "Proper nouns keep their capitals in a hint as
   anywhere else (Great Britain, Northern Ireland)." The design source sets the opposite for this banner,
   with a worked example — prototype-dr2-1-source-p7-046 ("'ACME Haulage' shows as 'Acme haulage
   transporter added'"), trace-prototype-dr2-1-p9-040 and prototype-dr2-1-specs-p2-121 ("Hill haulage
   transporter added") — and the house rules say to build copy as the design source sets it. Built the
   design source's way; recorded for a reviewer to raise with the designer if they wish (section 15's
   risk).
3. **The two add forms' cancel is a button where the INS front door's twin and this repo's overview cancel
   are links.** `src/server/app/sets/live-animals/docs/page-design.md:44`–`:45` describes the overview
   cancel as a link below the buttons. The design source sets a secondary submit here and the control has
   to write (decision 5), so this page ends differently; the page-design doc gains that fact (section 12,
   hit 3).
4. **The fifth criterion does not hold on the walk that changes the transporter type, and nothing in this
   row's footprint can make it.** The criterion: "'Cancel and return to dashboard' on either add form, even
   with partial or invalid values entered, shows no error, adds no transporter, leaves the notification's
   chosen transporter as it was before the add began, and takes the trader to the dashboard, wherever the
   notifications list lives." Against it,
   `repos/trade-imports-animals-frontend/src/server/app/sets/live-animals/obligations/sections/transport.js:33`–`:34`:
   "Purge-on-flip: switching transporterType from 'Commercial' to 'Private' drops any stored
   commercialTransporter address", carried out by the `equalsGate(transporterType, …, { inScope: false })`
   arms at `:38` and `:53` and proved today by
   `repos/trade-imports-ins-tests/tests/animals/e2e/features/private-transporter-scope.spec.ts:56`–`:57`;
   and `repos/trade-imports-animals-frontend/src/server/app/docs/scope-and-wipe.md:13`–`:15`: "when a
   controlling answer makes a value leave scope, the value is deleted. Returning to the earlier branch does
   not restore stale data." Reason: the type question commits the new type
   (`transporter-add/transporter-add.controller.js:101`) before the add form is ever rendered, so the
   previously chosen transporter is already gone when the trader reaches the form and there is nothing for a
