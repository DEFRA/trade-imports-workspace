## 0. Decisions

1. **The first acceptance criterion wins over the eleventh on where the Transporter radio sits and what
   hint it carries; the eleventh is a stale variant of the same requirement, not a second one.**
   The two contradict each other: criterion 1 puts Transporter third, before Branch, hinted "Private,
   Commercial"; criterion 11 puts it after a "Place of Destination" option and before a divider, hinted
   "This is the person or company responsible for transporting the consignment." Read against the design
   source: Design Release 2.1's own four-category list is `app/data/address-book-add-categories.js:16-21`
   ("value: 'transporter', text: 'Transporter', hint: 'Private, Commercial'"), its rendered trace shows
   "Transporter / Private, Commercial" third of four, and its driving spec asserts exactly four labels in
   that order with that hint (`prototype-specs/e2e/address-book.fit.spec.js:80-83`). Criterion 11's wording
   comes from `app/data/address-book-address-types.js:27-31`, the seven-type Design Release 1 list, which
   the 2.1 mount does not render: that list has a "Place of Destination" type and a divider, and the page
   the address-book theme built has neither — three options whose hints group roles
   (`insfrontend:src/server/app/features/address-book/copy/copy.en.js:91-101`). So criterion 11 is dropped
   as a stale duplicate and criterion 1 is built. This is the check the row's own 27 October note asked
   for. Rejected: building criterion 11, which would need a "Place of Destination" option and a divider
   that the live page does not have and no 2.1 source asks for.

2. **Criterion 2's "'Back' link returns to 'Choose an address type'" and criterion 6's "Back link goes to
   the address book's add page" name the same page, and the Back link goes to the type question.** In the
   prototype `/address-book/add` *is* the type question and `/address-book/add/lookup` is the form; in the
   real service `shared/paths.js:4-5` makes `/address-book/add` the form and
   `/address-book/add/address-type` the question. Both criteria therefore mean "back to the type
   question", which is also what the design source's own branch says
   (`prototype:dr2-1-source p7-051`: the type page's back link goes to the address book's add page when the
   add came from the address book). Rejected: reading criterion 6 by URL shape and sending the trader to
   the address form, a page they never opened.

3. **A transporter is its own record on its own address-book route, never an `Address`.** Ruling decisions
   4 and 5. It reuses the service's organisation scoping (`filter/IdentityHeaderFilter.java:56` filters
   every `/organisation/**` path, so the new route is scoped with no new filter), its soft-delete
   tombstone, its optimistic locking, its outside-prod expiry stamp
   (`address/AddressService.java` `stampExpiry` and `configuration/AddressTtlConfig.java`) and the Standard
   Address Block field rules. Rejected: a seventh `AddressRole` and a fourth `RoleGroup`
   (`address/AddressRole.java`, `address/RoleGroup.java`), which the ruling forbids and which would make
   the receiving-roles-in-the-United-Kingdom rule and the three role groups meaningless, and which
   `AddressRequest`'s `@NotEmpty` roles and `@Null` type could not carry anyway.

4. **The Transporter address type gets its own branch in the INS front door, and the role map gains no
   entry for it.** This is the concrete blocker the 6 November re-analysis named:
   `services/address-book/address-types.js:1-29` maps every address type to a role set, and
   `features/address-book/address-book-tabs.js:6-17` and `list/list.controller.js` read the tabs straight
   off that map, so adding the type the obvious way would demand a role set the ruling forbids. The fix is
   to stop treating "the address types the service offers" and "the roles an address type groups" as one
   list: one owner says which types the question offers and which tabs the list shows, and the role map
   keeps only the three types that group roles. Rejected: a role set for the Transporter type (ruling
   decision 5), and a second type enumeration beside `ADDRESS_TYPES` (a second mechanism).

5. **The transporter record stores no approval status in this row.** Ruling decision 10 says the concept
   needs its own name rather than the soft-delete status *if* it is stored; decision 3 parks approved
   transporters, so every transporter an organisation adds is not yet approved and the field would have
   exactly one reachable value. So the animals list's Status tag reads the not-yet-approved word from the
   one function that maps an address-book transporter onto a list row, and nothing is persisted. inc-265
   (blocked) is the row that reaches the second value. Rejected: persisting the status now, which rule 15
   forbids.

6. **A commercial transporter's country is the stored code the ruling fixes, with its display word a
   constant beside it, and a tampered value is refused rather than corrected.** Ruling decision 6, and the
   pattern already in the animals frontend
   (`commercial-transporter-details.controller.js:84-87` refuses a posted country that is not the fixed
   one). No reference-data lookup, in the form or in the service. The address book enforces it as a
   class-level rule beside the two it already has
   (`address/ReceivingRolesInTheUnitedKingdom.java`, `address/RolesHeldTogether.java`). Rejected: deriving
   Northern Ireland from the postcode, and reusing the United Kingdom code, both of which the ruling rules
   out. Ruling point 11 asks what happens to records captured before the change: there are none — the
   animals frontend's store is a per-process in-memory map (`services/transporters/register.js:3`) that is
   lost on restart, so nothing outlives the change and no migration is needed.

7. **The address book becomes the one store for an organisation's own transporters, and the animals
   frontend's in-memory register goes.** Ruling decisions 1 and 7 say so outright. Keeping the register
   beside the new route would put a second mechanism next to the one the ruling names, and would make
   criterion 10 true for transporters added one way and false for the other. So the animals frontend's two
   transporter detail controllers write through a transporters client, the transporters barrel reads the
   organisation's transporters from it, and `services/transporters/register.js` and its tests go. This
   changes callers — the barrel (`services/transporters/index.js:10-33`), both detail controllers and the
   list's validation (`features/transport/transporters/validate.js:13-19`) — which is a structural change
   the row needs rather than a widening: without it criterion 10 cannot hold. Rejected: merging a
   surviving register with the address book's list, and leaving the register alone and reading only the
   address book, which would silently drop the journey's own adds.

8. **The register's silent replace-by-name goes with it; duplicates are prevented by the warning the
   design source puts on the type question.** `services/transporters/register.js:30-42` corrects a
   transporter re-entered under the same name rather than adding a second row. The address book has no
   upsert by name, and the design source's own answer to duplicates is the warning criterion 4 quotes.
   A find-by-name-then-replace against the new route would be a rule no source states, and a race between
   two instances. Rejected: name-keyed upsert on the new route.

9. **This row builds the Transporter tab, its table and its search; inc-075 keeps the Type filter.**
   Criterion 8 needs the new transporter at the top of "the address book filtered to transporters"
   carrying its approval number, and criterion 9 needs a search over it — neither can be shown without the
   tab and a column for the approval number. So the tab, its position, its heading, its columns and its
   search land here. inc-075 is left with its Type filter; its second criterion (a Type column reading
   "Transporter" on the tabs that show one) cannot hold once a transporter is not an address, and goes to
   section 7 as a re-distil. Rejected: landing the save on the default tab, which contradicts criteria 7
   and 8.

10. **The transporter add pages are an address-book-started route only in this row.** Criteria 6, 7 and 8
    are each conditioned on "when adding a transporter was started from the address book", and no
    criterion here describes a journey-started add. Rule 15: the pages carry no journey-handshake branch
    yet, and `features/address-book/handshake-context.js` and `journey-registry.js` are untouched. The
    journey hand-off is inc-038 and inc-039's, which now wait on this row. Rejected: building the
    handshake mode now, whose only caller would be a later row.

11. **The identity filter's path-mismatch refusal stops naming addresses.**
    `filter/IdentityHeaderFilter.java:86-91` answers a path-organisation mismatch with a detail that says
    an address was not found. Once that filter also guards a transporters path, the detail is wrong for
    half the requests it refuses. One concept, one name: the detail names what the filter actually
    refuses. In footprint because the change is what makes the line wrong.

12. **The tests repo's and the INS frontend's single "unsupported value" stand-ins become two concepts
    each.** `tests:domain/ins/constants/address-book-types.ts:71` is used both as an address type no tab
    offers (`tests/ins/e2e/features/address-book/address-book-tabs.spec.ts:56`) and as a role outside the
    six (`address-book-roles.spec.ts:98,112`); the INS frontend does the same
    (`features/address-book/fit/address-book-list.js:11`,
    `features/address-book/address-type/address-type.controller.test.js:35`,
    `features/address-book/address-book-tabs.test.js:32,57`). Transporter stays a value that is not a role
    (decision 3) but stops being an unknown address type, so the two readings get two homes and two values,
    neither of which is a real address type or role.

13. **The address book's paging bounds and its search-term-to-pattern rule get one owner the two routes
    share.** `address/AddressService.java` holds `MIN_PAGE_SIZE`, `MAX_PAGE_SIZE`, `DEFAULT_PAGE_SIZE`,
    `servedPageSize` and `toPartialMatchRegex`; the transporters route needs the same rules. One rule, one
    owner: they move to a home in the service both read, and the addresses service reads them from there.
    This touches `AddressService` and `AddressComplianceIT`'s import of `DEFAULT_PAGE_SIZE`. Rejected:
    copying the bounds into the new service, and having the new service import them from the addresses
    service, which would make the addresses feature the owner of a rule neither feature owns.

14. **In the tests repo the Transporter address type is a value of the shared address type list, and the
    maps that exist only for the add form's roles question are re-keyed to the address types that ask it.**
    `tests:domain/shared/constants/address-types.ts:1-7` owns the address type values and the `AddressType`
    they make, and `tests:domain/ins/constants/address-book-types.ts` keys two total maps on that type:
    `rolesQuestionOptions:73-77` (the roles each type's add form offers) and `rolesQuestionLegends:110-114`
    (that question's legend). A fourth member of the union makes both maps incomplete, which `npm run
    typecheck` fails, and `tests/ins/e2e/features/address-book/address-book-add-roles.spec.ts:40-44` reads
    both for every tab at module load, which would hand the Transporter tab undefined. So the value joins
    the shared list — one concept, one name, matching the INS front door's own type list — and the two maps
    are keyed by a narrower type, declared beside the values, naming the address types whose add form asks
    the roles question. The tab list splits the same way: the four tabs in order for what the list shows,
    and the role-backed three for what lists by role, so a tab that offers no role filter cannot carry one.
    `addressTypesRequiringUnitedKingdom:79-82` is a list of types, not a total map, and gains nothing.
    Rejected: a Transporter entry in either map, which would invent role options and a legend for a form
    the type never opens; a fourth key holding an empty list, which the add-roles loop and the Type select
    would both read as "this tab offers no roles" and generate empty cases from; and keeping the value out
    of the shared list, which would leave the Transporter tab unable to carry an address type at all.

15. **A private transporter's Approval number cell reads the deck's not-applicable word, and a search
    matches only a stored approval number.** The design source records a saved private transporter with
    approval number "Not applicable" (`prototype:dr2-1-source p7-084`), and the Transporter tab heads an
    Approval number column (`p15-031`), while decision 3's rule is that only a commercial transporter
    carries one. So nothing is stored for a private transporter and the word is a display rule, owned by
    the one function that builds a transporter row, exactly as the animals frontend already does it
    (`frontend:.../transport/transporters/rows.js:22-23` reads its deck's leaf). The address book matches a
    search term against stored fields, so the word is not matchable: a transporter is found by its approval
    number when it has one, which is every commercial transporter and no private one. Rejected: storing the
    word, which would make the approval number a field every transporter carries and contradict the rule
    the service enforces; and matching the word in the frontend after the service has paged the results,
    which would make a page of results and the result count disagree.

16. **The animals frontend's fixed commercial country gets one owner holding its stored code and its
    display word together.** The commercial journey form carries the display word from its own module
    constant and builds no country code at all
    (`commercial-transporter-details.controller.js:34` and `:161-172`), while the private form stores both
    (`private-transporter-details.controller.js:186`). The ruling fixes the stored code and the word it is
    shown as, both as constants in the service. So the pair moves to one module in the transporters service
    folder, read by the commercial form's fixed-country refusal, by its record and by the mapping that
    sends a transporter to the address book — the record keeps the shape it has apart from reading the word
    from there. Rejected: leaving the word in the controller and putting the code in the mapping, which is
    two owners of one rule; and looking the code up in reference data, which the ruling rules out.

17. **One leaf owns one word in the INS address-book deck: the transporter forms' cancel label is the
    existing one, and the not-applicable word moves up to where both its readers can read it.** The cancel
    wording the transporter forms need is already in the group's deck (`copy/copy.en.js:129`, in the add
    flow's branch, which both forms belong to), so they read it and no second leaf is written. The
    not-applicable word is at `copy/copy.en.js:147`, inside the delete page's branch, and the Transporter
    tab's Approval number cell needs the same word from the list: a branch neither reader shares. So the
    leaf moves to the deck's group level and the delete page's summary (`delete/delete.controller.js:67`)
    and the copy test's pin read it there. Rejected: a second leaf carrying the same word, which is a
    second owner of one piece of wording; and reading the delete page's leaf from the list, which would
    make a page branch the owner of a word the list shows.

18. **The animals frontend's transporter tests keep their set-up at the network boundary, and the
    register-emptying hook goes with the register.** The three controller tests and the shared transport
    helper drive the register directly today
    (`transport/test-support.js:5,23-31`, `transporters/transporters.controller.test.js:402-493`,
    `private-transporter-details.controller.test.js:183-186`,
    `commercial-transporter-details.controller.test.js:230-233`). With the address book as the store there
    is no module to empty: the repo's unit tests run outside stub mode (`src/config/config.js:258` defaults
    it off), so the organisation's transporters are an HTTP call, and the repo's own convention for a
    service-backed test is to answer that call at the boundary
    (`services/address-book/address-book.test.js:24` stubs fetch). So the shared transport helper serves
    the organisation's transporters and captures what is created, for all three tests, and the reads it
    offers are asynchronous. The FIT suite is unaffected in shape: it runs in stub mode
    (`playwright.config.js:68`), where the new stub holds what the forms save. Rejected: a per-test
    organisation id, which would rewrite every assertion in three files for no behaviour gain; and keeping
    an in-memory register beside the address book, which decision 7 rules out.

19. **The two INS front door clients that reach the address book share one module for the parts that are
    the same request.** `services/address-book/client.js:10-44` owns the organisation-scoped base URL and
    its missing-organisation refusal, the header set carrying the organisation and the trace id, and the
    raise that turns a bad request into a validation failure. The transporters client sends the same
    request to the same service against a different resource, so those parts are extracted rather than
    copied: into a module at the `services/` root beside `services/stub-seed.js:1`, the precedent for a
    module two service folders share, with the generic response-to-error half going beside the raises that
    already live in `lib/http-client.js:15-28`. Each client keeps its own resource segment, its operations
    and its query parameters. Rejected: the transporters client importing from `services/address-book/`,
    which would make the addresses feature the owner of a rule neither resource owns; and a second copy,
    which the structure rule forbids.

  (`add/add.controller.js:229-241` already logs the no-type case at info with the organisation id and the

  causes apart.
- **A transporter form opens or saves with no transporter type chosen, and sends the trader back to the
  transporter type question.** A new redirect, the mirror of the address form's own
  (`add/add.controller.js:229-241`). Logs once at info with the organisation id and the request path, so
  support can see a trader who reached a form without passing the question.
- **A transporter is created from the address book.** A new state switch: the record now exists. Logs once
  at info with the organisation id and the new transporter's id, as
  `add/add.controller.js:326-329` does for an address, so support can tie a row in the book to the request
  that made it. No request or response bodies.
- **The address book refuses a new transporter with a 400.** Logs once at warn with the throwable and the

- **Reaching the address book to create a transporter fails.** Logs once at error with the throwable and the
  organisation id, as `add/add.controller.js:345` does.

  trader's own typing — the field is hidden and fixed — so it logs once at warn with the organisation id

- **A blank transporter type, and a blank or over-long field on either form.** The trader's own input error
  shown back on the form: not logged.
- **Cancel from the address book.** Not logged, following the one owner of that behaviour today
  (`add/add.controller.js:216-227` logs a cancel only when a journey is waiting for the hand-back; an
  address-book cancel is navigation with nothing for support to find later).

  Already logged at info by `list/list.controller.js:102-110` and `:144-149`; both now cover the new tab
