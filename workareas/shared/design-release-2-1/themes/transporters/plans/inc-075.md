## 0. Decisions

**D1 — The address book service needs no change, so the plan changes two repos, not three.**
Everything this row needs from the system of record is already built and already proved:
`TransporterController.list` takes a repeatable `type` parameter that narrows the collection
(`TransporterController.java:154-160`), `TransporterService.criteriaOf` passes it as the criteria's
`types` (`TransporterService.java:81-83`), `TransporterListQueryImpl.liveTransporterCriteria` ands it
into the Mongo query before paging (`TransporterListQueryImpl.java:39-41`), and the searchable text
fields already include the approval number (`TransporterListQueryImpl.java:53-64`). Both are proved
by `TransporterSearchIT.aTypeFilterKeepsOnlyThatType` and
`TransporterSearchIT.aSearchTermMatchesTheApprovalNumber`
(`TransporterSearchIT.java:37-65`). Rejected: adding a second, type-specific list route or a
frontend-side filter over a fetched page — the second would break "filtered on the server" and
"across the whole category".

**D2 — Acceptance criterion 2 is a defect and nothing is built for it.** It asks that "such an
address's Type column reads 'Transporter' on the tabs that show a Type column". Neither cited claim
says that: `prototype-dr2-1-source-p15-024` says the Transporter *category* holds the prototype's
`transporter` type, and `trace-prototype-dr2-1-p16-031` says that category is headed "Transporter
addresses". The prototype's own rule for that column is the opposite —
`prototype-dr2-1-source-p15-036`: on the Transporter tab the Type is "Commercial" or "Private",
which is what criterion 3 states. The decision of 6 November (decision 5) then removes the only
other reading: a transporter is a record in its own collection with no role, and the address API
refuses an address `type` outright, so no row on a role-backed tab can ever read "Transporter".
Criterion 2 therefore contradicts criterion 3 and cannot be made observably true. Planned against
criterion 3. Reported as a defect in the returned summary.

**D3 — Acceptance criterion 6 already holds and is already proved end to end; it gets no new
work.** The frontend already passes the search term to the transporters route
(`list.controller.js:193-209` → `services/transporters/client.js:30-32`) and the service already
matches the approval number (D1). The end-to-end proof exists:
`tests/ins/e2e/features/transporters/commercial-transporter.spec.ts:73-87` searches the Transporter
tab by the stored approval number among other terms. Rejected: a second test asserting the same
behaviour from the same page.

**D4 — One Type select, one owner, driven by the selected tab's filter; the `{% if %}` branch in the
template goes.** Today the select is role-only: `roleItemsOf` returns nothing for the Transporter
tab (`list.controller.js:109-119`) and the template hides the control
(`list.njk:56-65`). Every tab now offers the filter, so the select is rendered unconditionally from
one view-model value carrying its query-parameter name and its options, and one controller function
owns building those options. Rejected: a second `{% if %}` block and a second items builder beside
the role one — two mechanisms for one control, which the house rules forbid.

**D5 — The chosen filter value is resolved by one generalised function, replacing `resolveRole`, and
every name that carries that value follows it.** `resolveRole` (`address-book-tabs.js:33-34`)
honours a role the tab offers. The Transporter tab's filter needs the identical rule over
transporter types, so the rule is generalised to "the requested value when the selected tab's filter
offers it, else nothing" and `resolveRole`'s two callers (`list.controller.js:226-234`,
`address-book-tabs.test.js:59-76`) move to it. Because one value now carries either a role or a
transporter type, every local, log field and view-model key still named `role` for it is renamed
with the rule — including the failed-load log's field (`list.controller.js:272-275`), which would
otherwise tell support a role when the Transporter tab logs a transporter type (section 13). This
changes a signature across its callers, which bounded tidy-up would not allow — it is allowed here
because the row's own behaviour needs the rule and the house rules require one owner for it and one
name per concept. Rejected: `resolveRole` plus a sibling transporter-type resolver; and keeping the
`role` field name on the generalised value.

**D6 — Each tab keeps its own query-parameter name: `role` on the role-backed tabs, `type` on the
Transporter tab.** The row's notes leave the names to the service. A role and a transporter type are
two concepts, and the address book's own API already names them `role` and `type`, so one name per
concept holds from the URL through to the API call. Every URL the role-backed tabs produce today
stays byte-identical. Rejected: one shared parameter name for both filters, which would rewrite the
role-backed tabs' URLs, pagination links and tests for no behaviour.

**D7 — The Transporter tab's filter offers Commercial before Private.**
`trace-prototype-dr2-1-p16-024` sets the order "Select one", "Commercial", "Private". That is the
reverse of the transporter *type question*'s radio order, which
`trace-prototype-dr2-1-p16-051` sets as Private then Commercial and inc-038 built. Two different
controls, each following its own design source, so no `design` finding: the prototype sets both
explicitly and they do not disagree about one element.

**D8 — The copy keys for the Type column heading and the Type select are renamed off "role".**
`copy.list.table.role` (`copy.en.js:78`) is the heading of the Type column on all four tabs —
inc-074 already reuses it for the transporter table (`list.controller.js:70`) — and
`copy.list.search.role` (`copy.en.js:28-31`) is the label and placeholder of the one Type select
every tab now shows. Both keys name a concept the value no longer carries. Both live in files this
row edits anyway and have no readers outside them (`list.njk:61`, `list.controller.js:60,70,112`,
`copy.test.js:225-226,260,282`), so they are renamed to name the Type column and the Type filter.
The visible English and Welsh words do not change. Rejected: leaving them, which would leave one
concept with two names across the four tabs.

**D9 — The approval number's format is not imposed.** Criterion 3 quotes
`RO/BUCHAREST/T1/00092010` from `trace-prototype-dr2-1-p16-033`, a Romanian *approved* transporter —
the parked concept (decision 3 of ruling:ian-2026-11-06). The criterion is satisfied by the stored
approval number appearing verbatim in the Approval number column, which
`fit/transporter-forms.fit.spec.js` and `tests/ins/e2e/.../commercial-transporter.spec.ts` already
prove. No pattern validation is added. Rejected: validating the approval number against that shape,
which nothing in scope asks for and which would refuse the Northern Ireland numbers the forms accept.

**D10 — Criterion 5's Welsh is met the way this repo meets it everywhere.** No locale toggle exists
and every call site resolves English (`shared/copy.js:1-4`, and
`repos/trade-imports-ins-frontend/src/server/app/docs/features.md`, "Copy and templates"). The
programme invariant is kept by writing a machine-draft Welsh value beside every new or changed
English string and pinning it leaf by leaf in `copy.test.js`. Rejected: building a locale switch,
which no row asks for.

**D11 — The Transporter tab's filter gets its own end-to-end spec rather than joining
`address-book-role-filter.spec.ts`.** That file is about the role filter over the addresses
collection and stays entirely true; ten coverage links point at its path. The new behaviour has
different fixtures (transporter records) and different columns. Rejected: renaming that spec and
merging, which would rewrite ten coverage paths and its describe blocks for no behaviour.

**D12 — The tests repo's list page object names the Type filter for the control, not for roles, and
keeps one chooser; its placeholder constant follows.** `selectRoleFilter` is already the generic
`getByLabel('Type')` (`list-page.ts:124-134`) and `chooseRoleFilter`/`filter` open the disclosure and
select by label (`list-page.ts:136-150`). The new spec drives the same control with a
transporter-type label, so the accessors are renamed for the Type filter and the one chooser takes
the option label, with the role and transporter-type label maps applied at the call sites
(`address-book-role-filter.spec.ts`, `run-addresses.ts:73-81`). `roleFilterPlaceholder`
(`domain/ins/constants/address-book-types.ts:35`) is the first option of that same control and the
new Transporter-tab spec reads it for the 'Select one' it asserts, so it is renamed for the control
too — the concept's whole vocabulary across the two repos moves together with D8's copy keys.
Rejected: a second transporter-only accessor and chooser beside the role ones; and leaving the
placeholder role-named while its control is not.

**D13 — The role-backed-tabs list is promoted, not re-derived.**
`list.tabs.controller.test.js:31` re-derives the role-backed tabs that
`ROLE_BACKED_ADDRESS_BOOK_TABS` (`address-book-tabs.js:24-26`) already exports; both files are edited
for this row, so the local copy goes and the test reads the export. Rejected: deleting the export,
which features.md documents and which is the shared set-up for two tests.

**D14 — The unavailable-load stub is generalised, not duplicated.** The list's nock stubs build their
interceptor in two places: `interceptListRequest` (`list.test-support.js:137-148`) for the addresses
route, which `stubAddressPage` (`:150-155`) and `stubAddressBookUnavailable` (`:156-162`) share, and
`stubTransporterPage` (`:164-168`), which builds its own against `transportersApiPath()`. Test 6
needs a failed load on the Transporter tab, and `stubAddressBookUnavailable` can only fail the
addresses route. So `interceptListRequest` becomes the one interceptor builder for whichever route
the named tab reads — the addresses path with the tab's roles, or the transporters path — and all
three stubs go through it, leaving one unavailable stub for every tab. Rejected: a second
transporter-only unavailable stub beside the existing one, which is a second mechanism for one
concept.

**D15 — The `view-model/list.js` house-rule breaches in the lines this row edits are fixed with it.**
The row edits that module for `buildAddressBookQueryString`, and the file holds two breaches the
house rules make defects: a module-scope literal for the commercial transporter type (line 108) read
only by `transporterCountryLabelOf` (lines 110-117), restating a value `TRANSPORTER_TYPES`
(`services/transporters/transporter-types.js:1-4`) already owns; and a direct import of that service
module (line 4) past the barrel the service documents as its only door
(`src/server/app/docs/services.md:21-22`, "The barrel exports both. A feature imports only the
barrel, and nothing imports any other file from outside its folder."). Both are fixed in this change
(section 2). Rejected: leaving them as pre-existing, which the house rules forbid for a file this
plan edits.

**D16 — The role-backed tabs' column headings get one owner.** `TABLE_HEADINGS`
(`fit/address-book-list-text.js:3`) is that value, re-exported by `fit/address-book-list.js:7-9` and
by `list.test-support.js:21-24`; `expectEmptyAddressBookList` (`fit/address-book-list.js:77-88`)
holds an inline copy of the same five headings. The row edits both files — section 11 makes
`searchAndExpectQuery` the shared submitter and adds the Transporter tab's headings to the text
module — so the inline copy goes and the helper reads the export. Rejected: adding the Transporter
tab's headings to the text module while leaving a second owner for the role-backed ones, which would
end the row with two owners for one column list.
