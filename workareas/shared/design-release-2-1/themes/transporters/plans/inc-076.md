## 0. Decisions

1. **Which "transporter list" the row means.** The row's own source `repo:frontend` names `features/transport/transporters, no action column today` and acceptance criterion 2 ties Back to "the same notification's transporter list" — a notion that only exists for the per-journey page. I therefore read this row as the animals-frontend journey page `sets/live-animals/journeys/linear/features/transport/transporters` (where a trader picks a transporter for one notification), not the INS address-book's own Transporter tab list (inc-075). Rejected alternative: the INS Transporter tab — rejected because inc-075's own acceptance criterion 3 deliberately ships that tab with "the action column with no visible heading" (i.e. empty by design for now), and a tab over the whole address book has no "notification" to return to.

2. **Where the details page lives.** Ruling `sam-2026-10-09` (p1-070, p1-093) and the 6 November re-analysis say the details page is "the real services' conventions" — i.e. the address book's own view page, already built as `trade-imports-ins-frontend`'s `features/address-book/view` (inc-064) with its honoured-return Back link (inc-066). I build the link to point there and reuse that mechanism exactly; I do not build a new transporter-specific details page. Confirmed against the live tree: `return-to.js`'s own unit test already exercises a `/live-animals/notifications/abc`-shaped URL on the animals origin (`return-to.test.js:28`, `LIVE_ANIMALS_URL`), generically proving the destination honours a return exactly this shape — **insfrontend needs no code change for this row.**

3. **Link wording.** Visible text "View details", with the transporter's own name appended as visually-hidden text. Taken verbatim from the design source (`prototype-dr2-1-source-p7-026`: "Each row has a 'View details' link…"; `prototype-dr2-1-specs-p2-106`'s own FIT assertion uses the exact text "View details"), and the hidden name is the fix for a flaw the trace extraction itself records: `trace-prototype-dr2-1-p8-089-m1` — "Every transporter row's link reads only 'View details', with no visually hidden transporter name, so the 8 identical link texts cannot be told apart out of context." I do **not** reuse the bare word "View" that a different, unrelated feature (the consignor/party picker's own address-book view link, `EUDPA-721`) uses — that is a different page with its own copy, not a shared mechanism.

4. **Column position.** The design source states the columns in order — "Name, Address, Approval number, Type and Status, plus a select column and an action column" (`prototype-dr2-1-source-p7-021`) — select first, action last. I append the new cell as the table's last column, matching acceptance criterion 1's "ends with".

5. **Change context on the return value.** The existing "Add a transporter" button on this same page builds its href with `kit.withChangeContext(request, pagePath(...))` so a trader who opened the list from a Change link keeps that context. I use the identical mechanism for the return URL, rather than inventing a second rule for what Back should do in a change flow.

6. **A new "my own base URL" config and helper are needed.** Building a `return` value that INS's `animalsUrl()` will honour needs an *absolute* URL on the animals frontend's own origin (`return-to.js:36-46`, confirmed in `return-to.test.js`). Nothing in `trade-imports-animals-frontend` today knows its own browser-visible base URL — only the INS-side `tradeImportsAnimalsFrontend.baseUrl` config entry (`trade-imports-ins-frontend/src/config/config.js:405-411`) knows it, for validating returns. I mirror that exact entry (same key path, same env var `TRADE_IMPORTS_ANIMALS_FRONTEND_URL`, same doc wording pattern, default `http://localhost:3000`) onto the animals-frontend's own `config.js`, alongside its existing `tradeImportsInsFrontend.baseUrl` entry, and add one new helper function beside `common/helpers/ins-frontend-url.js` that joins a path to it (same shape as `buildInsFrontendUrl`, the other half of the same pair). Rejected alternative: deriving the origin from the request (`request.info.host`/forwarded headers) — rejected because the codebase has no precedent for trusting those behind the CDP/nginx front door, and the explicit-config pattern is the one already proven on the INS side for exactly this concept (one concept, one name, across repos). This needs **no docker-compose edit**: `docker/stack/frontend.compose.yml` does not set `TRADE_IMPORTS_ANIMALS_FRONTEND_URL` on the `trade-imports-animals-frontend` service itself, so the new config falls back to its own default `http://localhost:3000` — which is exactly the real nginx-fronted port the compose file already publishes (`frontend.compose.yml:108`, `ports: ['3000:3000']`), so the real/E2E stack needs nothing extra. `docker/stack/` is outside this row's repos (frontend, insfrontend, tests) regardless. The equivalent wiring for a deployed CDP environment lives in `cdp-app-config`, which no session may write to; flagged under Out of scope/Follow-ups for whoever owns that config.

7. **The shipped/demo transporters have no address-book record behind them.** `services/transporters/records.js`'s `TRANSPORTER_OPTIONS` (e.g. `garcia-livestock-transport`, `aberdeen-livestock`) are plain in-repo constants, not address-book documents — confirmed by reading `partiesFor()` (`services/transporters/index.js:37-45`), which only fetches *added* transporters from the real address book and appends the shipped constants verbatim. So acceptance criterion 2 ("opens that transporter's details page showing its record") is fully true only for a transporter the organisation added itself (an address-book-backed `id`); for a shipped row, the already-built dead-link handling (`return-to.js`'s `returnDestinationOf`, inc-064) means the link still renders (criterion 1 holds for every row) but, followed, finds no live address and bounces straight back to the list rather than showing a record. This is a pre-existing data gap, not something this row's repos (frontend, insfrontend, tests) can close — closing it is what the *blocked* `inc-265` ("Approved transporters: the records offered, and the list they come from") is for. I build the link uniformly for every row and record this caveat rather than hiding it; see Out of scope/Follow-ups.

8. **Rigour.** The row's `rigour` is `"fast"`, with its own note: "If the plan finds real work here, raise it back to standard or full before building rather than running fast on a contract change." This plan finds exactly that: a new cross-repo config contract (decision 6) and a genuine data-coverage gap (decision 7). **I flag this: rigour should be raised to at least `standard` before the loop builds this row.**

9. **Where the href is computed vs. where the accessible text is composed.** The existing select-radio cell already splits this: `rows.js` supplies plain data (`id`, `name`), and the `_cells.njk` macro composes the hidden accessible text itself (`copy.selectRowPrefix + " " + row.name`). I follow the same split: `rows.js` computes the one new thing a template cannot (the cross-origin URL, via `URLSearchParams` and the two `build*FrontendUrl` helpers) as a new `detailsHref` field per row; the new `_cells.njk` macro composes the visible-plus-hidden accessible text, exactly mirroring the select cell's own shape.
