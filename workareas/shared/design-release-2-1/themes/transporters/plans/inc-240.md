## 0. Decisions

1. **Where the fix lives.** `transporters/validate.js`'s `fields()` (`:47-54`) builds its one Joi rule with `oneOf('transporter', ids, copy.errors.transporterRequired)` unconditionally — `oneOf` is `Joi.string().allow('').valid('', ...values)` (`lib/validate/validators.js:189-196`), so a blank or missing pick passes. I change `fields()` to branch on `context.stored` (already passed in by `pageValidation`'s `onSubmit`/`onStored`, `lib/validate/page-validation.js:53,59`): unchanged `oneOf(...)` when `stored` is true, `requiredOneOf('transporter', ids, copy.errors.transporterRequired)` (already exported, `lib/validate/validators.js:156-187` via `index.js:16`) when it is false. This is not a new pattern: the repo's own `docs/validation.md:71-74` states exactly this shape — "A rule may also use `stored` to refuse a blank answer on submit, with `requiredOneOf` … while accepting it on the stored reading, with `oneOf`" — and names `import-reason/validate.js` as the example. Its `countryRule` (`import-reason/validate.js:58-65`) is the literal structural exemplar: `stored ? oneOf(field, codes, copy.errors.xNoLongerAvailable) : requiredOneOf(field, codes, copy.errors.xRequired)`. I keep the single existing message (`copy.errors.transporterRequired`) on both branches, matching `transporters/validate.js`'s current call exactly — no new or reworded copy, and no Welsh change, matching the row's own note that the message already exists under the feature's `transporterRequired` key.

2. **Why the stored branch is unaffected and needs no new message.** `fromAnswers: () => ({ transporter: '' })` (`validate.js:80`) always hands `fields()` a blank value on the stored (GET) reading by design — the real "is the stored pick still valid" check is the separate `checks()` function (`validate.js:59-74`), which matches the stored transporter's name against the live register and returns `copy.errors.transporterNoLongerAvailable` when it has vanished. Keeping `oneOf` (which allows `''`) on the stored branch reproduces today's GET behaviour exactly: no page that already holds a valid transporter starts in error, and `checks()` keeps sole ownership of "no longer available". Rejected alternative: short-circuiting the stored branch to `compose()` the way `cph-number/validate.js:64-66` does — rejected because the documented exemplar (`import-reason/validate.js`) keeps calling the service-backed `oneOf`/`requiredOneOf` pair on both branches rather than skipping the lookup, and matching the documented pattern exactly is less of a departure than a second, shorter-circuited shape beside it.

3. **No controller, template or copy change.** `transporters.controller.js`'s `post()` already calls `validation.onSubmit(payload, { records })` and renders the same 400 error page for *every* POST that fails it, before it looks at `payload.exit` — so "Save and return to overview" (`exit=hub`) already runs through the identical check as "Save and continue", with no branch to add. This already matches `docs/validation.md:59-63` ("'Save and return to overview' runs the same checks as 'Save and continue', with no opt-in") and the row's own ruling source. `transporters.njk`'s inline error block (`:38-41`) and `kit.errorSummary`'s href mapping (`transporters.controller.js:72-73`) already render and link `errors.transporter` for the existing "not on the list" refusal (proven by the existing test "Should reject a transporter that is not on the list", `transporters.controller.test.js:142-151`); a blank submission now populates the same `errors.transporter` key through the identical render path, so AC1's inline-plus-summary wording needs no template change, only the validator swap that makes the key populate.

4. **No plants mirror.** The row's `repos` list (`frontend`, `tests`) is authoritative and I confirm it against the live tree: `trade-imports-plants-frontend/src/server/app` has no transporter feature at all (only mentions in its own spec/backlog JSON and docs, no `validate.js`/`controller.js`/page under that name). The programme's "mirror to plants" invariant does not apply — there is no twin page to change.

5. **Spec home: `journey-pages/transporter`, not `journey-obligations/transporter`.** `journey-obligations/transporter`'s `REQ-OB-TRANSPORTER-001` already states the transporter is asked for "as a mandatory answer", but its one scenario (`SCN-OB-TRANSPORTER-001-A`) only proves the list's shape (one combined list, no type-first question) — it has never proved the mandatory wording is enforced. I resolve this gap in `journey-pages/transporter` instead of amending the obligations requirement, because the exact sibling pattern already exists there: `journey-pages/transporter-type`'s `REQ-TRANSPORTER-TYPE-005` ("A transporter type must be chosen") states the identical shape of rule — refuse the save, name the one message, in the summary and inline, leave the stored answer unchanged — for the type question one step along the same flow. I add the transporter list's own instance of that requirement, `REQ-TRANSPORTER-009`, rather than editing `REQ-OB-TRANSPORTER-001`'s text, keeping "what is mandatory" (obligations) and "how the page refuses a missing mandatory answer" (the page's own requirement) apart exactly as the two capabilities already divide it for every other obligation/page pair in this spec area.

6. **One requirement, two scenarios, split by save control.** Unlike `REQ-TRANSPORTER-TYPE-005`'s split (by *what* is wrong: nothing chosen vs. an out-of-list value), this row's own subject is specifically that *both* save controls refuse a blank pick identically (ruling `sam-2026-10-26`). I split `REQ-TRANSPORTER-009`'s scenarios by *which* control — `SCN-TRANSPORTER-009-A` for "Save and continue", `SCN-TRANSPORTER-009-B` for "Save and return to overview" — so the ruling's own claim (one check, no opt-in) is traceable to a named scenario for each button, matching AC1 and AC2 one-to-one. The already-specified "a submitted pick not on the list is refused" behaviour (tested today, e.g. `transporters.controller.test.js:142-151`, but not itself named as a requirement anywhere in this capability) is a pre-existing spec gap, not this row's subject — flagged under Follow-ups rather than fixed here.

7. **Claims checked against the live tree.** The row's own notes name `transporters.controller.test.js:167` and `:210` as the two tests that invert; the current tree has them at `:176` (`'Should walk on without saving when no transporter is picked'`) and `:219` (`'Should go to the overview, not the next page, and commit nothing when no transporter is picked'`) — line drift from an unrelated edit since the note was written, not a wrong claim. Every other claim in the row (today's blank-pass-through bug, the existing `transporterRequired` message, `requiredOneOf` already existing beside `oneOf`) is confirmed true by reading the live files. `rigour: "fast"` is confirmed appropriate: the whole fix is the one `fields()` branch in decision 1, with no new design.
