## 0. Decisions

1. **Salvage as the starting point, cleaned to the house rules.** Each repo starts from the salvage commits the row names: animals `e6f5d7cf`, plants `4d08998`, INS `2d7619e`, tests `3205feb` and the locator and spec line of `f583ca8`, and the inc-148 slice of workspace `7479b4ea`. Every departure below is where the live tree or the house rules disagree with the salvage. Rejected: rewriting from scratch, which loses tested shape for no gain.
2. **The hand-over is INS form POST, then a 302 to `<receiving base URL><set base>/start`, then a session-authenticated GET start entry on the receiving service.** The start entry creates the draft, begins the opening run and redirects to the first page.
   - Rejected: posting straight to the receiving service's create POST. That needs the receiving service's crumb, which INS cannot hold: the crumb cookie is SameSite=Strict on both journey frontends (`src/plugins/csrf.js:27`), and a crumb never crosses services.
   - Rejected: a GET form on INS, because every state change is a form post and the question's refusal needs a POST.
   - Rejected: a GET start that renders a confirm page with its own crumb-protected button. The criteria land the trader on origin (or commodity-type) straight after Continue, so an extra page differs from the design source.
3. **The GET start entry changes state, and that is accepted, limited as follows.** It departs from the "every state change is a form post" invariant (section 14).
   - The trader's own state change is the INS form post: the type question's Continue, with INS's crumb. The GET start is only the target that POST redirects to.
   - Consequence: a link on any other site that a signed-in trader follows opens an empty draft for that trader. The draft belongs to the trader's own organisation, carries no answers, and the trader lands on its first page and sees it. That is the same outcome as pressing Create new on the trader's own dashboard. Nothing is read, sent or changed in any other record.
   - Limit: the session is the `@hapi/cookie` auth cookie (the `auth.cookieName` cookie), set in `getCookieOptions()` (`src/plugins/auth.js:101-108` animals, `:104` plants). It sets no `isSameSite` and `server.js:64-66` sets no state default, so it takes @hapi/statehood's default `isSameSite: 'Strict'` (`node_modules/@hapi/statehood/lib/index.js:52`). The Lax at `src/config/config.js:19` belongs to the Bell OAuth state cookie (`plugins/auth.js:69`), and the Lax at `engine/journey.js:33` to the journey cookies. Neither protects the session.
   - So a link, image, script, iframe or fetch on another site reaches the start entry with no session at all, and is sent to sign-in with no draft created.
   - The hand-over from INS still carries the session where the receiving service already has one: INS and the receiving frontends are same-site hosts locally (`localhost` on different ports) and on cdp-int (`*.cdp-int.defra.cloud`), and Strict cookies are sent on same-site navigations. A trader with no session there goes through sign-in on the way (Decision 14).
   - Limit: the start GET answers `Cache-Control: no-store`, so no cache replays it.
   - Rejected: checking `Sec-Fetch-Site` or the Referer on the start entry. The legitimate hand-over is itself cross-site (INS to animals, INS to plants), so such a check could not tell it apart from a link elsewhere.
4. **One way to open a new notification, per twin.** In both the animals and plants dashboard controllers, the existing create POST and the new start GET go through one helper. The helper starts the journey, begins the opening run, logs the new draft once and redirects to the entry page (origin for animals, commodity-type for plants). The start GET adds only `Cache-Control: no-store`. The salvage's alias that makes the create handler equal the helper is fine. Its comment above the start handler describes another service, so it is dropped.
5. **Only the route-shape builder is added to each twin's `shared/paths.js`.** The salvage also adds a prefixed link builder that nothing calls, and it is left out (build only what is reachable). The `add-a-set.md` route-builders table therefore gains the route shape only.
6. **The CSP form-action origin of the sign-in service is derived, not configured.** Chrome checks INS's `form-action` at every redirect hop of the hand-over POST. For a trader with no session on the receiving service, the chain ends at the Defra ID (stub) authorize URL, so that origin must be allowed.
   - The salvage's new `DEFRA_ID_FORM_ACTION_ORIGINS` (default `localhost:3007`) is set in neither compose nor cdp-app-config, so it passes locally and fails in CDP.
   - Instead, INS derives the browser-facing Defra ID origin from `defraId.oidcDiscoveryUrl`, through the same hostname rewrite the sign-out URL already uses. In the stacks that maps `host.docker.internal:3007` to `localhost:3007`. In CDP the rewrite is off and the discovery URL is already browser-facing.
   - This needs no new environment config and no cdp-app-config change. Rejected: the explicit config key, which needs Sam to edit CDP repos that agents may not write.
7. **That browser-facing Defra ID rule gets one owner, and the config key keeps its shared chassis name.**
   - The owner is a new module under `src/auth/`, which the sign-out URL builder (`src/auth/get-sign-out-url.js`) and the CSP helper both call. `getSignOutUrl` stops doing its own rewrite.
   - The convict key `defraId.signOutHostnameRewrite` (and its `enabled`, `from`, `to` children) is one concept, with one name, across INS, the animals frontend, the plants frontend and the animals admin (each repo's `src/config/config.js` and `src/auth/get-sign-out-url.js`). Renaming it in INS alone would give one concept two names across twin repos. So INS keeps the key name.
   - The new owner's name says what it returns: the browser-facing form of a Defra ID URL. The key's three `doc` strings in INS are reworded to say the rewrite applies to every browser-facing Defra ID URL this service builds (sign-out and form-action), not the sign-out URL alone.
   - Renaming the key and its env vars (`DEFRA_ID_SIGN_OUT_HOSTNAME_REWRITE_*`) in every chassis repo together is a section 7 follow-up.
   - Rejected: renaming in INS only, which splits the vocabulary across the twins.
8. **Today's INS home start control is repointed, not made always-visible.** The row notes say this row repoints the existing empty-state "Start a new notification" button at the type question, and inc-149 then makes the control "Create new" and always shown. The salvage's always-visible button, copy-key move and dashboard fit test are not taken.
