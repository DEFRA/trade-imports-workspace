## 0. Decisions

1. **One always-shown Create new button, placed straight after the h1 and before the reference search form, outside every state branch of `dashboard/template.njk`.**
   - So it renders in the listed, empty, search-match, no-match and cannot-load states, because none of them hides it.
   - The empty state keeps its "There are no notifications yet." paragraph and loses its own button.
   - Rejected: a button inside each branch. That is five copies of one control.
2. **Its copy moves out of the `empty` group to a top-level key in the dashboard copy, en and cy together.**
   - English is "Create new". Welsh is the salvage's machine draft "Creu newydd". The MACHINE-DRAFT marker line at `copy.cy.js:1` stays (a marker, not a comment).
   - A rename covers the concept's whole vocabulary. The copy key, the view-model href key (`startNewNotificationHref`) and every test title that says "start a new notification" are renamed to the Create new concept. The implementor picks the names.
   - Rejected: keeping it under `empty`, which would state an empty-state control.
3. **The link is the question's path from `shared/paths.js` `notificationTypePath()`, a host-free path on the INS origin.** It works unchanged in CDP, the local Docker stack and the CI Docker stack, with no config. This row adds no cross-service link and needs no environment value.
   - The home's old cross-service start link (animals `/live-animals` via `tradeImportsAnimalsFrontend.baseUrl`) is already gone (inc-148 deleted the builder). The row note's "drop buildStartNewNotificationLink" is already done. `tradeImportsAnimalsFrontend.baseUrl` stays for the row View links.
4. **The cannot-load state is proved by the controller test (nock answers the INS backend with 500 through the real server), not by a new failure branch in the INS backend stub.**
   - The row notes ask to salvage `188f55be`'s stub failure reference (`GBN-AG-26-500000`) so the FIT can reach that state.
   - Rejected. It adds a branch to `services/ins-backend/stub.js` that exists only to fail on a magic reference, and the controller test already reaches the real recoverable-error render. That render has the same template, the same DOM order and the same banner.
   - The FIT covers the states its stub can reach: listed, and search with no match.
   - Consequence: there is no browser proof of the cannot-load state, only a server-rendered DOM proof. Placement is proved by document order in both cases.
5. **The empty state is proved by the controller test only.** The ins-backend stub is not scoped by organisation (`services.md:71-72`) and always lists three rows, and the E2E shared identities have notifications. So no browser test reaches it.
6. **The browser walk from the home to the question is one new E2E test in `tests/ins/e2e/features/notification-type/notification-type.spec.ts`, in a describe of its own with no service tag and no `@compose`.**
   - It never leaves INS, so it does not exercise the animals or plants frontend. Tagging it `@animals-frontend`/`@plants-frontend` (the existing describe's tags) would be wrong.
   - INS's own domain runs by path (`tests/ins/`), so INS frontend PRs run it. Leaving out `@compose` means the CDP Portal suite runs it too (the CDP run leaves out only `@compose`, `@a11y`, `@active` and `@dynamics`).
   - The existing tests in that file keep opening the question directly. Rejected: rewiring them through the home, which slows six tests to prove one link.
7. **Proofs are positive.**
   - "The one button for beginning a notification reads Create new" is proved by the whole list of link-buttons (`a` with role button) in main being exactly one, labelled "Create new". The search and sort controls are `<button>` elements, not links.
   - "Standard, not start" is proved by that element's class list being exactly the standard GOV.UK button class.
   - Neither is proved by the absence of the old label or the start modifier. Tests carry no `RETIRED_*`-style constant, and nothing asserts on the old animals URL.
8. **The Welsh criterion is met as inc-148 Decision 10 settled it.** INS has no locale toggle (`features.md`: every call site resolves `en`). So the Welsh string is proved by the dashboard copy test (the exact Welsh value under the same key) and the repo's `copy-parity.test.js`, with no browser Welsh test and no Welsh spec scenario.
9. **The salvaged spec is cut to this row.**
   - REQ-INS-DASH-004 (scenarios A to D) of workspace `7479b4ea` is taken (this branch numbers it REQ-INS-DASH-005, after main's pagination REQ-INS-DASH-004). REQ-INS-DASH-005 (Use template), its coverage entries and the Purpose's templates clause are left out.
   - The requirement's "MUST NOT offer 'Start a new notification'" is restated positively: Create new is the home's one control for beginning a notification.
10. **The capability's coverage entries name the tests as they are titled now.** inc-148 stripped the `(ACn)` ids from the dashboard FIT titles, so `coverage/ins/notification-dashboard/coverage.json`'s existing `test` strings ("… (AC1, AC2)", "(AC3)", "(AC4)", "(AC5)") no longer match. This row edits that file, so they are corrected to the live titles (as retitled by this row, where it retitles one).

   - Today `notification-type.fit.spec.js:17-40` owns it inline (its own label literal and a loop over `radios.nth(index)`). The dashboard FIT needs the same check after Create new, in two tests.
   - So the check is promoted to a new helper file under `features/notification-type/fit/`, following `features/address-book/fit/dashboard.js`. It proves: the URL is `notificationTypePath()`, the h1 is the question, the radios are exactly the five labels in order, none checked. The local copy in `notification-type.fit.spec.js` is deleted and that spec uses the helper.
   - Promoting it makes the notification-type FIT a file this row edits, so its own breaches are fixed: the literal `PAGE_URL` becomes `notificationTypePath()` (both at `goto` and in the hand-over response match), and the Back link's literal `'/'` (`:47`) becomes `dashboardPath()`.
   - Rejected: the dashboard FIT proving only path and heading. Then its own path-and-heading check would be a second partial copy of the same question check, and the browser proof of SCN-INS-DASH-005-A's options would rest on the E2E alone.

That covers the absence-only assertions in `controller.test.js` and the dashboard FIT, the history-narrating title in `copy.test.js`, and the dashboard FIT's literal `'/'` paths.
