## 0. Decisions

1. **Where "started from the type question" is recorded.** The animals start entry (`GET <set>/start`, `features/dashboard/controller.js:152`) is the only route the INS type question opens; the list's create button is the `POST` create (`:170`). Both go through `openNewNotification` (`:139`). That helper gains a named option saying which of the two began the opening run, and records it through `beginOpeningRun` in `app/flow/run-state.js`. Run-state gains one reader that says whether the active opening run began at the start entry.
   - The fact is stored as its own per-journey session record through the session seam (`engine/persistence/session.js`), beside the opening-run record, with its own per-set cookie name. The real (`services/persistence/session/real.js`) and stub (`stub.js`) adapters each gain the read/write pair.
   - Each adapter already holds three copies of one by-journey reader body, differing only in the cookie-name accessor (`real.js:26-39`, `stub.js:16-29`). A fourth would breach "extract the shared part". So each adapter's three readers fold into one reader that takes the cookie name, and the new record reads through it too. The reader stays inside each adapter, because real reads `request.yar` and stub reads `request.state`.
   - Rejected: one reader shared across both adapters. It would need a "where to read" argument, a second mechanism beside the two adapters the session seam already selects between.
   - Rejected: reshaping the opening-run record from a bare phase string into an object. Every test that seeds `openingRun: RUN_ACTIVE` or asserts the cookie equals `{ [id]: RUN_ACTIVE }` (opening-run.test.js, dashboard controller.test.js and about ten controller tests) would change, and a session written before the deploy would read as no run.
   - Rejected: a second "active" phase value. It puts two facts in one value, and `inOpeningRun`/`completeOpeningRun` would have to know both spellings.
   - Rejected: a query string on the origin URL. It is lost when the origin page re-renders after a refused POST and when Back from a later run step returns to origin.
   - The fact is platform-level and set-agnostic: it names the start entry, which `shared/paths.js` already owns for every set (`startRoutePath`). It is not live-animals knowledge, so L2 (`app/flow`) is the right home.
2. **Back on origin.** `entryBackLink` (`sets/live-animals/journeys/linear/flow/entry-guard.js:50`) is extended, not replaced. While the opening run is active and began at the start entry, Back is the INS type question for this notification. While it is active and began at the list's create, Back is the set's list, as now. After the run, the overview/list rule stays as it is. So "opened from the overview → overview" wins over "started from INS", which matches criterion 2 and the existing REQ-ORIGIN-013.
3. **What the Back link carries.** A GET link to INS `/notification-type` with the notification's reference and its notification type in the query. The type is the live-animals set's id (`sets/live-animals/set.js` `SET_ID`, `live-animals`), which is also INS's value for Live animals (`notification-type/destinations.js:12`). That is the cross-service contract, written down in both repos' docs (section 12).
   - The reference's query parameter reuses the name the address handshake already uses for the same concept, `notification-id` (`addresses/ins-handshake.js:92`, INS `address-book/handshake-context.js:46`). One concept, one name.
   - Rejected: INS reading the notification's stored category from a backend. INS has no per-notification read. The row's note says a stored category that is absent means live animals, and the set raising the link knows it is live animals. No backend change is needed.
4. **How the type question picks the notification back up.** The GET reads the reference and type from the query, as `address-book/handshake-context.js` reads its query. Where the type is one INS offers and that type can take a notification back, and a reference is present, the matching radio is checked and the form carries the reference and the notification's type as hidden fields. The add page does the same (`address-book/add/add.njk:14-17`). Otherwise the question shows nothing selected, as now.
   - The POST compares the chosen type with the notification's type. If they match, it redirects to that notification's origin page. If they differ, it falls through to the existing `startUrlFor` hand-over. If there is no notification, it behaves as now.
   - Only live animals can take a notification back in this row. Its entry in `NOTIFICATION_TYPES` gains the page a returning notification lands on (the origin page). The other entries gain nothing (section 15).
   - Rejected: storing the context in the INS session. It would leak into a fresh Create new, which must show nothing selected (criterion 6). Query plus hidden fields work without JavaScript and survive a re-sign-in, because both frontends' `redirectTo` keeps pathname and search (INS `plugins/auth.js:89`, animals `plugins/auth.js:109`).
5. **The return URL is built from config, never from the request.** It is `tradeImportsAnimalsFrontend.baseUrl` + the live-animals set base + `/notifications/<encoded reference>` + the origin page slug, built through `buildSetBaseUrl` (`common/helpers/set-base-url.js`). The reference is URL-encoded as one path segment, as `buildNotificationLink` and `buildReturnUrl` already do. It is not checked against a pattern. A forged reference reaches the animals origin route, which refuses a notification it does not know. CSP form-action already trusts the animals origin and the Defra ID origin (`content-security-policy.js:28`).
6. **One owner for "a live-animals notification's URL on the animals frontend" in INS.** `dashboard/view-model/list.js:51-60` already builds `<animals><set>/notifications/<ref>`. The return URL needs the same root plus the origin slug. The root moves to one owner that both `buildNotificationLink` and the return URL use. Without that, two builders would drift. List.js is touched only for that.
7. **One owner for "a browser-facing INS frontend URL" in animals.** `config/nunjucks/context/context.js:49-50` and `addresses/ins-handshake.js:89` each strip the trailing slash from `tradeImportsInsFrontend.baseUrl` and append a path. The Back link would be a third copy. Extract one helper, mirroring INS's `buildSetBaseUrl`, and move both existing callers onto it in this change. This is the structural decision that changes those two callers. Only their touched lines are fixed.
8. **Which "dashboard list gains no new entry".** Criterion 3 is proved on the animals live-animals list, which lists the journeys this session knows (`engine/journey.js:129`). It is per-session, so it is deterministic under parallel E2E. The INS dashboard reads an eventually consistent read model shared by an organisation, so it is not used.
9. **Germinal choice.** It uses inc-148's existing `startUrlFor('germinal-products')` (`<animals>/germinal-products/start`). Like inc-148's own E2E, the proof is the URL reached. The animals frontend on this branch has no germinal-products set. The germinal origin's Back link is a separate requirement and is not built here.
10. **Logging.** INS POST's return branch, which redirects to an existing notification, is a redirect and logs once at info. Its home is beside the existing hand-over log (INS `notification-type/controller.js:49-57`). The animals info log in `openNewNotification` (`features/dashboard/controller.js:142`) gains which entry began the run. No new line is added there (section 13). No log is added for which Back link is rendered: it changes no outcome.
   - Rejected: a new animals log line for the start entry. The existing line already marks the opening at its one owner.
11. **Checked claims.** The row's claims hold against the tree: `entryBackLink` exists as described; the list and overview cases are spec'd (SCN-ORIGIN-013-A..D) and tested (ins-tests `tests/animals/e2e/pages/origin.spec.ts:27`, `:238`; FIT `origin.fit.spec.js:206-249`); INS `buildSetBaseUrl`/`SET_BASES` exist; the type question has no preselect and no return. One correction: INS has no `DEFRA_ID_FORM_ACTION_ORIGINS`. inc-148 derived the form-action's Defra ID origin from the discovery URL (`get-browser-facing-discovery-url.js`), so no env var or compose change is needed.
