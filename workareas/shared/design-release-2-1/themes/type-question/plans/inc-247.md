## 0. Decisions

1. **The behaviour already holds; this row adds proof only.** Checked against the live tree: `commodity-type/controller.js:104-111` validates the payload with `validate(fields(), payload)` and re-renders at 400 before the hub exit (`exit: 'hub'`) is ever read; the hub exit is read only inside `kit.nextTarget` on a valid save (`controller.js:141`). Unit proof exists at `controller.test.js:160` (nothing chosen, lines kept), `:175` (unoffered type) and `:209` (valid choice to the overview). The FIT suite exercises the refusal on Save and continue only (`commodity-type.fit.spec.js:172`, `:191`), and has a valid Save and return test (`:140`). The tests repo has no commodity-type Save and return E2E. If a new test goes red, the fix goes in `controller.js` `post` and nowhere else. Rejected: re-implementing or "hardening" the controller with no failing test.
2. **The first criterion is proven in full in the browser, on a notification that holds a line.** A notification holds commodity lines only after a type is saved, and the saved type renders pre-checked, so a user cannot click it off. The FIT reaches the nothing-chosen-with-lines state the same way it already reaches the unoffered case: the DOM is tampered through `evaluate` (as `commodity-type.fit.spec.js:194-200` does) to clear the pre-checked radio. The form then posts no `commodityType`, which is exactly the state `controller.test.js:160` seeds on the server, and `controller.js:107-111` refuses it before the line reconcile at `:125-127` can run. So FIT test 1 (section 4) proves every half of the first criterion together: stays on the page, the error in the summary and beside the options, nothing saved, and the line still listed afterwards. Rejected: a FIT on a fresh notification with no lines, which leaves "keeps any commodities already added" unproven in the browser while the row asks for browser proof; and a FIT that seeds lines without a type through the session, which seeds a journey state through a back door when the page's own form can be driven to it.
3. **The unoffered-type case is proven in FIT, not E2E.** It needs the DOM tampered (`evaluate` setting a radio's value), which the plants FIT suite already does (`commodity-type.fit.spec.js:194-200`) and no plants E2E does. The E2E proves what only the real stack can: the refusal leaves the notification's commodity row unsaved on the real overview, and a valid Save and return lands on the real overview with the answer kept. Rejected: a DOM-tampering E2E in the tests repo.
4. **E2E home is `tests/plants/e2e/features/commodities.spec.ts`**, the commodity section spec that already drives the commodity-type page (`:118-133`). Structure follows the Save and return precedent `arrival.spec.ts:186-242`. Not tagged `@compose`; asserts on the page's own `expectedUrl` and the overview's, so it runs on CDP too. The plants PR scope (`config/e2e-tests-pr-scope.json:10`, suite `tests/plants/`) already picks it up. Rejected: a new spec file for two tests.
5. **The inline error beside the options gets a locator on the commodity-type page object**, scoped to the options group (the fieldset named by the legend "What are you importing?"), following `page-objects/ins/notification-type-page.ts:39-41`'s `inlineError` but scoped to the group rather than the whole page. Rejected: a raw locator in the spec (`AGENTS.md`: specs reach pages through page objects).
6. **The DOM tamper becomes one helper inside the FIT spec**, owning every change the spec makes to the commodity-type inputs in the DOM: submitting a value the service does not offer, and clearing the checked radio so nothing is submitted. It is used by the existing unoffered-type test (`:191`) and both new Save and return tests. What it does is chosen by an argument that says so (an options object or the value to submit), never a positional boolean flag. It is set-up shared by tests in one file only, so it stays module-level in that spec beside `radioFor`, not in `fit/high-risk-plants-journey.js`. Rejected: promoting it to the shared FIT journey helper, which no other spec needs; and a second tamper helper beside it for clearing, which would be two mechanisms for one job.
7. **The theme envelope already states the same-checks rule** (header invariant 10: "Save and return to overview makes exactly the same checks as Save and continue …"). The row's note about a stale invariant applied to the older type-question-and-templates backlog, not this one; nothing to change.
8. **Spec: widen REQ-PLANTS-COMMODITY-TYPE-003 to either save control and add a Save and return scenario under it**, rather than a new requirement, because the rule (an unoffered value is refused) is one rule whichever button posts. Provenance: ruling sam-2026-10-26 claim 1.
9. **Not routed through frontend-change.** The row adds no field, page, section or collection and changes no obligation or flow; it adds tests and spec text only. Section 8 still applies.

## 4. Tests

All production behaviour these tests prove lives in `commodity-type/controller.js` `post`, `:107-111` (validate, then re-render at 400 before either save button's destination is read). Removing that refusal, or letting the hub exit skip it, turns each refusal test red; removing the hub exit in `kit.nextTarget` (`:141`) turns the valid Save and return tests red.

### FIT (plantsfrontend, `commodity-type.fit.spec.js`)

1. **Nothing submitted, Save and return to overview, line kept.** On a wood-and-cut-trees notification holding one cut-coniferous-trees line (set up as test 2), reopening the commodity-type page, clearing the pre-checked radio through the tamper helper and selecting Save and return to overview leaves the browser on the commodity-type page URL, and shows "Select what you are importing" (`copy.errors.commodityType`) as an error-summary link and inside the options group (the group named by `copy.legend`). Nothing is saved: reopening the page shows wood and cut trees still checked. The commodities list then still shows exactly one line. Red without `controller.js:107-111` (an unvalidated save would commit an empty type and run the line reconcile at `:125-127`). This is the whole first criterion in the browser (Decision 2).
2. **Unoffered value, Save and return to overview, line kept.** On a wood-and-cut-trees notification holding one cut-coniferous-trees line, reopening the commodity-type page, tampering the checked radio's value to one the service does not offer and selecting Save and return to overview leaves the browser on the commodity-type page URL, shows the error-summary link "Select what you are importing", leaves no radio checked; and the commodities list then still shows exactly one line. Red without `controller.js:107-111` (an unvalidated save would also run the line reconcile at `:125-127`).
3. Existing `:140` (valid choice on Save and return reaches the overview and the choice is checked on return) stays as it is; it already proves the third criterion in the browser.
4. Existing `:191` changes only to call the extracted tamper helper; it must stay red without `controller.js:107-111`.

### E2E — the integration proof (tests, `tests/plants/e2e/features/commodities.spec.ts`)

5. **Nothing chosen, Save and return refused through the real stack.** A new notification's commodity-type page, Save and return to overview with nothing chosen: the URL is still `plantsPages.commodityType.expectedUrl(reference)`, the error-summary links read exactly `['Select what you are importing']`, the inline error beside the options reads "Select what you are importing"; then the overview's "What are you importing?" task row reads "Not yet started". Red without `controller.js:109-111`.
6. **A chosen type, Save and return saves and shows the overview.** A new notification, a type checked, Save and return to overview: the URL is `plantsPages.overview.expectedUrl(reference)`; reopening the commodity-type page shows that type checked. Red without the hub exit in `kit.nextTarget` (`controller.js:141`) or the commit at `:122-124`.
