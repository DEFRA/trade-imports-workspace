## What is there now

Two hostname rules for Defra ID, in two files, each with its own idea of "local":

| Rule | Where | Driven by | Used by |
|---|---|---|---|
| Browser-facing: the discovery URL's hostname becomes `to` when the rewrite is enabled and lists that hostname | `src/auth/get-browser-facing-discovery-url.js:10-25` | `defraId.browserFacingHostnameRewrite.{enabled,from,to}` (`src/config/config.js:237-255`) | sign-out URL (`src/auth/get-sign-out-url.js:5`), CSP form-action origin (`src/server/common/helpers/content-security-policy.js:6`) |
| Server-facing: the OIDC document's `token_endpoint` and `jwks_uri` take the discovery URL's hostname, keeping port and path, when that hostname is in a hard-coded set | `src/auth/get-oidc-config.js:8-22`, `:36-39` | `LOCAL_HOSTNAMES` = `localhost`, `host.docker.internal` | sign-in token exchange (`src/plugins/auth.js:35`), token refresh (`src/auth/refresh-tokens.js:11`), token verification (`src/auth/verify-token.js:11`) |

Why the server-facing rule exists: the Defra ID stub advertises its browser endpoints at `WELL_KNOWN_HOST_OVERRIDE` (`localhost:3007`) and its API endpoints at that host with `localhost` swapped for `host.docker.internal` (`repos/trade-imports-defra-id-stub/src/open-id/host.js:20-32`). Run natively against `localhost:3007` (README "AUTHENTICATION"), the frontend must reach the token and key endpoints at `localhost`; in the stack it reaches them at `host.docker.internal`.

## 0. Decisions

1. **One owner, by moving the existing browser-facing module and giving it both rules.** `src/auth/get-browser-facing-discovery-url.js` becomes the Defra ID hostname module (implementor names it for what it owns: the hostnames Defra ID URLs are rewritten to). It keeps the browser-facing discovery URL function and gains the server-facing endpoint rule. Rejected: a third module beside both (a second mechanism), and leaving the rule in `get-oidc-config.js` but reading the config there (still two owners of "which hostnames are local").
2. **"Local" is one set, read in one private helper of the owner:** the rewrite is enabled, and the hostname is in `from` or is `to`. Adding `to` to the browser-facing check changes nothing (rewriting `to` to `to` is a no-op). It lets the server-facing rule keep covering `localhost` (the native-dev case, `to` defaults to `localhost`) and `host.docker.internal` (in `from`). Rejected: adding `localhost` to `from` — that changes a configured list CDP and the stack never set, and reads as "rewrite localhost to localhost".
3. **The config key and env var keep their names.** AC1 names `defraId.browserFacingHostnameRewrite`, and the workspace stack sets `DEFRA_ID_BROWSER_FACING_HOSTNAME_REWRITE_ENABLED=true` for this frontend (`docker/stack/frontend.compose.yml:152`). The three convict `doc` strings change to state that the setting now also decides which local hostnames the server-side token and key endpoints follow. The key's name under-describes that — see section 14 and the follow-up.
4. **Behaviour is unchanged on every configured path** (checked against the live tree):
   | Where | enabled | discovery host | Before | After |
   |---|---|---|---|---|
   | CDP | `false` (`!isProduction`, and cdp-app-config sets no rewrite variable) | real Defra ID | no rewrite either side | no rewrite either side |
   | Workspace stack, local and CI (CI runs the same `scripts/stack/run-stack.sh`, `.github/workflows/lighthouse.yml:63`) | `true` (env) | `host.docker.internal` | browser → `localhost`; server endpoints → `host.docker.internal` | same |
   | Native `npm run dev` (README) | `true` (`NODE_ENV` not production) | `localhost` | browser unchanged; server endpoints → `localhost` | same |
   | FIT (`STUB_MODE=true`, `playwright.config.js:44`) | — | — | no OIDC fetch | no OIDC fetch |
   Two corners change, and neither is configured anywhere: a production-mode run with the rewrite left off but a local discovery URL now passes server endpoints through (before: rewritten); a discovery URL at `trade-imports-defra-id-stub` with the rewrite on now has its server endpoints follow that host (before: untouched). Both follow the configured setting, which is what the row asks for. No CDP change is needed, so nothing to write up for Sam.
5. **The owner returns a new OIDC document, it does not mutate the one fetched.** `rewriteEndpointHostnames` mutates its argument today; the owner's server-facing function's name must predict a returned document with endpoints rewritten.
6. **The owner reads `defraId.oidcDiscoveryUrl` and the rewrite settings itself**, as the browser-facing function does now. `get-oidc-config.js` passes it only the fetched document. Rejected: passing the discovery hostname in as an argument — it splits "which host" between caller and owner.
7. **`get-oidc-config.test.js` is rebuilt to the house test rules because this change edits it** (bounded tidy-up): it mocks the repo's own `config.js` and logger modules, asserts on a config spy, and mocks Wreck rather than the network. It moves to real config (`restoreConfigAfterEach`), `refuseOutboundHttp()` and nock at the discovery URL through `serve-oidc-discovery.js` (Decision 10). Its eight rewrite cases move to the owner's test, where the rule now lives.
8. **The integration proof is the existing `tests/ins/` E2E suite** the gate's `e2e` rung runs for this repo (scope `tests/ins/`, `config/e2e-tests-pr-scope.json`): every INS sign-in there goes through the stub's authorize page and the token exchange at the rewritten `token_endpoint`, and the notification type hand-over form-posts under the CSP form-action. No INS sign-out spec runs on the stack today: the only one, `tests/ins/security/address-book/address-book-auth.spec.ts:23`, is `@active` and excluded by `test:docker-compose`. The sign-out URL is a pure function of config and stays proven by `get-sign-out-url.test.js`, which sets the stack's values (`host.docker.internal:3007` → `localhost:3007`). Adding a stack sign-out spec needs the tests repo, which this row does not list: a follow-up (section 7), not a reason to stop.
9. **The stack's rewrite settings become one shared test helper** (new file, section 3). The owner's test, the rebuilt `get-oidc-config.test.js` and `get-sign-out-url.test.js` all set `enabled`/`from`/`to` to the stack's values and restore the same three keys. Promoting it in this change moves `get-sign-out-url.test.js:11-16` (the rewrite lines of `configureSignOut`) and its three rewrite keys at `:23-25` onto the helper; `configureSignOut` keeps only the discovery and sign-out redirect settings. Rejected: each test setting the values locally (two tests sharing set-up, against the house rule).
10. **The discovery-URL interceptor has one shared home: `serve-oidc-discovery.js`.** It gains an exported helper that sets up the interceptor at the configured discovery origin and path; `serveOidcDiscovery` goes through it, and the rebuilt test's trace-header, delayed-reply and failed-fetch cases build their replies on it. Rejected: the test deriving origin and path from `defraId.oidcDiscoveryUrl` itself (a local copy of `serve-oidc-discovery.js:8-11`).
11. **The workspace edit to `docker/stack/AGENTS.md:465` belongs to the orchestrator**, not the implementor: the workspace repo is not in the row's repos and the orchestrator commits it (section 12).
