## 0. Decisions

1. **The sign-out URL criterion already holds in animals, plants and admin.** Each `src/auth/get-sign-out-url.test.js` already sets config with `config.set`, restores it after each test and asserts the returned URL with `toBe`. None has a `vi.mock` or a spy assertion. The engineering-review commit on the theme branch (animals `dca26dfe`) did this. So this row plans no change in those three repos. Section 5 checks the criterion still holds. The rejected alternative was editing files that already meet the rule.
2. **The INS recipe criterion already holds.** `src/server/app/docs/add-a-page.md:113-117` (step 8, unit tests) already tells you to start the server with `startRealModeServer()` / `startRealModeServerServingCountries(countries)` and says it serves OIDC discovery through `serveOidcDiscovery()`. No `vi.mock` is described. No edit is needed.
3. **The INS claim is partly out of date.** No INS test that starts a server through `startRealModeServer` mocks `get-oidc-config.js` any more. The two INS tests that still do are the unit tests of the modules that *call* discovery:
   - `src/auth/refresh-tokens.test.js:12-15`
   - `src/auth/verify-token.test.js:17-20`

   Neither starts a server. The criterion "No INS frontend test mocks the repo's own get-oidc-config.js" therefore lands on these two files. Each is moved onto the network boundary in the shape of its sibling `src/auth/get-oidc-config.test.js`:
   - `refuseOutboundHttp()`
   - `restoreConfigAfterEach`
   - `serveOidcDiscovery(document)`
   - nock interceptors for the endpoint the module then calls

   `startRealModeServer` is not used, because there is no server to start. The rejected alternative was to keep the mock and only rename it, which leaves the criterion false.
4. **Both rewritten files meet the house rules in full, not only the discovery mock** (the house rules say every touched file meets them in full). Concretely:
   - **Config:** the `vi.mock` of the repo's own `config.js` goes. Tests set values with `config.set` and restore them with `restoreConfigAfterEach`. The real defaults for `tracing.header`, `defraId.clientId`, `defraId.clientSecret` and `defraId.redirectUrl` (`src/config/config.js:192-228`, `:366`) may be read with `config.get` rather than hard-coded.
   - **Logger:** the `vi.mock` of the repo's own `logging/logger.js` goes. The exemplar `get-oidc-config.test.js` runs without it.
   - **Wreck:** the `vi.mock('@hapi/wreck')` goes. nock answers at the network boundary. The request a module sent is proven by nock `reqheaders` / body matching and `scope.isDone()`, never by `toHaveBeenCalledWith`. This is the house tooling the INS `testing.md:135-142` names.
   - **verify-token:** the `vi.mock`s of `node:crypto` and `@hapi/jwt` go, together with every spy assertion on them. Without them, the only way to prove what is checked (the signing key and the first JWK) is a real signed token. Audience and issuer are not checked today (Decision 6). So the test generates a real RS256 key pair, serves the public key as a JWK from the discovery document's `jwks_uri`, and signs tokens with `@hapi/jwt`'s generator. The rejected alternative was keeping library mocks with call-record assertions, which the testing guide §1 forbids ("No spy assertions").
   - **Kept:** `vi.mock('@defra/hapi-tracing')` with a hoisted `getTraceId` stays. The exemplar (`get-oidc-config.test.js:17-21`) and INS `testing.md:146-148` both use it. The console.log spy read through `readEmfDocuments` also stays: it is the existing way to read the EMF metric line.
5. **Timeouts are proven by behaviour.** The old tests pinned `timeout: 3000` / `timeout: 1000` through the Wreck call record. The new tests prove each timeout as `get-oidc-config.test.js:117-125` does: a nock reply delayed past the timeout, and a rejection with the gateway-timeout status code.
   - The token endpoint timeout is a module-local constant (3000 ms) and is not exported. The test delays past that literal value and stays under Vitest's default 5 s test timeout.
   - Exporting the constant only for a test was rejected: the house rule allows a module-scope value a test imports, but the row needs no new export, and a literal in the test keeps the footprint inside the test file.
6. **verifyToken checks neither audience nor issuer today, and this row does not fix it.**
   - What the code does: `src/auth/verify-token.js:29-34` passes `aud` and `iss` inside the second argument of `Jwt.token.verify`. In @hapi/jwt that argument is only the secret (`node_modules/@hapi/jwt/lib/token.js:122-126`). The payload checks (`internals.audiance(payload.aud, options.aud)` at `:150`, `internals.match('iss', …)` at `:154`) read the third argument, which is never passed. So a token signed by the served key resolves whatever its audience or issuer.
   - The same call shape is in animals and plants (`src/auth/verify-token.js:29-34`). Admin passes no audience or issuer at all (`src/auth/verify-token.js:23`).
   - Decision: leave the gap to its own backlog row, "Defra ID token verification refuses a token for another audience or issuer, in every frontend" (section 7, Follow-ups). Drop the wrong-audience and wrong-issuer tests from this row. No test in this row asserts anything about audience or issuer, either way, so today's unchecked behaviour is not pinned as correct.
   - Why not fix it here: it is a sign-in behaviour change in four frontends, not a test move. Turning the checks on can refuse every real sign-in if Defra ID or the Defra ID stub issues tokens whose `aud` is not the client id or whose `iss` differs from the discovery document's `issuer`. Nothing in this row checks that. Admin also needs an issuer source it does not read today. That needs its own decisions, logging for the new refusal (section 13 of its own plan), a spec scenario under each prefix, and an E2E sign-in proof through the stack. This row is `kind: test` and its criteria are about mocks.
   - Rejected: fixing the call in all four repos inside this row, for the reasons above; and keeping the two tests, which the implementor could not make green without that fix.
7. **`plugins/auth.test.js`, which mocks `get-oidc-config-with-retry.js`, stays out of this row.** That is a different module, and the criterion names `get-oidc-config.js`. The file also mocks five more of the repo's own modules, so it needs a full rewrite of its own. It goes to section 7 as a follow-up. This is a scope call, not something a test proves.

Behaviours the file must prove:
- **The posted request:** the refresh POSTs to the discovery document's token endpoint, with:
  - the form-encoded body: client id, client secret, `refresh_token` grant, scope `openid offline_access <clientId>`, the refresh token and the redirect URL;
  - the `Content-Type` header;
  - the trace id in the configured tracing header.

  It resolves to the token endpoint's reply payload. Prove it with nock body + `reqheaders` matching, `scope.isDone()` and `toEqual` on the returned value.
- **No trace id:** with no trace id, the tracing header is sent empty.
- **EMF metric:** the call is measured as dependency `defra-id`, operation `token-refresh`, interface `SYN-13`, with no failure.
- **Failure:** when the token endpoint fails (nock `replyWithError`), the call rejects with that error and a failure metric is written.
- **Timeout:** a token endpoint reply slower than the timeout rejects with the gateway-timeout status.

### insfrontend `src/auth/verify-token.test.js`

What has to be true afterwards:
- No `vi.mock` of `./get-oidc-config.js`, `../config/config.js`, the logger, `@hapi/wreck`, `node:crypto` or `@hapi/jwt`.
- No `toHaveBeenCalled*` assertion.
- Unused imports go.

Set-up is the same shape as the refresh test. The served discovery document carries a `jwks_uri` and an `issuer`. On top of that:
- A real RSA key pair (Node's crypto) whose public key, exported as a JWK, is the JWKS nock serves at `jwks_uri`.
- Tokens signed with `@hapi/jwt`'s generator, RS256, with that private key.
- The tokens carry the configured client id as audience and the document's issuer, so they stay valid once the follow-up row turns those checks on. No test varies either one (Decision 6).

Behaviours the file must prove:
- **Valid token:** a token signed by the served key resolves to `undefined`. The JWKS request carried the trace id in the tracing header (nock `reqheaders`, `scope.isDone()`).
- **Wrong key:** a token signed by a different key rejects with the signature error the module really throws.
- **First key only:** when the JWKS lists the signing key second and another key first, the token rejects. This proves only the first key is used. It replaces the old `createPublicKey` call-record assertion.
- **Empty key set:** a JWKS with no keys rejects. Assert the error the module really throws (its code or message), not just "throws".
- **No trace id:** with no trace id, the JWKS request's tracing header is empty.
- **EMF metric:** the key fetch is measured as dependency `defra-id`, operation `jwks`, interface `SYN-12`, with no failure. A failed key fetch (nock `replyWithError`) rejects with that error and writes a failure metric.
- **Timeout:** a JWKS reply slower than `OIDC_DOCUMENT_TIMEOUT_MS` (exported by `get-oidc-config.js`) rejects with the gateway-timeout status.

Assertion style: each rejection asserts its error contract (`rejects.toMatchObject` / `rejects.toThrow` with the specific message or code observed), never a bare `rejects.toThrow()` (testing guide §7).

## Plan review: must address

The plan review left these findings open on the revised plan. Each is required work for the implementor, and the consistency reviewer reports any the change does not address.

1. [detail] 2. Edits (refresh-tokens and verify-token, EMF metric and Failure behaviours) and 4. Tests: The plan moves both files onto a real getOidcConfig served by serveOidcDiscovery. But getOidcConfig wraps its own fetch in measureExternalCall (`src/auth/get-oidc-config.js:11-19`, operation `openid-configuration`). So each refreshTokens and verifyToken call now writes two EMF documents to the console.log spy, not one. `readEmfDocuments` (`src/server/common/test-helpers/emf-documents.js:10-15`) returns every EMF line in order. The plan says the call 'is measured as dependency defra-id, operation token-refresh / jwks' and that a failure 'writes a failure metric', but it does not say how to pick that line out. The existing tests use `toHaveLength(1)` and destructure `[document]` (`verify-token.test.js:81-82`, `:157-158`). Carried over, that waits for one document or reads the discovery metric by mistake. Then the test proves the wrong line, or it times out. Rule: .claude/rules/code-quality.md Tests: "A test title states what its assertions prove." and "A test must fail without the change it covers." Must become true: Section 2 says the metric and failure-metric checks in both files select the document for the operation they cover: token-refresh with SYN-13, or jwks with SYN-12. They must not rely on there being one EMF document. Breaking `DEFRA_ID_CALLS.tokenRefresh` or `DEFRA_ID_CALLS.jwks` must still turn the test red, even though the discovery metric is there too.
