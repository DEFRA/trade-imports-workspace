1. **Three of the row's six parts have already landed; plan only what is left.** Checked against the live tree:
   - One shared axe helper exists: `fit/axe.js` (`expectNoSeriousOrCriticalViolations`), imported by every FIT spec that runs axe (dashboard, notification-type, address-book add/edit/view/delete/list, smoke). No inline copy remains.

   - `expectDashboard` already lives at `features/dashboard/fit/dashboard.js`. There is no `features/address-book/fit/dashboard.js`. The address-book specs (delete, edit, list, view) already import it from the dashboard feature. `testing.md:227-228` and `features.md:14-17` already describe it there.
   - No dashboard FIT title carries an acceptance-criteria id (`grep -rnE "\(AC[0-9]"` over `src/server/app/features` finds nothing).

   What is left: the INS backend stub's organisation-scoped empty seed, a FIT for the empty dashboard, View link hrefs built from configuration, and organisation ids on every `signIn`. Section 5 still checks all three acceptance criteria, including the parts that have landed.
2. **The row says "under services in the INS frontend". The stub is at `src/server/app/services/ins-backend/stub.js`.** There is no top-level `services/` folder.
3. **Only the stub keys its data by organisation. The real dashboard stays unscoped.** `services.md:72` says "The dashboard is not scoped to an organisation", and `ins-backend.test.js:79` proves the client sends no organisation header. The INS backend has no organisation support (`grep -rli organisation repos/trade-imports-ins-backend/src/main` finds nothing).
   - The service barrel (`services/ins-backend/index.js`) takes the organisation id first, as the address-book barrel does (`listAddresses(organisationId, listQuery)`). It passes the id to the stub only.
   - The client keeps its signature and still sends no organisation.
   - Rejected: sending the organisation to the real backend. That changes cross-service behaviour the backend cannot honour, and belongs to another row.
   - Rejected: keying the empty seed on a query value. The empty state is the no-search state, so the query cannot pick it.
4. **The controller reads the organisation without refusing a request that has none.** It uses `organisationIdOf(request)` (`src/server/common/helpers/organisation-id.js:1`), not `kit.requireOrganisationId`.
   - Rejected: `requireOrganisationId`. It would add a 403 to the signed-in landing page, which is new behaviour this row has no grounds for.
   - Consequence: the stub must treat a missing organisation as an ordinary one, so it serves the canned notifications.
5. **The stub's seeds follow the address-book stub's suffix convention, empty seed only.** An organisation id ending `-empty` gets no notifications. Every other id, or none, gets today's four canned notifications, one of them deleted.
   - No `-paginated` seed: nothing would reach it (house rule "Build only what this change makes reachable").
   - The canned list is read-only, so the stub does not need the address-book stub's per-organisation `Map`.
6. **Expected View link hrefs come from `config.get('tradeImportsAnimalsFrontend.baseUrl')`.**
   - In `controller.test.js` and `dashboard.fit.spec.js`, the expected href is the configured base URL plus the literal `live-animals/notifications/...` path. It is never built by calling `buildNotificationLink`: a test that uses the code under test to build its own expectation cannot fail.
   - In `view-model/list.test.js`, the test sets the base URL itself (`ANIMALS_BASE_URL`, `list.test.js:14,21`). Its expectations are built from that same input constant instead of repeating the `http://localhost:3000` literal (`:69,77,84,92,121`).
   - The FIT runner and the FIT web server read the same environment: Playwright's `webServer.env` is added on top of `process.env`. They also share the same convict default, so both resolve the same base URL.
7. **"Every FIT signs in with its own organisation id" applies to every FIT spec that signs in, not only the two the row names.** `page-title.fit.spec.js:21` also calls `signIn(page)` bare. `address-book/fit/list.fit.spec.js:21-23` shares `ORG_DEFAULT`, `ORG_EMPTY` and `ORG_PAGINATED` across about twenty tests.
   - Both files are in scope, because acceptance criterion 3 says "every FIT".
   - Each test gets its own id, with the `-empty` or `-paginated` suffix where it needs that seed.
   - **Id scheme for the re-signed specs (dashboard, notification-type, page-title, list):** the literal `stub-org-<page>-<case>` id that `add-a-page.md:136-137` sets, with `-empty` or `-paginated` appended where the test's seed needs one. None of these tests writes store data (checked: the list, page-title and notification-type tests only read, search, page or submit an empty form; the dashboard stub is read-only), so none mints a `crypto.randomUUID()` id and none gains an inline minting copy.
   - Rejected: minting a random id per test the way the address-book write specs do. It adds another local copy of that set-up and the recipe reserves it for tests that write.
   - Where a spec signs in from a `beforeEach` today (notification-type, page-title), each test signs in with its own literal id instead, so the id names the case.
   - **`fit/sign-in.js` refuses a call with no organisation id.** Dropping the `'stub-org-1'` default alone is not enough: `signIn(page)` would still destructure `{}` and navigate to `?organisationId=undefined`, which the stub sign-in accepts as an ordinary organisation. So the organisation id becomes a required argument, and `signIn` throws, before it navigates, when the id is missing or empty. A future spec that leaves it out fails at its first step instead of signing in silently as `'undefined'`.
   - Rejected: only removing the default. It keeps the silent `'undefined'` sign-in.
   - Rejected: refusing `'undefined'` in the stub sign-in route. That changes production-side code to guard a test helper.
   - Once the specs above are fixed, every caller (smoke, `sign-in-and-open.js`, the dashboard, notification-type, page-title and list specs) passes one.
   - The guard has no test of its own: `fit/**` is excluded from the unit run (`vitest.config.js:9`), and every FIT spec calls `signIn` first, so a spec that omits the id goes red on its first step.
8. **Out of the row:** `notification-type.fit.spec.js` hard-codes `ANIMALS_ORIGIN` and `PLANTS_ORIGIN` (`:76,94`). The criterion names only dashboard tests, so this goes to section 7 as a follow-up. The same goes for `notification-type/controller.test.js:25` and `common/test-helpers/journey-handshake.js:35`.
9. **No end-to-end test in the tests repo.** Nothing a user or another system sees changes. The stub serves only stub-mode runs (FIT and local `STUB_MODE`). The real-mode dashboard sends the same request as before, and the page renders as before. The FIT added in section 4 is the proof the empty state can be reached.
