## 0. Decisions

- **Which run steps build their Back link by hand.** `RUN_STEPS` (`src/server/app/sets/live-animals/journeys/linear/flow/run.js:29-74`) has thirteen entries. Seven already call `runBackLink`: commodities (search, `src/server/app/sets/live-animals/journeys/linear/features/commodities/search/search.controller.js:54-56`), import reason, consignment details, additional details, transit countries, documents (`src/server/app/sets/live-animals/journeys/linear/features/documents/view-model/render.js:86`) and addresses. Six do not:
  - animal identification, `src/server/app/sets/live-animals/journeys/linear/features/commodities/animal-identification/animal-identification.controller.js:69` (`hubPath` by hand);
  - arrival details (the port-of-entry page, its title is "Arrival details"), `src/server/app/sets/live-animals/journeys/linear/features/transport/port-of-entry/port-of-entry.controller.js:64` (`hubPath` by hand);
  - the transporter list, `src/server/app/sets/live-animals/journeys/linear/features/transport/transporters/transporters.controller.js:57` (`hubPath` by hand);
  - contact address, `src/server/app/sets/live-animals/journeys/linear/features/contact/controller.js:85` (`hubPath` by hand);
  - **the review page**, `notificationViewPage` (`run.js:73`), whose `backLinkFor` (`src/server/app/sets/live-animals/journeys/linear/features/check-answers/controller.js:74-77`, used at `:135`) builds `hubPath` by hand for a draft or amendment and `dashboardPath()` for a submitted notification;
  - origin, `src/server/app/sets/live-animals/journeys/linear/features/origin/controller.js:58`, through `entryBackLink` (`src/server/app/sets/live-animals/journeys/linear/flow/entry-guard.js:61-71`).
  The row names only the first four. The earlier plan's claim that every other run step already calls `runBackLink` was wrong, and this plan corrects it.
- **The review page goes through `runBackLink` for a draft and an amendment.** Its Back link stays as `src/server/app/sets/live-animals/docs/journey-flow-and-gates.md` and REQ-CYA-003 state it: a draft's review and an amendment's review go back to Overview, and a submitted notification's view goes to the notification list. The draft and amend branch now comes from `runBackLink` for the review page's step id, with the journey, scope and answers the render already holds. The submitted branch keeps `dashboardPath()`: that destination is not a run Back link and `runBackLink` has no rule for it. `runBackLink` answers Overview for the review page in every draft and amend state: it has no `backCandidates`, so `previousRunTarget` is null, and the GET completes the opening run before it renders (`check-answers/controller.js:196`). So no Back link changes. Rejected: recording the review page as a departure from AC 1. The move is small, keeps the page's behaviour, and makes the criterion true for this step too.
- **Origin keeps `entryBackLink`, recorded as a departure from AC 1 (section 14).** Origin's Back link has rules no other step has: the start-entry opening run goes to the INS type question, any other opening run goes to the dashboard, and a journey the overview would not admit goes to the dashboard (`entry-guard.js:61-71`). REQ-FLOW-016 says origin "MUST keep the Back link it has without the Change link". `runBackLink` would answer Overview for origin in all of those states. Moving origin onto it means adding origin-only branches to the shared helper. Rejected: an origin option on `runBackLink`. That is a second rule set inside the shared owner for one caller, and no backlog row asks for it.
- **The CPH number page stays as it is.** `src/server/app/sets/live-animals/journeys/linear/features/cph-number/controller.js:40` builds `hubEntryReturn(request) ?? hubPath(...)` by hand, but CPH is not a run step. It has no `RUN_STEPS` entry, and REQ-FLOW-007 says the run never offers it. AC 1 covers run steps only, so this is no departure.
- **No Back link changes, so the row's "where the move changes a Back link" has no case.** None of the four named steps nor the review page has `backCandidates`. So `previousRunTarget` returns null for each, and `runBackLink` (`src/server/app/shared/kit.js:289-305`) falls back to Overview in every state: opening run active, a draft opened from a Change link, opened from Overview, and amending. None passes `returnsToReview`. This matches REQ-FLOW-016 ("A page whose opening-sequence Back link is Overview MUST keep Overview") and `journey-flow-and-gates.md:153-155`. Rejected: giving any of these steps a `backCandidates` entry. That is a journey-flow change the design source has not asked for.
- **The page's own state reaches the helper the way transit countries does it.** `runBackLink` needs `{ journey, scope, answers }`. Each page's render takes the state `state.get` returns (or the fields the helper needs from it) in place of the bare journey, and awaits the helper. Exemplar: `src/server/app/sets/live-animals/journeys/linear/features/transport/transit-countries/transit-countries.controller.js:41-68`, whose render takes `current` and awaits `kit.runBackLink(request, page.id, current)`. The review page's render already holds journey, scope and answers. It reads the request from `h.request`, as origin's render does. Rejected: working out the Back link once in each handler and passing a string to render. That repeats the call at every render call site: four or five per page.
- **Animal identification's render becomes async, and its cap-reached path follows.** `capReachedResponse` (`src/server/app/sets/live-animals/journeys/linear/features/commodities/animal-identification/form/forms.js:114-133`) calls the injected `render` and returns what it returns. It still returns null when the add is not at the cap, so the post's `if (capReached)` check stays correct with an async render. `renderRefused`'s chained `.code(...)` has to await the render first. `capReachedResponse` changes only where it passes state through, if the render's signature needs it.
- **Pinning tests, and the probe that shows they go through the helper.** Behaviour does not change, so a Back link test passes before the move and after it. The row asks for controller tests proving each moved page follows the journey-flow spec in all three states (AC 2). Those tests catch a regression. The probe that shows they exercise the helper is the Overview fallback in `runBackLink` (`src/server/app/shared/kit.js:303`): after the move, breaking that fallback turns every moved page's tests red. Before the move, the same probe leaves them green.
- **One shared test registrar for "Back stays on Overview".** Four test files and the addresses tests need the same cases. It goes beside `itSendsBackCarryingChangeTo` in `src/server/app/sets/live-animals/journeys/linear/test-support.js`, asserts through `expectBackLinkIsPath` (`src/server/app/engine/test-support.js:360`), and the copies in the addresses tests are deleted (house rule: promoting a helper deletes the local copies). The review page keeps its own tests (`src/server/app/sets/live-animals/journeys/linear/features/check-answers/check-answers.test.js:345-370`): they already pin the three statuses through that file's own engine set-up, and the registrar's GET driver does not render the review.
- **Local shared-copy duplicates in edited files.** `contact/controller.js:35` and `check-answers/controller.js:41` each build `copyFor({ en: sharedEn, cy: sharedCy })` beside `sharedCopy` in `src/server/app/shared/kit.js:19`, which is the same value. Both files are edited for this row, so both duplicates go (one mechanism, one owner) and each page reads the kit's `sharedCopy`.
- **Port-of-entry's label-class literal.** `QUESTION_LABEL_CLASSES` (`port-of-entry.controller.js:35`) is used only by `render`, so it moves into `render` (house rule: a literal used by one function lives in that function).
- **The transporters and contact posts take the committed state from `recoverableSave`'s value.** Both posts are edited (their fallback renders change), and both declare `let committed` and assign it inside the save callback (`transporters.controller.js:141-145`, `contact/controller.js:170-179`). `recoverableSave` already returns the save's value (`src/server/app/shared/kit.js:409`), and port-of-entry reads it (`port-of-entry.controller.js:107`). Code style §11 and §4 apply: no `let` without a reassignment need, no mutation from a callback.
- **Spec: one new scenario under REQ-FLOW-016, naming the five pages the tests cover.** REQ-FLOW-016 already states the rule; no scenario covers it, so the new tests have nothing to link to. The scenario names the five pages whose controller tests the shared registrar drives, by their titles: Identification details, Arrival details, Transporter details, Contact address for consignment, Consignment addresses. Rejected: "none". The row says openspec records this, and AC 2 ties the tests to the journey-flow spec. The review page needs no spec change: REQ-CYA-003 and its four scenarios already state its Back link.
