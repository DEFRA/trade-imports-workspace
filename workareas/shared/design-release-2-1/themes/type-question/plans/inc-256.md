## 0. Decisions

1. **The shape guard's one owner is the existing generic module, moved to `lib/`.** The live tree already has three copies of one rule (a plain object: not null, of type object, not an array): `services/persistence/session/real.js:9`, `services/persistence/session/stub.js:9`, and the exported one in `services/persistence/records/fulfilment-codec/shape/object.js:3`, which five codec modules import. Adding a new helper under `lib/` would leave two owners (the row's own example, taken literally). Having the session adapters import from `records/fulfilment-codec/shape/` would make session code depend on a codec's internals. So `shape/object.js` moves whole to `src/server/app/lib/object.js` — `architecture.md:45` makes `lib/` the home of "small generic helpers", and every helper in that module is generic. Services already import `lib/` (e.g. `services/address-book/client.js`), and `.dependency-cruiser.cjs` allows it. Rejected: a new lib module beside the codec's (two owners); importing the codec module from session (wrong-layer coupling).
2. **That move changes five codec import lines.** This is a structural decision the row needs: one rule, one owner. Each of those five files gets only its import line changed, plus a fix to any house-rule breach in the lines touched.
3. **`byJourneyFrom` and `knownFrom` stay in each adapter.** The two adapters read from different stores (`request.yar` vs `request.state`), so only the shape check is the shared rule. Rejected: a shared read helper that takes the store as a parameter. It adds a new abstraction this row does not ask for.
4. **context.js: delete all three inline comments.**
   - Lines 64–65 describe the view.
   - Lines 69–71 describe hapi-vision and a set's extension.
   - Lines 80–82 describe `kit.base()` and the dashboard's view.

   The rationale in the second and third (the global view context reads the set from the request path, because the view renders after the handler's async context may be gone; it supplies a home link that a view's own context overrides) moves as a stated fact into `src/server/app/docs/add-a-set.md`. The house rule puts rationale in docs, not code. Rejected: rewording the comments.
4a. **add-a-set.md rule 2 gains its stated exception, and the moved fact sits there.** Rule 2 (`add-a-set.md:54-57`) says a request resolves its set "from the owning plugin realm, never from the URL" and "Do not parse the path to work out which set you are in". The live tree already parses the path, through `setIdForPath` in `shared/set-context.js:15`, in three server-wide places that run where no set route's context holds:
   - the set context resolved before routing, `setContextExtension` (`shared/set-context.js:84-93`, an `onRequest` extension the composition root registers);
   - the shared error page (`common/helpers/errors.js:16`);
   - the global view context (`config/nunjucks/context/context.js:72`), which runs at hapi-vision's marshal step after the handler's context has gone.

   So rule 2 is untrue today, and placing the moved context.js fact beside point 4 would make the doc contradict itself. Rule 2 must state one consistent rule: a set route resolves its set from its plugin realm, and a set's own code never parses the path; the server-wide cases above, which run before routing, outside every set route or after the handler, resolve it from the path through the one shared path resolver. The moved context.js fact goes with that exception in rule 2, not in point 4. Rejected: putting the fact in point 4 and leaving rule 2 absolute (the doc contradicts itself); deleting the fact (rationale is lost).
5. **context.js: trim `activeNavigationItem`'s doc comment to its contract as well.** The file is touched, so it meets the rules in full. The summary line says "so the layout can mark it active", which describes a caller. The contract it keeps: the active navigation item id for a request path — `dashboard` for any path inside the dashboard's section, including a notification's pages — and null outside a set context or outside every item.
6. **roles-and-addresses.js: the doc comment states the contract of `rolesAndAddressesCard` only.** That is: a summary card with one row per party, a CPH row when CPH applies, and, unless read-only, a card Change action to the addresses page and an edit link on each party row. It also says what `parties` and `partyErrors` hold. Three things go, because they narrate other code:
   - "computed once by the controller and threaded down";
   - "the page the hub's addresses task row leads with";
   - "The one Change link" (a count).

   The rows-span-two-pages and Change-target facts are observable behaviour. Section 8 confirms the behaviour spec already owns them or needs nothing.
7. **The positional boolean `readOnly` in `rolesAndAddressesCard(journeyId, answers, readOnly, …)` stays this increment.** Fixing it means changing the signature across its caller (`sections/consignment-parties.js:21`) and the shared `editableActions(readOnly, …)` in `rows/change-link.js`. The row's bound forbids a signature change across callers for clean-up alone. It goes to section 7 as a follow-up.
8. **The row's claim that lighthouse.md "still describes 19 literal URLs" no longer holds.** An earlier type-question commit (`aae6429c`) already rewrote the guide around derived targets. The guide is still untrue in places against `seed-audit-targets.js`, `audit-targets.js`, `run-audit.js` and `lighthouserc.cjs` (listed in section 2). The row's work is to make it fully current, not a rewrite from scratch.
9. **No new unit test.** The change preserves behaviour. These existing tests already exercise the moved rule through the adapters' and codec's own inputs and outputs:
   - `session.test.js:196`: a stub cookie value that is not an object reads as no entry;
   - `real.test.js`;
   - `fulfilment-codec.test.js`.

   Adding a test only to cover a moved helper is barred.

It follows `docs/best-practices/doc-comments/jsdoc.md`: summary, then `@param`/`@returns` for the exported function. No code changes.
- `src/server/app/docs/add-a-set.md` rule 2 (lines 54–57, "A request resolves its set from the owning plugin realm, never from the URL"), per Decision 4a. It must state, as one consistent rule:
  - a set route resolves its set from its owning plugin realm through the sandboxed `onPreAuth`, and a set's own code never parses the path;
  - the server-wide cases resolve it from the request path through the shared path resolver in `shared/set-context.js`: the set context resolved before routing, the shared error page, and the global view context;
  - the global view context resolves it from the path because the view renders after the handler returns, when the handler's set context may be gone (the fact moved out of context.js);
  - the global view context supplies the chrome's home link for every rendered view, and a view's own context, such as `kit.base()`'s, overrides it (the other fact moved out of context.js).

  Point 4 ("Async boundaries are wrapped") and the co-residency list entry at line 75 stay as they are; line 75 already names the before-routing case and agrees with the new rule 2.
- `src/server/app/sets/live-animals/docs/lighthouse.md`: bring every statement in line with the code. The guide must state, as facts:
  - **How to run it.** Start the workspace stack, then run `npm run lighthouse`, never `lhci autorun` alone. The run is `lighthouse:targets` then `lighthouse:run`.
  - **What `lighthouse:targets` does** (`seed-audit-targets.js`):
    - makes sure the address book holds an address, via `TRADE_IMPORTS_ADDRESS_BOOK_URL`, default `http://localhost:8089`;
    - signs in;
    - seeds one notification per seed shape: draft, submitted and transit;
    - derives one URL per audited GET route;
    - re-fetches every URL in a fresh signed-in session and fails the run unless each answers 200 with a heading;
    - writes origin, journey ids, URLs and report names to `.lighthouse/targets.json`.
  - **The origin.** It is `LIGHTHOUSE_BASE_URL`, default `http://localhost:3000`. Replace the untrue "does not read `LH_BASE_URL`" line (29) and the fixed-origin claim (18).
  - **How pages are picked** (`audit-targets.js`):
    - every GET route of the set, minus `SKIPPED`;
    - `FILLED_BY` picks the seeded shape a route is audited on, draft by default;
    - `QUERY` adds a query string a route needs;
    - a route with a path parameter other than the journey id must be skipped, or derivation fails;
    - every list entry is checked against the live route table;
    - the dashboard route maps to the set base.
  - **Adding or changing a page.** It adds `FILLED_BY`, `QUERY` and the render check to the steps.
  - **Reports.** `lighthouse:run` clears the previous run's reports, runs LHCI, then renames each report to a route-derived name: the mount prefix and seeded journey ids dropped, `home` for the root. Two routes that would share a name fail the run. With no URLs it writes an empty manifest. This replaces the untrue "filename uses the requested path" section (65–71) and the "overwrites its predecessor's reports" line (126).
  - **The Chromium flags.** As `lighthouserc.cjs` sets them, including `--disable-dev-shm-usage`. Or drop the flag list rather than leave it partial.
  - **Keep as is.** The score table, the flagged-findings output and the CI section, which hold against `.github/workflows/lighthouse.yml`.
