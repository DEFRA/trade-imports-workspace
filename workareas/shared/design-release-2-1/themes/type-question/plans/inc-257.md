## 0. Decisions

1. **What a "state a controller test starts in" is.** Five of `driveHandler`'s options describe the state the journey or the request is in before the handler runs, and each one is used across many files:
   - an amendment: the journey submitted and an amendment opened (`amend`, 7 files);
   - a phase of the opening run, with the entry that began it (`openingRun` and `openingRunEntry`, 7 files; the entry is only ever passed together with a phase);
   - session-only answers (`flowOnly`, 4 files);
   - a page opened from a Change link (`query: { change: '1' }`, about 45 calls; the row's detail names "change context");
   - the records store refusing every save (`saveFailure`, 13 files).
   Each gets one named helper in `engine/test-support.js`. Rejected: leaving `saveFailure` as an option because it is a backend condition rather than journey state. A test that says "the backend refuses saves" is just as much a starting state, and the row's criterion asks for `driveHandler` to keep only what no helper covers.
2. **How the helpers reach `driveHandler`: one composable list, not a wrapper per state.** Tests combine states (opening-run phase and entry; amendment and Change link; flow-only answers in or outside the run), and several local helpers turn a state on or off by argument (`postCommoditySelection({ openingRun })`, `guardFor({ openingRun })`, `itSendsBackToOverview`'s cases). So each named helper returns a starting-state value. `driveHandler` takes a list of them through one option, which replaces the five options above, and applies each in list order once the journey exists and its answers are seeded. Rejected:
   - one wrapper function per state (`drive…During…`), because combinations would multiply wrappers;
   - helpers that seed a journey and return its id for `{ journeyId, state }`, because a test would then need two statements and build cookies by hand.
3. **What one starting-state value can contribute.** Each one contributes some of four things, and `driveHandler` alone composes them:
   - work on the created journey in the store (the amendment: submit, then open an amendment through the records adapter);
   - request cookies for the journey (the opening-run phase cookie, the opening-run entry cookie, the flow-only answers cookie);
   - query parameters (the Change link's `change=1`), merged with the test's own `query` and passed both to the request's `query` and to the `url` that `pathOf` builds;
   - a records adapter that refuses saves while the handler runs. `driveHandler` keeps owning the `try/finally` that restores the stub records afterwards.
   The test's own `query` and `state` win on a clash, as `state` does over the seeded cookies today.
4. **What `driveHandler` keeps:** `payload`, `seed`, `params`, `query`, `state`, `journeyId` and `pathOf`, plus the one starting-state option. No helper covers these. `seed` holds answer data, not a state. `journeyId`, `state` and `pathOf` serve a few specialised tests: an existing journey, an earlier journey's cookies, the added-address banner, a request path. They are not common seeds.
5. **The opening-run helper takes the phase, and optionally the entry.** Callers vary the phase (`RUN_ACTIVE`, `RUN_COMPLETE`) by argument, so it is one helper with the phase as its argument. It is not two helpers for "during" and "after", which would force those parameterised tests to branch. The entry is never recorded without a phase, so it is a named option of the same helper and not a helper of its own. No positional boolean.
6. **The change-link helper covers `driveHandler` calls only.** Tests that build a request with `journeyRequest(…, { query: { change: '1' } })` or `stubH` directly do not go through `driveHandler`, and they stay as they are (`shared/kit.test.js`, `engine/journey.test.js`, and the `viewOfJourney` path in `check-answers.test.js`).
7. **The change-link helper uses the literal `change=1` that `appendChangeContext` writes.** `shared/kit.js` exports no constant for the parameter name: `requestSaveChoice` reads `request.query.change`, and `appendChangeContext` writes `change=1`. Rejected: adding a production constant, because the row says no production code changes. Recorded as a follow-up.
8. **Check-answers' local `journeyIdForStatus` and cancel-amend's `startAmend` keep their own submit-then-amend lines.** Neither drives a handler through `driveHandler`. They build a journey for `journeyRequest`/`stubH` directly. Moving them would widen the footprint (cancel-amend's file is not otherwise touched) and needs a store-only form of the amendment seed that this row does not otherwise need. Recorded as a follow-up.
9. **Plants is not changed, and this is a recorded departure from the one-concept-one-name rule.** Plants' `engine/test-support.js` has its own, shorter `driveHandler` with `amend`, `openingRun` and `saveFailure` options (`:255`–`:290`). Once animals moves to named seeding helpers, the twin test supports use two vocabularies for the same three concepts: seeding an amendment, seeding a run phase, refusing saves. That breaks "One concept, one name, … across twin repos" (`.claude/rules/code-quality.md`, Names), and the workspace guide says both frontends' file shares its rows (`docs/best-practices/node/testing/frontend.md:103`). The row's `repos` is `["frontend"]` only, so the planner cannot change plants here. It is listed in section 14 as a departure, and the plants follow-up in section 7 closes it. Rejected: returning ok:false to add plants, because the row's requirement is animals-only and the plants half is a self-contained follow-up row.
10. **The workspace testing guide is outside this row's repos.** `docs/best-practices/node/testing/frontend.md` sits in the workspace repo and describes both frontends' `driveHandler`. It is listed under section 12 as made untrue for animals, with the fact it must state, and as a follow-up. This row's edits stay in `frontend`.
11. **Test count.** The migration moves set-up only. Every `it`/`it.each` case stays, so the suite count stays at the baseline above. `itSendsBackToOverview`'s four case descriptions are unchanged: they are the filter keys callers pass in `cases`.
12. **`driveHandler` refuses an option it does not take.** Its destructuring today drops any unknown key silently, so a caller still passing a removed option (by key, by shorthand such as `{ saveFailure }` or `{ openingRun }`, or through a `...options` passthrough) would run with no seeded state and might still pass. `driveHandler` therefore throws, naming the key, when it is given any option outside the ones decision 4 keeps. Every leftover caller then fails the unit suite. Rejected: proving the migration by grep alone, because the option words are also production names (`session.openingRun`, `records.amend`) and local names, so no grep can be empty afterwards and still catch shorthand callers.
13. **The opening-run cookie shape gets one exported owner in `engine/test-support.js`.** `opening-run.test.js`'s local `runRecord(journeyId, phase)` (`:66`–`:68`) builds `{ [openingRunCookie()]: { [journeyId]: phase } }` by hand. It is the same shape the module-private `openingRunState` (`:217`–`:218`) builds. Its callers (`:381`, `:530`) need it for a journey other than the one driven ('some-other-journey'), and `:530` passes it to a request built outside `driveHandler`. So the shared test support exports one builder of the opening-run cookie for a given journey and phase. The opening-run seeding helper builds its cookie through it, and `runRecord` is deleted, its two callers using the exported builder. Rejected: keeping `runRecord` as a local copy. That breaks "Promoting a helper deletes the local copies". The earlier claim that it "replays a cookie the handler set" was wrong: it builds the cookie.
