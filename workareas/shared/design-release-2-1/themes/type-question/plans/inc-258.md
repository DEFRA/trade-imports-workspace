## 0. Decisions

1. **Every rationale comment in `start.spec.ts` is deleted, not reworded.** There are six (lines 29–30, 46–47, 61–63, 67–70, 75–76, 132–133). Each explains why the app behaves as asserted. Per house rules, that reasoning belongs in the behaviour spec, and the plants overview and dashboard capabilities already state it. Rejected: moving any of them into a test title, which would turn a title into narration.
2. **Two test titles in `start.spec.ts` are retitled, because the file is being edited and both titles break the title rule.**
   - The Overview test (line 34) says "the task rows landed so far". That is build history, and its assertions prove something else: the journey strip, the Draft status and reference, no cancel/amend, the four group captions in order, and each row's status and link state.
   - The delete test (line 120) says "soft-deletes". The assertions never observe a soft delete. They prove the deleted banner and that a search for the reference no longer finds the card.
   - Each new title states what its assertions prove. The implementor writes the wording.
   - Rejected: leaving them. The file is touched, and "pre-existing" is not a reason.
3. **Whether a page-object or journey doc comment stays depends on one test.** It stays only if it states what a caller needs to call that exported member correctly: a precondition (which page it must start on), the page it lands on, its side effects, its return, or a parameter constraint. A comment about the UI, govuk-frontend, the backend, another method, scope rules or test intent is deleted, not reworded. That is the doc-comments guide's default fix.
4. **"Exported method" in the first acceptance criterion is read as "exported public API",** as the house rule says. So contract comments on the exported `CommodityLine` type and on the option fields of the exported `completeNotification` stay. Those fields are that method's parameter contract. Rejected: deleting them to fit the criterion's narrower wording, which would lose the uniqueness constraint a caller has to know.
5. **A comment that mixes contract with rationale keeps its contract sentence and loses the rationale clause.** It is applied to every doc comment `journey.ts` keeps, one by one. Four need a trim:
   - `CommodityLine` (journey.ts:7): the second sentence goes.
   - The `name` option (journey.ts:73): the clause after "Must be unique" goes.
   - The `existing` option (journey.ts:76): the purpose clause goes.
   - `toArrivalStatus` (journey.ts:206): the clause explaining that potatoes skip the question goes. What stays is the landing page and the precondition: not for potatoes, use `toArrivalDetails`.

   The other kept comments were read against this test and already state only a contract:
   - `startNotification` (92): side effect, landing page, return.
   - `toOverview` (102): landing page and side effect (Cancel saves nothing).
   - `chooseCommodityType` (108), `addCommodityLine` (121), `toArrivalDetails` (213), `answerArrivalStatus` (220), `deleteFromDashboard` (297): landing page.
   - `toOrigin` (137): landing page and precondition (the opening run is still open).
   - `toDestinationOfNewNotification` (166): landing page and the parameter defaults.
   - `toConsignorOfNewNotification` (187): side effect and landing page.
   - `completeNotification` (237–241): landing page and side effects, including which records it picks per commodity type.
   - The `countryCode` option (71): parameter meaning.

   The remaining words are the original text with clauses removed, not new wording.
6. **The `row()` doc comment on the notification-view page (line 30) stays.** It states the exact-key matching contract a caller relies on.
7. **Module-scope literals in `journey.ts` that only one function uses move into that function.** The house rules require it in a file this row edits.
   - `TYPE_AHEAD_FIELD` → `fillCommodityLine`
   - `ALREADY_ARRIVED` → `completeNotification`
   - `NOT_YET_ARRIVED` → `toDestinationOfNewNotification`
   - The default-line table and the coniferous-tree values that only it uses → `toOriginOfNewNotification`, the one method that reads them.

   No caller's signature changes.

   Rejected: exporting the arrival labels for the specs that retype them. That adds call sites in four other specs, which is wider clean-up, so it is a follow-up in section 7.
8. **The `startNotification` doc comment stays as it is.** It does not mention that the method records the reference on the journey context, but nothing it says is false. Renaming the method would touch every plants spec, so that is out of this row's footprint.
9. **`flows/plants/notification-actions.ts` is left alone.** Its doc comment is rationale, but the row names only `journey.ts` among the flows. It goes in as a follow-up.
