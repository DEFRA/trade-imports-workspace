## 0. Decisions

1. **The first acceptance criterion does not hold as written, and the plan follows the ruling it cites instead.** The criterion says that with nothing chosen, Save and return to overview "shows the same error as Save and continue". Save and continue shows no error on these pages when nothing is chosen. Both buttons post to one handler (`address-book-picker/picker-routes.js:118-138`, `saveSelection`), and it never checks which button was pressed. With nothing chosen it moves on and saves nothing (`:131-133`). For an id that is not in the book it refuses with the page's error (`:134-135`). Three specs say a picker with nothing chosen MUST NOT be refused: `plants/addresses` REQ-PLANTS-ADDR-005, `plants/journey-pages/consignor-select` REQ-PLANTS-CONSIGNOR-004 and `plants/journey-pages/place-of-destination` REQ-PLANTS-PLACE-OF-DESTINATION-005. The animals twin says the same (`live-animals/addresses` "Saving a role's address with nothing chosen is not refused…").
   The 26 October ruling (`sources/ruling-sam-2026-10-26.md` claim 1) asks only that both buttons make **the same checks**. Here they already do. These pages make one check, an address not in the book, and both buttons apply it. Nothing chosen is accepted on both.
   - **Settled:** no production change. The plan proves that both buttons make the same checks: a refused address on Save and return gives the same error, stays on the page and keeps the search. Nothing chosen on Save and return moves on, as Save and continue does. The spec is reworded to say both buttons make one check.
   - **Rejected:** making "nothing chosen" an error on both buttons. That changes what Save and continue does, which the ruling never asked for. It also contradicts three plants requirements and the animals twin (the programme invariant: plants mirrors animals' behaviour). It would be a product decision this follow-up row has no source for.
   - Flag for the orchestrator: the row's first criterion should read "an address not in the book" where it says "nothing". Its intent, "the same checks as Save and continue", is met.
2. **The existing "Save and return with nothing chosen reaches Overview without an error" scenarios stay** (SCN-PLANTS-CONSIGNOR-004-D, SCN-PLANTS-PLACE-OF-DESTINATION-005-C). They are true under the ruling, because Save and continue does the same thing. The requirement text above them is changed to say that the outcome is the same on every save control. That makes the sameness the stated rule, not a coincidence.
3. **Proof goes through the shared picker suites, not per-page copies.** The consignor, place of destination and consignment contact pickers all register `describeAddressBookPickerController` (unit) and `describeAddressPicker` (FIT). The new and strengthened tests go there once and run for all three pages. Contact gains the proof too. That is the shared helper's own reach, not wider scope.
4. **The FIT refusal helper learns which save control to press.** `postUnknownAddressId` (`fit/high-risk-plants-journey.js:841-853`) always clicks Save and continue. The Save and return refusal test needs the same post through Save and return to overview. Extend this one helper, and its exported wrapper `postAnIdNotInTheBook`, with an options object that names the control. No positional boolean. The default stays Save and continue so existing callers are unchanged. No second helper beside it.
5. **The end-to-end proof posts a real refused id through the real stack, once through each button, under the same conditions.** A refusal re-renders the picker with nothing ticked (`picker-routes.js:53-55` passes `selectedId: ''`) and re-reads the rows from the live book, which no longer lists the deleted record. So pressing Save and continue straight after a refused Save and return posts nothing chosen, moves on with no error (`picker-routes.js:131-133`), and proves nothing about the comparison. Each button therefore gets its own pass, and each pass sets up the same conditions afresh: make a new record, search for it, tick it, delete it through `addressBookApi`, then press the button. Pass one presses Save and return to overview; pass two, on the same picker after the first refusal, makes a second record and presses Save and continue. Both passes assert the same URL, the same exact error and the kept search term. The live address book refuses each save (`save-selection.js:49-56`), so this proves the check against the real backend for both controls. It is one test, looped over both pickers, in `tests/plants/e2e/features/address-book/addresses-picker.spec.ts`. That spec already owns cross-picker address-book behaviour and runs under the plants frontend's PR scope (`tests/plants/`). Looping avoids two copies of one body.
   - **Rejected:** pressing Save and continue on the re-rendered page after the Save and return refusal. Nothing is ticked there, so it would go red on "the same error".
   - **Rejected:** ticking two records and deleting both before the first press. The re-render after the first refusal unticks the second, so it fails the same way.
   - **Rejected:** one test in each of `parties.spec.ts` and `destination.spec.ts`, which duplicates the set-up.
6. **The amend-time "Save and return" (to the review) is not separately proved.** It posts to the same handler, so it gets the same checks, and the ruling names Save and return to overview.
7. **The two comments in `addresses-picker.spec.ts` are deleted.** Both explain what the application does and why (rationale and UI narration), which the house rules keep out of code. The existing test's title already states what its two halves prove, so it reads clearly without them. Not reworded: a comment that breaks the rule is deleted.
