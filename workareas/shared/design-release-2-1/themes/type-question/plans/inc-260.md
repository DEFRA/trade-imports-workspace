## 0. Decisions

1. **Browser links, animals → INS (checked in code).** The animals frontend sends the browser to the INS frontend in three places, all through its one helper that builds an INS frontend URL from `tradeImportsInsFrontend.baseUrl` (`TRADE_IMPORTS_INS_FRONTEND_URL`):
   - the service navigation's Address book item → INS `/address-book` (`src/config/nunjucks/context/context.js:49`, rendered in `src/server/app/shared/layout.njk:37-40`);
   - the address handshake → INS `/address-book/add` with `journey-type`, `notification-id`, `fulfilment-id` and `handshake-token` (`sets/live-animals/journeys/linear/features/addresses/ins-handshake.js:80-97`);
   - the live animals origin page's Back link, when the opening run began at the start entry → INS `/notification-type` with `notification-id` and `current-notification-type` (`sets/live-animals/journeys/linear/flow/entry-guard.js:53-64`).
   The animals frontend's Dashboard item and service name stay inside the animals frontend (its own set dashboard). Not a link to the INS.
2. **Browser links, INS → animals (checked in code).** The INS frontend sends the browser to the animals frontend from:
   - the type question: Live animals → `/live-animals/start`, Germinal products → `/germinal-products/start` (`features/notification-type/destinations.js:13-59`);
   - the type question with Live animals kept → that notification's `/live-animals/notifications/{reference}/origin` (`destinations.js:79-84`);
   - the dashboard rows → `/live-animals/notifications/{reference}`, or `…/notification-view` when SUBMITTED (`features/dashboard/view-model/list.js:40-49`);
   - the address handshake return → `/live-animals/notifications/{notification-id}/address-return` (`features/address-book/journey-registry.js`);
   - an address-book page's honoured `return` query, which may name an animals frontend URL on the configured animals origin (`features/address-book/return-to.js:29-71`).
3. **Where the animals doc lists them.** `docs/repos/trade-imports-animals-frontend.md` has no Integrations table, only "Infrastructure dependencies". Settled: add a section for the browser links with the INS frontend (both directions), shaped like the Integrations table in `docs/repos/trade-imports-ins-frontend.md:29-42` (Direction, System, Mechanism, Purpose). Rejected: a full Integrations table for every system the animals frontend calls, which widens the row beyond browser links.
4. **The INS doc's outbound animals row (line 37)** lists the type question's starts and return, "resume or view a notification" and the handshake return. It misses the honoured `return` query. Add it there, and add the inbound origin-page Back link and the service-navigation Address book link if they are not already named (line 41-42 name the handshake and the Back link; the Address book item from the animals service navigation is missing). Settled: one inbound row per animals → INS link, matching decision 1.
5. **Claim checked: "openspec ins/notification-dashboard's Purpose still says '(today: live-animals)'".** True (`openspec/specs/ins/notification-dashboard/spec.md:5`). Against the sources: ins-backend consumes one SQS queue (`NotificationSqsListener.java:34`), fed by the animals backend's outbox SNS topic (`docker/stack/backend.compose.yml:160`, `trade-imports-animals-backend/compose/start-floci.sh:41`). The plants backend publishes nothing (no SNS, SQS or outbox code in `src/main`). The animals frontend has no germinal products set on this branch (`src/server/app/sets/` holds `live-animals` only). So the dashboard lists live animals notifications only. Settled: the Purpose states plainly that the dashboard lists live animals notifications today, and that high-risk plants and germinal products notifications are not listed. Rejected: leaving the parenthesis, which reads as a note, not a statement.
6. **The ins/service-navigation capability.** New capability with area code `INS-NAV` (no collision: `grep -rn "INS-NAV" openspec` finds nothing). Its subject is the INS frontend's navigation as `src/server/app/shared/layout.njk:28-58` and `src/config/nunjucks/context/context.js:24-32` with `src/server/app/shared/paths.js:12-15` build it:
   - signed in, four items in this order: Dashboard, Address book, Manage account, Log out;
   - Dashboard is current on the dashboard and on the type question;
   - Address book is current on the address book and on every page under it (add, view, edit, delete);
   - no item is current on any other page, such as an error page; Manage account and Log out are never current.
   Structure follows `openspec/specs/live-animals/service-navigation/spec.md`.
7. **The moved scenario gets a new ID.** The type question's Dashboard-current scenario (notification-type REQ-001's fifth scenario) moves to ins/service-navigation under the current-item requirement, with its name kept verbatim and its two coverage links moved with it. Its ID changes to that requirement's own sequence, because an ID's area is the capability's. The scenarios after it in notification-type keep their IDs (stable IDs; a gap in letters is allowed — the stable-ID rule numbers in file order and never renumbers).
8. **No signed-out scenario.** The layout renders no items for a signed-out user, but the only page a signed-out user sees in this layout outside production is the stub sign-in page; every routed page needs sign-in. Settled: no scenario for it (config.yaml: "No scenario for a state the service cannot reach yet"). Rejected: a scenario backed only by the layout unit test.
9. **What the Address book item opens stays in `ins/address-book`.** `SCN-INS-ADDR-012-C` already says following the navigation's Address book link opens the list. Settled: the new Purpose cross-references `ins/address-book` for it and `ins/authentication` for sign-out, rather than restating either (one subject, one capability).
10. **Coverage links are to existing tests only.** The row changes no repo, so no test is added. Every link is `partial` (none has been seen failing by an invert probe here). Scenarios a unit test alone proves say so in notes.
11. **INS doc line 24 is wrong in two ways, and both are fixed.** It says dashboard links go to `/notifications/{reference}`; the code builds `/live-animals/notifications/{reference}`. It then says "Only one journey is supported; how other journeys will be told apart is Unclear from code." Once this row lands, that sentence is vague and conflicts with decision 5's new dashboard Purpose, and the type question already hands users to three journeys (live animals and germinal products on the animals frontend, high-risk plants on the plants frontend). Settled: correct the path, and replace the sentence with the fact decision 5 records: the dashboard rows link to live animals notifications only, because the ins-backend read model aggregates only the animals backend's events. Rejected: keeping the sentence (it contradicts the spec), and deleting it without a replacement (it leaves the "Does not own" line silent on which notifications the dashboard links to).
