h3. Background

The place-of-landing and country lists a trader picks from on a high-risk plants notification now show exactly what master reference data (MDM) really serves, through the reference data service, rather than a hand-kept list held in the code.

Three things follow. The country list on the origin page now holds territories as well as countries, each named with its parent country, so a consignment from the Canary Islands can say so rather than only "Spain" — and a territory is accepted or refused on the same basis its country would be. Places of landing are grouped by what they are — airports, then seaports, then rail — rather than mixed together in one alphabetical run, and each reads its name with its code. And both the review page and the dashboard card read those answers back in the same words the trader chose.

No list entry is added, removed or respelt by hand. Whatever MDM serves is what a trader sees, so a change in MDM reaches the service without a code change.

This ticket covers the *high-risk plants journey only*. The same increments changed the live animals journey and the Import notification service address book, each of which has its own ticket under the same epic. *This work is merged to {{main}}.*

h3. What changes for the user

h4. The country of origin can be a territory

The list holds every country and territory the reference data service serves for the SPS origin block, in alphabetical order of the name shown. A territory reads with its country in brackets — "Canary Islands (Spain)".

h4. A territory is allowed where its country is

Choosing the Canary Islands for a ware-potato consignment is accepted, because Spain is one of the countries that needs notifying. Choosing Martinique is refused, because France is not — and the refusal names the four ware-potato countries, so the trader knows what is allowed.

h4. Places of landing are grouped by type, and read with their code

The list runs airports first, then seaports, then rail ports, each group A to Z by name ignoring capitals. A port whose type the reference data service does not know comes after every rail port rather than being dropped. Each reads "<port name> - <port code>".

h4. The review and the dashboard read the answers back the same way

The place-of-landing row on check your answers reads the same text as the option the trader chose. The country of origin reads "Canary Islands (Spain)" on both check your answers and the notification's card on the dashboard.

h3. Acceptance criteria

Copied from the service's behaviour specification. All 9 scenarios for the plants journey are listed in full.

h4. The country of origin list

h5. The country list holds the reference data service's SPS origin countries and their territories, by name

* *GIVEN* the user is on the origin of the import page
* *WHEN* the country list is read in full
* *THEN* besides the placeholder it holds exactly the countries and territories the reference data service serves for the SPS origin block, by their served names, in alphabetical order

h5. A territory is accepted where its country is allowed

* *GIVEN* a notification carries a ware-potato commodity line
* *WHEN* the user chooses the Canary Islands, a territory of Spain
* *THEN* the country is accepted and saved

h5. A territory is refused where its country is not allowed

* *GIVEN* a notification carries a ware-potato commodity line
* *WHEN* the user chooses Martinique, a territory of France
* *THEN* the country is rejected, naming the four ware-potato countries as the ones that need notifying

h4. The place of landing list

h5. Places of landing are listed airports first, then seaports, then rail ports, each A to Z by name

* *GIVEN* a potatoes notification is on the arrival details page
* *WHEN* the place-of-landing list is read in full
* *THEN* every airport comes before every seaport, and every seaport before every rail port
* *AND* a port whose type the reference data service does not know comes after every rail port
* *AND* within each group the ports run A to Z by name ignoring letter case, with non-breaking and doubled spaces read as single spaces

h5. Every port the reference data service serves is offered as a place of landing, in its order

* *GIVEN* a potatoes notification is on the arrival details page
* *WHEN* the place-of-landing list is read in full
* *THEN* it holds every port the reference data service serves, in the order the service serves them
* *AND* each reads "<port name> - <port code>", for example "Port of Dover - GB DVR"

h5. A potatoes notification chooses its place of landing from an ordinary list

* *GIVEN* a potatoes notification is on the arrival details without JavaScript
* *WHEN* they choose a port from the ordinary list, complete the page and save it
* *THEN* the list is labelled as the place of landing question and each port reads "<port name> - <port code>"
* *AND* returning to the page still holds that port's code

h4. Reading the answers back

h5. The place of landing row reads the option the user chose

* *GIVEN* a potatoes notification with a proposed place of landing
* *WHEN* the user views check-your-answers
* *THEN* the place of landing row reads the same "<port name> - <port code>" text as the option they chose

h5. A territory of origin is named with its country

* *GIVEN* a notification whose country of origin is the Canary Islands
* *WHEN* the user views check-your-answers
* *THEN* the country of origin row reads "Canary Islands (Spain)"

h5. A territory of origin is named with its country on the card

* *GIVEN* a notification whose country of origin is the Canary Islands
* *WHEN* the user views its card on the dashboard
* *THEN* its origin reads "Canary Islands (Spain)"
