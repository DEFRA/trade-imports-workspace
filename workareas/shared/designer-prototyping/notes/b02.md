## b75ce0a — "add address" (10:38) — LARGE

### What changed

New **Address book** capability, reachable from the service navigation and from
the consignment "select an address" pages.

**New views**
- `app/views/address-book.html` — Address book landing page. Notification banner
  for a success message, "Add a new address" button, a GET filter form (search

### Designer intent

Make "Add a new address" real end-to-end: from a consignment party page the user
can add an address, land back on the same page with a success banner and the new
address pre-selected; from the nav they can browse/filter a full address book.
The 500-record lookup and the 24-row padded table exist to make search and
pagination feel realistic in usability testing.

### Kit mechanics

Nunjucks views extending `layouts/main.html`; partial include for the manual
fields; govuk-frontend macros (table, pagination, select, notification-banner,
error-summary, button, input, back-link, phase-banner); `req.session.data` as the
only store, including hand-rolled flash messages (set then delete on next
render) and a "return to" marker; static JS data modules under `app/data/`; JSON
embedded in `<script type="application/json">` for progressive-enhancement JS;
custom vanilla JS modules registered through `window.GOVUKPrototypeKit.documentReady`
and `data-module` attributes; large custom SCSS with hard-coded values.

  - `addAddressHref` on consignment pages becomes `/address-book/add?from=...`.
  - `GET /address-book/add` — with `?from=` still redirects straight to lookup
    (type is inferred); without it, clears all `addressBook*` working state and

  - `POST /address-book/add` — validates the radio, re-renders with errors or
    stores `addressBookAddressType` and redirects to lookup.
  - New guard `redirectIfNoAddressBookAddressType` on both GET and POST of

  - `getAddressBookBackLink` returns `/address-book/add` when a type is held.
  - Error summary href changed `#address-book-type` -> `#address-type-importer`

### Designer intent

one-thing-per-page — and stop the lookup page being reachable without a type.
Labelled "fixed bugs" but it is a flow redesign.

### Kit mechanics

only store; hand-written govuk-radios markup to accommodate a divider.

## Cross-commit patterns

1. **Big drop, then same-day fix-ups.** Both features arrive as one large commit
   (2.6k and 0.8k lines) and are followed within minutes to two hours by smaller
   correcting commits (4d5b03e restructures the add flow; a79a15f and ce44397
   tune data and copy). Commit messages are terse and sometimes misleading
   ("fixed address bugs" is a flow redesign; "new dashboard" is a data swap).

2. **routes.js is the application.** Every feature adds view-model builders,
   validation, session mutation and routes to one file. Helper families are
   duplicated per feature with a renamed prefix (`buildAddressBookPagination` ->
   `buildDashboardPagination`, `...PageHref`, `...ResultsText`). The file grew
   710 lines in one day and is 13k lines today.

3. **Session is the database.** Added addresses, "return to" markers, chosen
   type, working form values and one-shot success messages all live in
   `req.session.data` under feature-prefixed keys (`addressBook*`,
   `consignmentAdded*`). Flash messages are done by read-then-delete on render.
   Working state is reset explicitly at entry points (`GET /address-book/add`).

4. **Static data modules with padding/generation for realism.** New
   `app/data/*.js` files per feature; two of them exist purely to make lists look
   full (24 padded address rows, ~500 generated lookup addresses, 32
   notifications). The designer first generates, then replaces with curated
   records when the fake pattern shows (a79a15f).

5. **Progressive-enhancement pattern via embedded JSON.** Server renders the full
   page; the same data is embedded as `<script type="application/json">` and
   custom vanilla JS filters/autocompletes client-side. Both new JS modules
   follow the same skeleton (`getXFromRoot` parse, `data-module` attribute,
   `GOVUKPrototypeKit.documentReady`). The lookup reuses the existing
   `app-commodity-search*` classes and markup from the commodity search.

6. **Custom SCSS over govuk-frontend tokens.** ~1k lines of BEM `.app-*` styles
   in one `application.scss`, hard-coded px/hex (GOV.UK palette values typed in
   by hand), no `govuk-spacing()`, `govuk-colour()`, `govuk-font()` or
   `govuk-media-query()`. Styles for a view were sometimes committed before the
   view (add-page styles in b75ce0a, view in 4d5b03e).

7. **Figma to code.** Dashboard icons are raw Figma SVG exports (Iconsans ids,
   `var(--fill-0, ...)`), sized to 35x35 to match the design; pixel dimensions
   (300px cards, 75px panels) suggest measuring the Figma frame.

8. **Placeholders left in.** "Hint text" hints, `href="#"` on View / Copy as new
   / alert card links, empty `<details>` filter shells, sort captured but never
   applied. The page needs to look complete for research, not behave completely.

9. **Navigation and home page reshuffled by editing the layout.** Service
   navigation items in `layouts/main.html` are edited directly, with an
   `active` flag driven by a `serviceNavActive` local set in each render helper.
   The root route moved from notification hub to dashboard within the day.

10. **No version folders in this batch.** All work is in-place on the single set
    of views under `app/views/`; no `design-release-*` or `testing` copies exist
    yet at 9aabc14 (see ls-tree). That mechanism, if it appears, comes later.

11. **Code style suggests AI-assisted authoring.** Consistent JSDoc-free but
    heavily factored helpers, `escapeHtml`, aria-live announcements, optional
    chaining, deterministic generators with `pick(items, index)` — far more
    engineering than a typical Prototype Kit designer commit, arriving in one
    2.6k-line drop. Worth cross-checking against other batches.

## Implications for designer skills on the plants prototype

- Designers expect to add a whole feature (view + data + routes + styles + JS)
  in one sitting and then iterate copy/data in tiny commits. A skill should
  support "add a page with realistic seeded data" and "tweak copy on page X"
  as separate, cheap operations.
- Realistic seed data matters a lot to them (three data files in one day, one
  rewritten by hand for believability). A stub-backed prototype should make
  "give me 30 believable notifications / 500 addresses" a one-line ask.
- Flash messages, return-to-origin flows and pre-selecting a just-created
  record are recurring interaction patterns they build by hand in session;
  the real frontend should expose these as recipes.
- They want the nav and home page to be editable in one place.
- They are comfortable with hand-written SCSS but not with govuk-frontend Sass
  tokens; a skill should nudge toward `govuk-*` utility classes and mixins.
