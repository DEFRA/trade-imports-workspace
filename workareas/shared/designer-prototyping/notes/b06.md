## Cross-commit patterns

1. **Copy a whole view folder to make a version, then diverge.** `design-release-2/` is a byte-level copy of the root views with `/design-release-2` prefixes hand-inserted into literal hrefs/actions, exactly as `testing/` was made earlier. The commit then immediately diverges the dashboard and review page while the other 20+ journey pages stay identical clones. This is the primary versioning mechanism of the prototype and it is now formalised in `lib/version-mount.js`, so a third release would be one 50-line config file + one `cp -r`.
2. **Same-afternoon iteration bursts.** 17 July: two rewrites of the same `testing/dashboard.html` 47 minutes apart (filter panel → IPAFFS full-width search). 22 July: DR2 landed at 10:44, copy pass at 14:50, templates page + more copy at 15:38, one-word fix at 15:45. Commit messages are terse ("text", "fixes") and do not describe scope — `25bcf8a` "text" adds a page and two routes.
3. **Placeholder-first, content-second.** New pages ship with scaffold copy ("Brief service description", "Description of what the user needs to do", `#` hrefs, "Error message"), then a follow-up commit hours later writes the real content. Many `#` links (Clone a certificate, Amend, Show notification, date presets, Copy as new, Delete) remain.
4. **Demo state is manufactured by index arithmetic in routes.js**, not by data files: `index % 6`, `Set([2,8,14,20])`, cycled name arrays, literal counts `(1)`/`(0)` baked into filter labels. The dashboard therefore looks populated without any real filtering/sorting working (search/sort/filter forms submit but are largely ignored).
5. **Session data seeded from snapshot builders** so a static dashboard row opens a fully populated review page (`dashboard-notification-snapshots.js` reuses `consignment-addresses`, `contact-addresses`, `transporters`). "Draft" rows load the snapshot *into* the live session so Change links then work end-to-end.
6. **Shared layout forks by `res.locals` flags** (`isTestingVersion`, `isDesignRelease2Version`) with the nav array duplicated three times rather than parameterised; the version mount's `setupLocals` is where version-specific hrefs are injected.
7. **One monolithic `application.scss`** (7.6k+ lines by the end of this batch) with BEM-ish `app-dr2-*` / `app-dashboard-*--testing` blocks and hard-coded pixel typography/colours, including a bespoke `.app-ipaffs-tag` that deliberately steps outside govuk-frontend to mimic the incumbent IPAFFS UI.
8. **Two audiences, two dashboards.** `testing/` is turned into an IPAFFS look-alike (comparison baseline for research); `design-release-2/` is the forward-looking task-led design. Both are reached from a version-picker `index.html` whose card copy was only written in this batch.
9. **Routes are added as GET/POST pairs guarded by a version check** (`if (!isDesignRelease2SessionData(...)) return res.redirect('/')`), and POST handlers store a single trimmed field then redirect — the standard Kit idiom, but done by hand per route rather than via the Kit's auto-store-data.
10. **The designer merges the developer's Playwright PR and never touches it** — the `journey-demo/` pipeline from 15–16 July is orthogonal to the design iteration flow.

## Implications for designer-facing skills on the plants prototype

- A "new design release" skill should do what `createVersionMount` + folder copy does today but in the real frontend's terms (feature flag / route prefix / template variant), because designers clearly want to keep the last release stable while iterating on the next.
- Designers iterate **dashboard/list pages and review/summary pages** most heavily; journey step pages are cloned untouched. Skills for "add a dashboard card/filter/status" and "change the review page layout" would map directly onto this batch.
- Realistic seeded records (multiple statuses, one that opens as a fully populated detail page) are essential — the equivalent of `dashboard-notification-snapshots.js`; the stub services should provide these rather than index arithmetic.
- Copy passes are frequent, small and same-day; a "content update" skill that edits Nunjucks strings and re-runs Playwright screenshots would cover ~half the commits here.
- Commit messages carry no information; any analysis workflow must diff, not read messages.
