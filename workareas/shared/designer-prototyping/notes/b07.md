## Cross-commit patterns

1. **Big drop, then a quick fix-up.** Both sessions are a multi-thousand-line commit followed 9–18 minutes later by a small correction (`6f6a308` landing-page href; `7da4f70` dashboard reshape). The designer works locally for days, commits once, deploys to Heroku, clicks through, then patches what looks wrong. There is no branch/PR flow — everything is on main.
2. **Commit subjects name one feature; the diff contains five.** "new address book, templates and amend" also carries the dashboard filter panel, the status vocabulary change, the journey-form-actions refactor and the NI lookup. "germinals" also carries delete, drafts, re-submit, and the import-reference block. Any tooling that mines history must read the diff, not the message.
3. **Versioning by copying the view folder.** `design-release-2.1` is a byte-for-byte copy of `design-release-2` with the path prefix replaced (confirmed by rename/copy detection), plus a 52-line `*-version.js` mount file that is itself a copy. Then divergence starts immediately in the copy (6 of 31 pages differ on day one) and the copy's dashboard is re-designed 18 minutes later. The `version-mount.js` library (router-stack cloning, session nesting, `res.render` view-folder fallback, redirect prefixing) is what makes this cheap — and it is the single most reusable idea in the repo for a "designer sandbox" workflow.
4. **Routes.js is a single 10k-line file and grows by ~1k lines per feature commit.** Version-specific behaviour is expressed as `if (isDesignRelease2SessionData(sessionData))` / `res.locals.isDesignRelease21Version` branches inside shared handlers rather than separate route files; the same handler serves `/`, `/testing/...`, `/design-release-2/...`, `/design-release-2.1/...`.
5. **Shared templates fork inline.** `address-book.html`, `notification-status.html`, `transporter-add-commercial-fields.html` keep the old markup in an `{% else %}` and add the new markup under `{% if isDesignRelease2Version %}`. So there are two axes of duplication: folder copies for journey pages, inline conditionals for shared pages.
6. **Data-file-driven enumerations.** Every new list (categories, uses, package types, germinal commodities, templates, NI addresses) lands as `module.exports = [...]` under `app/data/` and is required at the top of routes.js. Seed data is rewritten to tell the story the next review needs (7da4f70 throws away 30 rows for 8 curated ones).
7. **Session as state machine.** Multi-step flows are stitched with ad-hoc session flags (`addressBookAddressCategory`, `addressBookPendingManualAddress`, `addressBookHideSearch`, `addressBookAddingTransporter`, `notificationStatus` = Draft/New/Amend, `amendingFrom`, `amendOriginalSnapshot`, `draftNotifications`, `deletedNotificationReferences`). Each new flow adds 3–6 keys and a matching block of `= null` resets in every cancel/entry handler.
8. **Refactor when a third variant appears.** The 14× copy-pasted button block was only extracted into `journey-form-actions.html` when amend mode needed a different button set; `buildSpeciesConsignmentEntry` was only extracted when germinals needed extra fields. Extraction is reactive, not planned.
9. **Progressive adoption of richer components.** First MOJ date picker (dashboard filters, 23 Jul), then reused for the germinal "Collection date" identifier (4 Aug). Custom vanilla-JS modules are added one per behaviour (`amend-notification-modal.js`, `auto-dismiss-notification-banner.js`, `copy-text-button.js`) and registered in `application.js`; all are `data-*` attribute driven and framework-free.
10. **GOV.UK components are frequently re-implemented rather than used.** Tabs rendered as `govuk-tabs` markup around plain links with ~75 lines of custom SCSS (twice: address book and dashboard); a hand-rolled modal dialog; hand-rolled checkboxes on the usage page; `<details>` + SVG chevron image for collapsible filters. `application.scss` reaches ~8,200 lines with hard-coded GDS colours/font sizes in every block.
11. **Filters are presentational first.** The dashboard's date range / type / status filters (dc8dcc6) read and echo query params but don't filter; tabs (7da4f70) do filter. The designer ships the UI before the behaviour and adds behaviour when a session needs it.
12. **Sentence-case and copy polish rides along.** Button labels lengthened ("Create new" → "Create new notification"), labels de-capitalised ("Place of Origin" → "Place of origin"), status renamed ("Submission complete" → "Submitted"/"Completed") — all inside feature commits, never separately.

## Implications for a plants-prototype designer workflow (from this batch)

- Designers want a **cheap "fork this version" move** (copy folder + register base path + fresh session namespace + shared address book) — the plants prototype needs an equivalent that doesn't require duplicating a 10k-line routes file.
- They want to **rewrite seed data quickly** to stage a review scenario (8 curated dashboard rows with explicit labels and statuses).
- They lean on **query-string-driven view models** (`?tab=`, `?category=`, `?sort=`) and **session flags** to prototype multi-step flows; a skill should make "add a flag + reset it in cancel paths" mechanical.
- They reach for **MOJ frontend** and **hand-rolled JS/SCSS** when the GOV.UK toolbox lacks a pattern (modal, tabs-as-links, auto-dismiss banner, copy button) — the plants workflow should offer sanctioned equivalents or make the "govuk toolbox only" rule visible before they build.
- Commit hygiene is absent (one commit per multi-day session, one-word subjects) — any history-mining tool must be diff-driven, and a designer workflow could offer "commit per feature" scaffolding without imposing PRs.
