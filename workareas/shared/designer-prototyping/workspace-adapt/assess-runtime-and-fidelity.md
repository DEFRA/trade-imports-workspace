# Assessment: runtime and fidelity

Lens: the prototype stands up without the docker stack and deploys to dev (CDP) from its own Dockerfile. The workspace is where it gets built, so that it follows the real service. All paths below are relative to `~/git/defra/trade-imports-workspace` unless stated. `P/` means `repos/trade-imports-plants-prototype/` and `PF/` means `repos/trade-imports-plants-frontend/`.

## 1. The deployed image

### What the image does today (verified)

- `P/Dockerfile` differs from plants-frontend's only in `ARG PORT=3103` (checked with `git diff upstream/main -- Dockerfile`). The `production` stage copies only `package*.json`, `src/` and `.public/`, then runs `npm ci --omit=dev` and `node src`.
- **No designer tooling reaches the runtime image.** `scripts/designer/**`, `scripts/new-set/**`, `.claude/**`, `docs/designers/**`, `handoffs/**`, `.cache/**`, `fit/**` and `test/**` are not copied into the `production` stage. Nothing under `src/` imports `scripts/`: I grepped for it, and the only hits are in tests and in comments in `prototype-sets/releases.js` and `sets-index/controller.js`.
- **Every runtime feature lives in `src/`, so it ships.** The chooser (`src/server/sets-index`), the prototype sets (`src/server/prototype-sets/index.js`) and the seeder (`src/server/prototype-seed`) all ship. The seeder reads each set's `journeys/linear/flow/fixtures/happy-path.json` and `prototype-seed/fixtures|scenarios`, which are all under `src/`. So do the example data overlay (`src/server/prototype-data`), the stand-in services (`src/server/app/services/{transporters,templates,ins-address-book,notification-search}`) and every design release mounted by `new:set` into `prototype-sets/index.js`. The image also carries the seed CLI (`prototype-seed/cli`) and `*.test.js` files. They do no harm, but they are dead weight.
- **Stub data in production** comes from the patched `P/src/server/common/services/mode.js`: `isStubDataMode() = stubMode || isProduction`. **Sign-in in production** still uses `isStubMode()`, which is off in production, so it is Defra ID. `P/src/server/prototype-sets/production-run.test.js` proves both. I ran it: 7 of 7 pass (`npm --prefix … run test -- src/server/prototype-sets/production-run.test.js --coverage.enabled=false`).
- `P/src/prototype-defaults.js` sets `SESSION_CACHE_ENGINE=memory` (no Redis) and `STUB_MODE=true` when they are unset. `src/index.js` imports it first, so `node src` picks it up.
- **Persisted records do not leak into production.** `P/src/server/prototype-support/persist.js` line 35 turns persistence on only when `NODE_ENV=development`. The image runs as production, where records live in memory only.
- **Research mode** is a committed code change inside a release (`scripts/designer/research/research-mode.js`: one commit that relaxes `controller.js`/`obligations/*.js` rules, plus `research-mode.md`). A research release merged to `main` therefore deploys with relaxed rules and a "Research mode on" tag on the chooser. That is by design, not a leak, but designers need telling that "turn research mode off" must also be merged to leave dev.
- **CI builds the image but never boots it.** `P/.github/workflows/check-pull-request.yml` lines 48-52 run `docker build` only. `publish.yml` builds through `cdp-build-action`.

### Gaps and risks

1. **The deployed prototype needs a reachable Defra ID stub at boot.** `src/plugins/auth.js` fetches the OIDC configuration at registration (`get-oidc-config-with-retry.js`). `docs/repos/trade-imports-defra-id-stub.md` says neither the official stub nor CDP's supports the `signupsigninsfi` policy, so dev must point at a deployed `trade-imports-defra-id-stub`. It also needs `DEFRA_ID_REDIRECT_URL` and `DEFRA_ID_SIGN_OUT_REDIRECT_URL` set to the prototype's dev host. That is cdp-app-config, which is Sam's (draft locally, never commit). Also, `P/src/config/config.js` lines 227 and 233 still default the redirects to `localhost:3003`, the real twin's port. So `npm start` or `docker run` of the production image on a laptop, against the local stub, sends sign-in back to plants-frontend's port. The patched `config.js` should default them to `3103`, the same as its port line.
2. **Single instance only.** The records store, the stand-in services' fake stores and the session cache (`memory`) are all per process. With two or more CDP instances, dashboards differ between requests and sign-ins drop. The CDP service config must pin one instance, or set `SESSION_CACHE_ENGINE=redis` for sessions (records would still be per instance). Add this to the README's "For maintainers" and to the cdp-app-config draft.
3. **Every deploy wipes shared data, and anyone can wipe it.** Records live in memory, and every merge to `main` redeploys. The chooser's `/reset/{setId}` resets a set for everyone (`prototype-seed/index.js` `resetSet`). This matters for research on dev: freeze merges during a session, and say so in `research-session`.
3a. **The port.** Confirm in the CDP portal that the service is registered on 3103. The image exposes 3103, and plants-frontend uses 3003.
4. **No boot test of the built image.** Add a job to `check-pull-request.yml` (ours) that:
   - runs `defradigital/trade-imports-defra-id-stub` beside the built image, with `NODE_ENV=production` and the `DEFRA_ID_*` values from `P/README.md` lines 182-186
   - then checks `/health`, checks that `/` redirects to sign-in, and completes a stub sign-in to the chooser, one release and one example link.

   That proves "stub data, sign-in through the Defra ID stub, every set and the chooser, releases included". Today only unit tests prove it. Extend `production-run.test.js` too: it covers `high-risk-plants` only, not the chooser, `sample-journey`, a scaffolded release or a stand-in service. The release canary job could run it with `plants-working` mounted.
5. **`.dockerignore` lets local clutter into the build context.** The file is plants-frontend's. It excludes only `node_modules`, `Dockerfile` and `coverage`, so on a designer's laptop `.cache/designer/data`, `playwright-report`, `test-results` and `handoffs` enter the build context and the `development` stage (`COPY . .`). None of it reaches `production`. Low priority. A patched `.dockerignore` would cost a sync line, so leave it unless the development image is used.
6. **The "Address book" link in the service navigation** is `tradeImportsInsFrontend.baseUrl + /address-book` (`P/src/config/nunjucks/context/context.js` line 44). It is dead when the prototype runs on its own (`localhost:3002`). On dev it points wherever cdp-app-config says, which would be the real INS frontend with real, different data. Decide deliberately. One option: default `TRADE_IMPORTS_INS_FRONTEND_URL` in `prototype-defaults.js`, which is ours, to a prototype route that lands on a release's ins-address-book pages.
7. **Stale docs.**
   - `P/README.md` line 233 says the workspace stack runs "every trade-imports service including this one". It does not: nothing in `docker/stack` or `scripts/stack` names the prototype, and `repos.json` has `dockerStack: null`.
   - `docs/repos/trade-imports-plants-prototype.md` still says the repo "is NOT cloned" and that everything is "Unclear from code". Rewrite it from the code: port 3103, `isStubDataMode`, the chooser, `overrides.json`, the deploy requirements above, and "not in the stack, by design".

## 2. Standing up without the stack

This holds. `npm run dev` gives `NODE_ENV=development` and `STUB_MODE=true` by default, so stub sign-in and stub data, with nothing else running. `designer:show` and `designer:fresh` start their own server (`PROTOTYPE_PERSIST=false`). The prototype uses port 3103 and its own development cookie name (`config.js` patch), so it can run beside the workspace stack's plants-frontend (3003) and Defra ID stub (3007) without clashing. The suite must never tell a designer to start the stack to see a change.

Workspace hazards to guard against:

- `tim workspace branch <x>` moves every repo without branch `<x>` onto its default branch (`tim workspace branch --help`). Run by a designer's agent, it would pull the prototype off `design/*`.
- `tim workspace reset` hard-resets every repo, uncommitted designer work included.
- Designer-facing agents must never run either, and must not run `tim workspace update` while the prototype has uncommitted work. Better still, tim could skip a repo that has uncommitted changes, or one on `design/*` or `handoff/*`, unless it is named.

## 3. Fidelity: using the workspace to build like the real thing

- **The prototype's 14 skills are not discovered.** They were not in this session's skill list. `repos/` is gitignored in the workspace (`.gitignore` line 67). On the first turn a designer's "add a page" matches the workspace `CLAUDE.md` index row for `frontend-change`, which targets animals-frontend. ### Where stub data and stand-in contracts could be made truer

- **Ports and countries are already true.** `PF/src/server/app/services/ports/stub.js` re-exports `_capture/fixtures.js`, captured by `PF/src/server/app/services/_capture/capture.js` from reference-data (`/countries`, `/countries?blocks=GBNAG_SPS_EX`, `/ports-of-entry`), and the prototype inherits it through the sync. The weak spot is `P/src/server/prototype-data/` overlays, which let a designer add a port or country that reference-data does not have. `example-data` should check the captured fixture first and say plainly when a row is invented. Re-capturing is plants-frontend's job (`npm run capture:high-risk-plants` against the stack), never the prototype's.
- **The address book stub is invented on purpose.** `PF/.../address-book/stub/index.js` holds deliberately domain-neutral parties. That is fine. `ins-address-book` already copies the INS frontend client, and its `CONTRACT` (`pageSize: 25`) matches `address-book.list.page-size:25` in `OperatorService.java` line 39. `address-book-pages.md` should cite the locked OpenAPI file so the agent re-checks it rather than trusting the snapshot.
- **Transporters**: the stand-in invents `/organisation/{id}/transporters` (`P/src/server/app/services/transporters/index.js` line 28). The animals frontend already has a transporter register with a domain model: `APPROVED`, `COMMERCIAL`, `PRIVATE` and `NEW` in `records.js`, and per-organisation added transporters in `register.js`. Base a stand-in on that model and its field names, and name animals as prior art in the hand-off.
- **Notification search** (`owner: 'plants-backend'`, `/notifications`, `/notifications/counts`) is a plausible extension of plants-backend `GET /notifications` (page, sort, referenceNumber). The cross-journey dashboard read model, though, is ins-backend's `GET /notifications` (same parameter names). The `CONTRACT` should say which of the two it extends and why, with a pointer to `openspec/specs/ins/notification-dashboard`.
- **Uploads**: `PF/.../docs/services.md` says there is no upload service by decision. Animals has `document-uploads` (the cdp-uploader pattern). An upload stand-in should mirror that one, not invent a new shape.
- **Copy as new** is correctly marked "not a fake": `copy-as-new.md` cites `POST /notifications/{id}/copy`, and plants-backend has it (`NotificationController`, `@PostMapping("/{referenceNumber}/copy")`). It is a snapshot, though. Change the reference to "check the controller" so it stays true.
- Service tests: `scripts/designer/service/templates/service.test.js.tmpl` stubs `fetch` with `vi.stubGlobal`, the same network-boundary style as `PF/.../address-book/address-book.test.js` line 21. It is fine as it is.

### Tests and conventions a release does not get

`P/src/server/app/copy-parity.test.js` and `copy-convention.test.js` only walk `sets/high-risk-plants`. The suite forbids test files in a release. So a release feature has no `copy.test.js`, Playwright feature spec or axe test, all of which the real recipe requires. `prototype-checks/copy-shape` covers the shape, which is fine for a prototype. The hand-off (`prepare-handoff` workflow) must add the recipe's tests when it moves a change to plants-frontend, and the brief should say so.

## 4. Settings, permissions and how designer agents should behave

- **Which settings apply.** Claude Code reads settings and hooks only from the launch directory (`scripts/sonar/sonar-push-gate.sh` lines 5-24 say this in terms). From the workspace root, `P/.claude/settings.json`, with its stale `sonar-secrets` and `sonar-analyze.sh` hooks whose scripts `overrides.json` deletes, **never runs**. The problem only bites someone who opens Claude inside `P/`. Proposal: add `.claude/settings.json` to `deleted` and drop the `P/CLAUDE.md` "A missing hook script" section. The workspace root already runs the sonar secrets hooks. Written to `settings-proposal.md`.
- **What designers will hit** (`.claude/settings.json` plus `.claude/hooks/guard-bash.sh`):
  - **Every command in the suite assumes the prototype is the working directory.** Roughly 370 lines across `P/.claude/skills/**` and `P/AGENTS.md` say `npm run …` or `git …`. From the workspace root:
    - `npm run designer:*` fails, because the workspace has no such script, and it prompts, because it is not on the allow list.
    - Bare `git status`, `git switch -c design/…`, `git add` and `git commit` act on the **workspace** repo. A `design/*` branch would be cut in the workspace, and the prototype would stay on `main`.
    - Rewrite every command in the house form: `npm --prefix ~/git/defra/trade-imports-workspace/repos/trade-imports-plants-prototype run <script> -- …` (allowed, line 85) and `git -C ~/git/defra/trade-imports-workspace/repos/trade-imports-plants-prototype …` (allowed, line 83). Do it as a sweep of the text, not as a single translation note, so no step can be misread. `npm --prefix … run` runs scripts with the prefix as their working directory, so `designer:*` scripts that use `process.cwd()` keep working.
  - **Install**: `AGENTS.md` rule 7's `npx --yes npm@11.6.2 ci` prompts, because `npx` is not allowed. `npm --prefix <workspace path> ci` is denied by the guard's lockfile-symlink redirect (lines 167-170), which is stale because rule 1 makes the canonical path the checkout. Fix with a `tim prototype install`, or narrow the guard (Sam).
  - **Workflows**: `P/CLAUDE.md` gives `scriptPath: '.claude/workflows/design-session.js'`, which resolves against the workspace root and fails. Use `repos/trade-imports-plants-prototype/.claude/workflows/design-session.js`. The briefs inside the workflows also need the `--prefix`/`-C` form, because workflow agents' working directory resets to the workspace root.
  - **Denied outright**, where the deny text names the alternative: `node …`, `bash …`, `curl`, `chmod`, `rm -r`, literal `/Users/<user>/` paths, `&&` chains, and `npx playwright test`. The suite already uses one command per call, and `designer:*` wraps `node`. Gallery and log paths printed by `designer:*` are absolute. An agent must never paste one back into Bash: it must use Read, or turn the path into the `~/` form.
  - The sonar MCP servers report "failed to connect" in each designer session with no `SONAR_TOKEN` or Docker. Agents should ignore this and never raise it with the designer. A personal `settings.local.json` can switch them off (proposal).
- **Push gate.** `sonar-push-gate.sh` uses the Bash call's working directory, so `git -C <repo> push` from the workspace root checks the workspace repo, not `<repo>`. That is harmless for the prototype, which has no `sonar-project.properties`. For real repos pushed in the house `git -C` form, though, the gate silently checks the wrong repo. This is a workspace bug outside this lens; flagged for Sam.
- **Branch parity** (CLAUDE.md rule 2). `design/*` branches live in the prototype only, so parity does not apply to them. It starts to matter at hand-off. Once a ticket exists, the plants-frontend implementation branch must be `feat/EUDPA-XXXX-<slug>`, and so must any workspace branch that carries `openspec` changes (`spec-cover` commits in both). Recommendation: once a ticket exists, name the prototype's hand-off branch `feat/EUDPA-XXXX-<slug>` too, in place of `handoff/<slug>`. AGENTS.md already tells agents to stay on any non-`main` branch. Then `tim workspace branch EUDPA-XXXX` lines up the evidence (prototype), the build (plants-frontend) and the spec (workspace). The prototype keeps it out of `main` because `handoff/*` is never merged, and the same rule has to cover the renamed branch.
