=== inc-071 ===
The port-of-exit select is the port-of-entry list. Its captured DOM offers 80 options — a "Select port of exit" placeholder, a disabled separator and 78 ports — running from "Aberdeen Airport (GB DYC)" to the far end of the alphabet, each labelled with a UN location code, and including inland and cargo terminals such as "Nottingham Port (GB NTG)" and "HES Humber Bulk Terminal (GB HMR)". Nothing marks which of the 78 can handle animals and any of them is accepted, so a user can choose a port their consignment cannot lawfully leave from. The page says so out loud: the field's hint reads "Choose where the consignment will leave Great Britain. Exit and entry share the same port list." (src/server/app/sets/live-animals/journeys/linear/features/port-of-exit/copy/copy.en.js:5). This is a design decision rather than fixture contents. The controller builds the options by mapping the single shared ports service (src/server/app/sets/live-animals/journeys/linear/features/port-of-exit/controller.js:22-29) and validates the answer against that same list (:32-38); the service holds one list and primes it from the reference-data service's ports-of-entry endpoint (src/server/app/services/ports/client.js:4-6), and every record it returns is exactly a code and a name, with no designation to filter on (src/server/app/services/ports/index.js:9-14). There is no exit list and no filter over the entry list. The frontend's own obligation records where the decision came from: "Port selected from the port of entry list (Exit and Entry share the same list)" at src/server/app/sets/live-animals/obligations/sections/import-reason.js:81-83.

The port of exit is a short, purpose-built list of ten border control posts approved to handle animals: Edinburgh, Gatwick, Glasgow, three Heathrow posts, Holyhead, Manchester, Prestwick and Stansted, each carrying its BCP code. Design release 1 keeps it in its own file, separate from the arrival ports, and names it for what it is (app/data/exit-border-control-posts.js:1-14). Both reveals that ask for a port of exit use it — the transit reveal, where the field is named transitExitBorderControlPost, and the temporary-admission reveal, where it is named temporaryAdmissionPortOfExit — and both are fed by the same builder at app/routes.js:8763-8776, so Design release 1 uses one exit list rather than one per reason. Anything else is rejected with "Select a port of exit". The user is offered no other option. The ten are not a subset of the frontend's 78: entries such as "Heathrow Airport – Airpets Limited (animals)" have no counterpart in the ports-of-entry data at all, so this is a different list rather than a narrowing of the one Frontend already holds.

The port of exit has to become its own list of animal exit border control posts, labelled with their BCP codes, rather than a second use of the arrival ports. Frontend cannot do this alone: the ports service exposes one list and the reference-data service exposes only ports-of-entry, and the records carry a code and a name and nothing else, so there is no designation to filter on. A new endpoint and a new reference list are needed in trade-imports-reference-data, and the ports service needs a second accessor beside list(). Once that exists the frontend change is small — a different source for portItems and for the validation set in the same controller, and the hint sentence "Exit and entry share the same port list." comes out. Note for whoever schedules this: Frontend is not doing this by accident. It is following a different requirements source, the V4 field spec quoted in its own obligation, which says exit and entry share a list. Design release 1 is the signed-off design and says otherwise, so the two documents disagree and this ticket is where that gets settled.
