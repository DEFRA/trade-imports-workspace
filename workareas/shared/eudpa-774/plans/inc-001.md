## 0. Decisions

1. **Where the boundary with the Back row and the removal row falls.** The row holds the mechanism for Save and continue, the entry guard, Amend's landing and the amend endings. The Back row rebuilds Back. The removal row deletes the run record. So in this row:

The row's gate asks for the task-row rule, the change shortcut and the amend form actions to be "gone rather than bypassed". Leaving any of these behind would keep code nothing reaches.
   - **Kept for the Back row and the removal row:** the run record (`flow/run-state.js`, `beginOpeningRun`, `completeOpeningRun`, `inOpeningRun`), `RUN_STEPS` with `target`, `backCandidates` and `offersBackWhen`, `previousRunTarget` and its seam, `kit.runBackLink`, `entryBackLink` (animals), the `change=1` marker with `changeContext`, `appendChangeContext` and `withChangeContext`, and the documents page's `returnsToReview` Back. 3. **Which pages are steps of the order.** A step is a page in `journeySections()` that belongs to a task row and is not a sub-page. A sub-page sits in a section, so it keeps its section's prerequisites, status and analysis, and in a task row, so it keeps its row's status. But it is reached only from the page that opens it.
   - A new field on the page identity marks a page as a sub-page: animals CPH number (`alin/features/cph-number/page.js`) and plants commodity details (`plin/features/commodities/page.js:3-6`).
   - The field holds no opener id, because nothing would read one. Only its presence is read.
   - This departs from the page-identity shape both sets' docs state: "`page.js` exports only `{ id, slug }` and imports nothing" (`A:live-animals/docs/add-a-page.md:59`, `P:high-risk-plants/docs/add-a-page.md:67`), "A `page.js` exports `{ id, slug }`" (`A:live-animals/docs/features.md:9`, `P:high-risk-plants/docs/features.md:27`), and "Keep every `{ id, slug }` object in the import-free `page.js`" (`A:add-a-section.md:114`, `P:add-a-section.md:131`). The docs already allow one stated exception, an authored `gate` "only when that rule cannot express the page" (`A:add-a-page.md:229-231`), and nothing written allows a further field. Section 14 records the departure and its reason; section 12 lists those lines so they state the identity's shape as it will be: `{ id, slug }`, plus an authored `gate` where the derived gate cannot express the page, plus the sub-page marker on a page reached only from the page that opens it. The identity stays import-free, so the module-cycle reason the docs give still holds.
   - Why the marker cannot be derived instead: a step cannot be read off task rows. The rule "the first page of each task row" would drop the plants commodities list, which is the second page of its row (after commodity type) and is a step (criterion 10). The rule "every task-row page" would keep CPH and commodity details, which are not steps. Nothing else the sections, task rows or page identities hold separates the two cases, so the identity says it.
   - That leaves the dashboard, the review, the declaration and the confirmation out, because they are in no task row. The resulting orders are exactly the two criteria's lists.
   - Rejected: dropping CPH or commodity details from their section or row. That would take their obligations out of section and row status and the reachability analysis.

4. **"Applies" is the scope half of the page gate, not the whole gate.** Split `gates.js` `pageGatePasses` (`A:app/flow/gates.js:23-32`, P: the same) into the scope rule (the authored `page.gate`, else `inScopeReachable(collectsOf(page.id), scope)`) and the prerequisites rule. `pageGatePasses` then composes the two, so the scope rule has one owner. Save and continue passes over a page whose scope rule fails.
   - Why not the whole gate: the animals hub links every row from the start (`isHiddenRow` hides only conditional rows; `rowEntry` falls back to `row.pages[0]`). With only origin saved, Main import reason opened from Overview would otherwise find no later page whose prerequisites pass, and would land on the review. Under the scope rule it goes to Commodity details. Commodity details then sends a notification with no commodity line to What are you importing?, as it does today (`consignment-details.controller.js:89-98`).
   - Plants' hub blocks a row whose gate fails ("Cannot start yet"), so for plants this only matters for a typed address.
   - The potato skips (arrival status and the consignor out of scope) and the transit countries rule (in scope only for Rail or Road) fall out of the scope rule unchanged.
   - **A page's own "does this page apply" guard judges through the same scope rule.** The one such guard is the animals transit countries page (`alin/features/transport/transit-countries/transit-countries.controller.js:128-142`), which today calls the full `pageGatePasses`. That gate includes the countryOfOrigin and commodityCode prerequisites, so on a notification with no commodity code, Arrival details by Road would go to transit countries and transit countries would bounce to Overview, breaking criterion 3 ("from every start including Overview"). The guard calls the scope rule instead. It still redirects to Overview, saving nothing, and logs once, only when the page is out of scope (the means of transport is neither Rail nor Road); the log's reason names that cause, not a failed page gate. The set doc already states this behaviour (`journey-flow-and-gates.md:94-97`, "when the means of transport leaves transit countries out of scope"), so the code comes into line with it. Plants has no page-level guard of this kind (grep `pageGatePasses` over `P:src`: only the hub, `run.js`, `simulate.js` and `navigation.js`).
   - Kept on the full gate, because they are not Save and continue: the animals hub's `isHiddenRow` (`hub/controller.js:57-61`), the run's Back targets (`run.js:23`, the Back row's), `rowEntry`/`rowGatePasses` and `simulate.js`, in both frontends; and, in plants only, `sectionEntry` (the hub's review row reads it).    - Rejected: leaving the transit guard on the full gate and relying on Overview's links. Criterion 3 names every start.
