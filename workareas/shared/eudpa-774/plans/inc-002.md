## 0. Decisions

1. **Where the trader came from is a trail carried on one query parameter, an ordered list of places, newest last.** It travels on links and redirects, and on form posts because every journey form posts to its own address (`<form method="post">` with no `action`, e.g. `A:alin/features/origin/template.njk:14`, `P:plin/features/check-answers/template.njk:77`), so the POST handler sees the same `request.query`. A refused save renders from that POST, a refresh re-requests the same address, a new browser session opens the same address: all keep it. Nothing goes in the session.
   - An entry is either one of three start places (Overview, the dashboard, the Import Notification Service's type question) or the slug of a page in the journey's `journeySections()` (steps, sub-pages and the review page). Slugs contain `/` (`commodities/identification`), so the list separator is one no slug holds; the implementor picks the parameter name and separator.
   - The trail is a list, not a single "came from" marker, because criterion 3 asks Back to step back through several Save and continues in reverse until it reaches where the trader started, and criteria 32 and 35 ask Back to go to whichever page the trader actually pressed Save and continue on. Rejected: "start place plus the previous page in the order that applies". It cannot tell the page pressed from a page that applies by scope but was passed over by its own guard (identification details collects nothing, so its scope rule always passes; `A:app/flow/navigation.js:27-30` with inc-001's decision 5), so Back on Additional details would open identification details for a consignment of ostriches, which bounces straight back.
   - Rejected: collapsing a repeated entry. Opening the review from Overview, following a Change link and Save and continue on to the review again would collapse the trail to Overview, so Back on that review would skip the last journey page, against criterion 69.
   - The trail is bounded: past a fixed length the oldest entries are dropped. The bound fits two full passes of the longer journey's step list plus the review and a start place, so a Change link round trip from a review reached by a full pass still steps back to its start. A trail emptied by dropping simply falls back (decision 4). The literal lives in the one kit function that pushes.

2. **Three operations on the trail, each with one owner in `app/shared/kit.js`, mirrored in each frontend.** They replace the `change` marker (`changeContext`, `appendChangeContext`, `withChangeContext`, `A:app/shared/kit.js:175-182`, `P:app/shared/kit.js:147-154`) and every place it is carried, because the trail does everything `change=1` did and more. Extending the existing marker mechanism, not adding a second beside it.
   - **Carry**: an href with the request's trail unchanged. Used wherever `withChangeContext` / `appendChangeContext` / `{ change: kit.changeContext(request) }` is used today: every sub-page round trip and every link or redirect that brings a page back to itself (documents' upload return, Save and add another, remove and refresh status; identification's remove; the picker's pagination; the commodity detour's return; party edit; the plants commodities links).
   - **Push**: an href with the request's trail plus one entry appended (a page slug, or a start place). Used by every link that moves the trader forward in their own history: `kit.nextTarget` (pushes the `page` it is given, so Save and continue from origin lands on What are you importing? with origin on top; a transporter spoke passes the transporter list, so its save lands on Upload documents with Transporter details on top, criterion 37), the review page's Change links and error-summary links (push the review onto the review's own trail, criterion 4), Overview's task-row links and the review links on Overview (a trail of Overview), the create and start redirects (a trail of the dashboard or the INS start), the dashboard card's View link and Amend redirect (a trail of the dashboard), and identification details' Change number of animals link (pushes identification details, criterion 23).
   - **Back**: the top entry's href carrying the rest of the trail; with no trail, an unrecognised trail, or nothing left, the page's fallback (decision 4). The Back href is always built from a recognised slug or start place, never echoed from the request, so a forged trail cannot make an open redirect.
   - `kit.runBackLink`, its private `previousStepBackLink`, its `returnsToReview` option (animals) and its `fallback` option (plants) are deleted; the Back operation takes the page's fallback as a named option, keeping plants' `{ fallback }` shape, defaulting to Overview.
   - Rejected: threading `change` alongside a new trail. Two markers for one concept.

3. **A page keeps one Back rule; sub-pages keep their fixed opener.** Every journey page that calls `kit.runBackLink` today (animals: origin via `entryBackLink`, What are you importing?, main import reason, commodity details, identification details, additional details, arrival details, transit countries, Transporter details, Upload documents, Consignment addresses, Contact address; plants: commodity type, commodities list, origin, arrival status, arrival details, the three pickers via `address-book-picker/render.js:78`, identification numbers) takes its Back from the Back operation. So a round trip leaves the opener with the trail it had (criteria 13, 38, 46, 47, 76).
   - Plants commodity details' Back when the consignment holds no line (today `commodityTypeHref`, `P:plin/features/commodities/details/details.controller.js:82`) becomes the Back operation on its carried trail, i.e. where the list's Back would go, because the list redirects there when it is empty (`list.controller.js:90-92`) and a fixed link to commodity type carrying the list's trail would put commodity type on its own Back.    - Rejected: folding the `return` markers into the trail ("the top entry is the opener").
