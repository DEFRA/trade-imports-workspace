## 0. Decisions

1. **One edit in `buildView`, not four `withNoStore` call sites.** Checked against the live tree: `buildView` is the only path that calls `h.view` in `add.controller.js` — GET success, GET country-load failure (500), POST local validation failure (400), POST address-book API validation failure (400) and POST address-book server error (500) all return `buildView(...)`. Redirects (`redirectAfterAdd`, `redirectAfterCancel`) do not go through it. So one `.header(...)` on the response `buildView` returns covers every render main covered (main's four `withNoStore` sites) and leaves every redirect alone, as the resolution records. Rejected: porting main's `withNoStore` helper and `NO_STORE` constant — more code for the same behaviour, and it would bring back a pattern the aligned controller does not use.
2. **Chaining stays legal.** hapi response methods return the response, so the callers' existing `.code(HTTP_STATUS_BAD_REQUEST)` / `.code(HTTP_STATUS_INTERNAL_SERVER_ERROR)` after `buildView(...)` keep working unchanged.
3. **Header value is the literal `'no-store'`, header name `'Cache-Control'`,** exactly as main set it. An explicit `cache-control` header wins over hapi's own default (hapi only adds its default when the header is absent), which main's passing test already proved.
4. **Redirect assertion is `not.toBe('no-store')`, not an exact value.** hapi sets its own default (`no-cache`) on a 302; pinning that value would test hapi, not us. The criterion is "without that instruction", so the negative assertion is the right one.
5. **Tests: one new GET test (main's, re-pointed), header assertions added to the three existing re-render tests and the two existing non-handshake redirect tests.** The resolution names the GET, a POST validation error and a successful redirect. The acceptance criteria go wider ("every re-render after a validation or address-book API error", "a successful save or a cancel"), so the plan also asserts the header on the API-400 and API-503 re-renders and on the cancel redirect by adding one line to tests that already drive those paths. Rejected: a separate new test per path — each would duplicate an existing request purely for one header, which is coverage padding.
6. **No FIT spec change.** The unit tests use `server.inject` against the real `createServer()`, so they already run the full hapi pipeline (every plugin and `onPreResponse`), which is where the header would be stripped or overridden if anything did. A Playwright "press back after save" test was considered for criterion 3 and rejected: Chromium's back-forward cache now admits some `Cache-Control: no-store` pages, and the session cookie changes on save, so the assertion would depend on browser heuristics rather than our code — a flake source. Criterion 3 is met by the `no-store` contract (a browser must not store the page, so back re-requests the form, which renders empty); the header is what the application controls and what the tests pin.
7. **No E2E.** `gatePhases` is `["unit", "fit"]`; the end-to-end proof belongs to the cross-repo end-to-end row, per the programme invariant that the E2E rung runs once after all four merges land.
8. **No doc comment added.** `buildView` has none today and the change is one chained call; per the workspace's comment rules, rationale lives in git and docs, not in a code comment.

## 2. Edits

### `repos/trade-imports-ins-frontend/src/server/app/features/address-book/add/add.controller.js`

In `buildView` (lines 36–54), chain `.header('Cache-Control', 'no-store')` onto the `h.view(view, {...})` call so the arrow function returns the response with the header set. Result shape:

```js
const buildView = (
  h,
  { formValues, countryItems, errors = {}, recoverableError = false, handshake = null }
) =>
  h
    .view(view, {
      ...kit.base(copy.add.title, { recoverableError }),
      copy,
      formValues,
      countryItems,
      errors,
      errorSummary: kit.errorSummary(errors),
      handshakeContext: handshake
    })
    .header('Cache-Control', 'no-store')
```
