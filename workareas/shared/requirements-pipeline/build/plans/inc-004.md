## 0 Decisions

Every choice the two atoms leave open, made here. No fork reaches the implementer.

### D1 — The core is generalised in place, not copied

`tim/src/parity/ingest.js` becomes the one generic core. Parity calls it through a `parity-v1`
profile definition whose hooks are today's code verbatim.

**Why:** req-008's statement is "one core", and its `why` is "one core gives every programme the same
locks, op ids and lost-update refusals". A second implementation for requirements backlogs is the
drift the atom exists to stop.

**Rejected:** a new `tim/src/backlog/ingest.js` written beside the parity one. It would pass ac-3 and
ac-1 on the day and be two cores by the next increment.

### D2 — What moves to `tim/src/backlog/`, and what does not

`git mv` (history kept, per DESIGN 4.1):

| From | To |
|---|---|
| `tim/src/parity/io.js` | `tim/src/backlog/io.js` |
| `tim/src/parity/io.test.js` | `tim/src/backlog/io.test.js` |
| `tim/src/parity/ingest.js` | `tim/src/backlog/ingest.js` |
| `tim/src/parity/ingest.test.js` | `tim/src/backlog/ingest.parity-v1.test.js` |

`io.js` moves because the generic core writes through it and imports only `node:*` and `../errors.js`
— it has no parity vocabulary at all (survey §1). Leaving it under `parity/` would make every
registered programme's writer import from parity's folder, which is the coupling req-008 removes.
The cost is 25 import-specifier edits in files that change in no other way (§2.3).

**`schema.js`, `set.js` and the checks, citations and render pieces DESIGN 4.1 also lists do not
move.** DESIGN's own profile table (4.1) makes the schema profile-owned ("today's `schema.js:112-143`"
for `parity-v1`, "section 3, strict" for `requirements-v2`), so `tim/src/parity/schema.js` is
parity's schema, read by twelve parity modules; moving it into a generic folder would name parity's
zod shapes as generic. `set.js` writes prose slots, which is none of the "id, reference, ruling and
freeze logic" req-008's statement enumerates, and no criterion of either atom exercises it; moving it
would also force the survey's mismatch #3 (two, in fact three, prose-slot lists) to be settled by
this increment with no atom asking for it — a blocking objection class under L1. §5 names where each
one goes.

**Rejected:** the whole DESIGN 4.1 move list in one increment. The deferred files are parity's
evidence and report pipeline, not the writer core; moving them multiplies ac-2's risk (§5) for no
criterion, against an acceptance that is "parity is unchanged".

### D3 — The parity-v1 profile definition lives in `tim/src/parity/`

`tim/src/parity/profile-v1.js` holds the `parity-v1` definition and the parity-specific constants and
functions lifted out of `ingest.js`: `FINDINGS_DIR`, `INITIAL_STATUS`, `FINDING_TYPES`, `CONFIDENCES`,
`PROSE_SLOTS`, `findingsDir`, `verificationOf`, `manifestScreens`, `validateFinding`, `composeDetail`,
and the `resolveTarget` fallback.

**Why:** that vocabulary is findings, screens, bands and sides. `yield.js` and `duplicates.js` already
import two of those names, and they stay one directory away. DESIGN 4.1 says profiles live under
`tim/src/backlog/profiles/`; the deviation is recorded here on merit — `tim/src/backlog/` stays free
of parity vocabulary, which is what "one core [that] serves any registered programme" means in the
directory listing as well as in the code.

**Rejected:** `tim/src/backlog/profiles/parity-v1.js`. It puts screens, bands and capture manifests
inside the generic folder, naming parity's own vocabulary as generic — the opposite of what "one core
[that] serves any registered programme" means in the directory listing.

### D4 — One profile map, and the one import edge it costs

`tim/src/backlog/profiles/index.js` exports `PROFILE_KEYS`, `DEFAULT_PROFILE_KEY = 'parity-v1'` and
`profileFor(key)`, which throws `TimError('USAGE', …)` naming the known keys. It imports
`../../parity/profile-v1.js` and `./requirements-v2.js`.

That is one edge from `backlog/` to `parity/`, and it is acyclic: `profile-v1.js` imports only
`../backlog/io.js`, `./schema.js` and `../errors.js`. It is the price of a single answer to "which
profiles exist"; the alternative is one map per command group, which drifts.

### D5 — The core takes the programme it already takes, and looks up its definition

`runIngest({ profile, workspaceRoot, replace, dryRun, ...options })` keeps its parameter names.
`ingest.test.js` (moved, unchanged) calls `runIngest({ profile, workspaceRoot, target })` with an
inline profile object that carries no profile key, so the core resolves
`profileFor(profile.profileKey ?? DEFAULT_PROFILE_KEY)`.

**Why:** requiring the definition on the profile would force an edit to `buildProfile` in the moved
parity test — which is a parity test's fixture edited to make the change pass, req-008's own
falsifier. Defaulting to `parity-v1` is also the literal statement of "parity's behaviour unchanged".

**Rejected:** a separate `definition` argument (same falsifier, plus two arguments where the atom says
one profile).

### D6 — `loadCorpusProfile` gains `profileKey`, taken from the registry entry

`profileKey: raw.profile ?? 'parity-v1'`. Survey fact §6.5 is right: no entry carries `profile`
today, so the default is what the four corpora get. Adding the key to an entry later switches that
corpus with no code change.

### D7 — The registry is one reader over two files, and `tools/parity/corpora.json` does not move

New `tim/src/backlog/registry.js` reads, in order:

1. `tools/backlog/registry.json`, map `programmes`, each entry carrying its own `profile`;
2. `tools/parity/corpora.json`, map `corpora`, every entry defaulting to `profile: 'parity-v1'`.

Keys are merged; a key declared in both is refused by name, naming both files. A missing file
contributes nothing. `default` is read from `corpora.json` only.

**Why the parity file stays put:** three committed bash readers (`start-comparison.sh`, `phase.sh`,
`scaffold-corpus.sh`) read that path, and DESIGN 4.1 itself says they "keep working for the four
frozen corpora". More decisively, `corpus-profile.test.js:125` writes its fixture registry at
`tools/parity/corpora.json` and `:210` reads the real file at that path, and its assertions quote the
source strings `corpora.json default` and `runId in corpora.json`. Moving the file forces an edit to
a parity test fixture — req-008's falsifier, word for word.

**Rejected:** `git mv tools/parity/corpora.json tools/backlog/registry.json` as DESIGN 4.1 instructs
(falsifies ac-1); and two independent readers, one per file (the survey's mismatch #4/#5 exist
because there is no single seam today).

### D8 — `resolveCorpusId`'s run-id probe stays, and req-009 is met at the programme lookup

`corpus-profile.js:87-92` builds `workareas/journey-builder/<runId>/{backlog.json,.corpus-meta.json}`
and reads a corpus id out of it. Two tests pin it: "reads the corpus field off the backlog" and
"falls through to .corpus-meta.json when the backlog is silent". It is left exactly as it is.

req-009 is met where it is stated — **a programme's files**. Every path a command reads or writes
(`workarea`, `backlog`, the items directory) comes from the registry entry, for both profiles, and
the new `tim backlog <verb> <programmeKey>` entry point resolves a key straight through the registry
with no path built from anything. The probe resolves an *identifier* for parity's existing
`<runId>`-shaped command line; it reads no programme's files from a constructed path, because
`loadCorpusProfile` still takes every path from the entry it then looks up.

**The residual, named:** under the strictest reading of req-009's first clause, parity's
run-id-to-key resolution still opens a constructed path. Removing it deletes two passing parity tests,
which req-008 ac-1 forbids in the same increment. It goes with the `EUDPA-*` run-id rule and the
bash readers, in **inc-040** (`retire-old-paths`, req-112: "Every script, mode and workflow the new
pipeline replaces MUST be removed or clearly frozen, with nothing still calling it").

**Rejected:** reordering the precedence so the registry's `runId` match wins first. It breaks the test
that proves the backlog's own `corpus` field beats the registry, and that test protects a real
failure — a run whose backlog names a corpus the registry has not caught up with.

### D9 — `CORPORA_FILE` moves to `registry.js`, and `repoint.js` imports it from there

One home for the path constant closes the survey's mismatch #5 (two writers of the same file, only
one importing the name). `corpus-profile.js` imports it from `registry.js` too, and its
`NOT_FOUND` message keeps the exact text `Can't find tools/parity/corpora.json.`

**Behaviour change, accepted:** `loadCorpusProfile`'s own missing-file path used to reach that
message a different way. Before this increment it called its own `readJson` with no `existsSync`
guard, so a missing `tools/parity/corpora.json` failed inside `readFileSync`'s `try`/`catch` and
came out as `PARSE` (exit 1, `ERROR`). It now calls `registry.js`'s `readCorporaFile`, whose
`existsSync` guard throws `NOT_FOUND` first (exit 2, `USAGE`, via `commands/envelope.js`'s
`exitCodeFor`) — the same code `resolveCorpusId` already threw for the identical case. The message
text is unchanged (`corpus-profile.test.js` new test: "throws NOT_FOUND, not PARSE, when
tools/parity/corpora.json is missing"); only the code and exit status move, and they move to the
value the rest of the file already used for this exact failure, so this is a defect
`loadCorpusProfile` had and `resolveCorpusId` did not — not a new inconsistency.

### D10 — `tim backlog` ships two verbs, and no more

`tim backlog ingest <programme> [--replace] [--dry-run] [--json]` and
`tim backlog registry list | show <programme> [--json]`.

Those are what the four criteria need. Every other command in DESIGN 4.2 belongs to a later increment
(§5). `ingest` for a `parity-v1` programme delegates to `loadCorpusProfile({ workspaceRoot, explicit:
key })`, so `tim backlog ingest dr1 --dry-run` runs parity's ingest through the generic command —
which is req-009 ac-1's "any backlog command runs with that key" proved across both profiles.

### D11 — The exit-code mapping and the JSON envelope are shared, the wrappers are not

New `tim/src/commands/envelope.js` exports `jsonEnvelope({ ok, result, error, timVersion })` and
`exitCodeFor(error)` (`USAGE` and `NOT_FOUND` → exit 2, anything else → exit 1), lifted from
`commands/parity/index.js:68-101` with no change in behaviour. `makeParityAction` and the new
`makeBacklogAction` both call them.

**Why:** the survey's seam 11 — the mapping is inlined once with no exported function, and a second
command group would otherwise reimplement it. The two wrappers stay separate because they resolve
different things: parity resolves a corpus from a run id with a `--corpus` override, backlog resolves
a programme from a key.

**Rejected:** one shared `makeAction`. It would fold parity's corpus resolution into a generic
wrapper, which is more of parity's command layer changed than any criterion asks for.

### D13 — Reference resolution generalises to string-shaped fields as well as parity's objects

parity's `relatedTo` entries are objects with an `.id`; a v2 atom's `dependsOn` and `relatedTo` are
bare key strings which ingest must turn into ids in the same pass (DESIGN 3.4: "Cross-references are
written as keys and resolved to ids in the same pass"). The resolver keeps parity's three refusals —
no id, unknown slug, self-reference — with parity's exact message text, and `requirements-v2` supplies
its own text.

**Why include it:** ac-3 inserts an atom ahead of the others. A reference resolved by position rather
than by key is exactly the failure that would hide behind a passing id-stability assertion.

### D14 — `requirements-v2`'s schema in this increment covers what the core reads and writes

The header (`schemaVersion`, `programme`, `profile`, `requirements[]`) and the atom fields of DESIGN
3.4 the core touches: `id`, `key`, `slice`, `kind`, `title`, `statement`, `why`, `acceptance[]`,
`falsifiedBy`, `sources[]`, `surface`, `dependsOn[]`, `relatedTo[]`, `status`, `provenance`. Required
fields are refused by name when missing or malformed. **Unknown keys pass through untouched.**

**Why not strict:** the strict refusal that names a recipe or executor key with its proper home is
**req-010** (`writer--strict-schema`), a member of **inc-005** (`v2-assembly`). Writing it here is
scope no atom of inc-004 asks for. ac-3's "every refusal names its field" is about the refusals this
increment does make, and each of them names file and field.

### D15 — `requirements-v2` does not gate on verification in this increment

DESIGN 4.1 says verification is "always, with the registered-run guard" for `requirements-v2`. The
survey's fact §6.4 is right: no registered-run guard exists anywhere in the live code, and

in place for the increment that builds the guard: **inc-007** (`content-guards`, req-017 onward).

### D16 — `bornStatus` for `requirements-v2` is the constant `proposed`

### req-008 ac-1

> "Given the existing parity corpora, when the writer's existing test suite runs after the change,
> then every test passes with no fixture changed."

**How the change meets it.** Every parity-shaped constant, list, validator, message and tally moves

**How it is proven.** Invariant I1: the whole tim suite green, with the run recorded to a file.
