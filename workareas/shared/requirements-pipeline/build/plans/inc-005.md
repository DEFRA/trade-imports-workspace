### D1 — One profile owns several item collections; the core is pointed at one of them

`tim/src/backlog/profiles/index.js` stops being a flat map of one definition per profile key and
becomes a map of profiles, each holding named **collections**:

```js
const PROFILES = {
  'parity-v1': { default: 'findings', collections: { findings: parityV1 } },
  'requirements-v2': {
    default: 'atoms',
    collections: { atoms: requirementsV2, increments: requirementsV2Increments }
  }
}
```

`profileFor(key, collection)` gains an optional second argument: with no collection it returns the
profile's default collection definition, which is byte-for-byte what it returns today for both keys;
with one it returns that named collection or throws `TimError('USAGE', …)` naming the collections
the profile has. `runIngest` gains a `collection` argument and passes it straight through.

**Why:** the survey's seam 1 — nothing else in the increment can be built until the core can be
pointed at `distil/increments/` and `increments[]`. Keeping the resolution in one function keeps one
answer to "which definition serves this run", which is the property inc-004 built.

**Rejected:** `requirementsV2` growing into `{atoms, increments}` sub-objects. `programme.js:39`
and `profiles/index.test.js:7` both read `profileFor(key).key`, and parity has exactly one
collection; making every caller reach through a second level to get a definition pays for a
generality only one profile has, and would put a `collection` concept into `loadProgramme`, which
has no business knowing about one.

**Rejected:** a second `runIngestIncrements` entry point. That is a second core by another name —
the drift req-008 exists to stop, and the thing this increment's `dependsOn: [inc-004]` says has
just been removed.

### D2 — `--atoms` and `--increments` are optional; absent means the profile's default collection

`tim backlog ingest <p>` gains `--atoms` and `--increments`. Giving both is refused with
`TimError('USAGE', …)` before anything is read. Giving neither resolves the profile's default
collection: `atoms` for `requirements-v2`, `findings` for `parity-v1`. Giving `--atoms` or
`--increments` to a `parity-v1` programme is refused by `profileFor`, naming `findings`.

**Why:** DESIGN 4.2 writes the command as `ingest <p> --atoms | --increments`, which reads as a
required choice, but `tim parity ingest` routes through the same `runIngest` and has no such choice
to make; a required flag would make the parity route pass one for no reason. Defaulting to `atoms`
also keeps all 8 existing `tim backlog ingest` CLI cases and all 24 direct `runIngest` cases in
`ingest.requirements-v2.test.js` passing unchanged, which is not a cost argument (R8) but a correctness one: none of those cases is about
collection selection, so none of them should have to change to express it.

**Rejected:** making the flag required for `requirements-v2` only. A flag whose necessity depends on
the profile is a rule a person has to learn from a refusal; the default is the first pass, which is
also the pass that must run first.

**Ambiguity accepted and mitigated:** a person who means increments and types neither flag ingests
atoms. The ingest result carries `collection` (D3) and every assigned id in the printed assignment
list is `req-NNN` or `inc-NNN`, so the wrong pass is visible in the first line of output and is
idempotent.

### D3 — The ingest result names its collection

`runIngest` adds `collection: <name>` to its returned summary, in the core rather than in each
profile's `summary` hook.

**Why:** it is the one fact every caller needs to tell the two passes apart, and it must be the same
fact the core dispatched on. The cross-profile CLI test (`commands/backlog/index.test.js:309`)
asserts `backlogResult` equals `parityResult`; both run with no collection and both resolve
`findings`, so the added field is equal on both sides and the case stays green.

### D4 — The core reads the existing backlog before it builds its context

`runIngest`'s order becomes: resolve the definition → `readExisting` → `definition.context(profile, existing)` → `readItems` → `definition.expandItems` → assign ids → resolve references → build rows
→ cycle check → `definition.checkRows` → write.

`context` gains a second argument, `existing` (the parsed backlog or `null`). Parity's
`context(profile)` and atoms' `context()` ignore it.

**Why:** everything the increments collection derives — which atoms are adopted, which key maps to
which `req-*` id, which increments have a recorded build attempt — comes from the already-written
backlog, and `context` is the hook whose whole job is "what this definition needs to know before it
reads its items". Building those tables anywhere else would spread them across three hooks.

**Consequence recorded:** for `parity-v1`, `context` (which reads capture manifests) now runs before
the findings directory is read. The only observable difference is the order of two refusals when a
corpus has both a corrupt manifest and a missing `findings/` directory. No test exercises that pair,
and neither message changes.

**Rejected:** passing `existing` separately into `expandItems`, `referenceTables` and `isRuled`.
Three hooks would each re-derive the same tables from the same file.

### D5 — A reference names the table it resolves against, and an id is looked up like a key

Each entry in `definition.references` gains a `scope` and a `verifyIds` flag. The core builds a map
of lookup tables:

```js
const tables = { batch: batchTable, ...definition.referenceTables(context) }
```

Every table is a `Map` from **name to id**, where the names are both the slugs and the ids it knows:
the core builds `batch` as the id-to-itself pairs first and the slug-to-id pairs over the top, so a
slug that happens to read like an id still wins. `resolveReferences` reads `tables[scope]` for each
field. Every existing entry is written `scope: 'batch'` explicitly, in all three definitions.

For the increments collection: `dependsOn` is `{scope: 'batch', shape: 'string', verifyIds: true}`
(other increments, same batch, exactly as atoms' `dependsOn` works today) and `members` is
`{scope: 'atoms', shape: 'string', idPrefix: 'req-', verifyIds: true}`, resolved against
`context.atomTable`, the name-to-id map built from the already-written `requirements[]` (every row's
`key` to its id, and every row's id to itself).

**Why a scope:** the survey's mismatch 3 — resolving `members` through the batch map would refuse
every member with "no increment in this run", the right refusal shape pointed at the wrong table. The
scope makes the table an explicit property of the field rather than an implicit property of the
collection.

#### D5.1 — An id-shaped entry is verified, not waved through (the third audit objection)

`resolveReferences` today reads:

```js
const resolvedId = looksResolved(trimmed, definition.idPrefix) ? trimmed : slugs.get(trimmed)
```

(`ingest.js:139-141`). The short-circuit returns the string **without consulting any table**, so
`members: ["req-999"]` — an id no atom holds — is accepted, written to the row, and counted as a
claim on nothing, while the atom it was meant to claim quietly takes a solo instead. req-012's
statement is "The writer MUST refuse a dangling, self or cyclic reference between atoms or
increments, naming every key involved", so that is a hole in the very half of req-012 this plan
claims to prove. The same hole exists today for atoms' `dependsOn` and `relatedTo`.

The resolution becomes, per entry:

```js
const resolveOne = ({ entry, named, table, definition }) =>
  !entry.verifyIds && looksResolved(named, entry.idPrefix ?? definition.idPrefix)
    ? named
    : (table.get(named) ?? null)
```

`null` takes the existing `referenceUnknown` refusal path, which already names the file, the field
and the entry. Because every table carries its ids as well as its slugs, an id-shaped entry naming
something the run knows resolves to itself exactly as before; only a dangling one now fails.

**Which entries carry `verifyIds: true`:** all four requirements-v2 entries — atoms' `dependsOn` and
`relatedTo`, increments' `dependsOn` and `members`.

**Which does not, and why:** `parity-v1`'s `relatedTo`. `ingest.parity-v1.test.js:496-514` ("leaves
an id that is already an increment id alone on a re-ingest") happens to name an id the batch holds,
so it would stay green either way — but the frozen dr21 and dr1 corpora are not read in this session,
and a corpus holding a `relatedTo` id whose finding file was later struck would start being refused
by a change no member atom of inc-005 asks for. inc-004's req-008 ac-1 falsifier is a changed parity
behaviour, so parity keeps today's behaviour byte for byte. §5 hands parity's own dangling-id hole to
the increment that next touches `parity-v1`.

**Rejected:** deleting `looksResolved` outright and verifying everywhere. Same reason: it changes
parity.

**Rejected:** resolving `members` in `expandItems` and leaving `references` alone. The dangling and
self refusals req-012's statement requires for `members` already exist in `resolveReferences`;
re-implementing them one hook earlier would give two refusal paths with two messages.

**`self` for `members`:** `resolveReferences` refuses a reference that resolves to the item's own id.
An increment's member is a `req-*` id and the increment's own id is `inc-*`, so the self check can
never fire on `members` — correct, and stated here so nobody reads the absence as a gap.

**`needs` is not a resolved reference here.** DESIGN 4.4 lists `needs` among the fields the general
resolver covers, but `needs` holds `q-*` ids and no questions ledger exists (inc-009). It is carried
as opaque strings, with no scope table and no refusal, and §5 names the increment that resolves it.

### D6 — Cycles are found by a depth-first search in a new `graph.js`, over resolved ids

New `tim/src/backlog/graph.js` exports `findCycle(edges)`, where `edges` is a `Map` of id to the
ids it points at. It runs an **iterative** depth-first search with white/grey/black colouring and
returns the cycle as an array of ids in path order (first repeated node last), or `null`.

The core calls it after rows are built and before the write, over `definition.cycleEdges(rows)`, and
raises `TimError('USAGE', definition.messages.cycle(path))` where `path` carries each row's id, key
and title.

- `parity-v1`: `cycleEdges: () => []`, supplied by `DEFAULT_HOOKS` (§2.2), so `profile-v1.js` does
  not declare it. Parity's `dependsOn` is born `[]` and never resolved, so the edge set is empty and
  behaviour is unchanged. There is a second reason, checked this session.
  `ingest.parity-v1.test.js:215-264` hand-writes `dependsOn: ['inc-002']` onto a parity row, naming an
  id no row holds, and expects a re-ingest to keep it. A parity edge set built from `dependsOn` would
  put an unresolved edge into the graph. `findCycle` ignores it (F case 7), but parity has no rule that
  makes it meaningful either. Parity's hand-kept `dependsOn` is build-loop data, not a resolved
  reference.
- atoms: `cycleEdges: (rows) => rows.map((row) => [row.id, row.dependsOn ?? []])`.
- increments: the same over the derived `dependsOn`.

**Why a DFS and not Tarjan's:** DESIGN 4.4 names Tarjan's; DESIGN 3.11 names "a depth-first search
over atom `dependsOn`, then over increment `dependsOn`, [which] refuses a cycle and names every key
in it". Both sections agree on the requirement — name every key in the cycle — and req-012's own
acceptance is "the message names both keys". Tarjan's returns strongly connected components, which
then need a second walk to turn into the path a person can read. The DFS returns the path directly.
This is a deviation from one sentence of DESIGN 4.4, decided on merit (R8) and recorded here rather
than by editing DESIGN, which this increment does not name.

**Iterative, not recursive:** a backlog is authored by agents and this programme's own has 142
atoms; a recursive DFS is fine at that size but the depth is not bounded by anything the writer
controls, and an exceeded stack is not a refusal a person can act on.

**Out of the cycle check's reach, on purpose:** the repos' `consumes` cycle DESIGN 4.2 names under
`check`. `graph.js` is written to take any edge map, so that check is a call, not a rewrite; it
belongs with `check` (§5).

### D7 — Atom cycles are refused too

req-012's statement is "a dangling, self or cyclic reference **between atoms or increments**". Its
one acceptance criterion is the increment case, so the increment case is the proof; the atom case is

### D8 — Unknown keys are refused at intake; **refused** keys are refused on rows too; the row schema's tolerance of *other* unknown keys stays

Two checks, not one:

1. **Intake (authored files).** `validateAtom` and the new `validateIncrement` refuse any key on the
   authored file that is not a v2 field of that collection — both the named `REFUSED_FIELDS` and any
   other stray key.
2. **Rows (`parseAtom` and `parseIncrement`, D26).** Every row the writer reads in or writes out is
   checked against `REFUSED_FIELDS` alone. A refused key on a row stops the run and names the
   field's home. Any other unknown key on a row is still kept untouched.

`atomSchema`, `v2BacklogSchema` and the new `incrementSchema` keep `.catchall(z.unknown())` exactly
as they are. Check 2 is a walk over the parsed row's own keys, not a schema change.

**Correction to this plan's previous revision, recorded because an auditor was right.** The earlier
D8 said "The only way such a key can reach a saved backlog is the authored file, because `rowFrom`
builds every row from a fixed field list and `refreshed` only folds authored fields over an existing
row." The second clause is false, and the code was re-read this session to confirm it:

- `refreshed` (`tim/src/backlog/ingest.js:171-180`) spreads `...row` — the **existing** row —
  first, then the authored fields over the top. Its own doc comment says so: "anything this tool
  does not own survives untouched."
- `atomSchema` and `v2BacklogSchema` are built from
  `passthrough = (shape) => z.object(shape).catchall(z.unknown())`
  (`tim/src/backlog/profiles/requirements-v2.js:25`), so `parseAtom` preserves unknown keys on a row
  it re-parses, on the way in (`readExisting` → `parseBacklog`, `ingest.js:186`) and on the way out
  (`definition.parseItem(row, index)` over every written row).

So `"executor": "codex"` hand-added to a row of a saved `backlog.json` survives the read, survives
`refreshed`, survives the output re-parse and is written straight back out. That is req-010's
falsifier verbatim — "A saved requirement backlog that contains a recipe or executor key" — and
intake-only strictness leaves it open. Check 2 closes it: the same backlog is now refused on the
read, naming `executor` and `build/run.json`.

**Why check 2 is the named list only, and not a closed row schema.** A closed row schema would
refuse fields the unbuilt `rule`, `verify-record` and `combine` commands are documented (in
`profiles/requirements-v2.js:21-24`) as needing to add, and would turn the currently-passing D14
case red. Check 2 is strictly smaller: it refuses only keys DESIGN 3.14 names as "absent by design,
and refused by name". D14's case pins `needs: ['q-something']`, which is not in `REFUSED_FIELDS`
(it is a v2 state field), so that case stays green untouched; and D9's non-overlap test —
`REFUSED_FIELDS` shares no key with `ATOM_FIELDS` or `INCREMENT_FIELDS` — is what guarantees check 2
can never refuse a field the writer itself writes.

**Still recorded for the judge, not fixed here:** DESIGN 3.14 says "The v2 schema is strict: an
unknown key is refused, not passed through", without separating the authored file from the written
row. After this increment an unknown key is refused wherever it is authored and wherever it is
named-and-refused on a row; a *neutral* stray key on a row is still carried. Closing the row schema
outright belongs with the commands that write rows (inc-009 for `rule` and the ledgers; §5).

### D26 — The row-level refusal lives in `parseAtom` and `parseIncrement`, and nowhere else

*(Numbered last, placed here because it is D8's mechanism.)*

`refuseRefusedKeys({ row, where, known: REFUSED_FIELDS })` is exported from `intake.js` and called
by `parseAtom` and `parseIncrement` after their zod parse and before they return. It raises
`TimError('PARSE', …)` with the same home sentences intake uses, prefixed by the row's id when it
has one and by `<collection>[<index>]` when it does not.

**Why these two functions and not a step in `runIngest`:** they are the only doors a requirements-v2
row goes through. `parseBacklog` (`ingest.js:186`) runs them on every existing row read in, and
`parseItem` runs them on every row written out, so one call site pair covers both directions of the
carry-over path. A step in `runIngest` would cover the write and miss any other reader of a saved
backlog (`tim backlog next`, `check`, `render` — all later increments), and would have to be
repeated in each.

**`parity-v1` is untouched.** DESIGN 3.14's own last sentence keeps parity additive-tolerant for the
frozen corpora, and `parity/schema.js` is not edited (§2.3).

**Blast radius, checked this session.** The tracked fixture's `backlog.json` rows carry only
`acceptance, dependsOn, falsifiedBy, id, key, kind, provenance, relatedTo, slice, sources,
statement, status, surface, title, why` — none refused — and `fixture-requirements` is the only
programme in `tools/backlog/registry.json`, so no real backlog starts being refused when this lands.
Two rows of the programme's own unregistered `design/backlog.json` (`inc-003`, `inc-004`) carry a
refused key, `commit`. §5 says what that means for the later migration.

**Rejected:** refusing on the write only. The read is where a hand-edited backlog is caught, and
"somebody hand-edited the file" is the only way a refused key gets onto a row at all now that intake
refuses it.

**Rejected:** a warning rather than a refusal. req-010's statement is "MUST refuse".

### D9 — One classes file is the single source of every known field and every refused field

New `tim/src/backlog/profiles/requirements-v2.classes.js` exports:

- `ATOM_FIELDS` — every DESIGN 3.4 field mapped to `{class, persisted}`, where `class` is
  `requirement`, `meta` or `state`.
- `INCREMENT_FIELDS` — every DESIGN 3.5 field mapped to the same shape.
- `REFUSED_FIELDS` — every field DESIGN 3.14 lists as "absent by design, and refused by name",
  mapped to a sentence naming its home.

`persisted: true` means "a row this writer produces carries this field". It is not decoration: it is
what makes the G test able to fail. See D9.1.

The known-key set for an authored file is the keys of that collection's class map. The refusal, in
`refuseUnknownKeys`, is two-tier: a key in `REFUSED_FIELDS` is refused with its home; any other
unknown key is refused with "is not a field of a requirement atom/increment" and the known list.

Message copy, from DESIGN 3.14's own wording:

- `filesToTouch` → ``"filesToTouch" is a recipe field. The plan owns files: build/plans/<id>.md.``
- `executor` → ``"executor" is an executor field. The run configuration owns it: build/run.json.``
  The message names where the choice lives and nothing else. It never names a preferred executor,

- `verification` and the other recipe fields → ``… The plan owns how a change is verified: build/plans/<id>.md.``

- run-state fields → ``… Run state owns it: build/state.json.``

A sibling test asserts every field the writer actually writes appears in the class map with a class,
which is DESIGN 3.14's "a field cannot enter without being classed", and asserts that
`ATOM_FIELDS`, `INCREMENT_FIELDS` and `REFUSED_FIELDS` do not overlap.

**Why a class map rather than a bare list:** DESIGN 3.14 names the file and the test by name, the

#### D9.1 — The G test runs both ways (the second audit objection)

The previous revision's G test asserted only that every field `rowFrom` writes is in the class map —
`written ⊆ classed`. That direction cannot catch the opposite failure, which is the one this plan
walked into: a field **classed** in the map, relied on by another decision, and never written by the
writer at all. `needs` was exactly that (D28), and so, today, are `actor`, `confidence`, `decisions`,
`constraints`, `variantOf` and `supersededBy`, none of which `rowFrom` writes.

So the G test runs both ways:

1. **`written ⊆ classed`** — every key on a row the definition produces (through `rowFrom`,
   `bornExtras`, `bornStatus` and the frozen field) is in that collection's class map.
2. **`persisted ⊆ written`** — build one born row and one refreshed row per collection from a fully
   populated authored item, and assert every field the class map marks `persisted: true` is present
   on it. A field marked `persisted` that the writer never writes fails the test by name.

`persisted: true` in this increment is exactly the field set the writer produces after D28: the
fourteen `rowFrom` fields, `status`, and `needs`. Every other classed field is `persisted: false`
with its later owner named in the map's own entry, and §5 lists them. Flipping one to `true` without
writing it is a red test, which is the guard the objection asked for.

**Rejected:** asserting `classed ⊆ written` outright. DESIGN 3.4 and 3.5 class fields that later
commands write (`edgeChecks` by `COMBINE_VERIFIER`, `supersededBy` by `rule`, `amendments` by
`rule --by build`); demanding this increment write them all would pull four unbuilt commands into it.

**`id` and derived fields are known, not refused.** A field such as `id`, `status` or `surface` that
ingest derives is still a v2 field, so it is accepted on an authored file and then overwritten by
the derivation. The refusal req-010 asks for is for keys that are not v2 fields at all.

**`verification` is refused by name, as DESIGN 3.14 lists it (revision 5).** DESIGN 3.14's recipe
list contains `verification`, which is loop-v1's "how to verify this increment". It is in
`REFUSED_FIELDS` with the home
``"verification" is a recipe field. The plan owns how a change is verified: build/plans/<id>.md.``
and it is in neither `ATOM_FIELDS` nor `INCREMENT_FIELDS`.

The live code uses the same word for something else. `validateAtom` derives an **internal**
`item.verification` from `provenance.verifiedBy`, and the core's verify gate (`ingest.js:288-301`)
reads it. That property is built by the validator, never read from an authored key, and `rowFrom`
never writes it to a row. So refusing the authored key leaves the verify gate as it is. D26's row
check refuses `verification` on a row too. No row written today carries it: the three fixture rows
do not, and `jq` over `design/backlog.json` lists no `verification` key.

**One pinned case is revised on purpose.** `profiles/requirements-v2.test.js:109-126` ("reads a
verification record from provenance.verifiedBy and nowhere else") passes `verification: 'ignored'`
into `validateAtom` and asserts it is ignored. Its first half becomes an assertion that the key is
refused, naming `verification` and the plan. Its second half is kept unchanged: `provenance.verifiedBy`
is still read into `item.verification`. The case's own claim, "nowhere else", is kept and made
stronger. `verificationOf`'s own case at `:140-142` is not touched, because it tests the helper
directly rather than an authored file.

**Rejected: keep it known and ignored** (the earlier revisions' choice). A recipe key would then
pass intake without a word, the silent acceptance req-010's statement forbids. And the reason it was
kept, a passing case, is exactly the kind of cost argument R8 gives no weight.

### D11 — Solo increments are synthesised by an `expandItems` hook, before ids are assigned

The core gains `expandItems({ items, existing, profile, context })`, called after `readItems`,
returning the item list the rest of the pipeline sees. Parity and atoms return `items` unchanged.

The increments collection returns the authored items plus one synthesised item per **adopted** atom
that no authored increment claims:

```
key:        solo--<root atom key>
file:       null
members:    [<the atom's id>]
why:        the atom's why
title:      absent            (C-062: rendered from the member at read time)
outcome:    absent            (C-062)
class:      derived (D14 below)
milestone:  null
dependsOn:  []                 (then lifted, D12)
sequence:   null
checkpoint: null
size:       derived
combination: null
edgeChecks: []
```

A claim is matched on the atom's **id**: an authored `members` entry is normalised through
`context.atomTable`, which holds every existing atom's key **and** its id (D5).

**Correction to this plan's previous revision, recorded because an auditor was right.** The earlier
D11 said an entry matching neither "is left alone, so the dangling refusal in `resolveReferences`
still fires". It did not fire for an **id**-shaped entry: `resolveReferences` short-circuited on
`looksResolved` and never looked the id up (`ingest.js:139-141`), so `members: ["req-999"]` was
written to the row, claimed nothing, and let the atom it meant to claim take a solo — a saved backlog
holding a dangling reference, which req-012's statement forbids. D5.1 closes it: with
`verifyIds: true` on `members`, an id-shaped entry naming no atom is refused before any claim is
counted.

**Order, stated precisely.** `expandItems` runs before `assignIds` and `resolveReferences` (D4), so
the synthesiser does see the raw authored entry. An entry in neither table claims nothing there, and
a spurious solo may be built in memory — and then `resolveReferences` refuses the run before any id
is used and before anything is written, so no backlog is ever saved holding it. The A case asserts
both halves: the refusal names the file, the field and the entry, and `backlog.json` on disk is
unchanged.

**No `origin` field.** An earlier revision of this decision put `origin: 'solo'` on the synthesised
item. DESIGN 3.5's field table has no such field, and the G test ("every field `rowFrom` writes is
in `INCREMENT_FIELDS`") would then force an unDESIGNed field into the class map. A solo is already
identifiable two ways on its written row — its key begins `solo--`, and its `combination` is null —
so the synthesiser carries the flag only in memory, as a local, and writes nothing extra.

**Why before ids:** a solo must take an `inc-*` id from the same `assignIds` pass as an authored
increment, and must keep it, which is exactly what keying on the identity field buys.

**Why only adopted atoms:** req-013's statement and falsifier both say "adopted". A `proposed` atom
is not yet in scope; giving it an increment would put unverified work in the build order.

**A `proposed` atom named by an authored increment is not refused.** req-013 constrains adopted
atoms only. The buildability rule (DESIGN 3.9 rule 2, `tim backlog next`, inc-008) is what withholds
an increment whose member is not adopted.

### D12 — A solo's key is built from the root atom, resolved through `supersededBy`

`rootKeyOf(atomRow)` walks the inverse `supersededBy` chain — from an atom, to any atom whose
`supersededBy` names it — with a visited set, and returns the key of the earliest atom in the chain.
A solo is keyed `solo--<that key>`. An authored `members` entry naming an atom that has since been
superseded resolves **forward** to the survivor's id, so the member is swapped while the key, and
therefore the id, stand still.

**The swap applies only to an increment that has neither started nor been ruled on (revision 4).**
The forward resolution runs for every increment, solo or combined, but its result then meets D29's
regroup check like any other change of members. On a started or ruled increment the resolved member
set differs from the row's previous `members` (the survivor's id replaces the superseded one), so
ingest refuses the run and names the increment. That is deliberate:

- DESIGN 3.7 and 4.3 say `rule` "refuses an effect on a member of a started or done increment
  unless the decision carries `reopens: true`", and with `reopens` it "creates a variant atom and a
  follow-up solo increment that depends on the done one, and leaves the done increment … untouched".
  So a legitimate ruling never supersedes a member of started or done work. A `supersededBy` on such
  a member arrives only from a hand edit or from a `rule` bug, and ingest refusing it is the second
  line of the same defence.
- DESIGN 4.1 ("A ruled or started item cannot be struck, regrouped or **silently rewritten**") names
  the silent swap outright, and DESIGN 5.7 says "A started increment is never regrouped".
- No deadlock follows for the `reopens` flow. If `reopens` set `supersededBy` on the done member,
  the follow-up solo would be keyed `solo--<root key>`, which is the done solo's own key — a
  collision DESIGN cannot intend. So `reopens` leaves the done member unsuperseded and the follow-up
  solo is keyed from the variant. §5 records this as a constraint on inc-009's `rule`.

**Rejected: skip the forward walk on a started or ruled increment and keep the old member
silently.** It would accept the run while the backlog holds a started increment whose member is a
`superseded` atom, and nobody would be told. A refusal names the increment and the atom, and the
person decides.

**Why this is in scope:** req-011's statement is "An atom or increment MUST keep its id for life,
even when its key, **members** or position change", and C-054 and DESIGN 4.4 name this exact
mechanism ("A test rules a variant onto a solo member and onto a combined member and asserts both
increment ids are unchanged"). It is the only reading of req-011 under which "members change" means
anything.

**How it is proved without `rule`:** `rule` is unbuilt (inc-009). The test writes the supersession
into the backlog rows directly — the same way the existing "refuses `--replace` while any atom has
moved off proposed" case writes a status — then re-ingests and asserts the increment's id and key
are unchanged and its member is the survivor. Every such case uses an **unstarted `todo`**
increment, solo and combined. Sibling cases do the same to a started solo and to a `done` combined
increment and assert the refusal (D29).

**Cycle guard:** a `supersededBy` chain that loops back on itself stops at the visited set and the
walk returns the atom it started from. A cyclic supersession is a `rule` bug, not an ingest input,
and refusing it here would be a refusal with no author to act on it.

### D13 — Every adopted atom is counted, and a `checkRows` hook refuses a double claim

The core gains `checkRows({ rows, context, profile })`, called after the cycle check and before the
write. Parity does nothing. The increments collection tallies every `req-*` id across every
row's resolved `members`, restricted to atoms that are adopted, and refuses any id whose count is
not exactly 1, naming the atom's key and every increment that claims it.

**Atoms gains `checkRows` too, guarding the other direction.** `--replace` renumbers every atom by
its new position, so an id an increment's `members` already claims can vanish outright (its file
removed from `distil/atoms/`) or survive as a bare string while now pointing at a completely
different atom. Atoms' `context` reads the claim from the *existing* backlog's `increments[]`,
before the rebuild — `claimsByAtomId` (every claimed atom id, mapped to the increment keys claiming
it) and `claimsByAtomKey` (the same claim keyed by the atom's *key*, carrying its pre-rebuild id).
Its `checkRows` refuses in two cases: a claimed id absent from the rebuilt rows ("put the file back,
or clear the ruling first"), and a claimed key whose id has changed under `--replace` ("re-run
without `--replace`, or run the increments pass again afterwards so the claim tracks the new id").
Both name the atom's key and every increment that claims it — the same messaging contract as the
increments-side double-claim refusal below — and both are proved end to end in
`ingest.requirements-v2.test.js`, not through a standalone unit test: `checkRows` here is a closure
over `requirementsV2`, unlike the increments side's exported `checkOneIncrementPerAtom`.

With solos synthesised (D11) the zero case cannot occur, so the live refusal is the double claim.
The exported function `checkOneIncrementPerAtom` is unit-tested in both directions, and the ingest
path is tested end to end.

**"the strict check passes" (req-013 ac-1).** DESIGN 3.12 attributes this check to
`tim backlog check --strict`. That command is not built here: DESIGN 4.2's `check` also carries the
recipe and executor prose lint (inc-007, req-021), P11's five layer-chain rules (inc-011, req-115,
req-116), the credential lint, the header refusals and the `consumes` cycle — scope no member atom
of inc-005 asks for, and a blocking objection class under L1. The check req-013 names runs inside
`ingest --increments`, where it guards the write, and its result is **observable** rather than
merely non-throwing: the ingest summary carries
`membership: {adopted, covered, solo, combined}`, so "the strict check passes" is a number a test
and a person can read. §5 names `check` as the later command that will call the same exported
function.

### D14 — An increment is protected when it has started or been ruled on, and not otherwise

The increments definition's predicate is:

```js
const RULED_STATUSES = new Set(['deferred', 'dropped', 'done'])

isRuled: (row, context) =>
  context.startedIds.has(row.id) || RULED_STATUSES.has(row.status)
```

and the core's `ruled()` passes `context` through. Parity's and atoms' predicates ignore the second
argument and are unchanged. `RULED_STATUSES` is a named constant in
`requirements-v2-increments.js`, beside the status enum.

The predicate is keyed on req-014's own two words — **started** (a recorded build attempt, D15) or
**ruled** (a status only a decision or the build loop can put there) — rather than on "not `todo`".
DESIGN 3.9's increment enum is `todo, blocked, deferred, dropped, done, superseded`, and each status
is placed by who sets it:

| Status | Set by (DESIGN 3.9) | Ruled? | Why |
|---|---|---|---|
| `todo` | ingest, `rule` | no | The born state. A `todo` row that a decision re-opened is covered by `startedIds` if it has an attempt, and is otherwise exactly as regroupable as a born one |
| `blocked` | **"Derived: an open must-answer question in `needs`, or a `disputed` member"** — ingest, `rule` (recomputed) | **no** | A derivation, not a ruling. D21 writes `statusNote: null` on every born row, so a born-`blocked` increment carries no decision and no reason. Protecting it would refuse the very regroup DESIGN 3.12 describes ("When a later combine groups it, the solo increment becomes `superseded` if it has not started") and refuse `--replace` over work nobody has touched |
| `deferred` | `rule` only | yes | Only a decision puts it there, and `statusNote` names that decision |
| `dropped` | `rule`, ingest | yes | A ruling that it will never be built; the row is the record of that ruling. Its file going away is refused with the existing "put the file back, or clear the ruling first" message, exactly as a `dropped` atom's is today |
| `done` | `status`, `rule` | yes | Either built or resolved by a decision; DESIGN 3.9 forbids any transition back |
| `superseded` | ingest | **no** | Written **by** a re-combine to a row that has no file. Protecting it would make ingest refuse its own output on the very next run. No row reaches this status in this increment (§5, inc-036), and the exclusion is recorded now so inc-036 does not inherit a self-deadlock |

**Correction to this plan's previous revision, recorded because an auditor was right.** The earlier
D14 used `row.status !== 'todo'` and justified folding `blocked` in on the grounds that `blocked` and
`deferred` "got there by a derivation or a ruling that named a reason (`statusNote`, a decision)".
That is true of `deferred` and false of `blocked`: DESIGN 3.9 calls `blocked` "Derived" and sets it
from ingest, and this plan's own D21 writes `statusNote: null` on every born row. So a born-`blocked`
increment — reachable whenever a member carries a `needs` entry (D28) or has status `disputed` — was
neither started nor ruled, yet `ruled()` (`ingest.js:182-183`, used at `:227` for `--replace` and
`:259` for dropped rows) would have refused to let a re-combine drop it and refused `--replace` over
it. No atom asks for that refusal, and DESIGN 3.12 describes the opposite.

**What the predicate decides, and what uses it.** The predicate answers *which* increments are
protected: started means any status with a recorded attempt; ruled means `deferred`, `dropped` or
`done`. The statement then names three acts that must be refused for a protected increment, and
each act has its own guard:

| Act in req-014's statement | Guard | Where |
|---|---|---|
| **strike** or **drop** (its file goes, or a re-combine leaves it out) | `ruled(dropped, …)` | existing, `ingest.js:259` |
| rebuild from scratch (`--replace` would renumber and so strike it) | `ruled(existingRows, …)` | existing, `ingest.js:227` |
| **regroup** (its file stays but its resolved `members` change) | D29's regroup check | new, in the rows loop |

**Correction to this plan's previous revision, recorded because an auditor was right.** Revision 3
said the predicate plus the two existing guards were "every case the statement names, and no case it
does not". They were not: they covered strike and drop only. A started increment whose file stays
while its `members` change went through `refreshed` (`ingest.js:171-180`) with no check, and D12's
forward resolution could swap a member on a `done` increment silently. D29 is the missing third
guard, and only with it does this plan meet the whole statement.

**Born status.** A new increment is born `blocked` when its derived `needs` is non-empty or any
member is `disputed`, and `todo` otherwise (DESIGN 3.9). Both halves are now reachable from rows the
writer itself produces: the `needs` half through D28, the `disputed` half through an authored
increment naming a `disputed` atom (D11 does not refuse a non-adopted member). **Status is derived at
birth only**: on a refresh the existing row's status survives, because `status` is not in `rowFrom`
and `refreshed` spreads the old row first. Recomputing a status over a ruling is `rule`'s job
(DESIGN 3.10, inc-009), and recomputing it here would overwrite a ruled `deferred` with a derived
`todo`.

**Verification.** The increments definition sets `requireVerification: () => false`. The survey's
mismatch 1 (DESIGN 4.1 says requirements-v2 requires verification "always, with the registered-run
guard") is about **atoms**, is unchanged by this increment, and its home is inc-007 (req-017 to
req-022) with the registered-run guard C-053. An increment has no verification record in DESIGN 3.5
at all; `edgeChecks` is written by `COMBINE_VERIFIER`, which is not a record of having verified the
increment. Stating `false` here is the honest value, not an inherited default.

### D15 — A recorded build attempt is read from `build/state.json`, and this increment pins the one field it needs

New `tim/src/backlog/state.js` exports `startedIncrementIds(statePath)`: an empty set when the file
is absent, otherwise the ids in `state.increments` whose `attempts` is a non-empty array or a number
of 1 or more. `programme.js` adds `paths.state` (`<workarea>/build/state.json`) for every

**Why it must read a file:** req-014 ac-1 is "Given an increment with a **recorded build attempt**".
The build loop starts an increment, records the attempt, and leaves the row at `todo` until it
finishes; an increment that has been started but not finished is exactly the case the criterion
names, and the row carries no field that says so. DESIGN 3.1 puts attempts in `build/state.json` and
DESIGN 3.2 gives the reason they are not on the row. Reading it is the criterion, not scope creep.

**What is pinned, and what is not.** This increment pins one shape —
`{increments: {"<inc id>": {attempts: <array|number>}}}` — and reads it. It writes nothing, takes no
lock and defines no other field. inc-006 (req-015, req-016, req-023) owns state **writes**, the lock
and the replay rules, and is free to add fields; it must keep `increments[].attempts` readable, and
§5 says so. A malformed `state.json` surfaces through `readJsonFile`'s existing PARSE message, which
names the path.

**Rejected:** treating any non-`todo` status as the record. It would leave the started-and-still-
`todo` case — the one the criterion describes — undefended, and would make req-014 a restatement of
the drop refusal inc-004 already shipped.

### D29 — A started or ruled increment whose members would change is refused (the regroup guard)

*(Numbered last, placed here because it is the third guard D14's predicate serves.)*

**The rule.** In `runIngest`'s rows loop, when an item has a `previous` row (a refresh, not a birth,
and not `--replace`), `definition.regroupField` is set, and
`definition.isRuled(previous, context)` holds, the core compares the **set** of ids in
`previous[regroupField]` with the set on the row it has just built. If they differ, the row goes on a
`regrouped` list as `{id, key, before, after}`. After the loop, and after the frozen-field check,
a non-empty list raises
`TimError('USAGE', definition.messages.regrouped(list))`. Nothing is written, `--dry-run` included.

- `regroupField` is a new definition field. `DEFAULT_HOOKS` in `profiles/index.js` sets it to
  `null`, so `parity-v1` and atoms are untouched; the increments collection sets `'members'`.
- The comparison is on the **built** row, so it is after `resolveReferences` (keys become ids) and
  after the forward `supersededBy` resolution (D12). A member written as a key in one run and as an
  id in the next is the same member and is not a regroup. A reorder of the same members is not a
  regroup either: the comparison is on sets, because `members` has no order DESIGN 3.5 gives meaning
  to.
- A solo's `members` are synthesised (D11), so the same check covers a started solo: if its atom is
  superseded, the swap changes its set and is refused. A started solo *losing* its atom to an
  authored increment is not a regroup of the solo but a drop, because the solo is no longer
  synthesised, and the existing drop guard refuses it (§1, req-014 ac-1).
- **A member moving between increments** is refused through whichever end is protected. Take
  started A = `[x, y]` and unstarted B = `[z]`. Moving `y` to B makes A `[x]`, so A is refused. Moving
  `z` to a started increment makes that increment gain a member, so it is refused too. Only when
  neither end is started or ruled does the move go through.
- **Message**, in GDS plain English, one line per increment:
  ``Cannot regroup inc-001 (core-and-registry): it has started or been ruled on. Its members would change from req-001, req-002 to req-001. Put its members back as they were in distil/increments/, or rule a follow-up increment with --reopens.``
  The key, the id and the before and after lists are all named, as the objection asked.

**Why a definition field and not a new hook function.** The check is the same for any collection
that has a membership field: "protected, and the set changed". A field name is the only
profile-shaped part. A hook function would invite each profile to write its own comparison, which is
the drift req-008 exists to stop.

**Why the core, and not `checkRows`.** `checkRows` (D13) sees only the new rows. The regroup check
needs `previous` and the `isRuled` verdict on it, and both are already in hand at the one line in the
rows loop where `previous` is looked up (`ingest.js:271`).

**Why `USAGE`.** It is a policy refusal about the state of work, like the drop refusal it sits
beside, not a malformed file (D16). Through the CLI it exits 2 (`envelope.js:44-47`).

**Why only started or ruled, and not every regroup.** req-011 says an increment keeps its id "even
when its key, members or position change", and DESIGN 3.12 and C-054 say a re-combine regroups
unstarted `todo` and `blocked` increments freely (DESIGN 5.7: "A mid-build re-combine regroups only
unstarted `todo` and `blocked` increments"). So an unstarted `todo` or born-`blocked` increment's
member change is accepted, keeps its id, and is proved so. req-011 and req-014 do not conflict: for
unstarted work the members change and the id stands; for protected work the change is refused, so
the id trivially stands.

**Rejected: comparing member lists in order.** A combiner that writes `[y, x]` for `[x, y]` has
changed nothing a build depends on, and refusing it would stop a run over a cosmetic edit.

**Rejected: comparing root sets (DESIGN 4.4's matching rule) rather than id sets.** Root sets are
how a re-combine *matches* a group across runs, so that a variant swap keeps the id. They are the
wrong test for *protection*: a swap on a started increment keeps the root set and still silently
rewrites started work, which DESIGN 4.1 and 4.3 forbid. D12 records why that swap must be refused.

**Rejected: warning and carrying on.** req-014's statement is "MUST refuse".

### D28 — The atoms pass persists an atom's `needs`, at birth

*(Numbered last, placed here because D14 and D21 both rest on it.)*

**The gap, as the second audit found it and this session re-confirmed.** `validateAtom`
(`profiles/requirements-v2.js:194-213`) returns a fixed object literal with no `needs`, and
`requirementsV2.rowFrom` (`:253-268`) and `bornExtras` (`:269`, `() => ({})`) never write one. The
tracked fixture's rows carry `acceptance, dependsOn, falsifiedBy, id, key, kind, provenance,
relatedTo, slice, sources, statement, status, surface, title, why` — no `needs`. So an increments
pass that unions its members' `needs` would always union nothing, an increment could never be born
`blocked` from a question, and any test of that path could only pass against a hand-written row.
Worse, once D8 makes `needs` a **known** atom field at intake, an authored atom carrying
`needs: ["q-1"]` would pass the unknown-key walk and then be silently dropped by `validateAtom`'s
literal — the exact silent-drop the survey's §2.2 names.

**The change.** Three lines in `profiles/requirements-v2.js`:

- `validateAtom` checks `raw.needs` is a list of non-empty strings when present (refusing otherwise,
  naming the file and the field) and returns `needs: stringArray(raw.needs)`.
- `requirementsV2.bornExtras` becomes `({ item }) => ({ needs: item.needs })`.
- `ATOM_FIELDS.needs` is `{class: 'requirement', persisted: true}` (DESIGN 3.4 classes it
  `requirement`; DESIGN 3.14 lists it under `state`; the 3.4 table is the per-field one and is used,
  and the disagreement is recorded for inc-040's documentation sweep).

**Why at birth, and not in `rowFrom`.** DESIGN 3.4 says an atom's `needs` is written by "reconcile,
verify, `rule`", and DESIGN 3.10 says "`tim backlog rule` clears the need and recomputes the status in
the same write". If `needs` were in `rowFrom`, `refreshed` would fold the authored file's `needs`
back over the row on every ingest (`ingest.js:171-180`), resurrecting a question a ruling had
cleared — a silent loss of ruled work, which is what req-014 exists to stop. At birth only, the
authored value seeds the row, and from then on the row is `rule`'s; `refreshed` spreads the existing
row first, so whatever a ruling wrote survives. It is the same rule this plan applies to an
increment's `status` (D14) and the one the core already applies to `statement` (frozen).

**Consequence stated, not hidden:** an authored atom file whose `needs` changes after its first
ingest has that change ignored on the row. DESIGN 3.4 does not list the author among `needs`'
writers at all, so the authored value is a seed for a newborn row, and a change after birth belongs
in a ruling. A pair of B cases pins it: a born atom carries its authored `needs`, and a refresh with
a different authored `needs` leaves the row's value as it was.

**Why this is in scope.** No member atom's criterion names `needs`. But DESIGN 3.5 makes `needs` a
required increment field ("yes, may be empty") that ingest derives, and DESIGN 3.9 rule 3 makes it
one of the five conditions `tim backlog next` reads (inc-008). An increment row written by this
increment either carries the true union or carries a lie; there is no third option that ships the
collection. And D14's born-`blocked` rule is DESIGN 3.9's own definition of the status the predicate
must *not* protect — which the third objection shows is only testable if the status is reachable.

**Rejected: drop the `needs` derivation and the `needs` half of the born-status rule.** The auditor
offered it as the other acceptable option. It would write increment rows either missing a
DESIGN-required field that inc-008 reads, or always holding `[]` whatever the members say — and
inc-008 would then build an increment whose member has an open must-answer question. A known defect
handed to a later increment is not a trade-off worth making.

**Rejected: add `needs: z.array(z.string())` to `atomSchema`'s declared shape.** Every row written
before this increment has no `needs` key and would start failing `parseAtom`, with no migration to
add it. The field stays under the catchall on the row schema, like every other field a later
command writes; D9.1's G test is what guarantees the writer persists it, and D21 reads it
defensively.

**Not resolved here:** `needs` entries are `q-*` ids, and there is no questions ledger to resolve
them against (inc-009). They are carried as given; D5 records it.

### D19 — `frozen` may be null, and an increment freezes nothing

`born`, `refreshed` and the frozen-change check in the core become conditional on
`definition.frozen`. The increments definition sets `frozen: null`.

**Why:** the freeze is "the oracle every later rewrite is checked against" (DESIGN 3.4, C-055), and
DESIGN names `statement` on an atom as the only one. An increment's `outcome` is a slot
`tim backlog set` is documented to rewrite (DESIGN 4.2), so freezing it would put two commands in
direct conflict, and a solo increment stores no outcome at all.

**Rejected:** freezing `outcome`, and inventing a composed frozen field so the hook can stay
mandatory. Both add a refusal DESIGN does not ask for.

### D20 — Refusals name the authored file, or the key when there is no file

`resolveReferences` and the intake helpers name `item.file` today. A synthesised solo has no file, so
the core's `fail` call becomes `fail(item.file ?? definition.identityOf(item), …)`. A solo's members
are already ids and always resolve, so this path cannot fire for one; the fallback exists so that a
future synthesised item cannot produce a message beginning "null:".

### D21 — What an authored increment file may and must carry

Required (refused by name when missing or empty): `key`, `title`, `outcome`, `why`, `members` (at
least one), `class` (from `feat, fix, chore, refactor, test, docs`), `size` (`{class: S|M|L, basis}`),
`combination` (an object with a non-empty `why` and an array `rules`). Required to be **present**,
and may be null: `milestone`, `checkpoint` (null, `halt-after` or `walkthrough`).

Optional: `dependsOn` (defaults `[]`), `sequence` (defaults null), `edgeChecks` (defaults `[]`), and
any other v2 increment field, which is accepted and then overwritten by its derivation.

Derived by ingest and written to the row: `id`, `surface` (the union of the members' `surface.repos`
and `surface.area`), `dependsOn` (authored plus lifted, D22), `needs` (the union of the members'
`needs`, deduplicated and sorted), `status`, `doneBy` (null), `statusNote` (null).

**Where the members' `needs` comes from.** From each member's atom row, which carries `needs` because
D28 makes the atoms pass write it. A member row with no `needs` key — any row written before this
increment lands, which today is every row of the tracked fixture — reads as `[]`
(`Array.isArray(row.needs) ? row.needs : []`), so the derivation never throws on an older backlog.
Only a member that is not `superseded`, `parked` or `rejected` contributes, matching DESIGN 3.5's
"the union of the members' **open** `needs`"; whether a question is still open is read from the
questions ledger, which does not exist yet (inc-009), so every entry on a contributing member counts
as open here and §5 records it.

**`needs` is recomputed on a refresh; `status` is not.** `needs` on the increment row is recomputed on every
ingest (DESIGN 3.5: "recomputed on every ingest and ruling"), so it lives in `rowFrom`. `status` is
not (D14), so a refresh does not flip a `blocked` row to `todo` when a member's `needs` empties —
that recompute is `rule`'s (inc-009). The A case pins both behaviours.

**`combination` is validated shallowly.** `why` and `rules` are checked; `risk`, `attributability`
and `reverseEffects` pass through. No member atom's criterion reads them, and `check --strict`
(inc-007, inc-011, C-027) is where a combination rule keyed on repos is refused.

**`class: test` is not cross-checked against member kinds here.** C-025's rule ("`test` only when
every member is `hygiene`") is a `check` rule in DESIGN 4.2, and inc-011 owns the layer rules it
sits among.

### D22 — Lifting is derived here, because a cycle refusal over authored text is not a guard

For each increment, each member atom's `dependsOn` atom ids are mapped to the increment that owns
them; an edge pointing inside the same increment is dropped, one pointing outside is added to that
increment's `dependsOn`. Authored and lifted edges are unioned and deduplicated, and the increment's
own id is never added.

**Why, when no criterion names lifting:** req-012 ac-1 refuses a cycle in increment `dependsOn`, and
DESIGN 3.5 names ingest as that field's writer. If `dependsOn` were only ever what a combiner typed,
the refusal would be a check on authored text rather than on the graph the build loop reads, and the
one real source of increment-level cycles — two atoms in different increments depending on each
other — would pass unexamined. It is derived from data this pass already has in hand.

**Rejected:** deferring lifting to inc-036 (`Atoms combine into increments under rules, checked and
re-derivable`). That increment owns re-combination and the candidate signals; leaving `dependsOn`
underived until then would ship a cycle refusal that cannot see the cycles req-012 exists to catch.

**Not lifted here:** `edgeChecks` for cross-repo lifted edges (DESIGN 3.5, C-025) — inc-011.

### D23 — A solo's class and size are derived by a stated rule

- **class:** every member `hygiene` → `chore`; otherwise `feat`. A requirement atom describes
  behaviour that does not exist yet, which is a feature; a `hygiene` atom adds no behaviour (C-032).
  `test` is not used: C-025 reserves it for a grouping whose members are all hygiene, which is a
  combiner's judgement, not a synthesiser's.
- **size:** `class` by acceptance-criteria count across the members — 3 or fewer `S`, 4 to 8 `M`,
  more `L` — with `basis` "<n> criteria, 1 atom". The thresholds are named constants.

Both are recorded as this increment's choices: DESIGN 3.5 says class is "derived from member kinds"
and size is "requirement-level proxies" without giving the arithmetic.

### D24 — A missing `distil/increments/` is refused; an empty one is not

`readItems` keeps its NOT_FOUND refusal, with a message naming the directory and saying an empty
directory is correct when every atom is solo. An existing but empty directory ingests to all solos.

**Why:** the atoms pass already refuses a missing directory, and silently reading a missing
directory as "no groupings" would turn a mis-pointed workarea into a backlog of solos that looks
right.

### D25 — `ingest --increments` refuses when the programme has no atoms yet

The increments `context` throws `TimError('USAGE', …)` when the existing backlog is absent or its
`requirements[]` is empty, naming `tim backlog ingest <p> --atoms` as the pass to run first. Members
resolve against atoms, so without them every message would be a dangling-reference refusal that
blames the combiner for a missing first pass.
