### D4: `commitWrite` in detail: optimistic concurrency under a short lock

```
commitWrite({ path, body, format: 'json' | 'jsonl', validate, expectedSha, command,
              opId, fingerprint, opsLogPath, result, retryDelaysMs = LOCK_RETRY_DELAYS_MS })
  -> { replayed: false, sha256, bytes, notes: string[] }
   | { replayed: true, result }
```

The steps, in order:

1. **Parse after, before any effect.** Parse `body` (the whole text for `json`, each non-empty line
   for `jsonl`), then call `validate(parsed)`. A failure throws and nothing is touched. No folder is
   created and no lock is taken, so an invalid write leaves the file system exactly as it was
   (req-023 ac-1).
2. **Lock.** Create the target's folder (`mkdirSync` recursive), then acquire the lock (D6).
3. **Replay check under the lock.** When `opId` is given, look it up in the operation log (D7).
   When it is found, release the lock and return `{replayed: true, result: <recorded result>}`.
   Nothing is written.
4. **Lost-update check under the lock.** Read the file's current sha, or `null` when it is absent.
   When `expectedSha !== undefined` and the current sha differs, throw
   `TimError('LOST_UPDATE', …)` and write nothing (req-015).
5. **Replace the file.** Write the unique temp file (D3), then `renameSync` it over `path`.
6. **Record the operation.** When `opId` is given, append one line to the operation log:
   `{opId, fingerprint, command, path, sha256, result, at}`.
7. **Release the lock** in `finally`, on every path after step 2.

**The version checked is the version read.** Every writer passes
`expectedSha = expectSha ?? versionRead.sha256`. Without `--expect-sha`, a write is refused
whenever another write landed between this command's read and its rename, so two writes that read
the same version cannot both succeed. That is req-015 ac-1 with no flag at all. `--expect-sha` lets
a caller name the version it read in an **earlier** command, which is DESIGN 4.3's contract and
what the e2e witness uses to make "read the same version" deterministic across two processes.

**One residual window.** A crash between step 5 and step 6 leaves a write applied but not logged,
so a replay of that op id would apply again. It is refused only if the file moved, because the
replay reads the new version. Rejected alternative: recording before the rename, which on a crash
leaves an op recorded that never applied, which is worse. This is recorded in §5 as a known limit.

### D6: The lock, `tim/src/backlog/lock.js`

- **Exclusive creation with content.** Write `{pid, host, command, opId, at}` to a unique temp
  file, then `linkSync(temp, lockPath)`, then unlink the temp file. `link` fails with `EEXIST` when
  the lock exists, so the lock appears atomically and whole. This avoids the half-written lock file
  that `openSync(…, 'wx')` followed by a write can leave. `at` is `new Date().toISOString()`:
  DESIGN 4.3 has tim stamp its own machine events.
- **Live or stale.** A lock is **stale** only when its `host` equals `os.hostname()` and
  `process.kill(pid, 0)` throws `ESRCH`. `EPERM` means the process is alive. A lock from another
  host, or one that will not parse, is treated as **live**, because tim cannot prove it dead.
- **Breaking a stale lock** is race-safe:
  1. Rename the lock to `.<lock>.<pid>.<random>.stale`.
  2. Re-read the renamed file.
  3. When it is the same stale content, unlink it and create our own lock.
  4. When it is not (another process replaced it in between), link it back to the lock path, unlink
     our renamed copy, and treat the lock as live.

  The note `Broke a stale lock on <path> left by pid <pid> (<command>) at <at>.` is returned for
  the result's `notes`.
- **Retry.** On a live lock, retry after each of `LOCK_RETRY_DELAYS_MS = [100, 200, 400]`. That is
  three retries with back-off inside tim (DESIGN 4.3: "a committed tool polling, not an agent
  sleeping"). tim is synchronous here, so the sleep is `Atomics.wait` on a one-slot
  `SharedArrayBuffer`. After the last retry it throws `TimError('LOCKED', …)`. The message names
  the path, the holder's pid, host, command and `at`, and says:
  `Nothing changed. Run the same command again.`
- **Release** unlinks the lock path. It is called only by the holder, in `commitWrite`'s `finally`.
- `retryDelaysMs` can be passed in so tests run in milliseconds. It is configuration, not a mock.

**Survey item 13** (the bash lock is a `mkdir` directory polled 600 times): DESIGN's own 4.3
spec, a file created exclusively holding `{pid, host, command, opId, at}` with three retries and
then exit 4, is followed. The claim "journey-builder's lock in tim form" means the same idea
(atomic exclusive creation, released on exit), not the same mechanism. The file form is chosen
because it lets a stale lock be recognised and broken, which the directory lock cannot do.

### D7: The operation log, `tim/src/backlog/ops-log.js`

- **The file.** `.backlog-ops.jsonl` in the programme workarea (DESIGN 3.1) holds one JSON object
  per line. Every write in the programme (backlog, state, journal) shares the one log, because an
  op id names one operation, whatever the file.
- **`findOperation({opsLogPath, opId, fingerprint})`** returns the recorded entry or `null`. An
  entry with the same `opId` and a **different** `fingerprint` throws `TimError('USAGE',
  'Operation id "<id>" was already used for a different write (<recorded command>). Use a new
  operation id.')`. Otherwise a mis-assigned op id would silently swallow a real write, which is
  the lost write req-015 forbids. A line that will not parse throws `PARSE`, naming the file and
  line number. Lines are never skipped silently.
- **`recordOperation({opsLogPath, entry})`** appends with `appendFileSync`, one line under 4 KB in
  the common case, relying on `O_APPEND`. It is called while holding the target's lock.
- **The fingerprint** is `sha256Of(JSON.stringify(command-shape))`. For ingest the shape is
  `{verb: 'backlog ingest', programme, collection, replace, target}`. For state set it is
  `{verb: 'backlog state set', programme, id, field, value}`. For state note it is
  `{verb: 'backlog state note', programme, id, stage, by, note}`.
- **Fast path.** Each writer calls `findOperation` first, before reading anything else, and returns
  the recorded result when it is found. `commitWrite` checks again under the lock (D4 step 3), so
  two concurrent replays of one op id apply at most once.
- **Replays win over stale versions.** The replay check comes before the lost-update check, because
  a replay always carries the sha it was issued with.

### D9: The state schema, `tim/src/backlog/state-schema.js`

No schema for `build/state.json` exists yet (survey item 12: there is no `schema.js` under
`tim/src/backlog/`). This increment writes one with zod 4, strict where a wrong path must be
caught. That is req-023's "why": "hand-written edits landed on the wrong paths".

```
INCREMENT_ID = /^inc-\d{3,}$/
attempt       = z.looseObject({ n: z.number().int().positive() })
incrementState = z.strictObject({
  phase:    z.string().trim().min(1).optional(),
  attempts: z.union([z.number().int().nonnegative(), z.array(attempt)]).optional(),
  ticket:   z.string().min(1).nullable().optional(),
  branch:   z.string().min(1).nullable().optional(),
  plan:     z.string().min(1).nullable().optional(),
  heads:    z.record(z.string().min(1),
              z.strictObject({ sha: z.string().regex(/^[0-9a-f]{40}$/),
                               branch: z.string().min(1), dirty: z.boolean() })).optional()
})
stateSchema = z.strictObject({
  schemaVersion: z.literal(1).optional(),
  increments: z.record(z.string().regex(INCREMENT_ID), incrementState)
})
SETTABLE_FIELDS = ['phase', 'attempts', 'ticket', 'branch', 'plan', 'heads']
```

- **`attempts` accepts both an array and a number,** exactly the two forms `startedIncrementIds`
  reads (inc-005 D15 and `state.test.js`). The reader stays as it is. An attempt entry is loose
  beyond `n`, because the stage machinery (inc-014 and inc-017) defines its other fields.
  `schemaVersion` is optional so that the hand-written fixtures already in the tests
  (`{increments: {...}}`) stay valid. A writer stamps `schemaVersion: 1` on every file it writes.
- **`heads` follows DESIGN 4.2's `heads` row:** `{sha, branch, dirty}` per repo key.
- **Fields later increments add.** `holds` (inc-008, req-026), commits, PRs, CI, audits and
  acceptance (inc-021, inc-022) and registered build runs (inc-017) are **not** in the schema yet.
  Strict means a file carrying them is refused, and each of those increments adds its own field
  with its own writer. Rejected: a loose schema, which cannot catch a wrong path, and so cannot
  meet the atom's "why".
- **Validation errors** throw `TimError('PARSE', …)`. That follows inc-005 D16's precedent:
  `parseV2Backlog` reports schema failures as PARSE, and PARSE exits 1, which is DESIGN 4.3's
  "refused by validation". The message names the file, the dotted path of the first issue and what
  is wrong, in plain English, for example:
  `build/state.json would not be valid: increments.inc-001.heads.workspace.sha must be a 40-character commit sha. Nothing changed.`
  Rejected: a new `INVALID` code, because precedent already covers it.

### D11: The CLI shape: `state set` and `state note` subcommands; `--value`, not `--json v`

DESIGN 4.2 writes `state <p> <id> set <field> --json v`. Two facts of the live CLI force a
different shape:

- **Positionals.** commander subcommands precede their positionals, which is the existing
  `registry show <programme>` shape.
- **`--json`.** `--json` is already the global envelope flag that every command must carry
  (`cli-patterns.md`).

So the commands are:

```
tim backlog state set <programme> <id> <field> --value <json> [--op-id <id>] [--expect-sha <sha>] [--json]
tim backlog state note <programme> <id> --file <path> [--stage <s>] [--by <who>] [--op-id <id>] [--expect-sha <sha>] [--json]
tim backlog ingest <programme> … [--op-id <id>] [--expect-sha <sha>]
```

Each command's options are validated with a zod schema before any read (`cli-patterns.md`). A bad
`--value` (not JSON), an unknown `<field>`, a bad id shape, a bad op id or a bad sha is refused
with USAGE and exit 2. The field whitelist is `SETTABLE_FIELDS`. An unknown field is refused naming
the ones allowed.

**`hold`, `release` and `retry`** from DESIGN's `state` row are inc-008's (req-026).

**`state` needs a requirements-v2 programme.** A parity-v1 programme is refused with USAGE:
`"<p>" is a parity-v1 programme. Run state is only kept for requirements-v2 programmes.`
**The id must name an increment in the programme's `backlog.json`.** Otherwise it is refused with
NOT_FOUND, exit 2. An absent backlog is also NOT_FOUND.

**Results** (DESIGN 4.3: "every write prints the changed paths with their old and new values"):

- `state set`: `{path, id, field, before, after, sha256, notes}`.
- `state note`: `{path, entry, sha256, notes}`.
- `ingest`: its result gains `sha256` (`null` on a dry run) and `notes` (`[]` unless a stale lock
  was broken). These are additive. No test compares an ingest result whole (checked:
  `grep -rn written` over the backlog and commands tests).

Text mode prints one summary line plus any notes. A replay prints the original result, the same
bytes in `result`, and nothing extra (req-016: "MUST report the original result").

### D12: Exit codes. DESIGN's 3 and 4 are used, in their own constants file

DESIGN 4.3 gives `3 lost update, 4 locked`. `constants/exitCodes.js` already binds 3 and 4 to
`MISSING_DEP` and `USER_ABORT`, and `exitCodes.test.js` asserts every constant in that file is
distinct (survey §3, first mismatch). Adding `LOST_UPDATE = 3` there would break that test, and
with it the file's meaning.

Decision: a new `tim/src/constants/writerExitCodes.js` exports `LOST_UPDATE = 3` and `LOCKED = 4`
with a sibling test. This follows the per-group exit-code file pattern of the dropped inc-001's
`prExitCodes.js`. `exitCodeFor` maps `TimError('LOST_UPDATE')` to 3 and `TimError('LOCKED')` to 4,
with one lookup table in `envelope.js`, `EXIT_BY_CODE = {USAGE: 2, NOT_FOUND: 2, LOST_UPDATE: 3,
LOCKED: 4}`, falling back to 1. That removes the hand-kept `if` the survey's second mismatch names.

Exit codes are per command. `tim auth` exits 3 for a missing dependency, and `tim backlog` exits 3
for a lost update. No `tim backlog` path raises `MISSING_DEP` or `USER_ABORT`, and `exitCodeFor`
never mapped those two to 3 or 4 anyway (they exit 1 through it today). So no command's meaning
changes.

Rejected: new numbers 6 and 7. They would contradict DESIGN 4.3, which inc-017's `advance` and the
workflows will read, for an ambiguity no single command has. `errors.js` gains `LOST_UPDATE` and
`LOCKED` in `VALID_CODES` (survey item 6).

## 1 Criteria map

### req-015 ac-1

> "Given two writes that read the same version of the backlog, when both save, then exactly one is
> saved and the other is refused with a lost-update error."

**How it is met.** Every backlog write goes through `commitWrite` with
`expectedSha = expectSha ?? versionRead`, and the check happens under the lock (D4). The second
save sees a different sha and throws `LOST_UPDATE`, exit 3. The file stays as the first save left
it.

**Proven by:**

- **E1, the e2e witness through the real entry point.** Two concurrent
  `backlog ingest <p> --expect-sha S0 --json` processes, started together with `Promise.all`. The
  test asserts that the sorted exit codes are `[0, 3]`, that the loser's envelope has code
  `LOST_UPDATE`, and that the backlog's sha on disk equals the winner's `result.sha256`.
- **E2, the sequential form of the same criterion.** Ingest with `--expect-sha S0`, which succeeds.
  Add an atom file, then ingest again with `--expect-sha S0`. The second exits 3 with
  `LOST_UPDATE`, and the file's bytes are identical to those after the first run.
- **W3 and W4 (unit).** `commitWrite` refuses a stale `expectedSha` and a file created since an
  absent read.
- **IW1 (`runIngest`, unit).** A `runIngest` whose version was overtaken by a competing
  `commitWrite` is refused, and the file keeps the competing write.
- **The default path (no `--expect-sha`).** `runIngest` passes its own read sha as `expectedSha`,
  which the code review checks against D4. Its behaviour is W3's, since it is the same
  `commitWrite` branch. No deterministic test can interleave a second process between one ingest's
  read and its rename without a test-only hook in production code, and that hook is rejected under
  `tim/CLAUDE.md`'s input and output rule.

### req-016 ac-1

> "Given a ruling written with an operation id, when the same write is replayed, then the ledger
> holds one entry and the command prints the original result."

**How it is met.** D7. The writer looks the op id up first, and again under the lock. A replay
returns the recorded result and writes nothing. The ledger witnessed is `build/journal.jsonl`,
DESIGN's append-only journal. D10 explains why it stands in for the rulings ledger, which is
inc-009's.

**Proven by:**

- **E3 (e2e).** Run `backlog state note <p> inc-001 --file n.txt --op-id r1:inc-001:1:plan:t1:note
  --json` twice. The journal has exactly one line, `.backlog-ops.jsonl` has exactly one entry, and
  the second `result` deep-equals the first, including the original `at`.
- **E4 (e2e, a replay that would otherwise do harm).** Run `state set … phase --value '"plan"'
  --op-id A`, then `state set … phase --value '"implement"' --op-id B`, then replay A. The state's
  phase is still `implement`, the output equals A's original result, and the file's sha is
  unchanged by the replay.
- **E5 (e2e).** `ingest --op-id X`, replayed after an atom file was added, leaves `backlog.json`'s
  bytes unchanged and prints the original result.
- **O2, O3, W5 and W6 (unit).** A fingerprint mismatch is refused. A replay under the lock is
  skipped.

### req-023 ac-1

> "Given a state change that would break the state schema, when it is written, then it is refused
> and the file is unchanged."

**How it is met.** D4 step 1: the whole resulting file is parsed and validated against
`stateSchema` (D9) before any lock, folder or temp file. A refusal is `PARSE`, exit 1, naming the
path.

**Proven by:**

- **E6 (e2e).** `state set <p> inc-001 heads --value '{"workspace":{"sha":"nope","branch":"b","dirty":false}}'`
  over an existing valid state file. The command exits 1 with code `PARSE`, and the message names
  `increments.inc-001.heads.workspace.sha`. The state file's bytes are unchanged, and there is no
  temp or lock file in `build/`.
- **E7 (e2e).** The same bad value with **no** state file exits 1, creates no `build/` folder and
  creates no state file.
- **E8 (e2e, a wrong path).** A hand-edited state file carrying an unknown key
  (`increments.inc-001.phse`) makes any `state set` refuse. This is parse before: the result would
  still be invalid, so the file is unchanged.
- **S1 to S6 (unit, `state-schema.test.js`).**
- **Invariant 5,** on the real registered fixture through `npm run tim`.

**Coverage of the statement beyond ac-1** (run configuration and the phase ledger): see §5. This
increment builds the shared validated `commitWrite`, which demands a `validate` function (it throws
USAGE when none is given, test W8). So no later writer can bypass validation, and `run.json`'s and
`phases.json`'s writers, owned by inc-008 and inc-029, reuse it.

### deferred.md D6 and D7 (findings, not criteria)

- **D6:** all existing ingest tests pass unedited (invariant 1), and `ingest.js` has the named
  helpers (invariant 6).
- **D7:** E9. `backlog ingest <p> --json`, where `distil/atoms` is a **file**, which makes
  `readdirSync` throw `ENOTDIR`, a plain Node error. It prints exactly one JSON line with
  `ok:false`, `errors[0].code === 'UNKNOWN'` and the Node message, and exits 1. EN2 is the unit

## 3 Tests

All tests use vitest, test input and output, run in temp directories (`mkdtempSync`) and assert no
spy calls. No module is mocked. The file system and child processes are the real ones. Timing-
sensitive lock tests pass `retryDelaysMs: [1, 1, 1]`.

### W: `write.test.js`

1. `readVersioned` of an absent file returns `{exists: false, sha256: null, text: null}`. Of a file,
   it returns its exact bytes and `sha256Of` of them.
2. `commitWrite` with a valid body and no expected sha writes the bytes. It returns
   `{replayed: false, sha256, bytes, notes: []}`, where `sha256` equals `sha256Of(body)`. It leaves
   no `.tmp` and no `.lock` in the folder.
3. `commitWrite` with `expectedSha` of an older version throws `LOST_UPDATE`. The message names the
   path and says nothing changed. The file's bytes are unchanged, and there is no temp or lock file.
4. `commitWrite` with `expectedSha: null` (read as absent) over a file that now exists throws
   `LOST_UPDATE`.
5. With `opId` and a log entry of the same fingerprint already present, it returns
   `{replayed: true, result: <recorded>}`. The file's bytes are unchanged, and the log still has one
   line.
6. With `opId` and no entry, the write lands and exactly one entry is appended, carrying `opId`,
   `fingerprint`, `path`, `sha256` and `result`.
7. A body whose `validate` throws is refused with the validator's error. There is no target, no
   folder (the target is in a not-yet-existing subfolder), no temp and no lock.
8. Calling it without `validate` throws USAGE (the core refuses an unvalidated write).
9. A body that is not JSON (`format: 'json'`) is refused with PARSE and nothing is written. With
   `format: 'jsonl'`, a bad line is refused naming its line number.
10. A live lock (held by `process.pid` on this host) with `retryDelaysMs: [1, 1, 1]` throws
    `LOCKED`. The file is unchanged and the foreign lock file is still there.

### L: `lock.test.js`

1. `lockPathFor('/a/backlog.json')` is `/a/.backlog.lock`. `lockPathFor('/a/build/state.json')` is
   `/a/build/.state.lock`. `lockPathFor('/a/build/journal.jsonl')` is `/a/build/.journal.lock`.
2. `acquireLock` creates the lock with `{pid: process.pid, host: os.hostname(), command, opId, at}`,
   where `at` is ISO. `releaseLock` removes it.
3. A second `acquireLock` while the first is held throws `LOCKED` after the retries. The message
   names the holder's pid and command, and says to run the same command again.
4. A stale lock (same host, pid of a child process that has exited: `execa('node', ['-e', ''])`,
   awaited, then its pid used) is broken. The call succeeds and returns one note naming the old pid
   and command.
5. A lock from another host (`host: 'elsewhere'`, dead-looking pid) is treated as live: `LOCKED`.
6. A lock file that is not JSON is treated as live: `LOCKED`, naming the path.
7. After acquire and release, no `.stale` or `.tmp` file is left in the folder.
8. The retry waits: with `retryDelaysMs: [30, 30, 30]` against a held lock, the refusal comes after
   at least 90ms of wall time. This is a binary lower-bound check of the back-off, not a tolerance
   band.

### O: `ops-log.test.js`

1. `findOperation` on an absent log returns `null`.
2. A recorded entry with the same op id and fingerprint is returned.
3. The same op id with a different fingerprint throws USAGE, naming the op id and the recorded

4. A log line that is not JSON throws PARSE, naming the file and line 2.
5. `recordOperation` twice gives two lines, each parseable, in order.
