## 0 Decisions

Every fork the atoms leave open, decided. Each names what was rejected and why, judged on use (R8),
never on build cost.

**D1. `rule` is a standalone writer over `backlog.json`, not a `runIngest` collection.**
Survey 2.1: the profile registry has only `atoms` and `increments`. A ruling is not an authored file
to assemble; it is one read, a set of in-memory changes across five top-level arrays
(`questions`, `decisions`, `requirements`, `increments`, `assumptions`) and the `combination`
header, then one `commitWrite` of the whole document (survey 2.13). That single write is what makes
req-028 ac-1's "in the same saved version" true by construction.
Rejected: a third ingest collection. Ingest assembles rows from item files and has no notion of a
decision's effects, priors or supersession; bending it would couple two unrelated lifecycles.

**D2. The write goes through `commitWithReplay`, moved from `state.js` to `write.js` and exported.**
Survey seam 5.4. It already does the op-id replay check first, then read, build, `commitWrite`.
`state.js` imports it from `write.js`; its behaviour is unchanged. `rule` passes
`validate: (parsed) => parseV2Backlog(parsed)`, so the whole document, ledger included, is
re-validated before any byte is written. This satisfies D-inc-009 in `deferred.md`: a ruling
replays under `commitWrite` with `--op-id`, and the replay prints the original result.
Rejected: exporting it from `state.js` (a run-state module would then own the generic backlog
write path) and a bespoke read/commit sequence (a second copy of the ordering contract that could
drift).

**D3. The ledger schema lives in a new module, `profiles/requirements-v2.ledger.js`, and
`parseV2Backlog` calls its `checkLedger`.**
Survey 2.2 and seam 5.3: today `questions[]` and `decisions[]` pass through the `.catchall` with no
checks at all. With the check inside `parseV2Backlog`, every writer (`ingest --atoms`,
`ingest --increments`, `rule`) refuses a malformed question or decision, naming it. The records stay
additive-tolerant (`passthrough`): the live questions carry `audience`, `cluster`, `visual`, `lint`,
`raisedBy`, `blastRadius`, `meanwhile`, `recommendedBy`, which later increments own. Every
`questions`/`decisions`/`assumptions` key stays optional at the top level, so every existing fixture
(none carries them) still parses.
What `checkLedger` refuses, each naming the question or decision id and its headline where it has
one:
- a question with no `q-<slug>` id, an empty `headline`, fewer than two options, an option without
  a single-capital-letter `id`, a `text`, or a `sources` list (which may be empty: the live page
  prints "No source."), duplicate option ids, an `ifNobodyAnswers` without a `consequence`, or an
  `ifNobodyAnswers.option` that names no option;
- a `category` outside DESIGN 3.6's ten, or a `status` outside `open`, `outstanding`, `ruled`,
  `superseded` and `withdrawn`;
- a question in a must-answer category (`security`, `access-control`, `data-integrity`, `legal`,
  `policy`) whose `ifNobodyAnswers.option` is not `null` (req-031: such a question "MUST never take
  a default");
- a stored `class` or `mustAnswer` that disagrees with the derivation from `ifNobodyAnswers.option`;
- an option effect carrying `prior` (DESIGN 3.7: predeclared effects never do);
- duplicate question ids, or duplicate decision ids;
- a decision with no `d-NNN` id, a `status` outside `current`, `superseded`, `tentative` and
  `defaulted`, an empty `note`, or `decidedAt` that is neither an ISO date nor an ISO date-time
  (the live file uses dates, the writer passes date-times);
- a decision naming both or neither of `question` and `subject`, a `subject.kind` outside
  `conflict`, `combination`, `surface` and `design`, a `question` that is not in `questions[]`, or a
  `chosen` letter that is not one of that question's options;
- a `defaulted` decision whose `decidedBy` is not `default`;
- an applied decision effect with no `prior` key (DESIGN 3.7: "`check --strict` refuses an applied
  effect with no `prior`");
- a `supersedes`, `supersededBy` or question `decision` that names no decision, or a question
  `decision` whose decision names another question;
- more than one decision in force for one question (status `current` or `defaulted`, and
  `supersededBy` null);
- an atom's `needs` entry that names a question present in `questions[]` which has a default, or
  which is no longer awaiting a ruling (req-031: "every other question MUST block nothing"; DESIGN
  3.10: "Only must-answer questions enter `needs`"). A `needs` entry naming a question absent from
  `questions[]` is still accepted: the three pinned tests at
  `ingest.requirements-v2-increments.test.js:570, 582, 590` use `q-open` with no `questions[]`, and
  resolving dangling `needs` is ingest's reference pass (DESIGN 4.4), not this increment's.
Checked against the live `design/backlog.json`: every rule above holds for its six questions,
eight decisions and the one atom with `needs` (req-125 needs the must-answer
`q-conversation-retention`). Invariant I6 proves it by running the page check, which runs
`checkLedger`, on the live file.
Rejected: strict objects (they would refuse the live records' later-increment fields) and putting
the checks in `check --strict` (not built, and a check that only runs on request lets every write
through unchecked, which is survey 2.2's defect).

**D4. Ids are validated by anchored regexes next to `INCREMENT_ID`.** Survey seam 5.5.
`QUESTION_ID = /^q-[a-z0-9]+(-[a-z0-9]+)*$/`, `DECISION_ID = /^d-\d{3,}$/`,
`ASSUMPTION_ID = /^as-[a-z0-9]+(-[a-z0-9]+)*$/` and `REQUIREMENT_ID = /^req-\d{3,}$/` are exported
from the ledger module (`INCREMENT_ID` is imported from `state-schema.js`, not copied). The `rule`
positional `<question>` is parsed with `QUESTION_ID` before any read, so a question number, a
position or a headline is refused with exit 2 (req-030: "Question numbers lived only in prose and
were renumbered").

**D5. Rulings land by slug, never by position.** Every lookup in `rule` and in the page check finds
the question with `questions.find((question) => question.id === slug)`. Nothing indexes
`questions[]` by position. req-030 ac-1 is proven by reordering `questions[]` (and the page's
sections) and ruling by slug.

**D6. Effect targets are ids, not keys; no key resolver is built.** Survey 2.14 and seam 5.2.
Question options and decisions store resolved ids (`req-099`, `inc-016`, `as-panel-authority`), as
the live file and DESIGN 3.6 and 3.7 do. `rule` checks each target exists and refuses naming it
when it does not. Rejected: a key-or-id resolver over the persisted backlog. Nothing in a question
record is written as a key, and a second resolver beside ingest's would be a second definition of
identity to drift.

**D7. The effects engine implements eight of DESIGN 3.7's twelve ops, and refuses the other four
by name.** In `backlog/effects.js`, one function per op to apply and one to revert, each writing and
reading `prior`:

| op | target | apply | `prior` recorded |
|---|---|---|---|
| `adopt` | atom | `status: adopted`. `provenance` is not touched (D23) | status |
| `park` | atom | `status: parked` | status |
| `reject` | atom | `status: rejected` | status |
| `supersede` | atom, `by` atom | target `status: superseded`, `supersededBy: by`; the `by` atom `status: adopted`. Neither atom's `provenance` is touched (D23) | target status, plus `priorSupersededBy` (the target's `supersededBy` before, `null` when absent) and `byPrior` (the `by` atom's status before) |
| `clear-need` | atom | removes `value` (default: the decision's question) from `needs` | the whole `needs` list before |
| `set-assumption` | assumption | `default: value`, `decision: <new id>` (survey mismatch 3.1: the effect's `value` is written to the row's `default`, never to a stray `value` key) | the previous `default` |
| `defer-increment` | increment | `status: deferred`, `statusNote: "Deferred by d-NNN."` | status, plus `priorNote` |
| `drop-increment` | increment | `status: dropped`, `statusNote: "Dropped by d-NNN."` | status, plus `priorNote` |

The literal status strings come from one exported map, `EFFECT_STATUS`, and `deferred` and
`dropped` are asserted to be members of `RULED_STATUSES`, so a status `rule` writes engages ingest's
regroup protection through the same predicate (survey seam 5.6, survey 2.9).
`add-invariant`, `strip-dependency`, `set-delivery` and `split` are accepted by the schema (so a
stored record carrying one still validates) but `rule` refuses to apply one: "`rule` cannot apply
\"split\" effects yet. Nothing was written." No member atom asks for them; see section 5.
Rejected: automatically stripping dependencies on a dropped increment. DESIGN 3.7 asks for it, but
none of req-028 to req-031 does, and it needs its own note-on-dependant contract; it is listed in
section 5.

**D8. Ruling a question clears it from every atom's `needs`, as recorded `clear-need` effects.**
DESIGN 3.10: "`tim backlog rule` clears the need and recomputes the status in the same write."
After the option's own effects, every atom whose `needs` names the question gets one applied
`clear-need` effect on the decision (with `prior`), so a later superseding ruling restores it and
the ledger shows exactly which atoms were unblocked. A tentative answer clears nothing (D11).

**D9. Needs and statuses are recomputed with ingest's own derivation.** Survey 2.6 and seam 5.1:
`needsFor` and `bornStatusFor` are exported from `requirements-v2-increments.js` (their bodies are
unchanged). After the effects, `rule` recomputes every increment's `needs` with `needsFor(row,
{atomRows})`, and the status of every increment whose status is `todo` or `blocked` with
`bornStatusFor`. Every other status (`deferred`, `dropped`, `done`, `superseded`) is left alone:
DESIGN 3.9 allows no transition out of `done`, and a deferral or drop is a ruling, not a derivation.
`statusNote` is not touched by the recompute. Ingest itself is not changed: the pinned test
`needs recomputes on a refresh; status does not (D21)` stays true (survey 2.5, 3.3, section 4).
The `CONTRIBUTING_EXCLUDED_STATUSES` filter is used only through `needsFor`; nothing here derives
`blastRadius` (survey 2.7, 3.2).

**D10. "Reset combining" is done in the same write by clearing `combination.basis.atomsSha`.**
The phase ledger (`distil/phases.json`) does not exist: it is built by inc-029 (req-086). The only
combine-freshness record inside `backlog.json` is `combination.basis.atomsSha` (DESIGN 3.3: "basis
hash"; 5.7: it "records the atom set that was combined"). Every non-tentative ruling sets it to
`null` when a `combination` object exists, and the result reports `combineReset: true`; with no
`combination` header there is nothing to reset, and the result says so in a note. Rejected: writing
a second file for the phase reset (a second file cannot be "the same write", and the ledger it
would write does not exist yet).

**D11. A hedge is recorded as tentative whether or not `--tentative` is passed.**
req-029 ac-1 is phrased on the answer ("Given the answer 'maybe B?'"), and its falsifier is "An
effect applied from a tentative answer". If a caller forgot `--tentative`, relying on the flag alone
would apply a hedge. `isHedged(words)` is true when the words contain `maybe`, `probably`,
`perhaps` or `not sure` as whole words (any case), or a capital letter followed straight by `?`
(`B?`), which is DESIGN 6.4's rule word for word; any other `?` is punctuation. A tentative answer
appends a decision with `status: tentative`, `chosen` set, `effects: []`, moves the question to
`outstanding`, and changes nothing else: no effect, no need cleared, no recompute, no combine reset.
When the hedge came from the words and not the flag, the result carries the note
"Recorded as tentative because your words hedge. Rule again without the hedge to apply it."
Rejected: refusing a hedged answer without `--tentative` (Sam's words would then be lost rather than
recorded), and trusting the flag alone (see above).

**D12. `--by default` applies a defaulted question's default; a must-answer question is refused.**
`rule <p> <q> --by default --at <ISO>` takes the option from `ifNobodyAnswers.option`, writes a
decision with `decidedBy: default`, `status: defaulted`, runs that option's effects exactly as a
ruling does (D7 to D10), and leaves the question `open` with `decision: null`: the live file's five
defaulted questions have exactly that shape, and DESIGN 3.6 keeps a defaulted question "in section 1
under 'Has a default in force' until someone rules". `--words` and `--note` are optional for a
default and default to the live file's wording, "Default applied: option A." and "Applied by the
default rule. A ruling by a person supersedes it."; `revisitWhen` is "a person rules q-<slug>".
Refused, each with exit 2 and nothing written: `--by default` on a question with no default
("q-x must be answered by a person, so it has no default"), `--by default` with `--tentative`, with
an `--option` other than the default, or on a question that already has a decision in force.

**D13. A ruling supersedes the decision in force, reverting its effects first.** DESIGN 3.7. A
ruling by anyone other than `default` on a question with a `defaulted` decision in force supersedes
it automatically (C-044). A question with a `current` decision in force needs `--supersedes d-NNN`
naming exactly that decision, and is refused otherwise ("q-x was ruled by d-NNN. To change it, pass
--supersedes d-NNN."). Superseding: the old decision gets `status: superseded` and `supersededBy`,
the new one `supersedes`; the old decision's applied effects are reverted in reverse order, each
target restored to its `prior`, before the new effects apply. A revert is refused, naming the target
and the old decision, when the target has moved on (its current value is not what the old effect
set) or is built work (D14).
"Moved on" compares exactly the fields the effect wrote, and nothing else. `provenance` is never
compared for any op, because `rule` never writes it (D23), so an ingest refreshing it cannot trip
a revert:
- `adopt`: the atom's `status` is `adopted`.
- `park` and `reject`: the atom's `status` is `parked` or `rejected` respectively.
- `supersede`: the target's `status` is `superseded` and its `supersededBy` equals the effect's
  `by`, and the `by` atom's `status` is `adopted`. A revert restores the target's `status` to
  `prior` and its `supersededBy` to `priorSupersededBy`, and the `by` atom's `status` to `byPrior`.
- `clear-need`: the atom's `needs` does not contain the cleared question. The revert puts back the
  whole `prior` list only when the current list equals `prior` less the cleared entry; otherwise
  it is moved on.
- `set-assumption`: the assumption's `default` equals the effect's `value` and its `decision`
  equals the old decision's id.
- `defer-increment` and `drop-increment`: the increment's `status` is `deferred` or `dropped` and
  its `statusNote` is the note that effect wrote.
Each of these fields survives `ingest --atoms` and `ingest --increments` unchanged. Atoms: survey 2.11
and `refreshed()` in `ingest.js:202-216`. `rowFrom` carries none of `status`, `supersededBy` or
`needs`, and `needs` is a born extra only. Increments: `status` is kept on a refresh (the pinned D21
test). `statusNote` is a born extra only (`requirements-v2-increments.js:554`). `needs` is
recomputed on a refresh by the same `needsFor` that `rule` uses (T-I3). T-L13 proves all of this
end to end. So a superseding ruling reverts cleanly
after any number of re-ingests. Earlier tentative decisions on the question are marked `superseded`
with `supersededBy`; they carry no effects to revert. A tentative answer never supersedes anything.
Question `ruled`, `superseded` or `withdrawn` status: a ruling needs `--supersedes` for `ruled` and
is refused for the other two.
This is what makes a default "reversible" (req-031) and gives req-031 ac-2 a reversal command that
works.

**D14. `rule` refuses an effect that would change built work.** DESIGN 3.7 and 4.3 (C-055). An
effect or revert whose target is an increment that has started (`startedIncrementIds`) or is
`done`, or an atom that is a member of one, is refused naming both ids, with nothing written.
`clear-need` is exempt: clearing a need changes no behaviour, and refusing it would stop a ruling
from ever landing on a question that a built increment's member once cited. `--reopens` (the
variant atom and follow-up increment) is not built; see section 5.

**D15. `rule`'s result prints every change and, for a default, the command that reverses it.**
DESIGN 4.3: "Every write prints the changed paths with their old and new values." The result
carries `changes: [{target, field, before, after}]`, computed by diffing the backlog before and
after over the fields a ruling can touch (atom `status`, `needs`, `supersededBy`; increment
`status`, `needs`, `statusNote`; assumption `default`, `decision`; question `status`, `decision`;
earlier decisions' `status`, `supersededBy`; `combination.basis.atomsSha`). For a `defaulted`
decision it also carries `reverse`: one paste-ready command per other option, in DESIGN 6.3's exact

`--by sam` follows DESIGN 6.3 and 3.13 verbatim. req-031 ac-2 says "the report lists the call with
the command that reverses it"; the report is inc-025's (req-032, req-034), so this increment

**D16. The decisions page check is `tim backlog question check-page <p> --page <file>`.**
DESIGN 9.2: "Until then [inc-025], inc-009 adds a check that the page's ids, defaults and blocked
increments match the JSON." DESIGN 4.2 files question commands under `question`. It is read-only:
it reads `backlog.json` with `readJsonFile`, runs `checkLedger` on it, parses the page, and compares.
It deliberately does not run the full `parseV2Backlog`: the live backlog's increments inc-003,
inc-004, inc-005, inc-006 and inc-012 carry a `commit` key, which `REFUSED_FIELDS` refuses as run
state, so a full parse would fail the check on something that is not about questions (see Risks).
The page grammar is the one the live page already uses, one metadata line under each `###` question
heading:

```
`q-conversation-retention` · policy · must be answered · blocks nothing today
`q-house-rules-source` · process · default in force: A (d-005) · recommended: B
```

A metadata line matches `` ^`(q-[a-z0-9-]+)` · `` and its segments are split on ` · `. Recognised
segments: `default in force: <letter> (<d-NNN>)`; `blocks nothing today`; `blocks inc-NNN[, inc-NNN]`.
No `blocks` segment means the page claims it blocks nothing. Other segments (category,
`recommended`, `must be answered`) are ignored: req-030 ac-2 names ids, defaults and blocked
increments only. The comparison, where "awaiting a ruling" is DESIGN 3.6's one definition (status
`open` or `outstanding`):
- every page id is in `questions[]`, and every awaiting question is on the page;
- a page question the backlog has ruled is a mismatch;
- the page's default (letter and decision id) equals the backlog's default in force: the decision
  with that `question`, `status: defaulted` and `supersededBy: null`; a default on one side only is
  a mismatch;
- the page's blocked increments, sorted, equal the ids of the increments whose `needs` name the
  question (DESIGN 3.6's definition of `blastRadius.blocks`).
Any mismatch exits 1 with code `LINT` and lists every mismatch, one sentence each, each naming the
question id and its headline, for example "q-house-rules-source (Where should the four house rules
live, so Codex and people see them too?): the page says the default in force is A (d-005), but
backlog.json says B (d-009)." A clean check prints how many questions matched.
Rejected: comparing the "Owed to you" list (DESIGN 9.2 says those are not backlog records and the
fix-up review compares them), and a `--backlog <path>` flag (every command resolves paths through the
registry, req-009).

**D19. Decision fields `rule` writes.** DESIGN 3.7 field for field: `id` (the highest `d-NNN` plus

**D20. What `rule` does not accept.** `--subject`, `--choose`, `--split`, `--add-repo`,
`--answer-file`, `--effects-file`, `--why` and `--reopens` are not registered: commander refuses an

**D21. Exit codes and error codes follow the existing writer.** Refusals a caller fixes by changing
the command line or the ruling (unknown question, option or decision; must-answer default; already
ruled; built work; moved-on target; unsupported op; wrong profile) are `USAGE` (exit 2), the code
ingest's own regroup and drop refusals use. A backlog that fails `checkLedger` or `parseV2Backlog`
is `PARSE` (exit 1). A lost update is 3, a held lock 4, both from `commitWrite`. A page mismatch is
`LINT` (exit 1), as `standards --lint` uses.

**D22. The atom schema gains two optional, typed fields.** Survey 2.3: `needs` and `supersededBy`
ride through the catchall unchecked. `atomSchema` gains `needs: z.array(z.string()).optional()` and
`supersededBy: z.string().regex(REQUIREMENT_ID).nullable().optional()`, the two atom fields `rule`
writes. The class map (`requirements-v2.classes.js`) is not changed: it governs authored files, and
survey 2.4 confirms `rule` writes rows, never files. Survey 2.10 (atom drop protection) needs no
change. Survey 2.11 lists the fields `rowFrom` never re-touches: `status`, `needs`, `decisions`,
`supersededBy`, `assumptions` and `conflicts`. It is right for those fields, and they are the only
atom fields `rule` writes. `provenance` is not on that list, because `rowFrom` copies it from the
file on every refresh. That is why `rule` never writes it (D23). T-L13 pins that every atom row a
ruling touched, `provenance` included, is identical after a re-ingest.

**D23. `rule` never writes an atom's `provenance`. The ruling's verification of an atom is the
ledger record itself.** DESIGN 3.4's field table (line 427) names the owners of `provenance`: "`stage
accept`, `verify-record`". `rule` is not one of them. The live code agrees. `requirementsV2.rowFrom`
copies `provenance: item.provenance` from the atom file, and `refreshed()` spreads the authored
fields over the existing row (`ingest.js:210-215`). So a `provenance.verifiedBy: {phase: 'ruling',
decision}` stamp on the row would be overwritten by the file's `verifiedBy: null` on the very next
`ingest --atoms`. None of req-028 to req-031 asks for the stamp. DESIGN 3.13's "req-041 is adopted,
verified by the ruling" is already recorded, and cannot drift, in the ledger. The decision's
applied `adopt` (or `supersede` `by`) effect names the atom, and `appliesTo` lists it. The atom's
`status` is `adopted`. Whoever needs "which ruling verified this atom" (inc-025's report,
inc-010's `verify-record`) derives it at read time from `decisions[]`. That lookup is the applied
`adopt` or `supersede` effect naming the atom, on the decision in force.
So `adopt` and `supersede` write `status` (and `supersededBy`) only. `effects.js` records no
`priorVerifiedBy`. D13's "moved on" check compares only `status` for `adopt`, and `status` plus
`supersededBy` for `supersede` (and the `by` atom's `status`). It never compares `provenance`.
Rejected, option (a): keep the stamp, and have `requirementsV2.foldOnto` keep a ruling-phase
`verifiedBy` across a refresh. There are four reasons. It makes `rule` a second writer of a field
DESIGN gives to two other commands. It forces `foldOnto` to rule on precedence the design never
settles: an atom file that later gains a real `verify-record` stamp, or a `provenance: null` file
under a stamped row, would each need a rule no atom asks for. It makes the backlog row disagree with
its authored file on a `meta` field that the class map (`requirements-v2.classes.js`, `provenance:
{class: 'meta', persisted: true}`) treats as authored. And it duplicates a fact the ledger already
holds. `foldOnto` stays `() => ({})`, and `requirements-v2.js` changes only as D22 and D3 say.

**D24. Three narrowings from D13, D14 and D9, found during review, recorded here rather than left
implicit in code comments.**
(a) `revertEffect`'s "moved on" check for `defer-increment`/`drop-increment` compares `status` only,
not `statusNote`, though D13 reads as covering the whole applied shape. The live decisions d-005 and
d-006 carry hand-authored `statusNote` prose rather than the literal template `rule` itself writes
(`` `${verb} by ${decisionId}.` ``); comparing the note text would treat every hand-authored ruling
as "moved on" and refuse a clean revert of the two decisions that ship with the live backlog.
Rejected: comparing `statusNote` too, which would make D13 stricter than the live data it has to
revert.
(b) `builtWorkGuard` exempts `set-assumption` as well as `clear-need`, though D14 names only
`clear-need` as exempt. `set-assumption`'s target is always an assumption record, never an atom or
increment, so it is never itself "built work" in D14's sense — the guard's atom/increment checks
would not resolve an assumption id to anything, exempting it is required for the guard to be
meaningful, not a narrowing of what D14 protects.
Rejected: leaving `set-assumption` unexempted and unreachable in the guard's atom/increment checks,
which would either throw on a lookup miss or silently no-op — worse than naming the exemption.
(c) D9's recompute also skips a started increment (`startedIds`), not only `done` ones. Restoring a
cleared need on a re-supersede must never flip a started increment to `blocked` mid-build, which a
`done`-only skip would allow for the window between a build starting and it finishing.
Rejected: recomputing every `todo`/`blocked` increment regardless of `startedIds`, which is what D9
as first written implied.

**D25. `__fixtures__/ledger/backlog.json`'s `q-house-rules-source` carries only options A and B; the
live `design/backlog.json` carries a third, option C (`supersede req-046 by req-124`).** The fixture
is trimmed on purpose: T-L6 and the sibling tests in `rule.test.js`/`effects.test.js` only need two
options to prove a reversal round-trip (D15) and a straightforward supersede; adding C would mean
inventing fixture-local atom ids for `req-046`/`req-124` (which do not exist in this fixture's
eight-atom set) purely to keep the shape parallel to the live file, with no test that needs the
third path. `T-L6` therefore asserts `result.reverse` has length 1 (one other option, B), not the
two the live file's three-option question would print.
Rejected: mirroring the live file's option count exactly. The fixture is captured, lightly-trimmed
data (`tim/.claude/rules/test-patterns.md`), not a byte-for-byte copy, and a third option would be
fixture-invented data (fabricated atom ids), which the same rule asks us not to do.

## Risks

- **`rule` on the live programme is refused today.** The live `design/backlog.json` carries `commit`
  on inc-003, inc-004, inc-005, inc-006 and inc-012, a run-state field `REFUSED_FIELDS` refuses on
  every re-parse. `rule requirements-pipeline ...` would therefore stop with exit 1 naming `commit`
  until those values move to `build/state.json` (inc-008's run-state work, or a bootstrap fix). The
  read-only page check is unaffected (D16). This increment does not edit the live backlog (I7); it is
  raised for the judge.
- **The hand-written page can drift from the backlog between now and inc-025.** That drift is what I6
  catches; a failure of I6 caused by a later ruling is the check doing its job, not a defect here.
- **Moving `commitWithReplay` and the CLI helpers** could break `state.js` or `index.js` imports.
  I1 and I4 (the unchanged state and CLI tests passing) prove the move is behaviour-neutral.
- **The new ledger checks run on every ingest.** A programme whose authored atoms name a defaulted or
  ruled question in `needs` now fails ingest, which is the requirement. No existing fixture carries
  `questions[]`, and dangling `needs` still pass (D3).
