### D2: The CLI surface

```
tim backlog standards [--files <repoKey:path...>] [--repo-level <repoKey...>]
                      [--programme <key>] [--lint] [--json] [--workspace <path>]
```

- `--files` and `--repo-level` are commander variadic options. Repeated uses accumulate.
- At least one of `--files`, `--repo-level` or `--lint` is required. Without one, the command
  fails with USAGE, exit 2: "Name at least one file with --files, a repo with --repo-level, or
  run --lint."
- A `--files` spec must match `<repoKey>:<path>`. The path must be relative and must stay
  inside the repo after normalising, with no leading `/` and no escaping `..`. Otherwise the
  command fails with USAGE.
- The file does **not** need to exist. A planned file, or one a writer is about to create,
  gets its standards all the same (req-043, DESIGN 8.5 "a Codex writer creating a file nobody
  planned").
- Validation runs in a zod schema before any filesystem read (`cli-patterns.md`).
- Help text has a description and examples.
- **Rejected: taking the programme as a positional argument, as `ingest` does.** The design's
  signature has none. Resolution for a single file must work with no programme registered.
  Today that includes this programme itself, because `requirements-pipeline` is not in the
  registry until inc-005's registry work lands.

### D3: The code-style `routing.json` shape

```json
{
  "schemaVersion": 1,
  "patternSyntax": "shell-case: * matches any run of characters, including /; ? matches one character",
  "fileTopics": [
    { "patterns": ["*.java"], "topics": ["java"] },
    { "patterns": ["*.js", "*.mjs", "*.cjs", "*.jsx"], "topics": ["node"] },
    { "patterns": ["*.njk"], "topics": ["gds"] },
    { "patterns": ["*.spec.ts", "*.spec.js", "*.visual.spec.ts"], "topics": ["playwright", "node"] },
    { "patterns": ["*/k6/*", "*.k6.js", "*/perf/*.js"], "topics": ["k6"] }
  ],
  "topics": {
    "java": { "bestPractice": ["docs/best-practices/java/modern-java.md", "docs/best-practices/doc-comments/BEST_PRACTICES.md", "docs/best-practices/doc-comments/javadoc.md"] },
    "node": { "bestPractice": ["docs/best-practices/node/code-style.md", "docs/best-practices/doc-comments/BEST_PRACTICES.md", "docs/best-practices/doc-comments/jsdoc.md"] },
    "gds": { "bestPractice": ["docs/best-practices/gds/components.md", "docs/best-practices/gds/styles.md", "docs/best-practices/gds/patterns.md"] },
    "playwright": { "bestPractice": ["docs/best-practices/playwright/BEST_PRACTICES.md"] },
    "k6": { "bestPractice": ["docs/best-practices/k6/BEST_PRACTICES.md"] }
  }
}
```

- The values are copied **verbatim** from `file-topics.sh:34-58` and
  `bake-rules-bundle.sh:37-73`. The key order of `topics` is java, node, gds, playwright, k6,
  which is `file-topics.sh`'s emission order.
- **The emission order is the key order of `topics`.** Rejected: a separate `topicOrder`
  array. That makes two lists that can drift. JSON object key order for non-integer keys is
  preserved by jq's `keys_unsorted` and by JS `Object.keys`.
- **Patterns use shell `case` semantics, not picomatch.** That is what `file-topics.sh` does
  today: `*/k6/*` matches `a/b/k6/c/d.js` because `*` crosses `/`. The bash reader keeps it
  with `[[ $path == $pattern ]]`, where the pattern is unquoted, which is pattern matching like
  `case`.
  - tim compiles a pattern to an anchored RegExp: every regex metacharacter is escaped, `*`
    becomes `.*` and `?` becomes `.`. That gives the same semantics.
  - tim's loader refuses a pattern containing `[`, `]`, `{`, `}` or `\` with PARSE. Bash and
    tim treat those differently, so refusing them keeps the two readers from diverging
    silently.
  - Rejected: converting to picomatch globs. `**/k6/**` and `*/k6/*` disagree on `k6/x.js`, so
    golden parity would break.
- The validator (zod) refuses a `fileTopics[].topics` entry that is not a key of `topics`,
  and an empty `bestPractice`. Both fail with PARSE, naming the routing file and the key.
- `patternSyntax` is a human-readable declaration, not machine-read. Rejected: leaving the
  semantics undocumented, because the next editor would write `**/*.java` and silently get a
  different match.

### D5: The review `routing.json` shape, and the detect-tech reader

```json
{
  "schemaVersion": 1,
  "manifestDirs": ["service", "app", "src"],
  "technologies": [
    { "name": "k6",
      "when": { "anyOf": [
        { "fileContains": { "file": "package.json", "pattern": "\"k6\"" } },
        { "anyFileContains": { "glob": "*.js", "pattern": "from ['\"]k6[/'\"]|require\\(['\"]k6" } },
        { "dirExists": "k6" },
        { "fileExists": "k6.config.js" },
        { "allOf": [
          { "anyFileContains": { "glob": "*.js", "pattern": "export (default )?function|import \\{ (check|sleep|group)" } },
          { "anyFileContains": { "glob": "*.js", "pattern": "from ['\"]k6/http['\"]" } } ] } ] },
      "bestPractice": ["docs/best-practices/k6/BEST_PRACTICES.md"] },
    "… playwright, springboot, spring-data-mongodb (requires springboot), openapi-springdoc (requires springboot), aws-sdk-v2 (requires springboot), hapi, pino, nunjucks, rest-api, gds …"
  ]
}
```

- The array order is the emission order of `detect-tech.sh:202-265`: k6, playwright,
  springboot, then its three sub-technologies, hapi, pino, nunjucks, rest-api, gds.
- **The condition vocabulary:**
  - `fileContains {file, pattern}` checks the repo root and each of `manifestDirs`.
  - `fileExists {file}` checks the same places.
  - `anyFileContains {glob, pattern}` has `grep -rqE --include` semantics.
  - `dirExists` takes a repo-relative path, checked at the root only.
  - `anyOf[]` and `allOf[]` combine conditions.
  - `requires` names an **earlier** technology, and the entry is evaluated only when that one
    was detected.
  - The design names `fileContains`, `anyFileContains` and `fileExists`. `dirExists`, `anyOf`,
    `allOf` and `requires` are the minimum more that the live control flow needs. Every one of
    them is exercised by a fixture repo.
- **Patterns are copied from the bash source with bash's double-quote processing applied.**
  `\"` becomes `"`, and `\(` stays `\(`, so grep receives exactly the bytes it receives
  today. JSON then escapes `"` and `\`. The goldens catch any slip, because every pattern has
  a fixture that reaches it (section 3).
- **The springboot "pom or build.gradle" pairs** (`detect-tech.sh:219,224,229`) become
  `anyOf[fileContains pom.xml, fileContains build.gradle]`.
- **The GDS detector** becomes
  `anyOf[fileContains package.json "govuk-frontend", allOf[anyOf[dirExists src/views, views, service/src/views, service/views], anyFileContains *.njk "govukButton|govukInput|govukRadios|govukCheckboxes"], anyFileContains *.njk "govuk-"]`.

**The bash reader (`detect-tech.sh`):**

- The empty and non-directory early exit is unchanged.
- `file_contains`, `file_exists` and `any_file_contains` are kept. `file_contains` loops over
  `manifestDirs` read from jq.
- A recursive `eval_condition <json>` dispatches on `jq -r 'keys[0]'`. `anyOf` and `allOf`
  iterate `jq -c '.anyOf[]'` with short-circuit.
- A loop over `jq -c '.technologies[]'` skips an entry whose `requires` is not already in the
  detected list, then appends its `name` and `bestPractice[]`.
- The output block (`detect-tech.sh:271-279`) is kept **verbatim**. `jq -R . | jq -s .`
  pretty-prints the arrays over several lines, and the goldens pin that shape.
- `ROUTING` resolves as in D4, and a missing routing file exits 1 with the same message.
- **Rejected:**
  - Having `detect-tech.sh` call `tim`. People run it through `prepare-review.sh`,
    `prepare-plan.sh`, `prepare-implement.sh` and `prepare-check.sh` with no `tim` on PATH.
  - Keeping the detectors in bash with only the lists as data. Req-122 moves "routing" to
    data, and the design names the detector vocabulary explicitly.

### D6: Rules folders, matching and front matter

**Which rules folders apply to a file.**

- A file's rules folders are `<D>/.claude/rules/` for each ancestor folder `D`, from the
  workspace root down to the file's own folder. Every `*.md` in each folder is included,
  recursively.
- Each rule is matched with `picomatch(globs, { dot: true })` against the file's path
  relative to `D`. `D` is the rule's **scope root**, for example `tim/`.
- Rejected: scanning the whole workspace for rules folders on every resolution. The scan finds
  stale copies under `workareas/clones/`, `workareas/reviews/` and `.claude/worktrees/`. The
  find in this planning session listed about 40 of them. They would apply wrong rules to
  unrelated files.
- `dot: true` means `**/*.js` also matches `.claude/workflows/x.js`. Over-inclusion of a
  standard costs a read. Under-inclusion loses a standard, which is req-040's falsifier.

**Front matter.**

- Front matter is parsed with `js-yaml` (`load`, default schema, which is safe in v4).
- The rule body is everything after the closing `---`. Rejected: a hand-rolled parser for the
  `paths:` subset. YAML allows `paths: ['a', 'b']` and plain scalars, and the harness reads
  real YAML.
- A rule with no front matter, or no `paths`, matches **every** file under its scope root,
  with `matchedBy: null`. That is the harness's behaviour for an unscoped rule.
- `paths` that is neither a string nor a list of strings, or unparseable YAML, fails with
  PARSE: "Can't read the front matter of `.claude/rules/x.md`: …".
- **Rejected: including user-level `~/.claude/rules` and `~/.claude/CLAUDE.md`.** The atoms
  scope the chain to "the workspace's and each enclosing folder's". Neither user-level
  location exists on this machine. They are personal settings, and a pipeline must not make
  one person's settings another executor's standards.

### D7: The pointer grammar, and one wording fix in two rule files

**The grammar**, recorded in `rules.js`'s module JSDoc:

1. Pointers live only in **list items** of the rule body. A list item is a line starting
   `- `, plus its indented continuation lines. Paragraph text is prose. For example,
   `playwright.md`'s "`node.md` applies additively" and `copy.md`'s `copy/copy.<locale>.js`
   are not pointers.
2. In a list item, the backticked token after `Topic dir:` is the rule's **base folder**. It
   must end with `/`. Lint checks that it exists and is a folder.
3. Every other backticked token in a list item whose value, after brace expansion, ends in
   `.md` is a **pointer**. Brace expansion handles one level, `a/{b.md,c.md}` →
   `a/b.md, a/c.md`, which is the only form in use.
4. A pointer starting `~/git/defra/trade-imports-workspace/` is workspace-relative, with that
   prefix stripped. The same applies to the Topic dir. Any other pointer resolves against the
   Topic dir. With no Topic dir, it resolves against the rule's scope root.
5. The resolved paths, deduplicated in order of appearance, are `pointsTo`.

Tokens that are not `.md`, such as `` `npm run test:docker-compose` `` and `` `--json` ``, are
ignored.

**The wording fix.** Under this grammar, the live `node.md` and `java.md` each hold one
pointer that resolves wrong. Their Additive bullet says "read `doc-comments/BEST_PRACTICES.md`
first", which rule 4 resolves to `docs/best-practices/node/doc-comments/BEST_PRACTICES.md`.
That path does not exist. The file meant is `docs/best-practices/doc-comments/BEST_PRACTICES.md`,
relative to nothing the rule declares. **Decision:** rewrite that token in both rules as
`~/git/defra/trade-imports-workspace/docs/best-practices/doc-comments/BEST_PRACTICES.md`,
matching the full-path form the same bullet already uses for `jsdoc.md` and `javadoc.md`.

- **Rejected: a fallback chain of bases**, trying the Topic dir, then the previous absolute
  pointer's folder, then `docs/best-practices/`. A fallback can find some other file of the
  same name and hide a dead pointer, which is req-041's falsifier.
- **Rejected: moving the pointers into front matter.** That changes every rule file's shape,
  and it is out of proportion to one ambiguous token.

After the fix, every pointer in all ten live rules resolves. The live lint (I-5) and the
live-workspace test (L-1) prove it.

### D9: How the golden tests prove "before equals after" (req-122 ac-1)

1. In `beforeAll`, it builds a temporary HOME:

     `tools/review/detect-tech.sh`, located from the test file with

     absent, so bake's `(missing)` branch is pinned.

3. Each case records `{input, exitCode, stdout, stderr}`. bake cases add `bundle`, the written

4. `await expect(JSON.stringify(cases, null, 2) + '\n').toMatchFileSnapshot('__fixtures__/standards/__golden__/<script>.json')`,
   one snapshot file per script.

**Order is the proof.** Section 2's step S1 writes this test and its fixtures, then runs it
with `--update` **before any script or `routing.json` is touched**. The snapshots are
therefore the old scripts' output.

- After the move, the same test runs without `--update`, and it must pass with zero written
  and zero updated (I-2).
- The capture log and the final log are both kept under `build/logs/`, as the audit trail.

**Rejected alternatives:**

- Keeping frozen copies of the old scripts in the repo to diff against on every run. After
  the first legitimate routing change, that test would fail forever, and it would itself
  become the "copy that drifts".
- Hand-writing the golden outputs. They would not be the old scripts' output, which is the
  claim ac-1 makes.

**Why a vitest test spawns bash, when tim's rails say "never shell out to `../tools/*.sh`".**
That rule governs tim's integration path, which is `src/**` production code. A test is where
input and output are asserted, and the scripts under test **are** bash, so spawning them is
the input/output assertion. Rejected: a bats suite, which has no runner in the workspace
ladder or CI. The `tim-ci.yml` paths are extended so the goldens run when a script, the
routing or a rule changes (section 2).

**The goldens are JSON, and prettier must not reformat them.** Add
`src/**/__fixtures__/**/__golden__/` to `tim/.prettierignore`. Otherwise `format:check` in
CI could fail on a byte-exact snapshot. Rejected: a `.txt` extension, which would hide that
the content is JSON.

### D11: The CLAUDE.md chain, imports and the memory index

**The chain.**

- For a file, the chain is every existing `<D>/CLAUDE.md` and `<D>/.claude/CLAUDE.md`, for
  each ancestor `D` from the workspace root down to the file's folder, in that order.
- For a repo-level entry, the chain runs from the root down to the repo folder.
- Paths are workspace-relative. Rejected: `AGENTS.md`, which the harness does not load; the
  atoms say "project instruction files", meaning the harness's.

**Imports.**

- In each chain file, an import is a token `@<target>` at the start of a line or after
  whitespace, outside fenced code blocks and inline code spans. The target starts with `./`,
  `../`, `~/` or `/`, or ends in `.md`.
  - That excludes prose such as `@hapi/hapi` and email addresses, which the harness would
    try, fail on and silently drop.
  - Without the rule, the lint would raise false alarms. With it, every live import
    (`tim/CLAUDE.md:7-12`) is caught.
- A target resolves against the importing file's folder, and `~/` against the home folder.
- Imports recurse up to depth 5, the harness's limit, with a visited-set cycle guard.
- `imports` lists every target once, in discovery order. A target inside the workspace is
  workspace-relative; one outside it is absolute.
- A missing import target is a problem of kind `import` (D17).

**The memory index.**

- The path is `join(claudeConfigDir, 'projects', slug(workspaceRoot), 'memory', 'MEMORY.md')`.
  - `claudeConfigDir` is `process.env.CLAUDE_CONFIG_DIR ?? join(homedir(), '.claude')`. The
    harness honours that variable, and tests set it through execa's `env`.
  - `slug` replaces every character outside `[A-Za-z0-9]` with `-`.
- The memory index is one path per workspace, not per file. It goes into every file and repo
  entry, because both executors read it at start (DESIGN 8.6).
- It is listed **only when it exists**. When it does not, the result carries
  `notes: ["No memory index at <path>."]`.
- Rejected: listing a path that does not exist with a null sha. Req-122 ac-2 wants "every
  listed standards file carries its content hash", and a Codex task cannot read a file that
  is not there.
- It is absolute, because it lives outside the workspace.

### D12: Repo keys, and the result shape

**Repo keys.**

- With `--programme <key>`, `loadProgramme` gives `paths.backlog`, and the backlog header's
  `repos` gives `{repoKey: {path}}`.
  - A backlog with no `repos` map fails with NOT_FOUND: "`<key>`'s backlog names no repos."
- Without `--programme`, the map is `{workspace: {path: '.'}}` plus `{<name>: {path: 'repos/<name>'}}`
  for each existing folder under `repos/`.
- A repo key not in the map fails with USAGE: "Can't find repo key `<k>`. Name a programme
  with --programme, or use `workspace` or a folder name under repos/."

**Repo-level detection skips other repos.** When a repo's folder contains another mapped
repo's folder, detection for the outer repo skips the inner one. For the workspace (`.`),
that is every `repos/<x>`. It also skips `workareas/` and `.claude/worktrees/`: the workspace
CLAUDE.md calls `workareas/` gitignored runtime cache, and a worktree is another checkout.

- Nothing else is skipped, `node_modules` and `.git` included, for parity with
  `grep -r`.
- `detect-tech.sh` is never run on the workspace root by any caller, so no parity claim is
  lost.
- Symlinks are not followed, as with `grep -r`.
- `repo-files.js` walks a repo **once** per resolution and caches the file list. Every
  detector filters that list by basename glob (picomatch, `dot: true`, basename match) and
  tests the pattern per line. Grep is line-based, and per-line matching keeps `.` from
  spanning lines.
- Unreadable files are skipped silently, like grep's `2>/dev/null`.

**The result (JSON).**

```jsonc
{ "schemaVersion": 1,
  "routing": [ { "path": ".claude/skills/code-style/assets/routing.json", "sha": "…" },
               { "path": ".claude/skills/review/assets/routing.json", "sha": "…" } ],
  "files": [ { "file": "workspace:tim/src/x.js", "repoKey": "workspace", "path": "tim/src/x.js",
      "rules": [ { "path": ".claude/rules/node.md", "matchedBy": "**/*.js", "pointsTo": ["docs/best-practices/node/code-style.md", "…"] },
                 { "path": "tim/.claude/rules/cli-patterns.md", "matchedBy": "src/commands/**", "pointsTo": [] } ],
      "topics": ["node"], "bestPractice": ["…"],
      "claudeMd": ["CLAUDE.md", "tim/CLAUDE.md"], "imports": ["docs/best-practices/node/code-style.md", "…"],
      "memory": ["/Users/…/memory/MEMORY.md"],
      "shas": { "<every path above, the entry's own file excepted>": "<40-hex blob sha>" } } ],
  "repos": [ { "repoKey": "workspace", "path": ".", "technologies": ["…"], "bestPractice": ["…"],
      "claudeMd": ["CLAUDE.md"], "imports": [], "memory": ["…"], "shas": { "…": "…" } } ],
  "standards": [ { "path": "…", "sha": "…" } ],
  "notes": [],
  "lint": { "rules": ["…"], "problems": [] } }
```

- `matchedBy` is the first glob that matched.
- `standards` is the union of every path in every entry, including the routing files,
  deduplicated and sorted. It is what a writing task receives: its planned files' routing
  plus the repo-level routing for every repo in its surface (req-043 ac-2).
- `lint` is present only with `--lint`.
- The entry's own file is not a standard and carries no sha. It may not exist yet.
- **Rejected:**
  - Emitting `skills` (per-role SKILL.md and personas). That is req-135, inc-019.
  - Emitting `houseRules` or `knowledge`. See D13.
  - Emitting empty placeholders for them. A reader would take an empty list as "resolved,
    none".
- The text rendering prints each entry's file, then indented `rules`, `topics`,
  `bestPractice`, `claudeMd`, `imports` and `memory` lines. It ends with
  "`N` standards files, each with its blob sha." For `--lint` alone, it prints
  "Checked `N` rules. Every pointer resolves."

### D17: Failing loudly (req-041)

**Problems.** A problem is `{kind, source, pointer, resolved}`, with one of these kinds:

| Kind | Meaning |
|---|---|
| `rule-pointer` | a rule points at a missing file |
| `topic-dir` | a Topic dir is missing or not a folder |
| `routing` | a `routing.json` bestPractice path is missing |
| `import` | an `@` import target is missing |

**Resolution fails on any problem it touches.**

- It fails for a problem in a matched rule's pointers, a routed file, or an import on the
  chain.
- The error is `TimError('LINT', message)`. The message names every problem, one per line:
  "`.claude/rules/x.md` points to `docs/best-practices/x/renamed.md`, which does not exist."
- That is req-041's statement: "Rules resolution MUST fail loudly".
- Rejected: failing only under `--lint`. A task would then silently lose the standard, which
  is req-041's falsifier.

**`--lint`.**

- It checks **every** rule in the root `.claude/rules/`, plus every nested
  `<D>/.claude/rules/` found by a folder walk. The walk skips `node_modules`, `.git`,
  `workareas`, `.claude/worktrees` and every dot-folder other than `.claude`. Folders only;
  files are not read during the walk.
- It also checks both routing files' paths and the root chain's imports.
- It checks every Topic dir and pointer, whether or not a file matches the rule.
- On problems: `TimError('LINT', …)`. In `--json` mode, the envelope reads `ok:false`,
  `errors[0].code:'LINT'`. The exit code is 1.
- Clean: `lint: {rules: [...], problems: []}`, exit 0.

**The new error code.** `LINT` is added to `VALID_CODES` in `tim/src/errors.js`. It maps to
exit 1 through `exitCodeFor`'s existing default. `errors.test.js` gains one case.

- Rejected: `PARSE`. The file parsed fine, and a caller branching on `PARSE` would misread
  it.
- Rejected: `NOT_FOUND`. It maps to exit 2, a usage mistake, and the design says exit 1.
