# Proposal: the fewest agents per increment, with no loss of quality or safety

Written 2026-09-19 against `design/DESIGN.md` (sections 2, 4, 5, 7, 8 and 11), `design/backlog.json` (41 increments, 135 atoms), `consolidation/inventory.md`, `analysis/a-frontend-alignment.md`, `analysis/b-increment-build-loop.md`, `analysis/sam-requirements.md` and the tim sources.

## 0. The answer in one table

| Run | Before, as 7.2 specifies (one watcher per action) | Before, as 8.8 reads it (one watcher per stage) | After |
|---|---|---|---|
| Typical build increment, Claude preset | **97**: 39 judgement, 9 relays, 49 watchers | **59**: 39 judgement, 9 relays, 11 watchers | **42**: 37 judgement, 5 step agents |
| Clean build increment (reviews find nothing) | 82: 29 judgement, 5 relays, 48 watchers | about 45 | **33**: 29 judgement, 4 step agents |
| Build increment, `codex` preset | about 58 cheap agents | about 20 cheap agents | **about 2** cheap agents |
| Build increment, `codex-claude-checks` preset | about 62 | about 24 | **9**: 4 judgement, 5 step agents |
| Per build run, on top | 1 resolve watcher | 1 | **0** |
| Typical distil run | **81** (up to 91 when author and verify are pipelined per slice): 58 judgement, 23 relays | same | **66**: 56 judgement, 10 step agents |

"Typical" is the inventory's increment and distil run (`inventory.md`, "Typical increment used for the counts" and "Distil phases"). The build keeps every judgement stage the requirements need. Two judgement agents go: two verification tasks, because verification is batched by repo and review family (3.4). The distil keeps every judgement phase. Two cold readers go, because they would read report sections that render empty (3.3).

The per-increment count of cheap agents no longer grows with repos, rungs, shards or files. It equals the number of gaps between judgement stages, which is 5 for a typical increment and 4 for a clean one. Under the agent ceiling of 850, a run now covers about 20 typical increments rather than about 8.

## 1. The rules this proposal works to

- **An agent is the cost, not a stage** (Sam's steer). Each spawn pays a fixed start-up cost: the system prompt and tool schemas, the workspace `CLAUDE.md` (about 12 KB), the memory index (about 15 KB) and the GUARD RAILS block. It also uses tokens and wall-clock. Stage count is free; tim may run 100 internal steps if each is a tested function call.
- **Deterministic work is never folded into a judgement agent to save a spawn.** It runs as a tested tim command, issued by a cheap agent (Haiku, low effort) with a "run this" prompt: run these commands in order, stop at the first non-zero exit, report the exit codes and the paths tim wrote. That agent makes no judgement.
- **A judgement agent reads the facts tim recorded.** It never re-runs a rung, a diff or a scan.
- **Runtime facts.** A Workflow script cannot run a command, read a file or import a module, so any command is issued by some agent. Workflow agents have Bash, Read, Edit, Write and Skill, and no Agent tool. Opus fan-out stays at 6 or fewer at once (the design uses 5).
- **R8.** Build effort weighs nothing. A fixed overhead paid on every run or every increment weighs a lot, and this proposal is exactly that.
- **R2, R3, R5, R6, R7 and R4** must all still hold. Section 8 shows each one.

## 2. Three kinds of work, and who does each

| Kind | Examples | Done by | Agent spent |
|---|---|---|---|
| Judgement | plan, plan audit, implement, per-file style and code review, consistency, verify, judge, fix, fix-verify, acceptance, every repair, CI fix, discovered-atom verify; distil characterise, extract-verify, carryover, reslice, slice, author, verify, gap audit, reconcile, panel, dedupe, critic, question editor and critic, combiner and verifier, prose editor and claim verifier, cold reader, ruling applier | A model task: Claude Opus or Sonnet, or Codex, through the stage contract (8.1) | One per task, as today |
| Local mechanical | next, branch cut, heads, fetch, `merge-tree` probe, local merge of base, baseline rungs, implement-check rungs, manifest, secrets, ladder, stack up, shards, retry, stack down, commits, state commit, receipts, audit, report, handover, CI wait, Codex task runs | tim, in-process, inside one call of `tim backlog advance` | None of its own. ## 3. The five mechanisms

### 3.1 The step agent: one per gap, one command in a loop

The script spawns one Haiku agent, at low effort, whenever it needs the next step. It runs one command, `tim backlog advance`, in a loop. `advance` does every local mechanical step in-process and stops only when it reaches one of these:

- a judgement stage with tasks to spawn (`run`);
- outward commands the agent must run as its own calls (`act`);
- a slice boundary under the 600-second Bash ceiling (exit 75, "call again");
- its call budget for this agent (`handback`);
- a stop or a hold (`stop`).

The prompt, whole:

```
${GUARD_RAILS}
You run the pipeline's commands. You make no decisions.
1. Run: ${TIM} backlog advance ${P} --run ${LABEL} --agent ${AGENT_ID} --json${ACTED}
2. Exit 75: run exactly the same command again.
3. If "status" is "act": run each actions[i].cmd exactly as given, one Bash call each, in order.
   Stop at the first non-zero exit. Then go to step 1, adding
   --acted <id>:<exit> for every action you ran.
4. If "status" is "run", "handback" or "stop": return the JSON result fields verbatim.
Never run any other command. Never change a command. Never read or edit a file.
```

- **The budget.** `advance` counts calls per `--agent` id in run state. After `quality.stepBudget` calls (default 40) it returns `{status: handback}` at the next safe point, and the script spawns a fresh step agent. This keeps a Haiku agent's context short and bounded, however long an increment is.
- **No `--record` round trips.** Today each action costs a second tim start-up to record its exit code. Now the agent passes `--acted id:exit` on its next `advance` call as a hint, and tim establishes the result by observation (3.5 and section 6).
- **The relayed task list is still checked** (C-070). A `run` step carries the compact task list, the count and the sha256 of the span manifest. The script re-derives both before it spawns anything, exactly as 8.2 says today.

### 3.2 Judgement chains run as one fan-out

Between some judgement stages there is nothing mechanical at all, only `accept --finalise` of the first and `stage prepare` of the second. Each such boundary costs a relay today. Instead, `advance` returns a **span**: the tasks of two or more consecutive judgement stages as one task graph, with each task's upstream named.

```jsonc
{ "status": "run", "span": "review", "stageSha": "…", "count": 30,
  "tasks": [
    { "id": "review-code:fe:src/server/app/origin/controller.js", "tier": "doer", "dirAbs": "…", "dirTilde": "…" },
    { "id": "consistency", "tier": "think", "dirAbs": "…" },
    { "id": "verify:fe:code", "tier": "doer", "after": ["review-code:fe:…", "…"],
      "when": { "anyOf": [{ "task": "review-code:fe:…", "count": "findings", "gt": 0 }] } },
    { "id": "judge", "tier": "think", "after": ["verify:fe:code", "verify:fe:style", "verify:consistency"],
      "when": { "anyOf": [{ "stage": "verify", "count": "standing", "gt": 0 }] } },
    { "id": "fix", "tier": "doer", "after": ["judge"], "when": { "task": "judge", "count": "fixNow", "gt": 0 } } ] }
```

- **tim decides the graph; the script only walks it.** A task starts when every `after` task has returned an accepted receipt, and runs only if its `when` holds on those receipts' counts. The counts come from `receipt.json`, which `stage accept` writes (8.1): `findings`, `standing` (confirmed plus unsure), `fixNow`, `added`. The walker is one small helper, duplicated byte for byte between the two workflow scripts like the rails. `workflow-contract.test.js` extracts it with acorn and runs it on fixture graphs with a fake `agent()`, so it is tested code, not untested workflow JavaScript.
- **`advance` stays the only authority** (C-002). The walker's `when` is an optimisation, never the rule. On the next `advance` call tim re-derives the span from disk. A task whose condition held but which did not run (a misrelayed count, a dead upstream) is prepared and returned as a new `run`. A task that ran but should not have is recorded and ignored. The done gate still re-derives everything (4.5).
- **Prepare ahead.** `stage prepare --span` writes every task folder in the span at once. A downstream task's `input/upstream/` holds references by path to its upstream tasks' `output.json`, not copies. Its `stage accept` records the `outputSha256` of every upstream output it read. The audit checks each equals that upstream's accepted receipt.
- **Standards known only later.** A downstream writer's must list can depend on what upstream decided: the fix touches only the files the judge ruled on. `standards.json` for such a task lists the routing for every manifest file, keyed by file, marked `mustIf: {ruledFile}`. The reading audit, at accept, requires only the entries whose condition holds. Nothing extra is read, and nothing is missed.
- **Where it cannot apply.** A mechanical step between two judgement stages breaks the span: rungs after implement and after fix, the plan audit's added-repo set-up, a gate in the distiller. Those gaps each cost one step agent. They are the floor.

### 3.3 Skip what has no input

Every conditional stage is a `when` in the span, or a skip rule in the stage table, so a stage with nothing to act on spawns nothing and costs no gap:

| Stage | Skipped when |
|---|---|
| verify (a batch) | none of its files' reviews had findings |
| verify-consistency | the consistency output had no findings |
| judge | no finding is confirmed or unsure (all refuted, or none raised) |
| fix | the judge ruled no fix-now |
| fix check, fix-verify | no fix ran |
| consistency again at fix-verify | no fix touched a plan seam file |
| repair review | no repair diff |
| discovered-atom verify | the judge discovered nothing |
| plan revise round | the audit approved |
| carryover, reslice | no earlier distillation and no migrated rows |
| gap audit | `yield` flagged no slice |
| panel | no conflict survived precedence |
| cold reader, per section | the section renders empty, for example "Rulings applied" on a first run and "Build status" before any build. It is recorded "not read: empty" and the report says so |
| ruling applier | no ruling has effects pending |

The done gate treats a skip as it treats any fact: the audit re-derives the condition from disk and fails if a skipped stage should have run.

### 3.4 Verification batched by repo and review family

Today there is one verify task per file with findings. The review skill has no verifier worker of its own (`review/SKILL.md:65-67` lists the file reviewer, the consistency reviewer and the item fixer), so verification granularity is the pipeline's to choose, and the skill contract test is unaffected.

- **The batch.** One verify task per touched repo and review family (style or code) that has findings, capped at `quality.verifyBatch` findings (default 12) or 4 files, whichever comes first. Beyond the cap the batch splits. One verify-consistency task stays as it is.
- **Why nothing is lost.** A batch reads one persona (the family's reviewer method), one `SKILL.md` and one repo's routed best-practice files: the same must list each per-file verifier re-reads today. Independence stays: no verifier is the reviewer. Adversarial default stays: an unanswered finding is refuted. `completed` and `notReached` catch a batch that runs out, with one continuation, as for every checking output (C-006). The cap stops the batch from diluting attention.
- **Parity.** Both executors batch the same way, so R6's equal task counts per role hold. `compare` reports the verifier confirm rate per batch size, so any loss would show.
- **Typical increment.** 6 files with findings: 4 in the frontend and 2 in the backend, with style and code findings in both repos. That is 4 batches plus verify-consistency: 5 tasks instead of 7.

Per-file style and code review are **not** batched. R6 names "a style reviewer and a code reviewer per file" as the quality bar, and the two personas differ. The cold readers are not batched either: their value is reading one section in isolation (C-050).

### 3.5 Codex tasks run inside tim

`tools/codex/run-stage.sh` becomes `tim/src/backlog/codex/runner.js`, with the same contract: `CODEX_HOME` from `tools/codex/home/`, the stage lock, concurrency by sandbox, 540-second slices, resume, three correction rounds through `stage accept`, and the process-tree kill at the deadline. It is exposed as `tim backlog codex run <stageDir>` for people and a Codex-orchestrated session.

- **A stage bound wholly to Codex** runs inside `advance`, in-process. From the step agent's view it is mechanical: `advance` slices it with exit 75 like any long rung. So a `codex`-preset increment needs no Codex stage watcher, no relay and no action watcher: one step agent loops `advance` until its budget hands back. About 2 cheap agents per increment instead of about 58.
- **A span that mixes executors** (for example `codex-review-only`, whose consistency task stays on Claude) returns `run` with the Claude tasks, and one extra Haiku runner agent runs `tim backlog codex run <stageDir>` beside them, so neither waits for the other. That is one cheap agent per mixed span.
- **Why in tim rather than bash** (R8, on merit): the runner's slice, resume and correction logic become vitest-tested JavaScript on a fake Codex binary under `tim/src/test-support/`, instead of a bash script with its own `--self-test`. tim already spawns processes through `exec/exec.js` (execa). Codex is an executable, not a `tools/*.sh` script, so the tim rails allow it. The process-tree kill uses a detached process group per child and `process.kill(-pid)`, covered by the grandchild fixture (C-015).

Inventory's typical increment: 3 repos, 6 registry rungs plus 1 command invariant, F = 12 content-changed files, K = 6 with findings, consistency findings present, 1 fix round, the audit approves first time, `main` moved in one repo, 3 shards green, CI green, Claude preset.

| | Before (per-action) | After |

A clean increment (no findings) is 29 judgement tasks and 4 step agents: M2, M3, M5 and M6. The J3 span runs only the 25 reviews, M4 is skipped because no fix ran, and the step agent after J3 goes straight into M5's proving.

**The floor.** A step agent is spent only where a mechanical step sits between two judgement stages, and the J spans already merge every boundary that has none. With 5 judgement spans in an increment, 5 gaps is the minimum under the runtime fact that only an agent can issue a command.

### 4.3 The workflow script

`backlog-build.js` becomes thinner than 7.2 describes:

1. Take `firstStep` from args (computed by the main session).
2. On `run`: check the count and sha (C-070); walk the span's graph (3.2), spawning Claude tasks through the Claude adapter, and one Haiku Codex runner when the span mixes executors (3.5).
3. Spawn a step agent (3.1) and read its step.
4. On `handback`: spawn a fresh step agent. On `stop`: return.

There is no `act` branch in the script: the step agent runs the outward calls itself, so no act ever costs a spawn of its own. The agent ceiling rule stays (7.2), counting judgement tasks and step agents alike.

## 6. The safety line, decided on merit

Visibility to guard-bash, the auto-mode classifier and the allowlist comes from the **Bash call boundary**, not from how many agents there are. So an outward action can be its own visible call inside the one step agent, at no extra spawn.

| Action | Decision | Why |
|---|---|---|
| Fetch, `merge-tree` probe, local merge of base (abort and hold on conflict), branch cut, baseline and ladder rungs, secrets scan, manifest, receipts, audit, report, handover, local commits, wip commits, local stash under `local` delivery, the state commit | **tim, in-process** | Local and reversible. Tested on git fixtures (`test-support/git-fixtures.js`: `createBareRepo`, `pushCommit`, `createFatClone`). The COMMIT RULE (by name, never `git add -A`, `-F`, the trailer from args) and the rung rules (a `script` rung must be committed and unchanged at HEAD, C-067) become tested code. This **revises C-042's "tim runs only read-only git"** for local writes. C-042's actual reason, that the classifier and guard-bash must see each push, PR and merge, still holds in full: those stay visible calls. The rule becomes: tim never pushes, never opens or merges a PR, and never writes to Jira itself |
| `git push`: increment branches and the state branch | **Its own visible Bash call per repo**, in merge order, generated by tim, run verbatim by the step agent: `git -C <tilde repo> push -u origin refs/heads/<b>:refs/heads/<b>` | Hard to reverse, starts CI and exposes code. Guard-bash and the classifier see the refspec and the branch. The branch proof that `pre-push-check.sh` gave (on `<b>`, not `main`, the refspec names it) moves into tim: `advance` checks it, and checks that the push is a fast-forward of the observed remote ref, before it emits the command, and emits nothing otherwise. The refspec form cannot push `main` or force, whatever the checkout does between check and push. The sync merge's push is deferred to land, so a sync never needs a push of its own |
| Draft PR create or reuse | **Its own visible call**, `tim github pr ensure-draft …` through octokit | Library-first is a tim rail, so not `gh` and not `tools/*.sh`. The call names what it does, so the classifier can judge it. A PR is visible to the team but reversible (close it). Idempotency (reuse an open PR; exit 3 when only a merged or closed one exists) is tested code with undici MockAgent. tim emits the call only where it observes no open PR, so later increments of a programme usually emit none |
| Waiting for CI | **tim, in-process** (`ci-wait`, octokit, sliced with exit 75) | Read-only. SonarCloud arrives as a PR check. `scripts/sonar/sonar-check-pending.sh` is dropped from the pipeline: it reads records the push hook writes, and that hook never fires for `git -C` pushes (C-042), so it could only ever report nothing |
| PR merge (`per-increment` only) | **Its own visible call per repo**, `tim github pr merge --repo <slug> --number <n> --expect-head <sha>`, in `consumes` order, only after every PR is green and approved where required; never inside a tim macro | The least reversible action, on a shared `main`. `--expect-head` makes a merge of anything but the proven head impossible. It is not allowlisted, so the classifier judges each one |
| Jira create and transition | **Its own visible call**, `tim jira create` in M1 and `tim jira transition` in M6, through `jira-client` | A write other people see, outside the repos |
| Results of outward calls | **By observation, not relay** | On the next `advance`, tim reads the remote ref (`git ls-remote`), the PR (octokit) and the issue (Jira) and records a fact. ## 8. What survives, and how

- **Resume.** `advance` still derives the resume point from persisted state alone (C-002). Each macro is idempotent at the sub-step: a branch that exists is checked out, not cut; a base already merged is not merged again; a rung fact recorded at the same head and tree fingerprint is reused, not re-run; a commit carrying the increment trailer is found, not repeated; a push is observed, not repeated; a PR is found, not created. A step agent that dies mid-span leaves only fact records, so the next step agent continues from the next sub-step. `resumeFromRunId` replays completed agents as before, and a replayed step agent is harmless because every command it issues is idempotent.
- **Receipts and facts.** Model tasks keep `receipt.json` with `acceptMac` (8.1). Mechanical sub-steps gain `facts/<step>.json`, written by tim itself, never by an agent: the command, argv, working directory, exit, duration, log path and sha, heads before and after, and for outward actions the observed remote state. Each is MACed with `build/.accept-key`. Span tasks add `upstreamShas` to their receipts. No agent relays any fact.
- **The done-gate audit** (4.5) gains three checks and loses one. Gains: every mechanical sub-step the stage table requires has a MACed fact record; every outward action is backed by an observed fact; every span task's `upstreamShas` match its upstreams' accepted outputs, and every skipped conditional task's condition is false on disk. Loses: the watcher `--record` entries, which no longer exist. `status done --done-by build` still refuses unless the audit passes.
- **Codex parity (R6).** One stage contract, one stage table, the same spans, the same `when` conditions and the same verification batches for both executors, so task counts per role stay equal. Prompts stay byte-identical apart from the profile block. `compare` gains one measure: cheap Claude agents per increment in each run, from the journal, so the saving R6 exists for is measured. The Codex-orchestrated mode (8.11) becomes simpler: the session runs exactly the step agent's loop (3.1) and runs no separate `run-stage.sh`; a stage bound to Claude stops it with `claude-needed`.
- **Full-stack slices (R7).** Nothing is split by repo. `prepare` cuts the same branch in every surface repo and merges base into each. The plan, implementation, consistency review and acceptance still see the whole slice. `prove` builds every touched repo from its head through the include list. `land` commits every repo, and the pushes and merges follow `consumes` order as one unit.
- **Live standards (R2, R3).** Unchanged. `stage prepare --span` resolves standards per task through `tim backlog standards`, with live paths and audit-only shas. `mustIf` entries narrow a writer's must list to the files it touched, never below what 8.5 requires for them.
- **Neutral backlog (R5).** Spans, batches, budgets and the step agent are run knobs and stage-table data. The backlog carries none of them.
- **Hooks (R4).** Per-call hooks see every outward action as its own call, as before. The session-level gaps are unchanged, and the SonarCloud evidence still comes from PR checks.
- **Tool pin.** The step agent's `${TIM}` is the pinned prefix under `toolPin: launch-commit`. Far fewer tim start-ups happen per increment, because each gap is a few `advance` calls rather than two per action.
- **The agent ceiling.** Unchanged in rule, with a new yield: at about 42 agents an increment, one run of 850 covers about 20 increments. Each avoided relaunch avoids a new run label, `run start`, the launch and a pin check.

## 9. Considered and not adopted

| Idea | Why not |
|---|---|
| Let the last judgement task's `stage accept` also finalise the stage and prepare the next | That is deterministic work run inside a judgement agent's Bash call to save a spawn, which Sam's steer forbids. Its failure modes (a lock, a refused prepare) would also land in an Opus or Sonnet context. Spans (3.2) get the same saving wherever no mechanical step is due, without it |
| Put implement into the plan span | Implement's standards depend on the plan's files, and an added repo needs branch cut, merge and baseline first (stage 9). M2 is a real mechanical gap |
| Run fix-verify beside acceptance, after the proof | Saves one step agent on increments with fixes, but req-065 wants fixes confirmed before the ladder, and a refuted fix would force the whole proof to run again. The proof is the most expensive step in wall-clock; one Haiku spawn is not |
| Batch style and code review of a file into one task | R6 names both reviewers per file as the quality bar, and their personas differ |
| Batch cold readers | Their value is reading one section with no other context (C-050) |
| Group small sources for characterise and extract-verify | The extract verifier's per-unit verdicts depend on one source type's mechanics (`source-types/<kind>.md`); the saving is small and the loss is real |
| Run the critic beside dedupe | The critic judges the final atom set, which exists only after dedupe and ingest; it would count absorbed atoms |
| Let tim push, open PRs or merge inside a macro | The call boundary is what makes them visible to guard-bash and the classifier (C-042). Keeping them as calls costs no agent |
| Detached background rungs that outlive a Bash call | A process outliving its call escapes the per-call guards and the slice discipline. Shards sized under one call (C-019) serve the same need |
