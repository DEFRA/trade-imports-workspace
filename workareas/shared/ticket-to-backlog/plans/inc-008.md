# inc-008 plan: a ticket can be fetched into a workarea and distilled, and distil combines its rows

| Repo | Path | Branch | HEAD |
|---|---|---|---|

Three pieces, one slice, all in the workspace repo:

- **A ticket source kind** for DISTIL, with its extract brief.
- **`tim backlog from-ticket <KEY> [--check] [--workarea <workarea>]`**, which fetches a ticket into a workarea.
- **A combine review** in the distil workflow after the combiner, fed by a read-only **`tim backlog combine-candidates <workarea>`**.

## 0. Decisions

1. **The kind is `ticket`, and its source id is `ticket:<KEY>`** (such as `ticket:EUDPA-832`), following the convention that a source id's prefix is its kind (`repo:`, `confluence:`, `ruling:`). Rejected: the design plan's `jira` kind and `jira:` id, because the row's criteria name "the ticket kind". The provenance brackets in the next row (the intake) should use the same `ticket:` prefix; that is said under risks.
2. **The locator is the rendered ticket file**, `workareas/<workarea>/sources/ticket-<key in lower case>.md`. Beside it, `from-ticket` writes a small JSON record of the ticket key, Jira's `updated` time and when it was fetched, which `--check` reads. Rejected: parsing the `updated` time back out of the Markdown, which is fragile.
3. **The sources file holds one ticket source plus the tests repo, with fixed text.** The sources schema requires at least one repo in `repos` and a non-empty `scope` and `role` on every source, and tim refuses a repo that is not also a `repo:<key>` source. DISTIL's intake rule already puts the tests repo in every programme. So `from-ticket` writes exactly:
   - `repos`: one entry, key `tests`, path `repos/` followed by `TESTS_FOLDER` (`tim/src/build/stack-domains.js:8`, so `repos/trade-imports-ins-tests`).
   - Source `repo:tests`: kind `repo`, locator that same path, scope "every domain's e2e specs and journey flows", role "what is already proven end to end" (the role text the existing `shared/eudpa-774/sources.json` uses for the same source).
   - Source `ticket:<KEY>`: kind `ticket`, locator the ticket file (Decision 2), scope "the whole ticket: description, acceptance criteria, comments, linked Confluence pages and saved attachments", role "what the ticket asks for, and what its comments have changed".
   - `precedence`: `repo:tests`, then `ticket:<KEY>`, as DISTIL's default tiers say (target repos above policy and design documents).
   tim never narrows the tests scope to the ticket's area, because it cannot judge an area (the same reason Decision 7 rejects a judged slug). Narrowing it is intake's, which may edit `sources.json`, and Decision 4 keeps that edit. Rejected: relaxing `repos` to allow none, which weakens a check every existing DISTIL launch relies on.
4. **An existing `sources.json` is kept.** A rerun on a workarea with no built row rewrites the ticket file, its record and its attachments, but never overwrites a `sources.json` the intake may have extended. The result says whether it wrote or kept it. Rejected: overwriting, which loses intake edits.
5. **"A built row" is a row with status `done`.** Outside `--check`, `from-ticket` refuses a workarea whose `backlog.json` has one, naming the workarea and the row ids. The workarea is found by Decision 20, from the key alone, so the refusal happens before any Jira request.
6. **`--check` changes no file and exits 0** whether or not the ticket changed. Its result says changed or not, with both `updated` times. It finds the workarea by Decision 20 before any Jira request. It refuses (not found) when no workarea matches, or when the one that matches holds no ticket record, in both cases before any Jira request. Rejected: exit 1 on change, because a changed ticket is a fact to act on, not a failed check.
7. **Workarea and branch naming is deterministic.** A new workarea is `shared/<key in lower case>-<slug>`, the branch `<prefix>/<KEY>-<slug>`. Prefix: `fix` for a Bug, `feat` for a Story, `chore` for every other type. Slug: the first five words of the summary, lower case, with everything but letters and digits dropped from each word and empty words skipped. When Decision 20 finds an existing workarea, its folder name is kept, and the branch takes its slug from the folder name (the part after `<key>-`), so a summary changed in Jira since never moves the workarea or the branch; a folder named by the bare key has no slug, so the branch takes the summary's. Rejected: a judged slug (such as "address-search-by-country"), because tim cannot judge; the session can still rename the workarea before intake.
8. **Blockers are three plain rules, each owned by its own function, and one function gathers them.** All four live in `tim/src/backlog/from-ticket.js`:
   - one function owns "an inward link whose relation is 'is blocked by' and whose other ticket's status is not Done or Closed";
   - one owns "no acceptance criteria heading": no line in the description that is a wiki heading (`h1.` to `h6.`) or a whole-line bold, whose text starts "Acceptance criteria" in any case;
   - one owns "the ticket's status is Done or Closed";
   - one gathering function calls the three and returns the list of blockers the result carries. It owns no rule of its own.
   Section 10 names the same owners.
9. **Attachments:** image (`image/*`) and PDF (`application/pdf`) attachments are downloaded to `workareas/<workarea>/sources/attachments/`, named by their Jira filename. The ticket file lists every attachment: saved ones with their path, others by name and type as not saved. A download that fails is listed as not saved with the reason, and goes in the result's skipped list, as an unreadable comment or Confluence page already does in `tim refine prepare`.
10. **The renderer is extended, not copied, and the fetch sequence is shared, not copied.**
    - `ticketMarkdown` in `tim/src/commands/refine/ticket-markdown.js` gains optional sections for the parent (summary, status and rendered description), linked tickets (relation, key, status, summary), subtasks and attachments. Each section appears only when the caller gives it, so `tim refine prepare`'s output stays byte for byte as it is (its golden test proves it).
    - The sequence "fetch the comments, find the Confluence links in the description, fetch those pages" moves out of `prepareRefinement` (`prepare.js:119-128`) into one new exported function in `tim/src/commands/refine/prepare.js`, beside `fetchComments` and `fetchPages`, which it calls. It takes the ticket key, the rendered description, the progress log and the skipped list, and returns the comments and pages. It writes the same progress lines in the same order as `prepareRefinement` does today, so refine's output is unchanged. `prepareRefinement` and `from-ticket` both call it. Rule: `.claude/rules/code-quality.md` "When a new class or path mirrors one you are editing, extract the shared part in the same change."
    - `ticket/prepare-plan.js:112-119` and `review/prepare/ticket-file.js:40-47` hold the same sequence but are not otherwise touched by this row, so moving them onto it is a follow-up (section 7).
    - `from-ticket` also uses `refinementFieldsOf`, `commentsMarkdown` and `confluenceMarkdown` as they are.
11. **The Jira client gains attachment download and mime types.** `listAttachments` adds each attachment's mime type (additive, its existing caller ignores it). A new client method returns one attachment's bytes from `GET /rest/api/2/attachment/content/{id}`, mapping errors at the seam like `get` does. Rejected: reading attachments off `getTicket`, which would widen the one shape every Jira caller reads.
12. **The parent is read with a second `getTicket` call** (rendered), for its summary, status and description. A parent that cannot be read is left out and listed in skipped.
13. **Rows gain an optional `touches`**, the code areas the row owns, in the existing `touch` format (`<repoKey>:<path prefix>`). It is the same concept the drafts' `touches` and a theme's `touches` already name, so it keeps that name. The combiner copies each draft's `touches` onto the row it becomes. `combine-candidates` reads it. A backlog written before this has none, so its rows pair only by dependency. Rejected: guessing feature folders from criteria or sources text.
14. **A candidate pair is two `todo` rows** where either:
    - **they share code:** a touch of one is the same as, or inside, a touch of the other in the same repo key (sharing a feature folder means sharing its repo); or
    - **one waits only on the other:** the later row's `dependsOn`, leaving out rows already `done`, is exactly the earlier row, and it has no `externalDependsOn`.
    The result lists each pair once, in file order, with which relation links them and the shared touches. It also counts the rows still to build and names those with no `touches`. `blocked` rows are not candidates: their open question is already a reason to stand alone, and merging one would block the other.
15. **The command lives in `rows.js`**, beside `check` and `next`, because it reads one workarea's backlog the same way. Its logic lives in a new `tim/src/backlog/combine-candidates.js`, beside `shape.js`.
16. **The combine review is its own workflow stage**, "Combine review", between Consolidate and Report:
    1. A light relay saves a backlog snapshot under a new tag and runs `combine-candidates`.
    2. With no candidates, no agent runs. The backlog is untouched, the log says so, and the report says nothing was combined.
    3. Otherwise one think-tier agent follows a new brief, `workflow/distil/briefs/combine-review.md`. It merges each listed candidate unless the rows' notes give a reason to stand alone: an open question the other does not carry, a different code area, or too much for one plan (more than 3 service repos or about 15 criteria). It merges only listed candidates and keeps the earlier row of each pair.
    4. A light check runs `tim backlog check`, `tim distil coverage` and the snapshot compare against the new tag, and sends problems back up to the same send-back limit the combiner has.
    5. Still wrong after that, the run stops with a new stop reason, and every file it wrote stays as the check left it.
17. **The snapshot compare holds the review to its rules.** `tim distil backlog-snapshot` keeps one owner for "what changed since":
    - `--save` also records the ids of rows still to build;
    - `--compare-to` also reports rows added since the snapshot;
    - and each row that was still to build and is now `merged-into`, with the row its notes name. A merged-away row passes only when its notes name exactly one other row id that is still to build.
    A snapshot saved before this change has no to-build ids, so it reports no merged-away rows. The consolidator's existing compare against `before` ignores the added list, because new requirements add rows.
18. **"N rows became M" comes from tim, not an agent:** the rows still to build, counted by `tim backlog check` before and after the review. The workflow passes both counts, and the review's reasons for each row it kept apart, to the report prompt and its result.
19. **The consolidate brief's criteria target rises** from "three to ten" to "up to about 15", because the review merges to that size and the two briefs must agree. The wider "why combining is the default" wording in SKILL.md, DISTIL.md and SHAPE.md stays with the third row of this programme, which owns it.
20. **A ticket's existing workarea is found from the key alone, by one function in `tim/src/backlog/from-ticket.js`.** Both the built-row refusal (Decision 5) and check mode (Decision 6) go through it, before any Jira request. The rule:
    - With `--workarea <workarea>`, that workarea is the one, normalised by `normaliseWorkarea` (`tim/src/backlog/workarea.js:16`). No lookup runs.
    - Otherwise it lists the folders (not files) directly under `workareas/shared/` whose name is the key in lower case, or starts with the key in lower case followed by `-`. The trailing `-` keeps `eudpa-29` from matching `eudpa-294-address-book-link`, and the folder-only rule leaves out files such as `eudpa-296-remaining-plans.md`.
    - **None matches:** outside `--check`, a new workarea is named from the summary after the ticket is read (Decision 7). In `--check`, NOT_FOUND naming the key and saying `from-ticket` has not run for it.
    - **One matches:** that is the workarea, whatever the summary says now (Decision 7 keeps its name and slug). It is checked for a built row, or read for its record in `--check`.
    - **More than one matches:** refused with exit 1 before any Jira request, naming every match and telling the person to pass `--workarea`. Nothing is written.
    Rejected: a required workarea argument on every call, because the row's entry point is the key and nothing else; deriving the workarea from the summary on every call, because a renamed ticket would then write a fresh workarea and skip both the refusal and the record.

What `extract-ticket.md` must say:

- The file is the source. Never fetch the ticket yourself.
- Each acceptance criterion is its own claim. It quotes the ticket's words and cites its criterion number in `ref`: the ticket's own number where it has one, else its place in order.
- The description and background are claimed by `extract.md`'s rules.
- A comment that states or changes a requirement is a claim citing the comment's author and date. One that contradicts a criterion says so in `note`, naming the criterion, so the reconciler weighs it.
- The parent, links and subtasks are context: claimed only where they state a requirement for this ticket.
- A linked Confluence page in the file is claimed by `extract-confluence.md`'s method, in its own part.
- An image attachment is read by `extract-image.md`'s method, a PDF by `extract-document.md`'s. An attachment listed as not saved is a `gap` claim.

What `combine-review.md` must say:

- The default is combine. The only reasons to stand alone are: an open question the other row does not carry, a different code area, or too much for one plan (more than 3 service repos or about 15 criteria).
- Not reasons: "smaller is safer", a layer split, different headings in the source.
- A merge keeps the earlier row. That row takes the other's criteria, requirements, sources, repos (in merge order), touches and open questions, and a note naming what it absorbed.
- The merged-away row keeps its id, becomes `merged-into`, and gains a note naming the row it went into. No id is reused and no row is added.
- Each candidate kept apart gets a note saying which reason holds.
- Only listed candidates are merged. Only `todo` rows change.
- Run the checks the prompt gives until they pass.
