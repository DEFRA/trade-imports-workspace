## 0. Decisions

1. **Open mode is a flag on the existing `tim build branch`, not a new command.** Alternative rejected: a new `tim build open` beside it, which would be a second branch-cutting mechanism next to `runBuildBranch` (`tim/src/build/branch.js:180`). `tim build branch` is already a write command with no dry run: it checks out and cuts branches in repos outside `workareas/`. Open mode stays a write with no dry run, because the row requires the opening commit and a second run is a no-op (decision 4). The programme invariant "dry run or read-only wherever it would change something outside workareas/" is written for new commands; open mode is not one, and section 14 lists how it stands against that invariant. Alternative rejected: a dry-run default with `--confirm`, which would make open mode the only half of `tim build branch` that needs confirming, and adds a path nothing in TICKET.md or BUILD.md would take.
2. **The branch argument becomes optional in the parser, and required again without the flag.** With the flag and no branch, the branch is the envelope's `branch` (backlog.schema.json:49 "Split or ticket backlogs only"). Without the flag and with no branch, the action raises commander's own missing-argument error for `branch` on that command, the same error commander raises today for a required argument. So the message, the help printed after it (`program.js:129` `showHelpAfterError`) and exit code 1 stay as they are today, and test 10 proves it. The one visible change is the usage line in `--help`, which now shows the branch in optional brackets; section 14 lists that against the criterion. Alternatives rejected: a zod USAGE refusal at exit 2 (changes the non-open command's exit code and message); reading the envelope branch in both modes (changes the non-open command's behaviour; criterion: "Without open mode the branch command behaves exactly as today").
3. **The workspace repo joins in open mode only, and goes last.** When the envelope already maps a repo at `.`, that entry is used as it is; otherwise the workspace root is added after the envelope's repos under the key `workspace`. Last because the workspace merges last. Its uncommitted files travel with it, as the existing `wouldLoseWork` rule already says for the workspace (`branch.js:70`). Alternative rejected: requiring the envelope to list the workspace, which the branch lifecycle refuses as a backlog repo (BUILD.md "Branch lifecycle").
4. **"Commits of its own" means commits on the branch that the repo's default branch does not have** (origin's copy when there is one, else the local default; the same start-point rule as `startPointFor`, `branch.js:83`). A branch with none gets exactly one empty opening commit; a branch with one or more gets none. That is what makes a second run a no-op.
5. **The opening commit never takes anything from the index.** The workspace (and any repo already on the branch, which the command accepts dirty today, `branch.js:70-71`) may hold staged files that are somebody else's. The commit is created empty and excludes whatever is staged; the staged files stay staged. Alternative rejected: refusing a repo with staged files, which would block the workspace on every run.
6. **The opening commit runs the repo's own git hooks.** No `--no-verify`. The workspace rules ban bypassing hooks to make a commit pass (`.claude/rules/nightly.md` for nightly runs; CLAUDE.md rule 3's push check for the session). A hook that refuses the commit makes that repo's result fail with the hook's reason; the others still report.
7. **The opening commit's message is a conventional `chore` commit scoped by the envelope's `ticket` when the backlog has one, otherwise by the branch name.** The plan's evidence: every EUDPA-774 repo's first commit was a `chore(<key>)` commit that opened the branch. Wording is the implementor's.
8. **"On origin" is read with `git ls-remote` against the repo's `origin`, never with `gh` or the GitHub API** (programme invariant: no command wraps the GitHub CLI or API; tim/CLAUDE.md "No GitHub in tim"). Each repo reports whether origin has the branch and whether a push is still needed (origin missing the branch, or holding a different head from the local one). When origin cannot be reached, both are reported as unknown with git's reason, and the exit code is unaffected. tim never pushes.
9. **Open mode's new result fields appear only in open mode.** The non-open result keeps exactly today's fields per repo (`branch.js:152-163`), so `renderBranchText` and the JSON envelope of a non-open run are byte-identical to today.
10. **The what-shipped comment is rendered by tim, deterministically, from `derived.json`.** Alternative rejected: an agent writing the comment text as WRITE does descriptions. A deterministic render makes a rerun after merge produce the same comment with only its links changed, which is what makes "update, never add a second" and "links point at main after merge" checkable.
11. **The comment lives in `theme-ticket` as a new step, reached by a new `tim theme-ticket` subcommand.** It takes the workarea and the derived file, reads the ticket key from the backlog envelope's `ticket`, and refuses a backlog with no `ticket`. Dry run by default; `--confirm` posts. Alternative rejected: making the session call `tim jira comment` by hand, which cannot find the earlier comment to update.
12. **The earlier comment is found on the ticket by the comment's own opening heading line, not by a receipt in `workareas/`.** A receipt is lost when MERGE runs on another machine or after a clean, and then a second comment appears. The heading line is fixed text owned by the renderer. More than one comment carrying it is refused, naming the comment ids, rather than guessed at.
13. **Posting and editing a comment stay with `tim jira comment`'s `runComment`** (`tim/src/commands/jira/comment.js:66`), extended with an optional id of a comment to replace. With it, the comment is edited in place and read back by id. No CLI flag is added to `tim jira comment`: nothing reaches one (house rule "Build only what this change makes reachable"). The Jira client gains one method that edits a comment, beside `addComment` (`jira-client.js:503`), through the existing `sendJson('PUT', …)` used by `updateIssue` (`jira-client.js:548`).
14. **`tim theme-ticket push` refuses the ticket a ticket backlog names.** A ticket folder sits at `<workareaDir>/tickets/<slug>`; when the backlog beside that `tickets/` folder names a `ticket` and the key being pushed is that ticket, push refuses before any request, naming the key and saying the description is a person's. This makes the invariant "a person's Jira ticket description is never overwritten by any step of ticket mode" a check in code, not only a doc rule. Alternative rejected: relying on the skill text alone.
15. **`tim theme-ticket start` reports the backlog's `ticket`** (null when the backlog has none, or there is no backlog), so the skill branches to the ticket-owned path from data rather than from the phrase. The mode list does not change.
16. **Ticket mode's commit scope is the ticket key.** TICKET.md tells the session to pass `scope: '<KEY>'` in the loop args, so `tim theme-ticket derive --theme <KEY>` finds the row commits (`derive.js:52-53` matches `type(<scope>):`) on an unthemed backlog (`derive.js:62-64`, SKILL.md "A backlog with no themes").
17. **Ticket mode stops at green.** Settled by Sam on 25 November (row notes): it raises pull requests and waits for his go. No rule 3 exemption. The open question in the row is answered by that note.
18. **TICKET.md pushes with the fully qualified refspec** (`git -C <repo> push origin refs/heads/<branch>:refs/heads/<branch>`), as the branch lifecycle's land stage does (workflow README "The branch lifecycle", Land), never `-u`. The branch is cut `--no-track` so a bare push can never land on `main`.
18a. **The session commits and pushes the workspace before the end steps.** Under the branch lifecycle the land stage commits only `openspec/` in the workspace and never pushes it (`increment-build-loop.js:4706-4711`: "Do NOT push the workspace … Anything else changed in the workspace … is the orchestrator's to commit"), and anything else a row writes there comes back in the run's `leftUncommitted` (BUILD.md:1412-1413). So once the loop drains, TICKET.md and BUILD.md's end-of-run subsection have the session commit the `leftUncommitted` workspace files by explicit path, then push the workspace branch with the fully qualified refspec, before the pull request descriptions and the out-of-draft step. The what-shipped comment runs only after that push, because its spec links (`derive`'s `files[].url`, `blob/<branch>/openspec/…`) must point at files GitHub has. Alternative rejected: leaving the workspace push to the merge step, which leaves the workspace pull request holding only the opening commit while the checks are watched and the comment links to missing files.
19. **Claims checked against the tree.**
    - `tim build branch` "cuts branches across the envelope's repos today": holds (`branch.js:180-201`).
    - The branch lifecycle "refuses the workspace as a backlog repo" and the preflight refuses a repo on the branch with no open PR: holds (BUILD.md `no-open-pr` row, line 1192). So the workspace needs a branch and a PR, as the plan says.
    - `tim jira comment` exists and dedupes identical text (`comment.js:75-78`), but the client has no way to edit a comment: confirmed, so the client gains one.
    - `theme-ticket` already handles an unthemed backlog with `--theme <scope>` and squash merges with `--commits-from` (SKILL.md lines 267-273; `derive.js:62-64`): holds, so the comment path reuses derive unchanged.
    - "The skill's references" for intake already exist (inc-009 landed `ticket-intake.js`, `intake/briefs/read.md`, `refute.md`): holds. `docs/reference/worker-references.md` lists neither intake brief: confirmed missing.
    - SHAPE.md says nothing about combining (`grep -n -i combin` finds no line), though DISTIL.md:356 points at it for that rule: a broken pointer this row fixes.
    - "No lighter path" appears in SKILL.md:69, DISTIL.md:294 and workflow/README.md:46: confirmed.
20. **Onboarding decks.** `docs/onboarding/02-ticket.md` and its generator source `docs/onboarding/generator/skill-specs.js` say "implement EUDPA-1234" starts the `ticket` skill, which this row makes untrue. Both are edited (the `.md` by hand to exactly the text the generator would now emit). Regenerating the `.pptx` decks and the walkthrough deck is a follow-up (section 7): the generator rewrites every skill deck at once, a binary churn far outside this row.

## 3. New files

**`.claude/skills/requirements-pipeline/references/TICKET.md`**
- Owns ticket mode end to end, for the main session: entry, intake, questions, branch and pull requests, launch, the end, the ticket, escalation, and what it gives up against DISTIL.
- Why not part of an existing file: DISTIL.md and BUILD.md each own one phase; ticket mode spans both and adds steps neither has (opening the branch, the pull request end, the ticket comment). The plan names it (plan §8).
- Structure to follow: `references/DISTIL.md` ("Who does what" table first, then numbered sections), with each command in a fenced block, in the order it runs.
- Sections, in order, each naming its command or `gh` step:
  1. Entry: trigger phrases; `tim backlog from-ticket <KEY> --json`; the workarea and branch it names.
  2. Intake: the `Workflow` launch of `workflow/ticket-intake.js` by `scriptPath` with its args (the config table in `workflow/README.md`); what it returns; reruns keep ids.
  3. Questions: one batch, plain words, headlines not ids, each with a default; which hold the launch; an answer is a ruling in `sources/ruling-sam-<date>.md`, then the intake runs again.
  4. Escalation: the signals and what happens (stop, ticket-refiner, or DISTIL on the same workarea with `tim distil reset --stage reconcile` then `distil.js`); only before the first row lands.
  5. Before the launch: `tim backlog from-ticket <KEY> --check --json`; a changed ticket reruns the intake.
  6. Branch and pull requests: `tim build branch <workarea> --open --json`; for each repo it reports as needing a push, `git -C <repo path> push origin refs/heads/<branch>:refs/heads/<branch>` (the pre-push gate runs); for each repo with no open pull request, `gh pr create --draft --repo <github> --base main --head <branch> --title … --body-file …`, with the draft body's template (what the ticket is for, the sibling pull requests, that the build loop fills it in); `gh pr list --repo <github> --head <branch> --state open` to confirm one per repo.
  7. The ticket at start: `theme-ticket` START (status to In Dev); the loop claims it.
  8. Launch: the `Workflow` launch of `increment-build-loop.js` with `lifecycle: 'branch'`, `branch` from the envelope, `scope` the ticket key, every Jira key, `requireApproval` and `approvalWaitMinutes` `null`, `repos` the envelope's, `stopAfter: 'all'`; points at BUILD.md "Branch lifecycle" for the rest.
  9. The workspace after the drain (decision 18a): commit each path the run's result lists in `leftUncommitted` with `git -C . add -- <paths>` then `git -C . commit -m … -- <paths>`, never `add -A`, `commit -a` or a commit without a pathspec; then `git -C . push origin refs/heads/<branch>:refs/heads/<branch>` (the pre-push gate runs). Step 6 writes its per-repo push with `<repo path>`, never `git -C .` literally, so this is the first line of the file that pushes the workspace by `.`.
  10. The end: each pull request's description to `docs/best-practices/pull-requests.md` (`gh pr edit <n> --repo <github> --body-file …`); `gh pr ready <n> --repo <github>` unless the theme signed-off check made them drafts (then report the hold and stop); then the what-shipped comment at drain (`theme-ticket`: derive with `--theme <KEY>`, the comment step dry run, then `--confirm`), which runs only after step 9's push; `gh pr checks <n> --repo <github> --watch` as a background task, never polled; when every check is green, post the links and evidence and stop for the go (rule 3; Sam's ruling of 25 November).
